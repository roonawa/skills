# Linux共有版のデータ保持更新

## 目的と適用範囲

既存のSITE EXAMを更新し、サイトID・履歴・暗号化済み認証とその復号キー・利用者・接続設定を引き継ぐ。新規インストールやサイトへの操作テストではない。

最初に [更新手順](references/update-runbook.md) を読み、実環境の配置先・Composeプロジェクト名・マウントを特定する。記載されたパスやサービス構成は例であり、実機を調べず流用しない。

ユーザーが手順案内を求めている場合は、実行場所（Windows PC／Linuxのrootシェル）を明記して一段階ずつ案内し、出力を確認して次へ進む。実行を依頼され接続手段がある場合は許可された範囲を実施する。SKILL作成の依頼だけでLinuxへの接続・更新を始めない。

## 保持する不変条件

- 既存のComposeプロジェクト名とデータの実マウントを維持する。別名で起動して空のボリュームが生成された状態を移行成功と判定しない。
- `deploy/.env`、`deploy/secrets/key`、`deploy/secrets/users.json`を更新ZIPやサンプルで置き換えない。キーの再生成、利用者の初期化、`init-pilot.mjs`の再実行をしない。
- `/data`（サイト、履歴、認証、AI設定）、`/policy`、proxyの`/data`・`/config`を保持する。名前付きボリュームに限らずbind mount・外部保存先も棚卸しする。
- `docker compose down -v`、volume prune、system prune、`rsync --delete`、保存先の再帰削除は更新手順に使わない。
- パスワード・APIキー・Cookie・復号内容・環境変数一覧をチャットや公開ログに出さない。`docker inspect`全体や`compose config`の出力も保護ファイルに保存し、必要な非機密項目だけ表示する。
- バックアップは機密データを含む。rootのみが読める保存先を使い、配布ZIPに混ぜない。失敗・不完全なバックアップで配置・切替を進めない。
- 稼働中の検査・AI補完・ログイン保存・回収処理を中断して更新しない。短い保守停止を提示し、既存の許可に従って進める。許可されていない停止時間やデータ巻き戻しが必要な場合にだけ確認する。

## 実施順序

1. 現行の起動情報・データ対応表と更新前のサイトID／件数／代表履歴を記録する。
2. 更新ZIPの出所、SHA-256、内容、現行との差分を確認。安全な別ディレクトリへ展開し、MANIFEST/SHA256SUMSを照合する。
3. 保守停止後、プログラム・秘密情報・全永続領域・旧イメージをバックアップし、読み出し・展開検証する。
4. プログラムのみ更新。Compose/Dockerfile/Caddyfileなどは差分を確認して環境設定を保持しつつ更新する。初期設定ファイルは上書きしない。
5. 現行と同じプロジェクト名で構成検証・ビルド・起動する。ビルド成功だけで完了としない。
6. [引継ぎ検証・切り戻し](references/verification-rollback.md) の成功条件を確認。失敗したら新規登録やキー再作成で取り繕わず、原因を調べ切り戻す。
7. 更新した版、保持した保存先、バックアップ場所、確認結果、未確認事項、ロールバック方法を報告する。Linux実機を触っていなければ「手順作成のみ」と明記する。

## 追加の判断基準

- 管理画面のセッション失効はデータ消失と分ける。暗号化データが存在していても期限切れなら再ログインが必要。AIキーの検証目的で有料APIを呼び出さない。
- 起動確認のために注文・問い合わせ・テスト投稿を実行しない。まず読み取りとUI確認を使う。
- 現行より古い構成でqa/proxyだけが動いている場合もある。最新のegress・chromium・firefox追加を無視しない。ネットワーク隔離を外して起動を通す方法は採らない。
- Dockerfileが`deploy/user-manual.html`等をイメージへコピーしているか実物で確認する。ローカルにマニュアルがあってもコンテナー内に存在するとは限らない。不足時は必要ファイルを明示追加し、`deploy/secrets`を含むディレクトリ全体をCOPYしない。
