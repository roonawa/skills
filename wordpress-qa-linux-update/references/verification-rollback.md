# 引継ぎ確認と切り戻し

## 更新完了の判定

「Up」だけでは完了としない。

1. 全必須サービスが継続稼働し、再起動ループ・復号失敗・権限エラーがない。
2. 同じComposeプロジェクト、qa:/data、qa:/policy、proxy:/data・/configの実マウントが維持されている。キー・利用者ファイルのバイト列がバックアップと一致している（中身は表示しない）。
3. 既存の利用者とパスワードでHTTPS接続できる。証明書の警告が増えていない。匿名アクセスは認証が要求される。アプリの4310番やワーカーの3000番を新たに外部公開していない。
4. 更新前のサイトID・サイト数・代表サイトの履歴IDと件数が一致。過去HTML・画像・結果ダウンロードを開ける。新規サイトとして登録し直さない。
5. 保存済み認証・AI設定・許可接続先の登録状態が保たれる。認証値そのものを表示しない。WPの認証済み読み取り確認を行う場合は有効期限切れと復号失敗を分ける。
6. 配置済みファイルと起動中イメージの両方が更新版。コンテナー内の対象プログラムのハッシュを配布MANIFESTと照合する。今回なら非同期認証とストリーミング配信を含む版を確認。
7. 設定画面・ヘルプ・画像・報告書のリンクが動く。ヘルプの画像は埋め込みのためHTMLが配備されていることも確認。
8. 別途認められた場合だけ、既存の読み取り専用検査を少数実行。注文・メール送信・投稿作成は更新確認のためには行わない。

ログは必要な範囲で確認し、認証情報・サイト入力内容が含まれ得る全文を共有しない。バックアップは保守終了後も決められた期間保持し、このSKILLは自動削除しない。

## 失敗時の判断

### 起動前／データ形式変更なし

新サービスを停止し、バックアップした旧プログラム・Compose・.env・secretsを別の空ディレクトリへ展開して内容を確認する。元の配置先にプログラムと設定を戻す。旧Image IDを使う復旧用Compose overrideを作り、各サービスの`image:`を保存済みタグに固定する。`--no-build`で起動し、再ビルドで「旧版らしい新イメージ」を作らない。

旧環境に存在しなかったegress等が残る場合は、新版の構成で対象サービスを停止したことを確認する。既存データの削除・volume削除は行わない。同じプロジェクト名と元のマウントを使い、更新前のUI確認を再実施する。

### 新版がデータを変更した／後方互換性なし

単純なイメージ差戻しでは復旧できない可能性がある。まず新版を停止し、失敗時点のデータも別バックアップへ保全する。更新後の新規サイト・結果・入力を失う可能性と対象時間を説明し、巻戻しが既存許可に含まれなければ承認を得る。

元ボリュームを消去せず、新しい復旧用ボリュームへ停止時バックアップを展開する。所有者・ACL・xattrを保存して復元し、旧Composeの復旧用overrideでそのボリュームを明示指定する。初回起動による外部操作やログインを避け、既存データとの整合性を確認する。

復旧用マウントに切り替えた場合は、プロジェクト内の論理名・元の実ボリューム名・復旧用実ボリューム名を記録し、通常運用へ戻した後の次回更新でも新しい実測値を使う。元ボリュームや失敗時データは自動削除しない。

## 最終報告のテンプレート

- 対象ホスト・配置先・Composeプロジェクト名（機密値なし）
- 更新ZIP名・検証したSHA-256・新旧Image ID
- 停止／再開時刻、バックアップ先と検証結果
- サイト・履歴・認証登録状態・証明書・外部接続設定の引継ぎ結果
- 実施した動作確認と未実施の範囲
- 切り戻し用の旧イメージ／構成／保存領域の対応表
- 成否と、ユーザー側の追加対応が必要な場合は具体的な箇所

「ファイルをコピーした」「ビルドが成功した」「コンテナーがUp」だけを完了報告にしない。サーバー接続がない場合は、現地更新・引継ぎは未検証と明記する。
