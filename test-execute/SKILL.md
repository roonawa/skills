---

## 目的

テスト仕様書（spec-test／dev-test出力のTC-ID形式Md）を渡されたときに、そこに列挙された各テストケースを実際に**実行**し、結果を確定させるスキル。対応言語は当面C#とJavaのみ（他言語は将来追加予定）。

- テスト仕様書の「期待結果」を正として、実装が実際にその通り動くかを自動テストで検証する
- 自動化できるTCは既存テストを実行、無ければ新規作成して実行する（新規／編集はテストファイルのみ。実装コードは一切変更しない）
- 画面目視・実機・外部環境が必須でそもそも自動化に向かないTC、技術的に自動化を断念したTCは、**手動確認が必要な項目**として再現手順付きで洗い出す
- 期待結果と実際の結果が食い違う場合は🐛実装疑義として明示する（テスト仕様書側の期待結果が間違っている可能性も排除しない）
- 結果をHTMLレポート（Artifact）にまとめる

「テストを実行して」「このテスト仕様書の内容を確認して」と渡されたときに起動する。test-verify／uat-verifyのような**不具合修正の裏取り**が目的ではなく、**テスト仕様書に基づく網羅実行**が目的である点が異なる。

## スコープ

### やること
- テスト仕様書の読み込みとTC一覧化（spec-test／dev-test両方の列フォーマットに対応）
- 各TCの自動実行可否判定（自動化対象／手動確認／対象外の3分類）
- 自動化対象TCについて、既存テストを探して実行。無ければ新規作成して実行（テストファイルのみ新規・編集可）
- 期待結果と実際の結果の照合、不一致は🐛実装疑義として明示
- 自動化できないTCの手動確認リスト化（再現手順を明記）
- 実行結果のHTMLレポート発行（Artifact）

### やらないこと
- **回帰テスト**（修正前へのrevert→失敗確認→復元のような検証サイクル、既存テストスイート全体の実行）はやらない。1回の実行結果のみで判定する。既存実装への副作用まで確認したい場合はtest-verify／uat-verifyを別途使う
- 実装（プロダクション）コードの修正。🐛実装疑義は指摘のみで、コードは書き換えない
- 性能・セキュリティ・UIレイアウトなど、そもそも自動テストに向かない観点の代行実施（手動確認項目として明示するのみ）
- テスト仕様書自体の新規作成・改訂（→ spec-test／dev-testを使う）
- 工数見積もり

## 想定する入力

1. リポジトリのパス（アクセス権：**新規ファイル追加・既存ファイル編集は「テストファイルのみ」**。実装コードは一切変更しない）
2. テスト仕様書のパス（spec-test／dev-test形式のMd。TC-ID・種別・手順・期待結果に相当する列を含む想定）
3. 実装コードが格納されているフォルダのパス
4. 仕様書が格納されているフォルダのパス（要件定義書／基本設計書／詳細設計書など。テスト仕様書の期待結果があいまいな場合の裏取りに使う）

4点のうち欠けているものがあれば起動時に確認する。指示文が「これも実行して」等、短い場合は直前と同じ手順の繰り返しを意味するので、毎回全ステップを省略しない。

## 全体フロー

```
1. 入力4点の確認
   ↓
2. テスト仕様書の読み込み・TC一覧化
   ↓
3. 各TCの分類（自動化対象／手動確認／対象外）
   ↓
4. 自動化対象TCごとに：既存テスト探索 → 無ければ新規作成（テストファイルのみ）
   ↓
5. 実行し、PASS／🐛NG（実装疑義）を記録（revert検証・回帰テストは行わない）
   ↓
6. 手動確認TCの再現手順を作成
   ↓
7. HTMLレポート作成・Artifact発行
   ↓
8. チャットに要点とArtifact URLを短く報告
```

## 1. 入力の確認

4点（リポジトリ、テスト仕様書、実装コードフォルダ、仕様書フォルダ）が揃っているか確認する。実行対象を全TCとするか一部TC-IDに絞るかも確認する。

## 2. テスト仕様書の読み込み

「## 3. テストケース」相当のMarkdown表を解析し、TCごとに以下を展開する：

- TC-ID
- テスト名
- 種別（画面／I/F／内部ロジック／対象外）
- 手順
- 期待結果（spec-test形式では「期待結果」列、dev-test形式では「期待結果（あるべき値）」列。実装の現状動作列がある場合はテスト作成の参考にせず、期待結果側のみを正として扱う）
- 上流ID／RS-ID（あれば）

種別が「対象外」のTCは実行・確認いずれも行わず、対象外リストに記録するだけにする。

## 3. 各TCの分類

| 分類 | 条件 | 扱い |
|---|---|---|
| 自動化対象 | ロジック・API呼び出し・DB操作など、コードから直接呼び出して結果を検証できる | JUnit/xUnit等で実行 |
| 手動確認 | 画面表示・レイアウト・操作感などUI目視判断が必須 | 再現手順のみ作成 |
| 手動確認 | 外部システム・実機・本番相当環境が必要で、開発環境から到達不可 | 再現手順のみ作成 |
| 手動確認 | 性能・セキュリティなど自動テスト範囲外の専門観点 | 再現手順のみ作成 |
| 手動確認 | 自動化を試みたが、環境構築コスト等の理由で技術的に断念した | 断念理由を明記して再現手順を作成 |
| 対象外 | テスト仕様書側で種別が「対象外」と明記済み | 実行・確認いずれも行わない |

判定に迷う場合は自動化対象側に倒して試みる。実行時に技術的に不可能と判明したら手動確認に振り替え、その経緯を正直にレポートに残す（判定を誤魔化さない）。

## 4. 既存テストを探す。無ければ作る

まず既存テストを探す（`find`、`grep -rn "対象クラス名"`）。見つかったら実際に**実行する**。無ければ、そのモジュールの既存の作法に沿って最小限のテストを新規作成する（同じディレクトリ内の他テストファイルを真似る）。

**テスト仕様書の「手順」「期待結果」をそのままコードに落とすことに集中する。実装の出力を後からトレースして期待値を書き換えない**（期待結果が実装と食い違う場合はテストをFAILさせたままにし、🐛実装疑義として記録する）。

期待結果があいまいで判断できない場合は、仕様書フォルダ（要件定義書／基本設計書／詳細設計書）を読んで裏取りする。それでも判断できなければ「⚠要確認」として利用者に確認する。

### Java (Spring / Mockito / JUnit5)
- `protected`フィールド＋同一パッケージ配置でリフレクション無しに差し替え可能
- `@InjectMocks` + `@Mock`で依存Behaviorをモックし、狙った例外／戻り値を注入する
- `src/test`が無いモジュールでも、親pom.xml（またはGradleルート）に`spring-boot-starter-test`相当があれば使える
- マルチモジュール構成で依存モジュールが`.m2`に無い場合、先に`mvnw install`（Gradleなら`./gradlew publishToMavenLocal`）する
- Maven実行はPowerShellツールを使う（Bashツールにはmvnが無いことが多い）。`JAVA_HOME`は対象プロジェクトが要求するJDKの実パスに合わせる

### C# (.NET / xUnit)
- `dotnet test`が可能。NuGetキャッシュ（`~/.nuget/packages`）に必要パッケージが無ければ取得できるか確認する
- `private static`メソッドでもソース変更せず`MethodInfo`（リフレクション）で直接呼べる。`ProjectReference`で対象を参照する専用テストプロジェクトを作る
- 既存にテストプロジェクトが無いモジュールも多い。無ければ`dotnet new xunit`相当の最小csprojを新規ディレクトリに作る

### DB・SQLが絡む場合
本番同等DBに到達できないことが多い。到達できない場合のみ、使い捨てのDockerコンテナ（既存コンテナとは名前・ポートを分離）に、対象SQLが参照するテーブル・カラムだけの最小スキーマ（型は実DDLに合わせる）を作り、合成データで実行する。検証後は必ずコンテナを`docker rm -f`で削除する。個人情報・機微データは使わず、合成データに置き換える。

いずれのスタックでも、対象の関数・SQLが実際に機能から呼ばれているか（デッドコードでないか）を`grep`で確認しておく。

## 5. 実行して記録する（revert検証・回帰テストは行わない）

テストを1回実行し、結果をそのまま記録する。「このテストが本当にバグを検知できる設計か」を確認するrevert検証（test-verify／uat-verify参照）や、既存テストスイート全体の実行は**本スキルでは意図的に省略する**（トークン節約を優先し、対象TCの実行結果のみで判定する）。

- 期待結果と実際の結果が一致 → **PASS**
- 期待結果と実際の結果が不一致 → **🐛NG（実装疑義）**として記録。テスト仕様書側の期待結果が誤っている可能性も排除せず、判断が難しい場合はその旨を明記する
- ビルドが通らない・環境起因で実行自体ができない → 分類を「手動確認」に振り替え、断念理由を明記する（実行不可を隠して自動化対象のまま残さない）
- 数値・ログは実行結果をそのまま貼る。要約して作文しない

## 6. 手動確認TCの再現手順を作成する

自動化しなかった各TCについて、テスト担当者が実機・画面で手動確認するための具体的な手順を明記する。画面操作が必要なら画面遷移・入力内容を、DB操作が必要ならSQL文・操作手順を具体的に記載する。なぜ自動化しなかったか（UI目視／外部環境必須／技術的に断念）も併記する。

## 7. HTMLレポートを作成してArtifactとして発行する

`templates/report.html`を土台にする。Writeツールでファイルをコピーしてから中身を埋める（プレースホルダ`{{...}}`を全部実データに置き換える）。

- 数値・ログは実際の実行結果をそのまま貼る
- 🐛NGが1件以上ある場合のみ`.decision-banner`を有効化する（実装疑義があるため、利用者の判断が必要なことを明示。無ければ削除する）
- 発行前に`artifact-design`スキルの規約（ライト/ダークテーマ両対応、`body`に明示的な背景色等）を守る。このテンプレートは対応済みなので、色を追加する場合は既存の`--変数名`を再利用する
- favicon: 実行系の確認レポートには🧪を使う（同じレポートを再発行する場合は同じfaviconを保つ）
- title: 「〇〇テスト実行結果」のような、対象テスト仕様書が特定できる短い名前にする

## 8. チャットへの報告

Artifact発行後、チャットには短く要点だけ書く：

- 対象テスト仕様書のパス、実行対象TC数
- 自動実行件数（PASS／🐛NG）、手動確認件数、対象外件数
- 🐛NGがあれば冒頭で目立たせる
- 新規作成したテストファイルは**未コミットのまま残す**こととそのパスを明記する（コミットするかはユーザー判断。指示されない限りgit add/commitしない）
- Artifact URLを明記する

## 注意事項

- **実装（プロダクション）コードは絶対に変更しない**。新規作成・編集はテストファイルのみ
- **回帰テストは対象外**。既存テストスイート全体の実行、修正前へのrevert検証は行わない。既存実装への副作用まで確認したい場合はtest-verify／uat-verifyを使う
- **絶対にテスト結果を偽造しない**。実行できなかったものは手動確認へ振り替え、断念理由を明記する
- **期待結果を実装の出力に合わせて書き換えない**。食い違いは🐛実装疑義として残す
- **個人情報・機微データはテストデータに使わない**。合成データに置き換える
- **ユーザーの指示がない限りコミットしない**
- 一度に複数TC-IDを連続依頼された場合も、毎回全ステップを省略しない
- 使用したテストデータは、ルートフォルダ直下の'QA/test-data'にまとめる。既存のテストデータがある場合はそのフォルダを使う
