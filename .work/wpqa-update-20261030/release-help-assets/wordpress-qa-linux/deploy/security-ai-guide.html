安全対策・AI補完版 更新と利用ガイド

配布識別子：2026-10-29-security-claude ／ 社内LAN・VPN内の少人数向け

配布物にAPIキー・ログイン情報・登録サイト・テスト結果は含みません。実際のLinuxコンテナ起動、ブラウザーのサンドボックス、社内TLS、実キーでのAnthropic API接続は導入先で確認してください。コードと構成の改修を実施した段階であり、第三者による侵入試験済みを意味しません。

1. 診断で見つかった問題への対応

診断項目対応確認範囲
SEC01：メール検査への管理者認証の流用管理者用環境変数の指定を拒否。メール専用認証と送信先の完全一致を要求し、転送先には追従しない。回帰テスト済み
SEC02：内部サービスへの任意接続管理者が許可した接続元URLだけを専用プロキシで中継。DNS解決したIPを検査して接続時に固定。ループバック・リンクローカル等は禁止。社内サイトは固定IPも登録。IP判定・API制限を検証。Linuxでのネットワーク隔離は導入時確認
SEC03：ブラウザーと機密情報の同居Chromium／Firefoxを別コンテナへ分離。秘密ファイルや結果のボリュームをマウントしない。Chromiumのサンドボックスを有効化。Compose検証済み。Linuxで起動確認が必要
SEC04：失敗試行による正規利用者の締め出し誤ったパスワードの失敗回数で正しいパスワードを拒否しない。失敗記録の件数も制限。12回失敗後の正規ログインを検証
SEC05：リソース上限不足コンテナのメモリ・CPU・PID制限、Dockerログと監査ログのローテーション。保存量・空き容量を開始前と検査中10秒ごとに確認。設定検証済み。容量チェックは厳密なディスク割当ではなく、停止・後片付け中に超過し得る。ホスト側の容量監視・割当も併用

利用者は引き続き同じサイト・結果を共有します。サイト別権限や外販向けの顧客分離はありません。AI・接続先設定のみ、指定した管理者に制限します。

2. Linux更新：バックアップと配置

この手順は既存配置が /opt/wpqa/wordpress-qa-linux の場合です。実際の場所が異なる場合は読み替えてください。検査とログインの終了を待ち、rootで作業します。旧版の更新ガイドにある「Composeはコピーしない」という扱いは今回には適用しません。

  1. PCから新しいZIPと .sha256 をサーバーの作業フォルダーへ転送します。
  2. 転送先で整合性を確認して展開します。既存配置へ直接展開しません。
mkdir -p /opt/wpqa/update-security-ai
cd /opt/wpqa/update-security-ai
# このフォルダーへZIPと .sha256 を転送した後
sha256sum -c wordpress-qa-linux-2026-10-29-security-claude.zip.sha256
unzip wordpress-qa-linux-2026-10-29-security-claude.zip
cd wordpress-qa-linux
sha256sum -c SHA256SUMS

現在のコンテナを止め、プログラム・設定とデータを別々にバックアップします。バックアップには機密情報があるため権限を制限します。

cd /opt/wpqa/wordpress-qa-linux
BACKUP=/opt/wpqa/backup-security-ai-$(date +%Y%m%d-%H%M%S)
mkdir -m 700 "$BACKUP"
/bin/cp -a . "$BACKUP/program"
docker compose --env-file deploy/.env -f deploy/compose.yaml stop
docker compose --env-file deploy/.env -f deploy/compose.yaml run --rm --no-deps --entrypoint tar qa -czf - -C /data . > "$BACKUP/data.tar.gz"
chmod 600 "$BACKUP/data.tar.gz"
tar -tzf "$BACKUP/data.tar.gz" > /dev/null

tarが正常終了したことを確認した後、新版を配置します。.env、deploy/secrets、Caddyfileは保持します。暗号化キーを作り直さないでください。

cd /opt/wpqa/wordpress-qa-linux
UPDATE=/opt/wpqa/update-security-ai/wordpress-qa-linux
for item in bin lib builtin tests ui Dockerfile .dockerignore package.json package-lock.json playwright.config.mjs; do
  /bin/cp -a "$UPDATE/$item" . || break
done
/bin/cp -a "$UPDATE/deploy/compose.yaml" deploy/compose.yaml
/bin/cp -a "$UPDATE/deploy/browser-seccomp.json" deploy/browser-seccomp.json
/bin/cp -a "$UPDATE/deploy/security-ai-guide.html" deploy/security-ai-guide.html
/bin/cp -a "$UPDATE/deploy/user-manual.html" deploy/user-manual.html
diff -qr "$UPDATE/ui" ui
diff "$UPDATE/deploy/compose.yaml" deploy/compose.yaml

エラーが出た場合は起動に進まないでください。diffが無出力なら該当ファイルは一致しています。

3. Linux更新：管理者設定・ビルド・起動

deploy/.envに次を追加します。管理者名はこのツールに登録済みの利用者名です。WordPressのユーザー名ではありません。

WPQA_ADMINS=実際の管理者名
WPQA_MAX_DATA_MB=8192

複数管理者は半角カンマ区切りです。未登録名では起動を拒否します。APIキーは.envに書かず、起動後に画面で登録します。6GB前後のコンテナ上限合計にOS分を加味し、この構成はメモリ8GB以上を目安に負荷を確認してください。

cd /opt/wpqa/wordpress-qa-linux
docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml build
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
docker compose --env-file deploy/.env -f deploy/compose.yaml logs --tail=60 qa egress chromium firefox

qa・proxy・egress・chromium・firefoxの5サービスを確認します。ブラウザーが再起動を繰り返す場合は、サーバー担当者がLinuxのユーザー名前空間と同梱seccomp設定を確認してください。サンドボックス無効化では回避しません。既存の認証・結果を保つため、down -vは実行しません。

切り戻す場合は検査を止め、今回のコンテナを stop してからバックアップのプログラム・旧Composeを同じ配置先に復元し、旧版をビルド・起動します。データ復元が必要な場合は現状も退避し、同じ暗号化キーと組み合わせて担当者が復元してください。旧版へ戻すと今回の安全対策も戻るため、利用を制限してください。

4. 最初に管理者が設定すること

共有画面にログインAI・接続先の設定接続先を登録保存

更新直後は接続先が未許可です。既存の登録サイトも管理者が追加するまで検査・ログインを開始できません。対象URLのホストに加え、利用する画像CDN、ログイン転送先、メール検証サービスを必要な範囲で許可します。URLはパスを付けず、下記のように1行ずつ入力します。

https://対象のサイト.example
https://画像配信.example
https://社内サイト.example 10.0.0.20
https://api.anthropic.com

社内サイトはDNSが返す固定IPを記入します。IPが変わった場合は再設定が必要です。localhostやクラウドのメタデータIPは許可できません。公開サイトの平文HTTPは許可しません。許可不足はサイト不具合として扱わず、検査条件を整備して再実行します。

メール認証が必要な場合、管理者がサーバー環境にメール専用 WPQA_MAIL_任意名_HEADERS と WPQA_MAIL_任意名_HEADERS_ORIGIN を対で設定します。後者はメールサービスのoriginと完全一致させ、前者はメール用ヘッダーJSONです。管理画面認証を流用しません。機密値をチャットや報告書に貼らないでください。

5. Claude APIキーの設定と利用

旧OpenAI版から更新した場合、AIを無効にして旧キーを使用しません。画面でAnthropicのAPIキーと送信許可を登録し直してください。接続先には https://api.anthropic.com を追加します。古い api.openai.com の許可が不要なら削除してください。Claudeへのログイン情報ではなく、APIキーを入力します。

  1. 管理者が「AI・接続先の設定」を開き、Anthropic APIキーを入力します。
  2. 利用可能なモデル名と1日の呼出回数を設定し、外部送信の許可と「AI補完を有効にする」を選んで保存します。初期モデル名はclaude-sonnet-4-6です。アカウントで利用可能か確認してください。
  3. サイトの登録・設定画面で「AIで不足ケース・準備事項を確認」を押します。初回の登録前にも利用できます。
  4. 候補を確認し、採用するものだけ選んで「選んだ検査を設定に反映」を押します。ログインと他の入力は維持します。
  5. 確認事項の「この項目を設定する」から、既存の設定で期待値を入力します。サイトから取得できる値は既存の再取得機能を使います。
  6. 最後に「保存」→「検査を実行」で実際の結果を確認します。AIの提案だけで合格にはなりません。

自動生成の対象は横はみ出し、登録済みcanonicalの比較、合意済み上限を使った読込時間です。既存の広い確認項目を、狭い検査で置き換えて準備完了にすることはありません。他の設定が必要は確認事項を提案し、既存の設定画面へ案内します。注文・送信・テスト投稿の許可は変更しません。AIは仕様や期待値を勝手に確定しません。

APIキーは暗号化してサーバーに保存し、画面・報告書・ログへ戻しません。送信するのはページ番号・ページ種別・検査種類・準備状況・任意の読込上限です。URL、ページ本文、画像、認証情報、受注・問い合わせ内容は送りません。将来それらを使った診断を追加する場合は別途送信範囲を設計します。

利用回数は全員共通で、失敗したAPI呼出も数えます。UTCの日付変更で戻ります。金額の上限ではないため、Anthropic側のプロジェクト予算も設定してください。Anthropic側の不正利用監視等を含むデータ取扱いは契約・設定によります。構造化出力の公式説明。

AIが無効、キー不正、接続拒否、応答不正の場合は設定を変更しません。通常の検査はAIなしで使えます。実キーで最初の1回を試し、候補・費用・接続状況を確認してから利用者へ案内してください。

6. 更新後の確認

  1. 登録サイト・既存結果が残っている。
  2. 管理者だけがAIキー・接続先を変更できる。
  3. 許可した検証サイトで共有画面からWordPressにログインできる。
  4. 未許可URL・127.0.0.1・169.254.169.254への操作が拒否される（実際の内部サービスを調査しない）。
  5. 読み取り検査を1件実行し、画像と結果ZIPをダウンロードできる。
  6. AIで1回候補を取得し、選択・保存・再表示・検査実行を確認できる。

初回は送信・注文を伴わないサイトで確認してください。この配布物ではAPI応答を模擬したテストを使用し、実課金は発生させていません。
