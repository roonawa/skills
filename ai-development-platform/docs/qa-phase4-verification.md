## 方法

段階2・段階3の確認で作った QA リポジトリ（一時ディレクトリにある写し）に `aidev qa trace` をかけた。段階3のリポジトリを写し、わざと誤りを6つ植えたものも作った。HTML は Claude のブラウザの画面で、明るい表示と暗い表示、幅 375px の表示を見た。aidev-qa-report は、独立したセッション（サブエージェント、Sonnet）が作業者として初めて使う形で試し、日次のまとめと品質レポートを作らせた。

## HTML

- trace の HTML（段階3 Web）は、暗い表示と明るい表示のどちらも崩れない。幅 375px でページの横スクロールは出ない。AC-015 → TC-csv-004〜006 → #1 確認済み → runs/20261119-csv-fix のつながりが表で読める。外部の読み込みはなく、証跡の欄と result.md の自由文は載せていない。

## aidev-qa-report

作業者役のセッションが、段階3 Web の写しで 2026-11-19 の日次のまとめと品質レポートを、誤りを植えた写しで品質レポートを作った。

- レポートの数字は、すべて trace の JSON と一致した。誤りを植えた写しの品質レポートは、冒頭に trace のエラー5件を示した。
- Gitea と C-HUB には接続していない。QA リポジトリにコミットはしていない。
- 元のデータの食い違いを2つ見つけた。csv-fix の result.md の本文には「OK 11」とあるが、表と trace は OK 10。作業者は trace の数を使った。
- Skill の不足として、リスクの表の列の決め方、NG の傾向をどの結果で数えるか、報告日より後の run の扱い、長い TC-ID の一覧の書き方、優先度に関する終了条件を確かめる手段が挙がった。trace の JSON に優先度を足し、Skill に決まりを書き足した。

## 確認で見つかった改善点

各タスクのレビューと全体のレビューで見つかったもののうち、主なもの。どれも同じブランチで直した。

- trace の読み取りの正規表現に、長い行で極端に遅くなるもの（ReDoS）があった。1 MiB 近い行で 10 秒を超えていたものを、正規表現を使わない分け方に変え、数ミリ秒にした。`aidev qa issue create` の読み取りにも同じ形があり、同じく直した
- 改修確認の run 自身の NG で Issue を要確認に戻していなかった。表の行の形の誤りや同じ TC の行の重複が警告だけで、NG を隠したまま終了コード 0 になった。どちらも直した
- 読めないファイルの指摘に、絶対パスを含む Node のエラー文がそのまま入っていた。エラーコードとリポジトリの中のパスだけにした
- 同じ日の run の順（run-id の文字列の順）を書いていなかった。README・設計書・Skill に名前の付け方を書き、実行日時と順が逆のときの警告（run-order）を足した
- 日次のまとめの一部の数が JSON から出せなかった。`runDetails` に run ごとの行（TC-ID・結果・Issue 番号だけ）を足した

残したもの:

- `case-ac` の指摘に cases/ の値を最大 40 文字写す
- `--html` は既存の `.html` を確かめずに上書きする（compare-report と同じ）。README は QA リポジトリの外に書くよう勧めている
- わざと対象外にした AC は ac-uncovered のまま終了コード 1 になる。理由は plan/strategy.md の対象外の節に書き、trace の結果を伝えるときに添える
- 実際の Gitea を使った確かめは、作業者の了承とトークンが要るため、段階4の後に行う
