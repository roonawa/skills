# 基盤の構成
対象はチーム内でレビュー済みの手順を複数プロジェクトへ配布する開発者。原本を skills/core に集約し、CLI がプロジェクト内の .claude/skills と .agents/skills へ同じバイト列を配置する。ホストは description をもとに Skill を選ぶ。CLAUDE.md は AGENTS.md を参照する。プロジェクト固有の制約を作業前に読む。

## 境界
CLI は引数と終了コードを扱い、Registry は同梱 Markdown の列挙と検証を行う。プロジェクト操作は設定のスキーマ版、配置先、二つのコピーの一致を検査する。入力は単一のプロジェクト名または Skill 名に限定する。外部 URL、スクリプト、任意コマンドの登録口は設けない。対象は利用者が管理するローカル作業ディレクトリ。信頼できない別プロセスが同時にディレクトリを置換できる共有場所は対象外。

## 自律開発の流れ
画面開発では要件を仕様書・設計書に落とし、操作モックで利用者と UI/UX を決める。開発者が再利用する部品・型・契約と動く利用例を用意し、AI がその基盤上に画面固有の機能を実装する。Adapter で静的解析・回帰検査・ビルドを行い、AI がセキュリティと仕様乖離・過剰実装をレビューする。3つのゲートを通過した版について開発者のレビューを経て、指摘反映版を対象に受け入れテストを実施する。決定と引き継ぎは aidev-ui-delivery Skill が案内する。ゲート不通過時の差し戻しは人の確認なしで最大3回、同一エラー再発時はその時点で停止し、人の確認を要するタスク（needs-human と引継ぎ票）として返す。テスト削除、検査無効化、仕様変更は禁止。共通基盤への改善提案は別変更として審査する。

## 拡張

修正の開始と終了はホストが判断し、CLI の workflow check が検査と試行数を管理する。CLI はタスク名と試行番号で実行を予約し、検査結果をプロジェクト内に確定する。workflow status は記録を読み取る。セキュリティと仕様のゲートは CLI では判定できないため、ホストの AI がレビュー結果を JSON で渡す。同じ失敗の再発判定には検査項目とエラー署名、レビュー指摘の種類・参照・ファイルを使う。初回から存在するテストファイルや検査設定が失われた場合は再検査を開始せず、担当者へ引き継ぐ。
設定の template で Adapter を選ぶ。各 Adapter はプロジェクトの絶対パスを受け取り、検査名、状態（passed / failed / unavailable）、任意の診断を返す。新たな技術を追加するには src/adapter.ts に関数を登録し、templates 内に配布対象だけを列挙した files.json を用意する。既存の core 設定も読み取れる。

React はプロジェクトの npm scripts を実行する。Unity は Editor バージョンと Test Framework の設定を照合する。EditMode・PlayMode・ビルドの結果伝達は Mock で検査し、実機の XML とログの回収は次の作業に残す。Core のテストには Editor を要求しない。
