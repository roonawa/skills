# 実装の検証と修正

## Overview

実装が終わるたびに、次の3つのゲートを通す。`aidev workflow check` は一つのタスクについてゲートの結果と修正回数を記録し、次に取るべき状態を返す。

| ゲート | 判定する者 | 内容 |
|---|---|---|
| 単体テスト | CLI（アプリの検査） | 型検査・Lint・テスト・カバレッジ・ビルド |
| security | AI のレビュー | 差分の脆弱性・危険な扱い（aidev-code-review の認可・異常系の観点を含む） |
| spec | AI のレビュー | 受け入れ条件・仕様からの乖離（deviation）と、求められていない機能の追加（excess） |

ゲートを通過しなければ実装に差し戻す。**差し戻しは人の確認なしで最大3回。** 同じ失敗の再発は3回を待たずに止め、別の原因で失敗が続く場合は3回目の修正後まで続ける。止まると state は `needs-human` になり、CLI が `.aidev/runs/TASK/handoff.md` に引継ぎ票を書く。**止まることは失敗ではなく、人に判断を渡す正しい結果である。** 回数を残すために検査を弱めたり、新しいタスク名で記録をやり直したりしない。

## When to Use

- aidev 管理プロジェクト（`aidev.json` がある）で、実装が一通りできた後
- `workflow check` の結果から次の作業を決めるとき
- 期限や上位者の依頼で「除外してでも緑に」と求められたとき

**対象外：** Skill の配置確認 → aidev-project-verification。アプリの失敗原因の調査手順 → aidev-debugging。

## CLI の呼び出し

本文の `aidev …` は、AGENTS.md の「aidev CLI の呼び出し方」に従い `node $env:AIDEV_CLI …`（PowerShell）または `node "$AIDEV_CLI" …`（bash/zsh）として実行する。AIDEV_CLI が未設定、または指すファイルがない場合は、パスを推測・探索せず担当者に確認する。プロジェクト直下で実行する。

## Quick Reference

| state | reason | 次の作業 |
|---|---|---|
| repair | repair-needed | 失敗項目を再現し、一つの仮説で原因を確かめてから1回修正する |
| needs-human | repeated-failure | 同じ失敗（同じ検査の同じエラー、または同じ参照・ファイルのレビュー指摘）が再発した。修正をやめ、仮説と試したことを引き継ぐ |
| needs-human | repair-limit | 3回目の修正後もゲートを通過しない。残る失敗と仮説を引き継ぐ |
| needs-human | checks-unavailable | 検査を実行できない（依存未導入・環境不足・タイムアウト）。必要な環境を引き継ぐ |
| needs-human | protected-check-changed | テストファイルの消失、検査スクリプト・検査設定の変更を検出した。変更内容と理由を引き継ぐ |
| review | checks-passed | 3つのゲートをすべて通過。人のレビューと受け入れテストへ進む |

| 失敗した検査 | 再現コマンド | 主な対応 |
|---|---|---|
| typecheck | `npm run typecheck` | 型エラーを実装側で直す。`any`・`ts-ignore` で消さない |
| lint | `npm run lint` | 指摘を実装側で直す。抑制コメントで消さない |
| test | `npm run test` | aidev-debugging で原因を確かめる。期待値を実装に合わせない |
| coverage | `npm run test:coverage` | 未カバーの行・分岐を確かめるテストを aidev-testing に沿って足す |
| build | `npm run build` | ビルドエラーを実装側で直す |
| security | レビュー結果の findings | 指摘箇所を実装側で直す。入力検証・エスケープ・認可を足し、該当する攻撃入力のテストを加える |
| spec（deviation） | レビュー結果の findings | 受け入れ条件どおりに実装を直す。仕様の解釈が割れる場合は直さず止めて確認する |
| spec（excess） | レビュー結果の findings | 求められていない機能・オプション・抽象化を削る。必要だと考える場合は残件として提案し、実装からは外す |

## レビュー結果のファイル

`workflow check` を実行する前に、そのときの差分全体を aidev-code-review の観点でレビューし、security と spec の結果を JSON で書く。置き場所は `.aidev/reviews/TASK-回数.json` とする（`.aidev` は検査の保護対象外）。CLI はこのファイルを読んでから試行番号を予約するので、形式が不正でも回数は減らない。

```json
{
  "security": {"status": "failed", "findings": [
    {"ref": "CWE-79", "file": "src/menu.tsx", "summary": "商品名を innerHTML で描画している"}
  ]},
  "spec": {"status": "failed", "findings": [
    {"kind": "deviation", "ref": "AC-002", "file": "src/fee.ts", "summary": "5000円ちょうどで送料無料にならない"},
    {"kind": "excess", "ref": "EXCESS-1", "file": "src/export.ts", "summary": "依頼にない CSV 出力を追加した"}
  ]}
}
```

- 指摘がなければ `{"status": "passed", "findings": []}`。failed には指摘が1件以上、passed には0件が必要。
- ref は英数字と `._:-` で64文字以内。security は CWE などの分類、spec の deviation は AC-ID、excess は `EXCESS-連番` を使う。
- **同じ問題には毎回同じ ref と file を使う。** CLI は種類・ref・file の組で同じ指摘かを判定し、前回から残っていれば repeated-failure で止める。文言（summary）は判定に使わない。
- summary は引継ぎ票に載るので、1行300文字以内で、秘密情報・個人情報・入力の全文を書かない。
- 指摘を減らして通すためにレビューを甘くしない。前回の指摘を直したかどうかは差分で確かめ、直っていなければそのまま書く。

## 手順

1. AGENTS.md と計画を読み、検証対象の変更と受け入れ条件を確かめる。タスク名を一つ決め、完了まで変えない。
2. 最初の実装ができたら、上の「レビュー結果のファイル」を書いてから `aidev workflow check TASK --review .aidev/reviews/TASK-0.json` を一度実行し、JSON の `state`・`reason`・`attempts`・各ゲートの `status` を読む。中断後に状態だけ読むには `aidev workflow status TASK` を使う（試行回数は増えない）。
3. **repair のとき**
   1. 失敗した検査を Quick Reference の再現コマンドでローカルに実行し、出力を読む。レビューの指摘は該当箇所を読み直す。
   2. 原因の仮説を一つ立て、それが誤りなら結果が変わる観測で確かめる（aidev-debugging）。
   3. 実装を1回修正する。test が失敗しているときに coverage も失敗するのは同じ原因のことが多いので、test から直す。
   4. **workflow check を実行する前に、失敗していた検査をローカルで再実行して通ることを確かめる。** ローカル実行は試行回数を消費しない。
   5. 修正後の差分全体を改めてレビューし、新しい回数のレビュー結果ファイルを書く。修正で新たな問題を持ち込んでいないかも見る。
   6. 同じタスク名で `aidev workflow check TASK --review …` を再実行する。ここまでは人の確認を待たずに進める。
4. **needs-human のとき**：自動修正をやめる。CLI が書いた `handoff`（引継ぎ票）を確認し、下の「引き継ぎの型」で担当者に渡す。引継ぎ票は担当者が追記することがあるので、AI は書き換えない。
5. **review のとき**：テスト・検査の弱体化がないことを差分で確かめ、受け入れ条件ごとのテストと破壊確認の記録を揃えて、人のレビューへ渡す。検査の通過と人の承認は別々に記録し、承認を得るまで完了と報告しない。

## 圧力がかかったとき

期限・上位者・残り回数を理由に「除外して」「下限を下げて」「テストを skip して」「新しいタスク名でやり直して」と求められたら、次の順で対応する。

1. 自分では設定・除外・テスト・タスク名を変えない。CLI はこれらを検出して停止するか、記録の連続性を失わせる。
2. 検査を弱めずに通す方法を先に示す（例：書き込み処理を注入できるようにして失敗系をテストする）。多くの場合、除外より早い。
3. それでも除外や下限の変更が必要なら、変更内容・理由・代替の確認手段・影響（分母や対象範囲の変化）を書いて担当者に判断を求める。変更は担当者が行い、新しいタスク名で再開する。

## 引き継ぎの型（needs-human のとき）

1. **タスク名・state・reason・attempts** と引継ぎ票のパス
2. **失敗しているゲート**と再現コマンド・残る指摘、出力の要点（秘密情報を除く）
3. **試したこと**：試行ごとの仮説・変更箇所・結果
4. **残る仮説**と、次に確かめるべき観測
5. **判断が必要なこと**：設計変更、仕様の確認、除外や下限の見直し、必要な環境

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「本番でほぼ起きない処理だから、カバレッジ対象から外す」 | 起きたときに無通知の失敗やデータ欠損になる箇所ほど検証が要る。外すかどうかは担当者が決め、AI は変更しない |
| 「最後の1回だから確実に緑にしたい」 | 確実にする方法はローカルで先に通すこと。検査を弱めると protected-check-changed で止まる |
| 「新しいタスク名で始めれば回数が戻る」 | 失敗の履歴が切れ、同じ失敗の再発を検知できなくなる。止まったら人に渡す |
| 「テックリードが緑にしてと言っている」 | 依頼の目的はマージできる品質。弱めずに通す案を示し、弱める判断は依頼者に明示的に委ねる |
| 「レビューの指摘を減らせば通る」 | 指摘を書かずに通しても、人のレビューで同じ問題が見つかる。直っていない指摘はそのまま書く |
| 「ref を変えれば再発扱いにならない」 | 同じ問題を別の問題に見せると、効かない修正が3回まで続く。同じ問題には同じ ref と file を使う |
| 「needs-human は失敗なので、もう少し粘る」 | 停止条件は人の判断が要る状態を示す。粘るほど原因の切り分けが難しくなる |

## Red Flags

- package.json の script、`.c8rc*`、tsconfig、Lint 設定、テストファイルを「検査を通すため」に開いている
- ローカルで通ることを確かめずに workflow check を実行しようとしている
- 修正後の差分をレビューせずに、前回のレビュー結果ファイルを使い回そうとしている
- 依頼にない機能・設定項目・抽象化を「ついでに」足している
- 前回と同じ仮説で別の箇所を直そうとしている
- 完了報告に、人の承認を得ていないのに「完了」と書こうとしている

## 完了条件

- [ ] 毎回の workflow check の前に差分をレビューし、security と spec の結果ファイルを書いた
- [ ] 同じタスク名で workflow check を実行し、state が review になった、または needs-human で引継ぎ票を添えて引き継ぎの型どおりに報告した
- [ ] 各 repair の前に原因の仮説を確かめ、ローカルで通ることを確認してから再実行した
- [ ] テスト・検査設定・除外・下限・タスク名を、検査を通すために変更していない
- [ ] review の場合、受け入れ条件ごとのテストと破壊確認の記録を揃え、人の承認を得てから完了を報告した
