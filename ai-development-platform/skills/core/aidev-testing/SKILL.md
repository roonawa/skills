# 動作検証

## Overview

テストは仕様の検証であり、実装の写しではない。期待値は受け入れ条件から決め、実装が返す値とは別に記録する。テストの価値は「その振る舞いを壊したら失敗する」ことで決まり、それは実際に壊して失敗させるまで証明されない。カバレッジは証明ではなく、未検証の箇所を見つける診断材料として使う。

**テストが緑であることは完了条件ではない。** 完了は、受け入れ条件ごとに対応するテストがあり、そのテストが壊した実装で実際に失敗し、元の実装で成功したことを記録した時点とする。

## When to Use

- 機能追加・修正に伴うテストを書く（aidev-implementation から呼ばれる場合を含む）
- 既存テストの不足を調べる、カバレッジ不足を解消する
- 回帰テストが不具合を検知できるかを確かめる

**対象外：**
- 失敗の原因調査 → aidev-debugging
- 配布した Skill の欠損・差異の確認 → aidev-project-verification
- 移行前の現行挙動をそのまま記録する特性化テスト（期待値＝現行出力が正しい場面）。この Skill の「期待値は仕様から」と逆の原則になるため、方針を担当者と決めてから行う

## Core Pattern

**Before**：テストは通り、カバレッジも 80% を超えている。しかし `assert.ok(fee > 0)` は送料が 600 円でも 1 円でも通り、`shipping(x) === shipping(x)` は常に真。5,000 円ちょうどの境界は誰も試していない。

**After**：受け入れ条件「5,000 円以上は送料無料」に AC-ID を振り、4,999／5,000／5,001 円のケースを期待値の定数で書く。5,000 円のテストには品質契約「`>=` を `>` に変えると失敗する」を付け、実際に `>` へ書き換えて失敗を確認し、元に戻して成功を確認する。

## 手順

### 1. 期待値の根拠を確定する

1. 受け入れ条件を `AC-001` から番号付きで列挙する。aidev-requirements の出力があればそれを使い、無ければ依頼文・仕様書から抜き出す。
2. 期待値は受け入れ条件から決める。実装を読んで出力値を書き写さない。
3. 仕様と実装が食い違ったら、期待値は仕様側のまま書き、テストは失敗させたままにする。差異は「🐛実装疑義」として記録し、報告する。テストを緑にするために期待値を実装へ合わせない。
4. 仕様が無く実装しか手がかりが無い場合は、命名・バリデーション・DB 制約・類似機能・既存テスト・エラーメッセージなど実装本体以外の根拠から期待値を推定し、「期待値は推定」「確信度（高／中／低）」を明記する。確信度が低いものは「⚠要確認」として残す。
5. 依頼に書かれていない振る舞い（不正入力の扱い、端数、境界の含む／含まない）は、利用者に見える結果が変わるなら担当者へ確認する。確認できないまま進める場合は「仮定」として報告に列挙する。

### 2. 観点を抽出する

対象の公開入口ごとに、次の表を機械的に当てはめる。該当しない観点は「対象外」と理由を書く。

| 観点 | 確認すること |
|---|---|
| 境界 | 比較演算子ごとに n-1・n・n+1。範囲は両端の内外。`>` と `>=` の向き自体が誤りでないかを疑う |
| 分岐 | if／else、switch の各 case と default、三項演算子、`&&`・`||` の短絡（a=false／a=true,b=false／両方 true） |
| 型・特殊値 | null、undefined、空文字、空白、NaN、Infinity、負数、0、小数、最大長、空配列、1件、複数件 |
| 例外経路 | 例外を投げる条件、握りつぶし（catch してログだけで続行）、エラーが呼び出し元に届くか |
| 状態 | 状態遷移の正常・禁止・同一状態、二重送信・再実行（冪等性）、途中失敗後の状態 |
| 権限 | 許可ロール、禁止ロール、他人のデータへのアクセス |
| 外部依存 | 現在時刻・タイムゾーン・乱数・ファイル・ネットワーク。注入して固定する |
| 組み合わせ | 複数の条件が同時に成立するとき（例：会員割引と金額割引の併用、適用順） |

### 3. テストケース表を作る

テストコードより先に、次の欄をすべて埋めた表を作る。空欄の行はテストにしない。

| TC-ID | 根拠（AC-ID／分岐） | 入力 | 期待値（あるべき値） | 実装の現状（差異時のみ） | 品質契約（このテストを失敗させる変更） | リスク |
|---|---|---|---|---|---|---|
| TC-001 | AC-002 | total=5000, pref='13' | 0 | 600 🐛 | `total >= 5000` を `>` に変える | 高 |
| TC-002 | AC-002 | total=4999, pref='13' | 600 | — | 閾値 5000 を 4999 に変える | 高 |

- **品質契約**は「どの実装変更でこのテストが失敗するか」を一つ、具体的に書く。書けない場合はアサーションが緩いか、実装の内部を見ている。観点に戻って設計し直す。
- **リスク**は 高（金額・認証・権限・データ整合性）／通常／低 で付ける。
- すべての AC-ID と、手順2で列挙した分岐の両側に、少なくとも一つの TC-ID が対応していることを確かめる。

### 4. 既存テストを確認する

同じ振る舞いを検証する既存テストを、対象関数名・受け入れ条件・期待値で検索する。各 TC を「再利用／拡張／新規」に分類し、同じ入力・期待値のテストを別名で増やさない。既存テストも間違っている可能性があるため、期待値の根拠が仕様にあるかを確かめてから再利用する。

### 5. テストコードを書く

- 1 テスト 1 振る舞い。テスト名に条件と期待結果を書く（例：`5,000円ちょうどは送料無料`）。入力だけが違うケースは、配列で並べて 1 件ずつ独立した `test` を生成する。1 つの `test` に別々の TC のアサーションを並べない（最初の失敗で後続が実行されず、どの TC が壊れたか分からない）。
- 期待値は定数で書く。期待値を求めるために実装と同じ計算をテスト内で再実装しない。
- 戻り値、画面に表示された値、外部境界への副作用（保存・送信・通知）だけを確かめる。private な状態や内部の呼び出し回数を確かめない。
- 外部依存は Stub（固定値を返すだけ）で置き換えることを優先する。呼び出しの検証が仕様そのもの（例：通知が 1 回だけ送られる）の場合だけ呼び出しを確かめる。内部の協力オブジェクトはモックにしない。
- 非同期処理は必ず `await` する。`await` 漏れは例外が消えて成功に見える。
- 品質契約は TC-ID と一緒にテスト名かコメントに残す。

```ts
// TC-001 / AC-002 / 品質契約: `total >= 5000` を `>` に変えると失敗する
test('5,000円ちょうどは送料無料', () => {
  assert.equal(shipping(5000, '13'), 0);
});
```

### 6. 実行し、壊して失敗を確かめる（破壊確認）

テストが緑になっただけでは、そのテストが不具合を検知できるかは分からない。品質契約に書いた変更を実際に加えて確かめる。

1. 対象ファイルに未保存・未コミットの変更が他に無いことを確認する（`git status --short -- <ファイル>`）。
2. 品質契約どおりの最小の変更を実装に加える（`>=` を `>` に、定数を 1 ずらす、分岐を削る等）。
3. テストを実行し、**その TC-ID のテストが、契約に書いた理由と一致するメッセージで失敗する**ことを確認する。別のテストだけが落ちる、コンパイルエラーで落ちる、は確認にならない。
4. 直ちに元に戻す（`git checkout -- <ファイル>`、Git 管理外なら保存したコピーで復元）。差分が無いことを確認する。
5. テストを再実行し、成功を確認する。

**対象**：各 AC-ID の境界と分岐ごとに少なくとも一つの TC（境界の両側があれば緑の側で確かめる）と、新しく書いた回帰テストのすべて。リスク「高」の AC は、境界の向き（`>=`／`>`）と定数を壊す確認を必ず含める。失敗しなかった場合はテストを書き直し、もう一度確かめる。

🐛実装疑義で現在失敗している TC は、その失敗自体が検知の証拠になる。破壊確認の代わりに、失敗メッセージ（期待値と実際の値）を記録する。

破壊確認の途中で `aidev workflow check` を実行しない。壊した状態が検査記録に残る。

### 7. カバレッジを読む

- 未カバーの行・分岐は「観点の漏れ」として読み、手順2・3に戻って TC を足す。
- 呼び出し元が無い、常に成立しない条件など到達不能と判断できるコードは、テストを書かずデッドコード候補として根拠付きで報告する。
- 下限・除外対象・`/* c8 ignore */` 等の除外コメントを変更しない。除外が必要と判断したら、対象・理由・代替の確認手段（E2E や手動確認の記録）を担当者に渡す。
- aidev 管理の React プロジェクトでは `npm run test:coverage` が検査に含まれる。下限と除外は package.json の script が正であり、この Skill の記述ではない。

## 報告の型

報告は次の順で書く。該当が無い項目は「なし」と書き、項目を省かない。

1. **実行結果**：実行したコマンド、終了コード、成功・失敗・スキップの件数。実行していないものは「未実行」と書き、見込みを結果として書かない。
2. **テストケース表**（手順3の表）。
3. **破壊確認の記録**

   | TC-ID | 加えた変更 | 失敗したテストとメッセージ | 復元後の差分 | 再実行 |
   |---|---|---|---|---|
   | TC-001 | `>=` → `>` | `5,000円ちょうどは送料無料` expected 0, actual 600 | なし | 成功 |

4. **🐛実装疑義**：仕様と実装の差異。期待値、実装の現状、影響。
5. **⚠要確認・仮定**：仕様で決まっていなかった点と、採用した解釈。
6. **カバレッジ**：数値と、未カバー箇所の扱い（TC 追加／デッドコード候補／担当者判断待ち）。
7. **未実施と理由**：実行環境が無い、手動確認が必要、等。必要な環境と追試手順を書く。

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「実装を読めば期待値は分かる」 | それは現状の出力であり仕様ではない。実装のバグを期待値として固定し、二度と検知できなくなる |
| 「カバレッジ 80% を超えたので十分」 | カバレッジは実行されたかしか示さない。`assert.ok(x > 0)` でも行は通る。品質契約と破壊確認が十分性の根拠 |
| 「時間が無いので破壊確認は省く」 | 1 件あたり数十秒。省いたテストは「回帰テストのように見えるだけのテスト」で、結果に PASS と書けない |
| 「コードを読んだ限りでは通るはず」 | 見込みは結果ではない。実行していなければ「未実行」と書く |
| 「仕様と実装が違うので、とりあえず実装に合わせて緑にする」 | 期待値は仕様のまま、テストは赤のまま 🐛実装疑義として報告する。緑にする判断は担当者が行う |
| 「1 テストにまとめた方が短い」 | 失敗したときにどの振る舞いが壊れたか分からず、品質契約も一つに決まらない |
| 「このエラー処理は本番でほぼ起きない」 | 起きたときにデータ欠損や無通知の失敗になる箇所ほど検証が要る。依存を注入すれば数十行で書ける |

## Red Flags（作業を止めて手順に戻る）

- 期待値欄に、実装をトレースした出力値をそのまま書いている
- 品質契約が書けない TC がある、または「値が変わると失敗する」のような曖昧な契約になっている
- `assert.ok(...)`、`!== undefined`、`length > 0`、同じ式どうしの比較だけで終わるテストがある
- 破壊確認をしていないのに報告に「検知できる」と書こうとしている
- テストを緑にするために期待値・skip・除外・下限を触ろうとしている

## Common Mistakes

1. **境界の片側だけを試す**：`>` と `>=` の取り違えは境界ちょうどの値でしか見つからない。n-1・n・n+1 を揃える。
2. **組み合わせを試さない**：個別の条件が正しくても、併用時の適用順の誤り（会員割引の後に金額判定する、等）は残る。
3. **期待値をテスト内で計算する**：実装と同じ式を書くと、同じ誤りを含んだまま一致する。定数で書く。
4. **時刻やタイムゾーンを固定しない**：実行時刻で結果が変わるテストは不安定になり、境界（日付の切り替わり）も試せない。
5. **モックを増やしすぎる**：内部の協力オブジェクトまで置き換えると、各テストは通るが結合部分の不具合を検知できない。
6. **破壊確認で別の理由の失敗を成功とみなす**：構文エラーや別のテストの失敗では、そのテストの検知能力は確かめられていない。
7. **壊した実装を戻し忘れる**：戻した後に差分なしと再実行の成功を必ず確かめる。

## 完了条件

- [ ] すべての受け入れ条件に AC-ID があり、各 AC-ID に TC-ID が対応している
- [ ] 手順2で列挙した分岐の両側に TC-ID が対応している（または到達不能の根拠を報告済み）
- [ ] すべての TC に期待値の根拠と品質契約がある
- [ ] テストを実行し、コマンド・終了コード・件数を記録した
- [ ] リスク「高」の TC、新しい回帰テスト、各 AC につき一つ以上の TC で破壊確認を行い、失敗と復元を記録した
- [ ] 🐛実装疑義・⚠要確認・仮定・未実施を報告の型どおりに報告した
- [ ] 期待値・skip・除外・下限・検査設定をテストを通すために変更していない
