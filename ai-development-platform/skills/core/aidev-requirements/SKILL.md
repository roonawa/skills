# 要件定義

## Overview

要件定義の成果物は、後工程が**そのまま判定に使える受け入れ条件**である。受け入れ条件は「誰が・どの状態で・何をしたとき・外から何が観測できるか」を具体的な値で書き、実装方法を含めない。集めた情報は、確認済みの事実・関係者の希望・自分の仮定に分け、食い違いは片方に寄せずに判断を求める。

## When to Use

- 依頼文や関係者の声から、作るものと作らないものを決める
- 不具合の再発防止で、正しい振る舞いを定義し直す
- 関係者の希望どうし、または希望と現行仕様が食い違う

**対象外：**
- 受け入れ条件がすでに揃った変更 → aidev-implementation
- 実装方式の比較（DB 制約か排他制御か、等） → aidev-architecture
- 作業の分割と順序 → aidev-task-planning
- 画面の操作を決める工程 → aidev-ui-delivery（この Skill の受け入れ条件を入力にする）

## Core Pattern

**Before**：「二重送信で予約が 2 件できる」に対し、「送信ボタンを短時間に連打しても 1 件だけ作られる」「サーバー側で DB の一意制約により保証する」と書く。「短時間」は判定できず、一意制約は実装方法で、窓口の「同じ人は同じ日に 1 件まで」が現行仕様（2 件まで）と食い違うことも埋もれる。

**After**：情報を事実・希望・仮定に分け、窓口の希望と現行仕様の食い違いを「判断待ち」として独立させる。受け入れ条件は「利用者 U1 が枠 S1 の予約を送信し、応答前に同じ内容をもう一度送信したとき、S1 の有効な予約は 1 件で、2 回目の応答は 1 回目と同じ予約番号を返す」と書く。方式は aidev-architecture に渡す。

## 手順

### 1. 情報を分類する

集めた情報を一つずつ次の表に入れる。出典の無い情報は書かない。

| 区分 | 内容 | 出典 |
|---|---|---|
| 事実 | 現行仕様、障害記録、計測値、既存テストなど確認できるもの | 仕様書の節、障害番号、ファイル |
| 証言 | 関係者が実際に見た・経験した状況（「画面が固まって 2 回押すことがある」）。望む振る舞いとは分ける | 誰の発言か |
| 希望 | 関係者が望む振る舞い。誰の希望かを書く | 窓口担当、利用者アンケート |
| 仮定 | 自分が補った解釈。確かめる方法を添える | — |
| 食い違い | 事実と希望、希望どうしが両立しない点 | 関係する行 |

推測で書かれた事実（「原因は〜と推測」）は事実ではなく仮定として扱う。

### 2. 対象範囲を決める

- **やること**と**やらないこと**を両方書く。やらないことは、関係者が期待しそうだが今回扱わないもの（別の要望、将来の拡張）を必ず含める。
- 範囲外にした希望は、捨てずに「別件として起票するか」を判断待ちに入れる。

### 3. 受け入れ条件を書く

受け入れ条件には `AC-001` から番号を振り、次の形で書く。

```text
AC-001：<前提状態> のとき、<誰が> <操作・入力> をすると、<観測できる結果（値・件数・表示）> になる。
```

- **具体的な値**を使う。「短時間」「ほぼ同時」「適切に」「速やかに」のように判定できない語は、数値にするか ⚠要確認 にする。
- **観測できる結果**だけを書く。画面の表示、返る値、保存される件数、送られる通知。DB 制約・排他・キャッシュなどの実装方法は書かない。
- 正常、境界（ちょうど・前後）、異常（失敗・再試行・同時操作）、権限（本人・代理・他人）の各観点について、該当するものを書く。該当しない観点は理由を一行で書く。
- 番号は振り直さない。削除した AC は「取り下げ」と書いて番号を残す。

### 4. 判断待ちを整理する

食い違いと未確定事項を、次の表で判断を求める形にする。各案で利用者に見える結果がどう変わるかを書く。

| ID | 論点 | 案と結果の違い | 判断する人 | 影響する AC | 判断が出るまでの扱い |
|---|---|---|---|---|---|
| Q-001 | 同じ利用者が同じ日に 2 件予約できるか | A：できる（現行どおり）／B：できない（窓口の希望。家族分の代理予約も 1 件に制限される） | 業務責任者 | AC-004 | 現行どおり A で進め、B なら AC-004 を変更 |

可逆で影響が小さい点は「仮定」として進めてよい。利用者に見える結果が変わる点は、判断が出るまで該当 AC を「判断待ち」とする。

## 出力の型

1. **目的**：誰のどんな困りごとを解消するか（1〜2 文）
2. **情報の分類**（手順1の表）
3. **対象範囲**：やること／やらないこと
4. **受け入れ条件**（AC-ID 付き。観点ごとにまとめる）
5. **判断待ち**（手順4の表）
6. **仮定**：採用した解釈と確かめ方

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「方式まで書いた方が実装者に親切」 | 方式を書くと方式の比較が飛ばされ、別の方式で満たせるのに不合格になる。方式は aidev-architecture で決める |
| 「『短時間』で意味は通じる」 | テストは書けず、合否が人によって変わる。値にするか ⚠要確認 にする |
| 「食い違いは多数派に寄せればよい」 | 寄せた結果が業務ルールの変更になることがある。判断する人を書いて判断を求める |
| 「関連する要望も一緒に入れておく」 | 範囲が膨らみ、来週の着手に間に合わなくなる。やらないことに書き、別件にする |

## Red Flags

- 受け入れ条件に「DB」「排他」「キャッシュ」「一意制約」などの実装語が入っている
- 「短時間」「適切」「なるべく」が残っている
- 「やらないこと」が空
- 食い違いを自分の判断で片方に決めている

## Common Mistakes

1. **推測の原因を事実として扱う**：対策が推測した原因にだけ向き、本当の原因を防げない。両方の可能性を受け入れ条件で押さえる。
2. **代理操作を考えない**：職員が代理で操作する場面で、誰を基準に判定するかが抜ける。権限の観点で本人・代理・他人を確かめる。
3. **既存データを忘れる**：新しい制約を入れたとき、すでに条件に反する既存データをどう扱うかが決まらない。
4. **確認の文面が関係者に通じない**：判断待ちは、関係者が使う言葉（画面名・業務用語）で書く。

## 完了条件

- [ ] 情報を事実・希望・仮定・食い違いに分け、出典を書いた
- [ ] やること・やらないことを書いた
- [ ] すべての受け入れ条件に AC-ID があり、具体的な値と観測できる結果で書かれている
- [ ] 受け入れ条件に実装方法と判定できない語が無い
- [ ] 食い違い・未確定事項を判断待ちの表にし、判断する人と影響する AC を書いた
