# アーキテクチャ設計

## Overview

設計判断の成果物は、**採用案・不採用案とその理由・移行と切り戻しの手順・承認者**を残した決定記録である。案は同じ評価軸で比べ、採用案は代表的な一つの利用例で端から端までたどって破綻しないことを確かめる。公開 API・データ形式・既存利用者に影響する決定は、AI が確定せず推奨として出し、承認を得てから実装に渡す。

## When to Use

- 公開 API の形、データの持ち方、モジュールの境界が変わる
- 旧クライアント・既存データ・他チームの利用者との互換性が問題になる
- 実装方式の候補が複数あり、どれにするか決める必要がある

**対象外：**
- 既存パターンに沿った局所的な変更 → aidev-implementation
- 何を作るか（受け入れ条件）が決まっていない → aidev-requirements

## Core Pattern

**Before**：「キャンセル理由を必須にしたいが、旧アプリ v1 は本文なしで呼び続ける」に対し、新エンドポイント案を選び、来週から実装に入る前提で手順を書く。切り戻しの条件、承認する人、旧エンドポイントを消す判断基準が無い。

**After**：4 案を同じ評価軸で比べ、推奨案を一つの取消操作（v1 から本文なしで取消 → 集計バッチ → 90 日後の削除）でたどる。各移行ステップに切り戻し方法と、切り戻す判断の条件を書く。決定記録を作り、API の利用者に影響するため承認を求めて止める。

## 手順

### 1. 影響範囲を特定する

公開入口からデータの読み書きまでをたどり、変更で影響を受けるものを列挙する。

| 区分 | 確認すること |
|---|---|
| 利用者 | 呼び出し元（画面・アプリの版・他システム・バッチ）、更新できない利用者の割合と期限 |
| データ | 既存レコード、列の意味の変化、集計・帳票・エクスポートへの影響 |
| 運用 | デプロイ順序、設定、監視、ログ、バックアップ |
| 制約 | 個人情報・保持期間・セキュリティ・性能の社内方針 |

### 2. 案を比べる

少なくとも「現状を拡張する案」と「境界を変える案」を含め、同じ評価軸で比べる。明らかに不可能な案（更新できない利用者を切り捨てる等）も、不採用の理由を残すために表に入れる。

| 評価軸 | 案A | 案B | 案C |
|---|---|---|---|
| 既存利用者への影響 | | | |
| 受け入れ条件を強制できるか | | | |
| データ移行の要否と手順 | | | |
| 切り戻しのしやすさ | | | |
| 検証のしやすさ（テストできる単位） | | | |
| 運用・保守の負担と期間 | | | |

### 3. 採用案を一つの利用例でたどる

代表的な利用例を一つ選び、入力から保存・集計・削除まで順に追う。途中失敗（片方だけ成功）、二重実行、同時実行で壊れる不変条件を探し、それを守る責務をどこに置くか、どこで検証するかを決める。

```text
例：v1 アプリが本文なしで取消 → 旧エンドポイントが理由「未指定（旧版）」を補う → status=cancelled
    → 夜間集計（理由なしで件数を数える：影響なし） → 90 日後に自由記述だけを消去（コードは残す）
不変条件：取消済みの予約は必ず理由コードを持つ（旧経路でも補う）
```

### 4. 移行と切り戻しを決める

移行をステップに分け、各ステップに「切り戻し方法」と「切り戻す判断の条件（観測値）」を書く。データを書き換えるステップは、切り戻せない点を明記する。

| ステップ | 内容 | 切り戻し方法 | 切り戻す条件 | 不可逆か |
|---|---|---|---|---|
| 1 | 列を NULL 許可で追加 | 列を削除 | — | いいえ |
| 2 | 既存行に理由コードを補う | 補った値を NULL に戻す | 集計値が変わった | いいえ |
| 3 | 自由記述の 90 日削除ジョブ開始 | ジョブ停止 | — | **はい（削除済みは戻らない）** |

### 5. 決定記録を作り、承認を求める

次の型で決定記録を作る。公開 API・データ形式・既存利用者・個人情報に影響する場合、または不可逆なステップを含む場合は、推奨として提示して承認を求め、承認まで実装に渡さない。

```markdown
# 決定記録：<題名>
- 状態：提案中／承認済み（承認者・日付）
- 背景：<困りごとと制約>
- 決定：<採用案>
- 不採用案と理由：<案ごとに一行>
- 影響：<利用者・データ・運用>
- 移行と切り戻し：<手順4の表>
- 確認が必要な点：<判断待ちと判断する人>
- 見直す条件：<例：旧エンドポイントの利用が 1% 未満になったら削除を判断>
```

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「明らかに最善の案があるので比較は省く」 | 不採用の理由が残らないと、後で同じ議論が繰り返される。不可能な案も一行で理由を書く |
| 「来週から実装したいので決めてしまう」 | 公開 API やデータ形式は、決めた後に戻すコストが最も大きい。推奨を出して承認を求めるのが最短 |
| 「切り戻しは問題が起きてから考える」 | 不可逆なステップは起きてからでは戻せない。どこから戻せないかを先に明記する |
| 「互換窓口は一時的なので設計は簡単でよい」 | 一時的な経路ほど削除が先送りされる。削除の判断条件と計測を最初から用意する |

## Red Flags

- 比較表に案が一つしかない
- 移行手順に切り戻しの列が無い
- 承認者を書かずに「決定」と書いている
- 個人情報や保持期間の方針を、DB 以外（ログ・バックアップ・監視）で確かめていない

## Common Mistakes

1. **集計・バッチ・帳票を見落とす**：API だけを見て、列の意味の変化で夜間集計が壊れる。
2. **デプロイ順序を決めない**：クライアントがサーバーより先に新しい形式で呼び、失敗する。
3. **旧経路を暗黙の分岐で残す**：ヘッダーの有無で分岐すると、新しいクライアントからも必須項目を回避できてしまう。
4. **削除方針を DB だけで満たしたと考える**：ログ・エラー監視・バックアップに同じデータが残る。

## 完了条件

- [ ] 影響範囲（利用者・データ・運用・制約）を列挙した
- [ ] 2 案以上を同じ評価軸で比べ、不採用の理由を書いた
- [ ] 採用案を一つの利用例でたどり、不変条件と検証箇所を決めた
- [ ] 移行の各ステップに切り戻し方法・条件・不可逆かを書いた
- [ ] 決定記録を作り、承認が必要な場合は承認を求めて止めた
