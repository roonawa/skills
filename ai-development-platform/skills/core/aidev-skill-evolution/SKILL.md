# Skill の改善提案

## Overview

Skill の改訂は、**旧版で失敗を再現し、新版で直ることを同じ条件で確かめてから**人の承認を経て配る。決まった手順で機械的に判定できる問題（禁止パターン、設定の必須化、CI での実行条件）は、文章で頼むより CLI・Lint・CI で強制する方が確実なので、まずそちらを検討する。文章を足すときは最小の変更にし、過去の失敗に過剰適合した規則を増やさない。

## When to Use

- 複数の開発記録で同じ失敗・手戻りが起きている
- Skill の文言を変えたい、旧版と比べたい
- 改訂版を配布してよいか判断する

**対象外：** 個別アプリの不具合 → aidev-debugging。新しい Skill をゼロから作る場合も、この Skill の比較手順は使えるが、まず適用範囲を利用者と決める。

## Core Pattern

**Before**：「AI のテストで日時の検証漏れが 3 回続いた。Skill を直して今日中に全プロジェクトへ」に対し、現行の Skill 本体を読まずに、境界の一覧表と多数の必須規則を足した改訂案を書き、そのまま配布手順に進む。

**After**：現行の Skill 本体を読み、3 件の記録を「Skill の指示不足」「指示はあるが守られない」「機械で防げる」に分類する。CI で `TZ=UTC` と `TZ=Asia/Tokyo` の両方を実行する案を機械的な対策として先に出す。文言は観点表の 1 行を具体化する最小の変更にとどめ、3 件を模した課題で旧版と新版を比べる。結果と戻し方を添えて承認を求め、配布は承認後に一部のプロジェクトから行う。

## 手順

### 1. 記録を分類する

現行の Skill 本体（配布されている版）を読んでから、各記録を次のいずれかに分類する。

| 分類 | 判断の基準 | 対策の場所 |
|---|---|---|
| 指示不足 | Skill に該当する指示が無い、または抽象的で具体的な行動に落ちない | Skill の文言 |
| 不遵守 | 指示はあるが、圧力や手間で守られなかった | 出力の型に必須欄を作る、言い訳と実際の表 |
| 機械で防げる | 正規表現・設定・CI の実行条件で確実に判定できる | CLI・Lint・CI・保護対象（Skill ではない） |
| 環境・個別 | 特定のプロジェクトの設定や事情による | そのプロジェクトの AGENTS.md |
| 誤選択 | 別の Skill が使われた、Skill が使われなかった | description |

### 2. 最小の変更案を作る

- 一つの判断を変える最小の変更にする。過去の 3 件だけに当てはまる細かな規則を並べない（次の失敗は別の形で起きる）。
- 失敗の型に合わせて書き方を選ぶ。守られない規則には言い訳と実際の表、抜ける要素には出力の型の必須欄、形がばらつく出力には型そのものを書く。
- 機械で防げる部分は、Skill の変更とは別の変更案（CLI・CI・Lint）として出す。

### 3. 旧版と新版を同じ条件で比べる

1. 記録を匿名化し、失敗を誘う課題（シナリオ）を 3 件以上作る。対象外の課題も 1 件入れる。
2. **旧版で失敗を再現する。** 再現しない課題は、その Skill の改訂で直せる失敗ではない。課題を作り直すか、分類を見直す。
3. 同じホスト・モデル・予算・課題で、旧版と新版を独立したセッションで実行する。各課題は複数回（目安 3〜5 回）実行し、結果のばらつきも見る。
4. 成否、記録の型を満たしたか、指摘数、所要時間、再試行回数、取得できたコストを記録する。取得できない値は空欄にして理由を書き、推定値を入れない。
5. aidev 管理下では `aidev skill eval NAME` が課題と観測の雛形を出力し、`--observations` で集計できる。

### 4. 承認を求める

次をまとめて人のレビューに渡す。共通の原本への反映と配布は承認後に行う。

- 分類と、Skill で直す理由（機械で防げる部分は別案）
- 変更の差分と新しい版番号（`metadata.version`）
- 比較結果（旧版で再現した失敗、新版での結果、対象外の課題での副作用）
- 戻し方（旧版の版番号と、配布済みプロジェクトの戻し手順）

### 5. 段階的に配る

承認後、まず一部のプロジェクトに配り、次の作業で効果と副作用を確かめてから全体に広げる。各プロジェクトに入っている利用者の変更は上書きしない（aidev-project-verification）。

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「原因は明らかなので比べなくてよい」 | 旧版で失敗を再現できないなら、改訂で直るかは分からない。比べないと副作用（対象外の依頼での過剰な手順）にも気づけない |
| 「必須規則を増やせば確実になる」 | 規則が増えるほど形だけ埋める出力が増え、他の指示も読まれにくくなる。最小の変更と機械的な強制を優先する |
| 「今日中に全プロジェクトへ配りたい」 | 未検証の改訂を全体に配ると、副作用も全体に広がる。承認後に一部から配る |
| 「現行の内容は記憶で分かる」 | 配布済みの版と記憶はずれる。本体を読んでから分類する |

## Red Flags

- 現行の Skill 本体を読まずに改訂案を書いている
- 旧版で失敗を再現していない
- 機械で判定できる問題を文章の規則で防ごうとしている
- 承認を得る前に原本を書き換え、配布しようとしている

## Common Mistakes

1. **単発の観測で効果を判断する**：1 回の成功はばらつきの範囲内かもしれない。複数回実行する。
2. **description に手順を書く**：手順の要約を description に書くと、本文を読まずに要約どおりに動く。description には使う場面だけを書く。
3. **版番号を上げ忘れる**：配布済みの版との差を `verify` で検出できなくなる。
4. **対象外の課題を試さない**：改訂した Skill が関係ない依頼にまで適用され、手順が重くなる。

- [ ] 機械で防げる部分を、Skill とは別の変更案にした
