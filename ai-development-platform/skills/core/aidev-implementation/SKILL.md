# 実装

## Overview

実装の完了は「コードを書いた」ではなく、**受け入れ条件ごとに、それを検証するテストが成功し、そのテストが実装を壊すと失敗することを確かめた状態**とする。テストは実装の後付けではなく、実装より先に失敗させて期待値を固定する。依頼に書かれていない振る舞いを決めたときは、それを仕様ではなく「仮定」として引き渡す。

## When to Use

- 受け入れ条件または仕様が示された機能追加・修正
- 原因と直し方が確認済みの不具合修正（aidev-debugging から引き継いだもの）

**対象外：**
- 期待動作が決まっていない → aidev-requirements
- 原因が分かっていない障害 → aidev-debugging
- 公開 API・データ形式・モジュール境界が変わる設計判断 → aidev-architecture（承認後に戻る）

**REQUIRED SUB-SKILL：aidev-testing** — テストケース表・品質契約・破壊確認はこの Skill に従う。aidev 管理プロジェクトで検査を回すときは aidev-repair-workflow を使う。

## Core Pattern

**Before**：「ポイント付与を追加して」に対し、実装とテストをまとめて書く。100 円未満の注文にもキャンペーン +50 を付ける、不正な金額で例外を投げる、といった依頼に無い振る舞いが黙って入る。テストは 1 件に 5 つのアサーションを詰め、実行はしていない。

**After**：受け入れ条件を AC-001〜004 に分け、依頼で決まっていない点（100 円未満の注文に +50 を付けるか、不正入力の扱い）を「確認」と「仮定」に振り分ける。AC ごとに失敗するテストを先に書いて赤を確かめ、実装して緑にし、破壊確認を記録する。引き継ぎメモに AC 対応表と仮定の一覧を付ける。

## 手順

### 1. 受け入れ条件と未決事項を分ける

1. 受け入れ条件を `AC-001` から番号付きで列挙する。
2. 依頼で決まっていない点を洗い出し、次の基準で振り分ける。

   | 判定 | 基準 | 扱い |
   |---|---|---|
   | 確認 | 利用者に見える結果（金額・件数・表示・可否）が変わる | 実装前に担当者へ質問する。回答待ちの間は、その AC に依存しない部分だけ進める |
   | 仮定 | 結果が変わらない、または後から容易に変更できる内部の選択 | 採用した解釈を記録して進める |

3. 依頼に無い振る舞い（入力検証で例外を投げる、値を丸める、既定値を補う）を追加する場合は、それも「仮定」に入れる。仕様として黙って入れない。

### 2. 既存コードを読む

呼び出し元から対象へたどり、次を確認する。

- 再利用できる既存の型・共通部品・ユーティリティ（同じ処理を新しく書かない）
- 旧データ・既存の呼び出し元で維持すべき動作
- 対象ディレクトリの規約（AGENTS.md、既存テストの書き方、import の形式、テストファイルの拡張子）

### 3. テストを先に書き、失敗を確かめる

aidev-testing の手順1〜5に従い、AC ごとのテストケース表とテストを書く。実装前に実行し、**期待した理由で失敗すること**を確認する。新しい関数は、まず型どおりの仮の実装（例：常に `0` を返す）を置いて実行し、モジュール未解決や型エラーではなく値の不一致で落ちることを確かめる。不具合修正では、修正前のコードでテストが失敗することを必ず確かめる。

### 4. 実装する

- テストを通す最小の変更を行う。依頼の範囲外のリファクタリングや機能追加を混ぜない。
- 時刻・乱数・ファイル・ネットワークは引数や依存として注入できる形にし、テストで固定できるようにする。
- 新しく追加したファイル・関数・分岐には、同じ変更の中でテストを付ける。

### 5. 検証する

1. 対象テストと既存スイートを実行し、成功を確認する。
2. aidev-testing の手順6に従い破壊確認を行う。
3. プロジェクト規定の検査（型検査・Lint・テスト・カバレッジ・ビルド）を実行する。aidev 管理プロジェクトでは aidev-repair-workflow に沿って `aidev workflow check` を使う。
4. 失敗したら原因を一つの仮説で確かめてから直す。原因が分からなければ aidev-debugging に切り替える。

## 引き継ぎメモの型

レビュアーへの引き継ぎは次の順で書く。該当が無い項目は「なし」と書く。

1. **変更概要**：何をどこに追加・変更したか（ファイル単位）。
2. **AC 対応表**

   | AC-ID | 受け入れ条件 | 実装箇所 | TC-ID | 結果 | 破壊確認 |
   |---|---|---|---|---|---|
   | AC-003 | 期間中は +50（開始・終了日を含む、JST） | `points.ts:calculatePoints` | TC-007〜010 | 成功 | TC-008 で確認済み |

3. **仮定**：採用した解釈と、変えたい場合の影響範囲。
4. **確認待ち**：担当者の回答が必要な点と、その回答で変わる AC。
5. **実行結果**：コマンド、終了コード、件数。未実行のものは「未実行」と理由。
6. **残件**：未対応の範囲、手動確認が必要な点、既知の制約。

## 守ること

- テストの削除・skip、期待値の緩和、カバレッジの下限・除外・除外コメントの変更、検査設定の変更で失敗を解消しない。
- 仕様と実装が食い違ったら、テストを実装に合わせず 🐛実装疑義として報告する。
- 実装後は単体テスト・セキュリティ・仕様乖離と過剰実装のゲートを通す。差し戻しは人の確認なしで最大3回。同じ失敗が再発したらその時点で止め、原因の仮説と残件を引き継ぐ。

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「テストは実装の後で書けば同じ」 | 後から書いたテストは実装の出力を写しやすく、最初から成功するので検知能力を確かめられない。先に失敗させる |
| 「入力検証を足すのは親切」 | 依頼に無い振る舞いは呼び出し側の前提を壊すことがある。足すなら仮定として明記し、レビューで判断してもらう |
| 「細かい解釈は自分で決めた方が早い」 | 利用者に見える結果が変わる解釈は、実装後に覆ると手戻りが大きい。確認か仮定かを表で振り分ける |
| 「CI で確認してもらえばよい」 | 自分で実行していない結果は報告できない。実行していなければ「未実行」と書く |
| 「ついでに周辺も整理した」 | 依頼外の変更はレビュー範囲を広げ、回帰の原因を特定しにくくする。別の変更に分ける |

## Red Flags

- AC 対応表に TC-ID が空の行がある
- 「仮定」の欄が空なのに、依頼に無い分岐や例外処理を書いている
- テストを一度も失敗させずに実装を終えた
- 報告に「通る見込み」「問題ないはず」と書こうとしている

## Common Mistakes

1. **未決事項を仕様として実装する**：レビュアーは依頼と実装の差に気づけず、そのまま本番の仕様になる。
2. **既存の共通処理を使わずに同じ処理を書く**：二重実装は片方だけ直されて食い違う原因になる。
3. **時刻・タイムゾーンを実行環境に依存させる**：日付境界の不具合はテストで再現できず、本番でだけ起きる。
4. **不具合修正で修正前の失敗を確かめない**：テストが不具合を検知できるかが分からないまま「修正済み」になる。
5. **引き継ぎメモに実行結果を書かない**：レビュアーは検証済みかどうかを判断できず、再実行の手間が生まれる。

## 完了条件

- [ ] 受け入れ条件に AC-ID を振り、未決事項を「確認」と「仮定」に分けた
- [ ] すべての AC-ID にテストがあり、実装前に期待した理由で失敗した
- [ ] 実装後にテストと既存スイートが成功し、破壊確認を記録した
- [ ] プロジェクト規定の検査を実行し、結果を記録した
- [ ] 引き継ぎメモを型どおりに書いた（AC 対応表・仮定・確認待ち・実行結果・残件）
- [ ] テスト・検査・仕様を緩めて失敗を解消していない
