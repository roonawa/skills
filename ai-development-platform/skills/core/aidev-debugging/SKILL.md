# 障害の切り分け

## Overview

原因は推測ではなく観測で決める。まず症状を最小の手順で再現し、仮説を一つずつ「誤っていれば結果が変わる観測」で確かめる。報告に含まれる手がかり（ログの形式、時刻、直前の操作）は仮説の材料であって、原因の証拠ではない。修正は、修正前に失敗する回帰テストを書いてから行い、同じ書き方の箇所が他に無いかも確かめる。

## When to Use

- テストの失敗、例外、特定の条件でだけ起きる不具合
- 利用者・窓口からの症状の報告
- aidev-repair-workflow の repair 状態で失敗の原因を確かめるとき

**対象外：** 原因と修正方法が確定している変更 → aidev-implementation。配布した Skill の欠損 → aidev-project-verification。

## Core Pattern

**Before**：「取消直後に同じ利用者だけ予約が失敗する。ログの時刻が UTC なのが怪しい」に対し、時刻の扱いを日本時間に直して様子を見る。症状は変わらない。

**After**：2 件予約 → 1 件取消 → 予約、の最小手順で再現するテストを書き、失敗を確かめる。仮説「時刻が原因」は、判定に時刻が使われていないことをコードで確かめて退ける。仮説「有効件数のキャッシュが取消で更新されない」は、取消後のキャッシュ値を観測して確かめる。キャッシュを更新する他の経路も検索し、修正後にテストの成功と、修正を戻すと再び失敗することを確かめる。

## 手順

### 1. 再現する

1. 症状を「前提状態 → 操作 → 期待 → 実際」の形で書く。
2. 最小の入力で再現する。可能なら自動テストとして書き、失敗を確かめる。
3. 再現しない場合は、OS・版・時刻とタイムゾーン・実行順序・並行性・データの違いを一つずつ変えて調べる。再現できないまま修正しない。
4. 調査用の一時ファイルやスクリプトは作業ディレクトリの中に作り、終わったら消す。作業ディレクトリの外には書き込まない。

### 2. 仮説を一つずつ確かめる

仮説ごとに次の表の行を追加する。一度に変える条件は一つだけにする。

| # | 仮説 | 誤っていれば何が観測されるか | 実際の観測 | 判定 |
|---|---|---|---|---|
| H1 | ログの時刻が UTC であることが原因 | 判定処理が時刻を使っていない | `book()` の上限判定は件数のみ、時刻はログ出力だけに使用 | 棄却 |
| H2 | 取消でキャッシュの件数が減らない | 取消後のキャッシュ値が 1 になる | 取消後も 2 のまま | 採択 |

- 報告者の推測（「UTC が怪しい」）も仮説として表に入れ、観測で判定する。
- 「コードを読んだらそれらしい」は観測ではない。値を出力する、テストで状態を確かめる、条件を変えて結果を比べる。

### 3. 直す

1. 手順1の再現テストを回帰テストとして残す（aidev-testing の品質契約を付ける）。
2. 原因に対応する最小の修正を行う。原因と関係の無い改善（ログ形式の変更など）を混ぜない。
3. 再現テストと既存スイートを実行し、成功を確かめる。
4. 修正を一時的に戻して回帰テストが失敗することを確かめ、元に戻す（aidev-testing の破壊確認）。
5. **同じ原因の別の経路**を検索する（例：キャッシュを使う他の関数、同じ状態を変更する他の操作）。見つかれば同じ修正とテストを行うか、残件として報告する。

### 4. 止めるとき

同じエラーが再発した、または 3 回修正しても解消しない場合は修正をやめ、仮説の表と残る仮説・次の観測を引き継ぐ。テスト・検査・仕様を緩めて解消しない。

## 報告の型

報告先が利用者・窓口の場合は、専門用語を画面や操作の言葉に置き換える。

1. **結論**：直したか、直していないか（直していない場合は理由）
2. **原因**：何が起きていたか。症状と一致する理由
3. **再現手順**：前提状態・操作・期待・実際（人が実機で追試できる具体性で）
4. **退けた仮説**：報告者の推測を含め、なぜ原因でないか
5. **修正**：変更箇所と内容
6. **確認**：実行したテスト・終了コード、修正前の失敗と修正後の成功、破壊確認
7. **残件**：同じ原因の他の経路、別件にした改善、未確認の環境

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「報告者が怪しいと言う箇所から直す」 | 報告者の推測は仮説の一つ。観測で判定してから直す。外れた修正は症状を残し、別の不具合を足す |
| 「再現しないが、たぶんここなので直す」 | 再現しないまま直すと、直ったかどうかを確かめられない |
| 「ついでにログも日本時間にしておく」 | 原因と無関係な変更は、修正の確認と切り戻しを難しくする。別件にする |
| 「テストが通ったので完了」 | 修正前に失敗することを確かめていないテストは、不具合を検知できるか分からない |

## Red Flags

- 再現テストを書く前に修正を始めている
- 一度に二つ以上の条件を変えている
- 仮説の表に観測の列が空の行がある
- 同じ原因の他の経路を探していない

## Common Mistakes

1. **キャッシュ・状態の更新経路を一つしか見ない**：作成で増やす処理はあっても、取消・削除・失敗時の巻き戻しで減らす処理が無い。
2. **最初の失敗箇所ではなく、最後に例外が出た箇所を直す**：状態が食い違い始めた最初の箇所をたどる。
3. **不安定なテストを再実行で通す**：時刻・順序・並行性の違いを特定せずに再実行すると、本番で同じ失敗が起きる。

## 完了条件

- [ ] 症状を最小手順で再現し、失敗するテストとして残した
- [ ] 仮説の表に、報告者の推測を含む各仮説の観測と判定がある
- [ ] 修正前に回帰テストが失敗し、修正後に成功し、破壊確認を記録した
- [ ] 同じ原因の他の経路を探し、結果を報告した
- [ ] 報告の型どおりに、相手に通じる言葉で報告した
