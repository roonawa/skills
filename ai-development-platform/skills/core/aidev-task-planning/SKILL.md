# 実装タスクへの分解

## Overview

作業計画の成果物は、**各タスクが単独で完了を判定でき、すべての受け入れ条件に担当タスクがあり、並行するタスクどうしが同じファイルを変更しない**表である。タスクは層（API・画面・テスト）ではなく、利用者から見える振る舞いの単位（縦の単位）で切る。各タスクは自分のテストを含み、別の人がテストだけを書くタスクを作らない。

## When to Use

- 受け入れ条件と設計が合意済みで、作業の順序と分担を決める
- 開発者と AI エージェントが並行して進める

**対象外：**
- 受け入れ条件が決まっていない → aidev-requirements
- 方式が決まっていない → aidev-architecture

## Core Pattern

**Before**：開発者 A が API、開発者 B が画面、AI が回帰テストを担当する層ごとの分担。API の完成まで画面は結合できず、テストを書く AI は実装の詳細を知らないまま待つ。返金失敗時の扱い（AC-4）はどのタスクの完了条件にも入っていない。

**After**：最初に契約（型とモック）を確定するタスクを置き、その後は「無料取消」「手数料取消」「返金失敗時の保留」「二重実行」の振る舞いごとに、API・画面・テストを含むタスクを切る。各タスクに AC、先行タスク、変更するファイル、完了を判定するコマンドを書き、並行するタスクのファイルが重ならないことを確かめる。

## 手順

### 1. 入口と再利用できるものを特定する

利用者が通る入口（画面操作、API、バッチ）ごとに、変更が必要な箇所と再利用できる既存の実装を列挙する。既存コードを確認していない箇所は「未確認」と書き、確認タスクを最初に置く。

### 2. 縦の単位で切る

- 1 タスクは一つの振る舞い（一つ以上の AC）を、入口から保存・通知まで動く状態にする。テストはそのタスクに含める。
- 複数のタスクが同じ契約（型・API の形・DB 列）に依存する場合だけ、契約を先に確定するタスクを置く。
- 失敗時に残る状態と復旧（外部 API の失敗、途中までの書き込み、再実行）を扱うタスクを必ず含める。
- 1 タスクは 1 日以内で終わる大きさを目安にする。

### 3. タスク表を作る

| T-ID | 振る舞い | AC | 先行 | 変更するファイル | 担当 | 完了の判定 |
|---|---|---|---|---|---|---|
| T-01 | 契約の確定（型・モック） | — | — | `src/cancel/types.ts`, `src/cancel/mock.ts` | 開発者A | 型を全員がレビュー済み、`npm test` 成功 |
| T-02 | 24 時間前までの無料取消 | AC-1, AC-3 | T-01 | `src/cancel/fee.ts`, `src/cancel/api.ts` | AI | 境界（24h ちょうど・1 秒前後）のテストが成功、破壊確認済み |
| T-03 | 返金失敗時の保留表示 | AC-4 | T-02 | `src/admin/pending.tsx` | 開発者B | 返金 API の失敗を模擬して保留が表示されるテストが成功 |

- **完了の判定**は、実行するコマンドと観測する結果で書く。「実装する」「確認する」だけの判定は書かない。
- **変更するファイル**は、ファイルまたはディレクトリ単位で書く。

### 4. 並行作業を確かめる

並行させるタスクの組ごとに、変更するファイルと契約が重ならないことを確かめる。重なる場合は、先行関係にするか、共通部分を契約タスクに移す。

### 5. 網羅を確かめる

- すべての AC に、少なくとも一つのタスクが対応している（AC→T-ID の逆引き表で確かめる）。
- 仕様の抜け（境界ちょうどの扱い、外部 API の冪等性など）は「要確認」として表の外に書き、影響するタスクと、回答が出るまでの扱いを添える。
- 実機や外部環境が無いと判定できないタスクは、必要な環境と、代わりに使える検査（スタブ・モック）を書く。

## 出力の型

1. **前提**：合意済みの AC、設計、未確認の既存コード
2. **タスク表**（手順3）
3. **AC 逆引き表**：AC-ID → T-ID
4. **並行作業の組**と、ファイルが重ならないことの確認結果
5. **要確認事項**：論点、影響するタスク、回答が出るまでの扱い
6. **リスク**：遅れやすいタスクと、その理由

## よくある言い訳と実際

| 言い訳 | 実際 |
|---|---|
| 「得意分野ごとに API・画面・テストで分けた方が速い」 | 層ごとの分担は結合まで動くものが無く、問題が最後に見つかる。振る舞い単位で切り、契約だけを先に確定する |
| 「テストは別担当がまとめて書く」 | 実装の詳細を知らない担当のテストは弱くなり、実装者はテストを走らせずに完了と判断する。テストは各タスクに含める |
| 「完了条件は『実装済み』で十分」 | 判定する人によって完了が変わる。コマンドと観測結果で書く |
| 「ファイルの重なりは後でマージすればよい」 | 並行作業のマージ衝突は、どちらかの作業のやり直しになる。計画の時点で分ける |

## Red Flags

- 「テストを書く」だけのタスクがある
- 完了の判定に「確認する」「実装する」しか書かれていない
- 並行タスクの変更ファイルが重なっている
- 失敗時の状態を扱うタスクが無い

## Common Mistakes

1. **外部 API の失敗を正常系の後回しにする**：返金・通知の失敗は利用者への影響が大きく、後から入れると設計の手戻りになる。
2. **既存の一覧・集計への影響をタスクにしない**：新しい状態（保留など）が既存画面で想定されていない。
3. **要確認事項を抱えたまま着手する**：回答で振る舞いが変わるタスクは、回答が出るまでの扱いを決めておく。

## 完了条件

- [ ] すべてのタスクに AC・先行・変更ファイル・担当・完了の判定がある
- [ ] すべての AC に対応するタスクがある
- [ ] 並行タスクの変更ファイルと契約が重ならない
- [ ] 失敗時の状態と復旧を扱うタスクがある
- [ ] 要確認事項に、影響するタスクと回答までの扱いがある
