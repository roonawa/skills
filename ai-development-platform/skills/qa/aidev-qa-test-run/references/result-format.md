# result.md の書き方

テストケースを実行した結果を `runs/<YYYYMMDD>-<run-id>/result.md` に書くときに読む。基本の形は QA リポジトリの `runs/README.md` にあり、ここではそれに足す節と、各節に何を書くかを決める。

## 全体の形

冒頭の3行と、TC-ID ごとの表は `runs/README.md` の形のまま変えない。`aidev qa trace` と起票の Skill がこの表を読むので、列を足したり名前を変えたりしない。ケースごとの詳しいことは、表の後の節に TC-ID を見出しにして書く。

```markdown
# 実行結果 20261118-new-cases

- 環境: new
- 版: 2.3.0（画面の右下の表示）
- 実行日時: 2026-11-18 14:05〜14:21（テストの実行の記録から）

| TC-ID | 結果 | 証跡 | Issue |
|---|---|---|---|
| TC-order-001 | OK | runs/20261118-new-cases/evidence/TC-order-001/ | |
| TC-order-002 | NG | runs/20261118-new-cases/evidence/TC-order-002/ | |
| TC-order-003 | 実行不能 | | |
| TC-order-010 | 実行不能 | | |

## 実行の条件

- 対象: cases/order.md の TC-order-001〜003、010
- コマンド: test_commands の e2e（`npx playwright test --project=cases --grep "TC-order-00[1-3]"`、automation/web で実行）
- 環境変数: QA_ENV=new、QA_BASE_URL はプロファイルの new の url、QA_RUN_DIR=runs/20261118-new-cases。資格情報は環境変数の名前（SAMPLE_BUYER_USER、SAMPLE_BUYER_PASSWORD）だけを書き、値は書かない
- 確かめたこと: e2e のコマンドはデータの初期化を含まないことを読んで確かめた
- テストのコードの版: QA リポジトリのコミット 1a2b3c4（未コミットの変更があればその旨）
- セッション: 実行の直前に aidev-qa-login-session で作り直した

## NG の詳細

### TC-order-002 数量が上限を 1 超えると注文できない
- AC: AC-022
- テスト: automation/web/tests/order.spec.ts の「TC-order-002 …」
- 再現手順
  1. 購入者のロール（SAMPLE_BUYER_USER）でログインする
  2. 商品の詳細画面（商品コード P-0001）で数量に 100 を入れ、注文を押す
- 期待結果: 注文されず、数量の欄の下に「数量は 99 以下にしてください」と表示される
- 実際の結果: 注文履歴の画面に移り、数量 100 の注文が先頭の行に出た。エラーの表示はなかった
- 証跡: runs/20261118-new-cases/evidence/TC-order-002/（02-after-submit.png、02-after-submit.values.json）
- 再現: 3回とも同じ
- 補足: 期待結果の誤りの可能性は低い（設計書 4.2 に上限 99 の記載がある）

## 実行不能の理由

### TC-order-003
- 理由: 前提の在庫切れの商品が環境にない
- 実行できるようにする手段: 在庫 0 の商品を用意する（データの投入には承認が要る）

### TC-order-010
- 理由: 手動確認待ち（実行が「手動」のケース）。手動確認の項目に再現手順を書いた

## 手動確認の項目

### TC-order-010 注文の確認メールの文面が設計どおりである
- 手動にした理由: メールの受信箱にテストから届かない
- 再現手順
  1. 購入者のロール（SAMPLE_BUYER_USER）でログインし、任意の商品を 1 個注文する
  2. テスト用のメールの受信箱を開く
- 確かめる点: 件名が「ご注文ありがとうございます」で、本文に注文番号と数量が入っている
- 撮る証跡: 受信したメールの画面。個人情報は隠す
- 結果: （確かめた人が OK か NG と証跡を書き、表の行も書き換える）

## 失敗を検出できるかの確認

| TC-ID | 変えたこと | 失敗のしかた | 戻したあと |
|---|---|---|---|
| TC-order-001 | 期待する見出しを「注文を受け付けませんでした」に変えた（変える前に git add し、QA_RUN_DIR は .qa-scratch/ の下に向けた） | 見出しの不一致で失敗 | 戻して緑。インデックスとの git diff で差分なし |

## 流し直しの記録

| TC-ID | 回 | 結果 | 打った手 |
|---|---|---|---|
| TC-order-002 | 1 | 食い違い | - |
| TC-order-002 | 2 | 食い違い | 商品の在庫と上限の設定を画面で確かめ直した |
| TC-order-002 | 3 | 食い違い | セッションを作り直した |

## 新しく書いた、または直したテスト

- automation/web/tests/order.spec.ts（TC-order-001、002 を追加。未コミット）

## 残ったテストデータ

- 接頭辞 QA-new-cases- の注文 2 件（注文の画面に削除の操作がないため消せない。書き込む前の承認で作業者に伝えた）
```

例の値（環境名、版、商品、環境変数の名前）は説明のためのもので、実際の値は案件のプロファイルと実行の記録から書く。

## 冒頭

- 環境はプロファイルの `environments` の name で書く。URL は書かない
- 版は、画面の表示、デプロイの識別子、コミットのハッシュのうち、確かめたものを書き、何で確かめたかを添える。分からなければ「不明」と書いて作業者に伝え、推測で埋めない
- 実行日時は、記憶ではなくテストの実行の記録（実行の出力、テストの結果のファイルの時刻）から書く

## 表

- 結果は OK、NG、実行不能のどれかだけを書く。「要確認」や「未実施」を結果の欄に書かない
- 証跡の列には、リポジトリのルートからの相対パスで、ケースの証跡のディレクトリを書く。`evidence.method` が `local` か `external` なら、リポジトリの外の保存先のパスを書く
- 証跡の列に書くのは、最終の結果にした実行の証跡だけにする。直しながら流した途中の実行や失敗を確かめる実行の証跡は `.qa-scratch/` などの Git に入らない場所に置き、ここに書かない
- 実行不能のケースは、証跡を空にしてよい。途中まで進んで撮ったものがあれば書く
- 手動のケースと自動から手動に回したケースは、実行不能にして理由を「手動確認待ち」と書く。人が確かめて OK か NG を記録するまで、そのままにする
- Issue の列は空けておく。起票した番号は、起票する aidev-qa-bug-ticket が書く

## NG の詳細

NG のケースごとに、起票する人がこの節だけを読んで Issue を書ける情報を残す。

- AC：ケースの AC の行のまま
- テスト：失敗したテストのファイルとテスト名
- 再現手順：ケースの手順に、実際に使ったロール、データ、入力の値を足したもの。アカウントは環境変数の名前で示し、パスワードを書かない
- 期待結果：ケースの期待結果の文面のまま。言い換えない
- 実際の結果：観測した値、画面の表示、API の状態コードとエラーのメッセージを、出力からそのまま写す
- 証跡：ディレクトリと、食い違いが写っているファイルの名前
- 再現：流した回数と、毎回同じだったか。毎回は出なかったときは、再現した割合（例 3回中2回）と「⚠ 要確認: 間欠的な不具合の可能性」を書き、食い違いが見えた回の証跡を示す
- 補足：期待結果の誤りの可能性、影響の範囲、関係しそうな他のケースなど、判断の材料になること

## 残ったテストデータ

テストが作った記録で、消せなかったもの（後始末に失敗した、アプリに削除の操作がない）を、接頭辞、件数、場所で書く。個人の値や ID の値は書かない。何も残っていなければ節を省いてよいが、後始末を検索で確かめたことは実行の条件に書く。決まりは SKILL.md の「データの状態と流し直し」にある。

## 秘密情報

result.md はリポジトリの履歴に残り、作業者以外も読む。資格情報、Cookie、トークン、セッションの ID を書かない。実行の条件に写すコマンドにも値を入れない。資格情報は環境変数で渡し、名前だけを書く。URL にトークンが付くときは、クエリの値を伏せてから書く。テストのトレースへのリンクを証跡として書かない。
