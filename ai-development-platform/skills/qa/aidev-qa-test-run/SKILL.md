# テストケースの実行

## Overview

テストケースの期待結果を正として、実装がそのとおりに動くかを実際に流して確かめ、ケースごとの結果を確定させる。結果の正本は `runs/<YYYYMMDD>-<run-id>/result.md` で、後続の工程（不具合の起票、改修の確認、AC との対応の検査）はこのファイルを読む。

この Skill の仕事は、ケースを流すことと、結果を誤りなく分けることである。自動のケースは `automation/` のテストで実行し、テストがなければ書く。手動のケースは実行せず、人が追える確認項目にする。結果は OK、NG、実行不能の3つに分ける。NG はアプリの挙動が期待結果と違うこと、実行不能は環境や前提のせいで確かめられなかったことで、この2つを取り違えると、不具合を見逃すか、存在しない不具合を起票することになる。

緑のテストが、期待結果を本当に確かめているとは限らない。新しく書いたテストは、一度わざと失敗させて検出できることを見てから結果に使う。

## When to Use

- テスト仕様書（`cases/*.md`）の全部または一部の TC-ID を、ある環境に対して実行する
- 新しい版がデプロイされたので、既存のケースを流し直して結果をまとめる
- 自動のケースにテストがまだないので、書いてから実行する

使わない場面は次のとおり。

- AC からテストケースを作るときは aidev-qa-test-design を、作ったケースのレビューは aidev-qa-test-review を使う
- 仕様ではなく今の実装の挙動を画面ごとに記録するときは aidev-qa-characterization を使う
- 同じテストを旧版と新版に流して差異を分けるときは aidev-qa-regression-compare を使う
- ロールと操作の可否の表を作り、拒否されるべき操作を網羅的に確かめるときは aidev-qa-authz-test を使う
- ロールごとのログイン済みのセッションは aidev-qa-login-session で作る。この Skill はそれを使う側である
- Windows のダイアログやネイティブの画面を操作するテストを新しく書くときは aidev-qa-desktop-gui を使う。書かれたテストを `test_commands` で流すのはこの Skill でよい
- NG からの Issue の起票（aidev-qa-bug-ticket）と、修正後の確認（aidev-qa-fix-verify）は、後の段階で追加する予定で、まだない

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`test_commands`（テストの実行方法）を使う。あれば `environments`（実行する環境）、`login`（ログイン方式）、`stack`（テストの道具の選び方）、`evidence`（証跡の保存方式）も使い、本文の到達手順、テストデータの準備方法、落とし穴も読む
- `cases/*.md` と、実行する TC-ID の範囲（全部か、作業者が指定した一部か）
- `plan/acceptance.md` と、期待結果があいまいなときに裏取りする設計書
- `automation/` の既存のテスト

出力は次のとおり。

- `runs/<YYYYMMDD>-<run-id>/result.md`。形式は `references/result-format.md` に書いた。冒頭に環境名、版、実行日時を書き、TC-ID ごとに1行で結果と証跡を書く。Issue の列は空けておく
- 証跡 `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/`（`evidence.method` が `local` か `external` なら、リポジトリの外の同じ構成の場所）
- 新しく書いた、または直したテストのコード（`automation/web/tests/<機能>.spec.ts` など）。テスト名の先頭に TC-ID を付ける。コミットするかは作業者が決める
- 作業者への返答。NG を先頭に、結果の件数、手動確認の項目の数、新しく書いたテストのパス、要確認の点を書く

HTML のレポートは作らない。結果を表で見たいときは、後の段階で追加する予定の `aidev qa trace --html` と aidev-qa-report を使う（まだない）。作業者が求めたときだけ、result.md をもとに HTML を作って公開する。

## 進め方

### 1. プロファイルと実行の条件を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-test-run` で検査する。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

次に、実行の条件を決める。決まらないものは作業者に確かめ、推測で埋めない。

- どの環境で流すか。プロファイルの `environments` の name で指す
- その環境の版を何で特定するか（画面に出る版の表示、デプロイの識別子、コミットのハッシュ）。版の分からない結果は、後で改修の前か後かを区別できない
- 実行する TC-ID の範囲
- ケースの場所に合う `test_commands` のどの項目を使うか。項目の `run` をどのディレクトリで実行するかが分からなければ、QA リポジトリの README か作業者に確かめる

プロファイルの `login.method` が `none` でなければ、実行の直前に aidev-qa-login-session でロールごとのセッションを作り直す。前回のセッションを使い回すと、期限切れでログイン画面に落ち、実行不能のはずの結果を NG と取り違える。

### 2. ケースを読み、実行の仕方を決める

`cases/*.md` から対象のケースを読み、TC-ID、AC、手順、期待結果、備考を取り出す。ケースの形式は QA リポジトリの `cases/README.md` にある。

実行が「自動」のケースはテストで流す。ただし、実際に自動化してみて、外部のシステムに届かない、実機が要る、見た目の判断が要る、と分かったものは手動の確認項目に回し、理由を result.md に書く。黙って自動のまま実行不能にしない。実行が「手動」のケースは、この Skill では流さず、手動確認の項目にする。ケースの「実行」の欄そのものは書き換えない。書き換えたほうがよいと思えば、理由を添えて作業者に提案する。

期待結果があいまいで、テストの判定に落とせないケースは、`plan/acceptance.md` と設計書で裏取りする。それでも決まらなければ「⚠ 要確認」として作業者に確かめる。確かめる間、そのケースを都合のよい解釈で流さない。

### 3. 既存のテストを探し、なければ書く

まず `automation/` を TC-ID で検索する。テスト名の先頭に TC-ID を付ける決まりなので、見つかればそれが候補である。見つかったら、流す前にアサーションを読み、ケースの今の期待結果を確かめているかを見る。ケースが改訂されてテストが古いまま、ということがある。期待結果より緩い確かめ方（応答があったことだけ、画面が開いたことだけ）なら、ケースに合わせて直す。

テストがなければ書く。置き場所と書き方は次のとおり。

- Web の画面や API のケースは `automation/web/tests/<機能>.spec.ts` に Playwright で書く。設定、環境の渡し方、対象の画面にいることの確かめ方、証跡の撮り方は、aidev-qa-characterization の Playwright と証跡の資料に合わせる。実行する環境は `QA_ENV`（プロファイルの環境名）と `QA_BASE_URL` で渡し、URL をテストに書かない。ロールは aidev-qa-login-session の `authFile()` で storageState を選ぶ。証跡は環境変数 `QA_RUN_DIR` が指す run のディレクトリの `evidence/<TC-ID>/` に書く
- デスクトップの GUI のケースは aidev-qa-desktop-gui の書き方で `automation/desktop/` に置く
- それ以外の道具（API のテストの仕組みなど）は、プロファイルの `stack` と `test_commands`、すでにあるテストの作法に合わせる
- 画面や API を通さないと確かめられない内部のロジックのケースで、製品のリポジトリの単体テストとして書くほうが自然なら、置き場所を作業者に確かめる。製品のコードそのものは変えない

1つの TC には1つのテストを対応させ、テスト名の先頭に TC-ID を付ける。複数のケースを1つのテストにまとめると、1つの失敗で残りの結果が分からなくなる。ロールなどの組み合わせを表から生成するときも、生成されるテストの名前ごとに TC-ID を付ける。

テストの期待値は、ケースの手順と期待結果からそのまま作る。実装を流して出てきた値を後から期待値に写さない。それは実装を正とすることで、期待結果と違う挙動を見逃す。期待結果と実装が食い違ったら、テストは失敗させたままにして NG の候補にする。作成日時や採番された ID のように実行ごとに変わる値は、ケースが値そのものを求めていなければ、形式（日時の書式、ID の桁）を確かめる。画面マニフェストの `normalize` に規則があればそれに合わせる。変わる値を理由に、その項目の確かめを外さない。

データを作る、変える、消すケースは、使ってよい環境とデータの範囲、後始末の方法を作業者に示して承認を得てから流す。テストで作るデータには実行ごとに一意の接頭辞を付け、後始末はそのデータだけにする。テストデータに実在の個人情報を使わない。検索や一覧のケースは、結果が0件では中身を確かめられないので、複数の行が出るデータで流す（0件の表示を確かめるケースを除く）。

### 4. 新しいテストが失敗を検出できるかを確かめる

新しく書いたテストと、確かめ方を変えたテストは、期待結果を確かめていることを、一度失敗させて確かめる。やり方は次のどちらかである。

- 期待値を逆にする。「403 になる」なら一時的に「200 になる」に変える。「一覧に出る」なら「出ない」に変える。テストが失敗し、その失敗のメッセージが変えた期待値を指していることを見る
- 作業者の手元で動かしているアプリなら、不具合を注入する（権限の判定を外す、など）。注入は作業者の承認を得てから行い、共有の環境では行わない

変える前に、戻したことを確かめられる状態にしておく。新しいテストのファイルは Git がまだ追跡していないので、そのままでは `git diff` に何も出ず、逆にした期待値が残っても気づけない。変える前に `git add` でインデックスに入れるか、ファイルの写しを取っておく。不具合を注入する製品のリポジトリでも、変える前の状態を同じように押さえる。

失敗を確かめる実行では、`QA_RUN_DIR` を `test-results/` の下などの Git に入らない場所に向ける。このときのスクリーンショットを証跡にしないためである。失敗を見たら元に戻し、`git diff`（インデックスとの差）か写しとの比較で戻し漏れがないことを確かめてから、もう一度流して元の結果に戻ったことを見る。不具合を注入したなら、製品のリポジトリでも同じ確かめをする。失敗しなかったテストは、アサーションが効いていないか、対象の画面に着いていない。直してから結果に使う。何をどう変え、どう失敗したかは result.md に書く。

新しいテストが最初から失敗して NG の候補になったときは、失敗の理由が期待結果との食い違いであることを、失敗のメッセージと証跡で確かめる。期待どおりに動く版（旧版など）があれば、そこで緑になることも見ると、テストの側の誤りを除ける。

### 5. 実行する

`test_commands` の `run` を使い、対象の TC-ID に絞って流す。絞り方は道具によって違う（Playwright の `--grep`、`dotnet test` の `--filter` など）。

流す前に、`run` の中身とそれが呼ぶスクリプトを読む。データを初期化する、投入する、消す処理を含むもの、共有の環境や本番の環境に向くものは、何が起きるかを作業者に示して確かめてから流す。資格情報はプロファイルに名前がある環境変数で渡し、コマンドの引数に書かない。引数はシェルの履歴やプロセスの一覧に残り、result.md に写したコマンドにも入ってしまう。

最終の結果にする実行では、run-id を決めて `runs/<YYYYMMDD>-<run-id>/` を作り、そのパスを `QA_RUN_DIR` に設定してから流す。`evidence.method` が `local` か `external` なら、リポジトリの外の同じ構成の場所を指す。run のディレクトリは空の状態から書く。テストを直しながら流す途中の実行は、`QA_RUN_DIR` を Git に入らない場所に向け、`runs/` に残さない。result.md が参照するのは最終の実行の証跡だけである。

- テストの設定の自動の再試行は切る（Playwright なら `retries: 0`）。再試行で通ったテストは不安定さを隠し、更新を伴うケースでは二重の登録を起こす。流し直すかどうかは次の節の基準で決める
- PC の操作を占有するデスクトップのテストは、Web のテストと同時に流さない
- 証跡は、テストの中で `$QA_RUN_DIR/evidence/<TC-ID>/` に保存する。期待結果を確かめた時点の画面のスクリーンショット、画面の値、API の応答（状態コードと本文。ヘッダーは保存しない）を残す。NG のケースでは、食い違いが見える状態を残す
- テストのトレースは通信のヘッダーと Cookie を含むので、証跡にしない。`test-results/` に置いたまま診断に使う
- 撮ったスクリーンショットは開いて見る。ログイン画面、エラー画面、読み込みの途中、0件の画面を撮っていないか、資格情報やトークンが写っていないかを確かめる

### 6. 結果を判定する

失敗したテストは、まず失敗の性質を分ける。テストのコードの不具合（セレクタが合わない、待ち方が足りない、期待値の転記の誤り）なら結果にせず、直して流し直す。失敗した実行の証跡は、診断用として `test-results/` などの Git に入らない場所（例 `test-results/_failed-<時刻>/`）に移してから直す。`runs/` の下には置かない。テストのコードを直したら、そのテストは4の確かめをやり直す。

残りを、次の基準で OK、NG、実行不能に分ける。

| 結果 | 基準 |
|---|---|
| OK | 対象の画面や API に正しく着き、期待結果のすべての項目を確かめて、アサーションが通った |
| NG | 対象に正しく着き、操作もできたが、観測した挙動が期待結果と違った。同じ条件でもう一度流しても同じ食い違いが出た（毎回は出ない食い違いは下の流し直しの基準による） |
| 実行不能 | 環境、データ、セッション、外部の要因のせいで、期待結果を確かめるところまで進めなかった。手動のケースもここに入れる |

実行不能に当たるのは、たとえば次の場合である。環境が応答しない、デプロイの途中だった。ログイン画面や IdP に落ちた（セッションの期限切れ、アカウントのロック）。前提のデータがない、他の人の操作でデータが変わった。外部のシステムに届かない。実機や人の判断が要る。

見分けに迷うのは、エラーが画面に出たときである。対象の画面に着いたうえでアプリがエラーを返したなら、それは挙動の食い違いなので NG である。権限がないと拒否されたときは、ケースの期待結果が拒否なら OK、許可なら NG で、どちらも実行不能ではない。ただし、拒否の原因がセッションの期限切れなら実行不能にしてセッションを作り直す。

流し直しは、最初の実行のあとに2回までにする。流し直す前に、疑った原因（セッション、環境、データ）を確かめて手を打ち、何をしたかを記録する。原因に手を打たずに緑になるまで流し直さない。

- 3回とも同じ食い違いなら NG、3回とも同じ環境の理由なら実行不能
- 結果が割れ、どこかの回で対象に正しく着いたうえで期待結果との食い違いが見えたなら、間欠的な不具合の可能性がある。NG にして再現した割合（例 3回中2回）を書き、「⚠ 要確認: 間欠的な不具合の可能性」として NG の詳細の形で食い違いを残す。通った回があっても OK にしない
- 結果が割れ、食い違いは一度も見えず（時間切れ、環境の応答なし、など）、原因が特定できなければ、不安定として実行不能にする。OK にしない
- どちらの場合も、各回の結果を result.md に残す
- 原因がテストのコードの待ち方だと分かったら、テストを直してから流し直す。これは回数に数えない
- 更新を伴うケースは、結果が分からないまま流し直さない。先に画面でデータの状態を確かめる

期待結果そのものが誤っている疑いがあっても、NG のまま記録し、「期待結果の誤りの可能性」と根拠を書いて作業者に伝える。期待値を実装に合わせて書き換えて OK にしない。

### 7. 手動確認の項目を書く

実行が「手動」のケースと、自動から手動に回したケースは、結果を実行不能にして理由を「手動確認待ち」と書き、result.md の手動確認の項目に再現手順を書く。人が OK か NG を記録するまで、実行不能のままにする。人がそのまま追えるように、ロール（アカウントはプロファイルの環境変数の名前で示す）、開く画面と経路、入力する値、確かめる点（期待結果）、撮る証跡を具体的に書く。なぜ自動にしなかったかも添える。人が確かめたら、その結果と証跡で行を OK か NG に書き換える。

### 8. NG の情報を残し、報告する

NG のケースごとに、後で Issue を起票するのに要る情報を result.md に残す。起票する aidev-qa-bug-ticket は後の段階で追加する予定で、まだないので、この Skill は起票せず、Issue の列も空けておく。残す項目は `references/result-format.md` にある。要点は、ケースの手順に実際に使ったデータを足した再現手順、期待結果（ケースの文面のまま）と実際の結果（観測した値やメッセージをそのまま）、証跡の場所、失敗したテストのファイルと名前、再現した回数である。

最後に作業者へ報告する。NG があれば先頭に書き、結果ごとの件数、手動確認の項目の数、新しく書いたテストのパス、失敗を検出できるかを確かめた結果、要確認の点を書く。数値やメッセージは実行の出力から写し、要約で作り直さない。

## よくある誤り

- 実装を流して出た値をテストの期待値に写し、期待結果と違う挙動を OK にする
- ログイン画面に落ちたまま流し、拒否や空の表示を NG と判定する。またはテストが通ったことにする
- テストのコードの不具合で落ちたものを NG にして起票の候補にする
- 原因を確かめずに流し直し、通った回だけを見て OK にする
- 既存のテストを TC-ID だけで信用し、改訂後の期待結果を確かめているかを読まない
