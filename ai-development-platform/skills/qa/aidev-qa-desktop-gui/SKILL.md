# Windows の GUI のテスト

## Overview

Windows のデスクトップアプリのテストケースを、実際に動いているアプリの GUI を操作して確かめる。テストは FlaUI（UIA3）を使う C# のテストプロジェクトとして QA リポジトリの `automation/desktop/` に置き、テスト名の先頭に TC-ID を付ける。結果と証跡の形は aidev-qa-test-run と同じで、`runs/<YYYYMMDD>-<run-id>/result.md` と `evidence/<TC-ID>/` に残す。

デスクトップの GUI のテストは、Web のテストと違って作業者の PC そのものを動かす。フォーカスを奪い、ダイアログを開き、ファイルを書く。誤ると作業者の別のアプリを操作したり、作業者のフォルダにファイルを作ったりする。この Skill は、テストの書き方と同じくらい、何に触れてよいかの線引きを扱う。触れてよいのは、今回起動したアプリのプロセスと、そのアプリが開いたダイアログだけである。

モーダルのダイアログは、出る場所が作り方で変わり、同期で開くものは UIA の呼び出しを止めることもある。見つからない、返らない、を「アプリの不具合」と取り違えないように、検出の仕方を `references/dialogs.md` と `references/flaui.md` にまとめた。

## When to Use

- 画面の操作が要るデスクトップアプリのケース（行の選択、ボタン、メニュー、確認のダイアログ）を自動のテストにする
- 保存・フォルダ選択・印刷のダイアログ、帳票のビューア、外部アプリ、IME を伴うケースを確かめる
- デスクトップアプリのネイティブのログイン画面や、証明書の選択のダイアログが出るログインを通す
- WebView2 の画面の記録から `native-required` として渡された操作を確かめる
- メッセージボックスが見つからない、操作が返らない、といった FlaUI のテストの不安定さを調べる

使わない場面は次のとおり。

- 書かれたデスクトップのテストを、他のケースと一緒にプロファイルの `test_commands` で流して結果をまとめるだけなら aidev-qa-test-run でよい
- WebView2 の中の DOM の操作と画面の記録は aidev-qa-characterization を使う。この Skill は WebView2 の外の操作を受け持つ
- ブラウザのロールごとのログインのセッションと、証明書が PC にあるかの確認は aidev-qa-login-session を使う
- テストケースを作るのは aidev-qa-test-design、旧版と新版の照合は aidev-qa-regression-compare を使う
- GUI を通さずに確かめられるロジックは、製品のリポジトリの単体テストのほうが速く安定する。置き場所を作業者に確かめる

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`stack`（WPF、WinForms、WebView2 などの画面の技術）と `evidence`（証跡の保存方式）を使う。あれば `test_commands`（テストの実行方法）、`environments`（アプリがつながるサーバー）、`roles`（ログインのアカウントの環境変数の名前）、`login`（証明書方式なら `certificate_thumbprint`）も使う。本文のビルドと起動の手順、AutomationId の一覧、落とし穴も読む
- `cases/*.md` の対象の TC-ID と、`plan/acceptance.md`
- 対象のアプリのソース（ダイアログのタイトルと文言、AutomationId を確かめる）と、起動する exe
- aidev-qa-characterization の画面マニフェストのうち、`native-required` として渡された項目（あれば）

出力は次のとおり。

- テストのコード `automation/desktop/`（C# のテストプロジェクト）。テストメソッドの名前か表示名の先頭に TC-ID を付ける。コミットするかは作業者が決める
- `runs/<YYYYMMDD>-<run-id>/result.md` と証跡 `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/`。result.md の書き方は aidev-qa-test-run の result.md の資料に合わせ、デスクトップに固有の実行の条件（下の8）を足す
- ネイティブの接点の一覧（下の2）。result.md の節として書く
- 作業者への返答。NG を先頭に、結果の件数、手動確認の項目、未カバーの接点、PC の占有の始まりと終わり、片付けの状態を書く

## 進め方

### 1. プロファイルと実行の条件を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-desktop-gui` で検査する。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

次に、次のことを決める。決まらないものは作業者に確かめ、推測で埋めない。

- 起動する exe と、その版を何で特定するか（ファイルの版、ビルドのコミット、画面の表示）
- アプリがサーバーにつながるなら、どの環境に向けるか（プロファイルの `environments` の name）。result.md の冒頭の「環境」には、プロファイルに `environments` があればその name を書き、なければ exe の名前とファイルの版を書く（例 `<アプリ>.exe 1.4.2.0`）。ビルドのコミットは実行の条件に書いてよい
- 実行する TC-ID の範囲
- アプリが設定やデータをどこに置くか。実行ファイルの横か、`%APPDATA%` などか。テストのたびに初期の状態に戻す方法と、作業者のデータと分ける方法

`stack` に `webview2` があるなら、aidev-qa-characterization の WebView2 の資料も読む。WebView2 の中と外の境目はそこに書いてある。

### 2. ネイティブの接点を洗い出す

作業者が挙げたケースだけで範囲を決めない。PC を占有しない段階で、アプリのソースから Windows 側に出る接点を洗い出す。保存・フォルダ選択・印刷のダイアログ、メッセージボックス、ビューアや外部アプリの起動、IME を使う入力欄、ネイティブのログイン画面、証明書の選択である。

接点ごとに、画面、到達の手順、ダイアログの種類、対応する TC-ID を一覧にし、result.md の「ネイティブの接点」の節に書く。TC-ID のない接点は「未カバー」とし、ケースを足すかを作業者に確かめる。ソースだけで分からない接点（プラグインが出すものなど）は、実物の UIA のツリーで確かめ、確かめられなければ「要確認」として残す。

接点の種類ごとに、ケースにする観点の目安は次のとおり。要らない観点は理由を残して外す。

| 接点 | 観点 |
|---|---|
| 保存・フォルダ選択 | 正常、キャンセル、既存のファイルの上書きの確認、日本語や長いファイル名、書き込めない保存先 |
| 確認のメッセージボックス | はい・いいえ・キャンセルの各分岐と、その後の画面とデータの状態 |
| 警告のメッセージボックス | 出る条件で出ること、確認が出ないこと、データが変わらないこと |
| 帳票のビューア・外部アプリ | ファイルの種類ごとの表示、今回の文書を開いていること、既存のインスタンスとの共有 |
| 印刷 | 認められた仮想のプリンターへの出力、キャンセル |
| IME | 変換、確定、取り消しと、入力欄ごとの確定の結果 |

### 3. PC の占有を作業者と決める

テストを書く、ビルドする、要素のツリーを調べる、結果をまとめる、といった作業は PC を占有せずに進める。GUI のテストを流すのは、作業者と時間を決めてからにする。Skill を作る依頼やテストを書く依頼を、GUI を流してよいという許可とは扱わない。

流す前に、対象のケース、前面に出るウィンドウやキー入力の有無、かかる時間の目安、止める条件を作業者に示す。作業者がその時間 PC を空けると言っていれば、改めて聞かない。決まっていなければ、この PC で今流すか、専用の Windows の PC や仮想マシンで流すかを確かめる。

- デスクトップのテストは、Web のテストや他のデスクトップのテストと同時に流さない。UIA の操作だけでフォーカスを使わない場合も、占有として扱う
- 画面がロックされた状態や、サービスのセッション、切断した RDP のセッションで GUI が安定して動くと仮定しない。UIA のパターンの操作はロック中でも通ることがあるが、スクリーンショットにはロック画面が写り、キー入力は届かない。流している間は画面のロックと人の入力を避けてもらう
- 最初のケースの前に、入力のデスクトップが使えること（セッションが接続中でロックされていないことを WTS のセッションの状態で見る、入力のデスクトップを開ける）と、起動したアプリのウィンドウを前面にでき、前面のウィンドウがその PID のものであることを確かめる（`references/flaui.md` の「流す前の確かめ」）。確かめられなければそこで止め、残りのケースを実行不能にして作業者に伝える。ロック画面を撮った証跡を作らない
- 占有の始まりと終わりを作業者に伝える。止めてと言われたら、新しい操作を始めず、途中の保存や更新の状態を確かめてから止める
- 終わりが近づいたら、片付けの時間を残して新しいケースを始めない。残ったケースは実行不能（時間切れ）として報告する

### 4. テストを書く

`references/flaui.md` に従って `automation/desktop/` にテストを書く。要点は次のとおり。

- 1つの TC に1つのテストを対応させ、テストメソッドの名前か表示名の先頭に TC-ID を付ける。分岐（はい・いいえ）は別の TC にする
- 起動する exe は環境変数 `QA_APP_EXE`、run のディレクトリは `QA_RUN_DIR` で渡す。パスをテストに書かない
- テストごとにアプリを起動し、今回起動したプロセスの ID とそのウィンドウだけを操作する。既に動いている同じアプリのプロセスには接続しない。作業者のデータと設定を分けられないなら、流さずに作業者に伝える
- 操作は UIA のパターン（Invoke、SelectionItem、Toggle、Value）で行う。座標のクリックやキー入力は、パターンで操作できないとき、または実際のキー入力でないと確かめられないとき（保存のダイアログのファイル名、IME）だけにする
- 要素は AutomationId を優先し、名前で探すときは ControlType と組み合わせ、探す起点をアプリのウィンドウかダイアログにする。デスクトップ全体から「保存」「はい」の名前で最初の要素を拾わない。作業者の別のアプリを操作することになる
- ダイアログのタイトルと文言は、呼び出し元のコードから取る。期待値はケースの期待結果からそのまま作り、アプリを動かして出た値を写さない
- 操作の後は、観測できる条件（ダイアログが出た・閉じた、ステータスが変わった、ファイルが書き終わった）を期限付きで待つ。期限は代表のケースで測って決める
- データを作る、変える、消すケースは、使ってよいデータの範囲と戻し方を作業者に示して承認を得てから流す。ファイルを書くケースは、`AppSession` がテストごとに作る `%TEMP%\qa-desktop-<guid>\out\<TC-ID>\`（`OutDir`）にだけ書く。`runs/` に直接書かせず、残したいファイルは確かめた後に証跡のディレクトリへ写す

本格的に書き始める前に、代表のケースを1つ書いて流し、要素の探し方、ダイアログの検出、証跡の撮影が実機で動くことを確かめる。動いてから他のケースに広げる。

### 5. ダイアログを確かめる

メッセージボックス、保存・フォルダ選択・印刷のダイアログ、外部アプリ、IME の扱いは `references/dialogs.md` に従う。とくに次の点で誤りやすい。

- ダイアログは、所有ウィンドウの子を先に探し、なければデスクトップの直下を対象の PID で絞って探す。メッセージボックスのタイトルは本体と同じことが多いので、本体のハンドルを除く
- 同期で開くメッセージボックスで操作が返らないときは、操作を別のスレッドで発火し、Win32 の API で検出する。発火したタスクは、ダイアログを閉じた後に終わったことを確かめる
- 保存のダイアログでは、`OutDir` の下の保存先の絶対パスをキー入力で入れる（入力の前に IME を直接入力にする）。保存の前にダイアログが表示しているフォルダと、その中の同じ名前に合うファイルを記録し、保存の後に、指定したパスにファイルができたことと、記録したフォルダに新しいファイルが増えていないことを確かめる
- 期待していないダイアログが出たら、ケースを止めて画像を撮る。閉じるために勝手にボタンを押さない

### 6. 新しいテストが失敗を検出できるかを確かめる

新しく書いたテストと、確かめ方を変えたテストは、一度わざと失敗させて検出できることを確かめる。期待値を逆にする（「警告が出る」を別の文言に変える、「行が消える」を「行が残る」に変える）か、作業者の承認を得て手元のアプリに不具合を注入する。失敗のメッセージが変えた期待値を指していることを見る。

変える前に `git add` でインデックスに入れるか、写しを取っておく。新しいファイルは Git が追跡していないので、そのままでは戻し漏れに気づけない。失敗を確かめる実行では、`QA_RUN_DIR` を `.qa-scratch/` の下などの Git に入らない場所に向ける。戻したら差分がないことを確かめ、もう一度流して緑に戻ったことを見る。何をどう変え、どう失敗したかは result.md に書く。失敗しなかったテストは、アサーションが効いていないか、対象の画面やダイアログに着いていない。

### 7. 流して証跡を撮る

最終の結果にする実行では、run-id を決めて空の `runs/<YYYYMMDD>-<run-id>/` を作り、`QA_RUN_DIR` に設定してから流す。プロファイルの `evidence.method` が `local` か `external` なら、リポジトリの外の同じ構成の場所を指す。テストを直しながら流す途中の実行は、`QA_RUN_DIR` を Git に入らない場所に向け、`runs/` に残さない。失敗した実行の証跡は、診断用として `.qa-scratch/failed-<時刻>/` などに移してから直す。流し直すときは新しい run-id の run に全ケースを流す（aidev-qa-test-run の「データの状態と流し直し」）。

- テストの自動の再試行は切る。流し直すかどうかは aidev-qa-test-run の基準で決める
- 証跡は `$QA_RUN_DIR/evidence/<TC-ID>/` に、checkpoint の名前で保存する。期待結果を確かめた時点の画面、画面に出た値（`<checkpoint>.values.json`）、保存したファイルの写しを残す。NG のケースは食い違いが見える状態を残す
- 画像は、アプリのウィンドウかダイアログの範囲だけを撮る。全画面は撮らない。他のアプリのウィンドウや通知に個人の情報が出ていることがある。対象のモニターや領域を限った全画面の撮影が要るときは、理由を result.md に書く
- 保存のダイアログの画像には、作業者のフォルダの名前やファイルの一覧が写る。撮るなら今回の空のフォルダを表示した状態にし、それでも写るなら撮らずに値だけを残す
- 撮った画像は開いて見る。ロック画面、他のウィンドウの重なり、開きかけのダイアログ、端に写り込んだ後ろの画面、0件の一覧、資格情報が写っていないかを確かめる。崩れていれば撮り方か待ち方を直して流し直す
- OK だけのメッセージボックスは、撮影と本文の記録の後、判定のアサートの前に閉じる（`references/dialogs.md` の「メッセージボックス」）。開いたまま失敗すると、アプリが閉じられずに残る

### 8. 結果を書く

結果は aidev-qa-test-run と同じく OK、NG、実行不能に分け、result.md の形もそれに合わせる。基準は同じで、対象の画面やダイアログに正しく着き、期待結果のすべての項目を確かめて通れば OK、着いて操作できたが挙動が期待結果と違えば NG、環境や前提のせいで確かめるところまで進めなければ実行不能である。

デスクトップで実行不能に当たるのは、たとえば次の場合である。exe が起動しない、ログインで止まった（PIN を作業者が入れられなかった、など）、PC がロックされて撮影やキー入力ができなかった、作業者のデータと分けられなかった、占有の時間が終わった、UIA で要素が見えず手動に回した。UIA の期限切れやダイアログの検出の失敗は、テストのコードの待ち方の不足であることが多い。アプリの不具合と決める前に、ダイアログが出たままの画像と、ツリーを書き出した結果で確かめる。

result.md の実行の条件には、aidev-qa-test-run の項目に加えて次を書く。

- exe のパスと版、起動したプロセスの ID
- PC の名前ではなく種類（作業者の PC、専用の PC、仮想マシン）、モニターの構成（解像度、位置、表示倍率）、OS の言語
- 待ちの期限と、その決め方
- PC の占有の始まりと終わり、片付けの結果

手動に回したケースは、理由を「手動確認待ち」と書いて実行不能にし、人がそのまま追える再現手順を手動確認の項目に書く。

### 9. 片付ける

- 今回起動したプロセスだけを、ウィンドウを閉じる操作で終える。閉じなければ強制終了せず、画面を撮って作業者に伝える。同じ名前のプロセスをまとめて終了させない
- 退避した設定を戻し、戻ったことを確かめる。IME などの状態を変えたら戻す
- 今回作った一時のフォルダとファイルだけを消す。消す前に、そのパスが `%TEMP%\qa-desktop-<guid>\`（今回の `WorkDir`）の中であることを確かめる。`runs/` は片付けの対象にしない。消せなかったフォルダ、閉じなかったプロセスは、result.md と作業者への報告に書く。既定のフォルダなどにファイルを作ってしまったら、作業者に伝えてから片付ける
- 保存のダイアログを使ったら、アプリが最後に使ったフォルダとしてテストの一時フォルダを覚えていることを作業者に伝える。この履歴はレジストリを書き換えて消さない
- 最後に、残っているウィンドウ、戻した設定、PC をもう使えるかを作業者に伝える

## ログインと証明書

プロファイルの `login.method` が `none` でなければ、アプリのログインもこの Skill で扱う。

ネイティブのログイン画面に ID とパスワードを入れるのは、テストのコードがプロファイルの `roles` に名前がある環境変数から読んで行う。値を会話、ログ、証跡に出さない。パスワードの欄が写る画像を撮らない。テスト用の環境だと名前で判断できない接続先では、自動で入れない。テスト用のインスタンスを起動し、どのウィンドウ（プロセスの ID）にどのロールでログインするかを作業者に示して、ログインしてもらう。

`login.method` が `certificate` なら、先に aidev-qa-login-session で `login.certificate_thumbprint` の証明書が PC にあり、期限内で、秘密鍵を持つことを確かめてもらう。そのうえで、ブラウザやアプリが出す証明書の選択のダイアログを `references/dialogs.md` の「証明書の選択と PIN のダイアログ」のとおりに扱う。拇印から引いた証明書の発行先と期限で一覧の項目を選び、決められなければ止める。PIN やパスワード、OS の資格情報の入力は、エージェントもテストのコードも行わず、作業者に入れてもらう。

ブラウザで出る選択のダイアログでは、aidev-qa-login-session の setup がブラウザを画面付きで起動してそのプロセスの ID を残し、アプリのページに着くのを待つ。この Skill はその PID のブラウザが出したダイアログだけを扱い、セッションの保存と確認は aidev-qa-login-session に戻す。

ログインに失敗した、ロックや証明書のエラーが出た、というときは、文言を記録して止める。同じアカウントで続けて試さない。

WebView2 の画面のテストのためにネイティブのログインだけを行う場合は、ログインまでで止め、プロセスの ID、CDP のポート、ロール、ログインの方法、時刻を `$QA_RUN_DIR/launch-<環境>.json` に書いて aidev-qa-characterization に渡す。この前処理はケースではない。

## エージェントの安全

この Skill は作業者の実際のデスクトップで動く。テストのコードとエージェントの操作の両方で、次を守る。

- 操作するのは、今回起動したアプリのプロセスと、そのアプリが開いたダイアログだけにする。作業者のアプリ、OS の設定の画面、通知には触れない
- パスワード、PIN、OS の資格情報の入力のダイアログには、エージェントは値を入れない。作業者に渡す
- エクスプローラーの表示、プリンター、IME、表示倍率、証明書ストア、ブラウザの方針など、PC の設定を変えない。変える必要があれば作業者に頼む
- 実際のプリンターへの印刷、メールの送信、外部への連携は、一般のテストの依頼に含まれると考えない。宛先と範囲を示して作業者に確かめる
- 証跡、ログ、ツリーを書き出した結果に、資格情報、作業者のフォルダやファイルの名前、他のアプリの画面を残さない

## よくある誤り

- デスクトップ全体から名前だけで「保存」「はい」を探し、作業者の別のアプリのボタンを押す
- 所有ウィンドウのあるダイアログをデスクトップの直下だけで探し、見つからないのをアプリの不具合にする
- メッセージボックスのタイトルが本体と同じことに気づかず、本体をダイアログと取り違える
- 返らない操作をもう一度送り、二重の保存や二重の更新を起こす
- 保存のダイアログのファイル名を値の設定で入れ、既定のフォルダに保存されたのに気づかない。保存を押したことやファイルがあることだけで成功にする
- `Capture.Screen()` で全画面を撮り、他のアプリや通知を証跡に入れる。ロック中に撮ってロック画面を証跡にする
- Web のテストと同時に流す。UIA の操作だけならフォーカスを使わないので占有しない、と説明する
- 作業者が挙げたケースだけを流し、ソースの他の接点を確かめずに終える
- 同じ名前のプロセスをまとめて終了させる。作業者の表計算のアプリを、文書を閉じるために丸ごと終了させる
- 実際のプリンターへの印刷を、一般の依頼の範囲とみなす
- NG を消すために期待値を実装に合わせる。テストのコードの不具合を直すことと、期待値を変えることを混ぜる
- 新しいテストを一度も失敗させずに結果に使う

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- ネイティブの接点の一覧があり、すべての接点に TC-ID か、未カバー・要確認の理由がある
- 対象のすべての TC-ID に、TC-ID が先頭にあるテストか、手動確認の項目がある
- 新しく書いた、または確かめ方を変えたテストを一度失敗させて検出できることを確かめ、戻して緑に戻ったことを見た
- result.md の冒頭に環境名（プロファイルの `environments` の name、なければ exe の名前とファイルの版）、版、実行日時があり、すべての TC-ID に OK、NG、実行不能のどれかが付いている。実行の条件にデスクトップに固有の項目がある
- OK と NG のケースに、アプリのウィンドウかダイアログの範囲の証跡があり、開いて中身を確かめた。証跡に資格情報、他のアプリの画面、作業者のフォルダの名前が入っていない
- `runs/` に残っている証跡は最終の実行のものだけである
- 今回起動したプロセスを終え、設定を戻し、今回作ったファイルを片付けた。その状態を作業者に伝えた
