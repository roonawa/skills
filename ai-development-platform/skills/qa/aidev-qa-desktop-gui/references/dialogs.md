# ダイアログと外部アプリの扱い

メッセージボックス、保存・フォルダ選択・印刷のダイアログ、帳票のビューアや外部アプリ、IME、証明書の選択と PIN のダイアログを扱うテストを書くときに読む。FlaUI の基本の書き方は `flaui.md` にある。

## モーダルを見つける

ダイアログは、出る場所が作り方で変わる。

- 所有ウィンドウを指定して開いたダイアログ（WPF の `Owner`、`MessageBox.Show(owner, ...)`、`ShowDialog(owner)`）は、UIA では所有ウィンドウの子として出る
- 所有ウィンドウのないダイアログや、別のプロセスが出すダイアログは、デスクトップの直下に出る

どちらか分からなければ両方を探す。先に所有ウィンドウの子を探し、なければデスクトップの直下を対象の PID で絞って探す。プラグインや外部の部品が別のプロセスで出すダイアログは、起動の時刻と親子関係で今回の操作が出したものかを確かめる。

```csharp
public Window WaitModal(string title, TimeSpan? timeout = null)
{
    var pid = App.ProcessId;
    var mainHandle = Main.Properties.NativeWindowHandle.Value;
    return Retry.WhileNull(() =>
    {
        var owned = Main.FindAllChildren(cf => cf.ByControlType(ControlType.Window)).FirstOrDefault(w => w.Name == title);
        if (owned != null) return owned.AsWindow();
        var top = Automation.GetDesktop()
            .FindAllChildren(cf => cf.ByProcessId(pid).And(cf.ByControlType(ControlType.Window)))
            .FirstOrDefault(w => w.Name == title && w.Properties.NativeWindowHandle.ValueOrDefault != mainHandle);
        return top?.AsWindow();
    }, timeout ?? Short, throwOnTimeout: true, timeoutMessage: "ダイアログが出ない: " + title).Result!;
}
```

- タイトルは、ダイアログを開くコードの引数から取る。画面から読んだ文字を推測で使わない
- メッセージボックスのタイトルは、アプリの本体と同じ文字のことが多い。本体のハンドルを除いて探す
- マルチモニターでは、ダイアログが本体と別のモニターに出ることがある。座標で探さず、ツリーで探す
- 閉じたことは、ダイアログの要素が消えた（`IsAvailable` が false か `IsOffscreen` が true）ことで確かめる。閉じる操作をしただけで閉じたことにしない
- 期待していないダイアログが出たら、そのケースを止める。閉じるために勝手にボタンを押さず、画像を撮って種類と所有のプロセスを記録する。同じインスタンスで後のケースを続けない

## メッセージボックス

標準のメッセージボックス（クラス名 `#32770`）は、どのアプリから出してもツリーの形がほぼ同じである。

| 要素 | 見え方 |
|---|---|
| 本文 | ControlType が Text、AutomationId が `65535`、`Name` に本文 |
| はい・いいえ | Button の `6`・`7`。名前は OS の言語で変わる（「はい(Y)」など） |
| OK だけのとき | Button の `2`（`1` ではない） |
| OK とキャンセル | Button の `1`・`2` |

- ボタンは名前ではなく、ControlType の Button と AutomationId の組で探す。名前は OS の言語で変わる
- 本文はアサートに使う。タイトルだけで判定すると、同じタイトルの別のメッセージ（確認と警告など）を取り違える
- 確認のダイアログでは、はい・いいえ（・キャンセル）の分岐ごとにケースを分け、押した後の画面とデータの状態まで確かめる。ダイアログが閉じたことだけでは結果を確かめていない
- 「確認が出ない」ことを確かめるケース（警告だけが出る、何も出ない）は、出てはいけないダイアログが出ていないことを、出るはずのものを待った後に確かめる

## 保存のダイアログ

Windows の標準の保存のダイアログ（共通項目ダイアログ）は、作業者のフォルダやファイルの一覧を表示する。テストで扱うときは次を守る。

- 保存先は、`AppSession` が作る `OutDir`（`%TEMP%\qa-desktop-<guid>\out\<TC-ID>\`）にする。作業者の書類のフォルダ、共有のフォルダ、QA リポジトリの `runs/` には直接保存しない。残したいファイルは、確かめた後に証跡のディレクトリへ写す。既存のファイルを上書きしない
- ファイル名の欄は `FileNameControlHost` の中の Edit（AutomationId `1001`）、保存とキャンセルは ControlType が Button で AutomationId が `1`・`2` のものである。AutomationId だけで探すと、ファイルの一覧の項目（`0`、`1`、`2`…）を拾う
- ファイル名の欄には、保存するファイルの絶対パス（`OutDir` の下のファイル名まで）を入れる。名前だけを入れると、ダイアログが今表示しているフォルダに保存される
- ファイル名の欄に ValuePattern で値を入れると、欄の表示と読み返しは変わっても、ダイアログが保存に使う名前は変わらず、既定のフォルダに既定の名前で保存されることがある（実機で確かめた）。欄をフォーカスし、キー入力で絶対パスを入れる。キー入力の前に IME の状態を記録し、入力のモードがオンなら直接入力にする。IME を切り替えられないときは、作業者に切り替えてもらう。終わったら元の状態に戻す
- 保存を押す前に、ダイアログが今表示しているフォルダ（アドレスのバーの値）と、そのフォルダにある、保存しようとしている名前に合うファイルの一覧を記録する。保存の後に、指定したパスにファイルができたことと、記録したフォルダに新しいファイルが増えていないことをアサートする。増えていたら、それは今回の操作が作ったものなので、作業者に伝えてから片付ける
- ダイアログで保存すると、Windows はアプリごとに最後に使ったフォルダを覚える。作業者がそのアプリを使ったとき、テストの一時フォルダが開くことがある。この履歴は作業者の状態なので、レジストリを書き換えて消さない。テストで保存のダイアログを使ったことを作業者に伝える
- ファイル名の欄の表示は、エクスプローラーの「登録されている拡張子は表示しない」の設定で変わる（`<名前>.csv` が `<名前>` と出る）。既定のファイル名を確かめるケースでは、実行した PC の設定を読み、設定に応じた表示を期待値にする。作業者の設定を変えない
- 保存の後は、ダイアログが閉じたこと、ファイルが書き終わったこと（大きさが落ち着いた、アプリが完了の表示を出した）、中身（見出し、行数、値、文字コード）を確かめる。保存を押したこと、ファイルがあることだけでは成功にしない
- キャンセルのケースは、ダイアログが閉じたこと、ファイルが作られていないこと（既定のフォルダも見る）、メッセージが出ないことを確かめる
- 上書きの確認、日本語や長いファイル名、書き込めない保存先は、観点として要るかをケースの設計で決める。書き込めない保存先は、作業者の環境の権限を変えずに用意できる場所だけで試す
- 保存のダイアログの画像には、作業者のフォルダ名、ピン留めした場所、ファイルの一覧が写る。証跡には、ファイル名の欄と保存先の値を values.json に書き、画像は今回の空のフォルダを表示した状態で撮る。それでも作業者の情報が写るなら、ダイアログの画像は撮らず、そのことを result.md に書く
- 保存したファイルは、証跡のディレクトリに写して残す（帳票の中身を後で確かめるため）。個人情報を含む帳票なら、プロファイルの `evidence.method` に従って置き場所を決める

## フォルダ選択のダイアログ

新しい形のフォルダ選択（`FolderBrowserDialog` の既定や `OpenFolderDialog`）は、保存のダイアログと同じ共通項目ダイアログで、フォルダの欄と「フォルダーの選択」のボタンがある。古い形はツリーでフォルダを選ぶダイアログである。どちらが出るかは実物のツリーで確かめる。選ぶフォルダは今回作った空のフォルダにし、選んだ後にアプリが表示するパスや、そこに書かれたファイルで結果を確かめる。

## 印刷のダイアログ

- 実際のプリンターに印刷しない。印刷のケースは、作業者が認めた仮想のプリンター（PDF への出力など）か出力先だけを使う。実際に紙に出す必要があるときは、宛先と枚数を示して実行の前に作業者に確かめる
- PDF への出力は、続けて保存のダイアログを出す。そこからは保存のダイアログと同じ扱いにする
- プリンターの既定や設定を変えない。変える必要があれば作業者に頼み、実行の後に戻してもらう
- キャンセルのケースは、印刷のジョブが作られていないことまで確かめる

## 帳票のビューアと外部アプリ

アプリが PDF のビューアや表計算のアプリを起動するケースでは、今回のアプリが起動した、今回の文書を開いたウィンドウだけを相手にする。

- 起動したプロセスを、起動の時刻、親のプロセス、ウィンドウのタイトルに入る文書の名前で特定する。既に開いていた作業者のビューアやブックを検証しない
- 表計算のアプリなどは、既に動いているインスタンスに文書を開かせることがある。その場合はアプリ全体を終了させず、今回の文書のウィンドウだけを閉じる。作業者の保存していないブックがあるかもしれない
- 表示を確かめるだけでなく、出力されたファイルそのもの（CSV の列・値・行数、PDF の中身）を証跡に残して確かめる。生成の日時のように変わる値は、名前を挙げた項目だけを根拠付きで正規化する
- 外部アプリのツリーは UIA で見えないことがある。見えなければ、ファイルで確かめられる部分を自動にし、表示の確認は手動の確認項目に回す

## IME

IME の入力は、ValuePattern で値を入れても確かめたことにならない。変換と確定を経ない文字列が入るだけである。

- 対象の入力欄をフォーカスし、実際の IME とキー入力で変換、確定、取り消しを行い、確定した結果を読む。画面がロックされているとキー入力は届かない
- 実行の前に IME の状態（オン・オフ、入力のモード）を記録し、変えたら終わった後に戻す
- IME を使わないケースに IME の操作を足さない

## 証明書の選択と PIN のダイアログ

プロファイルの `login.method` が `certificate` のとき、ログインには `login.certificate_thumbprint` の拇印の証明書を使う。証明書が作業者の PC にあり使える状態かは、aidev-qa-login-session が先に確かめる。この Skill は、その後のログインの操作を受け持つ。

ブラウザで動く画面で OS の証明書の選択ダイアログが出る場合と、デスクトップアプリのネイティブのログイン画面で出る場合がある。どちらも次のように扱う。

- ブラウザの場合の分担は次のとおり。aidev-qa-login-session の setup がブラウザを画面付き（headed）で起動し、起動したブラウザのプロセスの ID を Git に入らない場所（`test-results/` の下）に書いて、アプリのページに着くのを待つ。この Skill は、その PID のプロセスが出した選択のダイアログだけを操作する。ダイアログが閉じた後のセッションの保存（`.auth/`）と、保存したセッションの確認は aidev-qa-login-session が行う
- ダイアログが、今回起動したブラウザかアプリのプロセスのものであることを確かめる
- 選択のダイアログには拇印が出ない。拇印で証明書ストアから引いた証明書の発行先、発行者、有効期限と、一覧の項目を突き合わせて選ぶ。候補が複数あって決められない、一致するものがない、というときは選ばずに止め、作業者に確かめる
- PIN、パスワード、スマートカードの入力を求められたら、エージェントは入れない。テストのコードにも入れさせない。作業者に、どのプロセスのどのダイアログかを示して入れてもらい、ログインが終わったことを期限付きで待つ。手で入れたことを記録に残す
- 「Windows セキュリティ」などの OS の資格情報の入力にも、同じように作業者に入れてもらう
- ブラウザの方針（自動で証明書を選ぶ設定）や証明書ストアの変更は、PC の設定の変更である。この Skill では行わない。必要なら作業者か管理者に頼む
- アプリの設計では選択のダイアログを出さないはずなのに出た、という場合は、選ばずに止め、ダイアログの種類と所有のプロセスを記録して作業者に伝える。アプリの不具合の候補として扱う

## WebView2 の画面から渡されたもの

aidev-qa-characterization は、WebView2 の画面の中で OS のダイアログや外部アプリが要る操作を、画面マニフェストの `excluded` に `native-required` として載せ、この Skill に渡す。

- 渡された項目ごとに、同じ TC-ID を使う。ケースがなければ、`cases/<機能>.md` の形式でケースを作り、作業者に確かめる
- 前の実行のプロセスやセッションが生きていると仮定しない。テスト用のインスタンスを新しく起動して、前提を作り直す
- ダイアログに着くまでの画面の操作は、アプリの UI を FlaUI で操作するか、WebView2 に CDP で接続して DOM を操作する。どちらも準備の操作であり、host object や API の応答をモックして到達を代わりにしない
- ネイティブのログイン画面の後に WebView2 の画面のテストを流す場合は、この Skill でテスト用のインスタンスを起動してログインまでを行い、プロセスの ID、CDP のポート、ロール、ログインの方法（自動か手動か）、時刻を `$QA_RUN_DIR/launch-<環境>.json` に書いて渡す。CDP を有効にして起動する方法は aidev-qa-characterization の WebView2 の資料に合わせる。プロセスは終了させない。ログインの後のメニューの操作までは進めない
- ネイティブのログイン画面に ID とパスワードを入れるのは、テストのコードがプロファイルの `roles` の環境変数から読んで行う。テスト用の環境だと名前で判断できない接続先では自動で入れず、起動までを行って作業者にログインしてもらう
- ログインに失敗した、ロックや証明書のエラーのメッセージが出た、というときは、その文言を記録して止める。同じアカウントで続けて試さない。アカウントのロックを招く
