# 修正を戻した版での確認

修正を戻した版でテストが失敗し、修正の入った版で成功することを確かめるときに読む。戻す操作は製品のリポジトリの作業用の複製で行い、作業者の作業ツリーには触れない。

## なぜ複製で行うか

作業者の作業ツリーで `git revert` や `git checkout <hash>~1` をすると、次のことが起こる。

- 作業者の未コミットの変更と、戻した変更が混ざる。片付けのときに作業者の変更まで消しやすい
- 戻し忘れると、修正のない版が作業者の手元に残る。そのままビルドやコミットをされると、直したはずの不具合が戻る
- 作業者が別の作業でそのツリーを使っていると、作業中のファイルが入れ替わる

`git worktree` の複製は、同じリポジトリの履歴を共有しながら別のディレクトリに別の版を取り出す。複製の中で何をしても、作業者の作業ツリーのファイルとインデックスは変わらない。

## 片付けは、どう終わっても行う

3 と 4 の途中から抜けるときは、終わり方を問わず（確かめが済んだ、失敗した、諦めた、作業者に止められた、エラーで中断した）、先に 5 と 6 を行う。戻した版のアプリを止め、複製を消し、作業者の作業ツリーを前の記録と比べる。そのうえで次の作業や報告に移る。片付けられずに残ったもの（止められなかったプロセス、消せなかった複製のディレクトリ、作業ツリーの違い）があれば、パスと状態を作業者に伝え、result.md の「確かめられなかったこと」にも書く。複製を残したまま次の Issue の確認に移らない。どの版のアプリが動いているのか分からなくなり、次の結果を取り違える。

## 1. 前の状態を記録する

戻す前に、作業者の作業ツリーの状態を記録する。後で同じであることを比べるためである。

```bash
git -C <製品のリポジトリ> rev-parse HEAD
git -C <製品のリポジトリ> status --porcelain=v1 --untracked-files=all
git -C <製品のリポジトリ> stash list
git -C <製品のリポジトリ> worktree list
```

出力は `.qa-scratch/fix-verify-<run-id>/before-state.txt` などの Git に入らない場所に保存する。

## 2. 複製を作る

複製は、確かめる版（修正の入った環境が動かしているコミット）から作る。修正の直前のコミット（`<修正>^`）から作るのではない。確かめる版から修正だけを戻せば、2つの版の違いは修正だけになる。修正の直前から作ると、修正の後に入った別の変更も一緒に消え、失敗の原因が修正なのか別の変更なのか分からなくなる。

```bash
git -C <製品のリポジトリ> worktree add --detach <QA リポジトリ>/.qa-scratch/fix-verify-<run-id>/repo <確かめる版>
```

- 置き場所は QA リポジトリの `.qa-scratch/` の下か、一時ディレクトリにする。製品のリポジトリの作業ツリーの中には作らない（`git status` に出る、ビルドの道具が拾う）
- `--detach` を付け、ブランチを作らない。ブランチを作ると、エディタの連携などが自動で push することがあり、片付けのときに消すブランチも増える
- Windows でパスが長くなりすぎるときは、短い一時ディレクトリを使う

## 3. 修正を戻す

複製の中で、修正のコミットを戻す。コミットはしない（`--no-commit`）。履歴に戻しのコミットを残さないためである。

この節の git のコマンドは、どれも `git -C <複製>` の形で複製を指して流す。`-C` を付けずに流すと、シェルのいる場所によっては製品のリポジトリの作業者の作業ツリーで戻しが起き、作業者の変更を巻き込む。戻す前に、`git -C <複製> rev-parse --show-toplevel` の出力が複製のパスであり、作業者の作業ツリーのパスでないことを確かめる。違えば何も流さずに止まる。

- 1つのコミット：`git -C <複製> revert --no-commit <修正>`
- 連続する複数のコミット（本体と追いのコミット）：`git -C <複製> revert --no-commit <最初の修正>^..<最後の修正>`。新しいものから順に戻される
- 間に関係のないコミットが挟まる複数のコミット：修正に属するものだけを新しい順に並べる。`git -C <複製> revert --no-commit <新しい修正> <古い修正>`
- マージのコミットで取り込まれた修正：取り込み先の側を親に指定して戻す。`git -C <複製> revert --no-commit -m 1 <マージ>`。1番目の親が取り込み先であることを `git -C <複製> log --first-parent` で確かめてから指定する
- squash で取り込まれた修正：1つのコミットとして戻す

修正のコミットがテストを足していたら、戻すとテストも消える。テストは修正の入った版のものを使うので、戻した後にテストのファイルだけを確かめる版に戻す（`git -C <複製> checkout <確かめる版> -- <テストのパス>`）。QA リポジトリの `automation/` のテストは別のリポジトリなので、この操作は要らない。

戻しが衝突したら、修正の後に同じ箇所を触ったコミットがある。衝突が修正の行そのものに限られ、どちらを取るかが明らかなら解決し、どう解決したかを記録する。明らかでなければ、`git -C <複製> revert --abort` で取り消し、5 の手順で複製を消して `<最初の修正>^` から作り直す。この場合は、修正の後に入った変更も一緒に消えていることを result.md に書き、失敗のメッセージが症状と一致するかをいっそう注意して見る。

戻した後、`git -C <複製> diff --stat HEAD` で、変わったのが修正のファイルだけであることを確かめる。

## 4. 戻した版を動かしてテストを流す

単体テストなら、複製の中でそのまま流す。依存の取得（`npm ci` など）が要れば複製の中で行う。

画面や API を通すテストなら、複製からアプリをビルドして起動する。

- ビルドと起動の方法は、製品のリポジトリの README か、プロファイルの本文の到達手順から読む。分からなければ作業者に確かめる
- 修正の入った版のアプリがすでに動いていれば、ポートを分けて起動するか、作業者に確かめてから止める。作業者が自分の端末で動かしているアプリを黙って止めない
- テストの向き先は、`QA_BASE_URL` を戻した版のアプリに向けて渡す。`QA_ENV` には、プロファイルの環境のうち、戻した版を動かす場所に当たるもの（作業者の PC の環境など）を使う。当たるものがなければ作業者に確かめる
- 共有の環境に、戻した版をデプロイしない。他の人の確かめを壊す
- データの状態は、修正の入った版で流すときと同じにする。初期データを入れ直せるなら両方で入れ直し、入れ直せなければ接頭辞で記録を分ける。アプリを起動し直したら、aidev-qa-login-session でセッションを作り直す。決まりは aidev-qa-test-run の「データの状態と流し直し」にある
- `QA_RUN_DIR` は `.qa-scratch/fix-verify-<run-id>/reverted/` に向ける。`runs/` には置かない

失敗したら、失敗のメッセージと証跡を開き、元の run の NG の詳細の「実際の結果」と同じ食い違いかを見る。たとえば NG が「権限のないロールで CSV が出力された」なら、戻した版の失敗も「CSV が出力された」でなければならない。ビルドの失敗、起動の失敗、ログイン画面に落ちた、要素が見つからないといった失敗は、症状の再現ではない。原因を直して流し直す。

戻した版をどうしても動かせないとき（依存が取れない、外部のシステムが要る）は、単体の水準で修正の箇所を確かめるテストを書けないかを考え、作業者に相談する。どちらもできなければ、修正の前で失敗することは確かめられなかったと result.md の「確かめられなかったこと」に理由とともに書く。元の NG の run は、修正の前の版で症状が出た記録として添えてよいが、その版との違いは修正だけとは限らないので、同じ確かめにはならない。

## 5. 複製を消して戻す

確かめが終わったら、戻した版のアプリを止め、複製を消す。

```bash
git -C <製品のリポジトリ> worktree remove <複製のパス>
```

ビルドの成果物や依存のディレクトリが複製に残っていると、`worktree remove` は止まる。消そうとしているパスが自分の作った複製であることを `git -C <製品のリポジトリ> worktree list` で確かめてから、`--force` を付けて消す。作業者の作業ツリーで `git clean` や `git reset --hard` は使わない。

`git worktree prune` は、ふだんの片付けでは使わない。prune は、ディレクトリが見つからない複製の記録を、自分の作ったものに限らずまとめて消す。複製のディレクトリを手で消してしまい、`worktree list` に残った記録が自分の作った複製のものであると確かめたときだけ使う。

戻した版のアプリが共有のデータに記録を作ったなら、その後始末も aidev-qa-test-run の決まりで行う。

## 6. 作業者の作業ツリーが変わっていないことを確かめる

1 と同じコマンドを流し、記録と比べる。

- `HEAD` が同じ
- `status` の出力が同じ（未コミットの変更と未追跡のファイルが前のまま）
- `stash list` が同じ
- `worktree list` に複製が残っていない

違いがあれば、何が変わったかを作業者に伝える。自分で直そうとして作業者のファイルを消さない。

## 7. 修正の入った版で成功することを見る

修正の入った版のアプリが動いていることを確かめ（止めたなら起動し直してセッションを作り直す）、同じテストを流して成功することを見る。最終の結果にする実行は、SKILL.md の 6 のとおり、新しい run-id の空の run に、対象の TC と関連する TC を全部流す。

## result.md に書く例

```markdown
## 修正の前後の確認

| TC-ID | テスト | 戻し方 | 戻した版 | 修正の入った版 |
|---|---|---|---|---|
| TC-csv-004 | automation/web/tests/csv.spec.ts「TC-csv-004 …」 | 確かめる版 9f8e7d6 から 1a2b3c4 と 5d6e7f8 を git revert --no-commit（worktree、.qa-scratch/fix-verify-csv-fix/repo） | 失敗：「expected status 403, received 200」。元の NG と同じく CSV が出力された | 成功（runs/20261119-csv-fix） |

- 作業者の作業ツリー：前後で HEAD、status、stash list が同じ。worktree list に複製は残っていない
- データの状態：両方の実行の前に初期データを入れ直し、セッションを作り直した
```

例の値（ハッシュ、TC-ID、パス）は説明のためのもので、実際の値は確かめたときの出力から書く。
