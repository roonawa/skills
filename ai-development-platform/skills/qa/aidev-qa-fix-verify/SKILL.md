# 改修の確認

## Overview

「直しました」という報告は、修正した人の理解を書いたものであって、不具合が消えたことの証明ではない。報告のコミットが別のブランチにしかない、主張の一部しかコードに入っていない、テストが修正の前でも通ってしまい何も確かめていない、ということが実際に起こる。この Skill は、報告を出発点にして、修正がコードに入っていること、その修正が不具合を消したこと、他の動きを壊していないことを、作業者が自分で追える形で確かめる。

確かめ方の中心は、修正を戻した版でテストが失敗し、修正の入った版で成功することを見ることである。修正の後に緑になっただけでは、そのテストが不具合を検出できるのかが分からない。修正の前に不具合の症状どおりに失敗して初めて、修正の後の緑が「直った」ことの根拠になる。修正を戻す操作は、製品のリポジトリを作業用の複製に写して行い、作業者の作業ツリーには触れない。

結果の正本は新しい run の `result.md` である。元の NG の run は、起票と改修確認をつなぐ記録として、そのまま残す。

## When to Use

- aidev-qa-bug-ticket で起票した Issue について、修正が入ったと連絡があったので確かめる
- 修正の説明やコミット、差分だけを渡され、それで不具合が直っているかを確かめる
- 1回のやり取りで複数の Issue の確認を続けて頼まれた（「これもお願い」は、同じ手順を最初から繰り返す意味に取る）

使わない場面は次のとおり。

- NG のケースから Issue を起票するときは aidev-qa-bug-ticket を使う
- 不具合の原因の特定と、人が追える再現手順を書くときは aidev-qa-cause-repro を使う。修正のコミットがまだないなら、この Skill の出番ではない
- 修正と関係なく、新しい版にケースを流して結果をまとめるときは aidev-qa-test-run を使う
- 旧版と新版の照合で差異を分類するときは aidev-qa-regression-compare を使う
- Issue のクローズ、コメント、ラベルの変更はしない。確かめた結果を見て、作業者が行う

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`test_commands`、`environments`、`login`、`evidence` と、本文の到達手順、テストデータの準備方法、落とし穴を使う
- 修正の主張。Issue の番号と本文、修正した人の説明、コミットのハッシュやブランチ、差分のどれか。全部揃っていなくてよい。Issue の本文は作業者から受け取るか、作業者が開いた画面で読む。Gitea の API は呼ばない
- 元の NG の run（`runs/<YYYYMMDD>-<run-id>/result.md`）と、その NG の詳細。Issue の列に番号が入っている行が対象の TC である
- 製品のリポジトリの場所と、確かめる版（修正の入った環境が動かしているコミット）。分からなければ作業者に確かめる
- `cases/*.md`、`plan/acceptance.md`、`automation/` の既存のテスト

出力は次のとおり。

- 新しい run `runs/<YYYYMMDD>-<run-id>/result.md` と証跡。形式は aidev-qa-test-run の result.md の資料に従い、冒頭と節を下の「result.md に足すもの」のとおりに足す
- 新しく書いた、または直したテストのコード。コミットするかは作業者が決める
- 作業者への返答。修正が効いたかどうかを先頭に書く

HTML のレポートは作らない。結果を表で見たいときは、後の段階で追加する予定の `aidev qa trace --html` と aidev-qa-report を使う（まだない）。作業者が求めたときだけ、result.md をもとに HTML を作って公開する。

## 進め方

### 1. プロファイルと確かめる範囲を決める

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-fix-verify` で検査する。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

次に、確かめる範囲を決める。

- 対象の Issue の番号と、元の run で Issue の列にその番号がある TC-ID。同じ番号の TC がいくつもあれば、全部を対象にする
- 修正の入った版を、どの環境で動かすか。プロファイルの `environments` の name で指す。修正を戻した版を動かす場所（作業者の PC など）も決める
- 製品のリポジトリの場所と、確かめる版のコミット

### 2. 修正コミットを特定する

主張から検索の手がかりを抜き出す。Issue の番号（`#12`、`fixes #12` の形）、TC-ID、AC-ID、ブランチ名、画面名、クラス名、関数名、テーブル名やカラム名である。製品のリポジトリで、全部のブランチを対象にコミットメッセージを検索する（`git log --all -i --grep=... --oneline`）。ブランチ名が分かっていれば、そのブランチと取り込み先の差（`git log <取り込み先>..<ブランチ>`）も見る。

- 修正は1つのコミットとは限らない。本体の修正にレビューの指摘を直した追いのコミットが続く、マージのコミットで取り込まれている、ということがある。検索で出たコミットは全部を開き、修正に属するものを決める。`git show --stat` で変わったファイルを、`git show <hash> -- <path>` で個別の差分を見る
- 見つかったコミットが、確かめる版に入っていることを確かめる（`git merge-base --is-ancestor <修正> <確かめる版>`）。cherry-pick で別のハッシュになっていることもある
- 見つからなければ、キーワードを変えて何度か探し、他のブランチやリモートの取り込み漏れ（手元が古い）も疑う。それでも見つからなければ、見つからないことをそのまま作業者に伝えて、コミットを確かめる。似たコミットを当てはめて話を合わせない。`git pull` や `git fetch` は作業者に確かめてから行う

### 3. 主張を実装で裏取りする

コミットメッセージや修正の説明を信じずに、確かめる版のファイルを開き、主張の行、変数、条件、コメントがそのとおりにあるかを読む。説明に行番号があっても、コミットの後の変更でずれているので、確かめる版で探し直す。修正が複数の箇所にあれば全部を読む。前の不具合の修正が引用されていれば、そのコミットも開いて経緯を掴む。

説明に含まれる主張は、1つずつ切り分けて独立に確かめる。1つが正しかったことで、残りを正しいとみなさない。

| 主張の種類 | 確かめ方の例 |
|---|---|
| 「この条件を足した」「この処理を外した」 | 確かめる版のファイルを読み、修正の差分と突き合わせる |
| 「他の箇所に同じ書き方はない」「呼び出し元はここだけ」 | リポジトリ全体を検索して数える |
| 「A の画面と B の画面で処理が同じ」 | 両方のソースを並べて比べる |
| 「このカラムは NULL を許す」 | DDL やマイグレーションのファイルを読む |
| ライブラリの型や関数の振る舞い | ライブラリのソースや型の定義を読むか、小さなスクリプトで実際に呼ぶ |
| SQL の計算結果 | 本番と同じ DB に届かなければ、名前とポートを既存のものと分けた使い捨てのコンテナに、対象の SQL が参照するテーブルだけの最小のスキーマを実際の DDL から作り、合成データで修正の前後の SQL を流して比べる。終わったらそのコンテナだけを消す |

修正した関数や SQL が、実際に機能から呼ばれていることも検索で確かめる。使われていないコードを直しても、不具合は消えない。

主張と実装が合わないときは、手元が古い可能性を先に作業者に伝える。合わないことを推測で埋めず、「食い違い」として記録する。

### 4. テストを探し、なければ書く

元の run の NG の詳細にある、失敗したテストのファイルとテスト名から始める。`automation/` を TC-ID で検索し、修正のコミットが製品のリポジトリにテストを足したり変えたりしていないかも見る。

- 修正のコミットがテストの期待値を変えていたら、ケースの期待結果より緩くなっていないかを読む。修正に合わせてテストを緩めて緑にしていれば、それは直ったことの根拠にならない
- テストがなければ書く。置き場所と書き方は aidev-qa-test-run の「既存のテストを探し、なければ書く」に従う。期待値はケースの期待結果から作り、修正の後の版を流して出た値を写さない
- 画面や API を通すテストのほかに、製品のリポジトリの単体テストで確かめるほうが確かな修正もある（計算の誤り、境界の判定）。製品のリポジトリにテストを足すときは、置き場所を作業者に確かめる。製品のコードそのものは変えない

### 5. 修正を戻した版で失敗し、修正の入った版で成功することを確かめる

この節がこの Skill の中心である。手順の詳細は `references/revert-check.md` にある。要点は次のとおり。

- 製品のリポジトリを `git worktree add --detach` で作業用の複製に写し、そこで修正のコミットだけを戻す。作業者の作業ツリーで戻したり、ブランチを切り替えたりしない。作業者の未コミットの変更を巻き込み、戻し忘れると誤った版を製品のリポジトリに残すからである
- 戻した複製でアプリを起動するか単体テストを流し、テストが失敗することを見る。失敗のメッセージが、Issue に書かれた症状（元の NG の詳細の「実際の結果」）と同じ食い違いを指しているかまで確かめる。ビルドの失敗や、ログイン画面に落ちたことによる失敗は、ここでの失敗に数えない
- 複製を消し、修正の入った版でテストが成功することを見る。最後に作業者の作業ツリーが前と同じであることを確かめる

戻す前後の2つの実行は、同じデータの状態で流す。アプリの再起動や初期データの入れ直しの扱いは、aidev-qa-test-run の「データの状態と流し直し」に従う。戻した版の実行の証跡は `.qa-scratch/` の下に置き、`runs/` には置かない。result.md には、そのときの失敗のメッセージを出力からそのまま写す。

新しく書いたテストは、修正を戻した版で症状どおりに失敗すれば、aidev-qa-test-run の「新しいテストが失敗を検出できるかを確かめる」を満たしたものとして扱ってよい。

### 6. 同じ機能の他のケースへの影響を確かめる

修正が他の動きを壊していないかを見るため、同じ機能の他の TC（同じ `cases/<機能>.md` のケース、同じ画面や API を通るケース、修正したファイルを通るケース）を、対象の TC と一緒に流す。どこまで流すかは、修正の差分が触った範囲から決め、決めた範囲と理由を result.md に書く。

最終の結果にする実行は、修正の入った版に対して、新しい run-id の空の `runs/<YYYYMMDD>-<run-id>/` に、対象の TC と関連する TC を全部流す。流し方、結果の分け方、流し直しの回数は aidev-qa-test-run と同じである。修正を戻した複製を消し、修正の入った版のアプリを起動し直した後に流す。起動し直したら、ログインの方式が `none` でなければ aidev-qa-login-session でセッションを作り直す。

既存のテストが失敗したら、修正のせいと決めつける前に、失敗のメッセージと証跡で性質を分ける。環境のせいなら実行不能、修正が壊したなら NG である。

### 7. 結果を判定する

対象の TC ごとに、次の基準で判定する。

| 判定 | 基準 | 表の結果 |
|---|---|---|
| 修正が効いた | 主張がコードで確かめられ、戻した版で症状どおりに失敗し、修正の入った版で成功した | OK |
| 修正が効いていない | 修正の入った版でも、元の NG と同じ食い違いが出た | NG |
| 確かめきれない | 修正の入った版では成功したが、戻した版で失敗しなかった、失敗の内容が症状と違った、戻した版を動かせなかった | OK（「確かめられなかったこと」に理由を書き、⚠ 要確認として作業者に伝える） |

戻した版で失敗しなかったときは、テストが不具合の症状を確かめていないか、特定したコミットが本当の修正ではない（環境やデータの変化で症状が消えただけ）かのどちらかである。テストのアサーションと、元の NG の再現の条件を見直す。

関連する TC で、元の run から同じ NG が残っているものは、別の不具合として扱う。表の Issue の列には、元の run でそのケースに付いていた Issue の番号を書き、result.md と返答で「修正と関係のない NG が残っている」と分けて書く。修正が効いていないことと混ぜない。元の run では OK だったのに今回 NG になったケースは、修正が壊した可能性がある新しい NG である。Issue の列を空けて、NG の詳細を aidev-qa-test-run の形で残し、aidev-qa-bug-ticket での起票を作業者に提案する。

### 8. 確かめられなかったことを書き、報告する

検証できなかったこと、修正の説明に書かれた未回答の論点、対象外とされたことを洗い出して result.md に書く。修正の説明の文言をそのまま引き継ぎ、言い換えて弱めたり省いたりしない。

- 実機や本番に近い環境では確かめていない、該当するデータがなく確かめていない、など説明に書かれた限界
- 判断待ちの論点（回答次第で修正を戻す可能性があるもの）
- 別の課題とされた対象外の事項
- 自分が加えた限界（DB に届かず合成データで代わりにした、代表のケースだけを流した、戻した版を動かせなかった）

自動で確かめられない部分は、aidev-qa-test-run の手動確認の項目の形で、人がそのまま追える再現手順を書く。

最後に作業者へ返す。先頭に、Issue ごとに修正が効いたか（効いた、効いていない、確かめきれない）を書く。続けて、修正コミットのハッシュ、日付、作者、主張ごとの裏取りの結果、修正の前後の確認の結果、関連する TC の結果、確かめられなかったこと、新しく書いたテストのパス（未コミット）を書く。数値と失敗のメッセージは実行の出力から写し、要約で作り直さない。Issue をクローズするか、コメントで知らせるかは作業者に任せる。

## result.md に足すもの

形は aidev-qa-test-run の result.md の資料のとおりにし、次を足す。

冒頭の環境名、版、実行日時の3行の後に、次の行を足す。後の段階で追加する予定の `aidev qa trace` は、この行がある run を改修確認として読む（まだない）。

```markdown
- 改修確認: #12
- 修正コミット: 1a2b3c4、5d6e7f8（追いのコミット）
- 元の run: runs/20261118-new-cases
```

1つの run では1件の Issue を確かめるのを基本にする。複数の Issue を同じ実行で確かめるときは、`改修確認` と `修正コミット` の行を Issue ごとに並べる。

表の Issue の列には、対象の TC の行に元の Issue の番号（`#12`）を書く。これは作業者が手で書く列で、`aidev qa issue create` は使わない。関連する TC の行は、元の run で Issue が付いていたものだけ番号を書き、それ以外は空ける。

表の後に、次の節を足す。

- 主張の裏取り：主張ごとに、主張の文面、確かめ方（読んだファイルと行、検索の範囲、流したスクリプト）、結果（確認済み、食い違い、未確認）を1行で書く
- 修正の前後の確認：TC ごとに、テスト、戻したコミットと戻し方、戻した版での結果（失敗のメッセージをそのまま）、修正の入った版での結果、作業者の作業ツリーが変わっていないことの確かめを書く
- 関連するテスト：流した範囲と、その範囲にした理由
- 確かめられなかったこと：上の 8 の内容

## よくある誤り

- コミットメッセージや修正の説明を読んだだけで「確認済み」にし、確かめる版のファイルを開かない
- 主張のうち確かめやすい1つを確かめて、残りも正しいとみなす
- 修正の入った版で緑になったことだけを見て、戻した版で失敗するかを確かめない
- 戻した版の失敗が、ビルドの失敗やログイン画面に落ちたことによるものなのに、症状どおりの失敗と数える
- 作業者の作業ツリーで `git revert` や `git checkout` をして修正を戻し、未コミットの変更を巻き込む。戻した状態を残す
- 修正のコミットがテストの期待値を緩めていたのに気づかず、そのテストの緑を根拠にする
- 修正と関係のない NG が残っているのを、修正が効いていないと報告する。逆に、修正で壊れた新しい NG を、元からある不具合として扱う
- 元の run の result.md の結果や Issue の列を書き換える
- Issue をクローズする、コメントを書く
- 確かめられなかったことや未回答の論点を、返答や result.md から省く
- 戻した版の証跡を `runs/` に置き、最終の実行の証跡と混ぜる

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- 修正コミットを特定し、確かめる版に入っていることを確かめた。特定できなかったときは、作業者に確かめた
- 修正の主張を1つずつ、確かめる版のコードで裏取りし、結果を result.md に書いた
- 対象の TC ごとに、修正を戻した複製で症状どおりに失敗し、修正の入った版で成功することを確かめた。確かめられなかったときは理由を書き、⚠ 要確認として作業者に伝えた
- 作業用の複製を消し、作業者の作業ツリーが確かめる前と同じであることを確かめた
- 新しい run の result.md の冒頭に「改修確認」「修正コミット」の行があり、対象の TC の Issue の列に元の Issue の番号がある。元の run の result.md は変わっていない
- 同じ機能の関連する TC を流し、修正と関係のない NG と、修正で壊れた可能性のある NG を分けて書いた
- 確かめられなかったこと、未回答の論点、対象外の事項を result.md に書いた
- Issue のクローズとコメントはしていない
