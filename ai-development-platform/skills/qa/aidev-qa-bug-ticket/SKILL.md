# NG のケースの起票

## Overview

テストで NG になったケースを、開発者が直しに取りかかれる Gitea の Issue にする。Issue の題名と本文は、`aidev qa issue create` が result.md の「NG の詳細」から機械的に組み立てる。この Skill の仕事は、その前後の判断である。NG が本当に製品の不具合か、どの NG を1件にまとめるか、本文に載せてはいけないものが入っていないか、送ってよいかを作業者と確かめる。

起票は、開発者の時間を使わせる操作で、Gitea に送ったものは取り消せない。テストのコードの誤りや環境の不調を不具合として起票すると、開発者は存在しない不具合を探すことになる。同じ不具合を TC ごとに別の Issue にすると、修正と確認が重複する。本文に個人情報やトークンが入れば、Issue を読める全員に広がる。どれも送った後では直せないので、送る前に止める。

Gitea への書き込みは Issue の作成だけで、コメント、編集、クローズ、ラベル付けはしない。コマンドにもその機能はない。C-HUB には転記しない。

## When to Use

- aidev-qa-test-run で記録した NG のケースを起票する
- aidev-qa-fix-verify の確認で、元の run では OK だったのに NG になったケース（修正が壊した可能性のあるもの）を起票する
- aidev-qa-regression-compare の比較先の run で、要確認の差異があって NG にしたケースを起票する。要確認は不具合と決まったわけではないので、下の 2 で確かめてから起票する。その run の NG の詳細には差異の ID しかないことが多く、そのままではコマンドが止まる。足りない項目は 4 の表のとおり compare.md から写す

使わない場面は次のとおり。

- 原因が分からない、テストの側の誤りかどうか判断できない NG は、起票の前に aidev-qa-cause-repro で調べる
- 「直した」という連絡を受けて修正を確かめるときは aidev-qa-fix-verify を使う
- ケースを流して result.md を作るときは aidev-qa-test-run を使う。result.md がまだない、NG の詳細が書かれていないときも、そちらに戻る
- 既存の Issue にコメントを足す、クローズする、ラベルを付ける。この Skill もコマンドも行わない。必要なら作業者が Gitea の画面で行う

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`product` と `issue_tracker`（`type: gitea`、`url`、`repo`）を使う
- `runs/<YYYYMMDD>-<run-id>/result.md` の NG の行と「NG の詳細」、その run の証跡
- `cases/*.md`（ケースの手順と期待結果）と `plan/acceptance.md`（AC の文面）
- 作業者が設定した環境変数 `GITEA_TOKEN`（作業者個人のトークン）と `GITEA_URL`（起票先の Gitea の URL）。AI 専用のアカウントのトークンは使わない

出力は次のとおり。

- Gitea の Issue。本文の節の並びと書き方は `references/issue-template.md` にある
- result.md の、起票した TC の行の Issue の列の `#番号`。コマンドが書く。同じ Issue にまとめた残りの TC の行には、同じ番号を手で書く
- 作業者への返答。起票した Issue の番号と URL、まとめた TC、起票しなかった NG とその理由を書く

## 進め方

### 1. プロファイルと接続先を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-bug-ticket` で検査する。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。`issue_tracker` がなければ、起票先のリポジトリを作業者に確かめてプロファイルに足してもらう。推測で埋めない。

次に、作業者が `GITEA_URL` と `GITEA_TOKEN` を設定しているかを確かめる。コマンドは、プロファイルの `issue_tracker.url` と `GITEA_URL` の接続先（スキーム、ホスト、ポート）が違えば、`--dry-run` でも何も送らずに止まる。トークンは `GITEA_URL` にだけ送られる。トークンの値は必ず画面、ログ、ファイル、会話に出さない。作業者個人の権限で Gitea を操作できる値だからである。設定されているかは、値を表示しない方法（`[ -n "$GITEA_TOKEN" ]` の終了コードなど）で見る。作業者にトークンを会話に貼ってもらうこともしない。

### 2. NG が製品の不具合かを確かめる

起票の候補は、result.md の表で結果が NG の行だけである。実行不能のケースは起票しない。NG の行ごとに、aidev-qa-test-run の結果の判定の基準（対象に正しく着き、操作もでき、観測した挙動が期待結果と違い、流し直しても同じ食い違いが出た）に当たるかを、次の材料で確かめる。

- 証跡を開いて見る。対象の画面に着いているか。ログイン画面、IdP の画面、読み込みの途中、0件の画面を撮っていないか。食い違いが写っているか
- 失敗したテストのアサーションを読み、`cases/*.md` の今の期待結果を確かめているか。ケースが改訂されてテストが古いままではないか
- NG の詳細の「期待結果」がケースの文面のままか、「実際の結果」が観測した値か
- 「再現」の回数。毎回は出なかったもの（「⚠ 要確認: 間欠的な不具合の可能性」）は起票してよいが、再現した割合が本文に入っていることを確かめる
- 「補足」に期待結果の誤りの可能性が書かれていれば、`plan/acceptance.md` と設計書で裏取りする。期待結果のほうが誤りなら起票せず、ケースの見直しを作業者に提案する
- regression-compare から来た NG は、要確認の差異が仕様に照らして不具合かを確かめる。基準の側を支持する仕様の根拠がなければ、起票の前に作業者に判断してもらう

分け方は次のとおり。

| 判断 | 次にすること |
|---|---|
| 製品の不具合と言える | 3 に進む |
| テストのコードの誤り、セッションの期限切れ、データや環境の問題と分かった | 起票しない。aidev-qa-test-run に戻してテストを直すか環境を整え、新しい run で流し直す。この Skill は result.md の結果を書き換えない |
| どちらとも言えない（証跡からは食い違いの理由が読めない、テストの側か製品の側か決められない） | 起票しない。aidev-qa-cause-repro で原因を調べてもらい、製品の側と分かってから戻る |

### 3. 同じ原因の NG をまとめる

複数の NG が同じ不具合から出ているなら、1件の Issue にまとめる。まとめてよいのは、次の全部に当たるときである。

- 食い違いの性質が同じ（同じメッセージが出ない、同じ項目の値が同じ向きにずれる、同じ操作で同じエラーになる）
- 製品のコードの上で、原因の箇所（ファイルと関数、または分岐）が1つに特定されていて、どの NG もその箇所を通ることを説明できる。原因の箇所の根拠は、aidev-qa-cause-repro の報告書で確度が確定か有力のもの、または自分で製品のコードを読んで、それぞれの NG の再現の条件がその箇所を通ることをたどったもののどちらかに限る
- 同じ run の NG である。別の run や別の版の NG は、まとめずに別に判断する

テストの失敗の位置、証跡、画面や API が同じことは、症状が同じことを示すだけで、原因が同じことの根拠にならない。同じ画面の同じ項目でも、別々の原因で崩れていることがある。症状しか根拠がないときは、分けて起票するか、aidev-qa-cause-repro で原因の箇所を特定してから判断するかを作業者に確かめる。迷ったら分けて起票する。まとめた Issue の片方の原因だけが直ったときに、取り違えて両方を直ったことにする事故は、後から防ぎにくい。

原因の箇所が特定できていれば、ロールやデータだけが違う組み合わせのケースが同じ食い違いで NG になったのは、まとめる典型である。

まとめるときは、代表の TC を1つ決める。NG の詳細が一番具体的で、再現手順を人がそのまま追えるものを選ぶ。コマンドは TC ごとに Issue を作るので、残りの TC についてはコマンドを実行しない。実行すると、TC ごとに別の Issue ができる。代わりに、代表の TC の NG の詳細の「補足」に、まとめる TC-ID と、根拠にした原因の箇所を書き足す。こうすると Issue の本文に、どの TC が同じ不具合かが残る。書き方は `references/issue-template.md` にある。すでに `- 補足:` があればその下に字下げした続きの行として足し、`- 補足:` の行を2つにしない。2つ目の `- 補足:` はコマンドに読まれず、本文から落ちる。書き足す内容は作業者に見せてから書き、5 の `--dry-run` の本文の「補足」の節に出ていることを確かめる。

### 4. 本文の材料を整える

コマンドは、表の行と、「NG の詳細」の `### <TC-ID> <ケース名>` の節から題名と本文を作る。節の項目の書き方と、本文のどこに入るかは `references/issue-template.md` にある。再現手順、期待結果、実際の結果のどれかが欠けていると、コマンドは止まる。aidev-qa-test-run の run で欠けていれば、aidev-qa-test-run に戻して、新しい run で書いてもらう。観測していないことを推測で書き足さない。

aidev-qa-regression-compare の比較先の run では、NG の詳細に compare.md の差異の ID しか書かれていないことが多い。その場合は、compare.md の「要確認の詳細」から、次のように項目を足す。

| 項目 | 写すもの |
|---|---|
| 再現手順 | 要確認の詳細の再現手順のまま |
| 実際の結果 | 比較先の値と、その証跡のファイル（要確認の詳細の「比較先」のまま） |
| 期待結果 | 2 で仕様の根拠を確かめた値。基準の run の値を使うときは「基準の run の値（仕様の根拠: <AC-ID や設計書の節>）: <値>」と書き、仕様のどこが支えているかを示す |
| 証跡 | 比較先の証跡のパス。基準の側の証跡のパスは補足に書く |

足すときは、どの差異の ID から写したかを補足に書き、作業者に見せてから書く。

NG の詳細に手を入れてよいのは、次の2つだけである。result.md は実行の記録で、期待結果はケースの文面のまま、実際の結果は観測したままでなければならない（aidev-qa-test-run の result.md の書き方の資料による）。

- 秘密情報か個人情報の値を伏せる。値を消し、その場所に「（個人情報のため値を省略。値は <証跡のファイル>）」のように、伏せたことと値のある場所を書く。黙って消したり言い換えたりしない
- 補足に書き足す。まとめた TC と原因の箇所、影響、上の表で compare.md から写した差異の ID

上の regression-compare の run で欠けた項目を足すことは、この2つと同じ扱いにする。期待結果と実際の結果の意味を変える書き換え、言い回しを整える書き換え、再現手順の書き直しはしない。本文がそれでは足りないと分かったら、起票を止めて aidev-qa-test-run に戻し、新しい run で記録し直してもらう。変えた行は、変える前と後をそのまま控えておき、8 で報告する。

コマンドは秘密情報らしい記述（トークン、パスワード、Cookie の形）を検査するが、個人情報は検査しない。5 の `--dry-run` で出た本文の全体（題名、環境、版、テスト、再現手順、期待結果、実際の結果、再現の回数、証跡のパス、補足のコードブロックの中のすべての値）を読み、氏名、メールアドレス、電話番号、住所、生年月日、学籍番号や社員番号のような個人を指す ID が入っていないかを確かめる。期待結果やファイルのパスにも個人の値が入ることがある。見つかれば上の書き方で伏せ、性質と証跡の場所で書く（「氏名の欄が空の記録」「電話番号の欄（値は 02-detail.values.json）」）。テスト用に作った架空のデータでも、実在の人と区別がつかない値は同じように扱う。

アカウントは環境変数の名前で示し、パスワードを書かない。証跡はリポジトリの中のパスで示し、画像やファイルを Issue に添付しない。証跡そのものに個人情報が写っていることがあり、Issue に貼るとリポジトリより広く読まれるからである。プロファイルの `evidence.method` が `local` か `external` で、証跡がリポジトリの外にあるときは、そのパスを開ける人が限られることを作業者に伝える。

NG の詳細に手を入れるときは、何をどう変えるかを作業者に見せてから変える。表の結果の列や、他の TC の行、表の後の他の節は変えない。

### 5. --dry-run で題名と本文を作り、作業者に見せる

```bash
aidev qa issue create --profile knowledge/<product>/profile.md --run runs/<YYYYMMDD>-<run-id> --tc <TC-ID> --dry-run
```

`--dry-run` は末尾に書く。このときコマンドはトークンを読まず、Gitea に接続せず、result.md も書き換えない。ただし `GITEA_URL` は読み、プロファイルとの接続先の照合と、秘密情報の検査は行う。秘密情報で止まったときは、出力に本文の行番号だけが出る。その行に入った値を result.md の NG の詳細で探し、環境変数の名前や証跡の場所で書き直してから、もう一度 `--dry-run` で作る。

出力は1行の JSON で、`to`（送信先の `url` と `repo`）、`title`、`body` が入っている。作業者には次を見せる。

- 送信先。`GITEA_URL` のホストと、`repo`（owner/name）
- 題名と本文。JSON の中の `\n` を改行に戻し、読める形で見せる
- 4 で確かめたこと（個人情報の有無、まとめた TC とその根拠）

作業者が送信先と本文を確かめて了承するまで、`--dry-run` を外して実行しない。了承は Issue ごとに、見せたその本文に対するものである。了承の後で result.md、`GITEA_URL`、プロファイルのどれかが変わったら、もう一度 `--dry-run` で作って見せ直す。

本文を直したいと言われたら、4 で許した範囲（値を伏せる、補足に書き足す）でだけ NG の詳細を直し、もう一度 `--dry-run` から始める。期待結果や実際の結果の意味を変えたいという求めなら、起票を止めて aidev-qa-test-run に戻す。送られる本文を作るのはコマンドで、Gitea の画面で手で直すことはこの Skill ではしない。

### 6. 送る

作業者の了承を得たら、`--dry-run` を外して同じコマンドを実行する。コマンドは、トークンの持ち主のユーザーを確かめ、同じ目印の Issue を探してから作る。目印と重複の扱いは次のとおり。

- 本文の1行目に `<!-- aidev-qa: <product> <TC-ID> -->` の目印が入る。目印に run-id は入らないので、同じ TC を別の run で起票し直しても同じ目印になる
- 目印が1行目にあり、トークンの持ち主が作った、開いている Issue があれば、新しく作らずにその番号を使う。閉じた Issue や、他の人が作った Issue は重複とみなさず、出力の `ignored` に番号と理由を出したうえで新しく作る
- 探すのは検索の結果の先頭の 50 件までである。古い Issue が多いリポジトリでは見落としがありうるので、送る前に作業者に、同じ不具合の Issue がすでにないかを Gitea の画面で見てもらう。とくに、同僚が手で起票した Issue はコマンドから重複として見えない
- 題名か本文に `GITEA_TOKEN` の値がそのまま入っていれば、送らずに止まる

送った後の出力の `issue.number` と `issue.url`、`created`（新しく作ったか、既存を使ったか）、`ignored` を作業者に伝える。`ignored` に閉じた Issue があれば、以前に直ったはずの不具合が再発した可能性として伝える。

### 7. result.md に番号を書く

コマンドは、送った TC の行の Issue の列だけを `#番号` に書き換える。ほかの行や列、表の後の節は変えない。次のときは書き換えずに止まる。

- その行の Issue の列に、別の番号か `#番号` 以外の文字が書かれている
- その行の列の数が表の見出しと合わない
- 起票の途中で result.md が変わった

Issue は作ったのに書き戻せなかったときは、出力のメッセージにその番号が出る。その TC の行の Issue の列に、その番号を手で書く。

3 でまとめた残りの TC の行には、同じ `#番号` を手で書く。手で書くときも、コマンドと同じことを確かめてから書き、1つでも合わなければ書かずに作業者に確かめる。

- 書くのは、代表の TC と同じ run の result.md である
- その TC-ID の行が表に1行だけあり、結果の列が NG である
- その行の列の数が表の見出しの列の数と同じである。値の中の `\|` は区切りではないので、数に入れず、書き換えもしない
- Issue の列が空である。別の番号や他の文字が書かれていれば書き換えない

書き換えるのは Issue の列の中身だけで、列の区切りの `|`、前後の空白の付け方、ほかの列は変えない。まとめた TC を後でコマンドに渡すと、その TC の目印の Issue は見つからないので、書かれた番号と食い違うとして止まる。重複の Issue ができることはないが、まとめた TC にはコマンドを使わない。

### 8. 報告する

作業者への返答に、次を書く。

- 起票した Issue ごとに、番号、URL、代表の TC と、まとめた TC
- 既存の Issue を使ったもの、`ignored` に出た Issue
- 起票しなかった NG と理由（テストの側の誤り、環境の問題、aidev-qa-cause-repro に回したもの、期待結果の誤りの可能性）
- result.md に書いた番号（コマンドが書いた行と、手で書いた行）
- NG の詳細で変えた行の、変える前と後。伏せた値そのものは書かず、伏せたことと値のある場所を書く

result.md の変更をコミットするかは作業者が決める。Issue の担当者の割り当てやラベル、関連する Issue との紐付けが要るときは、作業者に Gitea の画面で行ってもらう。

## よくある誤り

- `--dry-run` を飛ばして送る。送信先と本文を作業者に見せずに送る
- テストのコードの誤りやセッションの期限切れで落ちた NG を、証跡を見ずに起票する
- 同じ不具合で NG になった TC を、TC ごとに別の Issue にする。逆に、製品のコードの原因の箇所を示せないまま、テストの失敗の位置や画面が同じだからとまとめる
- 本文を読みやすくしようと、NG の詳細の期待結果や実際の結果を言い換える。伏せた値を、伏せたと書かずに消す
- 了承を得た後に result.md を直し、見せ直さずに送る
- まとめた TC の補足を2つ目の `- 補足:` として書き、本文から落ちたことに気づかない
- まとめた残りの TC にもコマンドを実行し、別の Issue を作ってしまう
- 秘密情報の検査が通ったことを、個人情報がないことと取り違える
- 証跡の画像を Issue に添付する。リポジトリの外の証跡のパスを、誰でも開ける前提で書く
- トークンの値を表示して設定を確かめる。作業者にトークンを会話に貼ってもらう
- 本文の誤りを Gitea の画面で直す、コメントで補う、Issue をクローズする
- 実行不能のケースや、期待結果の誤りが疑われる NG を起票する
- result.md の結果の列を、起票しなかった理由に合わせて書き換える
- 起票の結果を C-HUB に転記する

## 完了条件

- `aidev qa profile check --skill aidev-qa-bug-ticket` がプロファイルに対して成功し、`GITEA_URL` がプロファイルの `issue_tracker.url` と同じ接続先だった
- 起票した NG のそれぞれについて、証跡とテストのアサーションを見て、製品の不具合であることを確かめた。判断できない NG は起票せず、aidev-qa-cause-repro に回した
- まとめた Issue には、まとめた TC と、製品のコードの原因の箇所が本文の補足に入っている。原因の箇所は aidev-qa-cause-repro の確定か有力の報告書、または製品のコードを読んでたどったもので示した
- NG の詳細に入れた手は、値を伏せること、補足への書き足し、regression-compare の run で compare.md から欠けた項目を写すことだけで、変える前と後を報告した
- 送る前に `--dry-run` の題名と本文、送信先を作業者に見せ、了承を得た。了承の後に result.md、`GITEA_URL`、プロファイルを変えていない（変えたなら見せ直した）
- `--dry-run` の本文の全体を読み、秘密情報と個人情報の値が入っていない。証跡はパスで示し、画像を添付していない
- 起票した TC の行と、まとめた残りの TC の行の Issue の列に、同じ `#番号` が入っている
- Gitea には Issue の作成だけを行い、コメント、編集、クローズ、ラベル付けをしていない。C-HUB に書き込んでいない
- トークンの値を、出力、ファイル、会話のどこにも出していない
