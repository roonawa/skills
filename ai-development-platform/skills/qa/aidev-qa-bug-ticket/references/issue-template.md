# Issue の題名と本文

`aidev qa issue create` が作る Issue の題名と本文の形と、その材料になる result.md の「NG の詳細」の書き方を決める。本文を整えるとき（SKILL.md の進め方の 4）と、`--dry-run` の出力を作業者に見せる前に読む。

本文はコマンドが組み立て、この Skill は手で書かない。直したいときは、result.md の NG の詳細を直して `--dry-run` から作り直す。

## 材料：result.md の NG の詳細

result.md の全体の形と NG の詳細の各項目に何を書くかは、aidev-qa-test-run の references/result-format.md にある。コマンドが読むのは次のところである。

- 冒頭の `- 環境: …` と `- 版: …` の行（表より上にあるもの）
- TC-ID、結果、証跡、Issue の列を持つ最初の表の、その TC の行。結果が `NG` でなければ止まる。同じ TC-ID の行が2行あっても止まる
- `## NG の詳細` の下の `### <TC-ID> <ケース名>` の節。`### ` の後の最初の語が TC-ID、残りがケース名で、ケース名は題名になる

節の中は、行頭（字下げなし）の `- ` で始まる項目を、`ラベル: 値` の形で読む。区切りは半角の `:` でも全角の `：` でもよい。ラベルだけの行（`- 再現手順`）の後に字下げして続けた行は、その項目の値になる。

| 項目のラベル | 本文での置き場所 | なければ |
|---|---|---|
| AC（または AC-ID） | 対象の「AC-ID」 | 「（result.md に記載なし）」と書かれる。AC のないケースは少ないので、ケースから補う |
| テスト | 対象の「テスト」 | 本文から省かれる |
| 再現手順 | 「再現手順」の節 | コマンドが止まる |
| 期待結果 | 「期待結果」の節 | コマンドが止まる |
| 実際の結果 | 「実際の結果」の節 | コマンドが止まる |
| 再現 | 「再現の回数」の節 | 「（result.md に記載なし）」と書かれる |
| 証跡 | 「証跡の場所」の節 | 表の証跡の列の値を使う。それも空なら「（result.md に記載なし）」 |
| 補足 | 「補足」の節 | 節ごと省かれる |

書くときの注意は次のとおり。

- 再現手順の番号付きの行は字下げする。字下げしない `- ` の行を手順の途中に書くと、そこから別の項目として読まれ、手順が切れる
- 同じラベルを2回書くと、最初のものだけが使われる。値が空の項目は、ないものとして扱われる
- 影響（どの利用者のどの業務が止まるか、データが壊れるか、回避の手段はあるか）は専用の節がないので、補足に書く。分かっていることだけを書き、推測は推測と書く
- 3 でまとめた TC は、代表の TC の補足に「同じ原因と判断してこの Issue にまとめる TC: TC-…、TC-…（根拠: …）」の形で書く
- AC-ID、TC-ID、run-id は本文に入るので、ここで書き換えない

## 題名

題名は `［<TC-ID>］ <ケース名>` になる。コマンドは `[<TC-ID>] <ケース名>` を組み立ててから、次の文字を全角に置き換える。

| 元の文字 | `@` | `#` | `!` | `<` | `>` | `[` | `]` | `(` | `)` | `\` | `` ` `` | `:` | `/` |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 置き換え後 | ＠ | ＃ | ！ | ＜ | ＞ | ［ | ］ | （ | ） | ＼ | ｀ | ： | ／ |

Gitea は題名の `@名前` を言及に、`#番号` や `owner/repo#番号` や Issue の URL を参照にするので、そうならない形にしている。改行とタブは空白に置き換わる。255 文字を超える題名は、254 文字で切って末尾に `…` を付ける。ケース名は短く、何が起きないか、何が違うかが分かる名前にしておく。

例：`### TC-order-002 数量が上限を 1 超えると注文できない` からは `［TC-order-002］ 数量が上限を 1 超えると注文できない` ができる。

## 本文

本文は次の順に並ぶ。見出しとラベル、TC-ID、run のパスだけがコードブロックの外にあり、result.md から写した値はすべて、それぞれのコードブロックの中に入る。

1. 目印の行 `<!-- aidev-qa: <product> <TC-ID> -->`。1行目に置かれ、重複の判定に使う。product はプロファイルの `product`
2. `## 対象`。`- TC-ID: <TC-ID>` と `- 実行: runs/<YYYYMMDD>-<run-id>` の2行と、その後にラベルとコードブロックの組で、AC-ID（常に出る）、環境、版、テスト（値があるものだけ）
3. `## 再現手順`
4. `## 期待結果`
5. `## 実際の結果`
6. `## 再現の回数`
7. `## 証跡の場所`
8. `## 補足`（値があるときだけ）
9. 区切りの `---` と、`aidev qa issue create が runs/<YYYYMMDD>-<run-id>/result.md の NG の詳細から作りました。` の1行

値をコードブロックに入れるのは、Gitea が本文の `@名前` で利用者に通知し、`#12`、`!12`、`owner/repo#12` で他の Issue やプルリクエストに参照を足し、HTML と画像を表示するからである。コードブロックの中ではどれも起きない。囲みのバッククォートは、値の中のバッククォートの最も長い連続より1つ長く（最低3つ）なるので、値の中の行がブロックを閉じることはない。その代わり、値の中の Markdown（太字、表、リンク）はそのままの文字で表示される。再現手順の番号や改行は、result.md に書いた形のまま見える。

例：上の題名の例と同じ NG の詳細（aidev-qa-test-run の result-format.md の例）からは、次の本文ができる。product が `sample-shop` のとき。

````markdown
<!-- aidev-qa: sample-shop TC-order-002 -->
## 対象

- TC-ID: TC-order-002
- 実行: runs/20261118-new-cases

AC-ID

```
AC-022
```

環境

```
new
```

版

```
2.3.0（画面の右下の表示）
```

テスト

```
automation/web/tests/order.spec.ts の「TC-order-002 …」
```

## 再現手順

```
1. 購入者のロール（SAMPLE_BUYER_USER）でログインする
2. 商品の詳細画面（商品コード P-0001）で数量に 100 を入れ、注文を押す
```

## 期待結果

```
注文されず、数量の欄の下に「数量は 99 以下にしてください」と表示される
```

## 実際の結果

```
注文履歴の画面に移り、数量 100 の注文が先頭の行に出た。エラーの表示はなかった
```

## 再現の回数

```
3回とも同じ
```

## 証跡の場所

```
runs/20261118-new-cases/evidence/TC-order-002/（02-after-submit.png、02-after-submit.values.json）
```

## 補足

```
期待結果の誤りの可能性は低い（設計書 4.2 に上限 99 の記載がある）
```

---

aidev qa issue create が runs/20261118-new-cases/result.md の NG の詳細から作りました。
````

例の値は説明のためのもので、実際の値は result.md とプロファイルから入る。

## 送る前にコマンドが止まる場合

`--dry-run` でも次の場合は止まり、本文は出ない。

- プロファイルの検査が通らない、`issue_tracker.url` と `GITEA_URL` の接続先が違う、`GITEA_URL` がない
- `--run` が `runs/<YYYYMMDD>-<run-id>` の形でない、`--tc` が TC-ID の形でない
- 上の表で「コマンドが止まる」とした項目が欠けている、結果が NG でない
- 本文か題名に秘密情報らしい記述がある。出力には本文の行番号だけが出るので、その行の値を result.md で探して書き直す
- その TC の行の列の数が表の見出しと違う、Issue の列に `#番号` 以外が書かれている

送るときには、ほかに次の場合に止まる。題名か本文にトークンの値がそのまま入っている。Issue の列にすでに番号があり、それがトークンの持ち主の開いている同じ目印の Issue の番号でない。

## 本文に書かないもの

- 秘密情報（パスワード、トークン、Cookie、セッションの ID、URL に付いたトークン）。コマンドの検査は形で見つけるので、形に当たらない値は通ってしまう。読んで確かめる
- 個人情報の値。性質と証跡の場所で書く。コマンドは検査しない
- 画像と添付ファイル。証跡はパスで示す
- 担当者やほかの利用者への呼びかけ、他の Issue の番号。値はコードブロックに入るので言及や参照にはならず、意味がない。関連する Issue は作業者に伝え、作業者が Gitea の画面で紐付ける
