# 日次のまとめと品質レポート

## Overview

QA リポジトリには、AC（`plan/acceptance.md`）、ケース（`cases/*.md`）、実行の結果（`runs/*/result.md`）が積み上がっていく。この Skill は、それを人が判断に使える2種類の報告にまとめる。日次のまとめは、その日に何を流し、何が見つかり、何が止まっているかを伝える。品質レポートは、AC がどこまで確かめられ、どこにリスクが残っているかを、リリースの判断の材料として伝える。

報告の価値は、数字が QA リポジトリの記録と一致していることにある。数字は `aidev qa trace` の JSON から数え、AI が result.md を目で数え直したり、足りない数を見当で補ったりしない。trace が数えられないものは「trace では数えられない」と書き、空欄にした理由を添える。

## When to Use

- その日のテストの実行が終わり、日次のまとめを作る
- リリースの判定や定例の前に、品質レポートを作る
- 残るリスクを、テスト戦略のリスクの評価と今の結果で突き合わせたい

使わない場面は次のとおり。

- ケースを流して result.md を作るのは aidev-qa-test-run。result.md がまだないなら、先にそちらを使う
- NG の起票は aidev-qa-bug-ticket、修正の確認は aidev-qa-fix-verify を使う
- リスクの評価そのものを作り直すのは aidev-qa-strategy を使う。この Skill はリスクの帯を書き換えない
- C-HUB のタスクの状況の集計や、Gitea の Issue の開閉の確認はしない。どちらにも問い合わせない

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`product` を使う。最初に読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-report` で検査する。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう
- `aidev qa trace` の JSON（下の「数字の取り方」）
- `plan/strategy.md` のリスク分析の表（機能、AC、帯）。品質レポートで使う
- `runs/*/result.md` の「実行不能の理由」の節。理由の文言だけを使い、数は数えない
- 対象の日付。言われなければ作業者のローカルの今日とし、報告に書く

出力は次のとおり。形式は `references/report-format.md` にある。

- 日次のまとめ `reports/<YYYYMMDD>-daily.md`
- 品質レポート `reports/quality-<YYYYMMDD>.md`
- 作業者への返答。trace のエラーの指摘の有無、主な数字、書いたファイルのパスを書く。コミットするかは作業者が決める

同じ名前のファイルがすでにあれば、上書きする前に作業者に確かめる。前に出した報告を誰かが読んでいるかもしれないからである。

## 数字の取り方

QA リポジトリの直下で次を実行し、標準出力の JSON を使う。

```bash
aidev qa trace .
```

`ok` が false で `error` だけが返ったとき（DIR の誤りなど）は、報告を作らずに作業者に伝える。`findings` に level が error の指摘があるときは終了コードが 1 になるが、JSON は揃っているので報告は作る。そのときは報告の先頭に、エラーの指摘の件数と、コードごとの内容を書く。エラーの指摘は記録の抜け（NG に Issue がない、AC に TC がない、実行不能に理由がない、表が読めない）なので、その下の数字もその分だけ実態とずれている。読む人がそれを先に知る必要がある。

数え方の定義は `references/report-format.md` の「数字の定義」に従う。要点は、結果は AC につながる TC ごとの最新の行で数え、同じ TC が複数の AC に出てきても1件とすることである。これは `--html` の上の件数のまとめと同じ数え方なので、HTML を作ったときは件数が一致するかで検算できる。

表で見たいと言われたときは、HTML を QA リポジトリの外に書く。`--html` の出力先は実行場所から下の相対パスなので、QA リポジトリの親のディレクトリで実行する。

```bash
cd ..
aidev qa trace <QA リポジトリのディレクトリ名> --html <QA リポジトリのディレクトリ名>-trace.html
```

HTML は `reports/` に置かない。いつでも作り直せる表示用の生成物で、作成日時を持つため、置けばすぐに runs/ の記録と食い違う。報告の正本は Markdown の `reports/*.md` とし、HTML のパスも報告に書かない（作業者の PC の絶対パスには利用者名が入ることがある）。

## 判断の基準

- 日次のまとめの「その日の run」は、ディレクトリ名が `runs/<YYYYMMDD>-` で始まる run である。JSON の最新の行と `issues[].fixRun` に出てくるものを数える。`runs/` にその日の run があるのに JSON に出てこなければ（その run の TC がどの AC にもつながらない、後の run に結果を上書きされた）、run の名前を挙げ、trace で数えられる行がないと書く
- 「新しい NG」は、その日の run で NG の行である。前の日から続く NG かどうかは、前の日次のまとめの NG の一覧と TC-ID で突き合わせて分ける。前のまとめがなければ分けずに「その日の NG」とだけ書く
- 実行不能の理由は result.md の「実行不能の理由」から写す。件数は JSON の 実行不能 の数とし、理由ごとの一覧の合計がそれと合うことを確かめる。合わなければ、合わない TC を挙げる
- 機能は TC-ID の `TC-<機能>-<連番>` の `<機能>` で分ける。傾向は件数と TC-ID・Issue 番号で示し、原因の推測は書かない。原因が分かっているものは、その報告（`reports/cause-*.md` など）を参照先として挙げる
- 残るリスクは、`plan/strategy.md` のリスクの表の行ごとに、その AC の TC の最新の結果と Issue の状態を突き合わせて決める。帯は戦略に書かれたものをそのまま使い、結果を見て付け直さない。戦略にリスクの表がなければ、残るリスクの節に「plan/strategy.md にリスクの評価がない」と書き、リスクを作らない
- Issue の状態は result.md の記録から trace が決めたもの（確認済み、未確認、要確認、効いていない）を使う。Gitea で閉じられているかは見ない
- C-HUB の滞留時間（QA のリードタイム）は、読み取りの手段が決まるまで「後の段階で検討」と書く。数字を置かない

## 書かないもの

報告に写すのは、ID（AC、TC、Issue）、件数、結果、run のディレクトリ名、AC の本文、TC の名前、戦略のリスクの行までにする。result.md の再現手順、実際の結果、証跡のセル、担当者のメモ、ロールのアカウント名、環境の URL や接続情報は写さない。報告は案件の外の人も読むので、個人情報や秘密情報が入ると、取り消せない形で広がる。理由の文言に個人名やアカウントが含まれていたら、その部分を「（個人の情報のため省略）」に置き換える。

Gitea と C-HUB には必ず何も書き込まない。報告を Issue やタスクに貼るかは、作業者が報告を読んで決める。

## よくある誤り

- JSON にない数を result.md や cases/ から目で数えて足す。見当で埋める
- trace のエラーの指摘を、報告の末尾や付録に回す。エラーがあるのに「全件 OK」のような書き出しにする
- 同じ TC を AC ごとに数えて、結果の件数を水増しする
- その日の NG を、前の日から続くものかを確かめずに「新しい不具合」と書く
- リスクの帯を、結果を見て付け直す。戦略にないリスクを作る
- Gitea の画面で閉じられた Issue を確認済みとする
- HTML を `reports/` や QA リポジトリの中に置く。報告に作業者の PC の絶対パスを書く
- 再現手順や実際の結果、担当者の名前を報告に写す
- C-HUB の滞留時間に、手で見た数字や見積もりを書く

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- `aidev qa trace .` の JSON から、`references/report-format.md` の定義どおりに数え、報告の数字がすべて JSON と一致する
- trace にエラーの指摘があれば、報告の先頭にその件数と内容を書いた
- 日次のまとめと品質レポートを、`reports/` の決まった名前で、形式どおりに書いた。既存のファイルは作業者に確かめずに上書きしていない
- 残るリスクを `plan/strategy.md` の帯のまま突き合わせた。リスクの表がなければ、そう書いた
- C-HUB の滞留時間は「後の段階で検討」と書いた
- 個人情報と秘密情報を写していない。Gitea と C-HUB には何も書き込んでいない
