# 日次のまとめと品質レポート

## Overview

QA リポジトリには、AC（`plan/acceptance.md`）、ケース（`cases/*.md`）、実行の結果（`runs/*/result.md`）が積み上がっていく。この Skill は、それを人が判断に使える2種類の報告にまとめる。日次のまとめは、その日に何を流し、何が見つかり、何が止まっているかを伝える。品質レポートは、AC がどこまで確かめられ、どこにリスクが残っているかを、リリースの判断の材料として伝える。合否は書かない。基準は aidev-qa-strategy で作った戦略にあり、判断するのは読む人である。

報告の価値は、数字が QA リポジトリの記録と一致していることにある。数字は `aidev qa trace` の JSON から数え、AI が result.md を目で数え直したり、足りない数を見当で補ったりしない。trace が数えられないものは「trace では数えられない」と書き、空欄にした理由を添える。

## When to Use

- その日のテストの実行が終わり、日次のまとめを作る
- リリースの判定や定例の前に、品質レポートを作る
- 残るリスクを、テスト戦略のリスクの評価と今の結果で突き合わせたい

使わない場面は次のとおり。

- ケースを流して result.md を作るのは aidev-qa-test-run。result.md がまだないなら、先にそちらを使う
- NG の起票は aidev-qa-bug-ticket、修正の確認は aidev-qa-fix-verify を使う
- リスクの評価や終了条件そのものを作り直すのは aidev-qa-strategy を使う。この Skill はリスクの帯も基準も書き換えない
- C-HUB のタスクの状況の集計や、Gitea の Issue の開閉の確認はしない。どちらにも問い合わせない

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`product` を使う。最初に読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-report` で検査する。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう
- `aidev qa trace` の JSON（下の「数字の取り方」）
- `plan/strategy.md` のリスク分析の表（機能、影響度、起こりやすさ、スコア、帯、対応方針、関連する要件 ID）と、開始と終了の基準。品質レポートで使う
- `plan/acceptance.md`。AC の本文と出どころを、リスクの行と AC を結びつけるのに使う
- `cases/*.md` の TC の名前と、`runs/*/result.md` の実行不能の理由。理由は、JSON で 実行不能 になっている TC-ID についてだけ、その行の run の result.md から読む（読み方は `references/report-format.md` の「JSON にない文言」）。文言だけを使い、数は数えない
- 対象の日付。言われなければ作業者のローカルの今日とし、報告に書く

出力は次のとおり。形式は `references/report-format.md` にある。

- 日次のまとめ `reports/<YYYYMMDD>-daily.md`
- 品質レポート `reports/quality-<YYYYMMDD>.md`
- 作業者への返答。trace のエラーの指摘の有無、主な数字、書いたファイルのパスを書く。コミットするかは作業者が決める

同じ名前のファイルがすでにあれば、上書きする前に作業者に確かめる。前に出した報告を誰かが読んでいるかもしれないからである。

## 数字の取り方

QA リポジトリの直下で次を実行し、標準出力の JSON を使う。

```bash
aidev qa trace .
```

trace はコミットではなく作業ツリーを読む。そのため、`git rev-parse --short HEAD` の短いハッシュと、`git status --porcelain` で未コミットの変更があるかを、報告の「数字の出どころ」に書く。どちらも報告を書く前の状態で確かめる。報告のファイル自体は数字を取ったあとに書くので、未コミットの変更には数えない。QA リポジトリが git 管理でなければ、「git なし（コミットと未コミットの変更は確かめられない）」と書く。

`ok` が false で `error` だけが返ったとき（DIR の誤りなど）は、報告を作らずに作業者に伝える。`findings` に level が error の指摘があるときは終了コードが 1 になるが、JSON は揃っているので報告は作る。そのときは報告の先頭に、エラーの指摘の件数と、コードごとの内容を書く。エラーの指摘は記録の抜け（NG に Issue がない、AC に TC がない、実行不能に理由がない、表や AC の行やケースの見出しが読めない）なので、その下の数字もその分だけ実態とずれている。読む人がそれを先に知る必要がある。

使う値は次のとおり。数え方の定義は `references/report-format.md` の「数字の定義」に従う。

- `coverage[].latest` と `coverage[].notRun`：AC につながる TC の、最新の結果と未実行。どちらの TC にも、ケースの優先度 `priority` と実行の種類 `execution`（自動・手動）が付く（書かれていなければ付かない）
- `runDetails`：run ごとの、その run のすべての行の OK・NG・実行不能の数、表の行（`rows`。TC-ID、結果、Issue 番号だけ）、改修確認の結果（Issue の番号と判定）。日次のまとめはこれで数え、NG と実行不能の一覧もこの `rows` から作る
- `issues`：Issue ごとの TC と状態

最新の結果は、AC につながる TC ごとの最新の行で数え、同じ TC が複数の AC に出てきても1件とする。これは `--html` の上の件数のまとめと同じ数え方なので、HTML を作ったときは件数が一致するかで検算できる。

表で見たいと言われたときは、HTML を QA リポジトリの外に書く。`--html` の出力先は実行場所から下の相対パスなので、QA リポジトリの親、またはその外の作業ディレクトリで実行する。

```bash
cd ..
aidev qa trace <QA リポジトリのディレクトリ名> --html <QA リポジトリのディレクトリ名>-trace.html
```

HTML は `reports/` に置かない。いつでも作り直せる表示用の生成物で、作成日時を持つため、置けばすぐに runs/ の記録と食い違う。報告の正本は Markdown の `reports/*.md` とし、HTML のパスも報告に書かない（作業者の PC の絶対パスには利用者名が入ることがある）。

## 判断の基準

- 日次のまとめの「その日の run」は、`runDetails` のうち `date` が対象の日付の run である。対象の日付より後の日付の run は、その日の報告の数に入れない。品質レポートの最新の結果にも入れないので、`runDetails` の `dir` で名前を挙げ、「trace の指摘」の節に「対象の日付より後の run（数に入れていない）」として並べる。件数はその run のすべての行で数え、表の見出しにもそう書く。同じ TC を同じ日に2回流していれば、両方の行が数に入る
- NG の一覧は、その日の run の `runDetails[].rows` のうち NG の行である。行の数は `runDetails` の NG の数と必ず一致する。後の run で結果が置き換わった行は、「今の結果」の列にその結果と run を書く。後の run の結果が同じ（NG のまま）でも、その run の結果を今の結果とする
- 「新しい NG」は、前の日次のまとめの NG の一覧と TC-ID で突き合わせて分ける。前のまとめがなければ分けずに「その日の NG」とだけ書く
- 実行不能の一覧は、その日の run の `runDetails[].rows` のうち 実行不能 の行で、TC-ID と行の数は JSON から取る。理由だけは JSON にないので、その TC-ID についてだけ result.md から読み、個人の情報を省いて写す。理由が書かれていなければ「記載なし」と書く。理由は止まっている原因（手動確認を待っているのか、環境が使えないのか）を読む人に伝えるので、日次のまとめから外さない
- `runDetails[].environment` や `version` がない run は、その欄に「記載なし」と書く
- trace に `run-order` の警告があれば、同じ日の run の run-id の順と実行日時の順が逆なので、最新の結果を取り違えているおそれがある。その run を「trace の指摘」に挙げ、run-id を直すよう作業者に伝える
- 自動のケースの実行割合は、実行が「自動」の AC につながる TC のうち、最新の結果が OK か NG のものの割合である。手動のケースは別に、件数と OK の数を書く。手動確認の残りは、実行が「手動」で最新の結果が OK でない TC（未実行を含む）である。実行の種類が書かれていない TC は、どちらにも入れずに件数を書く
- 機能の軸は2つあり、名前で区別する。「TC の機能名」は TC-ID の `TC-` と最後の `-<数字>` の間の文字列で、不具合の傾向に使う。「戦略の機能」は `plan/strategy.md` のリスクの表の機能の列で、残るリスクに使う。2つを同じものとして扱わない
- リスクの行と AC の結びつけは次の順に決める。行に AC-ID の列があれば、それを使う。なければ、関連する要件 ID を、出どころ（前後の空白を除く）がその ID と完全に一致する `plan/acceptance.md` の AC に結びつける。AC-ID の列で結びつけたときは、「関連する要件 ID」の列に「AC 列から対応」と書く（要件 ID を見当で埋めない）。どの AC にも結びつかない行は「AC に結びつかないリスク」に並べ、AC を見当で当てない
- 残るリスクは、結びつけた AC の TC の最新の結果と Issue の状態から書く。帯は戦略に書かれたものをそのまま使い、結果を見て付け直さない。戦略にリスクの表がなければ、残るリスクの節に「plan/strategy.md にリスクの評価がない」と書き、リスクを作らない
- TC の機能名ごとの不具合の傾向の NG は、TC の最新の結果が NG のものの数である。run の行を数えず、同じ TC が複数の run で NG でも1件とする
- リスクの表と AC の表で ID が多いときは、件数と ID を5件まで書き、残りは「ほか n 件」とする。全部の一覧は trace の HTML と JSON にあり、報告には写さない
- trace の `case-not-run` の警告の数は、AC につながる未実行の TC の数より多いことがある。AC が分からない TC は AC につながらず `coverage` に入らないが、警告には数えられるからである。差があるときは、その理由を一文で書く
- 要点には、事実だけを3〜5行で書く。ID の一覧は要点に置かない。CRITICAL・HIGH の帯で何かが残っているリスクの行の数、確認済みでない Issue の数、未実行の数、戦略の終了条件のうち JSON で確かめられるものを満たしているか。優先度で決まる条件（例：優先度が高いケースがすべて OK）は、`priority` で確かめられる。良い悪いの評価や、リリースしてよいかは書かない
- Issue の状態は result.md の記録から trace が決めたもの（確認済み、未確認、要確認、効いていない）を使う。Gitea で閉じられているかは見ない
- C-HUB の滞留時間（QA のリードタイム）は、読み取りの手段が決まるまで「後の段階で検討」と書く。数字を置かない

## 書かないもの

報告に写してよいのは、ID（AC、TC、Issue）、件数、結果、run のディレクトリ名、環境の名前、版の括弧より前、戦略のリスクの行、そして次の場所の本文だけである。

- AC の本文：品質レポートの「AC の網羅」（TC のない AC と結果のない AC の一覧）と「残るリスク」
- TC の名前：「NG と Issue」と「手動確認の残り」
- 実行不能の理由：「実行不能とその理由」と「手動確認の残り」

これらの本文に個人名、アカウント名、URL、接続情報が含まれていたら、その部分を「（個人の情報のため省略）」に置き換える。result.md の再現手順、実際の結果、証跡のセル、担当者のメモは写さない。Issue の題名も写さない（この Skill は Gitea を読まない）。報告は案件の外の人も読むので、個人情報や秘密情報が入ると、取り消せない形で広がる。

Gitea と C-HUB には必ず何も書き込まない。報告を Issue やタスクに貼るかは、作業者が報告を読んで決める。

## よくある誤り

- JSON にない数を result.md や cases/ から目で数えて足す。見当で埋める
- trace のエラーの指摘を、報告の末尾や付録に回す。エラーがあるのに「全件 OK」のような書き出しにする
- 同じ TC を AC ごとに数えて、結果の件数を水増しする
- 日次の件数を最新の結果だけで数え、後の run に置き換わった行を落とす
- 自動と手動を混ぜて「AI が実行した割合」と書く。手動確認の残りを、手動確認待ちの行だけで数え、未実行の手動のケースを落とす
- TC の機能名と戦略の機能を同じ列に並べる。リスクの行の AC を、名前が似ているからと当てる
- その日の NG を、前の日から続くものかを確かめずに「新しい不具合」と書く
- リスクの帯を、結果を見て付け直す。戦略にないリスクを作る。要点に合否を書く
- Gitea の画面で閉じられた Issue を確認済みとする
- HTML を `reports/` や QA リポジトリの中に置く。報告に作業者の PC の絶対パスを書く
- 再現手順や実際の結果、担当者の名前、Issue の題名を報告に写す
- C-HUB の滞留時間に、手で見た数字や見積もりを書く

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- `aidev qa trace .` の JSON から、`references/report-format.md` の定義どおりに数え、報告の数字がすべて JSON と一致する。数字の出どころに QA リポジトリのコミットと未コミットの変更の有無を書いた
- trace にエラーの指摘があれば、報告の先頭にその件数と内容を書いた
- 日次のまとめと品質レポートを、`reports/` の決まった名前で、形式どおりに書いた。既存のファイルは作業者に確かめずに上書きしていない
- 残るリスクを `plan/strategy.md` の帯のまま突き合わせた。AC に結びつかない行はそう分けた。リスクの表がなければ、そう書いた
- C-HUB の滞留時間は「後の段階で検討」と書いた
- 写してよい場所の外に本文を写していない。Gitea と C-HUB には何も書き込んでいない
