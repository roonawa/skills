# 報告の形式と数字の定義

aidev-qa-report で `reports/<YYYYMMDD>-daily.md` と `reports/quality-<YYYYMMDD>.md` を書くときに読む。数字の定義は2つの報告で共通である。

## 数字の定義

`aidev qa trace .` の JSON のどの値から数えるかを決める。ここにない数は報告に書かない。

| 数 | JSON からの数え方 |
|---|---|
| AC の数、TC の数、run の数 | `acs`、`cases`、`runs` |
| TC のある AC | `coverage` のうち `cases` が空でないもの |
| TC のない AC | `coverage` のうち `cases` が空のもの。`ac-uncovered` の指摘と一致する |
| 結果のある AC | `coverage` のうち `latest` が空でないもの |
| AC につながる TC | `coverage[].cases` の TC-ID の重複を除いた数 |
| 最新の結果（OK・NG・実行不能） | `coverage[].latest` を TC-ID で重複を除き、`result` ごとに数える |
| 未実行 | AC につながる TC のうち、`latest` に出てこないもの |
| Issue の状態 | `issues[].status` ごとに数える（確認済み、未確認、要確認、効いていない） |
| 検査の指摘 | `findings` を `level`（error、warning）と `code` ごとに数える |
| AI が実行したケースの割合 | （OK ＋ NG）÷ AC につながる TC。分子と分母も並べて書く |

TC-ID の重複を除くのは、1つの TC が複数の AC を参照すると、`coverage` に同じ行が AC の数だけ出てくるからである。この数え方は `aidev qa trace --html` の上の件数のまとめと同じである。

JSON は TC ごとに自動と手動を区別しない。実行が「手動」のケースは、結果が 実行不能 で理由が「手動確認待ち」の行として出てくる。そのため、AI が実行したケースの割合は、結果が OK か NG の行（実際に流して判定まで進んだもの）を数える。実行不能の行には、手動確認待ちのほかに、環境やデータの都合で流せなかったものも含まれる。内訳は result.md の理由で分ける。

日次のまとめでは、上の行のうち `run` が `runs/<YYYYMMDD>-` で始まるものだけを数える。確認済みになった Issue は、`status` が 確認済み で `fixRun` がその日の run のものである。

下の2つの形の例の数字は、形を示すためのものである。報告には、その日に実行した trace の JSON から数えた値を書く。

割合は小数第1位までの百分率で書き、分子と分母を添える（例：62.5%（10 / 16））。分母が 0 なら割合を書かず「対象なし」とする。

## 日次のまとめ

`reports/<YYYYMMDD>-daily.md` の形は次のとおり。節の並びを変えない。該当がない節も見出しを残し、「なし」と書く。

```markdown
# 日次のまとめ 2026-11-19

- 数字の出どころ: aidev qa trace .（QA リポジトリのコミット 1a2b3c4、未コミットの変更なし）
- 作成: 2026-11-19 18:05 +09:00

## trace の指摘

エラーの指摘はありません。警告は 84 件（case-not-run 83 件、issue-unconfirmed 1 件）です。

## その日の run

| run | 最新の結果の行 |
|---|---|
| runs/20261119-csv-fix | 13 |

runs/20261119-csv-detail は、どの行も後の run の結果に置き換わったため、trace で数えられる行がありません。

## 結果の内訳

| OK | NG | 実行不能 |
|---|---|---|
| 10 | 2 | 1 |

## NG と Issue

| TC-ID | Issue | Issue の状態 |
|---|---|---|
| TC-csv-002 | #2 | 未確認 |
| TC-csv-003 | #2 | 未確認 |

## 実行不能とその理由

| TC-ID | 理由 |
|---|---|
| TC-detail-001 | 手動確認待ち |

## 確認済みになった Issue

| Issue | TC | 改修確認の run |
|---|---|---|
| #1 | TC-csv-004、TC-csv-005、TC-csv-006 | runs/20261119-csv-fix |
```

- trace にエラーの指摘があるときは、「trace の指摘」の節を「⚠ trace にエラーの指摘が N 件あります」で始め、コードと内容と場所の表を置く。そのうえで、以下の数字がその分ずれていることを一文で書く
- 前の日次のまとめと突き合わせられたときだけ、「NG と Issue」の表に「区分」の列を足し、「その日の NG」と「前から続く NG」に分ける。突き合わせていなければ列を置かない
- NG の行に Issue がないとき（`ng-without-issue`）は、Issue の列に「なし（起票待ち）」と書く
- 実行不能の理由は result.md の `- 理由:` の行の文言を短く写す。個人の情報やアカウント名、URL は写さない

## 品質レポート

`reports/quality-<YYYYMMDD>.md` の形は次のとおり。節の並びを変えない。

```markdown
# 品質レポート 2026-11-19

- 数字の出どころ: aidev qa trace .（QA リポジトリのコミット 1a2b3c4、未コミットの変更なし）
- 作成: 2026-11-19 18:10 +09:00
- 対象: AC 15 件、TC 96 件、run 2 件

## trace の指摘

エラーの指摘はありません。警告は 84 件です。

## AC の網羅

| TC のある AC | TC のない AC | 結果のある AC |
|---|---|---|
| 15 / 15 | 0 | 6 |

## 最新の結果

| OK | NG | 実行不能 | 未実行 | AC につながる TC |
|---|---|---|---|---|
| 10 | 2 | 1 | 83 | 96 |

AI が実行したケースの割合: 12.5%（12 / 96）

## 機能ごとの不具合の傾向

| 機能 | NG | Issue | 未解決の Issue |
|---|---|---|---|
| csv | 2 | #1、#2 | #2（未確認） |

## 残るリスク

| 帯 | 機能（戦略の表のまま） | AC | 残っているもの |
|---|---|---|---|
| CRITICAL | CSV 出力の権限 | AC-015 | 未実行 3 件（TC-csv-010〜012） |
| HIGH | 一覧の並び順 | AC-006 | NG 1 件、#2 未確認 |

## 手動確認の残り

| TC-ID | 理由 |
|---|---|
| TC-detail-001 | 手動確認待ち |

## QA のリードタイム

C-HUB の滞留時間は、読み取りの手段が決まるまで後の段階で検討します。
```

- 「trace の指摘」の書き方は日次のまとめと同じ。エラーの指摘があれば、この節がレポートの最初の節になる
- 「AC の網羅」では、TC のない AC と結果のない AC の AC-ID を表の後に並べる
- 「機能ごとの不具合の傾向」は、NG の行か Issue がある機能だけを並べ、NG の多い順にする。未解決の Issue は、状態が 確認済み 以外のものである
- 「残るリスク」は、戦略のリスクの表の行のうち、AC に NG、確認済み以外の Issue、未実行、実行不能、TC のない状態のどれかが残る行だけを、帯の重い順に並べる。残るものがない行は表に入れず、表の後に「残るものがない: AC-001、AC-002 …」と1行で書く。戦略にリスクの表がなければ、表の代わりに「plan/strategy.md にリスクの評価がないため、残るリスクは評価していない」と書く
- 「手動確認の残り」は、最新の結果が 実行不能 で、result.md の理由が「手動確認待ち」の TC を並べる。手動確認待ち以外の理由の 実行不能 は、表の後に別に並べる
- 「QA のリードタイム」は、上の文のまま書き、数字を置かない
