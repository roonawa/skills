# 報告の形式と数字の定義

aidev-qa-report で `reports/<YYYYMMDD>-daily.md` と `reports/quality-<YYYYMMDD>.md` を書くときに読む。数字の定義は2つの報告で共通である。

## 数字の定義

`aidev qa trace .` の JSON のどの値から数えるかを決める。ここにない数は報告に書かない。

| 数 | JSON からの数え方 |
|---|---|
| AC の数、TC の数、run の数 | `acs`、`cases`、`runs` |
| TC のある AC | `coverage` のうち `cases` が空でないもの |
| TC のない AC | `coverage` のうち `cases` が空のもの。`ac-uncovered` の指摘と一致する |
| 結果のある AC | `coverage` のうち `latest` が空でないもの |
| すべての TC が OK の AC | `coverage` のうち `cases` が空でなく、`notRun` が空で、`latest` がすべて OK のもの |
| AC につながる TC | `coverage[].cases` の TC-ID の重複を除いた数 |
| 最新の結果（OK・NG・実行不能） | `coverage[].latest` を TC-ID で重複を除き、`result` ごとに数える |
| 未実行 | `coverage[].notRun` を TC-ID で重複を除いた数 |
| 自動のケースの実行割合 | 分母は `latest` と `notRun` のうち `execution` が 自動 の TC。分子はそのうち `latest` の `result` が OK か NG の TC |
| 手動のケース | `latest` と `notRun` のうち `execution` が 手動 の TC の数と、そのうち `latest` の `result` が OK の数 |
| 手動確認の残り | `execution` が 手動 で、`latest` の `result` が OK でない TC と、`notRun` の TC |
| 実行の種類のない TC | `latest` と `notRun` のうち `execution` がない TC の数 |
| その日の run の件数 | `runDetails` のうち `date` が対象の日付の run の `ok`、`ng`、`blocked`。その run のすべての行の数 |
| その日の改修確認 | その日の run の `runDetails[].fixChecks`（Issue の番号と判定） |
| その日の NG の行 | その日の run の `runDetails[].rows` のうち `result` が NG の行。行の数は、その日の run の `ng` の合計と一致する |
| その日の実行不能の行 | その日の run の `runDetails[].rows` のうち `result` が 実行不能 の行。行の数は、その日の run の `blocked` の合計と一致する |
| TC の今の結果 | `runDetails` を前から見て、その TC の行がある最も後の run の行の `result` と、その run の `dir` |
| Issue の状態 | `issues[].status` ごとに数える（確認済み、未確認、要確認、効いていない） |
| 検査の指摘 | `findings` を `level`（error、warning）と `code` ごとに数える |

TC-ID の重複を除くのは、1つの TC が複数の AC を参照すると、`coverage` に同じ TC が AC の数だけ出てくるからである。最新の結果と未実行の数え方は、`aidev qa trace --html` の上の件数のまとめと同じである。

`runDetails` の件数は最新の結果ではない。後の run で結果が置き換わった行も、その run の数に入る。日次のまとめではこの数を使い、品質レポートの最新の結果と混ぜない。

TC の機能名は、TC-ID の `TC-` と最後の `-<数字>` の間の文字列である（`TC-order-list-003` なら `order-list`）。戦略の機能（リスクの表の機能の列）とは別の軸として扱う。

`runDetails[].version` は result.md の冒頭の行のままなので、括弧の中に確かめ方の説明が続くことがある。報告には括弧より前だけを写す。`runDetails[].version` や `runDetails[].environment` がない run（result.md の冒頭に「版」や「環境」の行がない）は、その欄に「記載なし」と書く。見当で埋めない。

`runDetails[].rows` は、その run の表の行を表の順に並べたもので、TC-ID、結果、Issue 番号だけを持つ。証跡、実行不能の理由、そのほかの自由記述は JSON に入らない。

JSON にない文言は、次の場所からだけ読む。数はここから数えない。

- TC の名前：`cases/*.md` の、その TC-ID の見出し
- AC の本文と出どころ：`plan/acceptance.md`
- 実行不能の理由：JSON の `runDetails[].rows`（日次のまとめ）か `coverage[].latest`（手動確認の残り）で 実行不能 になっている TC-ID についてだけ、その行のある run の result.md から読む。「## 実行不能の理由」の `### <TC-ID>` の下の `- 理由:` の行を使い、なければ結果のセルの `実行不能（理由）` の括弧の中を使う。どちらもなければ「記載なし」と書く。ほかの TC の理由や、result.md のほかの節は読まない。写すときは SKILL.md の「書かないもの」のとおり、個人名、アカウント名、URL、接続情報を「（個人の情報のため省略）」に置き換える
- リスクの表と終了条件：`plan/strategy.md`

下の2つの形の例の数字は、形を示すためのものである。報告には、その日に実行した trace の JSON から数えた値を書く。

割合は小数第1位までの百分率で書き、分子と分母を添える（例：12.6%（12 / 95））。分母が 0 なら割合を書かず「対象なし」とする。

## 日次のまとめ

`reports/<YYYYMMDD>-daily.md` の形は次のとおり。節の並びを変えない。該当がない節も見出しを残し、「なし」と書く。

```markdown
# 日次のまとめ 2026-11-19

- 数字の出どころ: aidev qa trace .（QA リポジトリのコミット 1a2b3c4、未コミットの変更なし）
- 作成: 2026-11-19 18:05 +09:00

## trace の指摘

エラーの指摘はありません。警告は 84 件（case-not-run 83 件、issue-unconfirmed 1 件）です。

## その日の run

件数は、それぞれの run のすべての行の数です（後の run で置き換わった行も含みます）。

| run | 環境 | 版 | OK | NG | 実行不能 | 改修確認 |
|---|---|---|---|---|---|---|
| runs/20261119-csv-detail | new | 記載なし | 2 | 3 | 1 | なし |
| runs/20261119-csv-fix | new | 6b6cab6 | 2 | 1 | 0 | #1 確認済み |
| 合計 | | | 4 | 4 | 1 | |

## NG と Issue

その日の run の NG の行です（4 行）。今の結果は、その TC の行がある最も後の run の結果です。

| run | TC-ID | TC の名前 | Issue（状態） | 今の結果 |
|---|---|---|---|---|
| runs/20261119-csv-detail | TC-csv-002 | 区切り文字の設定が反映される | #2（未確認） | NG |
| runs/20261119-csv-detail | TC-csv-004 | 出力の列の順が画面と同じ | #1（確認済み） | OK（runs/20261119-csv-fix） |
| runs/20261119-csv-detail | TC-csv-005 | 空の値が空のセルになる | #1（確認済み） | OK（runs/20261119-csv-fix） |
| runs/20261119-csv-fix | TC-csv-003 | 改行を含む値が1つのセルに入る | #2（未確認） | NG |

## 実行不能とその理由

その日の run の実行不能の行です（1 行）。

| run | TC-ID | 理由 |
|---|---|---|
| runs/20261119-csv-detail | TC-detail-001 | 手動確認待ち |

## 改修確認の結果

| Issue | 判定 | 改修確認の run | 今の状態 |
|---|---|---|---|
| #1 | 確認済み | runs/20261119-csv-fix | 確認済み |
```

- trace にエラーの指摘があるときは、「trace の指摘」の節を「⚠ trace にエラーの指摘が N 件あります」で始め、コードと内容と場所の表を置く。そのうえで、以下の数字がその分ずれていることを一文で書く
- 「改修確認の結果」の「今の状態」は `issues[].status` である。判定が 確認済み でも、後の NG で 要確認 に戻っていれば、そのまま 要確認 と書く
- 前の日次のまとめと突き合わせられたときだけ、「NG と Issue」の表に「区分」の列を足し、「その日の NG」と「前から続く NG」に分ける。突き合わせていなければ列を置かない
- 「NG と Issue」と「実行不能とその理由」は、その日の run の `runDetails[].rows` から、run の順、表の順に1行ずつ並べる。同じ TC を同じ日に2回流していれば2行になる。行の数がその日の run の `ng`・`blocked` の合計と一致することを確かめる
- 「Issue（状態）」は、行の `issues` の番号ごとに `issues[].status` を括弧で添える。`issues` が空なら「なし（起票待ち）」と書く
- 「今の結果」は「数字の定義」の TC の今の結果である。その日の run の行がそのまま今の結果なら結果だけを書き、後の run で置き換わっていれば、結果とその run を書く
- 実行不能の理由は、上の「JSON にない文言」のとおり、その行の run の result.md から短く写す。日次のまとめでは理由ごとにまとめ直さず、行ごとに書く

## 品質レポート

`reports/quality-<YYYYMMDD>.md` の形は次のとおり。節の並びを変えない。

```markdown
# 品質レポート 2026-11-19

- 数字の出どころ: aidev qa trace .（QA リポジトリのコミット 1a2b3c4、未コミットの変更なし）
- 作成: 2026-11-19 18:10 +09:00
- 対象: AC 15 件、TC 96 件、run 2 件

## trace の指摘

エラーの指摘はありません。警告は 84 件です。

## 要点

- CRITICAL・HIGH の帯で何かが残っているリスクの行: 2 行（CRITICAL 1、HIGH 1）
- 確認済みでない Issue: 1 件（#2 未確認）
- 未実行の TC: 83 件（AC につながる TC 96 件のうち）
- 戦略の終了条件「CRITICAL の AC の TC がすべて OK」: 満たしていない（AC-015 に未実行 3 件）

## AC の網羅

AC 15 件の内訳です。

| TC のある AC | TC のない AC | 結果のある AC | すべての TC が OK の AC |
|---|---|---|---|
| 15 | 0 | 6 | 0 |

## 最新の結果

| OK | NG | 実行不能 | 未実行 | AC につながる TC |
|---|---|---|---|---|
| 10 | 2 | 1 | 83 | 96 |

- 自動のケースの実行割合: 12.6%（12 / 95）
- 手動のケース: 1 件（OK 0 件）
- 実行の種類のない TC: 0 件

## TC の機能名ごとの不具合の傾向

| TC の機能名 | NG | Issue | 確認済みでない Issue |
|---|---|---|---|
| csv | 2 | #1、#2 | #2（未確認） |

## 残るリスク

| 帯 | 戦略の機能 | 関連する要件 ID | AC | 残っているもの |
|---|---|---|---|---|
| CRITICAL | CSV 出力の権限 | 要件 3.2 | AC-015 | 未実行 3 件（TC-csv-010〜012） |
| HIGH | 一覧の並び順 | 要件 4.1 | AC-006 | NG 1 件、#2 未確認 |

残るものがない: AC-001、AC-002

### AC に結びつかないリスク

| 帯 | 戦略の機能 | 関連する要件 ID |
|---|---|---|
| MEDIUM | 帳票の文字化け | 要件 7.3 |

## 手動確認の残り

| TC-ID | TC の名前 | 最新の結果 | 理由 |
|---|---|---|---|
| TC-detail-001 | 詳細画面の印刷の見た目 | 実行不能 | 手動確認待ち |

## QA のリードタイム

C-HUB の滞留時間は、読み取りの手段が決まるまで後の段階で検討します。
```

- 「trace の指摘」の書き方は日次のまとめと同じ。エラーの指摘があれば、この節がレポートの最初の節になる
- 「要点」は3〜5行の事実だけにする。終了条件は、JSON の数で確かめられるもの（AC の網羅、未実行、NG、Issue の状態）だけを「満たしている」「満たしていない」と書き、確かめられないものは「trace では確かめられない」と書く。合否やリリースの可否は書かない
- 「AC の網羅」では、表の後に、TC のない AC と結果のない AC の AC-ID と本文を並べる
- 「最新の結果」の割合と件数は「数字の定義」のとおり数える。手動確認待ちの 実行不能 は手動確認の残りにも出るが、最新の結果の数は変えない
- 「TC の機能名ごとの不具合の傾向」は、NG の行か Issue がある TC の機能名だけを並べ、NG の多い順にする。確認済みでない Issue は、状態が 確認済み 以外のものである
- 「残るリスク」は、戦略のリスクの表の行を AC に結びつけ（結びつけ方は SKILL.md の「判断の基準」）、AC に NG、確認済み以外の Issue、未実行、実行不能、TC のない状態のどれかが残る行だけを、帯の重い順に並べる。残るものがない行は表に入れず、表の後に「残るものがない: AC-…」と1行で書く。AC に結びつかない行は「AC に結びつかないリスク」に並べ、残っているものは書かない。戦略にリスクの表がなければ、表の代わりに「plan/strategy.md にリスクの評価がないため、残るリスクは評価していない」と書く
- 「手動確認の残り」は、実行が「手動」で最新の結果が OK でない TC と、未実行の手動の TC を並べる。未実行なら最新の結果を「未実行」、理由を空にする
- 「QA のリードタイム」は、上の文のまま書き、数字を置かない
