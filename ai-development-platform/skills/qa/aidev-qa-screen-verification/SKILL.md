# 画面単位の検証の取りまとめ

## Overview

画面の内部を作り直す改修が終わると、その画面には、改修前の挙動の記録（基準）、認可の検証、旧版と新版の照合、証跡の確認が要る。工程ごとに Skill があるが、別々に回すと工程の間の受け渡しが抜ける。抜けやすいのは次の3つである。

- 基準の記録がない、または改修の入った版で記録されていて、照合が成り立たない
- 画面マニフェストで既知の認可の不具合として除外した項目が、改修で直ったのか残っているのかを、誰も確かめないまま照合を終える
- 比較先でテストが応答を読めずに落ちたものを差異として分類し、新版を1件も確かめないまま「検証した」と報告する

この Skill が扱うのは、工程の順番、工程の間で渡すファイル、次の工程へ進んでよいかの判断、作業者に戻す場面、画面ごとのまとめである。各工程の手順と判定の基準は、それぞれの Skill のものをそのまま使う。取りまとめの都合で緩めたり、ここで書き直したりしない。

## When to Use

- 改修が比較先の環境に入った画面について、基準の確認から照合とまとめまでを通しで行う
- 基準の特性テストがない、なくした、改修の入った版で記録してしまった画面を含めて、回帰を確かめる
- 複数の画面をまとめて渡され、画面ごとの検証の状態を1か所で示す

使わない場面は次のとおり。

- 基準の記録だけ、認可の検証だけ、照合だけを行うときは、その工程の Skill を直接使う
- 改修に入る前で比較先がまだない画面は、aidev-qa-characterization で基準を記録するところまでにする
- 期待結果を正として仕様どおりかを確かめるのは aidev-qa-test-run である。照合で分かるのは回帰がないことで、仕様どおりであることではない
- 権限の表そのものを決めること、改修そのもの、見つかった不具合の修正は扱わない
- NG と要確認からの Issue の起票（aidev-qa-bug-ticket）と、修正後の確認（aidev-qa-fix-verify）は、後の段階で追加する予定で、まだない

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。この Skill が自分で使うのは `product` と、本文の画面とソースの対応、到達手順、テストデータの準備方法、落とし穴である。`environments`、`roles`、`login`、`stack`、`evidence` は各工程の Skill が使う
- 対象の画面の一覧と、画面ごとの改修の内容（変更の一覧、コミット、設計書の節）。作業者が示す
- どの環境が基準（改修前）で、どれが比較先（改修後）かと、それぞれの版を特定する手段
- 既存の成果物。`automation/web/manifests/<画面>.json`、`automation/web/tests/`、`automation/web/authz/<機能>.json`、`automation/desktop/`、`runs/`

出力は次のとおり。工程の成果物の形は各 Skill のものである。

- 工程ごとの run。基準の環境の run、認可の run、比較先の環境の run の3つを分け、それぞれに `runs/<YYYYMMDD>-<run-id>/result.md` と `evidence/<TC-ID>/` を置く。run-id は `<対象>-base`、`<対象>-authz`、`<対象>-new` のように工程が分かる名前にする
- 認可の結果を反映した画面マニフェスト
- 照合の結果 `runs/<比較先の run>/compare.md` と、比較の HTML（`<証跡の根>/runs/<比較先の run>.compare.json` から `aidev qa compare-report` で作る）
- まとめ `runs/<比較先の run>/summary.md`。形は「5. まとめを書く」に書いた
- 作業者への返答。部分完了の画面と NG・要確認を先頭に書き、summary.md と HTML の場所を示す

## 工程の順番

| 工程 | 使う Skill | 次の工程に渡すもの | 次へ進む条件 |
|---|---|---|---|
| 0. 対象と前提 | この Skill | 画面ごとの区分の表（summary.md の冒頭） | 画面ごとに、進めるか外すかと、使う Skill が決まった |
| 1. 基準 | aidev-qa-characterization（ネイティブの画面は aidev-qa-desktop-gui） | マニフェスト、テスト、基準の run | 基準の run が改修前の版で取られ、完全で、NG がない |
| 2. 認可 | aidev-qa-authz-test | `automation/web/authz/<機能>.json`、認可の run | 対象の操作と既知の認可の不具合のすべてに行があり、結果が決まった |
| 3. 反映と凍結 | この Skill（ケースの追加は aidev-qa-characterization） | 反映したマニフェスト、凍結したコミット | 既知の認可の不具合の項目すべての扱いが決まった |
| 4. 照合 | aidev-qa-regression-compare | 比較先の run、compare.md、HTML | 照合の Skill の完了条件を満たした |
| 5. まとめ | この Skill | summary.md | 画面ごとの状態が決まった |

ログインが要る案件では、各工程の run の直前に aidev-qa-login-session でセッションを作り直す。前の工程のセッションを使い回さない。順番を入れ替えないのは、照合で見えた許可と拒否の差を分類するには、どの認可の不具合が直り、どれが承認のうえで残っているかが先に決まっている必要があるためである。

## 進め方

### 0. 対象と前提を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-screen-verification` で検査する。続けて、使う予定の Skill の名前でも同じ検査を流しておく（`--skill aidev-qa-characterization`、`aidev-qa-authz-test`、`aidev-qa-regression-compare` など）。工程の途中で必須の項目の欠けに気づくと、そこで止まる。欠けている項目は作業者に確かめ、推測で埋めない。

画面ごとに次を決め、summary.md の冒頭に区分の表として書く。

- 改修が比較先に入っているか。画面のファイルだけを見て判断しない。画面が薄い包みで、データの取得は共有の部品にあることが多い。データの経路を API の呼び出しまでたどり、改修後の呼び出しになっているかで決める。サーバーの側だけ先に改修が済み、画面はまだ旧い呼び出しのまま、ということもある。その食い違いは開発者に伝える
- 改修が入っていない画面は、入るのを待つのか、もともと対象外（本番にない検証用の画面、作り直さないと決まった画面）なのかを作業者に確かめる。どちらでもその画面を外し、理由を書いて、残りの画面を進める
- 基準と比較先のソースの場所。手元を探して見つからないことを「ない」と断定せず、作業者に確かめる。ソースが2か所にあり共有のテストの部品が食い違うときは、ファイルごとにどちらを使うかを決め、理由を残す
- 画面の技術と、使う Skill（下の表）

| 画面 | 基準の記録と照合のテスト | Skill を分ける境目 |
|---|---|---|
| ブラウザの Web の画面 | aidev-qa-characterization（Playwright） | なし |
| デスクトップアプリの中の WebView2 の画面 | aidev-qa-characterization（CDP で接続） | OS のダイアログ、外部アプリ、ネイティブのログイン画面は、マニフェストで `native-required` にして aidev-qa-desktop-gui に渡す |
| ネイティブの画面（WPF、WinForms など） | aidev-qa-desktop-gui | マニフェストはない。aidev-qa-desktop-gui のテストとネイティブの接点の一覧を分母にする。PC を占有するので、作業者と決めた時間にまとめて流す |

認可の検証は直接の HTTP リクエストで行うので、どの技術の画面でも、画面が呼ぶサーバーの操作が対象になる。サーバーを持たないアプリには認可の工程がない。その場合はまとめに「非該当」と理由を書く。

画面に AC から作った期待結果のあるケース（`cases/*.md` で特性テストではないもの）があれば、照合とは別に aidev-qa-test-run で比較先に流し、結果をまとめに含める。

### 1. 基準を確かめ、なければ記録する

基準があるかは、次の順で確かめる。どこかで落ちたら基準は「ない」として記録する。

1. 両方の環境に流せるテストのコード（`automation/web/tests/` か `automation/desktop/`）がある。マニフェストや過去の result.md が残っていても、テストの本体がなければ同じテストを両方に流せず、照合は成り立たない
2. マニフェストの `path` と `sources` が対象の画面のものである。ファイル名が似ているだけの別の画面のマニフェストを使わない
3. 基準の run とマニフェストの `observedBuild` が、基準の環境の、改修の入っていない版で取られている。改修の入った版で取った記録は基準にならない。比較先と同じものを基準と呼ぶことになり、回帰を何も検出しないためである

記録は aidev-qa-characterization で基準の環境に対して行う。基準の環境がもう改修前の版を動かしていないときは、比較先や改修の入った別の環境で代わりに記録せず、その画面を止めて作業者に戻す（改修前の版を動かせる環境を用意してもらう）。

改修が終わった後に基準を記録するときは、新版の姿がすでに分かっている。この非対称は、良い方にも悪い方にも働く。

- 新版での API の名前は、改修の内容（コミット、開発者の答え）から `matchByEnvironment` に書いてよい。分からない名前は推測で埋めない
- 基準の期待値は、基準の環境で観測したものだけから作る。新版の結果を見てから旧版の期待値を書かない
- 新版がサーバーの側で決めるようになった引数（本人の ID、基準日など）に依存する件数や行の集合を、期待値に固めない。行はキーで突き合わせる
- アサーションが読む項目が、基準の応答に実在し値が入っていることを確かめる。旧い構造にない項目を読むアサーションは、値がないもの同士で通り、成功が何も示さない。aidev-qa-characterization の「期待値を1か所だけ変えて失敗するか」の確かめで、この空読みも見つかる

基準の run から次へ進むのは、マニフェストを分母にした完全性がケースごとにそろい、NG がなく、失敗を検出できることを確かめたときだけである。基準の NG は基準の環境の異常なので、開発者に伝え、そのケースを照合の対象から外すか直るのを待つ。基準の欠けや NG を抱えたまま照合に進まない。

### 2. 認可を確かめる

aidev-qa-authz-test に渡す対象の操作は、マニフェストの `apis` に、`excluded` の `reason` が `known-authz-bug` の項目の `target` と、`acceptedRisks` の `target` を足したものである。既知の認可の不具合は、更新や削除のように通常のケースの記録がない操作のことが多く、`apis` だけを拾うと漏れる。漏れると、その不具合が直ったかを誰も確かめないまま照合が終わる。判定は `reason` の値の完全な一致で行い、似た文字列の別の理由を含めない。

認可の表は画面ではなく操作の単位なので、ほかの画面の担当者が作った表があればそれを使い、行を足す。既知の認可の不具合の項目ごとに、同じ根拠（設計書の既知の課題の節や課題の記録）を `basis` に持つ行があることを確かめる。なければ行を足してもらう。今の版の基準は基準の環境で、期待との突き合わせは比較先の環境で取る。

### 3. 認可の結果をマニフェストに反映し、凍結する

`excluded` の `known-authz-bug` と `acceptedRisks` の項目ごとに、対応する認可の行の比較先での結果を見て、次のように扱う。マニフェストの変更は aidev-qa-characterization の点検（進め方の5）を通してから入れる。

| 認可の行の結果 | 扱い |
|---|---|
| 行がない、または実行不能 | 2 に戻る。テストデータを用意できないと分かったときは、項目を `excluded` のまま保留にし、理由をまとめに書く |
| すべて OK（比較先で正しく拒否された） | `excluded` の項目はそのまま残し、`evidence` に認可の run と TC-ID を足す。`operations` に移さない。基準の版には不具合が残っているので、移すと不具合を基準として記録することになる。直ったことの証拠は認可の run である。`acceptedRisks` の項目は照合で許可と拒否の差として出るので、認可の行の `basis` を根拠に分類してもらう |
| NG があり、是正を後に回すことが承認されている | `acceptedRisks` に移し、`decidedBy`、`decidedDate`、認可の TC-ID を書く。aidev-qa-characterization でケースを足し、基準の環境で記録する |
| NG があり、承認がない | `excluded` のまま残し、認可の NG としてまとめに書く。画面は部分完了になる。承認するかを作業者だけで決めない |

既知の不具合として挙がっていない操作で、認可の行が NG になり、基準の環境でも同じ振る舞いだったときは、その不具合を `operations` の通常の挙動として記録してしまっている。作業者に示し、`excluded` に移すかを決めてもらう。移すなら aidev-qa-characterization でケースを外す。

反映が済んだら、比較先に流す前にマニフェストとテストのコードをコミットし、そのコミットをまとめに書く（凍結）。比較先の結果を見た後で基準の期待値を直してよいのは、記録の誤りと分かったときだけである。そのときは前後のコミットと理由をまとめに書く。理由のない変更は、新版に合わせて基準を書き換えたのと区別がつかない。

### 4. 照合する

aidev-qa-regression-compare で、凍結したテストのコードを比較先に流し、基準の run と照合する。比較の HTML はこの Skill では毎回作る。照合の Skill の手順に加えて、工程の切れ目で次を確かめる。

- 比較先には、まず1ケースだけ流す。セッションがその日に作ったものか、`matchByEnvironment` で応答が捕まるか、期待値の読み出しが値を返すか（空や未定義になっていないか）、前の実行が残したテストデータ（`QA-<run-id>-` などの接頭辞）が環境にないかを見てから、全ケースを流す
- 比較先のケースが全部か大半、同じ形で落ちたら、分類に入らない。応答は届いているのに値が読めない失敗は、テストが旧い構造を読んでいるためで、差異ではない。aidev-qa-characterization で読み出しを環境ごとに切り替える形に直し、期待値は新旧で共通のまま保つ。テストのコードを直したら、同じコードで基準の環境にも流し直す。照合は同じコミットのテスト同士で行うためである
- 比較先の失敗を分類する順は、テストのコードの不備、環境とデータとセッション、根拠のある意図した差分、要確認である。前の2つは差異ではないので、直して流し直す
- 照合が成り立ったかは、ケースごとに数える。スクリーンショットが撮れていても、比較先が値の照合まで届かずに止まったケースは、照合できなかったケースである。実装の不具合で止まったものは、止めた NG と、直った後に流し直すケースをまとめに書く。テストや環境のせいで止まったものが残っている間は、照合を終えない
- 使い捨てのデータを使ったケースでは、名前、ID、日時、件数が新旧で一致しないのが正常である。正規化で扱えないものは compare.md に書き、実在の同じデータで値を照合したかどうかも書く
- 流した後、テストが作ったデータが残っていないことを、接頭辞で環境を検索して確かめる。後始末が動いたはずだ、で済ませない
- ネイティブの操作（`native-required` やネイティブの画面）は、aidev-qa-desktop-gui のテストを基準と比較先の両方に、作業者と決めた時間に流して照合に含める

### 5. まとめを書く

`runs/<比較先の run>/summary.md` に、渡された画面のすべてを書く。指摘のない画面も「指摘なし」と書き、記載を省かない。

- 冒頭に、基準と比較先の環境名と版、各工程の run（基準、認可、比較先）、凍結したコミットを書く。続けて、0 の区分の表（進めた画面、外した画面と理由）
- 画面ごとの節に、状態、基準（新しく記録したか既存か。基準の run の OK の数と全数）、認可（結果ごとの件数、NG の一覧、既知の認可の不具合の項目ごとの扱い）、照合（基準と比較先それぞれの OK の数と全数、照合が成り立ったケースの数と全数、一致・意図した差分・要確認の件数、意図した差分の根拠の数、照合できなかったケースと理由、未検証の列や範囲）、基準の期待値を後から直したならその前後のコミットと理由、後片付けを検索で確かめた結果
- 最後に、全画面の NG と要確認を1つの表にまとめる（画面、TC-ID か差異の ID、期待と実際の要旨、証跡か compare.md の場所）。Issue の起票は後の段階で追加する Skill で行うので、ここでは一覧にとどめる
- 各工程の result.md、compare.md、HTML への相対パス

画面の状態は「完了」「部分完了」「未実施」のどれかにする。完了と書いてよいのは、認可の NG、要確認、保留、照合できなかったケースがどれもない画面だけである。比較先で照合が成り立ったケースについてだけ「新版でも同じ」と書く。失敗を分類し終えたことを、確かめたことと書かない。値は工程の Skill の出力から写し、手で数えない。資格情報や個人情報の値は、ほかの成果物と同じく写さない。

## 複数の画面をまとめて扱う

- 最初に、渡された全画面について 0 を済ませ、区分の表を作業者に示す。環境への書き込み（テストデータの作成と削除）を伴う工程は、各 Skill の決まりに従って、対象の画面、環境、データの範囲をまとめて示して承認を得る。過去の承認を今回の範囲に広げない
- 工程は画面ごとではなく、工程ごとに全画面をそろえて進める。基準の run と比較先の run は、それぞれ全画面のケースを1つの run にまとめる。セッションの作り直しと流す時刻をそろえるためで、照合の条件が画面ごとにずれない。ネイティブの操作は、全画面の分を1回の占有の時間にまとめる
- 認可の表は操作の単位で、画面をまたいで1つにする。同じ操作を画面ごとに別の表で確かめない
- ある画面が止まっても、ほかの画面は先へ進める。止まった画面は、止まった工程と理由をまとめに書く。ただし、共有のテストの部品を直したときは、それを使う全画面の基準と比較先を流し直す
- まとめは全画面で summary.md を1つにする。画面ごとにファイルや run を分けると、全画面の NG と要確認を横に見られなくなる
- 修正のたびに流し直しても、残すのは最終の run だけである。1回目と2回目を並べて経過を見せることはしない

## よくある誤り

- 認可の結果を待たずに照合し、既知の不具合が直ったのか承認のうえで残っているのかを決めないまま、許可と拒否の差を分類する
- 認可の対象を `apis` だけから拾い、`known-authz-bug` の項目の操作を落とす
- 直った認可の不具合を `operations` に移し、基準の版の不具合を記録する。承認の記録なしに `acceptedRisks` に入れる
- マニフェストや過去の result.md が残っていることを、基準があることの根拠にする。改修の入った版で取った記録を基準にする
- 基準がないことを理由に全体を止める。基準がない画面は記録してから進める
- 比較先の結果を見てから基準の期待値を書き、または直し、理由と前後のコミットを残さない
- 比較先の全件か大半の失敗を、意図した差分や要確認として分類する。テストの読み出しが新版に合っていないだけのことが多い
- テストのコードを直した後、比較先だけを流し直し、基準を同じコードで流し直さない
- スクリーンショットがそろったことを、照合が成り立ったことと取り違える
- 後片付けを確かめずに「片付け済み」と書く
- 画面ごとにまとめや run を分け、全画面の指摘を横に見られなくする
- 取りまとめの都合で、各 Skill の判定の基準や完了条件を緩める

## 完了条件

- `aidev qa profile check` が `--skill aidev-qa-screen-verification` と、使った各 Skill の名前で成功した
- 渡された全画面に区分があり、外した画面には理由がある
- 進めた画面のすべてで、基準の run が改修の入っていない版で取られ、完全で、NG がない。新しく記録した画面では、アサーションが値の入った項目を読んでいることを確かめた
- 既知の認可の不具合の項目と `acceptedRisks` の操作を含めて認可の表に行があり、各項目の扱いが 3 の表のとおりに決まってマニフェストに入った
- 比較先に流す前にマニフェストとテストを凍結し、その後の変更はすべて前後のコミットと理由がある
- 照合が aidev-qa-regression-compare の完了条件を満たし、比較の HTML ができた。テストや環境のせいで照合できなかったケースが残っていない
- 環境に残ったテストデータを検索で確かめた
- summary.md に全画面の状態、工程ごとの件数、NG と要確認の一覧、各成果物へのパスがあり、完了と書いた画面に NG、要確認、保留、照合できなかったケースがない
