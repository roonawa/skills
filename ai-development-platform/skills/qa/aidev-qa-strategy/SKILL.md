# テスト戦略書の作成

## Overview

テスト戦略書は、何をどこまで確かめるかを関係者が合意するための文書である。リスクの大きい機能にテストの工数を寄せ、テストレベルごとの範囲、終了条件、品質ゲートを決める。方針を決めるのは作業者と関係者で、この Skill は文書とコードを根拠に、質問と提案で判断を助ける。

戦略書の価値は、日々のテストの判断に使えることにある。根拠のない数値や、更新されない戦略書は、誤った安心感を与える。そのため、未確定の値は未確定と分かる形で残し、見直しのきっかけも戦略書に書いておく。

## When to Use

- 要件定義書や設計書がそろい、これからテスト戦略書を書く
- 改修案件で、既存コードと変更範囲からテストの重点を決める
- 以前に作った `plan/strategy.md` を、体制の変更や不具合の流出を受けて見直す

使わない場面は次のとおり。

- 1つの仕様書や機能からテストケースを作るときは aidev-qa-test-design を使う
- 個別の不具合の原因を調べるときは aidev-qa-cause-repro を使う

## 入力と出力

入力は、作業者が渡した要件定義書、設計書、既存コード、タスク管理の本文と、QA リポジトリの案件プロファイル（`knowledge/<product>/profile.md`）である。タスク管理の本文は、作業者が渡したものだけを読む。システムの API から取りに行かない。

出力は次の2つで、どちらも QA リポジトリ（`aidev init <name> --template qa` で作った構成）に置く。

- `plan/strategy.md` はテスト戦略書の本体である。章立ては `references/strategy-outline.md` に従う。案件の規模が小さければ章を薄くしてよいが、対象外とリスク分析の章は省かない
- `plan/acceptance.md` は受け入れ条件の全件である。後続の Skill と検査が、AC の正本としてこのファイルを読む。1行に1件、`- AC-001: 観測できる結果（出どころ: 文書 節）` の形で、雛形の「一覧」の節に書く

AC の本文には、画面や出力で観測できる結果を書く。出どころには、要件定義書や設計書の名前と章番号を書く。出どころを示せない条件は AC にせず、作業者に確認する。すでにある AC-ID は、欠番が出ても振り直さない。テストケースや結果のファイルが ID で参照しているためである。

## 進め方

最初に案件プロファイルを読む。`knowledge/<product>/profile.md` を開き、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-strategy` で検査する。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう。プロファイルがなければ、雛形の `knowledge/profile.template.md` から作るよう作業者に頼む。足りない項目を推測で埋めない。プロファイルの本文にある観点や落とし穴は、リスク分析の材料にする。

次に、渡された文書とコードを読み、戦略を決めるのに足りない文脈だけを作業者に聞く。文書に答えがあることは聞かない。答えによって次の質問が変わるものは、一度にまとめず順に聞く。聞く内容の目安は次の4つである。

- 製品と業務：利用者、止まると困る業務の流れ、リリースの頻度、守るべき規制
- 今のテスト：レベルごとのテストの量、使っている仕組み、カバレッジ、CI の所要時間、不安定なテストの割合
- 課題と目標：直近のリリースで本番に漏れた不具合、関係者が考える「十分な品質」
- 体制と制約：開発者とテスト担当の人数、自動化の経験、予算、納期

文脈がそろったら、機能ごとに影響度と起こりやすさでリスクを評価し、優先順位、対象外、テストレベルの配分を骨子にまとめる。骨子を作業者に見せ、合意を得てから戦略書の全体を書く。全体を書いた後の作り直しは、骨子の段階での修正より手間がかかる。

既存の戦略書を見直す場合は、`plan/strategy.md` を読んで要点を作業者に示し、変える章を決めてから直す。改訂履歴に版、日付、変更内容を足す。

## 判断の基準

未確定の数値は「⚠ 要確認」と書く。金額、工数、期日、カバレッジの目標などを、もっともらしい値で埋めない。推測の値は確認済みの値と見分けがつかず、そのままリリース判定の根拠に使われてしまう。空欄は見落とされやすいが、印は目に留まる。急いでいるときほど仮の値を入れたくなるが、仮の値はほぼそのまま残る。

網羅よりリスクを優先する。工数はコードの量ではなく、不具合が起きたときの業務への影響に合わせて配分する。リスクの評価は影響度と起こりやすさをそれぞれ 1 から 5 で付け、その積で帯を決める。

テストレベルの配分を決める前に、今のテストの形を診断する。E2E が多く単体が少ない形は、フィードバックが遅く保守にも手間がかかる。目標の比率は、今の形からどう近づけるかとあわせて書く。

対象外を書く。何を確かめないかを決めておくと、範囲の広がりを防げ、後から漏れを指摘されたときの判断材料にもなる。対象外には理由を添える。

数値で表せる目標には、目標値と測る頻度を付ける。測れない目標は、戦略書に本当に必要かを作業者と確かめる。

すべてを自動化しようとしない。回帰の確認は自動化し、探索的なテストは手で行う。どれを手で行うかを戦略書に明記する。

個人名は書かず、「担当者A」のような役割の表記を使う。要件定義書などに要件 ID が振られていれば、それを引用する。この Skill が新たに振るのは AC-ID だけである。

文書の深さは案件と体制の規模に合わせる。少人数で短期の案件に、大規模な案件と同じ量の文書は要らない。

## 確認

書き終えたら、作業者に渡す前に次の点を確かめる。

- 対象外の節があり、それぞれに理由がある
- 未確定の数値が「⚠ 要確認」になっていて、推測の値が確定値のように書かれていない
- リスク分析の表から数点を選び、影響度と起こりやすさの積が正しい帯に入っているかを検算した
- テストレベルの目標比率の合計がおおむね 100% になっている
- 品質指標の表の各行に、目標値と測る頻度がある
- 本文で使う用語、ID、章番号が、すべて本文の中で定義されている
- 改訂履歴と役割分担の節がある
- `plan/acceptance.md` の各行が AC の形式に合い、出どころが書かれている

## よくある誤り

- 文書に書いてあることを作業者に聞き直す。作業者の時間を使い、文書を読んでいないという印象を与える
- 骨子の合意を取らずに全体を書き、方針の違いが最後に見つかる
- ツールの名前から戦略を始める。何を確かめるかを決めてから、それに合う仕組みを選ぶ
- カバレッジの目標を一律に 100% にする。80% を超えると効果が下がり、結合部分のように不具合が多い箇所への工数が減る。目標は機能のリスクに合わせて決める
- 他の案件の戦略書を流用し、その案件にしかない用語や前提が残る

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- `plan/strategy.md` に、対象外、リスク分析、テストレベルの方針、終了条件、品質ゲート、品質指標、役割分担、改訂履歴がある
- 未確定の数値がすべて「⚠ 要確認」で示されている
- `plan/acceptance.md` の各 AC に出どころがある
- 骨子と完成版について作業者の合意を得た。v1.0 として確定したら、次の工程に進む前に社内のレビューを受けるよう作業者に伝えた
