# OIDC でのセッションの取得

アプリが利用者を IdP の認可エンドポイントに送り、IdP で認証した後、認可コードを付けてアプリのリダイレクト URI に戻す方式（認可コードフロー）で読む。ログインの判定の基準とセッションの確認は SKILL.md にあり、ここでは OIDC に特有の流れと落とし穴を扱う。setup・設定・確認の関数の形は `references/form.md` と同じものを使う。

## 流れ

1. アプリのログインの入口（プロファイルの `login.entry_url`）を開くか、アプリのログインボタンを押す。認可エンドポイントの URL を自分で組み立てて開かない。`state` や `nonce`、PKCE の値はアプリが作り、戻ってきたときに照合するためで、組み立てた URL では照合に失敗する
2. IdP のホストへのリダイレクトを待ち、フォームに入力して送信する
3. IdP のホストから離れるのを待つ。リダイレクト URI（コールバック）を経て、アプリの画面に着くまで待つ
4. SKILL.md の4つの判定に当てはめ、成功なら保存して新しいコンテキストで確かめる

IdP の画面の段数、遅さ、MFA や同意の画面で止める判断は、`references/saml.md` の「IdP の画面」と同じである。

## トークンの置き場所

OIDC のアプリは、ログインの結果をどこに持つかで、storageState に入るものが変わる。

- サーバー側でコードをトークンに交換し、セッションの Cookie を発行するアプリ。フォーム認証と同じく、storageState の Cookie で再現できる
- ブラウザの JavaScript がトークンを受け取り、localStorage に置くアプリ。storageState には localStorage も入るので再現できる
- トークンを sessionStorage やメモリだけに置くアプリ。storageState には sessionStorage が入らず、メモリの値は保存できない。保存したファイルで開くとログインしていない状態になる

3つ目のアプリでは、SKILL.md のセッションの確認が失敗する。そのとき、sessionStorage の中身を `page.evaluate(() => JSON.stringify(sessionStorage))` で取り出して別のファイルに保存し、テストの開始時に `context.addInitScript` で戻す方法がある。このファイルもトークンを含むので、`automation/web/.auth/` に置き、storageState と同じく秘密情報として扱う。IndexedDB にトークンを置くアプリでは、`storageState({ path, indexedDB: true })` で保存できる（Playwright 1.51 以降）。メモリにしか持たないアプリは保存で再現できないので、テストごとにログインするかを作業者と決める。

アクセストークンの寿命は数分から1時間程度のことが多い。リフレッシュトークンで更新するアプリでも、更新の仕組みが IdP のドメインの Cookie に頼っていると、テストの途中で切れることがある。テストの直前に setup を流し、長い実行の途中で切れていないかを SKILL.md の期限切れの兆候で見る。

## IdP やコールバックで出るエラー

- `redirect_uri` が登録されていないというエラーが IdP の画面に出たら、その環境の URL が IdP のクライアントの設定に登録されていない。テストのコードでは直せないので、作業者に伝える
- コールバックで `state` の不一致や `invalid_grant` のエラーが出たら、入口を経ずに認可エンドポイントを開いた、古いタブや保存した URL から再開した、時間がかかりすぎてコードが期限切れになった、のどれかを疑う
- アプリのログイン画面やエラー画面に戻されたら、IdP の認証は通っている。アプリがトークンの検証（発行者、対象者、署名の鍵）やアカウントの連携に失敗している可能性があり、アプリのサーバーのログを見る

## 落とし穴

- 保存した storageState には IdP のドメインの Cookie も入る。次回は IdP がフォームを出さずに通すことがあるため、setup は空のコンテキストから始める。逆に、IdP にログイン済みのまま別のロールのログインを始めると、前のロールのまま戻ってくることがある。ロールごとに新しいコンテキストを使う
- 同意の画面は、初めてそのアプリにログインしたアカウントでだけ出ることが多い。テスト用のアカウントで同意を済ませるかどうかは作業者に確かめる。この Skill が同意のボタンを押さない
- `prompt=login` や `max_age` を付けるアプリでは、IdP にログイン済みでも毎回フォームが出る。待ち方を、フォームが出る場合と出ない場合の両方に対応させるより、空のコンテキストから始めて毎回フォームが出る前提にそろえるほうが単純である
