# SAML でのセッションの取得

アプリ（SP）が利用者を IdP に送り、IdP で認証した結果を SAML の応答としてアプリに POST で返す方式で読む。ログインの判定の基準とセッションの確認は SKILL.md にあり、ここでは SAML に特有の流れと落とし穴を扱う。setup・設定・確認の関数の形は `references/form.md` と同じものを使う。

## 流れ

1. アプリの SAML の開始 URL（プロファイルの `login.entry_url`）を開く。SP から始める流れ（SP-initiated）が基本である
2. IdP のホストへのリダイレクトを待つ。`page.waitForURL(url => url.hostname === idpHost)` のように、ホスト名で待つ
3. IdP のフォームにユーザー名とパスワードを入れて送信する
4. IdP のホストから離れるのを待つ。`page.waitForURL(url => url.hostname !== idpHost, { timeout })`。時間切れなら、その時点で「IdP で停止」と判定し、画面の本文のテキストを取る
5. アプリのオリジンのログイン画面以外のパスに着くことと、アプリのログイン画面かエラー画面の要素が出ることの早いほうを待つ。`references/form.md` の setup の例と同じ待ち方で、読み込みの完了（`waitForLoadState`）だけを待ってから URL を見る書き方にしない。中間のページや SPA の画面の切り替えの途中で判定し、成功を拒否と誤るためである。その後で SKILL.md の4つの判定に当てはめる
6. 成功なら `page.context().storageState({ path })` で保存し、新しいコンテキストでセッションを確かめる

IdP のホスト名は、開始 URL を開いてリダイレクトされた先から取るか、プロファイルの本文に書いてもらう。setup のコードに IdP の URL を決め打ちで書くと、IdP を替えた案件や環境で動かない。

## IdP の画面

IdP の画面は製品と設定によって違う。同じ IdP でも、本番と検証環境で画面の段数やセレクタが違うことがある。対象の環境で実際に画面を開いて確かめてからセレクタを書く。

- ユーザー名とパスワードが2段階に分かれる IdP がある。どちらの段も同じ表示名のボタン（「次へ」「Continue」など）で、ボタンの名前で段を見分けられないことがある。2段目の入力欄が現れるのを待ってから入力する
- IdP の画面は描画に数十秒かかることがある。setup のプロジェクトだけ `timeout` を長めにし（例 180 秒）、`retries` を 1〜2 にする。認証はすべてのテストの前提なので、IdP の一時的な遅さで全体を落とさないためである。ただし、資格情報の誤りを繰り返し試さないよう、リトライは判定が「着地点が不明」や時間切れのときに限るのが望ましい
- IdP で止まったときの診断は画面の本文のテキストで行う。スクリーンショットを撮るなら、パスワード欄を空にしてから撮る。setup のトレースと動画は `references/form.md` の設定のとおり切っておく。トレースには入力したパスワードと、IdP やアプリが返した Cookie が残る
- MFA、同意、パスワードの期限切れ、利用規約の画面に着いたら、そこで止めて作業者に判断を求める。テスト用のアカウントで MFA を無効にできるか、別の方法でセッションを用意するかは作業者と IdP の管理者が決める
- 保存した storageState には、アプリの Cookie だけでなく IdP のドメインの Cookie も入る。次回、IdP がフォームを出さずに通すことがあり、そのときは IdP の画面を待つ手順がタイムアウトになる。setup は空のコンテキストから始める

## アプリへ戻るところ

IdP は認証の後、自動で送信されるフォームでアプリの受け口（ACS）に SAML の応答を POST する。この間に IdP 側の中間ページが一瞬表示される。`networkidle` は長い接続を持つページでは終わらないことがあるため、アプリのオリジンへの `waitForURL` を基本にし、その後で着地点の要素を待つ。

着地点は RelayState（開始時に渡した戻り先）で決まる。開始 URL によっては、アプリのルート（`/`）や、意図しないページに着く。ルートに着いただけでは成功と判定せず、ログインが必要なページを開いて確かめる。

アプリのログイン画面やエラー画面に戻されたら、IdP の認証は通っている。次を疑い、アプリのサーバーのログを見る。

- アプリが IdP の証明書やメタデータを古いまま持っていて、署名の検証に失敗している
- 応答の有効期間（NotBefore、NotOnOrAfter）が、サーバーの時計のずれで外れている
- IdP のユーザーとアプリのアカウントの連携がない、または属性（メールアドレス、社員番号など）の対応付けが合わない
- 応答の宛先（Audience、Destination）が、その環境の URL と合わない

これらはテストのコードでは直せない。セレクタや待ち方を直し続けず、作業者に判定とログの所見を伝える。

## 経路と Cookie

SAML の受け口は、移行の途中で複数のアプリが同じパスを持つことがある。どのアプリが応答するかはリバースプロキシの転送の設定で決まり、それによって発行される Cookie（サーバーのセッション ID か、署名付きのトークンの Cookie か）が変わる。ログインが成功していても、期待した名前の Cookie がないことがある。成否は着地点と画面で判定し、保存した Cookie の名前とドメインを返答に書いて、後続の Skill がどの経路を前提にできるかを作業者が判断できるようにする。

## 落とし穴

- `baseURL` がアプリのサブパス（例 `https://host/app/`）のとき、SAML の開始 URL がホスト直下にあることがある。`page.goto('saml/start')` のように先頭の `/` を落とすと `baseURL` の下に解決され、開始 URL に届かない。開始 URL は絶対 URL か、先頭に `/` を付けたパスで開く。画面の遷移では逆に `baseURL` の下に解決させたいことが多く、書き方が逆になる点に注意する
- 検証環境は社内の認証局の証明書を使うことが多く、既定では証明書のエラーで開けない。検証環境に限り `ignoreHTTPSErrors: true` を設定する。証明書のエラーを「環境が落ちている」と誤診断しない
- IdP から始める流れ（IdP-initiated）しか許さない案件では、IdP のポータルからアプリを選ぶ手順になる。どちらの流れかはプロファイルの本文に書いてもらう
- 本番の IdP は、検証環境の IdP と画面も段数も違いうる。検証環境で動いた自動化が本番でもそのまま動くとは考えない
