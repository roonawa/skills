# 認証済みセッションの取得

## Overview

画面のテストも認可のテストも、テスト対象のロールでログインした状態から始まる。この Skill は、案件プロファイルに書かれたログイン方式でロールごとにログインし、Playwright の `storageState`（Cookie とオリジンごとのストレージ）をファイルに保存する。後続の Skill とテストは、そのファイルを読み込んでログイン済みの状態から始める。

ログインの自動化で難しいのは、入力欄を埋めることより、ログインできたかどうかの判定である。IdP の画面で止まったのか、IdP は通ったがアプリに拒否されたのかで、疑う場所がまったく違う。また、発行される Cookie は経路によって変わり、セッションには寿命がある。この Skill は、この判定と確認の基準を中心に扱う。

## When to Use

- 画面や API のテストを始める前に、ロールごとのログイン済みの状態を用意する
- 保存したセッションが切れた、または環境の変更でログインが通らなくなったので作り直す
- ログインのセットアップが失敗し、原因が資格情報か、IdP か、アプリの側かを切り分ける

使わない場面は次のとおり。

- 保存したセッションで既存画面の挙動を記録するときは aidev-qa-characterization を使う
- ロールと操作の可否、行レベルの所有者の検証は aidev-qa-authz-test を使う
- 新旧の環境の照合は aidev-qa-regression-compare を使う
- デスクトップアプリのネイティブのログイン画面や証明書方式のログインの操作は aidev-qa-desktop-gui を使う
- プロファイルの `login.method` が `none` なら、ログインがないのでこの Skill は要らない

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`environments`（環境名と URL）、`roles`（ロール名と、ユーザー名・パスワードを入れた環境変数の名前 `user_env`・`password_env`）、`login`（`method`、`entry_url`、証明書方式なら `certificate_thumbprint`）を使う。本文の到達手順と落とし穴も読む
- 環境変数に入った資格情報。作業者が自分の PC で設定する
- 作業者が指定する、対象の環境とロール。指定がなければ `roles` のすべてを対象にし、環境は作業者に確かめる

出力は次のとおり。

- `automation/web/.auth/<role>.json`。ロールごとの storageState である。同じロールで複数の環境のセッションを同時に持つときは、`automation/web/.auth/<environment>/<role>.json` のように環境名で分ける。セッションは発行したホストに結び付くためである
- ログインを行う setup のコード（例 `automation/web/tests/auth.setup.ts`）と、それを他のテストより先に動かす `automation/web/playwright.config.ts` の設定。`automation/web/` に package.json や設定がまだなければ作る
- 作業者への返答。ロールごとの判定（成功、IdP で停止、アプリで拒否、着地点が不明）、着地した URL のパス、保存した storageState に含まれる Cookie の名前とドメイン、セッションの確認の結果を書く。Cookie の値は書かない

`automation/web/.auth/` は QA リポジトリの雛形の `.gitignore` で除外されている。`.gitignore` にこの行がなければ、ファイルを作る前に足す。storageState は必ずコミットせず、証跡や報告にも添付しない。中の Cookie を使えば、そのロールとして誰でもアプリを操作できるためである。ファイルの場所は、相対パスではなく設定ファイルの位置から組み立てる（`references/form.md` の「ファイルの場所」）。相対パスにすると、QA リポジトリのルートから `-c automation/web` で流したときにルートの `.auth/` にでき、除外の対象から外れる。

setup のプロジェクトでは、Playwright のトレース、動画、スクリーンショットを切る（`use: { trace: 'off', video: 'off', screenshot: 'off' }`）。トレースは入力した値（パスワード）とログインの通信（POST の本文、Set-Cookie）を平文で記録し、動画とスクリーンショットは画面を記録する。QA リポジトリの全体の設定でトレースを有効にしていても、setup だけは上書きする。setup のトレースや動画を証跡にしない。

## 進め方

最初に案件プロファイルを読む。`knowledge/<product>/profile.md` を開き、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-login-session` で検査する。この Skill が使う項目は `product`、`environments`、`roles`、`login` である。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう。`entry_url` がない、対象の環境がどれか分からないなど、足りない項目は作業者に確かめ、推測で埋めない。

次に、対象のロールの `user_env` と `password_env` に書かれた環境変数が設定されているかを、名前だけで確かめる。未設定なら、その環境変数の名前を作業者に伝えて止める。値を表示したり、ファイルやログに書いたり、コマンドの引数に入れたりしない。テストのコードでも `process.env` から読み、値をコードや設定ファイルに書き写さない。

方式ごとの流れは参照資料に分けてある。`login.method` に合わせて1つを読む。

- `form`：`references/form.md`。アプリ自身のログインフォーム
- `saml`：`references/saml.md`。アプリから IdP へ移り、SAML の応答でアプリに戻る
- `oidc`：`references/oidc.md`。IdP の認可エンドポイントへ移り、コードを受け取ってアプリに戻る
- `certificate`：この文書の「証明書方式」の節

setup のコードを書いたら、ロールを1つだけ選んで流し、判定と確認が通ることを見てから全ロールに広げる。最初から全ロールで流すと、セレクタの誤りでも全ロールの失敗が並び、共有アカウントのロックアウトを招くことがある。

## ログイン結果の判定

送信の後、ログイン画面（SAML・OIDC では IdP）から離れることと、エラーの表示が出ることの早いほうを待ってから、着いた URL と画面で次の4つに分ける。読み込みの完了だけを待って URL を見ると、XHR で送る画面やリダイレクトの途中でまだログイン画面の URL のまま判定し、成功するはずのログインを拒否と誤る。どちらも起きずに時間切れになったら、その時点の画面で判定する。判定は setup のコードに書き込み、失敗したときのエラーメッセージに、どれに当たったかと次に疑う場所を書く。次に失敗した人が、同じ切り分けをやり直さずに済む。

| 判定 | 状態 | 疑う場所 |
|---|---|---|
| 成功 | 環境のオリジンに戻り、ログイン画面以外のページに着き、ログインが必要な要素（ログインユーザーの表示、ログアウトのリンクなど）が見える | なし。storageState を保存する |
| IdP で停止 | 最終の URL が IdP のホストのまま | 資格情報の誤り、MFA、同意画面、パスワードの期限切れ、アカウントのロック。テストのコードと資格情報の側 |
| アプリで拒否 | アプリのログイン画面かエラー画面に戻された | SAML・OIDC では IdP の認証は通っている。アプリ側の応答の処理、アカウントの連携、属性の対応付けを疑い、サーバーのログを見る。フォーム認証では資格情報かアカウントの状態 |
| 着地点が不明 | 上のどれでもない（空白のページ、想定外のパス、ルートだけで中身がない） | 中断して画面を作業者に見せる |

「IdP で停止」と「アプリで拒否」を取り違えると、直す場所を誤る。アプリで拒否されたのにセレクタを直し続けても、ログインは通らない。

想定外の画面（MFA、同意、パスワードの変更、利用規約）に着いたら、要素を推測して押し進めず、そこで止めて作業者に判断を求める。パスワードの変更を誤って確定させるなど、テスト用アカウントの状態を変えてしまうおそれがある。診断には、画面の本文のテキストを使う。スクリーンショットを撮るなら、パスワード欄が画面から消えた後か、欄を空にしてから撮る。

成否を特定の Cookie の名前の有無で判定しない。判定は着地点と画面で行う。

## 発行される Cookie は経路で変わる

同じログインの入口でも、リバースプロキシがその時点でどのアプリに転送しているか、移行のどの段階にあるかで、応答するアプリが変わり、発行される Cookie の名前や性質（セッション ID か、署名付きのトークンか）も変わる。そのため、次のように扱う。

- Cookie を名前で1つだけ取り出して受け渡さず、`page.context().storageState({ path })` でコンテキスト全体を保存する。Cookie が入れ替わっても、後続のテストは壊れない
- 保存したら、含まれる Cookie の名前とドメインを一覧にして返答に書く。前回と違えば、経路が変わった可能性を作業者に伝える。後続の Skill が特定の Cookie（API を直接呼ぶときのセッションの Cookie など）を前提にするなら、それがあるかをここで確かめておく
- アプリが CSRF トークンを画面の起動時に自分で取るなら、ブラウザで操作するテストでは別に取る必要はない。API を直接呼ぶテストで CSRF トークンが要る場合は、取り方を aidev-qa-authz-test 側で扱う

## セッションの確認と期限切れの検出

保存しただけでは、そのセッションが使えるかは分からない。ロールごとに、保存した storageState を読み込んだ新しいコンテキストで、ログインが必要なページ（プロファイルの到達手順にある一覧などのページ）を開き、ログイン画面へリダイレクトされずにそのページの要素が見えることを確かめる。この確認は setup とは別のテストか関数にしておき、後続のテストを流す前にも使えるようにする。

この確認がログインしていない状態を本当に検出できるかも、一度確かめる。空の storageState（または storageState を指定しないコンテキスト）で同じ確認を流し、ログイン画面へのリダイレクトとして失敗することを見る。失敗しなければ、確認に使ったページか判定の条件が誤っている。ログインの判定についても、可能なら誤ったパスワードで1回だけ流し、「成功」と判定されないことを確かめる。ロックアウトの規則がある IdP や共有のアカウントでは、作業者に確かめてから行う。

セッションには寿命があり、数時間で切れることもある。テストの実行や証跡の撮影の直前に setup を流し直す運用にし、前回の実行で作った `.auth` を使い回さない。期限切れのセッションで流すと、画面がログイン画面に落ちたまま進み、「操作が1件も起きなかった」「権限がない」という誤った観測が残る。後続のテストが次のどれかを示したら、まず期限切れを疑い、setup をやり直してから判断する。

- ログインが必要なページを開くとログイン画面にリダイレクトされる
- API が 401 を返す、またはログイン状態を問い合わせると匿名のユーザーが返る
- ログインユーザーの表示が消えている

`.auth` のファイルの更新日時は、いつ作ったセッションかを知る手がかりになる。古いファイルは消すか作り直す。

## ログインに失敗したとき

失敗が一度出ただけで、資格情報が古いと決めつけない。同じ資格情報で、時間を置くと通ることがある。次を順に確かめる。

- 以前は成功していたか。そのロールの `.auth` のファイルの更新日時を見る
- 同じ setup のコードで、他のロールは通るか。通れば、セレクタや手順の問題ではない
- 送信の後、画面に何が表示されているか。判定の前に、画面の本文のテキストとスクリーンショットを取る。期限切れやロック、MFA なら画面に出る。何も出ていなければ一時的な事象を疑う

失敗が続くときは、試行を繰り返さずに時間を置く。連続した失敗は IdP 側のロックアウトを招く。そのロールのケースは、`runs/<YYYYMMDD>-<run-id>/result.md` で実行不能とし、理由に「ログイン失敗（要再試行）」と判定の種類を書く。恒久的に実行できないと断定しない。

共有のテスト用アカウントのパスワードが期限切れになっていても、この Skill がパスワードを変更しない。共有のアカウントは他の人も使っている。作業者に伝え、そのロールの setup だけを環境変数のフラグなどで飛ばし、他のロールを巻き込んで落とさない。飛ばす理由、確かめた日付、復旧の方法をコードのコメントに書く。こうしたフラグは、アカウントが直っても外されずに残りやすい。日付が古ければ、フラグを外して一度試す。

## 証明書方式

`login.method` が `certificate` のとき、ログインは Windows の証明書ストアにあるクライアント証明書で行う。証明書は `login.certificate_thumbprint` の拇印で指定する。拇印は秘密情報ではないのでプロファイルに書いてよいが、証明書そのものや秘密鍵、PFX のパスワードはプロファイルにもリポジトリにも置かない。

この Skill が行うのは、証明書が作業者の PC にあり使える状態かの確認までである。PowerShell で `Get-ChildItem Cert:\CurrentUser\My`（端末全体の証明書なら `Cert:\LocalMachine\My`）を拇印で絞り込み、証明書があること、有効期限内であること、秘密鍵を持つこと（`HasPrivateKey`）を確かめる。見つからなければ、拇印の誤りか、証明書がまだ入っていないかを作業者に確かめる。

証明書の選択ダイアログやネイティブのログイン画面の操作は、デスクトップの GUI を扱う aidev-qa-desktop-gui に渡す。ブラウザで動く画面でも、OS の証明書選択ダイアログが出る場合はブラウザの外の操作になるため、同じく aidev-qa-desktop-gui で扱う。その場合、この Skill の setup はブラウザを画面付き（headed）で起動し、起動したブラウザのプロセスの ID を `test-results/` の下に書いてアプリのページに着くのを待つ。aidev-qa-desktop-gui はその PID のブラウザが出したダイアログだけを操作し、ダイアログが閉じた後のセッションの保存（`.auth/`）と確認はこの Skill が行う。

## よくある誤り

- 特定の Cookie の名前があるかどうかでログインの成否を決め、経路が変わったときに成功を失敗と誤判定する
- Cookie を名前で1つだけ取り出して渡し、移行の進捗で Cookie が入れ替わると後続が壊れる
- アプリのログイン画面に戻されたのを、セレクタの問題だと思って直し続ける
- IdP の想定外の画面で要素を推測して押し進め、アカウントの状態を変えてしまう
- 資格情報や Cookie の値をコード、ログ、証跡、返答に書く。storageState をコミットするか、報告に添付する
- 保存しただけで、そのセッションでログインが必要なページを開けるかを確かめない
- 前回の実行の `.auth` を使い回し、期限切れの結果を認可の不具合や「操作が起きなかった」と誤診断する
- 一度の失敗で資格情報が古いと断定し、繰り返し試してアカウントをロックさせる

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- 対象のロールごとに、ログイン結果を4つの判定のどれかに分け、成功したロールの storageState を `automation/web/.auth/` に保存した
- 成功したロールごとに、保存した storageState でログインが必要なページを開き、ログイン画面へリダイレクトされないことを確かめた
- 空の storageState で同じ確認が失敗することを確かめ、確認がログインしていない状態を検出できることを示した
- 返答に、ロールごとの判定、着地点のパス、Cookie の名前とドメイン、失敗したロールの次に疑う場所を書いた
- 資格情報と Cookie の値が、コミットされるファイル、ログ、証跡、返答のどこにも書かれていない
