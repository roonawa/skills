# テストケースの作成

## Overview

テストケースは、受け入れ条件（AC）を満たしているかを、誰が実行しても同じ判定になる形で確かめるための手順である。この Skill は、AC と設計書（コードしかない案件ではコードから推定した仕様）を読み、機能ごとのテストケースを `cases/<機能>.md` に書く。どの観点を重く見るか、推定した仕様が正しいかを決めるのは作業者で、この Skill は根拠を示して判断を助ける。

ケースの価値は、AC との対応が追えることと、期待結果が観測できることにある。AC に結び付かないケースは何を確かめたのか説明できず、AC に対応するケースがなければその条件は確かめられないまま残る。

## When to Use

- `plan/acceptance.md` と設計書がそろい、機能ごとのテストケースを作る
- 設計書がなく、実装コードだけを手がかりにテストケースを作る
- 既存の `cases/<機能>.md` に、仕様の変更や不具合の流出を受けてケースを足す

使わない場面は次のとおり。

- テスト戦略、テストレベルの配分、AC の全体を決めるときは aidev-qa-strategy を使う
- 作ったケースのレビューは aidev-qa-test-review を使う。同じセッションで自分の出力をレビューしない
- ケースの実行と結果の判定は aidev-qa-test-run を使う

## 入力と出力

入力は、QA リポジトリの案件プロファイル（`knowledge/<product>/profile.md`）、`plan/acceptance.md`、作業者が渡した設計書・要件定義書・テスト戦略書（`plan/strategy.md`）、コードしかない案件では対象のソースコードである。

出力は `cases/<機能>.md` で、機能ごとに1ファイルにまとめる。ケースの書き方は `references/case-format.md` に従う。TC-ID、対応する AC-ID、優先度、自動・手動の区別、手順、期待結果をケースごとに書く。aidev-qa-test-review がこの形式を読む。後の段階で追加する予定のケース実行の Skill と AC の対応表を作るコマンドも、同じ形式を読む前提で作る。コードしかない案件では、推定した仕様の表を `plan/inferred-spec.md` にも置く。

AC は `plan/acceptance.md` を正本とする。設計書から読み取った条件が `plan/acceptance.md` にないときは、作業者に確かめてから AC を足す。足すときは既存の行の形式（`- AC-001: 観測できる結果（出どころ: 文書 節）`）に合わせ、既存の AC-ID は振り直さない。

## 進め方

最初に案件プロファイルを読む。`knowledge/<product>/profile.md` を開き、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-test-design` で検査する。この Skill が使う項目は `product` だけである。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう。プロファイルがなければ、雛形の `knowledge/profile.template.md` から作るよう作業者に頼む。プロファイルの本文にある観点、落とし穴、テストデータの準備方法は、ケースの材料にする。

次に、入力の種類を見分ける。設計書や要件定義書があれば、それと `plan/acceptance.md` からケースを作る。コードしかなければ `references/code-only.md` を読み、推定した仕様を作業者に確かめてからケースに進む。両方がある改修案件では設計書を正とし、コードは影響範囲と既存の挙動を知るために読む。

AC と設計書を読んだら、ケースを書く前に、足りない前提だけを作業者に聞く。文書に答えがあることは聞かない。聞く内容の目安は、テストの範囲（単体・結合・E2E のどこまでか）、重点を置く機能、テスト環境と本番との差、テストデータの準備方法、外部システムをモックにするか本物を使うかである。テストデータに個人情報や本番のデータを使う予定があれば、扱いを先に決めてもらう。テスト環境に本番データを持ち込むかどうかは、後から変えにくいためである。

前提がそろったら、AC ごとに観点を洗い出し、ケースの草案を作る。草案ができた時点で、AC とケースの対応表、観点ごとの件数、「⚠ 要確認」の一覧を作業者に見せる。作業者がここで人にレビューを頼むこともあるので、確認が取れるまで清書に進まない。全体を清書した後で観点の抜けが見つかると、TC-ID の採番や手順の書き直しが広がる。

清書したら、`references/case-format.md` の形式に合っているかを確かめ、どのケースにも対応しない AC がないかを数える。対応表を作るコマンドはまだないため、今は `plan/acceptance.md` の AC-ID とケースの AC 行を手で突き合わせて数える。対応のない AC があれば、ケースを足すか、対象外にする理由を作業者と決める。対象外にした AC は、その理由とともに作業者に報告する。

最後に、別のセッションで aidev-qa-test-review を使ってレビューするよう作業者に伝える。作ったセッションは自分の判断の前提を共有しているため、同じ漏れを見落としやすい。

## 判断の基準

期待結果には、画面の表示、ダイアログの文言、ファイルの内容、ログ、データベースの値など、実行した人が観測できる結果を書く。「正しく動作する」「エラーになる」のような書き方では、実行する人によって判定が分かれる。どのメッセージが、どこに出るかまで書く。

観点は AC ごとに次の順で考え、当てはまらないものは飛ばしてよい。正常系、異常系、境界値（境界の前後と境界そのもの）、0 件と上限、必須と文字数の範囲、権限（ロールごとの可否と、他人のデータを URL や ID の直接指定で開く行レベルの所有者の検証）、排他と二重送信、エラー処理（例外が呼び出し元や利用者に伝わるか）、ダイアログとキャンセル。画面にボタンが出ないことだけを確かめても、権限の検証にはならない。直接のリクエストで拒否されることを別のケースにする。

優先度は、`plan/strategy.md` のリスク評価があればそれに従う。なければ作業者に確かめ、確かめられないものは「中」にして「⚠ 要確認」を付ける。推測で「高」や「低」にしない。

実行の区別は、ケースを繰り返し実行するかと、結果を機械で判定できるかで決める。回帰で何度も流すケースや、権限のように見落としが事故につながるケースは自動にする。見た目の確認、印刷、外部の機器が必要なケースは手動にし、手動で確かめる理由を手順に書く。

1つのケースでは1つのことを確かめる。複数の AC に関わるケースは AC を並べて書いてよいが、1つのケースで判定が複数に分かれるなら分ける。複数の機能をまたぐ業務の流れは、機能ごとのファイルと分け、`cases/scenario.md` のような業務シナリオ用のファイルにまとめる。性能や負荷は観点として書くにとどめ、詳しい手順は別の計画に任せる。

TC-ID は `TC-<機能>-001` の形で、機能ごとに連番を振る。機能名は英小文字とハイフンの短い名前にすると、ファイル名と ID にそのまま使える。一度振った TC-ID は、ケースを消して欠番が出ても振り直さない。実行結果や Issue が ID で参照しているためである。

数値、件数、期日が文書から裏付けられないときは「⚠ 要確認」と書き、もっともらしい値で埋めない。個人名は書かず、「担当者A」のような役割の表記を使う。テストデータにパスワードやトークンの値を書かない。必要なときは、プロファイルの `roles` にある secrets のキー名で参照する。

## よくある誤り

- 期待結果に、実装を動かして得た値をそのまま書く。実装の不具合がそのまま正解として残る
- AC を持たないケースを書く。何を確かめたのかが追えず、AC との対応表にも出ない
- 画面の操作だけで権限を確かめ、URL や API を直接呼ぶケースを作らない
- 草案を作業者に見せずに全体を清書し、観点の抜けが最後に見つかる
- 作ったセッションのまま自分でレビューし、問題なしと報告する
- 他の案件のケースを流用し、その案件にしかない画面名やロール名が残る

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- `cases/<機能>.md` の各ケースが `references/case-format.md` の形式に合い、すべてのケースに AC-ID がある
- どのケースにも対応しない AC がないか、残る AC とその理由を作業者に報告した
- コードしかない案件では、推定した仕様を作業者が確かめてからケースを書いた
- 草案の段階で作業者の確認を得た
- 別のセッションで aidev-qa-test-review を使うよう作業者に伝えた
