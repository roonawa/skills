# コードしかない案件

設計書がなく、実装のソースコードだけが手がかりの案件で読む。

## 実装を正としない

コードは「今どう動いているか」を教えてくれるが、「どう動くべきか」は保証しない。実装を動かして得た値を期待結果に書くと、実装の不具合が正解として固定され、テストでは見つからなくなる。この姿勢がこの場面での作業の中心になる。

期待結果には、実装本体以外の根拠から推定した「あるべき値」を書く。根拠になるのは、関数や変数の名前、入力チェック、データベースの制約（NOT NULL、CHECK、外部キー）、型やスキーマの定義、同じ種類の処理をする別の機能、既存のテスト、エラーメッセージ、コメントや TODO、README やコミットメッセージである。既存のテストも実装と同じく誤っている可能性があるので、1つの根拠だけで決めない。

推定したあるべき値と実装の挙動が食い違ったら、期待結果を実装に合わせて書き換えない。期待結果には推定した値を残し、ケースの備考に「実装疑義: 実装は〜になっている」と書いて作業者に報告する。この Skill はコードを直さない。

推定に自信が持てない箇所は、無理に断定せず「⚠ 要確認」として残す。仕様が分からないことを理由にケースの作成を止める必要はない。逆に、要確認も実装疑義も1件もない結果は、実装をそのまま正としている疑いが強い。

## 推定仕様を作る

ケースを書く前に、対象のコードと周辺を読み、推定した仕様を `plan/inferred-spec.md` に表で書く。対象のファイルだけで判断せず、入力チェックの層、データベースの定義、同種の機能、既存のテストまで読む。

```markdown
| RS-ID | 対象 | 推定した仕様 | 根拠 | 確信度 | 実装との差異 |
|---|---|---|---|---|---|
| RS-001 | discount.ts の calculateDiscount | 割引の上限は 30% | コメント「上限は 30%」、同種の機能の上限 | 中 | 実装疑義: 実装は 50% で上限をかけている |
```

確信度は次の基準で付ける。

- 高: 名前、入力チェック、データベースの制約、同種の機能、既存のテストのうち複数の根拠が一致している
- 中: 具体的な根拠が1つある（コメント、エラーメッセージ、データベースの制約など）
- 低: 名前や類推しか根拠がない、または根拠どうしが食い違う

1つの RS-ID に複数の疑いがあるとき（値の食い違いに加え、その分岐に届く入力がないなど）は、差異の欄に並べて書く。一つにまとめない。RS-ID は一度振ったら振り直さない。

## 作業者に確かめる

推定仕様の表ができたら、ケースを書く前に作業者に見せる。確信度が低いものと、実装との差異があるものは、業務として正しい仕様を作業者に聞く。答えによって次の質問が変わるので、1件ずつ聞く。作業者が答えられないものは「⚠ 要確認」のまま進めてよいが、実装した技術者や業務の担当者に確かめるべき項目として一覧にして渡す。

作業者が確かめた推定仕様は、`plan/acceptance.md` に AC として書く。出どころには `plan/inferred-spec.md` の RS-ID を書く（例：`- AC-031: 割引額は購入金額の 30% を超えない（出どころ: 推定仕様 RS-001）`）。確かめていない推定仕様は AC にしない。

## 疑う観点

AC ごとの観点（SKILL.md の判断の基準）に加えて、次の点を疑ってケースにする。

- 境界の向き：`>=` と `>` の向きが業務の規則と合っているか。境界の前後と境界そのものを確かめる
- 型と特殊な値：null、空文字、0、負の数、極端に大きい値、想定外の型
- 例外の握りつぶし：catch でログを出すだけで処理を続け、利用者や呼び出し元に失敗が伝わらないことがないか
- 層ごとの食い違い：画面、API、データベースで許す範囲が違わないか（画面では弾くが、API を直接呼ぶと通るなど）
- 同種の機能との食い違い：同じ入力で、別の画面や API と結果が違わないか
- 名前と挙動の食い違い：validate という名前なのに例外を出さず既定値を返す、などがないか
- コメントや TODO との食い違い：コメントが示す本来の仕様と実装が違わないか
