# テストケースの形式

`cases/<機能>.md` は次の形で書く。この形式は QA リポジトリの `cases/README.md` と同じで、aidev-qa-test-review が読む。後の段階で追加する予定のケース実行の Skill と AC の対応表を作るコマンドも、この形式を読む前提で作る。見出しと、AC・優先度・実行の3行の書き方を変えると、後続の検査がケースを読めなくなる。

```markdown
# 注文

対象の設計書: 基本設計書 4.2、詳細設計書 3.1

### TC-order-001 数量を入れて注文すると注文履歴に出る
- AC: AC-021
- 優先度: 高
- 実行: 自動
手順
1. 購入者のロールでログインする
2. 商品の詳細画面で数量に 1 を入れ、注文を押す
期待結果
- 注文履歴の画面に移り、注文した商品が先頭の行に出る
- 画面上部に「注文を受け付けました」と表示される

### TC-order-002 数量が上限を 1 超えると注文できない
- AC: AC-022
- 優先度: 中
- 実行: 自動
手順
1. 商品の詳細画面で数量に 100 を入れ、注文を押す
期待結果
- 注文されず、数量の欄の下に「数量は 99 以下にしてください」と表示される
備考
- ⚠ 要確認: 文言は設計書に記載がない。現行の画面の文言を仮に置いた
```

各項目の書き方は次のとおり。

- 見出しは `### TC-<機能>-<3桁の連番> <ケース名>`。ケース名には、操作と確かめる結果を短く書く
- `- AC:` には、対応する AC-ID をカンマ区切りで書く。AC-ID は `plan/acceptance.md` にあるものだけを使う
- `- 優先度:` は 高、中、低 のどれか
- `- 実行:` は 自動 か 手動。手動にした理由は手順の中に書く
- 手順は番号付きで、前提（ロール、データの状態）から書く。テスト用アカウントのパスワードは書かず、プロファイルの secrets のキー名で示す
- 期待結果は観測できる結果を箇条書きで書く。1つのケースで確かめることは1つにする
- 備考は省いてよい。書くときはケースの最後、期待結果の後に置く。後続の検査は、期待結果を「備考」の行か次の見出しまでとして読む。「⚠ 要確認」と、コードしかない案件の「実装疑義」は備考に書き、期待結果に混ぜない

ファイルの先頭には、機能名の見出しと、「対象の設計書:」の行を書く。この行には、ケースのもとにした設計書の名前と節（コードしかない案件では `plan/inferred-spec.md` の RS-ID）を書く。
