# 原因の特定と再現手順

## Overview

不具合の症状は、見た人の言葉で書かれている。画面の名前は正式名称と違い、対象データは「あの申込」のように曖昧で、条件は「ときどき」で済まされていることが多い。この Skill は、その症状から該当するコードを自分で探し、再現の条件のもとで処理が実際にどこを通るかを読んでたどり、原因を特定する。そして、テストの担当者や開発者が手元で同じ症状を出せる再現手順にまとめる。

原因の特定で一番の事故は、もっともらしい推測を事実として書くことである。推測の原因で修正が行われると、本当の原因が残ったまま「直った」ことになる。そこで、原因には確度（確定、有力、候補）を付け、確度ごとに要る根拠を決めておく。根拠が足りないところは足りないと書き、症状だけでは1つに絞れなければ、何が分かれば絞れるかを決めて、顧客や報告者に聞く文面を作る。

修正のコードを書くこと、修正の後の確認、Issue の起票はこの Skill の範囲外である。

## When to Use

- 顧客や利用者から、画面名、対象データ、再現の条件だけの不具合の報告が来た
- aidev-qa-test-run の NG の原因を、起票の前か後に調べる。起票済みの Issue の原因を調べる
- 報告された症状が、手元のテスト用の環境で再現するかを確かめ、再現手順を書く

使わない場面は次のとおり。

- NG のケースから Gitea に Issue を起票するときは aidev-qa-bug-ticket を使う。この Skill は Issue を作らない
- 「直した」という報告を受けて修正を確かめるときは aidev-qa-fix-verify を使う。修正のコミットがすでにあるなら、そちらの出番である
- ケースを流して結果を runs/ に記録するときは aidev-qa-test-run を使う
- 旧版と新版の差異を分けるときは aidev-qa-regression-compare を使う

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`environments`（再現を試してよい環境）、`login`、`test_commands` と、本文の到達手順、テストデータの準備方法、落とし穴を使う
- 症状。画面名（メニュー名、画面のタイトル、URL の一部）、対象データ（どの記録、どの条件のデータか）、再現の条件（何をすると、いつ起きるか）。NG から始めるときは、result.md の TC の行と「NG の詳細」がこれに当たる。Issue があれば、その番号と本文（作業者から受け取る。Gitea の API は呼ばない）
- 症状が出た環境と版。分からなければ作業者に確かめる。コードは、症状が出た版のものを読む
- 製品のリポジトリの場所。`cases/*.md`、`plan/acceptance.md`、`automation/` の既存のテストも手がかりに使う

出力は次のとおり。

- QA リポジトリの `reports/cause-<ID>.md`。ID は、Issue があれば Issue の番号（`#12` なら `reports/cause-12.md`）、なければ TC-ID（`reports/cause-TC-order-002.md`）、どちらもなければ日付と短い名前（`reports/cause-20261118-csv-empty.md`）にする。同じ不具合を調べ直したら同じファイルを更新し、調べた日付を書き足す。形式は下の「報告書の形式」にある
- 報告書の末尾の「Issue に貼る節」。作業者が確かめて、Issue に手で貼る。この Skill は Gitea に送らない
- 原因を絞れなかったときの、顧客に送る質問の文面（報告書の中に書く）。送るのは作業者である
- 作業者への返答。原因と確度を先頭に書く

runs/ の result.md は書き換えない。原因は結果ではなく、結果の解釈だからである。再現を試したときの証跡と使い捨てのテストは `.qa-scratch/cause-<ID>/` に置き、runs/ には置かない。

## 進め方

### 1. プロファイルと症状を読む

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-cause-repro` で検査する。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

症状を、画面名、対象データ、再現の条件、実際に起きたこと、期待していたことに分けて書き出す。症状に書かれていないことは空欄のままにし、ありそうな値で埋めない。空欄は後で、コードを読めば分かるものと、聞かないと分からないものに分ける。

### 2. 症状から該当するコードを探す

画面名、対象データ、再現の条件のそれぞれから、検索の手がかりを抜き出す。

- 画面名から、画面のタイトルの文字列、メニューの定義、ルーティングの定義、コンポーネントやクラスの名前
- 対象データから、テーブル名、カラム名、区分の値、状態の値
- 再現の条件から、ボタンや処理の名前、分岐に関わりそうな値（0件、空、上限、日付の前後、権限）

製品のリポジトリを `grep -rn` で検索し、`git log --all -i --grep=<画面名> --oneline` で関連する過去の変更も探す。ヒットしなければ表記の揺れ（正式名称と略称、日本語と英語、全角と半角）を疑って何度か試す。プロファイルの到達手順や `cases/*.md` の手順に画面の経路が書かれていれば、それも手がかりにする。それでも該当するコードを特定できなければ、画面名の情報が足りないとして 6 に進む。

### 3. 再現の条件のもとで処理をたどる

特定した画面や機能を、画面（表示と入力の検査）、API やコントローラ（受け渡し）、ロジック（計算と分岐）、データアクセス（SQL と保存）の順に、ファイルを開いて読む。

- 再現の条件に出てくる値を、実際にコードの上でたどり、どの分岐、どの条件式に入るかを一行ずつ確かめる。「この場合だけ起きる」という条件は、その分岐がコードにあることを確かめる
- 似た画面や処理が複数あれば、対象データと再現の条件に合うほうを選ぶ。両方が残るなら両方を読む
- 同じ関数やテーブルを触った過去の変更は `git log -p -- <path>` で経緯を読む。症状が出始めた時期が分かっていれば、その前後の変更を優先して読む
- 症状が出た版とリポジトリの今の版が違えば、症状が出た版のコードを `git show <版>:<path>` で読む。今の版を読んで、すでに直った箇所や後から入った箇所を原因にしない

### 4. 仮説を根拠で裏付ける

コードを読んで「それらしい」で止めず、手で確かめられるものは確かめる。

| 仮説の種類 | 確かめ方 |
|---|---|
| ある条件で例外やエラーになる | 対象データが本当にその条件を満たすかを、DDL、マイグレーション、ログ、作業者から得た値で確かめる |
| 表示や計算の値が違う | 対象データの値で手計算し、コードの計算と突き合わせる |
| ある値のときだけ分岐が変わる | その分岐の条件を満たすデータと満たさないデータを作り、関数や SQL に通して結果を比べる |
| ある画面では起きず、別の画面では起きる | 2つの実装を並べて違いを書き出す |
| ある時期から起きるようになった | その時期の前後のコミットを読み、症状の条件に関わる変更を探す |

SQL を確かめるときは、共有の DB や本番の DB には流さない。名前とポートを既存のものと分けた使い捨てのコンテナに、対象の SQL が参照するテーブルだけの最小のスキーマを実際の DDL から作り、合成データで流す。終わったらそのコンテナだけを消す。

### 5. 再現を試し、確度を決める

アプリを動かして再現を試すのは、作業者の PC かプロファイルの `environments` にあるテスト用の環境だけにする。本番の環境と、`purpose` から本番かどうか判断できない環境では試さない。症状が本番で出たものでも、再現はテスト用の環境で行う。本番で操作すると、顧客の記録を変え、実在の個人情報が証跡に写るからである。

- データを作る、変える、消す操作を伴うときは、使う環境、作る記録、後始末の方法を作業者に示して承認を得てから行う。作る記録には `QA-cause-<ID>-` の接頭辞を付け、後始末はその記録だけにする。データの状態と、アプリを再起動したときの扱いは、aidev-qa-test-run の「データの状態と流し直し」に従う。ログインの方式が `none` でなければ、aidev-qa-login-session で作ったセッションを使う
- 再現の条件を満たすデータで症状が出るかに加えて、条件を満たさないデータ（条件の境の1つ手前、空でない値、権限のあるロール）では症状が出ないかも見る。両方がそろって初めて、その条件が原因だと言える
- 画面より関数や SQL で確かめるほうが確かな原因（計算の誤り、境界の判定）は、使い捨てのテストを `.qa-scratch/cause-<ID>/` に書いて流す。製品のリポジトリにテストを足すのは、置き場所を作業者に確かめてから行う。製品のコードは変えない
- 試した結果は、成功しても失敗しても、出力やメッセージを写して報告書に書く。写す前に、秘密情報（トークン、Cookie、パスワード、セッションの ID）と個人の値を `<masked>` に置き換える。それ以外は書き換えない

原因の確度は、次の基準で決める。基準に届かなければ、1つ下の確度にする。

| 確度 | 要る根拠 |
|---|---|
| 確定 | 再現の条件を満たすデータで、作業者の PC かテスト用の環境で症状と同じ食い違いが出た。または、原因の箇所を通るテストが症状と同じ理由で失敗した。どちらの場合も、条件を満たさないデータでは症状が出ないことを確かめ、食い違いが特定した分岐から出ていることをコードの経路で示した。再現した版（ビルドかコミット）は症状が出た版と同じで、その版を報告書に書いた。版が違うときは、原因の経路のコードが2つの版で同じであることを差分で示した場合だけ確定にし、示せなければ有力にとどめる |
| 有力 | コードの経路を一行ずつたどり、症状と合う分岐を特定した。対象データがその分岐の条件を満たすことを、DDL、ログ、作業者から得た値で確かめた。ほかの候補は根拠を付けて外した。ただし、実際に動かして再現してはいない |
| 候補 | コードの上で症状を起こしうる箇所だが、対象データが条件を満たすかを確かめていない、またはほかの候補を外せていない |

確定は、実際に動かして見たことにだけ付ける。コードを読んだだけの原因は、どれほど確かに見えても有力までにする。

### 6. 1つに絞れたかを判断する

確定か有力の原因が1つだけで、ほかの候補を根拠を付けて外せたときに、絞れたとする。次のどれかに当たれば、絞れていない。

- 候補が2つ以上あり、症状の情報ではどれか決められない
- 該当しそうなコードが複数の画面や版にあり、どれが対象か画面名だけでは決められない
- コードは正しく見えるが、症状の記述が曖昧で、再現の条件を満たす操作を具体的に書けない
- 対象データの実際の値（区分、件数、日付）が分からず、境界の問題かどうか判断できない

絞れたら 7 に、絞れなければ 8 に進む。絞れなかったときも、ここまでに確かめたことと、外せた候補は報告書に残す。

### 7. 再現手順を書く

テストの担当者や開発者が、テスト用の環境でそのまま追えるように書く。

- 前提：環境（プロファイルの環境名）、ロール（アカウントは環境変数の名前で示し、パスワードを書かない）、必要なデータと、それを既存のデータで用意するか新しく作るか。作るなら作り方（画面の操作、テストデータの準備方法、SQL）を書く
- 操作：どの画面から、どのメニューとボタンを、どの順に操作し、何を入力するか
- 期待される結果と実際に起きる結果を対で書く。実際に起きる結果は、症状の記述と合っていることを確かめる
- 確定のときは、試したときの出力を、秘密情報と個人の値を伏せて添える。有力のときは「コードから組み立てた手順で、まだ流していない」と書く

コードの分岐の条件を満たすと確かめた手順だけを書く。「たぶんこれで起きる」という手順を混ぜない。

### 8. 追加の情報を頼む文面を書く

症状だけでは1つに絞れないときは、何が分かれば絞れるかを決め、それを聞く質問を作る。質問を受け取るのは IT に詳しくない人であることが多いので、言い回し、1問ずつの組み立て、回答で何が変わるか、聞いてよい個人情報の範囲は `references/customer-questions.md` に従う。質問は報告書の中に書き、作業者が確かめて送る。

### 9. 報告書を書き、報告する

報告書を下の形式で書き、作業者に返す。返答の先頭に、原因（確度付き）か、絞れなかったことと理由を書く。続けて、該当するコードの場所、再現手順か質問、確かめられなかったことを書く。

まだ Issue がなく、原因が確定か有力で、それが NG の TC と結び付いていれば、aidev-qa-bug-ticket での起票を作業者に提案する。Issue があれば、「Issue に貼る節」を貼るよう伝える。どちらの場合も、この Skill は Gitea に送らない。

## 報告書の形式

`reports/cause-<ID>.md` は次の形にする。

```markdown
# 原因の調査 <ID>

- 調べた日: 2026-11-18
- 症状の出どころ: Issue #12 ／ runs/20261118-new-cases の TC-order-002 ／ 顧客からの報告（受け取った日）
- 症状が出た環境と版: <環境名>、<版>
- 読んだコードの版: <コミット>
- 再現を試した環境と版: <環境名>、<ビルドかコミット>（試していなければ「試していない」）

## 症状
画面名、対象データ、再現の条件、実際に起きたこと、期待していたこと。受け取った記述のまま書き、分からない項目は「不明」とする。

## 原因
確度（確定・有力・候補）と、その根拠。原因の箇所（ファイルと行、関数）を人の言葉で説明する。候補が複数あるときは候補ごとに書き、外した候補には外した理由を書く。

## 確かめたこと
読んだファイル、検索した範囲、流した SQL やテスト、試した環境とデータの条件、その結果（秘密情報と個人の値を伏せた出力）。

## 再現手順
（絞れたとき）前提、操作、期待される結果と実際に起きる結果。

## 追加で知りたいこと
（絞れなかったとき）顧客に送る質問の文面だけ。

## 質問の意図
（絞れなかったとき、内部用）質問ごとに、答えによって候補がどう変わるか。顧客には送らない。

## 確かめられなかったこと
本番のデータの値を見ていない、該当するデータがテスト用の環境になかった、など。

## Issue に貼る節
作業者が Issue に貼るための、原因と確度、再現手順の要約。
```

報告書はリポジトリの履歴に、「Issue に貼る節」は Issue に残り、作業者以外も読む。資格情報、Cookie、トークン、セッションの ID を書かない。個人情報は値を写さず、性質で書く（「氏名の欄が空の記録」「生年月日が2月29日の記録」）。顧客から受け取った回答に個人情報が含まれていても、同じように性質だけを書く。実行の出力やエラーの文言は、秘密情報と個人の値を `<masked>` に置き換えてから写し、それ以外は書き換えない。

「Issue に貼る節」は、作業者が Gitea に手で貼るので、aidev-qa-bug-ticket の起票（`aidev qa issue create`）と同じ守りを本文の側で行う。Gitea は `@名前` を利用者への言及にして通知し、`#12`、`!12`、`owner/repo#12` を他の Issue やプルリクエストへの参照にし、HTML と画像を表示する。コードの抜き出し（`@Override` のような注釈を含む）、コマンドの出力、エラーの文言、ファイルのパスで言及や参照が起きないように、次のように書く。

- コードの抜き出し、出力、エラーの文言、ファイルのパスは、全部をコードブロックの中に入れる。囲みのバッククォートは、中にあるバッククォートの最も長い連続より長くする（最低3つ）
- コードブロックの外には、`@名前`、この Issue 自身の番号以外の `#番号` や `!番号`、HTML のタグ、画像、他の Issue やプルリクエストへの URL を書かない。関連する Issue に触れるときは、番号を書かずに作業者に伝える

貼る前に、作業者に本文を読んで確かめてもらう。

## よくある誤り

- コードを読んだだけの原因を確定と書く。条件を満たさないデータで症状が出ないことを見ずに確定とする
- 候補が2つ残っているのに、ありそうなほうを原因として書く
- 症状の空欄を、ありそうな値で埋めて調べ始める
- 症状が出た版ではなく、リポジトリの今の版のコードを読む
- 本番の環境で再現を試す。共有の DB に確かめ用の SQL を流す
- 確かめていない再現手順を、確かめた手順と同じ書き方で書く
- 顧客への質問に専門用語を使う。1つの質問で複数のことを聞く。必要以上の個人情報を求める
- 原因を書くついでに製品のコードを直す。runs/ の result.md に原因を書き込む
- Issue に自分で本文を送る、コメントを書く
- 「Issue に貼る節」で、コードやエラーの文言をコードブロックの外に書き、`@Override` が言及に、`#3` が参照になる
- 症状と違う版で再現したのに、原因の経路が同じことを示さずに確定と書く

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- 症状が出た版のコードで、再現の条件のもとでの処理の経路を読んでたどった
- 原因に確度（確定・有力・候補）を付け、その確度に要る根拠を報告書に書いた。確定は、テスト用の環境か作業者の PC で動かして確かめたものだけに付けた
- 絞れたときは、人がそのまま追える再現手順を書いた。絞れなかったときは、`references/customer-questions.md` に従った質問を書いた

- 確定の原因には、再現した版を書き、症状が出た版と同じか、原因の経路が同じことを示した
