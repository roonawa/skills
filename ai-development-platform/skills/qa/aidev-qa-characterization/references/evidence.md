# 証跡の撮り方と完全性の確認

特性テストを流して証跡を残すとき、撮った証跡を確かめるとき、完全性を数えるときに読む。

## 保存先と名前

証跡は、実行ごとの `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/` に、ケースごとのディレクトリで保存する。1回の作業で複数の画面を流しても、run は1つにまとめ、画面の区別はケースの TC-ID で行う。画面ごとに run を分けると、完全性の確認が分断される。テストは、環境変数 `QA_RUN_DIR`（`runs/<YYYYMMDD>-<run-id>` のパス）が指すディレクトリに証跡を書く。テストを流す前に設定する。

`runs/` に残すのは、最終の結果となった実行の証跡だけである。テストのコードを直しながら流す途中の実行や、失敗の診断のための実行は、`QA_RUN_DIR` を `.qa-scratch/` の下などの Git に入らない場所に向けて流す。`test-results/` の下には向けない。Playwright が次の実行で消す。最終の実行で流し直すときは、新しい run-id の空のディレクトリに全ケースを流し、前の run のディレクトリは消す（残したいなら `.qa-scratch/` に移す）。同じ run-id を使い回すと前の証跡が黙って消え、一部のケースだけを流し直すとデータの状態の違う証跡が1つの run に混ざる（aidev-qa-test-run の「データの状態と流し直し」）。古い実行の証跡と混ざると、どれが最終の結果か分からなくなり、`lfs` の案件では不要な画像がリポジトリの履歴に残る。result.md が参照するのは最終の run の証跡だけにする。最終の実行でアプリの異常が見えたケース（NG）の証跡は、それが最終の結果なので残す。

プロファイルの `evidence.method` に従って置き場所を決める。

- `lfs`：QA リポジトリの `runs/` に置き、Git LFS でコミットする。個人情報が映る画面では選ばない
- `local`、`external`：証跡はリポジトリの外（作業者の PC か社内のストレージ）に、同じ構成（`<保存先>/runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/`）で置く。result.md の証跡の列には保存先のパスだけを書き、証跡そのものはリポジトリに入れない

ケースのディレクトリの中は、checkpoint の名前で並べる。

```text
runs/20261118-char-loans/evidence/TC-loans-char-001/
  01-initial.png          画面のスクリーンショット
  01-initial.values.json  画面に出た値を構造化したもの
  01-initial.API-01.json  API の応答（状態コードと本文）
  calls.json              送られた API の記録（時刻、パス、操作名、状態、エラーの件数）
  result.json             ケースの状態と checkpoint の時刻
TC-loans-char-020/
  loans.csv               帳票のファイル
```

checkpoint の名前は、環境が変わっても同じにする。aidev-qa-regression-compare が、TC-ID と checkpoint の名前で旧版と新版を突き合わせる。環境の区別は run（とその result.md の冒頭の環境名）で行い、TC-ID に環境の接頭辞を付けない。

## 撮る前に確かめること

- 撮影の設定を実行の前に読む。テストのコードに明示的な撮影の呼び出しがあるか、共通の撮影の関数が本当にこの資料の決まりを実装しているかを、関数の中身を開いて確かめる。「共通の関数があるから大丈夫」と仮定しない
- 対象の画面にいることをアサートしてから撮る（`playwright.md` の「対象の画面にいることを確かめる」）。IdP、ログイン画面、エラー画面を撮って成功にしない
- checkpoint は「撮影と値の保存」を先に、「判定のアサート」を後に書く。判定を先にすると、失敗したときの画面が残らない

## 撮り方

- ダイアログやオーバーレイ（`position: fixed` の要素）が開いている間は、`fullPage` を使わず、今のビューポートのまま撮る。全体を引き伸ばす撮影では、固定の要素が元の1画面分の帯にしか描かれず、ダイアログが半透明に見えるような実機と違う画像になる
- ダイアログの中身を全部写すために、ビューポートを広げたり、`overflow`、`position`、`transform` などの CSS を書き換えたりしない。レイアウトが変わり、実機と違う画面を証跡にすることになる。スクロールで隠れた部分があっても、それが利用者の見る画面である。中身の値は構造化した表示値で残す
- アニメーションを止める CSS を入れるなら、遷移の直後ではなく撮影の直前に入れ、失敗しても撮影は続ける。遷移の途中に評価すると、実行のコンテキストが失われて落ちる
- ダイアログの開閉の途中で撮らない。表示が落ち着く条件（ダイアログの表示、アニメーションの終わり）を待ってから撮る
- テストのコードの不具合で失敗した実行の証跡は、直して流し直す前に、診断用として Git に入らない場所（例 `.qa-scratch/failed-<時刻>/`）に移す。`runs/` の下に置かない。完全性を数えるスクリプトが、ケースのディレクトリと取り違える

## 撮った直後に見る

撮ったスクリーンショットは、次の工程に進む前に開いて見る。テストが通ったことは、画像が正しいことを意味しない。

- 確かめたい要素が写っているか
- 実機と同じ見た目か。ダイアログの位置のずれ、半透明のオーバーレイ、画面の一部にしか描かれない、といった崩れがないか
- アニメーションの途中の状態で止まっていないか
- ログイン画面、エラー画面、読み込みの表示のまま撮っていないか
- 検索、一覧、帳票で、結果が0件になっていないか（0件の表示を確かめるケースを除く）
- 資格情報、トークン、Cookie の値が写っていないか

崩れていれば、撮り方か待ち方を直して流し直す。崩れた画像を証跡として残さない。

## 0件の証跡を作らない

検索、一覧、帳票の証跡に、結果が0件の状態を使わない。返ってきたデータの中身を確かめるのが目的で、0件では照合しても何も確かめていない。改修でデータが返らなくなっても、旧版と新版がどちらも0件で「一致」になってしまう。撮る前に画面で実データを見て、複数の行が出る条件を選ぶ。条件を満たすデータがなければ、SKILL.md の「データやアカウントが足りないとき」に従ってデータを用意する。0件の表示そのものを確かめるケースだけは例外で、ケース名にそう書く。

## 完全性の確認

マニフェスト（`screen-manifest.md`）を分母に、ケースごとに証跡がそろっているかを確かめる。テストが通ったかどうかだけでは、記録すべきものが残ったかは分からない。

- ケースのディレクトリを走査して表を作るスクリプトを QA リポジトリに置き（例 `automation/web/scripts/completeness.mjs`）、手で数えない
- 判定はケースごとに行う。画面ごとの合計のファイル数を見て「そろった」としない。あるケースで増えたファイルが、別のケースのスクリーンショットが1枚もないことを隠す
- 表には、ケースごとにスクリーンショットの枚数、表示値、API の応答、帳票のファイルの有無と、状態を並べる
- 数えるのはファイルの有無で、テストの成否ではない。撮影と保存を判定より先に置いているので、NG になったケースにも証跡はある。テストの成否で欠落を決めるスクリプトは、比較先の run で NG のケースをすべて欠落にしてしまう（実機で確かめた）。result.md の結果（OK、NG、実行不能）は表の状態の列に並べるだけにし、欠落の判定に使わない
- 分母は、対象の画面のマニフェストだけにする。スクリプトにはマニフェストのファイルを引数で渡し（例 `node automation/web/scripts/completeness.mjs runs/<run> automation/web/manifests/loans-list.json`）、そこにある TC-ID だけを数える。run にほかの画面のケースがあっても、欠落にも余分にも数えない。複数の画面を1つの run で流したときは、画面ごとにマニフェストを渡して表を分ける

| TC-ID | png | 表示値 | API の応答 | 帳票 | 状態 |
|---|---|---|---|---|---|
| TC-loans-char-001 | 2 | あり | API-01 | - | そろっている |
| TC-loans-char-020 | 1 | あり | - | loans.csv | そろっている |
| TC-loans-char-003 | 0 | なし | なし | - | 欠落 |

欠落があれば、原因（撮影の設定、テストの失敗、撮った後の確認で崩れていた）に応じて前の工程に戻る。「だいたいそろった」で先に進まない。スクリーンショットの欠落は、画面表示の照合ができないことを意味するので、理由なしに残さない。過去に作り替える前のケースの残りがディレクトリにあれば消す。

## 秘密情報を証跡に入れない

テストそのもののスクリーンショット、表示値、API の応答は証跡にしてよい。ただし、資格情報、Cookie、トークンを含めない。証跡は作業者以外も見るもので、`lfs` の案件ではリポジトリの履歴に残り続ける。

- ログインの setup のトレース、動画、スクリーンショットは取らない。aidev-qa-login-session の setup はプロジェクトの設定でこれらを切ってある。全体の設定でトレースを有効にしても、setup のプロジェクトでは上書きされていることを確かめる
- 特性テストのプロジェクトのトレースは、失敗の診断のために `retain-on-failure` で残してよい。ただし、トレースは通信のヘッダーをそのまま持ち、storageState から送った Cookie や `Authorization` の値が入る。トレースは証跡のディレクトリに入れず、Playwright の出力先の `test-results/pw/`（`.gitignore` で除外されている）に置いたまま診断に使う。次の実行で消えるので、残したいトレースは `.qa-scratch/` に移す。開発者に渡す必要があるときは、そのセッションを先にログアウトして無効にし、無効にしたことを result.md に書く
- API の応答は本文と状態コードだけを保存し、ヘッダーは保存しない。応答の本文にトークンが入る API（セッションの情報、署名付きの URL を返すものなど）は、その項目を伏せてから保存し、伏せたことを記録する
- URL にトークンやセッションの ID が付くときは、記録や報告に書く前にクエリの値を伏せる
- スクリーンショットにトークンや個人情報が映る画面（設定画面、プロフィール）は、その要素だけを Playwright の `mask` で隠すか、撮影の対象から外す。隠したことを checkpoint の値に書く。照合に使う値を隠しすぎない
- 証跡をまとめて渡す（zip にする）前に、テスト用アカウントの個人情報やパスワードが写っていないかを見る

## result.md の書き方

QA リポジトリの `runs/README.md` の形式に従う。冒頭に環境名（プロファイルの `environments` の name）、版、実行日時を書き、表に TC-ID ごとの結果（OK、NG、実行不能）と証跡のパスを書く。実行日時は、記憶ではなく実行の記録（`result.json` の時刻）から書く。

表の後に、次を書く。

- 完全性の確認の表と、欠落の理由
- 失敗を検出できるかを確かめた内容（どの期待値を変え、どう失敗したか）
- 実行不能のケースの理由と、実行できるようにする手段（必要な承認、データの準備、aidev-qa-desktop-gui での実施など）。手段は提案だけにし、勝手に実行しない
- 更新を伴うケースで残ったデータがあれば、その識別子と場所。削除の操作がなく片付けられないデータも、接頭辞、件数、場所を書く
- モックを使ったケース、自分で用意したデータを使ったケースがあれば、その旨
