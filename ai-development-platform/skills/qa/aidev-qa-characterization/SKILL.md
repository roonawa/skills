# 既存画面の特性テスト

## Overview

画面の内部（API、データの取り方、フレームワーク）を作り直すとき、外から見た挙動を変えないことが求められる。そのとき正解になるのは仕様書ではなく、今動いている実装の挙動である。この Skill は、対象の画面のソースと実際の通信を調べて「どのロールが何を呼び、どう表示が分かれるか」を洗い出し、画面マニフェストで記録の範囲を決めてから、Playwright の特性テスト（ゴールデンマスターのテスト）として今の挙動を記録する。

記録するのは、画面表示、内部データ（API の応答）、帳票（CSV・PDF）の3点である。改修後の照合で、この3点を同じ単位で突き合わせるためである。テストは環境を外から差し替えられる形で書き、同じコードを旧版にも新版にも流せるようにする。照合そのものは aidev-qa-regression-compare が行う。

目的は、人が実機を操作して画面を確かめていた作業の置き換えである。境界値や異常系を網羅する QA ではない。正常系を基本にし、ロールや表示モードで挙動が変わるときだけ、その組み合わせの数だけ正常系を用意する。シナリオの数を増やすこと自体は目的にしない。完了の判定にカバレッジの数値は使わず、マニフェストのすべての項目が「記録済み」か「理由付きで除外」に決まったことで判定する。

## 特性テストの原則

特性テストは、仕様が正しいかではなく、今の実装がどう動くかを再現する。仕様を正とする普通のテスト設計とは逆で、これは意図した逆転である。ただし、逆転してよいのは表示の内容とデータの取得範囲までにする。

認可やアクセス制御の既知の不具合（担当外のデータが見える、など）を「今の挙動」としてそのまま記録すると、改修でそれを直したときに差分として誤検知されるうえ、不具合が仕様に見えてしまう。既知の不具合は次のどちらかにし、作業者だけの判断では決めない。

- 除外する（既定）。マニフェストの `excluded` に理由と根拠を書き、検証は aidev-qa-authz-test に回す
- リリースを優先して是正を後に回すと承認された場合は、マニフェストの `acceptedRisks` に承認者と是正の予定を書いて記録の対象にする。通常の `operations` に混ぜない。混ぜると、次の段階で直すべきものだと誰も気づけなくなる

「既知の不具合」かどうかは、コードを読んだ印象ではなく、設計書の既知の課題の節や課題管理の記録で判断する。根拠が見つからなければ「要確認」として開発者に確かめ、除外を先に決め打ちしない。

## When to Use

- 画面の改修や API の作り直しに入る前に、その画面の今の挙動を記録する
- 人が実機で確認していた画面のスモークテストを、自動のテストに置き換える
- 既存の特性テストに、ロールや表示モード、帳票のシナリオを足す
- 記録したテストを流し、証跡を runs/ に集めて、抜けがないかを確かめる

使わない場面は次のとおり。

- ロールごとのログイン済みのセッションを作るときは aidev-qa-login-session を使う。この Skill はそのセッションを使う側である
- 記録したテストを旧版と新版に流し、差異を「一致／意図した差分／要確認」に分けるときは aidev-qa-regression-compare を使う
- ロールと操作の可否、担当内と担当外の区別、ID の差し替えの検証は aidev-qa-authz-test を使う
- 保存・印刷・フォルダ選択のダイアログ、外部アプリ、IME、ネイティブのログイン画面の操作は aidev-qa-desktop-gui を使う
- 受け入れ条件からテストケースを新しく設計するときは aidev-qa-test-design を使う。境界値や異常系の網羅もそちらで扱う

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`environments`（記録する環境）、`roles`、`stack`（画面と API の技術。参照資料の選び方に使う）、`evidence`（証跡の保存方式）を使う。本文の到達手順、テストデータの準備方法、落とし穴も読む
- 対象の画面と、そのソースコード（作業者が場所を示す）
- `plan/acceptance.md` と、あれば `cases/*.md` の既存のケース
- aidev-qa-login-session が作った `automation/web/.auth/<role>.json`

出力は次のとおり。

- 画面マニフェスト `automation/web/manifests/<画面>.json`。形式は `references/screen-manifest.md` に書いた。コミットの対象にする
- 特性テストのケース。`cases/<機能>.md` に、QA リポジトリの `cases/README.md` の形式で書く。実行は「自動」にする
- テストのコード `automation/web/tests/<機能>.spec.ts`。テスト名の先頭に TC-ID を付ける
- 実行結果 `runs/<YYYYMMDD>-<run-id>/result.md` と、証跡 `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/`
- 作業者への返答。記録したケースの一覧、除外した項目と理由、要確認の項目、完全性の確認の結果を書く

ケースの AC の行には、そのケースが確かめる AC を `plan/acceptance.md` から選んで書く。今の挙動に対応する AC がないときは、AC を足すかどうかを作業者に確かめる。推測で AC を作らない。期待結果が仕様ではなく今の実装から取ったものであることは、ケースの備考に書く。

## 進め方

最初に案件プロファイルを読む。`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-characterization` で検査し、終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。どの環境を記録の対象にするか（改修前の版が動いている環境）がプロファイルから決まらなければ、作業者に確かめる。推測で埋めない。

次に、ログイン済みのセッションを用意する。プロファイルの `login.method` が `none` でなければ、aidev-qa-login-session でロールごとの storageState を作り直してから始める。前回の実行のセッションを使い回すと、期限切れでログイン画面を記録してしまう。

`stack` に `webview2` がある、または画面がデスクトップアプリの中の WebView2 に表示されるなら、`references/webview2.md` を読む。接続とログインの仕方がブラウザとは違う。それ以外の Web の画面は `references/playwright.md` を読む。

### 1. 画面を調べる

対象の画面のソースを読み、次を洗い出す。

- 呼んでいる API（REST のパスとメソッド、GraphQL の操作名）と、引数と応答の形
- 帳票のダウンロードを伴う呼び出し
- 画面に到達できるロール。ルーティングのガードだけでなく、テンプレートの条件分岐で実際に何が出るかまで見る
- ロールによって表示や呼び出しが変わる分岐、タブやラジオボタンなどの操作で表示が切り替わる分岐（表示モード）
- 必須入力のあるフォーム
- どこからも呼ばれていない処理（デッドコードの候補）。参照を検索した結果を根拠に残す

ソースだけでは決められないこと（子の部品の変更が再取得を呼ぶか、など）は「要確認」として残し、記録の対象か除外かを決め打ちしない。

サーバーで HTML を組み立てる画面のように、画面から API を呼ばないこともある。その場合は、画面に出た値を構造化して保存したものを内部データの代わりにし、マニフェストの `apis` を空にして理由を書く。

### 2. 動いている版を確かめる

リポジトリのソースが、記録する環境に実際にデプロイされている版とは限らない。共有の部品が先に改修されている、まだデプロイされていない、ということが起きる。テストを書く前に、対象の画面を通信の差し替え（モック）なしで1回操作し、実際に送られた API の一覧を、ソースから洗い出した一覧と突き合わせる。食い違えば、実際の通信を正とし、その版のソースを履歴から探して読む。この特性テストが記録するのは今動いているものであり、リポジトリの最新のコードではない。確かめた結果（実際の API の一覧、画面に出る版の表示、食い違いと参照した版）はマニフェストに書く。

### 3. 記録できるかと深さを決める

洗い出した操作を、記録の対象と除外に分ける。記録の対象は、通常のブラウザ操作と API の応答で、待ち方の工夫を重ねなくても安定して再現できるものである。次のものは除外し、マニフェストの `excluded` に理由と根拠を書く。

- タイミングに依存する処理（ポーリング、時刻で変わる表示）や、外部の要因に依存する処理
- 外部の SSO への遷移、OS のダイアログ、外部アプリの起動を伴う処理。デスクトップの GUI の操作は aidev-qa-desktop-gui に渡す
- デッドコード、既知の認可の不具合（前の節）

ただし、Playwright の標準の待ち方（応答や要素を待つ）で素直に安定するものまで「記録できない」として除外しない。除外を増やすと、置き換えたかった実機の確認の範囲が狭くなる。

記録の対象にした操作には、深さ（`light` か `full`）とリスク（高・通常・低）を付ける。ロールのガードだけ、本人のデータだけ、全件を参照できる、という操作は `light` でよい。担当範囲で行を絞る操作、個人情報を扱う操作、帳票、更新を伴う操作は `full` にする。迷ったら `full` にする。`light` は、明らかにリスクが低いときにだけ選ぶ省略であり、既定ではない。`full` の操作では、主要な分岐ごとに対応するケースがあるかを表で確かめ、一覧は表示されたすべての列を記録する。リスクが高い操作は、内部データを要約せず全量を保存する。

### 4. ケースの範囲を決める

ケースは次の3種類にする。

- 正常系。到達できるロールと表示モードの組み合わせごとに、正常にデータが返って表示される状態を1つずつ用意する。組み合わせにケースを付けないときは、理由をマニフェストに書く
- 必須入力のあるフォームだけ、「必須項目をすべて入れて送信すると成功する」と「必須項目を1つ空けて送信するとバリデーションのエラーが出る」の2通り。前者は正常系と同じでよい。後者を省くと、必須のチェックが壊れても検出できない
- 帳票。ダウンロードしたファイルそのもの（列、行数、値）を記録する

これ以外の異常系、件数の境界、null や空の表示は、この Skill では作らない。ただし、ロールによる表示の出し分けが画面の主な振る舞いなら、その出し分けは正常系の一部として記録する。

検索、一覧、帳票のケースでは、結果が0件の状態を記録しない。これらは返ってきたデータの中身を確かめるのが目的で、0件では何も確かめられない。事前に画面で実データを見て、複数の行（できれば複数ページ）が出る条件を選ぶ。0件の表示そのものを確かめたいときだけ、そのためのケースを別に1つ作る。一覧では、自由記述のように空になりやすい列にも値が入っている行を選ぶ。値の入った行が1件もない列は「未検証」と書き、確かめていない列を一致と扱わない。

同じ分岐、同じデータの範囲を重ねて記録するケースは作らない。既存のテストが同じ振る舞いを記録していれば、新しく作らずに拡張する。

### 5. マニフェストを書き、自分で点検する

`references/screen-manifest.md` の形式で `automation/web/manifests/<画面>.json` を書く。書いたら、テストのコードに進む前に次を点検する。

- 呼んでいる API と帳票に、洗い出しの漏れがない
- 除外したものすべてに、理由と具体的な根拠（検索の結果、設計書の節など）がある。「確認済み」のような感想を根拠にしていない
- 既知の認可の不具合が `operations` に混ざっていない
- 到達できるロールと表示モードの組み合わせごとに、正常系のケースがある
- 必須入力のあるフォームに、2通りのケースがある
- `full` の操作の主要な分岐に、対応するケースがある
- 「要確認」が残っていれば、開発者に確かめた。答えを待つ間に決め打ちしていない

### 6. テストを書いて流す

`references/playwright.md`（WebView2 の画面は `references/webview2.md` も）に従ってテストを書く。要点は次のとおり。

- 環境の URL はテストに書かず、プロファイルの `environments` から実行時に渡す。同じコードを別の環境に流せることが、aidev-qa-regression-compare がこのテストを使う前提である
- 捕まえる API の条件（パス、操作名）はテストに直接書かず、マニフェストから読む。改修で API の名前が変わっても、マニフェストを直すだけで追従できる
- 各ケースで、画面のスクリーンショット、画面に出た値、API の応答、帳票のファイルを保存する。保存先の run のディレクトリは、テストを流す前に環境変数 `QA_RUN_DIR`（`runs/<YYYYMMDD>-<run-id>` のパス）で渡す
- 実行ごとに変わる値（作成日時、採番された ID、更新日時、今日の日付、`QA-<run-id>-` の付いたテストデータ）は、名前を挙げた項目だけを明示した規則で正規化し、元の値も残す。規則はマニフェストの `normalize` に書き、aidev-qa-regression-compare が同じ規則で照合できるようにする。期待値を固める前に同じケースを2回記録し、2回で変わる値を挙動と区別する。データの差を消すために、スクリーンショットの `mask` や値の除外を広げない
- ケースごとに「このテストを失敗させる変更は何か」を1つ言えるようにする。言えなければ、応答があったことしか確かめていない緩いテストなので、記録する観点を考え直す

書いたら、確認を待たずに記録する環境へ流す。「作った」という申告では終えない。証跡の撮り方、撮った直後の確認、完全性の確認は `references/evidence.md` に従う。

### 7. 失敗を検出できるかを確かめる

テストが緑でも、そのテストが挙動の変化を検出できるとは限らない。ケースの種類ごとに少なくとも1つ、検出できることを確かめる。

- 期待値を1か所だけ変えて流し、失敗することを見る（一覧の1つの値、帳票の1行、API の応答の1項目）
- 空の storageState で流し、ログイン画面に落ちたことを「対象の画面にいない」として失敗にすることを見る
- 必須項目のケースは、必須の入力を入れたまま送ると「エラーが出ない」として失敗することを見る

失敗しなければ、アサーションか、対象の画面にいるかの確認が効いていない。確かめたあとは期待値を戻し、もう一度流して緑に戻ったことを見る。確かめた内容は result.md の備考に書く。

### 8. 結果を書く

`runs/<YYYYMMDD>-<run-id>/result.md` に、冒頭に環境名、版（画面に出る版の表示や、デプロイの識別子）、実行日時を書き、TC-ID ごとに結果と証跡を書く。結果は次のように決める。

- OK：今の挙動が記録でき、アサーションが通った
- NG：画面は動いたが、アプリの異常が見えた（API がエラーを返した、HTTP 200 でも応答にエラーが入っていた、画面にエラーが出た）。記録した挙動が異常を含むことになるため、開発者に伝える
- 実行不能：ログインの失敗、環境の停止、データの不足、ネイティブの操作が必要、などでケースを実行できなかった。理由と、実行できるようにする手段を書く

テストのコードの不具合で落ちたものは、NG にしない。直してから流し直す（「失敗の性質を分ける」の節）。

## 更新を伴う操作

登録、修正、削除も記録の対象にするが、既存のデータを壊さないために次の条件で行う。

- 書き込む前に、環境、画面、操作、使ってよいデータの範囲、後始末の方法を作業者に示して承認を得る。サーバーの実装を読んで、対象の行以外に何を書き込むか（関連の表、履歴、採番、通知）も示す。メールの送信や外部への連携など取り消せないものを伴う操作は、承認があっても記録の対象にせず、除外か実行不能にする
- テストで作るデータには、実行ごとに一意の接頭辞（例 `QA-<run-id>-`）を付け、更新と削除はそのデータだけにする
- 成功のメッセージだけで成功としない。保存のあと、画面で検索し直して全項目が反映されたことを確かめる。削除は検索し直して出ないことまで確かめる
- 途中で失敗しても、自分が作ったデータを消す後始末を最後に必ず流す。後始末に失敗したら、残ったデータの識別子と場所を result.md に書いて作業者に伝える
- 結果が不明なまま再実行しない。二重に登録されることがある。先に画面で検索して状態を確かめる

## データやアカウントが足りないとき

必要なロールと担当範囲とデータの組み合わせ（例：複数件の申請を持つ担当者）が、既存のテスト用アカウントと実データでそろわないことがある。まず既存のもので条件を満たせるかを確かめ、満たせないと分かったら、作業者の承認の範囲で専用のデータやアカウントを用意してケースを完成させる。保留や除外のまま終えない。検索や帳票で0件しか出ないときも同じで、0件のまま記録せず、複数件が出る状態を作ってから記録する。用意したものは、マニフェストの該当する項目に `testDataSource: "self-created"` と作った内容を書き、既存のデータで確かめたものと区別する。正式なアカウントの発行やデータの投入の依頼は並行して出してよいが、その返事を待つことを止める理由にしない。

## 失敗の性質を分ける

テストが失敗したら、次のどれかに分けてから扱う。分け方を誤ると、アプリの不具合を「テストが壊れているだけ」として見逃すか、テストの不具合をアプリの不具合として報告することになる。

| 性質 | 見分け方 | 扱い |
|---|---|---|
| アプリの異常 | API のエラー、HTTP 200 の応答の中のエラー、画面のエラー表示。対象の画面には正しく着いている | 証跡を残して NG。開発者に伝える |
| テストのコードの不具合 | セレクタが合わない、待ち方が足りない、期待値の転記を誤った | 失敗した証跡は診断用として `test-results/` などの Git に入らない場所に移してから直し、流し直す。直した理由を残す |
| 環境と認証 | ログイン画面や IdP に落ちた、環境が応答しない、データが変わった | セッションを作り直す、環境を確かめる。直らなければ実行不能 |

期待値を緩める、`test.skip()` で外す、条件分岐で早く抜けるといった方法で緑にしない。何も確かめないテストが残るだけである。

## よくある誤り

- 画面の表示だけを記録し、API の応答や帳票のファイルを保存しない。改修後の照合で、内部データと帳票を突き合わせられなくなる
- マニフェストを作らずに「記録した」と申告する。何を記録して何を除外したかを、誰も確かめられない
- 既知の認可の不具合を、承認の記録なしに `operations` に入れる
- リポジトリの最新のソースが動いていると思い込み、実際の通信を見ずにテストを書く
- 検索、一覧、帳票の証跡に0件の結果を使う
- 一覧の一部の列だけをアサートする。詳細の画面が一致しても、一覧の一致にはならない
- 期限切れのセッションのまま流し、ログイン画面を証跡にして緑にする
- 「記録できない」を理由に、標準の待ち方で安定する操作まで除外する
- 担当範囲や個人情報を扱う操作を `light` にする
- 必須入力のあるフォームで、必須項目なしのケースを作らない
- API の名前や環境の URL をテストに直接書き、改修後の環境に流せないテストにする
- 撮ったスクリーンショットを見ずに、証跡として扱う

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- 画面マニフェストができ、すべての項目が `operations`、`reports`、`acceptedRisks`、`excluded` のどれかに決まっている。除外にはすべて理由と根拠がある
- 到達できるロールと表示モードの組み合わせごとに正常系のケースがあり、必須入力のあるフォームには2通りのケースがある
- 記録の対象の項目ごとに、画面表示、内部データ（API がない画面は構造化した表示値）、帳票（ある場合）の証跡がそろっている。完全性はケースごとに機械的に数えて確かめた
- 検索、一覧、帳票の証跡に、0件の結果が使われていない（0件の表示そのものを確かめるケースを除く）
- 記録する環境でテストを流し、result.md に TC-ID ごとの結果と証跡を書いた
- 期待値を変えると失敗すること、ログイン画面に落ちると失敗することを確かめた
- 証跡、ログ、返答に、資格情報、Cookie、トークンの値が入っていない
