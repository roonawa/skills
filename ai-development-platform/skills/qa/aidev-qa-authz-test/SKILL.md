# ロールと所有者の認可の検証

## Overview

認可の不具合は、画面を操作するだけでは見つからない。画面がボタンを隠していても、サーバーがそのリクエストを受け付ければ、URL や API を直接呼ぶ人には操作できてしまう。この Skill は、ロールごとのセッションで対象の API や URL を直接呼び、許可されるべきものが通り、拒否されるべきものが拒否されることを確かめる。

認可は2つの層で確かめる。

- ロールの可否：そのロールがその操作をしてよいか
- 行レベルの所有者：してよい操作でも、対象が本人の分か、担当の範囲か。他人の ID に差し替えたリクエスト、他人の記録を指す ID を入れた更新、検索や一覧の結果に他人のデータが混ざらないかを見る

ロールの可否だけを確かめて終えない。参照の操作に所有者の判定があっても、同じデータの更新や削除にもあるとは限らない。書き込みの側だけ所有者の判定が抜け、担当外の記録を書き換えられる不具合は、ロールの可否の検査では見つからない。

拒否の確かめ方は、状態コードだけでは足りない。拒否の状態コードを返しながら本文に内容を載せる実装、拒否を返しながら書き込み自体は済ませている実装がある。拒否は、状態コード、本文に守るべき内容が出ないこと、書き込みなら記録が変わっていないこと、の3つで確かめる。

## When to Use

- 改修や作り直しの後に、ロールごとの可否と所有者の判定が要件や設計の権限の表のとおりかを確かめる
- 画面では隠れている操作（CSV の出力、他人の詳細の URL、管理者向けの API）が、権限のないロールから直接呼べないかを確かめる
- 認可の不具合を直した後に、その回帰テストを作る

使わない場面は次のとおり。

- ロールごとのログイン済みのセッションは aidev-qa-login-session で作る。この Skill はそれを使う側である
- 認可以外の期待結果を正としてケースを流すときは aidev-qa-test-run を使う。結果の分け方と NG の残し方は同じ基準に従う
- 同じ認可の表を旧版と新版の両方に流し、許可と拒否の差を分類するときは aidev-qa-regression-compare を使う。この Skill は、1つの環境の結果を期待の表と突き合わせる
- 画面の挙動を記録する特性テストは aidev-qa-characterization を使う。そこで見つかった認可の疑い（画面マニフェストの `known-authz-bug`）は、この Skill で確かめる
- 権限の表（どのロールに何を許すか）そのものを決めることはしない。要件や設計で決めたものを受け取って確かめる。決まっていない欄は作業者に確かめる
- 負荷、監査ログ、パスワードの強度、セッションの寿命の検査は扱わない
- NG からの Issue の起票は aidev-qa-bug-ticket を使う。Gitea に Issue を作り、起票した番号を result.md に書く

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`environments`、`roles`（2つ以上）、`login` を使う。証跡の保存方式 `evidence` も使い、プロファイルになければ作業者に確かめる。本文の到達手順、テストデータの準備方法、落とし穴も読む
- 権限の根拠。`plan/acceptance.md`、要件定義書や設計書の権限の表、`cases/*.md` の認可のケース
- 対象の操作の一覧の手がかり。画面マニフェスト（`automation/web/manifests/*.json` の `apis` と除外の理由）、API の定義やルーティングのコード、既存の API の棚卸し
- aidev-qa-login-session が作るロールごとのセッション `automation/web/.auth/<role>.json`（環境を分けるときは `automation/web/.auth/<environment>/<role>.json`）

出力は次のとおり。

- 認可の表 `automation/web/authz/<機能>.json`。形式は `references/authz-matrix.md` に書いた。1行が1つの TC-ID で、ロール、操作、リクエスト、所有の関係、期待（許可か拒否かと確かめ方）、今の版の基準を持つ。テストはこの表から生成するので、表とテストが食い違わない。表はコミットする。資格情報、Cookie、個人情報の値は書かない
- 認可のケース `cases/<機能>.md`。表の行ごとに、QA リポジトリの `cases/README.md` の形式で書き、実行は「自動」にする。すでに aidev-qa-test-design が作ったケースがあれば、その TC-ID を表の行に対応させ、足りない行のケースだけを足す
- テスト `automation/web/tests/<機能>.spec.ts`。テスト名の先頭に TC-ID を付ける

`<機能>` は、表のファイル名、表の `area`、ケースのファイル名、テストのファイル名、TC-ID の機能名で同じ1つの名前を使い、末尾に必ず `-authz` を付ける。例えば `expenses-authz` なら、表は `automation/web/authz/expenses-authz.json`、ケースは `cases/expenses-authz.md`、テストは `automation/web/tests/expenses-authz.spec.ts`、TC-ID は `TC-expenses-authz-001` になる。aidev-qa-test-design のケース（`cases/expenses.md`）や aidev-qa-characterization のケース（`cases/expenses-char.md`）と同じ名前にしない。Playwright の設定の `authz` のプロジェクトは、この `-authz.spec.ts` の末尾でテストを選ぶ。既存のケースや表のファイルを上書きしない。同じ名前のファイルがあれば、それが認可のケースかを確かめ、行を足す形で扱う。
- 実行結果 `runs/<YYYYMMDD>-<run-id>/result.md` と証跡 `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/`
- 作業者への返答。NG を先頭に、表の行の数と結果ごとの件数、未検証の行と理由、見つかった不具合の一覧を書く

表を `cases/` の Markdown ではなく `automation/web/authz/` の JSON に置くのは、テストが表を読んで行ごとにリクエストを組み立て、行の数を網羅の分母として機械的に数えるためである。ケースの正本は従来どおり `cases/*.md` で、表はそれをテストに渡す形である。

## 進め方

### 1. プロファイルと条件を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-authz-test` で検査する。この Skill では `roles` が2つ以上要る。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

続けて次を決める。決まらないものは作業者に確かめ、推測で埋めない。

- どの環境で流すか（`environments` の name）と、その版を何で特定するか
- その環境が本番ではないこと。`purpose` から判断できなければ作業者に確かめる。本番の環境には、拒否されるはずの書き込みも含めて送らない
- その環境が共有か、作業者の手元か。共有の環境で書き込みを試すかは、6の前に作業者の承認を得る
- 既存のテストや表がどこにあるか。`automation/web/authz/` と `automation/web/tests/` を対象の操作の名前と TC-ID で検索する。複数の画面から呼ばれる API は、別の画面の担当者がすでに表を作っていることがある

### 2. 対象の操作を洗い出し、絞り込む

認可の表は、画面ではなく操作（API、URL、帳票の出力）を単位にする。同じ API を複数の画面が呼ぶなら、操作として1つにまとめ、呼ばれる画面は参考として記録する。画面ごとに表を作ると、同じ操作の検証が重複し、どれが正か分からなくなる。既存の表があれば、その操作は再利用するか行を足すかで扱い、新しく作らない。

洗い出しの手がかりは、画面マニフェストの API、ルーティングやコントローラーのコード、API の定義（OpenAPI、GraphQL のスキーマ）、帳票やダウンロードの URL である。画面から呼ばれなくなったがサーバーにはまだ残っている操作（旧版の API、古い URL）も対象にする。画面が呼ばなくても、直接呼べるなら検証の対象である。

操作が多いときは、優先順位を付けて上から作る。高くするのは次のものである。

- 他人の記録の更新、削除、状態の変更（承認や取消）
- 多くの人のデータをまとめて返すもの（CSV や帳票の出力、検索、一覧）
- 個人情報や機微な情報の詳細
- 画面のボタンの表示だけで制御しているように見えるもの、特定のロールにだけ画面のある操作
- 既知の不具合や、過去に認可の不具合が出た操作

だれでも見てよい参照用のデータ（マスタの一覧など）は低くする。絞り込んだ範囲と、後回しにした操作とその理由は、表の `scope` に書いて作業者に伝える。黙って外さない。

### 3. 期待の表を作る

操作とロールの組ごとに、要件や設計の権限の表から期待を決める。実装の今の振る舞いを期待にしない。根拠のない欄は「⚠ 要確認」として作業者に確かめ、確かめるまでその行の期待を埋めない。

行の作り方は、期待の種類で分かれる。

| 権限の表の記述 | 作る行 |
|---|---|
| そのロールには許さない | 拒否の行。加えて、許されたロールで同じリクエストが内容を返す許可の行（下の対照） |
| そのロールに全件を許す | 許可の行。行レベルの所有者の行は要らない |
| 本人の分だけ、担当の範囲だけ、自分の組織の分だけ | 範囲の中の対象への許可の行と、範囲の外の対象への拒否の行を対にする |
| 上の範囲付きで、操作が対象の ID を入力に取る更新や削除 | さらに、範囲の外の記録の ID を直接入れた更新や削除の拒否の行。書き込みの後の記録が変わっていないことを確かめる |
| 上の範囲付きで、検索や一覧 | 結果に範囲の外のデータが1件も混ざらない行。検索の条件や絞り込みのパラメータで範囲の外を指定した行も作る |
| 作成の操作で、所有者や担当を入力に取れる | 他人を所有者にした作成の行。作られた記録の所有者が本人に強制されるなら `expected` を `forced-owner`、拒否されるなら `deny` にする。どちらが正しいかは設計で決め、作業者に確かめる |
| 上の範囲付きで、アプリに更新や削除の操作がない | 書き込みの拒否の行を、他人を所有者にした作成で作る（上の行）。ID の差し替えの行は作れないので、`uncovered` に理由を書く |

未ログインの状態（ロールは `anonymous`）の行は、ログインが要る操作のすべてに作る。

同じロールでも、属性（所属、雇用の区分、学年のような下位の区分）で期待が変わる操作は、属性ごとにロールを分けて行を作る。ロールの名前だけで1つのアカウントに決め打ちしない。

拒否の行には、何をもって拒否とみなすかを書く。期待する状態コード（403、401、存在を隠す設計なら 404、未ログインならログイン画面への転送）、本文に出てはいけない内容の目印、書き込みなら後で読み直して確かめる項目である。どの状態コードで拒否するかが設計に書かれていなければ、作業者に確かめて表に残す。「200 以外なら拒否」のような広い条件にすると、500 のエラーや、セッション切れによるログイン画面への転送まで拒否に数えてしまう。

各行には、その行を失敗させる実装の変更を一文で書く（`failsIfChanged`）。例は「詳細の取得で所有者の比較を外すと、他人の申請の件名が本文に出て失敗する」。書けない行は、確かめ方が緩いか、何を守る行なのかが決まっていない。

画面マニフェストの既知の認可の不具合（`excluded` の `known-authz-bug`）や `acceptedRisks` の項目を確かめる行には、`resolvesKnownIssue` にその項目を書く（書き方は `references/authz-matrix.md`）。aidev-qa-screen-verification が、この欄で認可の結果を既知の不具合に結び付ける。

### 4. 対象のデータと ID を用意する

行レベルの行には、範囲の中と外の対になる実在の記録が要る。用意の仕方は次のとおり。

- テストが作る。本人のロールと他人のロールでそれぞれ記録を作り、実行ごとに一意の接頭辞（例 `QA-<run-id>-`）を付ける。拒否されるべき書き込みは、このテストが作った記録に対してだけ試す。書き込みの拒否の行には、参照の行と共有しない専用の対象を作る。書き込みの不具合で記録が変わると、同じ対象の目印を探す参照の拒否の行が、目印の消えた記録に対して何も確かめずに通ってしまうためである
- 既存のデータから探す。全件を見られるロールや、担当の関係を持つマスタから、範囲の中と外の組を探す。探し方を表の `targets` に書き、ID や個人の値そのものは書かない

内部の ID の形式を推測して、実在を確かめずに ID を組み立てて使わない。許可の行がその ID で拒否されても、ID が存在しないのか、認可で拒否されたのか区別できない。実在の記録が用意できないときは、その行を実行不能にし、理由に「テストデータを用意できない」と、用意する手段（だれに何を頼むか）を書く。存在しない ID への応答（404）を確かめる行は、これとは別に作る。

本文に内容が出ないことを確かめる目印は、テストが作った記録の件名のような、その記録にだけある値にする。目印を表に書くときは、値ではなく「`targets` の other-1 の件名」のように指す。

### 5. 直接のリクエストのテストを書く

テストは、ロールごとの storageState を読み込んだ API のリクエストのコンテキストで、表の行のリクエストを送る。ブラウザで画面を開いてボタンの有無を見ることはしない。書き方の例は `references/authz-matrix.md` にある。要点は次のとおり。

- 環境は `QA_ENV`（プロファイルの環境名）と `QA_BASE_URL` で渡し、URL をテストに書かない。storageState は、aidev-qa-login-session の `authFile(role, process.env.QA_ENV)` でいつも環境を渡して選ぶ（`automation/web/.auth/<environment>/<role>.json`）。環境を省くと、setup が書いた場所と読む場所が食い違い、別の環境や古いセッションを読む。`anonymous` は storageState を読み込まない
- リダイレクトは自動でたどらない（`maxRedirects: 0`）。たどると、ログイン画面への転送が 200 のログイン画面に化け、拒否と許可の区別がつかなくなる
- 状態の変わる操作（POST、PUT、DELETE）は、アプリの CSRF 対策のトークンを、画面が送るのと同じ形で付ける。トークンの取り方は、同じセッションでフォームの画面を GET して hidden の入力欄から取る、meta タグから取る、Cookie の値をヘッダーに写す、トークンを返す API を呼ぶ、のどれかで、どれを使っているかはアプリの画面の送信を一度観察して決める。トークンがないと、認可の判定の前に CSRF の検査で拒否される。それは認可が効いている証拠にならない。拒否の行と同じ書き方で送った許可の行が通ることで、トークンの扱いが正しいことを確かめる
- GraphQL のように、拒否を 200 とエラーの本文で返す API では、エラーの分類（認可の拒否を表すコードや種類）で判定する。空の応答や `null` は拒否と区別できないので、拒否の判定に使わない。想定外のエラーの種類（内部エラー、検証エラー）が返ったら、拒否とせず、別の不具合を疑って NG の候補にする
- 拒否の行では、状態コードを確かめた後、本文に目印がないことを確かめる。書き込みの拒否の行では、許可されたロール（本人か全件を見られるロール）で対象を読み直し、項目が変わっていないこと、消えていないこと、作成なら接頭辞の付いた新しい記録が増えていないことを確かめる
- 1行を1つのテストにし、テスト名の先頭に TC-ID を付ける。表から生成するので、行を足せばテストも増える
- 表のテストは `workers: 1` で、表の行の順に1つずつ流す（aidev-qa-characterization の Playwright の資料の設定）。`test.describe.configure({ mode: 'serial' })` は使わない。1つの行が失敗すると後の行がすべて飛ばされ、NG と実行不能の区別が失われる。書き込みの行と参照の行が並行して同じ記録に触れると、結果が順序で変わる。表の最後に、対照の許可の行をもう一度流し、目印がまだ出ることを確かめる
- テストが失敗すると、Playwright はワーカーを作り直し、`beforeAll` を流し直す。対象を作る setup は、作った対象の ID と目印を `.qa-scratch/` の下のファイルに書き、ファイルがあれば作らずにそれを読む。読まないと、失敗のたびに対象が増え、後の行が別の対象を見る

証跡には、応答の状態コードと本文だけを保存する。ヘッダーは保存しない。Cookie、CSRF のトークン、セッションの ID がヘッダーや送った本文に入るためである。リダイレクトの行では、転送先のパスだけを書き、クエリは落とす。テストのトレースは通信のヘッダーと Cookie を含むので、証跡にせず Playwright の出力先（`test-results/pw/`）に置いたまま診断に使う。許可の行の本文は、多くの人の個人情報を含むことがある（一覧、検索、CSV）。本文をそのまま保存してよいのは、対象がテストの作った記録だけのときか、`evidence.method` が `local` か `external` のときである。`lfs` のとき、または既存のデータを返す許可の行では、状態コード、見つかった目印の名前、行の件数だけを保存する。拒否の行の本文は、内容が出ていないことの証拠なので保存する。ただし NG で内容が出ていた場合は、同じ基準で扱う。result.md には個人の値を写さず、「件名と金額を含む 1 件」のように性質で書く。

### 6. 今の版の基準を取る

期待の表を当てる前に、今の版（改修の前の版や、修正を入れる前の環境）で同じ表を流し、行ごとに観測した振る舞いを表の `baseline` に残す。基準は期待ではない。基準と期待が違う行は、改修でその行の振る舞いが変わるべきことを示し、作業者と開発者に見せる一覧になる。

基準の環境では、拒否されるべき書き込みが実際に通ることがある。基準を取る前に、書き込みの行で試す対象が4で作った記録だけであることを確かめ、共有の環境なら作業者の承認を得る。他人の実在の記録への書き込みを試して確かめることはしない。確かめられない行は、基準を「未確認」とし、開発者にコードで確かめてもらう。

基準を書き込むのは、その実行で流した行だけにする。流していない行（絞り込んで流した残り、実行不能だった行）の `baseline` は書き換えず、前の値を残す。

旧版と新版の両方が動いていて、両方の結果を並べて差を分類したいときは、この表とテストをそのまま aidev-qa-regression-compare に渡す。

### 7. テストが失敗を検出できるかを確かめる

新しく書いたテストは、一度失敗させて、失敗を検出できることを確かめてから結果に使う。考え方と戻し方（変える前に `git add` で押さえる、`QA_RUN_DIR` を `.qa-scratch/` の下に向ける、戻した後に差分がないことを見て流し直す）は aidev-qa-test-run と同じである。認可のテストでは、次の確かめ方が使える。

- 基準と期待が違う行は、基準の環境に流すと失敗するはずである。失敗のメッセージがその行の期待（状態コードや目印）を指していることを見る
- 拒否の行の目印の検査は、対照の許可の行で、同じ目印が本文に実際に出ていることで確かめる。許可の行で目印が見つからなければ、拒否の行の「目印がない」は何も確かめていない
- 基準と期待が同じ行は、期待を逆にする（403 を 200 にする、目印が「ない」を「ある」にする）か、作業者の手元のアプリで権限の判定を外して流す。注入は作業者の承認を得てから行い、共有の環境では行わない

### 8. 実行し、判定する

流す直前に、aidev-qa-login-session でロールごとのセッションを作り直す。アプリを再起動や再デプロイした後も作り直す。期限の切れたセッションで流すと、拒否の行がログイン画面への転送や 401 で「拒否された」ように見え、誤って OK になる。これを防ぐため、ロールごとに少なくとも1つの許可の行を同じ実行に含め、その行が通ったロールの拒否の行だけを判定に使う。許可の行が落ちたロールの拒否の行は、セッションを疑って実行不能にする。

最終の実行では、新しい run-id を決めて空の `runs/<YYYYMMDD>-<run-id>/` を作り、`QA_RUN_DIR` に設定して流す。テストの自動の再試行は切る（`retries: 0`）。書き込みの行が二重に送られるためである。テストを直しながらの実行は `QA_RUN_DIR` を Git に入らない場所に向ける。データの状態、流し直し、片付けられないデータの扱いは aidev-qa-test-run の「データの状態と流し直し」に従う。

結果の分け方は aidev-qa-test-run の基準に従う。認可の表で迷いやすいのは次の場合である。

| 観測 | 結果 |
|---|---|
| 期待どおりの拒否の状態コードで、本文に目印がなく、書き込みなら記録も変わっていない | OK |
| `forced-owner` の行で、作成は通ったが、作られた記録の所有者が本人になっていた | OK |
| `forced-owner` の行で、作られた記録の所有者が指定した他人のままだった | NG |
| 拒否の行で、内容を返した（200 と目印） | NG |
| 拒否の状態コードだが、本文に目印がある。または読み直すと記録が変わっていた | NG。状態コードだけを見れば OK に見える不具合として、詳細に書く |
| 拒否の行で、設計と違う状態コードで拒否した（403 のはずが 404 や 500） | NG。内容は守られていても、設計どおりではない。500 なら別の不具合の可能性も書く |
| 許可の行で、拒否された | NG。ただし、同じロールのほかの許可の行もすべて落ちたなら、セッションを疑って実行不能にし、作り直して流す |
| ログインしているはずのロールで、ログイン画面への転送や 401 が返った | 実行不能（セッションの期限切れ）。拒否の OK にしない |
| 検索や一覧で、範囲の外のデータが混ざった | NG。混ざった件数と、どの対象の目印が出たかを書く。個人の値は写さない |

流し直しの回数と、間欠的な食い違いの扱いは aidev-qa-test-run と同じで、最初の実行の後に2回までにする。書き込みの行は、結果が分からないまま流し直さない。先に許可されたロールで記録の状態を確かめる。

期待と違う結果が出ても、この Skill では製品のコードを直さない。修正が1行に見えても、開発者に「ついでに直して」と頼まれても、その場では直さず NG として記録する。検証する側が直して自分で合格と判定すると、独立した検証にならず、同じ操作のほかの判定の抜けも見落とす。

### 9. 結果を書き、報告する

result.md は aidev-qa-test-run の形式（冒頭の環境名、版、実行日時と TC-ID ごとの表）で書く。表の後に「認可の表の集計」の節を足し、操作ごとに、許可と拒否の行の数、結果ごとの件数、基準と期待が違う行の数、未検証の行と理由を書く。NG の詳細には、ロール、送ったリクエスト（メソッド、パス、ID は `targets` の名前で指す）、期待（状態コード、目印、書き込みなら読み直す項目）、実際（状態コードと、本文に出た目印の名前）、証跡の場所を書く。

テストが作った記録は、最後に作ったロールで消す。アプリに削除の操作がなければ後始末の手順を作らず、残った記録の接頭辞、件数、場所を result.md に書いて作業者に伝える。消そうとして消せなかったものも同じように書く。

作業者への返答は、NG を先頭に、見つかった不具合を操作ごとにまとめて書く。続けて、結果ごとの件数、後回しにした操作、未検証の行、要確認の期待を書く。数値は実行の出力から写す。

## よくある誤り

- ボタンやメニューが出ないことを拒否とみなし、直接のリクエストを送らない
- 拒否を状態コードだけで判定し、本文に内容が出ていることや、書き込みが済んでいることを見逃す
- ロールの可否だけを確かめ、他人の ID への差し替えや、検索と一覧への混入を確かめない。参照に所有者の判定があることを、更新にもあると思い込む
- 「200 以外なら拒否」とし、セッション切れの転送や 500 のエラーを OK にする
- 許可の行を作らず、すべてを拒否する実装でも通るテストにする。拒否の行の目印が、許可の行で本当に出るかを確かめない
- CSRF のトークンを付けずに書き込みを送り、CSRF の検査による拒否を認可の拒否と取り違える
- 今の版の振る舞いを期待の表に写す
- 内部の ID の形式から ID を組み立て、存在しない ID での拒否を認可の拒否と数える
- 共有の環境で、他人の実在の記録に拒否されるべき書き込みを試す。本番の環境に送る
- 証跡にヘッダー、Cookie、トークン、トレースを残す。result.md に個人の値を写す
- 見つけた不具合をその場で直し、自分で合格と判定する

## 完了条件

- `aidev qa profile check` が `--skill aidev-qa-authz-test` で成功した
- 対象の操作と、後回しにした操作とその理由が表の `scope` にあり、作業者に伝えた
- 表のすべての行に、根拠（AC-ID か設計書の節）、期待、確かめ方、`failsIfChanged` がある。根拠のない期待は要確認として作業者に確かめた
- 範囲付きの権限の操作に、範囲の中と外の対の行がある。対象の ID を入力に取る更新と削除に ID の差し替えの行があり、検索と一覧に混入の行がある。未ログインの行がある
- 拒否の行は、状態コード、本文の目印、書き込みなら読み直しで確かめ、目印が対照の許可の行で実際に出ることを確かめた
- 今の版の基準を表に残すか、取れなかった理由を書いた
- 書き込みの拒否の行が参照の行と対象を共有せず、表のテストを `workers: 1` で表の順に流した。作った対象の ID を `.qa-scratch/` に持ち、ワーカーが作り直されても同じ対象を使った
- 新しいテストを一度失敗させて検出できることを確かめ、戻して流し直した
- result.md のすべての TC-ID に OK、NG、実行不能のどれかが付き、セッション切れによる拒否を OK に数えていない
- 証跡が状態コードと本文（保存してよい場合だけ）で、ヘッダー、Cookie、トークン、トレースを含まない。`lfs` のときや既存のデータを返す許可の行では本文を保存していない。result.md と表に個人情報の値がない
- テストが作った記録を片付けたか、残したもの（削除の操作がなく消せないものを含む）を result.md に書いて作業者に伝えた
- `baseline` は、その実行で流した行だけを書き換えた
- 見つかった不具合を直さずに NG として記録し、一覧にして報告した
