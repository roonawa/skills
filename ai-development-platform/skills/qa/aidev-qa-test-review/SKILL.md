# テストケースのレビュー

## Overview

テストケースのレビューは、ケースを書いた人とは別の目で、確かめるべきことが確かめられる形になっているかを見る作業である。この Skill は、受け入れ条件（AC）、テストケース、案件プロファイルを読み、漏れ・過剰・粒度・不明確の4種類で指摘を返す。指摘を採るかどうか、ケースをどう直すかを決めるのは作業者で、直す作業は aidev-qa-test-design で行う。

ケースを書いたセッションは、自分の判断の前提を共有しているため、同じ漏れを見落としやすい。そのため、この Skill はケースを作ったセッションとは別のセッションで使う。今のセッションでケースを書いた形跡があれば（会話の中で `cases/` を作成・編集していれば）、新しいセッションで使い直すよう作業者に伝えて止める。

## When to Use

- aidev-qa-test-design で `cases/<機能>.md` を作った後、清書の前後に別の目で確かめる
- 人が書いた既存のテストケースを、AC と一般的な観点に照らして見直す
- 仕様の変更や不具合の流出の後で、ケースの漏れを探す

使わない場面は次のとおり。

- ケースを書く、または指摘を受けてケースを直すときは aidev-qa-test-design を使う
- テスト戦略や AC の全体を見直すときは aidev-qa-strategy を使う
- ケースを実行して結果を判定するときは aidev-qa-test-run を使う

## 入力と出力

入力は次のとおりで、すべて QA リポジトリから読む。

- 案件プロファイル `knowledge/<product>/profile.md`。本文の観点と落とし穴をレビューの観点に加える
- `plan/acceptance.md`。AC の正本である
- `cases/*.md`。作業者が範囲を指定すれば、そのファイルだけを見る
- あれば `plan/strategy.md`（優先度、対象外の範囲）と `plan/inferred-spec.md`（コードしかない案件の推定仕様）
- 作業者が渡した要件定義書や設計書。AC に書かれていない条件から漏れを見つける手がかりになる

出力は会話への返答で、ファイルには書かない。この Skill は必ず読み取りだけで動く。レビューする側がケースを直すと、どの指摘をどう判断したかの記録が残らず、作業者が採否を決める機会もなくなるためである。指摘を保存したいと作業者が言えば、保存先と書く内容を作業者に決めてもらい、書く作業は作業者か aidev-qa-test-design に任せる。

返答の形式は次のとおり。

```markdown
## レビューの範囲
- ケース: cases/order.md（TC-order-001〜TC-order-014）、cases/list.md（TC-list-001〜TC-list-009）
- AC: plan/acceptance.md の AC-001〜AC-024（うち対象の機能に関わるもの 18 件）
- 観点: references/review-checklist.md の全項目、プロファイルの観点 3 件

## 指摘
| 対象 | 種類 | 重要度 | 指摘 | 理由 |
|---|---|---|---|---|
| AC-022 | 漏れ | 中 | 数量の上限ちょうど（99）で注文できるケースがない | 上限を 1 超えるケース（TC-order-002）だけでは、境界の向きの誤り（> と >=）を見分けられない |
| TC-order-007 | 不明確 | 低 | 期待結果が「エラーになる」で、文言と表示位置がない | 実行する人によって判定が分かれる。設計書 4.2 に文言の定義がある |

## プロファイルへの追記案
（案件固有の観点が見つかったときだけ書く）
```

指摘の行には、対象として TC-ID か AC-ID を1つ書き、重要度を付ける。ケースがない漏れは AC-ID を、既存のケースの問題は TC-ID を書く。理由には、どの AC・設計書の節・チェックリストの項目・プロファイルの観点にもとづく指摘かを書く。根拠を書けない指摘は出さない。指摘は重要度の高いものから並べる。

重要度は高・中・低の3段階で付ける。権限や行レベルの所有者の漏れ、データの破損や二重登録につながる漏れ、どのケースにも対応しない AC、優先度が高のケースや AC に関わる指摘は高とする。`plan/strategy.md` にリスク評価があれば、その機能のリスクの帯も重要度の判断に使う。判定が分かれる期待結果や、リスクが中程度の機能の観点の漏れは中、書き方の揃えや軽い過剰のように直さなくても判定が変わらないものは低とする。作業者と aidev-qa-test-design のセッションは、この重要度で直す順を決める。

指摘がなければ、「指摘」の節に「指摘なし」と書く。そのときもレビューの範囲の節は省かない。どこまで見て指摘がなかったのかが分からないと、作業者はその結果を判断に使えない。

## 進め方

最初に案件プロファイルを読む。`knowledge/<product>/profile.md` を開き、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-test-review` で検査する。この Skill が使う項目は `product` だけである。終了コードが 1 なら、エラーの内容を作業者に伝えて直してもらう。プロファイルがなければ、雛形の `knowledge/profile.template.md` から作るよう作業者に頼む。本文の観点と落とし穴は、レビューで確かめる観点の一覧に加える。

次に `plan/acceptance.md` と対象の `cases/*.md` を読み、AC とケースの対応表を頭の中で作る。どのケースにも対応しない AC、存在しない AC-ID を書いたケース、AC の一部の条件しか確かめていないケースをここで拾う。`- AC:` の行だけで対応を判断せず、ケースの手順と期待結果がその AC の本文を本当に確かめているかを読む。

対応が取れたら、機能ごとに `references/review-checklist.md` を読み、当てはまる観点を当てる。機能に一覧があれば 0 件と上限を、入力欄があれば必須と範囲を、確認のダイアログがあればキャンセルを、というように、機能が持つ要素から観点を選ぶ。要件定義書や設計書が渡されていれば、そこに書かれた条件（ロール、上限、状態、出力の形式）を観点に当てはめる。プロファイルの観点も同じように当てる。

最後に、ケースごとに粒度と期待結果を見る。この順にするのは、AC の網羅と観点の漏れのほうが、個々のケースの書き方より見落としたときの影響が大きいためである。

## 判断の基準

漏れは、AC や設計書の条件、または機能が持つ要素に当てはまる観点を確かめるケースがないことである。機能にない要素の観点は漏れにしない。一覧のない機能に 0 件のケースを求めるような指摘は、作業者の時間を使うだけで判断の助けにならない。`plan/strategy.md` で対象外と決めた範囲も漏れにしない。

過剰は、同じことを確かめるケースが重なっている、対象外と決めた範囲を確かめている、どの AC にも結び付かない、ライブラリやフレームワーク自体の挙動を確かめている、のどれかである。過剰の指摘には、残すケースと外せるケースを書く。

粒度は、1つのケースで判定が複数に分かれる、手順が粗くて実行する人によって操作が変わる、前提のデータやロールが書かれていない、逆に1つのことを確かめるのに不要なほど細かく分かれている、のどれかである。

不明確は、期待結果が観測できない（「正しく動作する」「エラーになる」「適切に表示される」）、値や文言が書かれていない、AC の本文そのものが観測できる結果になっていない、のどれかである。AC の不明確は AC-ID を対象にし、直す場所が `plan/acceptance.md` だと分かるようにする。

備考にある「⚠ 要確認」と「実装疑義」は、ケースを書いた側がすでに把握している論点である。それ自体は指摘にせず、件数をレビューの範囲の節に書き添える。ただし、要確認のまま優先度が高のケースの期待結果が決まっていないなど、実行の判定に響くものは不明確として指摘する。

コードしかない案件では、`推定仕様 RS-xxx` を出どころにする AC が `plan/inferred-spec.md` の表にある RS-ID を指しているかを確かめる。期待結果が推定仕様ではなく実装の挙動をそのまま写しているように見えるケースは、不明確として指摘する。要確認も実装疑義も1件もないケース群は、実装を正としている疑いがあるので、その旨を範囲の節に書く。

期待結果の正しい値を、この Skill が推測で決めない。設計書にも AC にも値がなければ、値を提案せず「値の根拠がない」と不明確で指摘する。

## プロファイルへの追記案

レビューで当てた観点のうち、その案件にしかないもの（特定のロールの組み合わせ、業務上の締め日、過去に出た不具合の箇所、帳票の独自の形式など）は、プロファイルの本文への追記案として返答の最後に書く。追記案は、作業者が `knowledge/<product>/profile.md` の本文に貼り付けて PR にできる Markdown の文章にする。この Skill はプロファイルを直接書き換えない。ナレッジの追記は、PR で他の人の確認を経てから入れる決まりである。

どの案件にも当てはまる一般的な観点は、追記案にしない。それは `references/review-checklist.md` が持つ観点で、案件ごとに書き写すとプロファイルが一般論で埋まる。追記案がなければ、この節は省く。

## よくある誤り

- 指摘ついでにケースのファイルを直す。採否の判断と記録が作業者に残らない
- `- AC:` の行の有無だけを見て網羅を判断し、ケースの中身が AC を確かめていないことを見落とす
- チェックリストの観点を機能の要素に関係なくすべて当て、当てはまらない漏れを大量に出す
- 書式の誤りばかりを指摘し、権限や上限のような事故につながる漏れを見落とす
- 「指摘なし」とだけ返し、どのファイルと AC を見たのかを書かない
- 期待結果の値を推測で補い、その値を正解として指摘に書く
- ケースを作ったセッションのままレビューする

## 完了条件

- `aidev qa profile check` がプロファイルに対して成功した
- 対象のすべての AC について、対応するケースがあるか、ないことを漏れとして指摘した
- 各指摘に、TC-ID か AC-ID、種類、重要度、根拠を示した理由がある
- 指摘がないときも、レビューの範囲（ファイル、TC-ID と AC-ID の範囲、当てた観点）を書いた
- 案件固有の観点があれば、プロファイルへの追記案として返した
- どのファイルも書き換えていない
