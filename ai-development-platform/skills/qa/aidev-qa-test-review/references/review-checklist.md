# レビューの観点

ケースの漏れ・過剰・粒度・不明確を見るときに使う一般的な観点である。どの案件にも当てはまるものだけを置き、案件固有の観点はプロファイルの本文に書く。

観点は、機能が持つ要素に当てはまるものだけを当てる。各節の最初に、どんな要素があれば当てるかを書いた。当てはまる観点について、確かめるケースがなければ漏れとして指摘する。要件定義書や AC に具体的な条件（ロール、上限、状態、形式）が書かれていれば、その条件の値でケースがあるかを見る。

## 1. AC との対応

すべての機能に当てる。

- `plan/acceptance.md` の AC のうち、対象の機能に関わるものすべてに、少なくとも1つのケースがある
- ケースの `- AC:` に書かれた AC-ID が `plan/acceptance.md` に存在する
- ケースの手順と期待結果が、AC の本文を実際に確かめている。AC-ID が書かれていても、確かめている内容が別のことなら漏れとして扱う
- 1つの AC に複数の条件（「A のとき B し、C を表示する」）があれば、条件ごとに確かめられている
- AC が「できる」と書いていれば「できない」側（拒否される条件）も、AC が「できない」と書いていれば許される側も確かめている。片側だけでは、条件の判定が常に同じ結果を返す不具合を見分けられない
- 設計書や要件定義書にあるが AC になっていない条件は、AC の漏れとして AC の追加を提案する（対象は近い AC の AC-ID か、機能名）

## 2. 権限と行レベルの所有者

ロールが複数ある、ログインが要る、利用者ごとにデータの持ち主が決まる、のどれかに当てる。見落とすと情報漏えいや改ざんにつながるため、優先して見る。

- ロールと操作の組み合わせごとに、許されるロールで成功し、許されないロールで拒否されるケースがある。許される側だけのケースは漏れである
- 画面にボタンやメニューが出ないことだけで拒否を確かめていない。URL の直接入力、API の直接呼び出し、フォームの値の書き換えで拒否されることを別のケースで確かめている
- 行レベルの所有者を確かめている。自分のデータは見られて操作でき、他の利用者（同じロールの別の担当者、別の組織）のデータを ID や URL の直接指定で開こうとすると拒否される。一覧や検索の結果に他人のデータが混ざらないことも見る
- 更新や削除のリクエストで、対象の ID や所有者の ID を他人のものに書き換えても通らない（主キーの差し替えによる乗っ取り）
- 未ログインで画面や API を開くと、ログイン画面に移るか拒否される。ログアウト後や、セッションの期限が切れた後の操作も同じ
- 拒否の期待結果が観測できる形で書かれている（どの画面に移るか、どのステータスやメッセージが出るか、データが変わっていないこと）
- ロールを変えた直後や、担当を外れた直後に、以前の権限が残らない（要件に担当の変更がある場合）

## 3. 0 件、1 件、上限

一覧、検索結果、明細、添付、選択肢、出力ファイルなど、件数のあるものに当てる。

- 0 件のときの表示（空の一覧の文言、ボタンの活性、出力ファイルの中身）がケースになっている
- 1 件のとき、ちょうど 1 ページに収まる件数、1 ページを 1 件超える件数でのページングがある（ページングがある場合）
- 件数や個数の上限があれば、上限ちょうどで成功し、上限を 1 超えると拒否されるか、決められた扱い（切り捨て、警告）になる
- 上限が文書にないのに、極端に多い件数で問題が出そうな機能（一括処理、出力）では、上限を確かめる AC がないことを AC の漏れとして指摘する
- 合計や件数の表示が、0 件や大量のときにも正しい

## 4. 必須と範囲

入力欄、API の入力、取り込むファイルに当てる。

- 必須の項目ごとに、未入力で拒否されるケースがある。空白だけの入力も見る
- 文字数や桁数に範囲があれば、下限の 1 つ下、下限、上限、上限の 1 つ上がある
- 数値に範囲があれば、範囲の端と、その外側、0、負の数、小数を入れたときの扱いがある
- 形式の決まった項目（メールアドレス、電話番号、郵便番号、日付、コード）で、形式に合わない値が拒否される
- 記号、全角と半角、絵文字や環境依存文字、前後の空白、改行、HTML やスクリプトとして解釈されうる文字列を入れたときの扱いがある（保存した値をそのまま表示する機能では特に）
- 画面の入力チェックだけでなく、API を直接呼んだときにも同じ範囲で拒否されるか（画面では弾くが API では通る、という層ごとの食い違い）
- 複数の項目の組み合わせの条件（開始日は終了日以前、など）があれば、条件を満たさない組み合わせのケースがある
- エラーのとき、どの項目の近くにどの文言が出るか、入力した値が残るか消えるかが期待結果に書かれている

## 5. 境界値と日時

数値の閾値、期日、期間、日時で動きが変わる機能に当てる。

- 閾値の前後と閾値ちょうどの3点がある。片側だけでは `>` と `>=` の取り違えを見分けられない
- 期日や締め日があれば、当日、前日、翌日がある。当日の扱い（含むか含まないか）が期待結果で分かる
- 月末、年末、うるう日、年度の切り替えなど、日付の繰り上がりで動きが変わりうる箇所
- 時刻を扱う機能では、日付の変わり目とタイムゾーンの扱い
- 金額や割合の計算では、端数の処理（切り捨て、四捨五入）と、計算の順序で結果が変わる場合

## 6. 二重送信と排他

登録、更新、削除、送信、決済、採番など、データを変える操作に当てる。

- 確定のボタンを素早く2回押しても、登録が1件だけになる
- 送信の後に再読み込みや戻るの操作をしても、二重に登録されない
- 2人の利用者が同じデータを同時に編集したとき、後から保存した側の扱い（拒否、上書きの警告、マージ）が決まっていて、ケースになっている
- 他の利用者が削除したデータを、開いたままの画面から更新しようとしたときの扱い
- 処理中にボタンが押せなくなる、処理中の表示が出るなど、要件にある挙動が確かめられている

## 7. ダイアログとキャンセル

確認のダイアログ、編集のモーダル、途中で抜けられる入力の流れに当てる。

- 確認のダイアログで「はい」を選ぶケースと、「キャンセル」を選ぶケースの両方がある
- キャンセルの後に、データが変わっていないこと、画面が元の状態に戻ることを期待結果に書いている。ダイアログが閉じることだけでは不十分である
- 閉じるボタンや Esc キー、ダイアログの外のクリックで閉じたときも、キャンセルと同じ扱いになるか
- 未保存の入力があるまま画面を離れようとしたときの警告（要件にある場合）
- ダイアログの文言に、対象の件数や名前が出る場合は、その値が正しいか

## 8. 状態の遷移

申請、承認、注文、公開など、データに状態がある機能に当てる。

- 許された遷移ごとに、遷移の後の状態と画面の表示を確かめるケースがある
- 許されない遷移（承認済みのものをもう一度承認する、取り消したものを編集する）が拒否されるケースがある。画面にボタンが出ないことだけでなく、直接のリクエストでも拒否されるか
- 状態によって表示や操作できる項目が変わる場合、状態ごとに確かめている
- 状態の変更に伴う副作用（通知、履歴、在庫や残高の増減）が期待結果にある
- 削除済みや無効にしたデータが、一覧、検索、選択肢、出力に出ない（または決められた形で出る）

## 9. エラー処理

外部のシステム、ファイル、ネットワーク、データベースを使う機能に当てる。

- 外部のシステムが失敗や時間切れを返したとき、利用者に何が表示されるかのケースがある
- 失敗した後に、データが中途半端に書かれていない（一部だけ登録される、在庫だけ減る、などがない）
- 失敗が握りつぶされず、利用者か呼び出し元に伝わる。ログに出るだけで処理が成功扱いにならない
- やり直したときに二重に処理されない
- 取り込むファイルが壊れている、形式が違う、空である、大きすぎるときの扱い

## 10. 出力とファイルの形式

CSV、Excel、PDF などの帳票やファイルの出力、メールの本文、外部への連携データに当てる。

- 見出しの行、列の順序と名前、件数が、要件や設計書の定義どおりかを期待結果に書いている
- 文字コード、区切り文字、改行コード、BOM の有無が要件にあれば確かめている
- データにカンマ、引用符、改行、先頭の 0、長い数字が含まれるときに、列がずれず値が変わらない
- 先頭が `=`、`+`、`-`、`@` の値を表計算ソフトで開いたとき、式として実行されない扱いになっているか（要件や設計に方針がある場合）
- 日付、金額、割合の表示形式（桁区切り、小数の桁、和暦と西暦）
- 0 件のときの出力（見出しだけのファイルか、出力しないか、メッセージか）
- ファイル名の付け方（日付や対象の名前を含むか）と、画面の絞り込みの条件が出力に反映されること
- PDF や印刷では、改ページ、長い文字列の折り返しやはみ出し、ページ番号

## 11. 初期状態と表示

画面を開いた直後の状態がある機能すべてに当てる。

- 画面を開いた直後の表示（初期値、既定の絞り込みや並び順、選択済みの項目、ボタンの活性と非活性）がケースになっている
- 編集の画面では、保存されている値が正しく初期表示される
- 既定の並び順と、並び替えたときの順序（同じ値が並ぶときの順を含む）
- 長い文字列や大きな数値の表示が崩れない（見た目の確認が要る場合は手動のケースとして）

## 12. 検索と絞り込み

検索の条件や絞り込みがある機能に当てる。

- 条件ごとの一致の仕方（完全一致、部分一致、前方一致）と、大文字と小文字、全角と半角の扱い
- 複数の条件を組み合わせたとき（かつ、または）の結果
- 該当なしの表示
- 条件を消したときに、全件の表示に戻る
- 検索の結果にも権限と所有者の絞り込みが効いている（2 節）

## 13. 通知、履歴、監査

要件にメールや通知、操作の履歴、監査ログがある機能に当てる。

- 通知が届く相手、届かない相手、本文に入る値がケースになっている
- 失敗した操作や、キャンセルした操作で通知や履歴が出ない
- 履歴に残る項目（誰が、いつ、何を）が要件どおり

## 14. デスクトップのクライアント

Windows などのネイティブな GUI の部品を使うクライアントに当てる。要件が対象にしている項目だけを見る。

- キーボードだけで操作できるか、Tab キーで移る順序、画面を開いたときとエラーの後のフォーカスの位置
- 処理の途中でウィンドウを閉じる、アプリを終了したときの扱い。データが中途半端に残らないか、確認が出るか
- 保存のダイアログで、既存のファイルへの上書きの確認、キャンセル、書き込み権限のない保存先を選んだときの扱い
- 日本語の入力（IME での変換中の確定や、変換中のキー操作）で値が欠けたり二重になったりしない
- ウィンドウの大きさの変更、表示の拡大率（DPI）、複数のモニターでの表示の崩れ（要件にある場合。見た目の確認は手動のケースとして）
- 設定や画面の状態（ウィンドウの位置、最後に使ったフォルダー、絞り込みの条件）が、再起動の後に要件どおり残るか、初期化されるか

## 15. 改修案件

既存のシステムを変更する案件に当てる。

- 変更した機能とデータや部品（共通の画面部品、共通の処理、同じテーブル）を共有する、変更していない機能に回帰のケースがある。変更した箇所のケースだけでは、共有している部分への影響を見落とす
- 変更の前から動いていた正常系が、変更の後も同じ結果になることを確かめるケースがある
- 性能（応答時間）、アクセシビリティ、対応するブラウザや OS など、非機能の AC があれば、それぞれにケースがある。非機能の AC にケースがなければ漏れとして指摘する

## 16. 期待結果が観測できるか

すべてのケースに当てる。

- 「正しく動作する」「エラーになる」「適切に表示される」「問題がない」のような、実行する人によって判定が分かれる書き方をしていない
- 文言、表示する場所、値、件数、移る先の画面が具体的に書かれている
- データベースやログで確かめる期待結果には、どこの何を見るかが書かれている
- 「変わらないこと」を確かめるケースでは、何が変わらないかを比べる前後の値が分かる
- 期待結果の値に根拠（AC、設計書、推定仕様）がある。実装を動かして得た値をそのまま書いた疑いがあれば不明確として指摘する

## 17. 粒度と再現性

すべてのケースに当てる。

- 1つのケースで判定が1つになっている。期待結果に独立した確認が並び、一部だけ失敗することがありうるなら分割を提案する
- 手順の最初に前提（ロール、データの状態、画面の位置）がある。前提がないと、実行する人が前のケースの結果に頼ることになる
- ケースの実行順に依存していない。依存するなら、その旨が書かれている
- テストデータが特定できる（どのデータを使うか、どう準備するか）。パスワードの値ではなく、プロファイルの secrets のキー名で示している
- 逆に、同じ判定を手順の細部だけ変えて何件にも分けている場合は過剰として指摘する
- 手動にしたケースに手動の理由がある。繰り返し流す回帰や権限のケースが手動になっていれば、自動にできないかを指摘する

## 18. 過剰

すべてのケースに当てる。

- 同じ AC の同じ条件を、同じ入力の種類で確かめているケースが重なっている
- `plan/strategy.md` で対象外とした範囲を確かめている
- どの AC にも結び付かないケースがある（AC の追加で済むのか、ケースが不要なのかを分けて書く）
- ライブラリやフレームワーク、ブラウザ自体の挙動を確かめていて、案件のコードや設定の判断が入っていない
