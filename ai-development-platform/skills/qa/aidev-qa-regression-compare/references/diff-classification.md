# 差異の突き合わせ方と分類、compare.md の書き方

基準と比較先の証跡を突き合わせるとき、見つかった差異を分類するとき、`runs/<比較先の run>/compare.md` を書くときに読む。

## 突き合わせの単位

証跡は aidev-qa-characterization の決まりで `runs/<YYYYMMDD>-<run-id>/evidence/<TC-ID>/<checkpoint>.*` に置かれている。基準と比較先で、TC-ID と checkpoint の名前が同じものを対応付ける。環境の区別は run で行い、TC-ID に環境の接頭辞は付いていない。

テストのコードが環境で違う、テストの名前が変わった、という理由で TC-ID がそろわないときは、ケースの中身で対応を決める。

- ケースの手順、ロール、表示モード、データの条件が同じなら、同じケースとして並べる。ファイル名や撮影した人の付けた名前は手がかりにとどめる
- 名前が変わっただけで同じ確かめ方なのか判断がつかないときは、推測で並べず作業者に確かめる
- 比較先で新しく足したケースや、片方の環境でしか実行しなかったケースは、照合できなかったケースとして理由を書く。もう片方の結果を作らない

## 突き合わせる前に証跡の完全性を数える

両方の側に証跡がないことは、差がないことと見分けがつかない。比較のスクリプトは、ないファイル同士を比べて「差なし」と返しかねない。突き合わせる前に、基準と比較先の run のそれぞれについて、画面マニフェストを分母にして証跡を数える。数え方は aidev-qa-characterization の証跡の資料（完全性の確認）と同じで、ケースごと、checkpoint ごとに見る。

- `operations`、`reports`、`acceptedRisks` の各ケースに、ケースのディレクトリと、テストが撮るはずの checkpoint のスクリーンショット、表示値、API の応答がある
- `reports` のケースに帳票のファイルがある
- `apis` の届く呼び出し箇所が、`expectAt` の回数どおりに記録されている

どちらかの側で欠けているものは、照合の前提の崩れである（下の分類の基準の1）。原因を直して流し直すか、そのケースを照合できなかったケースにする。片方または両方で欠けたまま一致に数えない。数えた結果の表は compare.md に書く。

## 3点の突き合わせ方

### 画面表示

画面に出た値を構造化したもの（`<checkpoint>.values.json`）を項目ごとに比べる。スクリーンショットは差の確かめと見せ方に使い、値の比較の代わりにしない。

一覧と詳細は別々に照合する。旧版では一覧のデータをそのまま詳細に使い回していても、新版で一覧は「列に出す項目だけ」、詳細は「全項目」と取り方を分けると、一覧の側だけで項目が落ちることがある。このとき詳細の照合は一致するので、詳細だけを見ていると欠落に気づけない。

- 一覧は、表示されたすべての行と列を、行ごとに突き合わせる。人が選んだ列だけを比べると、選ばなかった列の欠落は見つからない
- 行の対応は、その一覧の行を一意に決める列（ID など）で取る。分からなければ画面マニフェストか作業者に確かめる
- 照合に使う行は、空になりやすい列（自由記述、補足）にも値が入っている行にする。値の入った行が1件もない列は「未検証」と書く
- テストが表示させなかった範囲（2ページ目以降、開いていないタブ、開いていないダイアログ）は照合していない。「全列を照合した」と言えるのは、表示させた範囲についてだけである
- フラグをラベルに直して表示する列のように期待値を作りにくい列は、変換の処理をテストに書き直さず、基準の画面に出た文字列をそのまま基準にして比べる

### 内部データ（API の応答）

正規化した応答の本文を、JSON の構造で項目ごとに突き合わせる。差は次の3つに分けて出す。

- 項目の増減（比較先で消えた項目、増えた項目）
- 値の違い
- 件数の違い（配列の要素の数）

応答の項目が減るのは、内部を作り直す改修でよく狙われる変化である（画面に出ない項目を返さない、など）。画面表示の照合だけではこれは見えないので、内部データの照合を省かない。HTTP 200 でも本文にエラーが入っている応答は、値の比較の前に要確認の候補にする。

API を呼ばない画面では、画面に出た値を構造化したものが内部データの代わりになる。その場合は画面表示の照合と同じものを見ていることを compare.md に書く。

### 帳票（CSV・PDF）

帳票はファイルをバイト単位や見た目で丸ごと比べない。生成日時や出力の部品の変更で大量の差が出る一方で、見た目がそろっていることに安心して、値の入れ替わりや欠落を見逃す。ファイルの種類ごとに、中のデータとして突き合わせる。

| 種類 | 突き合わせ方 | 値とは別に出す差異 |
|---|---|---|
| CSV | 行を読み、帳票の行を一意に決めるキーの列（例 注文番号と明細の番号）で行を対応付け、キー以外の列の値を比べる。列の名前と順序、行数も比べる | 並び順、文字コード、BOM、改行、区切りの文字 |
| PDF | 文字を取り出し、項目の名前と値を比べる。明細の表を含む帳票は、取り出した文字を行として読み、CSV と同じようにキーで対応付ける | ページ数、欠けや重なりなどの見た目の崩れ |

キーの列が分からなければ、画面マニフェストの `reports` か作業者に確かめる。推測で選んだキーでは、行の対応を誤って差を出したり消したりする。

値とは別に出す差異は、値の差と混ぜずに1件ずつ記録し、値の差と同じ基準で分類する。並び順を定めた記述が要件や設計にあれば、それに照らして分ける。記述がなければ要確認にして、並び順を問わないかを作業者に確かめる。問わないと決まったら、その決定を compare.md に書く。文字コードや BOM の変化は、利用者が表計算ソフトで開くと文字化けすることがあるので、黙って無視しない。PDF のフォントや余白の違いは値の照合の対象にしないが、開いて見て、利用者に影響する崩れがあれば差異にする。

機械的に本質の差か表現の差かを決められないときは、CSV のセルの値や PDF の取り出した文字の該当箇所を直接見比べ、判断の理由を書く。この確認を画面のスクリーンショットで代えない。画面と帳票は別の経路で作られている。

## 正規化

正規化は、画面マニフェストの `normalize` にある規則だけを、基準と比較先の両方に同じように当てる。規則は項目を名指しし、形式を確かめてから置き換えるものである。形式の違う値（日付の書式が変わった、など）は置き換えられずに差として残り、それを分類する。

正規化した値が一致しても、元の値が正しいとは限らない。形式は合っていて値が誤っている場合（日付が1日ずれた、時差の分だけ時刻がずれた、ID の採番の系列が変わった）は、正規化で消えてしまう。そこで、正規化の対象の項目は、元の値にも規則ごとに決めた妥当性の確かめをかける。確かめ方は、`normalize` の `rule` に置き換えの規則と一緒に書く（例「その run の実行の時間帯に入る」「その run の実行日と同じ日」「基準と同じ接頭辞と型の ID」）。確かめに通らない元の値は、正規化した値が一致していても差異として出す。正規化の対象の項目が関わる差異では、正規化した値と元の値の両方を示す（個人情報の扱いは後の「compare.md の形式」による）。規則に妥当性の確かめが書かれていなければ、照合の前に作業者と決めて書き足す。

照合の途中で、差を消すために規則を足したり、行や表の全体を対象にしたりしない。比較先にだけ実行ごとに変わる値が出たときは、比較先で同じケースを2回記録して毎回変わることを確かめてから、項目を名指しした規則をマニフェストに足す。足した規則と、2回の記録で確かめたことを compare.md に書く。

## 分類の基準

差異ごとに、上から順に当てはめて分類する。

1. 照合の前提が崩れている差異は、分類の前に原因を取り除く。ログイン画面やエラー画面を撮っていた、比較先で応答が捕まっていなかった、片方のデータの条件が違っていた、どちらかの側で証跡が欠けていた（完全性の確認）、基準の run に NG があった、という場合である。基準の NG は、基準の環境が記録した時から変わったか、異常を含んでいることを示すので、原因を確かめて基準を流し直すか、そのケースを照合できなかったケースにする。テストやデータを直して流し直し、それでも差が残れば次へ進む。前提が崩れたまま分類しない
2. 片方または両方で応答が空、または一覧や帳票が0件なら、下の「裏取り」で、データがあるのかを検証の対象とは別の経路で確かめる。データがあるのに比較先で出ないなら要確認。比較先の環境にそもそもデータがないと確かめられたら、データを用意して流し直す。流し直せないときは照合できなかったケースにし、一致に数えない
3. 許可と拒否の差（片方は表示され、片方は 403 や拒否のメッセージ）なら、要件や設計の許可の表と突き合わせる。比較先が表のとおりなら意図した差分、表と合わなければ要確認
4. 項目の増減や値の違いなら、比較先の挙動を定めた記述を探す。記述があり、比較先の値がその記述どおりなら意図した差分。そうでなければ要確認
5. 項目が減った差異は、減らすことを定めた記述があり、かつその項目が画面表示にも帳票にも出ていないこと（画面表示と帳票の照合で差がないこと）を確かめてから意図した差分にする。画面や帳票にも差が出ているなら要確認
6. 判断に迷うものは要確認にする

### 根拠になるもの、ならないもの

意図した差分の根拠になるのは、`plan/acceptance.md` の AC、要件定義書、設計書、承認された変更の一覧のうち、比較先の挙動をはっきり定めた記述である。

- 根拠には、文書の名前、箇所（AC-ID、節の番号）、記述の要旨を書く。どの値がどう記述に合っているかも書く（例「AC-031 は一覧を注文日の新しい順と定める。比較先は注文日の降順に並び、基準は注文番号の昇順」）
- 同じ話題に触れているだけの記述は根拠にならない（並び順の記述があっても、どの順かが比較先と違えば根拠ではない）
- 記述が基準の側の挙動を定めているなら、比較先の変化は要確認である（例 AC が金額の書き方を定めていて、基準はそのとおりで、比較先が違う書き方になった）
- 開発者の口頭の説明、コミットのメッセージ、コードのコメントは、それだけでは根拠にならない。文書に記述がないときは要確認にして、開発者と作業者に確かめる。確かめた結果、文書や AC が直されたら、その直された箇所を根拠にする
- 一般的な設計の方針（「一覧は画面に出す項目だけを返す」など）を根拠にするときは、その方針がその画面のその項目に当てはまることを書く

### 裏取り（空の応答と0件）

空の応答や0件は、実装が壊れた場合とデータがない場合の両方がありうる。どちらかに決め打ちせず、検証の対象とは別の経路で同じデータを読んで確かめる。

| 経路 | 内容 |
|---|---|
| データベース | 対象の環境のデータベースで、同じ条件の行の有無を見る |
| 別の実装の経路 | 比較先の環境に残っている旧の API など、今回の改修のコードを通らない経路で同じデータを読む |
| 基準の環境の同じ操作 | 基準でも同じ項目が空なら、比較先の絞り込みによる欠落ではない |
| スキーマと画面のソース | 件数ではなく、項目が消えたか形が変わったかの裏取りに使う。値が画面の側で組み立てられていないかも見る |

何で確かめたかを差異ごとに書く。データベースを見ていないのに「データベースで確かめた」と書かない。後で読む人が根拠の強さを取り違える。どの経路も使えなければ、要確認（裏取りの手段なし）にして開発者に戻す。

## compare.md の形式

`runs/<比較先の run>/compare.md` に置く。証跡が `local` や `external` の案件でも、compare.md は QA リポジトリに置く。そのため、資格情報と個人情報の値は書かない。

個人情報や機微な項目（氏名、住所、電話番号、メールアドレス、利用者の番号、自由記述の本文など）の差異は、値を写さずに差の性質で書く。「値あり→空」「形式 YYYY/MM/DD→YYYY-MM-DD」「11 桁の数字→10 桁」「文字列→数値」のように書き、値を確かめる場所として証跡のファイルと項目を示す。比較の HTML のマニフェストの `note` も顧客に渡るので、同じ書き方にする。個人情報でない値（金額、件数、コード、日付の形式）は、証跡からそのまま写してよい。

```markdown
# 照合結果 20261120-new-orders

- 比較の種類: 旧版と新版
- 基準: runs/20261120-old-orders（環境 old、版 1.8.2、画面の右下の表示）
- 比較先: runs/20261120-new-orders（環境 new、版 2.0.0、画面の右下の表示）
- テストのコード: QA リポジトリのコミット 1a2b3c4（両方の run で同じ）
- 正規化: automation/web/manifests/orders-list.json の normalize。照合の途中で足した規則はなし
- 照合日時: 2026-11-20 15:10

## ケースごとの照合

| TC-ID | 画面表示 | 内部データ | 帳票 | 判定 |
|---|---|---|---|---|
| TC-orders-001 | 一致 | D-001、D-003 | - | 要確認 |
| TC-orders-002 | D-004 | 一致 | - | 要確認 |
| TC-orders-020 | 一致 | 一致 | D-002 | 要確認 |
| TC-orders-030 | - | - | - | 照合できない |

## 差異

| ID | TC-ID | checkpoint | 対象 | 項目 | 基準 | 比較先 | 分類 | 根拠・裏取り |
|---|---|---|---|---|---|---|---|---|
| D-001 | TC-orders-001 | 01-initial | 内部データ | API-01 の items[].customerAddress | あり | なし（項目が消えた） | 意図した差分 | 基本設計書 5.2「一覧の API は画面の列に出す項目だけを返す」。住所は一覧の列になく、画面表示と帳票の照合でも差はない |
| D-002 | TC-orders-020 | 01-export | 帳票 | CSV の列「金額」の書き方 | 12000 | 12,000 | 要確認 | AC-040 は「金額は桁区切りのない整数」と定める。基準の側を支持している |
| D-003 | TC-orders-001 | 01-initial | 内部データ | API-01 の items[].orderedAt（正規化の対象） | 正規化後 <datetime>、元の値は実行の時間帯に入る | 正規化後 <datetime>、元の値は実行の時間帯より 9 時間前 | 要確認 | 正規化した値は一致。元の値が normalize の rule の妥当性の確かめに通らない。時差の扱いの変化を疑う。値は両方の 01-initial.API-01.json |
| D-004 | TC-orders-002 | 02-detail | 画面表示 | 詳細の「届け先の電話番号」 | 値あり（11 桁の数字） | 空 | 要確認 | 個人情報のため値は書かない。値は両方の 02-detail.values.json。項目を減らす記述は設計書にない |

## 要確認の詳細

  2. 注文の一覧で CSV 出力を押す

- 根拠を探した範囲: plan/acceptance.md、基本設計書 6章。書き方の変更の記述はない
- 裏取り: 不要（値の書き方の差で、データの有無の問題ではない）
- Issue: （後の段階で追加する予定の aidev-qa-bug-ticket が書く）

## 照合できなかったケース

### TC-orders-030
- 理由: 比較先の環境に絞り込みの前提のデータがなく、比較先で実行できなかった（比較先の result.md では実行不能）
- 照合できるようにする手段: 比較先の環境に同じ条件のデータを用意して流し直す（データの投入には承認が要る）

- なし
```

例の値（環境名、版、TC-ID、AC、環境変数の名前）は説明のためのもので、実際の値は案件のプロファイル、ケース、実行の記録から書く。

各節の書き方は次のとおり。

- 証跡の完全性の表は、基準と比較先の run ごとに、照合の対象のケースを並べる。欠落があるケースは照合できなかったケースか、流し直した結果を書く
- ケースごとの照合の表は、照合の対象のすべての TC-ID を1行ずつ並べる。3点のそれぞれに、一致、差異の ID、`-`（その点がないケース）のどれかを書く。判定は、要確認を含めば要確認、意図した差分を含めば意図した差分、すべて一致なら一致、照合できなければ「照合できない」にする
- 差異の表は、差異1件を1行にする。1つのケースで複数の項目が違えば、項目ごとに行を分ける。まとめると、一部だけが意図した差分であることが見えなくなる。基準と比較先の値は、個人情報や機微な項目でなければ証跡からそのまま写す。個人情報や機微な項目は差の性質で書き、証跡のファイルを示す。正規化の対象の項目は、正規化した値と、元の値の妥当性の確かめの結果を書く
- 意図した差分の行の「根拠・裏取り」には、文書と箇所と要旨、比較先の値がそれに合うことを書く。空のままにしない
- 要確認の詳細は、起票する人がこの節だけを読んで Issue を書けるようにする。TC-ID と AC、ケースの手順に実際のロールとデータを足した再現手順（アカウントは環境変数の名前で示す）、基準と比較先の値（個人情報や機微な項目は差の性質）と証跡のファイル、根拠を探した範囲、裏取りの結果を書く。Issue の行は空けておく
- 照合できなかったケースには、理由と、照合できるようにする手段を書く。手段は提案にとどめる
