# 比較の HTML のマニフェスト

基準と比較先の証跡を横に並べた HTML を `aidev qa compare-report` で作るときに読む。コマンドは、ここに書いたマニフェスト（JSON）を読んで HTML を書くだけで、ケースの対応付けや OK と NG の判定はしない。どのケースを同じ行に並べるか、各列の状態を何にするかは、マニフェストを書く側が compare.md から決める。

## 置き場所

マニフェストから参照する画像は、マニフェストのあるディレクトリの中になければならない（後の「制約」）。基準と比較先の証跡は別の run のディレクトリにあるので、マニフェストは両方を含む `runs/` に置く。

| もの | 置き場所 |
|---|---|
| 照合の結果（正本） | QA リポジトリの `runs/<比較先の run>/compare.md` |
| マニフェスト | `<証跡の根>/runs/<比較先の run>.compare.json` |
| HTML | `<証跡の根>/reports/<比較先の run>-compare/compare.html`（`--link` なら同じディレクトリに `assets/` ができる） |

`<証跡の根>` は、プロファイルの `evidence.method` が `lfs` なら QA リポジトリのルート、`local` か `external` なら証跡の保存先（`<保存先>/runs/...` と同じ構成の根）である。HTML は証跡の画像を埋め込むか写すので、証跡と同じ扱いにする。`local` や `external` の案件で、HTML や `assets/` を QA リポジトリに置かない。個人情報が映る画面を避けるためにその方式を選んでいるからである。HTML はマニフェストと証跡から作り直せるので、コミットするかは作業者が決める。

コマンドは `<証跡の根>` をカレントディレクトリにして実行する。MANIFEST と OUT は、カレントディレクトリからの相対パスでしか指定できない。

```text
aidev qa compare-report runs/20261120-new-orders.compare.json reports/20261120-new-orders-compare/compare.html
```

画像の枚数が多く、埋め込みの HTML が大きくなりすぎるときは、末尾に `--link` を付ける。画像は OUT と同じディレクトリの `assets/<マニフェストからの相対パス>` に写され、HTML はそれを相対パスで参照する。このときは HTML 単体ではなく、ディレクトリごと渡す。

成功すると、標準出力に JSON で `out`、`screens`（画面の数）、`testCases`（ケースの数）、`images`（画像の数）が出る。画像の数が証跡の数と合うかを見る。

## 形式

```json
{
  "title": "注文の画面 旧版と新版の照合",
  "customer": "〇〇株式会社 御中",
  "generatedAt": "2026-11-20",
  "rounds": ["old（旧版 1.8.2）", "new（新版 2.0.0）"],
  "screens": [
    {
      "screen": "注文の一覧",
      "testCases": [
        {
          "name": "TC-orders-001 一般のロールで一覧の初期表示",
          "note": "AC-030。判定: 要確認",
          "results": [
            { "round": 0, "status": "OK", "screenshots": [
              "20261120-old-orders/evidence/TC-orders-001/01-initial.png",
              "20261120-old-orders/evidence/TC-orders-001/02-page2.png" ] },
            { "round": 1, "status": "NG", "note": "意図した差分 D-001（基本設計書 5.2）。要確認 D-003 注文日時の元の値が実行の時間帯より 9 時間前", "screenshots": [
              "20261120-new-orders/evidence/TC-orders-001/01-initial.png",
              "20261120-new-orders/evidence/TC-orders-001/02-page2.png" ] }
          ]
        },
        {
          "name": "TC-orders-020 管理者のロールで CSV を出力する",
          "note": "AC-040。判定: 要確認",
          "results": [
            { "round": 0, "status": "OK", "screenshot": "20261120-old-orders/evidence/TC-orders-020/01-export.png" },
            { "round": 1, "status": "NG", "note": "要確認 D-002 CSV の金額に桁区切りが入った", "screenshot": "20261120-new-orders/evidence/TC-orders-020/01-export.png" }
          ]
        },
        {
          "name": "TC-orders-030 一覧の絞り込み",
          "note": "照合できない（比較先の結果は実行不能）: 比較先の環境に絞り込みの前提のデータがなく、比較先で実行できなかった",
          "results": [
            { "round": 0, "status": "OK", "screenshot": "20261120-old-orders/evidence/TC-orders-030/01-filtered.png" }
          ]
        }
      ]
    }
  ]
}
```

この例のマニフェストは `runs/20261120-new-orders.compare.json` にあるので、画像のパスは `runs/` からの相対パスになる。例の値は説明のためのもので、実際の値は compare.md と証跡から書く。TC-orders-030 は照合できなかったケースの書き方の例で、比較先の列は要素を入れずに「対象外」と出す。

## 項目

最上位の項目は次のとおり。

- `title`（必須、文字列）：報告の題名。作業者に確かめる
- `customer`（任意、文字列）：提出先。表示しない取り決めがあれば省く
- `generatedAt`（任意、文字列）：作成日
- `rounds`（必須、1件以上の文字列の配列）：列の見出し。`results[].round` はこの配列の位置（0 始まり）を指す。名前は歴史的なもので、時系列の回を意味しない

`screens` は画面ごとのまとまりの配列である。

- `screen`（必須、文字列）：画面の名前。画面マニフェストの `title` を使う
- `testCases`（必須、配列）：その画面のケース。1件が HTML の1行になる
- `testCases[].name`（必須、文字列）：`<TC-ID> <ケース名>` にする。TC-ID を先頭に置くと、compare.md と result.md から引ける
- `testCases[].note`（任意、文字列）：ケースの補足。AC、ケースの判定、照合できなかった理由を書く
- `testCases[].results`（必須、配列）：列ごとの結果。その列で実行していないケースと、照合できなかったケースの比較先の列は、要素を入れない。HTML には「対象外」と出る

`results` の要素は次のとおり。

- `round`（必須、整数）：0 以上、`rounds` の件数未満
- `status`（必須、文字列）：`OK` か `NG`。大文字と小文字は問わず、`pass`、`passed` は OK、`fail`、`failed` は NG と同じに扱われる。それ以外の値はすべて「未実施」と表示されるので使わない
- `note`（任意、文字列）：その列の補足。差異の ID と分類、根拠の箇所を書く。`note` は顧客に渡るので、個人情報や機微な項目の値は写さず、差の性質（「値あり→空」「形式 YYYY/MM/DD→YYYY-MM-DD」など）で書く。書き方は `diff-classification.md` の compare.md の形式と同じである
- `screenshot`（任意、文字列）か `screenshots`（任意、文字列の配列）：その列のそのケースのスクリーンショット。両方を書くと `screenshots` が使われる。どちらもなければ「スクリーンショットなし」と出る

## 状態の決め方

状態は compare.md と各 run の result.md から転記する。テストの生の成否（Playwright の passed と failed）をそのまま使わない。比較先では、記録した期待値との違いでテストが失敗していても、それが意図した差分なら OK である。

| 列 | 状態 |
|---|---|
| 基準 | 基準の run の result.md の結果で、照合に進んだケースは OK だけになる（基準の NG は照合の前提の崩れとして、分類の前に片付けている）。実行不能は要素を入れず、ケースの `note` に理由を書く |
| 比較先 | compare.md のケースの判定。一致と意図した差分は OK、要確認は NG。照合できなかったケース（比較先の result.md では実行不能）は要素を入れず、ケースの `note` に「照合できない」と理由を書く。比較先の画像があっても入れない。入れると状態の札が付き、照合したように見える |

生の成否と状態が食い違うケース（テストは失敗したが意図した差分で OK にした、など）は、`note` に差異の ID と根拠を書く。黙って上書きしたように見せない。

## 列の作り方

- 旧版と新版の比較では、環境ごとに1列にする。列の見出しは `<環境名>（<用途と版>）` にし、プロファイルの `environments` の name と purpose を使う。3つ以上の環境を並べてもよい
- 設定段階の前後の比較では、1つの HTML を「基準｜比較先の1段階」の2列にする。段階が複数あれば段階ごとに HTML を分け、段階を1枚に横に並べない。並べると修正の経過を見せる時系列の比較になる。列の見出しは `<環境名> <段階のラベル>（<段階の内容>）` にする
- 修正のたびに流し直した結果を列として並べない。各列は、その環境の最終の run だけを使う

## 画像

- 1つのケースの1つの列に、その run で撮ったスクリーンショットをすべて、checkpoint の順に入れる。NG のケースの画像も省かない
- 片方の列にだけ画像がない場合は、証跡の欠落を疑い、照合の前に戻って原因を確かめる

## 制約

コマンドは次の条件を満たさないと、HTML を書かずにエラーで終わる。

- MANIFEST と OUT は、カレントディレクトリからの相対パスにする。絶対パス、`..`、`:` を含むパス、途中にシンボリックリンクがあるパスは使えない
- マニフェストは 1 MiB 以下の通常ファイルの JSON にする
- OUT は `.html` で終わる名前にし、MANIFEST と同じパスにしない。OUT にすでにファイルがあると上書きされるので、新しいパスにするか、上書きしてよいことを確かめる
- 画像のパスは、マニフェストのあるディレクトリからの相対パスで、そのディレクトリの中にあるものに限る。`..` で外に出られない
- 画像は png、jpg、jpeg、gif、webp の通常ファイルで、1枚 20 MiB 以下にする。svg や PDF は使えない
- `--link` のとき、`assets/` の同じ場所に内容の違うファイルがあると止まる。前の HTML の `assets/` が残っていれば、別のディレクトリに出すか、作業者に確かめてから片付ける

## 渡す前に見る

作った HTML をブラウザで開き、次を確かめる。

- 画面とケースが意図どおりにまとまり、同じケースが列をまたいで同じ行に並んでいる
- 各列の状態が compare.md と result.md に合っている。要確認のケースが OK に見えていない
- 状態の札と冒頭の件数に「未実施」が出ていない（`status` の綴りの誤り）。札が「対象外」の列（本文は「このラウンドでは未実施」）は、実際に実行していない列か、照合できなかった（実行不能の）列だけで、どちらもケースの `note` に理由がある
- スクリーンショットに、資格情報、トークン、テスト用アカウントの個人情報が写っていない
- ファイルの大きさが渡し方（メールの添付など）に合っている。大きすぎれば `--link` で作り直す
