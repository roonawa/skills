# 旧版と新版の照合

## Overview

画面の見た目や操作を変えずに内部を作り直す改修では、「旧版と新版で同じ操作をして、同じ結果が返る」ことを機械的に確かめるのが、もっとも確かな回帰の確認になる。この Skill は、同じテストのコードを基準の環境（旧版、または設定段階を入れる前）と比較先の環境（新版、または段階を入れた後）に流し、画面表示、内部データ（API の応答）、帳票の3点を突き合わせて、見つかった差異を1件ずつ分類する。

照合を画面表示だけで済ませない。内部を作り直す改修で一番変わりやすいのは、画面に出ない応答の中身（余計な項目の混入、必要な項目の欠落）である。帳票も画面とは別の経路で作られることが多い。

差異は出るものとして扱い、ゼロを完了の条件にしない。完了の条件は、すべての差異が次の3つのどれかに決まり、その理由が書かれていることである。

- 一致：正規化の規則を同じように当てたうえで、基準と比較先が同じ
- 意図した差分：要件定義書、AC、設計書に、比較先の挙動を定めた記述があり、比較先の値がその記述どおりである。差異ごとに根拠の文書と箇所を書く
- 要確認：上のどちらでもない。根拠が見つからない、根拠と比較先の値が合わない、根拠が基準の側を支持している、判断に迷う

都合よく「意図した差分」に倒すと、改修で入った不具合を仕様に見せてしまう。迷ったら要確認にする。

## When to Use

- 改修や API の作り直しが終わり、リリースの前に旧版との回帰を確かめる
- 同じ環境で、設定や機能の段階（セキュリティの強化など）を入れる前と後に同じテストを流し、影響を確かめる
- 2つの環境の証跡を画面とテストケースの単位で横に並べた、顧客に出す HTML を作る

使わない場面は次のとおり。

- 照合に使う特性テスト（画面マニフェストとテストのコード）がまだないときは、先に aidev-qa-characterization で基準の環境の挙動を記録する
- ロールごとのログイン済みのセッションは aidev-qa-login-session で作る。この Skill はそれを環境ごとに使う側である
- 仕様（期待結果）を正として1つの環境でケースを流すときは aidev-qa-test-run を使う
- ロールと操作の可否、担当内と担当外の区別を網羅的に確かめるときは aidev-qa-authz-test を使う。この Skill は、照合で見えた許可と拒否の差を分類するところまでを扱う
- 要確認の差異からの Issue の起票は aidev-qa-bug-ticket を使う。Gitea に Issue を作る
- 修正のたびに流し直した結果を1回目、2回目と時系列に並べて経過を見せることはしない。残すのは最終の結果だけである

## 入力と出力

入力は次のとおり。

- 案件プロファイル `knowledge/<product>/profile.md`。`environments`（照合する環境。2つ以上）と `evidence`（証跡の保存方式）を使う。あれば `roles`、`login`、`stack`、`test_commands` と、本文の到達手順、テストデータの準備方法、落とし穴も読む
- 照合の対象の画面マニフェスト `automation/web/manifests/<画面>.json` と、そのテスト `automation/web/tests/*-char.spec.ts`（aidev-qa-characterization が作ったもの）。デスクトップの画面は aidev-qa-desktop-gui のテスト
- 根拠を探す文書。`plan/acceptance.md`、要件定義書、設計書、承認された変更の一覧。作業者が場所を示す
- すでに流した基準の環境の run があれば、その `runs/<YYYYMMDD>-<run-id>/`

出力は次のとおり。

- 環境ごとの run。`runs/<YYYYMMDD>-<run-id>/result.md` と `evidence/<TC-ID>/`。形は aidev-qa-characterization と aidev-qa-test-run のものと同じ
- 照合の結果 `runs/<比較先の run>/compare.md`。差異ごとの分類と根拠の正本で、形式は `references/diff-classification.md` に書いた。compare.md は証跡の保存方式にかかわらず QA リポジトリに置くので、個人情報や機微な項目の値は写さず、差の性質（「値あり→空」「形式の変化」など）と証跡のファイルで示す
- 環境ごとに名前が変わった API と帳票の捕捉の条件（画面マニフェストの `matchByEnvironment`）
- 求められたとき、比較の HTML。マニフェストを書いて `aidev qa compare-report` で作る。マニフェストの形式と置き場所は `references/compare-manifest.md` に書いた
- 作業者への返答。要確認を先頭に、分類ごとの件数、照合できなかったケースと理由、HTML の場所を書く

## 進め方

### 1. プロファイルと照合の条件を確かめる

最初に案件プロファイルを読み、`aidev qa profile check knowledge/<product>/profile.md --skill aidev-qa-regression-compare` で検査する。この Skill では `environments` が2つ以上要る。終了コードが 1 ならエラーの内容を作業者に伝えて直してもらう。

次に、照合の条件を決める。プロファイルから決まらないものは作業者に確かめ、推測で埋めない。

- 比較の種類。旧版と新版か、同じ環境の設定段階の前後か
- どの環境（`environments` の name）が基準で、どれが比較先か。段階の比較なら、段階のラベルと内容
- 基準と比較先のそれぞれの版を何で特定するか。基準に別の版（古い版や開発中の版）を流すと、照合そのものが意味を失う
- 照合する画面と TC-ID の範囲
- 意図した差分の根拠を探す文書の場所

### 2. テストと捕捉の条件を両方の環境に合わせる

照合は、同じコミットのテストのコードを両方の環境に流して行う。環境は `QA_ENV`（プロファイルの環境名）と `QA_BASE_URL` で切り替え、テストのコードに環境ごとの分岐を書かない。

比較先で API の名前や帳票のダウンロードの URL が変わっていることがある。比較先に流す前に、旧と新の名前の対応を開発者に聞き、画面マニフェストの `matchByEnvironment` に比較先の環境名で書く。`match` を書き換えると、基準の環境に流したときに捕まらなくなる。分からない名前を推測で埋めない。比較先で応答が捕まらないときは、それを「差がない」とも「呼ばれなかった」とも読まない。まずリクエストの本文を1本見て、操作名が載っているかを確かめる（aidev-qa-characterization の Playwright の資料にある、操作名のない構成の扱い）。

両方の環境で、照合するケースの前提のデータがそろっていることを確かめる。環境ごとにデータが違うと、差異の多くがデータの違いになり、本当の差が埋もれる。両方を同じデータの状態にする方法（初期データの入れ直しか再起動、戻せなければ接頭辞で作った記録を分ける）と、再起動や再デプロイの後に基準を流し直す決まりは、aidev-qa-test-run の「データの状態と流し直し」に従う。検索、一覧、帳票のケースは、両方で複数の行が出る条件にする。両方が0件なら、照合しても何も確かめていない（0件の表示そのものを確かめるケースを除く）。

### 3. 両方の環境で流す

環境ごとに別の run にし、`QA_RUN_DIR` をその run のディレクトリに向けて流す。ログインが要る案件では、流す直前に aidev-qa-login-session で環境ごとのセッションを作り直す。環境ごとのセッションは `automation/web/.auth/<environment>/<role>.json` に分ける。セッションは発行したホストに結び付くので、別の環境のものを使い回すとログイン画面を証跡にしてしまう。

基準と比較先は、同じテストのコード、同じ日の近い時刻、同じデータの条件で流す。既存の基準の run を使ってよいのは、基準の環境の版とテストのコードがその run から変わっておらず、データの条件も同じで、その run の後に基準の環境を再起動も再デプロイもしていないと確かめられたときだけである。一部のケースだけを流し直したいときも、同じ run のディレクトリに足さず、新しい run に全ケースを流す。

証跡の撮り方、`runs/` に最終の実行だけを残すこと、トレースを証跡にしないことは、aidev-qa-characterization の証跡の資料に従う。比較先では、記録した期待値との違いでテストが失敗することがある。テストは撮影と値の保存を判定より先に行う作りなので、失敗しても証跡は残る。失敗したことそのものは分類ではない。分類は次の照合で行う。撮影の前にテストが止まって比較先の証跡がないときは、テストの順序を直して流し直す。期待値を緩めて通したり、TC-ID の違う比較先だけのテストを別に作ったりしない。突き合わせができなくなる。

### 4. 3点を突き合わせ、差異を出す

突き合わせる前に、基準と比較先の run のそれぞれで、画面マニフェストを分母に証跡の完全性を数える（ケース、checkpoint、API の応答、帳票のファイル）。数え方は aidev-qa-characterization の証跡の資料と同じで、ファイルの有無で数え、テストの成否では数えない。比較先では記録した期待値との違いでテストが NG になるが、撮影と保存は判定より先なので証跡はある。NG のケースを欠落と数えない。画面ごとに照合するときは、その画面のマニフェストだけを分母にし、照合もそのマニフェストにある TC-ID だけで行う。run にほかの画面のケースがあっても、欠落にも照合できなかったケースにも数えない。両方の側でないファイル同士は「差なし」に見えるので、どちらかの側で欠けているものは照合の前提の崩れとして扱い、流し直すか照合できなかったケースにする。一致に数えない。基準の run に NG があるときも同じで、基準の環境が記録した時から変わったか異常を含んでいるので、分類の前に原因を確かめて片付ける。基準の NG を比較の結果に持ち込まない。

ケースと checkpoint の名前で基準と比較先の証跡を対応付け、画面表示、内部データ、帳票の3点を突き合わせる。比較はスクリプトで機械的に行い、目についた列だけを見比べない。比較のスクリプトは QA リポジトリに置く（例 `automation/web/scripts/compare-runs.mjs`）。

正規化は、画面マニフェストの `normalize` の規則を両方の側に同じように当てる。照合の途中で、差を消すために規則を足したり、範囲を広げたりしない。比較先にだけ実行ごとに変わる値が現れたときは、比較先で同じケースを2回記録して本当に毎回変わることを確かめてから、項目を名指しした規則をマニフェストに足し、compare.md にそのことを書く。形式を確かめてから置き換える規則なので、形式が変わった値は正規化されずに差異として残る。それが正しい。ただし、形式が合っていて値が誤っている場合（日付が1日ずれた、時差の分だけ時刻がずれた）は正規化で消える。正規化の対象の項目は、元の値にも規則の `mustMatch` に書いた妥当性の確かめ（実行の時間帯に入る、実行日と同じ日、基準と同じ形の ID など）をかけ、通らなければ差異として出す。規則の形は aidev-qa-characterization の画面マニフェストの資料にある。

突き合わせ方の要点は次のとおり。詳しくは `references/diff-classification.md` に書いた。

- 一覧と詳細は別々に照合する。詳細が一致しても、一覧の一致にはならない。一覧と詳細でデータの取り方が分かれた改修では、一覧の側だけで項目が落ちることがある
- 一覧は、表示されたすべての行と列を突き合わせる。2ページ目、開いていないタブ、ダイアログは、テストが表示させた範囲しか照合していない。照合していない列や範囲は「未検証」と書き、一致に数えない
- 一覧は、行の集合と並び順を分けて照合する。行の集合はキーの列で行を対応付けて比べ、並び順はキーの並びとして別に比べる。位置で行を対応付けると、並び順を変えた改修ですべての行が差になり、本当の値の差が埋もれる
- 内部データは、正規化した応答の本文を項目ごとに突き合わせ、項目の増減と値の違いを分けて出す
- 帳票はファイルを丸ごと比べない。CSV は行を読み、キーの列で行を対応付けてから値を比べる。PDF は文字を取り出して内容を比べる。並び順、文字コードと改行、レイアウトは、値とは別の差異として出す

ケースの対応付けが自明でないことがある。テストのコードが環境で違う、テストの名前が変わった、片方にしかないケースがある、といった場合である。ファイル名の一致で決めず、ケースの手順、ロール、表示モード、データの条件で同じケースかを判断する。判断がつかなければ作業者に確かめる。片方にしかないケースは照合できなかったケースとして理由を書き、結果を作らない。

### 5. 照合の仕組みが差を見つけられるかを確かめる

差異がゼロと出ても、照合のスクリプトや正規化が差を見逃しているだけかもしれない。分類に入る前に、基準の証跡の写しを Git に入らない場所（例 `.qa-scratch/compare-check/`）に作り、値を1か所変えて照合にかけ、その差が出ることを見る。画面の値、応答の項目、帳票のセルのそれぞれで1回ずつ確かめる。正規化の対象の項目は、形式を変えた値（日付の書式を変えたもの）を入れて正規化されずに差として出ることと、形式を保ったまま値をずらしたもの（日付を1日ずらしたもの）が元の値の確かめで差として出ることも見る。出なければ、スクリプトか正規化の規則を直してから照合をやり直す。`runs/` の証跡そのものは変えない。確かめた内容は compare.md に書く。

### 6. 差異を分類する

差異ごとに、`references/diff-classification.md` の基準で一致、意図した差分、要確認のどれかに分ける。判断が分かれるのは次の場面である。

- 意図した差分にするには、比較先の挙動を定めた記述を文書の中に見つけ、文書と箇所（AC-ID、節の番号）と記述の要旨を書き、比較先の値がその記述どおりであることを確かめる。同じ話題に触れているだけの記述や、記述が基準の側の挙動を支持しているときは、根拠にならない
- 応答が空や0件になった差異は、実装が壊れたのか、データがないのかを、検証の対象とは別の経路（データベース、別の実装の API、基準の環境の同じ操作）で確かめてから分ける。何で確かめたかを書く。確かめる手段がなければ要確認にする
- 許可と拒否の差は、要件や設計の許可の表と突き合わせる。表のとおりなら意図した差分、表と合わなければ要確認にする
- 応答の項目が減った差異は、減らすことを定めた記述があり、かつ画面表示と帳票に差がないときだけ意図した差分にする。画面にも差が出ていれば要確認にする

一致したケースでも、両方の側が AC と食い違っていることに気づいたら、compare.md に書いて作業者に伝える。照合で分かるのは回帰がないことで、仕様どおりであることではない。そのケースは aidev-qa-test-run や aidev-qa-authz-test で確かめる。

### 7. 結果を書く

`runs/<比較先の run>/compare.md` に、基準と比較先の run、ケースごとの照合の結果、差異の一覧、要確認の詳細を書く。要確認の差異には、後で Issue を起票するのに要る情報（再現手順、基準と比較先の値、両方の証跡の場所）を残す。起票は aidev-qa-bug-ticket が行う。

基準の run の result.md は、aidev-qa-characterization と aidev-qa-test-run の形式のまま書く。比較先の run の result.md は、分類のあとで書く。冒頭の環境名、版、実行日時の後に「結果の決め方: compare.md の分類による（仕様との照合ではない）」の1行を足す。一致と意図した差分だけのケースは OK、要確認を含むケースは NG、照合できなかったケースは実行不能にし、NG の詳細には compare.md の差異の ID を書く。記録した期待値との違いでテストが失敗したことは、備考に残す。意図した差分を理由に OK にしたケースのテストの期待値は、この Skill では書き換えない。新版を新しい基準として記録し直すかは作業者が決め、記録し直すときは aidev-qa-characterization で行う。

### 8. 比較の HTML を作る（求められたとき）

顧客や関係者に横並びで見せるときは、`references/compare-manifest.md` の形式でマニフェストを書き、`aidev qa compare-report MANIFEST OUT` で HTML を作る。画像が多く大きくなりすぎるときは `--link` を付ける。HTML の状態は compare.md の分類から転記し、テストの生の成否をそのまま使わない。この Skill が分類を作り、HTML はそれを見せるだけである。

作ったら、渡す前にブラウザで開いて見る。画面とケースのまとまり、同じケースが同じ行に並んでいるか、要確認のケースが OK に見えていないか、写り込んだ個人情報や資格情報がないか、ファイルの大きさを確かめる。

## よくある誤り

- 画面表示だけを照合し、応答の中身と帳票を見ない
- 差異のゼロを目指し、正規化の規則やスクリーンショットの `mask` を広げて差を消す
- 根拠を書かずに、または同じ話題に触れているだけの記述を根拠に、意図した差分にする
- 詳細の一致をもって一覧の照合を省く。一覧の一部の列だけを比べる
- 片方または両方が0件のケースを一致と数える。空の応答をデータがないせいだと決め打ちする
- 比較先で応答が捕まらないことを「差がない」と読む
- 環境ごとのセッションを分けず、ログイン画面を証跡にして照合する
- 基準に、合意した版ではない環境や古い run を使う
- 比較先だけの TC-ID でテストを作り直し、突き合わせができなくなる
- 帳票をバイトや見た目で丸ごと比べ、生成日時の差で埋もれるか、値の入れ替わりを見逃す
- テストの生の成否をそのまま HTML の OK と NG にする
- 照合のスクリプトが差を見つけられるかを確かめずに「一致」と報告する

## 完了条件

- `aidev qa profile check` が `--skill aidev-qa-regression-compare` で成功した
- 基準と比較先を、同じテストのコードで、それぞれの環境のセッションで流し、版と実行日時を各 run の result.md に書いた
- 突き合わせる前に、基準と比較先の両方で証跡の完全性を数え、欠けたケースを一致に数えていない。基準の run の NG は分類の前に片付けた
- 正規化の対象の項目で、元の値の妥当性も確かめた
- 照合の対象のケースごとに、画面表示、内部データ、帳票（ある場合）を突き合わせた。一覧と詳細は別々に照合し、照合していない列や範囲は未検証と書いた
- 照合の仕組みが、値の差と形式の差を見つけられることを確かめ、その内容を compare.md に書いた
- すべての差異が一致、意図した差分、要確認のどれかに決まり、意図した差分にはすべて文書と箇所の根拠がある
- 照合できなかったケースに理由があり、一致に数えていない
- 要確認の差異に、再現手順、基準と比較先の値、両方の証跡の場所が書かれている
- HTML を作ったときは、compare.md と食い違わないことと、写り込みがないことをブラウザで見て確かめた
- 証跡、compare.md、HTML に、資格情報、Cookie、トークンの値が入っていない。compare.md とマニフェストの `note` に、個人情報や機微な項目の値を写していない
