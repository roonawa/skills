## 目的

カスタムソリューション部の受託開発において、要件定義の壁打ちから要件定義書（Md）の出力までを一気通貫で支援するスキル。

以下の課題を解決する：
- 担当者ごとの表記・項目構成のゆれ → 統一テンプレートで解消
- 要件定義段階での観点漏れ → 必須4項目を必ず壁打ちする構造で防止
- Claude Codeと担当者だけの壁打ちによる属人化 → レビューチェックポイントを2箇所内蔵
- 後工程とのトレーサビリティ不足 → 機能要件にFR-IDを付与し後続スキルと連動

## スコープ

### やること
- 案件タイプ判定（新規開発／機能追加／リニューアル）
- 4項目の要件定義書作成のための壁打ち（草案フェーズ）
- 草案を要件定義書テンプレートに整形（整形フェーズ）
- 整形後のブラッシュアップサイクル（項目単位／FR-ID単位での部分修正・深堀り）
- 既存要件定義書からの再開モード（過去のMdファイルを読み込んで続きから壁打ち）
- 既存案件機能追加モード（任意形式の既存ドキュメント Word/PDF/Excel等を参照情報として読み込み、新機能要件のみを起こす）
- 機能要件へのFR-ID自動付与（FR-001, FR-002...）
- バージョン自動管理（v0.1 → v0.2 → ... → v1.0）
- 要確認事項の明示（推測値を載せない）
- レビュー依頼を促すメッセージ出力
- 受け入れ条件定義（顧客側受入基準として機能ごとにチェックリスト形式で提示）

### やらないこと
- 工数見積もり（既存の見積プロセスで対応）
- 基本設計への落とし込み（→ `spec-basic` スキルで対応予定）
- 顧客との議事録作成（別スキル候補）
- 案件タイプ別の観点切替（v0.2以降で検討。今は案件タイプを記録するのみ）
- 非機能要件の独立セクション化（必要時に「制約・前提」内で言及する運用）

## 全体フロー

```
[起動]
  ↓
[起動モード選択]
  ├─ A. 新規作成（完全新規案件、ゼロから壁打ちを始める）
  ├─ B. 既存要件定義書から再開（→ ブラッシュアップサイクルから開始）
  └─ C. 既存案件の機能追加（既存ドキュメント参照 → 案件タイプ「機能追加」固定）
  ↓
① 案件タイプ判定（A の場合のみ。C は「機能追加」固定でスキップ）
  ├─ 新規開発
  ├─ 機能追加
  └─ リニューアル
  ↓
  ※ C の場合：参照ドキュメント読み込み → 「0. 既存システム参照情報」に記録 → ② へ
  ↓
② 草案フェーズ（壁打ち）
  ├─ ※ C の場合：モードC固有の追加質問を先に行う（4項目壁打ちの前）
  ├─ 概要・目的
  ├─ スコープ（やること／やらないこと）
  ├─ 機能要件
  └─ 制約・前提・リスク
  ↓ ループ：「他に深堀りしたい項目は？」
  ↓
【チェックポイント1】整形に進む前の確認
  ↓
③ 整形フェーズ
  └─ 要件定義書 v0.1 として出力
      ※ C の場合：「0. 既存システム参照情報」セクションを先頭に含める
  ↓
④ ブラッシュアップサイクル（反復可能）
  ├─ 修正モード選択
  │   ├─ a. 項目単位で深堀り
  │   ├─ b. FR-ID単位でピンポイント修正
  │   ├─ c. 新規追加
  │   └─ d. これでOK → 終了
  ├─ ピンポイント壁打ち
  ├─ 該当箇所のみ更新（バージョン自動インクリメント）
  └─ サイクル先頭に戻る
  ↓ 「これでOK」が出た時点
  ↓
【チェックポイント2】v1.0確定前のレビュー依頼（v1.0確定時のみ発動）
  ↓
要件定義書 v1.0 として確定
```

## 起動時の動作

スキルが起動したら、最初に起動モードを確認する。

> 「要件定義スキル（spec-req）を起動した。以下のどれで進める？
> A. 新規作成（完全新規案件、ゼロから壁打ちを始める）
> B. 既存ファイルから再開（過去のspec-req出力Mdを読み込んで続きから）
> C. 既存案件の機能追加（既存ドキュメント Word/PDF/Excel等 を参照情報として読み込み、新機能要件を起こす）」

- **Aを選んだ場合**：案件タイプ判定から開始
- **Bを選んだ場合**：既存ファイルのパスを聞き、読み込んでブラッシュアップサイクルから開始
- **Cを選んだ場合**：参照ドキュメントのパスを1つ以上指定させ、読み込み後に案件タイプ「機能追加」固定で草案フェーズへ

## 草案フェーズの壁打ち（4項目）

質問は**1問ずつ**投げる。複数の質問を一度に投げない。回答内容に応じて追加深堀りを行う。

### ① 案件タイプ判定

> 「この案件は次のどれに該当する？
> 1. 新規開発（まったく新しいシステム・機能を作る）
> 2. 機能追加（既存システムに機能を追加する）
> 3. リニューアル（既存システムを作り直す）」

案件タイプを確認したら記録して次に進む。

### ② 草案フェーズ：4項目の壁打ち

#### 項目1：概要・目的
1. 「この案件は何を実現するもの？1〜2行で教えて」
2. 「顧客側の課題は何？なぜ今やるの？」

#### 項目2：スコープ
1. 「やることを箇条書きで挙げて」
2. 「逆に、やらないことを明確にしておきたい。除外する範囲は？」

※「やらないこと」を必ず聞くのが本スキルの特徴。スコープの肥大化を防ぐための重要項目。

#### 項目3：機能要件
1. 「主要な機能を一覧で挙げて。後でIDを振る」
2. 各機能について「これは何をする機能？利用者は誰？」を確認する（1機能ずつ）
3. 各機能について付随する受け入れ条件を確認する（1機能ずつ）
4. 整形フェーズでFR-001から自動採番する

#### 項目4：制約・前提・リスク
1. 「技術制約はある？（使用言語、既存システムとの連携、インフラ等）」
2. 「前提条件は？（納期、予算枠、組織制約等）」
3. 「現時点で未確定の事項や確認が必要な事項は？」→ 回答を「⚠ 要確認」マーク付きで記録する

### 4項目完了後の確認

4項目すべての壁打ちが完了したら以下を確認する：

> 「ひと通りの壁打ちが完了。他に深堀りしたい項目はある？なければ整形フェーズに進む。」

- **「あり」の場合**：該当項目に戻って追加質問を行う
- **「なし」の場合**：チェックポイント1へ

---

## チェックポイント1：草案完了時

整形フェーズに進む前に以下を伝える：

> 「草案ができた。整形に進む前に、漏れがないか確認したい項目はある？人にレビューを依頼する場合はここで一旦止めて。」

確認が取れたら整形フェーズに進む。

## 整形フェーズ

草案の内容を以下の構造に整形してMdファイルとして出力する。

**出力テンプレート：**

```markdown
# 要件定義書：<案件名>

| 項目 | 内容 |
|---|---|
| 案件タイプ | <新規開発／機能追加／リニューアル> |
| 作成日 | YYYY-MM-DD |
| 顧客 | <顧客名> |
| 自社担当 | <担当者> |
| バージョン | 0.1（草案） |

## 0. 既存システム参照情報（機能追加案件のみ・モードC使用時）
※ 新規開発・リニューアル案件、または既存ドキュメントなしの機能追加案件ではこのセクションは省略

### 0.1 既存システム概要
- システム名／対象範囲／使用言語・技術スタック等

### 0.2 参照ドキュメント
- `<パス1>`：<種別（要件定義書／設計書／仕様書等）／概要>
- `<パス2>`：<種別／概要>

### 0.3 機能追加で影響する既存機能
- <既存機能名>：<想定影響>

## 1. 概要・目的
（壁打ちで得た内容）

## 2. スコープ
### 2.1 やること
- ...
### 2.2 やらないこと
- ...

## 3. 機能要件
| ID | 機能名 | 概要 | 備考 |
|---|---|---|---|
| FR-001 | ... | ... | ... |
| FR-002 | ... | ... | ... |

## 4. 制約・前提・リスク
### 4.1 制約
- ...
### 4.2 前提
- ...
### 4.3 リスク・要確認事項
- ⚠ <未確定事項> — 要確認
```

**FR-IDの採番ルール：**
- FR-001から連番で自動採番する
- ブラッシュアップサイクルで機能追加した場合は続き番号を付与する（既存IDは変えない）
- 採番済みのFR-IDを振り直さない

整形完了後、ファイルの保存先を利用者に確認してから書き込む。ファイル名は以下の規則に従う：

```
要件定義書_<案件名>_v0.1_<YYYY-MM-DD>.md
```

## ブラッシュアップサイクル

整形フェーズ完了後、または既存ファイル再開モード起動時に開始する。「これでOK」と利用者が伝えるまで何度でも繰り返せる。

### サイクル起動時の問いかけ

> 「現状の要件定義書（v0.X）を確認した。どこを修正・深堀りしたい？以下から選んで：
> a. 項目単位で深堀り（概要／スコープ／機能要件／制約）
> b. 特定の機能要件をピンポイント修正（FR-IDを指定）
> c. 新規追加（機能要件・リスク・制約等を追加）
> d. これでOK（v1.0として確定）」

### 各モードの動作

| モード | 動作 |
|---|---|
| **a. 項目単位** | 4項目のいずれかを指定させる → 該当項目について追加質問・修正壁打ちを行う → 該当セクションのみ書き換える |
| **b. FR-ID単位** | 修正したいFR-ID（例：FR-003）を指定させる → 該当機能の詳細について壁打ちを行う → 該当行のみ更新する |
| **c. 追加** | 追加したい要素（新機能要件／新リスク／新制約等）を指定させる → 壁打ちを行う → 該当セクションに追記する（FR-IDは自動採番） |
| **d. OK** | ブラッシュアップサイクルを終了する → チェックポイント2へ |

### 部分更新の挙動

- 既存内容を保持しつつ、指定箇所のみ書き換える（全文書き直さない）
- 修正のたびにバージョン番号を自動インクリメントする（v0.1 → v0.2 → v0.3 → ...）
- バージョン管理の基本方針は上書き（最新版のみ保持。Git管理されている前提）
- 利用者が指示した場合のみ、旧版を `<案件フォルダ>/履歴/` に退避する

---

## チェックポイント2：v1.0確定時（必須）

利用者が「d. これでOK」を選択したら、以下を実行する：

1. バージョンを **v1.0** に確定する
2. ファイル名のバージョン部分を `v1.0` に更新する
3. 以下のメッセージを表示する：

> 「要件定義書を v1.0 として確定する。**顧客提示前に、社内でのレビュー（部長／補佐、または該当担当者）を必ず受けてください**。」

**重要**：チェックポイント2は v1.0 確定時のみ発動する。ブラッシュアップサイクルの途中（v0.2, v0.3 等）では発動しない。中間版を都度レビュー依頼すると運用が回らないため。

## 既存ファイル再開モード

### 起動フロー

1. 起動モードでBを選択した場合
2. 「既存の要件定義書のファイルパスを教えて」と聞く
3. 指定されたファイルを読み込み、以下をメモリに展開する：
   - 案件タイプ
   - 4項目の現在の内容（概要・目的／スコープ／機能要件／制約・前提・リスク）
   - FR-ID採番状況（次に振るFR-IDを把握する）
   - 現在のバージョン番号
4. 読み込んだ内容を要約して提示し、ブラッシュアップサイクルから開始する
5. テンプレート構造から逸脱した記述がある場合は警告を出す

### 想定ユースケース
- 顧客との打ち合わせ後、得た情報を既存要件定義書に反映する
- 草案を作って一旦止めていた案件を後日再開する
- v1.0確定後に追加要望が出てきた場合の更新（その場合は v1.1, v1.2, ... で管理）

## 既存案件機能追加モード（モードC）

既存案件への機能追加で、過去の要件定義書がspec-req未出力（Word/PDF/Excel等）の場合に使用するモード。

### 起動フロー

1. 起動モードでCを選択した場合
2. 「参照する既存ドキュメントのパスを教えて（複数可）」と聞く
3. 指定された各ドキュメントについて：
   - **読み込み可能な形式**（Md/テキスト等）：内容を要約してメモリに展開する
   - **読み込み困難な形式**（PDF/Word/Excel等）：可能な範囲で抽出を試み、抽出できない場合はパスと種別のみを記録し、「⚠ 内容未抽出」と明示したうえで利用者から口頭で概要を聞く
4. 「0. 既存システム参照情報」セクションに以下を記録する：
   - 既存システムの概要（壁打ちで得る）
   - 参照ドキュメント一覧（パス・種別・概要）
   - 機能追加で影響する既存機能
5. 案件タイプ「機能追加」固定で **案件タイプ判定をスキップ** → 草案フェーズへ

### モードC固有の追加質問（草案フェーズ4項目の前に必ず確認）

通常の4項目壁打ちを始める前に、以下を1問ずつ確認する：

1. 「既存システムの該当範囲はどこ？（モジュール名／画面／機能群）」
2. 「機能追加で影響する既存機能は？（連携、データ共有、画面遷移等）」
3. 「既存仕様で踏襲すべき部分・変更すべき部分は？」
4. 「既存システムへの影響範囲・回帰リスクは？」

これらの回答は「0. 既存システム参照情報」と「4.3 リスク・要確認事項」に分散して記録する。

### モードBとの使い分け

| 状況 | 使うモード |
|---|---|
| 過去にspec-req出力した要件定義書（Md）がある | **B** → そのファイルに追記する形でブラッシュアップ |
| 既存ドキュメントが Word/PDF/Excel/手書き 等で、新規にMdの要件定義書を起こしたい | **C** |
| 既存ドキュメントが一切ない（口伝・現行動作のみ） | **A** + 案件タイプ「機能追加」 |

### 想定ユースケース
- 自社既存製品（バイク整備管理／検診ソフト等）への機能追加
- 既存顧客のDelphi/C#レガシーシステムへの機能追加
- 過去の納品案件で、要件定義書がWord/PDFでしか残っていない案件への追加対応
- 顧客提供の仕様書（Excel等）を参照しながら追加機能の要件を起こす場合

## 出力ファイルの規則

### ファイル名規則

```
要件定義書_<案件名>_v<バージョン>_<YYYY-MM-DD>.md
```

| 状態 | バージョン例 | 備考 |
|---|---|---|
| 整形フェーズ初回出力 | v0.1 | 草案を整形した直後 |
| ブラッシュアップ中 | v0.2, v0.3, ... | 修正のたびに自動インクリメント |
| FIX | v1.0 | 利用者が「OK」を出した時点で確定 |
| FIX後の追加修正 | v1.1, v1.2, ... | 顧客合意後の修正があった場合 |

### 保存場所
利用者がスキル起動時（または整形フェーズ完了時）に保存先を指定する。案件フォルダ配下に保存するのが基本。

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **「やらないこと」は必ず聞く**。スコープ肥大化を防ぐための重要項目
- **数値を推測で記載しない**。未確定の金額・工数・期日等は「⚠ 要確認」として明示する。想定値を記録しない
- **個人名の扱い**：ドキュメント上で個人名を匿名化する必要がある場合は「担当者A」「担当者B」等の役割表記を使う
- **FR-IDは振り直さない**。一度付与したIDは変更しない（後続スキルとのトレーサビリティを維持するため）
- **チェックポイント2はv1.0確定時のみ**発動する。中間版では発動しない
- 工数見積もりはこのスキルのスコープ外。求められた場合は既存の見積プロセスで対応するよう案内する
- **モードCで参照ドキュメントが読み取れない場合**は「⚠ 内容未抽出」と明示し、利用者から口頭で概要を聞く
- **モードCの参照ドキュメントは3〜5本程度を目安**とする。それ以上の場合は利用者が事前に主要ドキュメントを選定して指定する
