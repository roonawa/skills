## 目的

UAT不具合管理表からコピーした顧客記載の「不具合の症状」だけを渡されたときに、次の作業を毎回同じ手順・同じ品質で実行するスキル。

- 症状の記述から該当する画面・機能のコードを自分で特定し、実際に読んで原因を突き止める
- 原因を、テスト担当者が実機で追試できる具体的な再現手順（画面操作・入力データ・期待される結果と実際の結果）に落とし込む
- 必要に応じてテストデータを作成する（CSVやSQLでの合成データ、画面操作での登録手順など）
- 修正コードを書くこと・回帰テストを実行すること・HTMLレポートを発行することは**このスキルの範囲外**（[[fix-verify]]は別スキル。「修正した」報告の裏取りが要る場合はそちらを使う）
- 症状の情報だけでは原因を一つに絞れない、または再現手順を具体的に書けないと判断した場合は、絶対に推測で埋めない。何が分かれば絞り込めるかを明確にし、**ITの専門用語を使わずに**顧客が答えやすい言葉で質問する

「この不具合の再現手順を教えて」と、症状の記述だけを渡されたときに起動する。

## 想定する入力

次の3点だけが渡される（それ以上の情報は無いことが前提）：

- 画面名（メニュー名、画面タイトル、URLの一部など）
- 対象データ（どのレコード・どの条件のデータで起きるか）
- 再現条件（何をすると起きるか、いつ起きるか）

「【修正内容】」のような対応方針の記述や、担当者自身による原因分析は付いてこない。ここが[[fix-verify]]との違い——[[fix-verify]]は「原因はもう分かっている前提で、その報告が正しいか検証する」スキルだが、このスキルは「原因がまだ分かっていない前提で、ゼロから特定する」スキル。

## 全体フロー

```
1. 症状の記述から検索キーワードを抽出し、該当する画面・機能のコードを特定する
   ↓
2. 特定したコードを実際に読んで、再現条件下で何が起きるかを追う
   ↓
3. 原因の仮説を裏付ける（ログ・DDL・類似画面との比較など、自分の手で検証できるものは検証する）
   ↓
4. 原因を一つに絞れたか判定する
   ├─ 絞れた → 5. 再現手順を作成する
   └─ 絞れない／情報不足 → 6. 顧客への追加質問を作成する
   ↓
7. チャットに「原因」「再現手順」（または「追加質問」）を報告する
```

## 1. 症状から該当コードを特定する

画面名・対象データ・再現条件それぞれから検索キーワードを抜き出す：

- 画面名 → 画面タイトル文字列、メニュー定義ファイル、ルーティング定義、コンポーネント名の手がかり
- 対象データ → テーブル名・カラム名・区分値・ステータス値
- 再現条件 → 操作名（ボタン名、処理名）、条件分岐に関わりそうな値（0件、null、上限値など）

```bash
grep -rn "画面名の一部" --include=*.{vue,tsx,jsx,java,cs} .
git log --all -i --grep="画面名" --oneline | head -20
```

ヒットしなければ表記ゆれ（正式名称と略称、和名と英名）を疑って何度か試す。それでも特定できなければ、画面名の情報が足りていない＝6節の追加質問に進む。

## 2. コードを読んで再現条件下の挙動を追う

特定した画面・機能について、フロントエンド（表示・入力チェック）→ API/コントローラ（受け渡し）→ ロジック（計算・分岐）→ データアクセス（SQL・永続化）の順に、実際にReadツールで開いて読む。

- 再現条件に出てくる値（対象データの状態、操作の順序）を実際にコード上でたどり、どの分岐・どの条件式に入るかを一行ずつ確認する
- 「〇〇の場合だけ起きる」という条件は、その分岐が実際にコード上に存在するかを確認する。推測で「たぶんここが原因」と決めない
- 似た画面・似た処理が複数ある場合、対象データ・再現条件に一致する方を選ぶ（両方候補が残るなら両方読む）
- 過去の関連修正（同じ関数・同じテーブルを触ったコミット）があれば `git log -p -- <path>` で経緯を確認する

## 3. 原因の仮説を裏付ける

「コードを読んでそれっぽいから」で終わらせず、可能な範囲で自分の手で検証する。

| 仮説の種類 | 検証方法 |
|---|---|
| 特定の条件でNullPointer/例外になる | 該当データが本当にその条件を満たすか、ログ・DB定義（DDL）を確認する |
| 表示上の計算が間違っている | 対象データの値を使って手計算し、コードの計算結果と突き合わせる |
| 特定のデータでだけ分岐が変わる | その分岐条件を作るデータを合成し、実際にロジックを通してみる（可能なら） |
| A画面ではエラーにならずB画面ではエラーになる | 両方の実装を横に並べて差分を比較する |

## 4. 原因を一つに絞れたか判定する

次のいずれかに当てはまる場合は「絞れていない」と判断し、推測で報告しない。5節ではなく6節に進む：

- 候補となる原因が2つ以上あり、対象データ・再現条件の情報だけではどちらか決められない
- 該当しそうなコードが複数の画面・複数のバージョンに存在し、どれが対象か画面名だけでは特定できない
- コード上は正常に見えるが、症状の記述（画面名・対象データ・再現条件）が曖昧で、そもそも再現条件を満たす具体的な操作手順を書けない
- 対象データの実際の値（区分値、件数、日付など）が分からず、境界値の問題かどうか判断できない

## 5. 再現手順を作成する

原因を一つに絞れたら、テスト担当者が実機（PT環境）で同じ症状を再現できるだけの具体性で書く。

- 画面遷移：どの画面から、どのメニュー・ボタンを、どの順で操作するか
- 入力データ：再現に必要な具体的な値（区分、件数、日付の前後関係など）。既存データで再現するのか、新規登録が必要なのかも明記する
- 操作：クリック・入力・保存等の具体的な操作
- 期待される結果 と 実際に起きる結果 を対で書く（症状の記述と一致するように）
- 前提条件（権限、データ登録済みかどうか等）があれば明記する

「多分こうすれば起きる」ではなく、実際にコード上の分岐条件を満たすと確認した手順だけを書く。

## 6. 顧客への追加質問を作成する（原因を絞れない場合）

**重要：質問を受け取るのはITに詳しくない顧客担当者**。IT用語・略語をそのまま使わず、画面や操作の言葉に置き換える。

| 悪い聞き方（IT用語） | 良い聞き方（自然な言葉） |
|---|---|
| エラーメッセージ・スタックトレースを教えてください | 画面に赤字や警告で出ていた文言を、そのまま（一字一句）教えてください。可能であれば画面のキャプチャ画像をいただけますか |
| リクエスト時のパラメータ／ペイロードを教えてください | その操作をしたときに、画面に入力・選択していた項目と値を教えてください |
| 対象レコードのIDを教えてください | 問題が起きたデータの、画面上に表示されている番号や名称（例：申込番号、氏名など）を教えてください |
| 再現手順を詳細化してください | もう一度同じ操作をすると必ず起きますか、それとも時々ですか。いつ頃から起きるようになりましたか |
| どの環境で発生しましたか | 本番の画面ですか、それとも確認用（テスト）の画面ですか |

質問は「なぜ知りたいか」を添えると回答してもらいやすい（例：「対象のデータを絞り込むために、〜を教えていただけますか」）。

## 7. チャットへの報告

- **原因が絞れた場合**：原因（該当ファイル・処理の要約を人間の言葉で）と、5節の再現手順を短くまとめて報告する
- **絞れなかった場合**：ここまでの調査で分かったこと・絞れない理由を一言添えたうえで、6節の追加質問をそのまま提示する（顧客に転送してそのまま使える文面にする）
- 断定できない部分を断定して書かない。「〇〇の可能性が高いが、△△が確認できれば確定できる」という書き方を使う

## 注意事項

- **原因を推測で断定しない**。コードで確認できた事実と、確認できていない仮説を混同しない
- **再現手順は実際にコードで確認した条件だけを書く**。「たぶん起きるはず」を書かない
- 顧客への質問は**必ずIT用語を自然な言葉に言い換える**。専門用語が混じっていないか、送る前に読み返す
- 症状の記述が過去の関連不具合（BUG-XXX等）を参照している場合は、その過去コミットも読んで文脈を掴む
- このスキルは原因特定と再現手順の提示までが範囲。修正・テスト実装・回帰確認・レポート発行が必要な場合は[[fix-verify]]を使う
