# 目的
実装コードからテスト観点を抽出し、以下を行ったうえでxUnitテストコードを作成する。
* テストケースの抜け漏れ防止
* 境界値の網羅
* 例外処理の確認
* 分岐網羅
* 副作用の検証
* 対象範囲における行・分岐カバレッジ80%以上の維持
* 完了した画面に紐づく区分A/Bの行・分岐カバレッジ100%の達成

---

# 基本原則
テストは実装の再現ではなく仕様の検証である。
実装変更に強く、仕様変更時のみ失敗するテストを優先する。

テストコードを先に生成してはいけない。
必ず以下の順で進める。
1. 仕様解析
2. 実装解析
3. テスト容易性判定
4. テスト観点抽出
5. 実装範囲・変更範囲確認
6. テストケース作成
7. 分岐対応確認
8. レビューと開発者承認
9. テストコード生成
10. カバレッジ測定

このSKILLは画面単位の実装完了時に実行する。画面に紐づく対象コードを先に確定し、その区分A/Bを100%の判定対象とする。

1テスト1責務を原則とする。
複数の検証項目を1テストへ詰め込まない。
Assertは意味的に1つを推奨する。

カバレッジ向上のみを目的とした意味のないテストを生成してはいけない。
業務価値の低いテストは生成しない。
以下は原則生成しない。
* privateメソッド単体
* 実装詳細の検証
* モックの過剰Verify
* 単純なGetter/Setter

**「80%目標」と「意味のないテスト禁止」は矛盾しない。**
80%はテスト対象と判定した範囲（業務ロジック・バリデーション・権限制御・分岐・例外処理）にのみ適用する。
テスト対象外（DTO/Mapper/Entity/単純プロパティ）とテスト困難コード（下記ステップ3で判定）は分母から除外したうえで数値を評価する。
除外して初めて到達する80%であり、除外を偽装して数値を作ってはいけない。除外した場合は理由を必ず明記する。

**カバレッジは品質の証明ではなく、テスト設計の診断材料である。**
行を通過するだけで期待結果を検証しないテストは、数値を上げても欠陥を検知できない。カバレッジは未検証の振る舞いを見つけるために用い、各テストには観測可能な結果または副作用に対する意味のあるAssertを置く。
行カバレッジだけで十分とはしない。条件分岐・短絡評価・例外経路は分岐カバレッジおよびステップ7の分岐対応表で確認する。
画面の100%対象は、その画面の振る舞いを担うViewModel、Service、Validator、Command等の区分A/Bである。画面描画やネイティブ連携などの区分Cを、単体テストの数値のために含めない。

# ステップ1 仕様解析

対象機能の仕様を解析し、期待される振る舞いを抽出する。
実装よりも仕様を優先する。
実装と仕様に差異が存在する場合はテストコードを生成せず、差異を開発者へ報告する。
仕様情報源
優先順位は以下とする。

* テスト仕様書（spec-test）
* 詳細設計書（spec-detail）
* 基本設計書（spec-basic）
* 要件定義書
* テスト戦略
* ソースコードコメント
* 実装コード
それぞれ必要な情報が不足している場合は、憶測せずに必ず必要な情報を質問すること。
仕様が存在しない場合のみ、実装を暫定仕様として扱う。
ただし以下を明示すること。
「期待値は実装から推定」

## 既存テスト・既存仕様書との整合確認
仕様書（テスト仕様書・詳細設計書）が、実装コード中に存在しないクラス名・メソッド名を前提に書かれている場合がある
（仕様が先行し実装が追いついていない、または実装がリネームされ仕様書が更新されていない状態）。
「仕様書にテスト済みと書いてあるから対象外」と即断せず、以下を確認すること。

* 仕様書が名指しするクラス・メソッドが実装コード中に実在するか（grep等で確認）
* そのテストケースについて、実施結果（合格/不合格の記録、実行日、エビデンス）が実際に残っているか
* 特にセキュリティ・リリース判定基準に関わる項目は、記載の有無だけでなく実装の有無を必ず裏取りする

実在しない、または実施記録が無い場合は「仕様と実装（またはテスト実施実態）に乖離あり」として開発者へ報告し、
それを理由にテスト対象外とすることを避ける。

## 外部依存
以下を検出する。
* Repository
* DbContext
* HttpClient
* API Client
* File
* Directory
* Environment
* DateTime.Now
* DateTime.UtcNow
* Guid.NewGuid
* Random
検出した場合は、既存プロジェクトのダブル用ライブラリと規約に従った置換方針を提示する。規約が無い場合はMoqを用いる。
非virtualメソッドやsealedクラスがモックできない場合は報告し、無理なモック化を行わない。
モックが効果的でない場合は、該当する単体テストを生成せず後工程のテストに回す旨を報告する。

### ダブル（テスト代役）の選択基準
外部依存をどう置き換えるかは、以下の4種から最も単純なものを選ぶ。

| 種別 | 内容 | 使用場面 |
| -- | -- | -- |
| Stub | 固定値を返すだけ、検証なし | 戻り値を制御したいだけの場合 |
| Spy | 実装を包み、呼び出しを記録 | 実装を変えずに呼び出しを確認したい場合 |
| Mock | 実装を置き換え、戻り値制御と呼び出し検証を両立 | 戻り値制御と呼び出し検証の両方が必要な場合 |
| Fake | 簡易だが動作する実装（インメモリDB等） | 状態を持つ依存を軽量に再現したい場合 |

原則として、呼び出し検証が不要ならMoqの`Verify`を使うMockではなくStubで済ませる。
外部依存として検出したもの（Repository/DbContext/HttpClient等）以外の内部の協力オブジェクトはモック化せず、実装のまま動作させる。全てをモック化すると、各テストは成功するが結合部分の不具合を検知できないテストになる。

## 既存テストの重複確認
テストコードを設計する前に、対象クラス・公開メソッド・受入条件・期待結果で既存テストを検索する。テストプロジェクトの配置や命名規約に従い、同じ振る舞いを検証済みのテストがある場合は、新規作成ではなく拡張またはデータケース追加を優先する。

次の表を出力する。

| 対象の振る舞い | 既存テスト | 判定 | 対応 |
| -- | -- | -- |
| 例: メール未入力を拒否 | `RegistrationViewModelTests.Submit_WhenEmailIsNull_Throws...` | 一部不足 | 境界値ケースを追加 |

判定は「再利用」「拡張」「新規」のいずれかとする。名前が似ているだけで重複と判断せず、入力条件・期待結果・副作用が同じかを確認する。

# ステップ3 テスト容易性判定
実装解析の結果をもとに、対象コードを次の3区分に分類する。80%目標の分母はこの分類結果に基づく。

## 到達不能コードの判定
カバレッジ不足としてテストを追加する前に、そのコードが本番で到達可能かを確認する。呼び出し元が存在しない、常に成立しない条件、廃止済みの分岐など、到達不能と合理的に判断できるコードは「未テストの生きたコード」ではなくデッドコード候補である。

デッドコード候補にはカバレッジ目的のテストを作成しない。根拠（参照検索、到達不能となる条件、利用停止の仕様）を報告し、削除または開発者判断に回す。削除が決まるまでは区分Cや通常の除外で数値を調整してはならない。

| 区分 | 定義 | 扱い |
| -- | -- | -- |
| A. 即時テスト可能 | 純粋ロジック・分岐・例外処理・自前バリデーション。外部依存があってもインターフェース越しにモック可能 | 80%目標の対象。優先してテストを書く |
| B. 設計変更で改善可能 | 判断ロジックが外部依存（UI操作・ネイティブAPI・自動化API等）呼び出しに直接埋め込まれている | まずロジックを純粋関数/静的クラスへ抽出できないか検討し、開発者に提案する。抽出できた部分はA区分としてテストする |
| C. 本質的にテスト困難 | UI Automation要素・ネイティブフック（キーボード/マウスフック等）・実画面描画・外部プロセス起動など、単体テストの土俵に乗らない処理そのもの | 80%目標の分母から除外する。除外理由と、代替の担保手段（E2E/手動確認テストの有無）を明記する |

区分Cとして除外する場合、以下を確認してから除外すること（ステップ1「既存テスト・既存仕様書との整合確認」と連動）。
* 本当に代替のE2E/手動テストが存在し、実施記録があるか
* 存在しない場合は「テスト計画上の空白」として報告し、除外の可否を開発者に確認する

区分Bを区分Aへ抽出する際は、既存の公開APIやシナリオの振る舞いを変えないこと。振る舞いを変える場合は開発者の承認を得る。

# ステップ5 実装範囲確認
画面名を明示し、その画面の振る舞いを担うコードを確定する。画面単位のカバレッジは、フォルダ名やViewのコード量ではなく、この対応表で定義した対象クラス・メソッドを分母とする。

| 画面 | 対象 | 役割 | 変更種別 | 区分(A/B/C) | リスク | 対応 |
| -- | -- | -- | -- | -- | -- | -- |
| 例: 会員登録 | `RegistrationViewModel.Submit` | ViewModel | 新規/改修/仕様変更 | A | 高 | TC-001〜004 |
| 例: 会員登録 | `RegistrationValidator` | Validator | 既存 | A | 高 | TC-005〜008 |
| 例: 会員登録 | `RegistrationView` | 画面描画 | 改修 | C | 通常 | E2E-001 |

`git diff` 等で今回の変更行と影響を受ける分岐を特定し、既存の未カバー箇所と分けて記録する。新規・変更された区分A/Bの業務ロジック、バリデーション、権限制御、例外処理には必ずテストケースを対応付ける。画面の対象に含まれる既存の区分A/Bも、画面完了時には100%の判定対象とする。

## 画面カバレッジ・マニフェスト
画面の分母を担当者判断にしないため、テストプロジェクト配下の`Coverage/Screens/<ScreenId>.json`を作成し、画面完了までコミット対象として維持する。対象は型単位で定義する。画面に無関係なメソッドを同じ型へ混在させて100%判定が不適切になる場合は、対象ロジックを専用の型へ抽出する。メソッド単位の恣意的な除外はしない。

```json
{
  "screen": "MemberRegistration",
  "testProject": "tests/MyApp.Tests/MyApp.Tests.csproj",
  "targets": [
    {
      "type": "MyApp.Features.Registration.RegistrationViewModel",
      "filter": "[MyApp.Application]MyApp.Features.Registration.RegistrationViewModel",
      "classification": "A",
      "risk": "high"
    },
    {
      "type": "MyApp.Features.Registration.RegistrationValidator",
      "filter": "[MyApp.Application]MyApp.Features.Registration.RegistrationValidator",
      "classification": "A",
      "risk": "high"
    }
  ],
  "excluded": [
    {
      "type": "MyApp.Features.Registration.RegistrationView",
      "classification": "C",
      "evidence": "E2E-001"
    }
  ]
}
```

区分A/Bが存在しない画面の場合は、`targets`を空にし`noTargetsReason`を記載する。

```json
{
  "screen": "StaticAbout",
  "testProject": "tests/MyApp.Tests/MyApp.Tests.csproj",
  "targets": [],
  "noTargetsReason": "静的なXAML配線のみで判断ロジックを持たないため区分A/Bが存在しない",
  "excluded": [
    {
      "type": "MyApp.Features.About.AboutView",
      "classification": "C",
      "evidence": "E2E-014"
    }
  ]
}
```

`targets`には区分A/Bのみを置く。`excluded`は区分Cだけを置き、ステップ3の根拠とE2E/手動確認の証跡を必須にする。`evidence`は「確認済み」のような感想ではなく、実施記録を特定できる具体的な参照（`E2E-001`のようなテストケースID、またはテスト仕様書内のパス）で記載する。

画面の対象がすべて区分Cで、区分A/Bが1件も存在しない画面（純粋なXAML配線のみの画面等）もあり得る。その場合は`targets`を空配列にしたうえで、トップレベルに`noTargetsReason`（区分A/Bが存在しない理由）を必須で記載する。`noTargetsReason`が無いまま`targets`が空のマニフェストは、対象抽出漏れとみなし完了として扱わない。

テスト種別の重複も確認する。既存のE2E/手動テストで十分に担保済みの単純な画面配線・委譲のみを、カバレッジのためだけに単体テストへ重複させない。ただし、区分A/Bの判断ロジック・例外処理・境界値はE2Eの存在を理由に単体テストから除外しない。

リスクを「高（決済・認証・権限・データ整合性）」「通常」「低（DTO・単純委譲等）」に分類し、テストケース表にリスク列を追加する。高リスクの区分A/Bは、100%達成後にミューテーションテストの対象とする。

# ステップ6 テストケース作成
テストケースは表形式で出力する。
| ID | 根拠（AC/分岐） | 分類 | 入力 | 期待値 | リスク | 既存テスト対応 | 理由 |
| -- | -- | -- | -- | --- | -- | -- | -- |
例
|TC-001|AC-001|正常|20|true|通常|新規|成人判定|

|TC-004|AC-002|異常|null|ArgumentNullException|通常|新規|引数検証|

理由列は必須。

# ステップ7 分岐対応確認
実装中の全分岐について（区分A・Bで抽出した部分のみ対象）

分岐対応表には、true/false、switchの各case/default、`&&`/`||` の短絡評価、例外へ進む経路を個別に記載する。行が実行されていても片側しか通っていない分岐は未カバーとして、対応TCを追加する。
| 分岐 | 対応TC |
| -- | ---- |

例
| 分岐              | 対応TC   |
| --------------- | ------ |
| age >= 20 true  | TC-001 |
| age >= 20 false | TC-002 |

未対応分岐がある場合はテストケースへ追加する。

# ステップ9 テストコード生成
xUnitを使用する。
既存のテストプロジェクト・命名規約・配置に従う。存在しない場合のみ、対象プロジェクトと同階層に`<ProjectName>.Tests`のテストプロジェクトを作成し、実装クラスに対応する`<ClassName>Tests.cs`へ格納する。

## 品質契約
テストコードを書く前に、各TCについて「このテストを失敗させる実装変更」と「観測する振る舞い」を1つずつ明示する。説明できない場合は、テストが実装詳細か到達確認だけになっているため、ステップ6へ戻って設計し直す。

テスト名は`<対象>_When<条件>_<期待結果>`とし、`正常系`、`Test1`、`ShouldWork`のような抽象名を禁止する。各テストは1つの振る舞いを検証し、戻り値・公開された状態・外部境界への意味のある副作用だけをAssertする。privateフィールド、内部キャッシュ、不要な呼び出し回数をAssertしない。

ステップ2の重複確認で「再利用」または「拡張」とした既存テストは、対応TCを追加・更新して利用する。同じ入力・期待結果・副作用を別名の新規テストとして作らない。

---

## AAAパターン必須
```csharp
[Fact]
public void IsAdult_WhenAgeIs20_ReturnsTrue()
{
    // Arrange
    var sut = new AgeService();

    // Act
    var result = sut.IsAdult(20);

    // Assert
    Assert.True(result);
}
```

---

## Theory優先
複数入力パターンはTheoryを利用する。
```csharp
[Theory]
[InlineData(19,false)]
[InlineData(20,true)]
[InlineData(21,true)]
public void 成人判定(int age,bool expected)
{
    // Arrange
    var sut = new AgeService();

    // Act
    var result = sut.IsAdult(age);

    // Assert
    Assert.Equal(expected, result);
}
```

---

## InlineDataとMemberData
少数で読みやすい値は`InlineData`を使う。複雑なオブジェクト、生成手順のある入力、多数のケースは`MemberData`またはテストデータビルダーを使う。件数だけを理由に機械的に切り替えない。

---

## 例外テスト
```csharp
[Fact]
public void Validate_WhenInputIsNull_ThrowsArgumentNullException()
{
    // Arrange
    var sut = new RegistrationValidator();

    // Act
    var action = () => sut.Validate(null!);

    // Assert
    Assert.Throws<ArgumentNullException>(action);
}
```

Assert.Throws<T>()を利用する。
非同期メソッドの例外検証はAssert.ThrowsAsync<T>()を利用する。

---

## 非同期テストの注意
`[Fact]`/`[Theory]`のテストメソッドが非同期処理を呼ぶ場合、テストメソッド自体を`async Task`として実装し、内部の呼び出しは必ず`await`する。
`await`を忘れると例外が握りつぶされ、Assertに到達しないままテストが成功する「見せかけの成功」になる。
`async void`のテストメソッドは使用しない（xUnitが完了を待機できず、内部例外がテスト失敗に反映されない）。

---

## モック利用
外部依存はモック化する。
既存プロジェクトのダブル用ライブラリと規約を優先する。規約が無い場合はMoqを用い、対応できない箇所は無理に作成せず報告する。
呼び出し検証が必要な場合のみ、以下を検証する（不要な場合はStubで済ませる。上記「ダブルの選択基準」参照）。
* 呼び出し回数
* 引数
* 戻り値

例
```csharp
mockRepository.Verify(
    x => x.Save(It.IsAny<User>()),
    Times.Once
);
```

# ステップ10 カバレッジ測定
テストコード生成・実行後、実際のカバレッジを測定し数値で報告する。

## 測定方法
まず既存のカバレッジツールとCI設定を確認し、それを利用する。未導入の場合は、ローカル計測には`coverlet.collector`、閾値でCIを失敗させるには`coverlet.msbuild`のいずれかを選ぶ。同じテストプロジェクトに両方を追加しない。

ローカル計測でcollectorを使う場合:
```bash
dotnet add <TestProject>.csproj package coverlet.collector
dotnet test <Solution>.sln --collect:"XPlat Code Coverage" --results-directory ./TestResults
```
HTMLレポートが必要で`reportgenerator`が導入済みの場合のみ、Cobertura出力から生成する。

## 評価方法
* 分母はステップ3区分A（＋抽出済みの区分B）の対象クラス・メソッドのみとする。区分Cは分母に含めない。
* 対象範囲は行カバレッジ80%以上に加え、分岐カバレッジも80%以上を目標とする。レポートから未カバーの分岐・行を特定し、ステップ6のテストケースへ追加する。意味のないテスト（アサーション無し・trivialなgetter等）で数値を埋めてはいけない。
* 画面完了時は、ステップ5で確定した当該画面の区分A/Bについて、行・分岐カバレッジとも100%を必須とする。対象に含まれる既存コードも分母に含める。未カバーの振る舞いがある場合はテストケースを追加し、100%未達のまま完了としない。
* 高リスクかどうかにかかわらず画面対象の区分A/Bは100%とする。高リスクの箇所は、100%に加えてミューテーションテストの対象とする。
* 画面対象外にある区分Bの「抽出見送り」により全体ベースライン80%へ届かない場合は、理由を明記して報告する。画面対象に含めた区分Bは100%の対象であり、未達のまま完了としない。
* WPF/UI/E2E経由でのみ実行される画面コードは、別プロセス起動のUIテスト（例：FlaUI等でexeを別プロセス起動する方式）ではテストプロセス側のカバレッジ計測に反映されないことがある。この場合、当該コードが実際にE2E/手動テストで検証されている記録（テスト仕様書の実施結果）を確認し、「カバレッジ数値上は低いが別経路で担保されている」ことを報告に明記する。確認できない場合は空白として扱う。

## 除外の統制
`[ExcludeFromCodeCoverage]`、coverletのフィルター、生成コード除外は、区分C・生成物・テスト対象外として事前に根拠を示した範囲にだけ適用する。業務ロジック、バリデーション、権限制御、例外処理を閾値達成のためだけに除外してはならない。

除外を追加・変更した場合は、対象、理由、代替担保、変更前後の分母への影響を報告する。属性をクラスに付与すると全メンバーが除外され得るため、必要最小の対象に付ける。

## ゲートの検証
CIにカバレッジ閾値を設定する場合は、設定して終わりにせず、実際に機能するかを確認する。`coverlet.collector`による`--collect:"XPlat Code Coverage"`は閾値判定を直接行わないため、Coverletの閾値でゲートする場合は、collectorと併用せず`coverlet.msbuild`を使用する。

```bash
dotnet add <TestProject>.csproj package coverlet.msbuild
dotnet test <Solution>.sln /p:CollectCoverage=true /p:Threshold="80,80" /p:ThresholdType="line,branch" /p:ThresholdStat=Total
```

上記の80%は全体ベースライン用である。画面完了の100%ゲートは、ステップ5の対象クラス・メソッドだけを含むレポートまたはCIジョブで評価する。画面ごとの対象定義をせずにアセンブリ全体へ100%を課してはならない。

### 画面100%ゲート
VSTestモードで`coverlet.msbuild`を使うプロジェクトでは、画面カバレッジ・マニフェストごとに、同梱の`scripts/Invoke-ScreenCoverage.ps1`を実行する。

```powershell
& <SKILL_DIR>\scripts\Invoke-ScreenCoverage.ps1 `
  -ManifestPath tests/MyApp.Tests/Coverage/Screens/MemberRegistration.json
```

このスクリプトはマニフェストを検証し、区分A/Bの`filter`だけをCoverletの`Include`へ渡して、行・分岐とも100%未満なら非ゼロで終了する。CIでは画面完了ごとに該当マニフェストを引数として同じスクリプトを実行する。

Microsoft.Testing.Platform v2では`coverlet.msbuild`による計測は使用できない。その場合は、このゲートを適用する前に、使用中のテストプラットフォームで対象型をフィルターし、行・分岐100%未満を非ゼロ終了にする同等のCI手段を整備する。整備できない場合、画面100%を達成したとは報告しない。

閾値を一時的に現状値より高い値（例：99）に変更し、ビルド/テストコマンドが非ゼロ終了することを確認する。ゼロ終了する場合は閾値の指定方法（プロパティ名・対象プロジェクトの誤り等）を疑う。確認後は元の値に戻す。

## ミューテーションテスト
カバレッジは「実行されたか」しか示さない。ミューテーションテストはソースを機械的に微小改変（`>`→`>=`、`true`→`false`等）し、テストがその変化を検知（＝失敗）できるかを確認する。検知できなければテストは実行されているだけで検証していない。

対象範囲は、新規・変更された高リスクまたは重要な業務ロジック（区分A、および抽出済み区分B）に限定する。区分Cおよびテスト対象外（DTO/Mapper/Entity等）は対象に含めない。単純な委譲、UI配線、低リスクの変更には実施しない。

.NETでは Stryker.NET (`dotnet-stryker`) を用いる。
```bash
dotnet tool install -g dotnet-stryker   # 未導入の場合
dotnet stryker --project <Project>.csproj
```

| スコア | 判定 |
| -- | -- |
| 90%以上 | 十分。ロジック変更のほとんどを検知できている |
| 70～89% | 目安達成。重要分岐の生存ミュータントは個別に確認 |
| 70%未満 | テストは実行されているが検証になっていない |

生存したミュータントのうち、実装を変えても外部から観測可能な違いが生まれない同値ミュータント（equivalent mutant）は、検知不能が正当なため除外してよい。除外する場合は理由を明記する。

# テスト不要項目
以下は原則テスト対象外とする。
* DTO
* Entity
* AutoProperty
* 単純なGetter
* 単純なSetter
* Mapperのみの処理
ただし業務ロジックを含む場合は対象とする。

# 完了条件
以下を全て満たした場合に完了とする。
* テストケース承認済み
* 全分岐に対応するテストケースあり（区分A・Bの範囲）
* テストコード生成済み
* テスト成功
* 対象範囲（区分A・B）の行・分岐カバレッジ80%以上、または未達の場合は理由を明記して報告済み
* 既存テストとの照合結果（再利用/拡張/新規）を報告済み
* 画面と対象クラス・メソッドの対応表、および画面カバレッジ・マニフェストを確定・バージョン管理へコミット済み
* 画面100%ゲートが100%未満で非ゼロ終了することを確認済みで、当該画面の区分A/Bは行・分岐カバレッジ100%（区分A/Bが存在しない画面は`noTargetsReason`を報告済み）
* 区分Cの除外理由と代替担保手段（E2E/手動確認の実施記録）を報告済み
* デッドコード候補は到達不能根拠と削除または開発者判断を報告済み
* `[ExcludeFromCodeCoverage]`等の除外は対象・理由・代替担保・分母への影響を報告済み
* テスト結果・カバレッジ測定結果報告済み
* CIにカバレッジ閾値を設定した場合、閾値超過時に非ゼロ終了することを確認済み
* 新規・変更された高リスクまたは重要な業務ロジックがある場合は、mutation test実施済みでmutation scoreが80%以上（同値ミュータント除外後の数値。未達の場合は生存ミュータントと対応方針を明記）
