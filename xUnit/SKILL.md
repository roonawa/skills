# 目的
実装コードからテスト観点を抽出し、以下を行ったうえでxUnitテストコードを作成する。
* テストケースの抜け漏れ防止
* 境界値の網羅
* 例外処理の確認
* 分岐網羅
* 副作用の検証

---

# 基本原則
テストは実装の再現ではなく仕様の検証である。
実装変更に強く、仕様変更時のみ失敗するテストを優先する。

テストコードを先に生成してはいけない。
必ず以下の順で進める。
1. 仕様解析
2. 実装解析　
3. 実装範囲確認
4. テストケース設計
5. レビュー
6. テストコード生成

1テスト1責務を原則とする。
複数の検証項目を1テストへ詰め込まない。
Assertは意味的に1つを推奨する。
カバレッジ向上のみを目的とした意味のないテストを生成してはいけない。
業務価値の低いテストは生成しない。
以下は原則生成しない。
* privateメソッド単体
* 実装詳細の検証
* モックの過剰Verify
* 単純なGetter/Setter
---

# 全体フロー
```text
[仕様解析]
↓
[実装解析]
↓
[実装範囲確認]
↓
[テスト観点抽出]
↓
[テストケース作成]
↓
[レビュー用チェックリスト出力]
↓
[開発者承認]
↓
[テストコード生成]
↓
[テスト実行]
↓
[結果報告]
```
承認を得る前にテストコードを生成してはいけない。

# ステップ1 仕様解析

対象機能の仕様を解析し、期待される振る舞いを抽出する。
実装よりも仕様を優先する。
実装と仕様に差異が存在する場合はテストコードを生成せず、差異を開発者へ報告する。
仕様情報源
優先順位は以下とする。

* テスト仕様書（spec-test）
* 詳細設計書（spec-detail）
* 基本設計書（spec-basic）
* 要件定義書
* ソースコードコメント
* 実装コード
それぞれ必要な情報が不足している場合は、憶測せずに必ず必要な情報を質問すること。
仕様が存在しない場合のみ、実装を暫定仕様として扱う。
ただし以下を明示すること。
「期待値は実装から推定」

## 業務ルール抽出

以下を抽出する。

- 入力条件
* 例
年齢は0～120歳

- 出力条件
* 例
18歳以上は成人

- 業務制約
* 例
退会済ユーザーは申請不可

- データ制約
* 例
メールアドレス最大255文字

- 受入条件抽出
仕様から受入条件を抽出する。
* 例
ID	受入条件
AC-001	成人判定が正しく行われる
AC-002	null入力時に例外となる
AC-003	年齢上限を超えた場合はエラー

受入条件ごとに最低1件以上のテストケースを作成する。

* 対象処理が業務フロー内のどの位置に存在するか確認する。

↓

↓
通知

状態遷移抽出

正常遷移

例

以下を確認する。

許可される操作

実装との差異確認

* 仕様から期待結果を抽出した後、実装との差異を確認する。

例

仕様

差異を検出した場合は以下を出力する。

項目	仕様	実装
成人年齢	18	20

差異解消までテストコード生成を停止する。

* テスト対象範囲確定

仕様から以下を分類する。

差異がある場合のみ出力する。

* internalメソッド
* テスト対象メソッド

---

## 入力
* 引数
* 戻り値
* nullable有無

---

## 条件分岐
以下を全て列挙する。

if
else if
switch
switch expression
?:演算子
&&
||

例
```c#
if(age >= 20)
```
↓
```text
条件:
age >= 20

分岐:
true
false
```
短絡評価も分岐として扱う。

例：
if (a && b)

分岐:
a=false
a=true,b=false
a=true,b=true
---

## 例外
明示的または暗黙的に発生する例外を列挙する。
例
```c#
throw new ArgumentNullException()
```
```c#
int.Parse()
```
```c#
First()
```
```c#
Single()
```

---

## 外部依存
以下を検出する。
* Repository
* DbContext
* HttpClient
* API Client
* File
* Directory
* Environment
* DateTime.Now
* DateTime.UtcNow
* Guid.NewGuid
* Random
検出した場合はMoqを使用したモック化方針を提示する。
非virtualメソッドやsealedクラスがモックできない場合は報告し、無理なモック化を行わない。
モックが効果的でない場合は、該当する単体テストを生成せず後工程のテストに回す旨を報告する。

# ステップ5 テストケース作成
テストケースは表形式で出力する。
| ID | 分類 | 入力 | 期待値 | 理由 |
| -- | -- | -- | --- | -- |
例
|TC-001|正常|20|true|成人判定|
|TC-002|境界値|19|false|下限確認|
|TC-003|境界値|20|true|境界確認|
|TC-004|異常|null|ArgumentNullException|引数検証|

理由列は必須。

# ステップ8 テストコード生成
xUnitを使用する。
テストコードは実装ファイルと同階層に__tests__フォルダを作成し(既にある場合は省略)、__tests__内に格納する。

---

## AAAパターン必須
```csharp
[Fact]
public void 正常系()
{
    // Arrange

    // Act

    // Assert
}
```

---

## Theory優先
複数入力パターンはTheoryを利用する。
```csharp
[Theory]
[InlineData(19,false)]
[InlineData(20,true)]
[InlineData(21,true)]
public void 成人判定(int age,bool expected)
{
    // Arrange

    // Act

    // Assert
}
```

---

## InlineData件数
5件を超える場合はMemberDataを利用する。

---

## 例外テスト
```csharp
[Fact]
public void Nullなら例外()
{
    // Arrange

    // Act

    // Assert
}
```

Assert.Throws<T>()を利用する。

---

## モック利用
外部依存はモック化する。
ライブラリはMoqで統一し、対応できない箇所は無理に作成せず報告する。
以下を検証する。
* 呼び出し回数
* 引数
* 戻り値

例
```csharp
mockRepository.Verify(
    x => x.Save(It.IsAny<User>()),
    Times.Once
);
```

---

# テスト不要項目
以下は原則テスト対象外とする。
* DTO
* Entity
* AutoProperty
* 単純なGetter
* 単純なSetter
* Mapperのみの処理
ただし業務ロジックを含む場合は対象とする。
