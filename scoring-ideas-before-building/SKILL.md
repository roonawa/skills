# Scoring Ideas Before Building

## Overview

AIによる開発はコストがほぼゼロになり、「作れてしまうこと」自体がリスクになる。ボトルネックは実装コストではなく、増えた機能を把握・レビュー・保守し、ユーザーが覚えなければならない**人間の認知コスト**である。このスキルは、モックや実装に着手する前にアイデアを100点満点で採点し、80点未満は作らないというゲートを設けることで、「作ってから判断する」を「作る前に判断する」に切り替える。

## When to Use

以下のような発言・状況で、コードやモックを書き始める**前に**自発的に発動する。頼まれるまで待たない。

- 「〜ってツール/機能があったら便利そう」「〜を作りたい」という思いつきが出たとき
- 新しい画面・メニュー・ボタン・設定項目を追加する提案が出たとき
- 既存機能に「ついでに」機能を足す提案が出たとき

以下には使わない：

- 明確なバグ修正、セキュリティ対応、障害対応
- 既に要件定義書・設計書で仕様が確定している実装（新規アイデアの発掘ではなく、決定事項の実行）
- ユーザーから「採点せず、まず作って」と明示された場合（その場合は理由を一言添えて従う）

## Core Pattern

```
アイデアが出る
  │
  ▼
① 4項目を埋める：誰が／いつ／何に困って／今どうしているか
  │   ※「今どうしているか」が「特に困っていない」なら
  │     困っている証拠の軸は自動的に最低評価にする
  ▼
② 7つの却下条件をチェック
  │
  ├─ 該当する ─→ その案は却下（0点扱い）
  │                └─→ ③には進まず、④の対案出しへ
  ▼（非該当）
③ 6軸・100点満点で採点
  │
  ├─ 80点未満 ─→ 却下
  └─ 80点以上 ─→ 合格（暫定）
  ▼
④ 対案を3つ出す：縮小案／統合案／逆張り案
  │   （②で却下された案についても必ず出す）
  │   各対案も②③と同じ基準で採点する
  ▼
⑤ 元の案と対案の最高点を比較し、最高点の案を推奨として提示
  │
  ▼
⑥ 却下・採用にかかわらず、全案を台帳に記録する
```

## Quick Reference

**7つの却下条件**（1つでも該当したら即却下。採点に進まない）

1. 既存機能と役割が重複している
2. 解決策が実質「設定項目を増やす」だけになっている
3. 受益者が開発チーム自身だけで、実ユーザーへの価値を説明できない
4. 既存の外部ツール・連携で代替可能である
5. 恒久的な保守負荷が発生するのに、保守担当が決まっていない
6. 動機が「作ってみたい」「技術的に面白そう」であり、課題起点になっていない
7. 過去に台帳で同種の案が却下されており、却下時の状況から何も変わっていない

**6軸・配点（合計100点）**

| 軸 | 配点 | 採点の考え方 |
|---|---|---|
| 困っている証拠 | 25 | 実際の問い合わせ・ユーザーテストでの観測がなければ最大1点。「便利そう」「あると嬉しい」「競合にもある」は根拠として認めない |
| UIの軽さ | 15 | 新しい画面・新しいメニューを追加する案は減点対象。既存動線内で完結するほど高得点。 |
| 課題の頻度・深刻さ | 20 | どれだけの頻度で、どれだけ深刻に困っているか |
| 解決策の的確さ | 15 | 提案が課題の根本原因を直接解くか、単なる回避策の後追いになっていないか |
| 受益範囲 | 15 | 恩恵を受けるユーザー数・製品の中核価値との近さ |
| 保守・複雑性コスト（逆評価） | 10 | 実装後の保守負荷や複雑性が低いほど高得点 |

**合否ライン**：合計80点未満は「作らない」。80点以上でも、対案の方が高得点なら対案に乗り換える。

## Implementation

### ①〜③ ヒアリングと採点

4項目と却下条件、6軸採点結果を以下のフォーマットでユーザーに提示する。

```
## アイデア採点：<アイデアの一言要約>

**誰が**：<対象者>
**いつ**：<発生タイミング>
**何に困って**：<課題>
**今どうしているか**：<現状の回避策 or 「特に困っていない」>

**却下条件チェック**：該当なし／該当（第N条：<内容>）

**採点**（却下条件に該当した場合はここは省略し「却下」とだけ記す）
| 軸 | 点数 |
|---|---|
| 困っている証拠 | x/25 |
| UIの軽さ | x/15 |
| 課題の頻度・深刻さ | x/20 |
| 解決策の的確さ | x/15 |
| 受益範囲 | x/15 |
| 保守・複雑性コスト | x/10 |
| **合計** | **x/100** |

**判定**：作る／作らない（80点ライン）
```

### ④ 対案の出し方

却下・合格にかかわらず、必ず3つ出す。

- **縮小案**：新しいUI要素を増やさずに解く案
- **統合案**：既存の画面・機能の中に組み込む案
- **逆張り案**：そもそも機能を足さずに課題を解く案（自動化、通知、運用でカバーなど）

それぞれを①〜③と同じ基準で簡易採点し、元の案と並べて最高点を推奨する。

### ⑤ 具体例

提案：「検索条件を保存できる『お気に入り検索』ボタンを検索画面に追加したい」

- 誰が：週次レポートを作る営業チーム3人／いつ：毎週月曜の朝／何に困って：毎回同じ検索条件を手入力するのが手間／今どうしているか：検索条件をメモ帳にコピペして使い回している（実際に回避策が運用されている＝一定の証拠あり）
- 却下条件：該当なし
- 採点：困っている証拠18/25、UIの軽さ6/15（新規ボタン追加のため減点）、頻度・深刻さ14/20、解決策の的確さ12/15、受益範囲6/15（3人限定）、保守コスト8/10 → **合計64点 → 作らない**
- 対案：
  - 縮小案：検索結果ページのURLをブラウザのブックマークに保存する運用に変える（新規UIなし）
  - 統合案：既存の「フィルタ」機能があればその保存先に統合する
  - 逆張り案：営業チームがよく使う検索条件の結果を毎週月曜朝に自動配信する（そもそも検索させない）
- 逆張り案を採点すると、UIの軽さ15/15・解決策の的確さ14/15などで82点となり、こちらを推奨として提示する

### ⑥ 台帳への記録

却下・採用にかかわらず全件を記録する。台帳ファイルがなければ、リポジトリ直下（プロジェクトのルート、対象がリポジトリでなければ作業ディレクトリ）に `IDEA_LEDGER.md` を新規作成してよいか一言確認してから作る。既にある場合はその末尾に追記する。

```
| 日付 | 提案 | 判定 | 合計点 | 却下理由/決め手 | 採用案 | 次に何が変われば通るか |
|---|---|---|---|---|---|---|
| 2026-09-28 | お気に入り検索ボタン | 対案採用 | 64→82 | UI追加が減点 | 週次自動配信 | - |
```

「次に何が変われば通るか」は、将来同じ発想が出たときに台帳を参照して却下条件7を判定できるように、具体的に書く（例：「営業チームが5人を超えて自動化の運用コストに見合うようになったら」）。

## Common Mistakes

- **聞かれるまで採点しない**：このスキルの価値は自発的に発動することにある。アイデアが口に出た時点で、頼まれなくても採点を始める
- **「あると嬉しい」を証拠として認めてしまう**：困っている証拠の軸は、実際の問い合わせやユーザーテストの観測がない限り最大1点。他の軸の高得点で相殺させない
- **却下条件チェックを飛ばして軸採点に直行する**：却下条件は軸採点より先に確認する。該当すれば軸採点自体を省略する
- **却下して終わりにする**：却下した案にも必ず対案を3つ出す。対案を出さない却下は未完了とみなす
- **台帳への記録を忘れる、却下案を記録から漏らす**：合格案だけでなく却下案も記録する。半年後に同じ発想が出たときの判断材料になる
- **「今どうしているか」が「特に困っていない」なのに他の軸だけで押し切る**：現状困っていないアイデアは、どれだけ良い機能に見えても採用しない
