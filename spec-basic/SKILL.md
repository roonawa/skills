---
description: カスタムソリューション部の受託開発における基本設計の壁打ちから基本設計書（Md）の出力までを一気通貫で支援する
---

## 目的

カスタムソリューション部の受託開発において、要件定義書（spec-req出力）をインプットとして、機能の振る舞い・外部仕様を決定する基本設計書（Md）を一気通貫で作成するスキル。

以下を実現する：
- 要件定義書 → 基本設計書 への展開を機械的に実施
- FR-ID →　BD-ID →　AC-ID →　BR-ID のトレーサビリティ確保
- 顧客レビュー可能な統一フォーマットで出力
- 反復ブラッシュアップで段階的に品質向上

**このスキルが作る文書は顧客レビュー対象**（外部仕様凍結フェーズ）。内部実装の詳細は `spec-detail` に委ねる。

## スコープ

### やること
- 上流要件定義書の読み込み（FR-IDの自動展開、案件メタ情報の引継ぎ）
- 5項目の基本設計書作成のための壁打ち（草案フェーズ）
- 草案を基本設計書テンプレートに整形（整形フェーズ）
- 整形後のブラッシュアップサイクル（項目単位／BD-ID単位での部分修正・深堀り）
- 既存基本設計書からの再開モード
- BD-ID自動付与（BD-001, BD-002...）と上流FR-ID連結
- バージョン自動管理（v0.1 → v0.2 → ... → v1.0）
- 「⚠ 要確認」の明示
- 顧客レビュー依頼を促すメッセージ出力

### やらないこと
- 内部実装仕様の決定（→ `spec-detail`）
- テストケース生成（→ `spec-test`）
- 工数見積もり
- 構成図の自動描画（テキストベース／mermaid記法での記述は支援）

## 全体フロー

```
[起動]
  ↓
[起動モード選択]
  ├─ A. 新規作成（上流ファイルを指定）
  └─ B. 既存基本設計書から再開（→ ブラッシュアップサイクルから開始）
  ↓
① 上流ファイル読み込み
  └─ 要件定義書からFR-ID・案件メタ情報を展開してメモリに保持
  ↓
② 草案フェーズ（壁打ち）
  ├─ 設計概要・前提
  ├─ システム構成
  ├─ 機能設計（FR-IDごとにBD-IDへ展開）
  ├─ 画面・データ・I/F設計
  ├─ 受け入れ条件
  ├─ 業務フロー
  └─ 非機能要件・制約・リスク
  ↓ ループ：「他に深堀りしたい項目は？」
  ↓
【チェックポイント1】整形に進む前の確認
  ↓
③ 整形フェーズ
  └─ 基本設計書 v0.1 として出力
  ↓
④ ブラッシュアップサイクル（反復可能）
  ├─ 修正モード選択
  │   ├─ a. 項目単位で深堀り
  │   ├─ b. BD-ID単位でピンポイント修正
  │   ├─ c. 新規追加
  │   └─ d. これでOK → 終了
  ├─ ピンポイント壁打ち
  ├─ 該当箇所のみ更新（バージョン自動インクリメント）
  └─ サイクル先頭に戻る
  ↓ 「これでOK」が出た時点
  ↓
【チェックポイント2】v1.0確定前のレビュー依頼（v1.0確定時のみ発動）
  ↓
基本設計書 v1.0 として確定
```

## 起動時の動作

スキルが起動したら、最初に起動モードを確認する。

> 「基本設計スキル（spec-basic）を起動した。以下のどちらで進める？
> A. 新規作成（要件定義書を上流ファイルとして指定し、ゼロから壁打ちを始める）
> B. 既存ファイルから再開（途中の基本設計書を読み込んで続きから）」

- **Aを選んだ場合**：上流ファイル読み込みから開始
- **Bを選んだ場合**：既存ファイルのパスを聞き、読み込んでブラッシュアップサイクルから開始

---

## 上流ファイル読み込み

### 上流ファイルの指定

> 「要件定義書（spec-req出力）のファイルパスを教えて」

指定されたファイルを読み込み、以下をメモリに展開する：
- 案件メタ情報（案件名、顧客名、自社担当、案件タイプ）
- FR-ID 一覧（機能名、概要）
- 未展開FR-ID数
- 受け入れ条件候補
- 業務ルール候補
- 画面要素候補
- 外部I/F候補
- スコープ（やること／やらないこと）
- 制約・前提・リスク（要確認事項を含む）

読み込んだ内容を要約して提示してから草案フェーズに進む。

### 省略運用

要件定義書がない場合は、顧客提供の仕様書・発注書等を上流ファイルとして指定可。その旨を整形フェーズで「設計概要・前提」セクションに明記する。

上流ファイルとして直前フェーズ（spec-req出力）だけでなく、より上流のファイルも指定可（省略運用に対応）。

---

## 草案フェーズの壁打ち（5項目）

質問は**1問ずつ**投げる。複数の質問を一度に投げない。回答内容に応じて追加深堀りを行う。

### 項目1：設計概要・前提

分析結果を要約して利用者へ提示する
1. 「上流要件定義書を読み込んだ。設計上の前提・方針は？（既存システムとの関係、技術スタック、開発体制など）」
2. 「上流要件定義書の中で、特に注意が必要な要件・要確認事項はある？」

### 項目2：システム構成

1. 「システム構成は？対象システム単独か、外部システムとの連携あり？」
2. 「稼働環境は？（オンプレ／クラウド、OS、ミドルウェア、ネットワーク要件）」
3. 「構成図はテキスト表現（mermaid等）でMd内に含める？別途作成？」

### 項目3：機能設計（BD-IDで一覧）

上流要件定義書のFR-IDを1件ずつ順番に確認する。各FR-IDについて以下を順に確認：

1. 「FR-XXX（機能名）を基本設計に展開する。1対1（BD-XXX 1件）か、複数のBD-XXXに展開するか？」
2. 「展開する機能の振る舞いは？ユーザー操作、業務フロー、入出力データを教えて」
3. 「画面が必要な機能か？画面遷移は？」
4. 「処理タイミングは？（同期／非同期、リアルタイム／バッチ等）」

全FR-IDの確認が完了したら、整形フェーズで BD-001 から自動採番する。各BD-IDに上流FR-IDを連結する。

### 項目4：画面・データ・I/F設計

画面・I/Fが不要な案件では「該当なし」と明記する（空欄禁止）。

#### 4.1 画面（必要な場合のみ）
1. 「画面一覧を挙げて」
2. 「画面遷移はどう描く？（テキスト表現で整理する？）」

#### 4.2 データ
1. 「データ構造は？（テーブル、エンティティ、項目一覧）」
2. 「ER図はテキスト表現でMd内に含める？」

#### 4.3 外部I/F
1. 「外部I/Fは？（API、ファイル連携、メッセージング、DB直接アクセス等）」
2. 「I/F仕様の詳細はここで決める？それとも別ドキュメント？」

### 項目5：非機能要件・制約・リスク

1. 「性能要件は？（レスポンスタイム、同時接続数、データ量等）」
2. 「セキュリティ要件は？（認証、権限、暗号化、監査ログ等）」
3. 「運用要件は？（監視、バックアップ、障害対応、ログ）」
4. 「拡張性・保守性の要件は？」
5. 「現時点で未確定の事項や確認が必要な事項は？」→ 「⚠ 要確認」マーク付きで記録

### 5項目完了後の確認

5項目すべての壁打ちが完了したら以下を確認する：

> 「ひと通りの壁打ちが完了。他に深堀りしたい項目はある？なければ整形フェーズに進む。」

- **「あり」の場合**：該当項目に戻って追加質問を行う
- **「なし」の場合**：チェックポイント1へ

---

## チェックポイント1：草案完了時

整形フェーズに進む前に以下を伝える：

> 「基本設計の草案ができた。整形に進む前に、漏れがないか確認したい項目はある？人にレビューを依頼する場合はここで一旦止めて。」

確認が取れたら整形フェーズに進む。

---

## 整形フェーズ

草案の内容を以下の構造に整形してMdファイルとして出力する。

**出力テンプレート：**

```markdown
# 基本設計書：<案件名>

| 項目 | 内容 |
|---|---|
| 案件タイプ | <新規開発／機能追加／リニューアル> |
| 上流ファイル | <要件定義書のパス> |
| 作成日 | YYYY-MM-DD |
| 顧客 | <顧客名> |
| 自社担当 | <担当者> |
| バージョン | 0.1（草案） |

## 1. 設計概要・前提
（案件サマリ・設計方針）

### 1.1 上流要件定義書との対応
| FR-ID | 機能名 | 展開先BD-ID |
|---|---|---|
| FR-001 | ... | BD-001, BD-002 |
| FR-002 | ... | BD-003 |

## 2. システム構成
### 2.1 構成図
（テキスト or mermaid）

### 2.2 外部システム連携
- ...

### 2.3 稼働環境
- ...

## 3. 機能設計
| BD-ID | 機能名 | 振る舞い | 上流FR-ID | 備考 |
|---|---|---|---|---|
| BD-001 | ... | ... | FR-001 | ... |
| BD-002 | ... | ... | FR-001 | ... |

### 3.1 各機能の詳細(受け入れ条件)
- テスト仕様書を高い精度で作成するための情報
| AC-ID | BD-ID | 条件 |
|---------|---------|---------|
| AC-001 | BD-001 | 必須項目が入力されている |
| AC-002 | BD-001 | メール形式が正しい |

### 3.2 業務ルール
- 境界値テスト等の材料になる
| BR-ID | 内容 |
|---------|---------|
| BR-001 | 100万円超は部長承認 |
| BR-002 | 在庫0以下は出荷不可 |

### 3.3 入力項目定義
| 項目 | 型 | 必須 | 桁数 | 制約 |
|---------|---------|---------|---------|---------|
| 氏名 | string | ○ | 50 | 全角 |
| 年齢 | int | ○ | 3 | 0～120 |

### 3.4 状態遷移
| From | To | 条件 |
|---------|---------|---------|
| 下書き | 申請中 | 申請実行 |
| 申請中 | 承認済 | 承認実行 |

### 3.5 エラーハンドリング
- 汎用できるものはテンプレートとして流用する
| ERR-ID | 条件 | メッセージ |
|---------|---------|---------|
| ERR-001 | 必須未入力 | 必須項目です |
| ERR-002 | 重複メール | 既に登録済です |

## 4. 画面・データ・I/F設計
### 4.1 画面
- 画面一覧、遷移図（画面がない場合は「該当なし」）

### 4.2 データ
- テーブル定義、ER図

### 4.3 外部I/F
- API仕様、ファイルレイアウト等（外部I/Fがない場合は「該当なし」）

## 5. 非機能要件・制約・リスク
### 5.1 非機能要件
- 性能、セキュリティ、運用、拡張性

### 5.2 制約
- ...

### 5.3 リスク・要確認事項
- ⚠ <未確定事項> — 要確認
```

**BD-IDの採番ルール：**
- BD-001から連番で自動採番する
- 1つのFR-IDから複数のBD-IDへの展開（1対多）を許容する
- ブラッシュアップサイクルで機能追加した場合は続き番号を付与する（既存IDは変えない）
- 採番済みのBD-IDを振り直さない

整形完了後、ファイルの保存先を利用者に確認してから書き込む。ファイル名は以下の規則に従う：

```
基本設計書_<案件名>_v0.1_<YYYY-MM-DD>.md
```

## ブラッシュアップサイクル
整形フェーズ完了後、または既存ファイル再開モード起動時に利用者に報告する前に自己レビューする

- 要件漏れ
- FR未展開
- BD未展開
- DD未展開
- 受け入れ条件不足
- 業務ルール不足

自己レビュー完了後、利用者への報告を開始する。「これでOK」と利用者が伝えるまで何度でも繰り返せる。

### サイクル起動時の問いかけ

> 「現状の基本設計書（v0.X）を確認した。どこを修正・深堀りしたい？以下から選んで：
> a. 項目単位で深堀り（設計概要／システム構成／機能設計／画面・データ・I/F／非機能要件）
> b. 特定の機能設計をピンポイント修正（BD-IDを指定）
> c. 新規追加（機能設計・画面・I/F・リスク等を追加）
> d. これでOK（v1.0として確定）」

### 各モードの動作

| モード | 動作 |
|---|---|
| **a. 項目単位** | 5項目のいずれかを指定させる → 該当項目について追加質問・修正壁打ちを行う → 該当セクションのみ書き換える |
| **b. BD-ID単位** | 修正したいBD-ID（例：BD-003）を指定させる → 該当機能の詳細について壁打ちを行う → 該当行のみ更新する |
| **c. 追加** | 追加したい要素（新機能設計・画面追加・I/F追加等）を指定させる → 壁打ちを行う → 該当セクションに追記する（BD-IDは自動採番） |
| **d. OK** | ブラッシュアップサイクルを終了する → チェックポイント2へ |

### 部分更新の挙動

- 既存内容を保持しつつ、指定箇所のみ書き換える（全文書き直さない）
- 修正のたびにバージョン番号を自動インクリメントする（v0.1 → v0.2 → v0.3 → ...）
- バージョン管理の基本方針は上書き（最新版のみ保持。Git管理されている前提）
- 利用者が指示した場合のみ、旧版を `<案件フォルダ>/履歴/` に退避する

## 設計品質ゲート

以下を満たさない場合はv1.0化禁止

- 全FR-IDがBD-IDへ展開済み
- 全BD-IDがDD-IDへ展開済み
- 全DD-IDに受け入れ条件が存在
- 全DD-IDにエラーパターンが存在
- ⚠要確認が未解消の場合は理由を明記
- トレーサビリティ表に欠番なし

## チェックポイント2：v1.0確定時（必須）

利用者が「d. これでOK」を選択したら、以下を実行する：

1. バージョンを **v1.0** に確定する
2. ファイル名のバージョン部分を `v1.0` に更新する
3. 以下のメッセージを表示する：

> 「基本設計書を v1.0 として確定する。**基本設計書は顧客レビュー対象**。顧客提示前に、社内レビュー（部長／補佐）と顧客レビューを必ず受けてください。」

**重要**：チェックポイント2は v1.0 確定時のみ発動する。ブラッシュアップサイクルの途中（v0.2, v0.3 等）では発動しない。

## 既存ファイル再開モード

### 起動フロー

1. 起動モードでBを選択した場合
2. 「既存の基本設計書のファイルパスを教えて」と聞く
3. 指定されたファイルを読み込み、以下をメモリに展開する：
   - 案件メタ情報（案件名、顧客名、自社担当、案件タイプ）
   - 上流要件定義書のパス（再読み込みする）
   - BD-ID採番状況（次に振るBD-IDを把握する）
   - 各BD-IDの内容
   - 現在のバージョン番号
4. 読み込んだ内容を要約して提示し、ブラッシュアップサイクルから開始する
5. テンプレート構造から逸脱した記述がある場合は警告を出す

### 想定ユースケース
- 社内レビュー後の指摘を既存基本設計書に反映する
- 草案を作って一旦止めていた案件を後日再開する
- v1.0確定後に追加変更が出てきた場合の更新（v1.1, v1.2, ... で管理）

## 出力ファイルの規則

### ファイル名規則

```
基本設計書_<案件名>_v<バージョン>_<YYYY-MM-DD>.md
```

| 状態 | バージョン例 | 備考 |
|---|---|---|
| 整形フェーズ初回出力 | v0.1 | 草案を整形した直後 |
| ブラッシュアップ中 | v0.2, v0.3, ... | 修正のたびに自動インクリメント |
| FIX | v1.0 | 利用者が「OK」を出した時点で確定 |
| FIX後の追加修正 | v1.1, v1.2, ... | 顧客合意後の修正があった場合 |

### 保存場所
利用者がスキル起動時（または整形フェーズ完了時）に保存先を指定する。案件フォルダ配下に保存するのが基本。

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **上流ファイルは必須**：起動時に要件定義書のパスを必ず指定させる。要件定義書がない場合は顧客提供仕様書等で代替可（その旨を「設計概要・前提」に記載）
- **数値を推測で記載しない**。未確定の金額・工数・期日等は「⚠ 要確認」として明示する。想定値を記録しない
- **個人名の扱い**：ドキュメント上で個人名を匿名化する必要がある場合は「担当者A」「担当者B」等の役割表記を使う
- **BD-IDは振り直さない**。一度付与したIDは変更しない（後続スキルとのトレーサビリティを維持するため）
- **画面・I/Fが不要な案件では「該当なし」と明記**する（空欄禁止）
- **FR-ID → BD-IDのマッピング表（1.1節）は必ず生成**する。1対多展開を許容
- **チェックポイント2はv1.0確定時のみ**発動する。中間版では発動しない
- **不足情報がある場合**不足項目をリストアップし、ユーザーに提示して追加情報の提供を促す
- 工数見積もりはこのスキルのスコープ外。求められた場合は既存の見積プロセスで対応するよう案内する
- 構成図の自動描画はスコープ外。mermaid等のテキスト表現での記述は支援する
