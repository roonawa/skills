# CSアプリのネイティブ経由API回帰テスト

## 対象と実行境界

Allcampusの実CSアプリを起動し、**ネイティブ操作を経ないと呼び出せないAPI**が、画面操作から適切に呼ばれることをPT/ST間で比較する。ネイティブ操作はFlaUI/UI Automationで行い、その前後の画面操作はWebView2へのCDP接続で行う。Allcampus本体はWinForms＋WebView2であり、WPF専用アプリとは扱わない。プラグイン・ビューア・外部アプリのUI技術は実物で確認する。

対象にするのは、次の3つをすべて満たす「ネイティブ経由のAPI呼び出し」（以下、対象チェーン）だけである。

1. 機能がAPI（GraphQL・REST・バッチ・マイクロサービス等）を呼ぶ。呼び出し元はWebView2のJSでも、host object・プラグイン等のC#側でもよい。
2. そのAPI呼び出しは、ネイティブ操作の結果（選んだファイル・保存先・印刷設定・ネイティブ画面での入力等）を受けて初めて起きる。
3. DOM操作だけで同じAPI呼び出しに到達する経路が無い。たとえばファイルパスの入力欄に直接入力して読み込める取込は、DOMだけで到達できるので `cs-webview-regression-test` の範囲とする。代替経路の有無はソースで判断し、判断できなければ小さく実証する。

次は対象外とし、ケースにしない（棚卸しには理由付きで残す）。

- ネイティブ操作だけで完結し、APIを呼ばないもの：ダイアログのキャンセル・表示内容（タイトル・フィルタ）、IMEの切替・変換、ヘルプ等の外部ブラウザ起動、ローカル・NASへのログやファイルの書込み、APIを伴わない印刷・保存。
- DOM操作だけで到達できるAPI呼び出し（`cs-webview-regression-test` で確かめる）。
- APIへの直接リクエスト、API応答のモック、DB検証、認可・負荷テスト。

APIの呼び出しは、画面操作で起きたものを観測して確かめる。直接リクエストで代替しない。WebView2から出る呼び出し（host経由の中継を含む）はCDPのネットワークで記録する。C#側から出る呼び出しはCDPで見えないので、アプリのログ、依頼側から受け取るサーバー側のログ、出力物・画面の結果のうち観測できるもので確かめる。観測できない呼び出しは「比較不能」とし、「一致」にしない。

Web画面だけで完結するケースは `cs-webview-regression-test` に分ける。このスキルのハーネスは対象チェーン専用とし、通常のWebView2回帰と同時に起動・並列実行しない。UIAでフォーカスを使わず操作できる場合も、このスキルの実行はPC占有枠として扱う。

例外として、次の「ログイン前処理」だけは、WebView2回帰の各実行の直前に、その実行のための認証準備として行ってよい。前処理はケースではなく、`native-required` の件数にも数えない。

### ログイン前処理（WebView2回帰の認証準備）

CSアプリが起動時にWebView2の外のログイン画面（WinFormsのLoginView等）を出す構成で、`cs-webview-regression-test` の実行のために行う。

1. 実行前に「前処理でPCを占有する時間（目安）・起動するアプリ・入力するアカウントの区分」を利用者に示す。占有の可否の確認は「PC占有の扱い」に従う。
2. テスト用のTEMP・プロファイル・`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<空きポート>` を、起動する子プロセスにだけ渡してCSアプリを起動し、PIDを記録する。
3. 対象PIDのLoginViewを、AutomationId・ControlTypeで特定し、ログインIDとパスワードを ValuePattern で入力して、ログインのボタンを InvokePattern で押す。資格情報は、利用者が `C:\Users\roonawa\pw\cs.env` に用意したものを使う（下の「資格情報ファイル」）。ログ・証跡・スクリーンショットに残さない。パスワード欄が写る撮影をしない。
4. 完了の条件を期限付きで待つ：LoginViewが閉じる（非表示になる）こと、CDPのエンドポイントに対象ホストの `/CS/` のページが現れること。失敗のメッセージ（失敗・ロック・時刻ずれ・証明書の不具合）が出たら、その文言を記録して止める。同じアカウントで続けて再試行しない（ロックを招くため）。
5. PID・CDPポート・アカウントの区分・完了時刻を、これから流すWebView2回帰の run の `evidence/<run-id>/login-handoff.json` に書き、FlaUIのプロセスを終える。CSアプリのプロセスは終了しない（WebView2回帰が接続して使う）。
6. WebView2回帰の終了後、そのPIDだけを終了する手順は `cs-webview-regression-test` 側の後始末に従う。

**資格情報ファイル**：ログインIDとパスワードは `C:\Users\roonawa\pw\cs.env`（利用者が用意。`KEY=VALUE` 形式）から読む。キーは `GAKUMU_ST_ID`・`GAKUMU_ST_PASSWORD`・`GAKUMU_PT_ID`・`GAKUMU_PT_PASSWORD`で、対象環境（ST/PT。段階比較は実行する環境）のものだけを使う。

- 読み込みはハーネスのプロセス内で行い、値を ValuePattern へ渡す以外に使わない。会話・コマンドライン引数・ログ・`launch-*.json`・`login-handoff.json`・report.html・スクリーンショットに値を出さない。ファイルの中身を表示（cat・Read等）しない。必要なら存在とキー名だけ確かめる。
- ファイルをリポジトリへコピー・コミットしない。ファイルまたは対象環境のキーが無ければ、推測せず手動ログイン（次の段落）に切り替えて報告する。
- `login-handoff.json` には `login: auto-cs.env`・環境（ST/PT）・時刻だけを書く（IDも書かない）。

利用者が上のファイルの使用を指示しているので、既定は自動入力とする。それでもエージェントの安全規則等で自動入力が止まる場合は、3 を行わない。2 の起動までを行い、利用者に PID とアカウント区分を示して手でログインしてもらい、4 の完了条件を待つ。`login-handoff.json` に `login: manual` を書く。規則を回避する手段（別の入力方法・資格情報の転記）を取らない。

前処理の失敗は、WebView2回帰の側で「未実施（認証準備失敗）」として扱われる。前処理の中で画面の操作（ログイン後のメニュー操作等）まで進めない。

証明書方式のCSアプリは、OSの証明書ストアを使わず証明書の選択ダイアログを出さない作りである。前処理の途中で証明書の選択・PINの入力のダイアログが出たら、選ばずに止め、ダイアログの種類と所有プロセスを記録して利用者に報告する（アプリの不具合候補として扱う）。

## PC占有の扱い

スキルの作成・ケース設計・コード調査・ハーネス作成・ビルド・結果の比較はPC占有なしで進める。**GUI実行直前**に、対象ケース、前面化・キー操作等の有無、実行場所、終了または中断条件を提示する。

利用者が今回の実行時間にPCを空ける旨を伝えていれば再確認しない。占有可能な時間が未指定なら、「このPCで今実行できるか、専用Windows PC/VMで実行するか」を確認し、GUI実行だけ待つ。スキルを作る依頼をGUI実行の許可とは扱わない。

専用PC/VMを使う場合も、そのWindows対話セッションが使用可能か確認する。実行中は画面ロック・セッション切断・人の入力を避ける。サービス/Session 0やロックされたデスクトップでGUIが安定動作すると仮定しない。RDP切断時の挙動は採用環境で確認する。

占有開始・終了を明示する。停止依頼を受けたら新しい操作を止め、処理中の更新・出力の状態を確認し、安全に停止する。終了時はケース結果、残っているウィンドウ、復元・片付け状況を伝え、PCを再利用できる状態か報告する。

占有枠の終了が近い場合は、終了・復元に必要な時間を残し、新規ケースを開始しない。途中の処理を安全に終えられない場合は状態を伝え、時間切れだけを理由に強制終了しない。

## ケースの入力と引継ぎ

`cs-webview-regression-test` が生成した `native-handoff.md` があれば読む。なくても利用者が指定した機能を扱える。引き継がれた項目・指定された機能も、「対象と実行境界」の3条件で選び直す。条件を満たさない項目はケースにせず、棚卸しに「対象外（APIなし）」「対象外（webviewで到達可）」として理由を書き、報告で引継ぎ元へ返す。対象チェーンについて、最低限次を揃える。

- TC-ID、画面・ロール、PT/STのURL、実行するexe/DLL/Web版の組合せ。
- ネイティブ操作へ到達する手順、対象ウィンドウ・操作、その後に呼ばれるAPI（操作名・エンドポイント・呼び出し元）、期待結果。
- 認証情報の取得方法、データ前提、更新有無、出力先（既定は「実行・比較・証跡」節のNAS保存先）、復元方法。
- 実行場所・PC占有可能時間、証跡保存先、意図した差分の根拠。

引継ぎ元と同じTC-IDを保持する。WebView2側の取得済み証跡を参照し、今回のWindows側checkpoint名を追加する。引継ぎ時点のプロセス・セッションが生存しているとは仮定せず、新しいテスト用インスタンスで前提を再構築する。

Windows UIに到達する準備は、実CSアプリのWebView2にPlaywrightでCDP接続してDOM操作してよい。これはnative専用ケース内の準備操作であり、通常のwebviewスイートを混在させる理由にはしない。host object・プラグインをモックしたり、直接APIを叩いて到達を代替しない。

既存のWebView2接続リファレンスは `cs-webview-regression-test` の `references/allcampus-webview2.md` を必要時に読む。閲覧には使えるが、同スキルのWindows操作禁止をnative実行へ持ち込まない。

## ネイティブ経由のAPI呼び出しの棚卸しと観点

ネイティブ接点を網羅的にテストしない。PC占有なしの段階で、実装ソースから対象チェーンだけを選び出す。

1. 対象画面のネイティブ接点を洗い出す（`OpenFileDialog`・`SaveFileDialog`・`FolderBrowserDialog`・印刷設定、帳票ビューア・外部アプリの起動、ネイティブ画面）。
2. 接点ごとに、その結果を受けて呼ばれるAPIを追う。WebView2側はダイアログの戻り値（パス等）を使う後続処理（GraphQL・バッチ・マイクロサービスの呼び出し）を、C#側はプラグイン・host objectがAPIクライアントで呼ぶ処理を見る。
3. 同じAPI呼び出しに、DOM操作だけで届く経路（パス入力欄への直接入力、`<input type="file">`、ダイアログを出さない既定の出力先等）が無いかを確かめる。
4. 各接点を次のいずれかに確定する。

| 区分 | 条件 | 扱い |
|---|---|---|
| 対象 | 3条件をすべて満たす | TC-IDを付けてケースにする |
| 対象外（APIなし） | ネイティブ操作の後にAPIを呼ばない | ケースにしない。根拠（ソースの箇所）を残す |
| 対象外（webviewで到達可） | DOM操作だけで同じAPIに届く | `cs-webview-regression-test` の範囲として返す |
| 要確認 | ソースだけで判断できない（プラグイン・動的な分岐等） | 実物で小さく確かめる。確かめられなければ残す |

棚卸しには、接点ごとに画面・ロール、ネイティブ接点の種別、後続のAPI（操作名・エンドポイント・呼び出し元・更新の有無）、DOMだけの代替経路の有無、区分、根拠、TC-IDを書く。対象が0件なら、それ自体を結論として報告する（GUI実行は不要）。

対象チェーンの観点は、APIが呼ばれる正常系を基本の1件にする。ネイティブ操作の分岐でAPIの呼ばれ方が変わる場合だけ、その分岐を足す（例：キャンセルしたときにAPIが呼ばれないこと、選んだ保存先・印刷設定がAPIの引数に反映されること）。APIの呼ばれ方を変えない観点（長いファイル名、ダイアログの表示内容等）は足さない。

更新を伴うAPIは、「実行前の分離」の承認条件（専用データ・復元手順）を満たす場合だけ実行する。満たせないチェーンは「未実施（承認待ち）」として残し、更新の手前まで進めて代替しない。

## 実行の効率化

対象チェーンに絞ったうえで、PC占有時間を減らす。逐次実行・PID/ownerへの絞り込み・占有の事前提示は変えない。

- **占有前に準備を終える**：UIA要素マップ（AutomationId、ControlType、親子関係）、データ、出力先、到達手順を、GUI実行前に用意する。占有枠内は操作・待機・証跡取得だけにする。
- **起動回数を減らす**：同じ環境・同種のケース（例：帳票出力の保存系）は1つのテスト用インスタンスで続ける。ケースごとにホーム状態へ戻ったことを確認する。戻れない、または状態が不明なら、そのインスタンスを隔離して新しく起動する。
- **ケース単位で両環境を交互に実行する**：1つのTC-IDをPT/STの両方で実行してから次へ進む。その場で比較でき、占有枠が途中で切れてもTC-ID単位で完結した結果が残る。
- **待機の期限を実測で決める**：固定sleepは使わず、チェックポイントごとに期限付きで待つ。期限は代表ケースの実測に余裕を持たせて決め、manifestに記録する。長すぎる期限を一律に使わない。
- **探索を狭める**：UIAの検索は事前に確認した要素マップとowner配下から始める。毎回ツリー全体を走査しない。
- **優先順に実行する**：代表ケース、リスクの高いチェーン（更新・出力）、残りの順。占有枠が足りなければ、残りを「未実施」として報告する。速度のために対象チェーンのcheckpoint（特にAPI呼び出しの記録）や片方の環境を削らない。

## 実行前の分離

リポジトリのAGENTS.mdを確認し、exe・設定・プラグインを調べる。PTを新版、STを旧版と固定せず、今回の版を記録する。同一ビルドなら環境間比較として報告し、新旧版検証とは言い換えない。

### 比較元と比較先が同じ環境の段階違いのとき（段階比較）

依頼が「同じ環境で、設定・機能の段階を入れる前（ベースライン）と後を比べる」場合は、`cs-webview-regression-test` の「段階比較」と同じ読み替えをする（ST・PT → ベースラインと比較先の段階、証跡の `ST/`・`PT/` → `<段階ラベル>/`、両環境のデータの同一 → 実行前のデータの状態が同じこと）。加えて次に従う。

- 「ケース単位で両環境を交互に実行する」は行えない（段階の切り替えはサーバーの設定）。ベースラインを全件取ってから切り替える。
- 帳票の比較の基準は、同じテストコード・同じ入力条件で取ったベースラインの出力原本にする。
- manifestに、段階ごとのサーバー側の設定と切り替えの日時、ベースラインの run-id を書く。
- 「実行・比較・証跡」と「終了と完了判定」の「両環境」「PT/ST」も、ベースラインと比較先の段階に読み替える。段階の切り替え（サーバーの設定）は本スキルで行わず、依頼側の担当者から設定を受け取る。
- 依頼の合格条件にサーバー側のログ（監査ログ等で拒否・エラーが無いこと）が入っている場合は、`cs-webview-regression-test` の「サーバー側のログを合格条件に含む依頼のとき」と同じく、ケースごとの開始・終了の時刻を記録し、受け取った集計結果で判定する。集計結果が無いケースは「一致」にしない。

起動・停止対象のPID、開始時刻、exeパスを記録する。既存の作業用CSアプリやExcel等にはattachしない。既存プロセスが使う設定・プロファイル・出力先と隔離できない場合は、該当アプリの実行を保留する。利用者のプロセスを勝手に終了しない。

AllcampusはTEMP配下にWebView2プロファイルを作り、起動時に閲覧データを消す実装がある。テスト子プロセスだけTEMP/TMPを実行別に分け、実プロファイルの分離を確認する。起動時に配布フォルダ内のファイルを変更する処理があれば、テスト用コピーや変更範囲を確認してから起動する。

設定変更は隔離コピーを優先する。共有設定を変更する必要がある場合は、原本を退避し、終了・例外時の復元処理を用意する。固定のsettings.jsonがあると決めつけない。今回作った出力先のファイルを使い、既存ファイルへの上書きを避ける。

GUI操作は対話セッション内で `workers: 1` 相当の逐次実行にする。CSアプリ、WebView2、ハーネスの権限レベルを揃え、アクセス拒否をアプリ不具合と誤認しない。必要な権限は確認し、勝手に管理者化しない。

登録・削除等の更新は、今回の承認済みテスト範囲・専用データ・復元手順を確認する。外部送信や実プリンタへの印刷は一般的な回帰依頼に含まれると仮定しない。印刷は承認済みの仮想プリンタ/出力先を使い、実印刷が必要なら宛先と枚数を示して実行前に確認する。

## FlaUI操作の原則

FlaUI/UIA3を第一候補にし、採用バージョンと対象コントロールの対応を小さなケースで確認する。UIA3で扱えないコントロールは、UIA2や手動確認を検討し、変更理由と残範囲を記録する。

| 操作 | 優先する方法 |
|---|---|
| ボタン、メニュー項目 | InvokePattern |
| リスト・行選択 | SelectionItemPattern |
| チェックボックス | TogglePattern |
| 入力欄 | ValuePattern/対応するFlaUIコントロール |
| 保存ダイアログ | 対象PID/ownerを確認して入力欄・保存ボタンを特定 |
| Owner付き・プラグインのダイアログ | owner配下とDesktop直下の両方を検索 |

AutomationId、ControlType、表示名、親子関係を組み合わせ、必ず対象のプロセス/ownerに絞る。「保存」「はい」という名前だけでDesktop全体の最初の要素を操作しない。

ダイアログタイトルやボタン文言はソースまたは実際のUIAツリーで確認する。WinForms、WPF、標準ファイルダイアログでツリーの形が同じとは仮定しない。プラグインが別プロセスを起動するなら起動時刻・親子関係・対象ファイル等を照合して識別する。

UIAパターンで操作できない場合だけ、対象を前面化してキー入力・マウス操作を行う。前面ウィンドウが対象PID/handleか毎回確認し、フォーカスが他アプリへ移ったら送信を止める。座標は対象要素のBoundingRectangleから求め、画面固定座標を使わない。DPI・複数モニタ・負座標・表示倍率を記録する。

IMEは原則として対象外（APIを呼ばない）。ネイティブ画面の入力がIMEでしか作れず、その値がAPIの引数になる場合だけ扱う。そのときはDOMのfillやValuePatternでは実証できないので、対象入力欄をフォーカスし、実IMEとキー入力で入力する。実行前のIME状態を記録し、変更した状態を復元する。

クリップボードへ秘密値を置かない。共有クリップボード・IME・プリンタ等の利用者の設定を無条件で変更しない。変更が必要なら占有枠内で範囲を明示し、復元可能な方法を選ぶ。

## モーダルとタイムアウト

操作後はウィンドウ出現・閉鎖、ボタン状態、出力完了等の条件を期限付きで待つ。固定sleepやクリック呼出しの正常終了だけで成功判定しない。

同期MessageBoxを開くInvoke/Selectが返らず、UIA呼出し全体が止まる場合がある。発火を管理した別スレッド/別ハーネスプロセスへ分け、検出をPID・owner・可視性で絞ったWin32 EnumWindows/EnumChildWindowsへ切り替えることを検討する。

発火タスクを放置して次ケースへ進まない。タイムアウト後の遅延クリックや二重操作を防ぐため、元の操作とダイアログの終端状態を確認し、回復できなければそのインスタンスを隔離してケースを止める。更新・出力中または状態不明なら強制終了しない。

## 実行・比較・証跡

PT/STで同一TC-ID・手順・データ条件を使う。まず小さな代表ケースでUIA探索・API記録・証跡取得を実証し、対象ケースへ展開する。結果は環境別・画面別・TC-ID別に保存し、既存のWebView2証跡を上書きしない。

各対象チェーンのcheckpointは、少なくとも次の3つにする。ダイアログが開いた・閉じたことだけでは合格にしない。

1. ネイティブ操作：対象PID/owner配下のウィンドウで操作し、閉じたこと（選んだパス・設定値を記録する）。
2. API呼び出し：ネイティブ操作の後に呼ばれたAPIの操作名・エンドポイント・回数・ネイティブ操作の結果に由来する引数・応答の成否（HTTP状態、GraphQLの `errors` の有無）を記録する。認証トークン・個人情報・秘密値は記録しない。ネイティブ操作の前にAPI記録を始め、対象外の呼び出し（ポータル・ログ送信等）は「画面外」として分ける。
3. 結果：APIの結果として画面・出力物に出たもの（登録件数、エラー表示、出力ファイル等）。

API呼び出しの比較では、件数・操作名・引数の構造と、ネイティブ操作に由来する値を突き合わせ、日時・ID・トークン等の揮発値だけを根拠付きで正規化する。

出力処理（帳票・CSV等のファイル出力）の保存先は `\\nas01\Public\GAKUMU-NAS\学務共有テスト\学務部\t\` とする。NASへ到達できない場合は代替先へ切り替えず、利用者へ報告する。

保存ダイアログが絡むケースは、保存先や保存の確定を受けてAPIが呼ばれる（出力処理の要求、出力ジョブの登録、保存後の登録等）場合だけ対象にする。帳票のデータ取得がダイアログより前にDOM操作だけで済み、ダイアログの後はローカルへの書込みだけなら、対象外（APIなし）とする。対象の例：実CSアプリから出力を指示 → Windows保存ダイアログで上記保存先配下の専用の空フォルダを選ぶ → その後のAPI呼び出し（操作名・保存先に由来する引数・成否）を記録 → ダイアログ閉鎖と新規ファイルの書込み完了を確認 → API呼び出しと出力原本の内容をPT/STで比較する。保存ボタンを押しただけ、ファイルが存在するだけでは成功にしない。

外部ビューアは対象ファイルを開いていることをタイトル・対象文書・表示内容で確認する。前回の文書や既存Excelのブックを誤って検証しない。CSVは列・値・件数・必要な順序、PDFは内容・必要なレイアウトを比較し、既知の生成日時等だけ根拠付きで正規化する。

Windows UIの証跡は対象ウィンドウ中心に撮り、OSの画面キャプチャが必要な場合も対象モニタ/領域を限定する。他の作業ウィンドウの個人情報を証跡へ混入させない。開いた状態・操作後・失敗時を記録し、画像を開いて意図した内容と表示の安定を確認する。

実行ごとに次を保存する。

```text
evidence/<native-run-id>/
  manifest.json
  cases.json
  inventory.json
  ST/<screen>/<TC-ID>/<native-checkpoint>.png
  ST/<screen>/<TC-ID>/api-calls.json
  PT/<screen>/<TC-ID>/<native-checkpoint>.png
  PT/<screen>/<TC-ID>/api-calls.json
  comparison.json
  report.html
```

manifestには実行時間（Asia/Tokyo）、占有開始/終了、環境URL、exe/DLL/Web版、表示条件、UIA方式、API記録の方法（CDP・アプリログ・サーバー側ログ）、所有PID、待機期限と決めた根拠、棚卸し件数（対象・対象外の内訳）と実施件数、元のwebview-run参照、復元結果を記録する。inventoryには接点の一覧と、後続のAPI・代替経路の有無・区分・根拠・TC-IDを記録する。casesには前提、操作、期待するAPI呼び出しと結果、更新有無、復元方法を含める。秘密値は保存しない。証跡・認証情報・出力原本はgit管理対象外とし、無確認で外部公開しない。

TC-ID × checkpointごとに両環境の実行結果と証跡を機械的に集計する。差異は「一致／根拠のある意図した差分／要確認／比較不能／未実施」に分ける。MFA・画面ロック・UIAタイムアウト等を成功や単なるskipへ埋め込まない。

失敗証跡・再現手順を保持し、アプリ不具合候補・テスト実装問題・環境問題を区別する。期待値やbaselineを緩めて成功させない。テスト側の誤りを修正する場合は元の証跡と修正根拠を残し、修正後の結果を別実行として記録する。アプリコードは本スキルでは修正しない。

## 終了と完了判定

テストで起動したウィンドウ・プロセスだけを閉じる。同名プロセスの一括killをしない。外部アプリが既存インスタンスを共有してしまった場合は、そのアプリ全体を終了せず、対象文書を安全に区別して扱う。未保存変更や処理中の状態が不明なら保留を報告する。

変更した設定・IME等を復元し、ブラウザ接続を閉じ、所有プロセス終了を確認してから専用一時プロファイルを片付ける。証跡と出力原本は残す。削除先は実行用ディレクトリ内の絶対パスを検証する。

対象チェーンすべてについて、両環境の実行・API呼び出しを含む比較・証跡確認・復元が揃い、棚卸しに「要確認」が無く、ケースに要確認・比較不能・未実施も残らないときに、この範囲の回帰完了とする。対象外の接点はケースが無くても完了を妨げないが、区分と根拠が棚卸しに書かれていることを条件とする。対象が0件なら、棚卸しの結論（ネイティブ経由のAPI呼び出しが無いこと）をもって完了とする。残る場合は実施済み範囲と残作業を報告する。WebView2側の結果と合算するときはTC-ID単位で必要checkpointを突き合わせ、どちらかの未実施を含めたままCS全体E2E完了とは報告しない。

report.htmlには棚卸しの結論（対象・対象外の件数と、対象外の理由）、対象チェーンごとの結果（ネイティブ操作・API呼び出し・結果の各checkpoint）、両環境の画像とAPI呼び出しの比較、差異の根拠、未実施・残作業、占有終了と復元状態を記載する。

報告書を作る時点で、ケースに「未実施」を残さない（`cs-webview-regression-test` の「報告書を作る時点で未実施を残さない」と同じ。確かめる意味がないものは理由付きで母数から外し、実施できるものは実施する）。依頼者がテスト環境として既存データの変更・削除を認めている場合の扱いも同スキルの「既存データの扱い」に従う。PT・ST で同じ動きをする（趣旨に沿わない）不具合候補は、同スキルの「テストの趣旨に沿わない不具合は「一致」にして、別の不具合報告書に分ける」に従い、「一致」にして別の不具合報告書へ書く。

報告の入口は、run ごとの report.html ではなく、全 run をタブで切り替えて見られる1つのHTMLにする（run が1つでも作る）。`cs-webview-regression-test` の `scripts/make-tabbed-report.cjs` を使い、手順・確認項目も同スキルの「報告書は、全画面をタブでまとめた1つのHTMLにする」に従う。各 run には comparison.json（`cases[].verdict`）と report.html を置く。同じ依頼で WebView2 側の run もあれば、同じまとめに並べてよい（タブ名で native と分かるようにする）。

## よくある誤り

- WebView2実行から自動でnativeへ切り替える。占有枠を別途確保して専用ケースを実行する。
- 既存WPFスキルの設定ファイル・同名プロセスkill例をWinFormsへそのまま移す。
- Desktop全体から同名の保存ボタンを拾い、利用者の別アプリを操作する。
- UIAのInvokeならPC占有なしと説明する。nativeケースは一貫して占有枠とする。
- UIAが返らない操作を再送して二重保存・二重更新する。
- 実印刷・外部送信・利用者データの上書きを、一般的な回帰依頼の範囲とみなす。
- ネイティブ接点を網羅的にケース化する。キャンセル・IME・長いファイル名・ダイアログの表示内容など、APIの呼ばれ方を変えない観点は足さない。
- DOM操作だけで届くAPI呼び出しを、ネイティブ経由で重ねてテストする。代替経路の有無を先に確かめ、webview側へ返す。
- ダイアログが開いた・閉じた、ファイルを選べた、だけで合格にする。後続のAPI呼び出しと結果を記録して比較する。
- C#側から出るAPI呼び出しをCDPで見えないまま「一致」にする。観測手段が無ければ比較不能とする。
- 更新を伴うAPIの承認が無いのに、更新の手前までの操作で代わりに合格とする。承認待ちの未実施として残す。
- 利用者が挙げた機能だけを見て、同じ画面の他のネイティブ経由のAPI呼び出しを棚卸ししないまま完了とする。
- 速度を理由に、対象チェーンのcheckpoint・片方の環境の実行を省く。短縮は準備の前倒しと待機の見直しで行う。
- ログイン前処理を「WebView2実行から自動でnativeへ切り替える」ことと混同して断る。前処理は実行前に示す認証準備で、ケースとは別。
- ログイン前処理でロックや失敗のメッセージが出たのに、同じアカウントで再試行を繰り返す。
- ログイン前処理のついでにメニューの操作まで進め、WebView2回帰の範囲を取り込む。
