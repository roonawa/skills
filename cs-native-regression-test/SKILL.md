# CSアプリのWindows側回帰テスト

## 対象と実行境界

Allcampusの実CSアプリを起動し、FlaUI/UI AutomationでWindows側の操作・操作結果をPT/ST間で比較する。Allcampus本体はWinForms＋WebView2であり、WPF専用アプリとは扱わない。プラグイン・ビューア・外部アプリのUI技術は実物で確認する。

対象は保存・フォルダ選択・確認・印刷ダイアログ、帳票ビューア、実際に必要な外部Excel/PDFアプリ、IMEの挙動等。APIへの直接リクエスト、API応答比較、DB検証、認可・負荷テストは行わない。

Web画面だけで完結するケースは `cs-webview-regression-test` に分ける。このスキルのハーネスは `native-required` ケース専用とし、通常のWebView2回帰と同時に起動・並列実行しない。UIAでフォーカスを使わず操作できる場合も、このスキルの実行はPC占有枠として扱う。

## PC占有の扱い

スキルの作成・ケース設計・コード調査・ハーネス作成・ビルド・結果の比較はPC占有なしで進める。**GUI実行直前**に、対象ケース、前面化・キー操作等の有無、実行場所、終了または中断条件を提示する。

利用者が今回の実行時間にPCを空ける旨を伝えていれば再確認しない。占有可能な時間が未指定なら、「このPCで今実行できるか、専用Windows PC/VMで実行するか」を確認し、GUI実行だけ待つ。スキルを作る依頼をGUI実行の許可とは扱わない。

専用PC/VMを使う場合も、そのWindows対話セッションが使用可能か確認する。実行中は画面ロック・セッション切断・人の入力を避ける。サービス/Session 0やロックされたデスクトップでGUIが安定動作すると仮定しない。RDP切断時の挙動は採用環境で確認する。

占有開始・終了を明示する。停止依頼を受けたら新しい操作を止め、処理中の更新・出力の状態を確認し、安全に停止する。終了時はケース結果、残っているウィンドウ、復元・片付け状況を伝え、PCを再利用できる状態か報告する。

占有枠の終了が近い場合は、終了・復元に必要な時間を残し、新規ケースを開始しない。途中の処理を安全に終えられない場合は状態を伝え、時間切れだけを理由に強制終了しない。

## ケースの入力と引継ぎ

`cs-webview-regression-test` が生成した `native-handoff.md` があれば読む。なくても利用者が指定したWindows操作のケースを扱える。最低限次を揃える。

- TC-ID、画面・ロール、PT/STのURL、実行するexe/DLL/Web版の組合せ。
- Windows UIへ到達する手順、対象ウィンドウ・操作、期待結果。
- 認証情報の取得方法、データ前提、更新有無、出力先、復元方法。
- 実行場所・PC占有可能時間、証跡保存先、意図した差分の根拠。

引継ぎ元と同じTC-IDを保持する。WebView2側の取得済み証跡を参照し、今回のWindows側checkpoint名を追加する。引継ぎ時点のプロセス・セッションが生存しているとは仮定せず、新しいテスト用インスタンスで前提を再構築する。

Windows UIに到達する準備は、実CSアプリのWebView2にPlaywrightでCDP接続してDOM操作してよい。これはnative専用ケース内の準備操作であり、通常のwebviewスイートを混在させる理由にはしない。host object・プラグインをモックしたり、直接APIを叩いて到達を代替しない。

既存のWebView2接続リファレンスは `cs-webview-regression-test` の `references/allcampus-webview2.md` を必要時に読む。閲覧には使えるが、同スキルのWindows操作禁止をnative実行へ持ち込まない。

## 実行前の分離

リポジトリのAGENTS.mdを確認し、exe・設定・プラグインを調べる。PTを新版、STを旧版と固定せず、今回の版を記録する。同一ビルドなら環境間比較として報告し、新旧版検証とは言い換えない。

起動・停止対象のPID、開始時刻、exeパスを記録する。既存の作業用CSアプリやExcel等にはattachしない。既存プロセスが使う設定・プロファイル・出力先と隔離できない場合は、該当アプリの実行を保留する。利用者のプロセスを勝手に終了しない。

AllcampusはTEMP配下にWebView2プロファイルを作り、起動時に閲覧データを消す実装がある。テスト子プロセスだけTEMP/TMPを実行別に分け、実プロファイルの分離を確認する。起動時に配布フォルダ内のファイルを変更する処理があれば、テスト用コピーや変更範囲を確認してから起動する。

設定変更は隔離コピーを優先する。共有設定を変更する必要がある場合は、原本を退避し、終了・例外時の復元処理を用意する。固定のsettings.jsonがあると決めつけない。今回作った出力先のファイルを使い、既存ファイルへの上書きを避ける。

GUI操作は対話セッション内で `workers: 1` 相当の逐次実行にする。CSアプリ、WebView2、ハーネスの権限レベルを揃え、アクセス拒否をアプリ不具合と誤認しない。必要な権限は確認し、勝手に管理者化しない。

登録・削除等の更新は、今回の承認済みテスト範囲・専用データ・復元手順を確認する。外部送信や実プリンタへの印刷は一般的な回帰依頼に含まれると仮定しない。印刷は承認済みの仮想プリンタ/出力先を使い、実印刷が必要なら宛先と枚数を示して実行前に確認する。

## FlaUI操作の原則

FlaUI/UIA3を第一候補にし、採用バージョンと対象コントロールの対応を小さなケースで確認する。UIA3で扱えないコントロールは、UIA2や手動確認を検討し、変更理由と残範囲を記録する。

| 操作 | 優先する方法 |
|---|---|
| ボタン、メニュー項目 | InvokePattern |
| リスト・行選択 | SelectionItemPattern |
| チェックボックス | TogglePattern |
| 入力欄 | ValuePattern/対応するFlaUIコントロール |
| 保存ダイアログ | 対象PID/ownerを確認して入力欄・保存ボタンを特定 |
| Owner付き・プラグインのダイアログ | owner配下とDesktop直下の両方を検索 |

AutomationId、ControlType、表示名、親子関係を組み合わせ、必ず対象のプロセス/ownerに絞る。「保存」「はい」という名前だけでDesktop全体の最初の要素を操作しない。

ダイアログタイトルやボタン文言はソースまたは実際のUIAツリーで確認する。WinForms、WPF、標準ファイルダイアログでツリーの形が同じとは仮定しない。プラグインが別プロセスを起動するなら起動時刻・親子関係・対象ファイル等を照合して識別する。

UIAパターンで操作できない場合だけ、対象を前面化してキー入力・マウス操作を行う。前面ウィンドウが対象PID/handleか毎回確認し、フォーカスが他アプリへ移ったら送信を止める。座標は対象要素のBoundingRectangleから求め、画面固定座標を使わない。DPI・複数モニタ・負座標・表示倍率を記録する。

IMEテストはDOMのfillやValuePatternだけでは実証できない。対象入力欄をフォーカスし、実IMEとキー入力で期待する変換・確定を確認する。実行前のIME状態を記録し、変更した状態を復元する。非IMEケースにIME操作を追加しない。

クリップボードへ秘密値を置かない。共有クリップボード・IME・プリンタ等の利用者の設定を無条件で変更しない。変更が必要なら占有枠内で範囲を明示し、復元可能な方法を選ぶ。

## モーダルとタイムアウト

操作後はウィンドウ出現・閉鎖、ボタン状態、出力完了等の条件を期限付きで待つ。固定sleepやクリック呼出しの正常終了だけで成功判定しない。

同期MessageBoxを開くInvoke/Selectが返らず、UIA呼出し全体が止まる場合がある。発火を管理した別スレッド/別ハーネスプロセスへ分け、検出をPID・owner・可視性で絞ったWin32 EnumWindows/EnumChildWindowsへ切り替えることを検討する。

発火タスクを放置して次ケースへ進まない。タイムアウト後の遅延クリックや二重操作を防ぐため、元の操作とダイアログの終端状態を確認し、回復できなければそのインスタンスを隔離してケースを止める。更新・出力中または状態不明なら強制終了しない。

## 実行・比較・証跡

PT/STで同一TC-ID・手順・データ条件を使う。まず小さな代表ケースでUIA探索と証跡取得を実証し、対象ケースへ展開する。結果は環境別・画面別・TC-ID別に保存し、既存のWebView2証跡を上書きしない。

保存操作のケース例：実CSアプリから帳票出力 → Windows保存ダイアログを確認 → 専用の空フォルダへ保存 → ダイアログ閉鎖と新規ファイルの書込み完了を確認 → 原本・内容・必要なレイアウトをPT/STで比較する。保存ボタンを押しただけ、ファイルが存在するだけでは成功にしない。

外部ビューアは対象ファイルを開いていることをタイトル・対象文書・表示内容で確認する。前回の文書や既存Excelのブックを誤って検証しない。CSVは列・値・件数・必要な順序、PDFは内容・必要なレイアウトを比較し、既知の生成日時等だけ根拠付きで正規化する。

Windows UIの証跡は対象ウィンドウ中心に撮り、OSの画面キャプチャが必要な場合も対象モニタ/領域を限定する。他の作業ウィンドウの個人情報を証跡へ混入させない。開いた状態・操作後・失敗時を記録し、画像を開いて意図した内容と表示の安定を確認する。

実行ごとに次を保存する。

```text
evidence/<native-run-id>/
  manifest.json
  cases.json
  ST/<screen>/<TC-ID>/<native-checkpoint>.png
  PT/<screen>/<TC-ID>/<native-checkpoint>.png
  comparison.json
  report.html
```

manifestには実行時間（Asia/Tokyo）、占有開始/終了、環境URL、exe/DLL/Web版、表示条件、UIA方式、所有PID、元のwebview-run参照、復元結果を記録する。casesには前提、操作、期待結果、更新有無、復元方法を含める。秘密値は保存しない。証跡・認証情報・出力原本はgit管理対象外とし、無確認で外部公開しない。

TC-ID × checkpointごとに両環境の実行結果と証跡を機械的に集計する。差異は「一致／根拠のある意図した差分／要確認／比較不能／未実施」に分ける。MFA・画面ロック・UIAタイムアウト等を成功や単なるskipへ埋め込まない。

失敗証跡・再現手順を保持し、アプリ不具合候補・テスト実装問題・環境問題を区別する。期待値やbaselineを緩めて成功させない。テスト側の誤りを修正する場合は元の証跡と修正根拠を残し、修正後の結果を別実行として記録する。アプリコードは本スキルでは修正しない。

## 終了と完了判定

テストで起動したウィンドウ・プロセスだけを閉じる。同名プロセスの一括killをしない。外部アプリが既存インスタンスを共有してしまった場合は、そのアプリ全体を終了せず、対象文書を安全に区別して扱う。未保存変更や処理中の状態が不明なら保留を報告する。

変更した設定・IME等を復元し、ブラウザ接続を閉じ、所有プロセス終了を確認してから専用一時プロファイルを片付ける。証跡と出力原本は残す。削除先は実行用ディレクトリ内の絶対パスを検証する。

native対象ケースの両環境実行・比較・証跡確認・復元が揃い、要確認・比較不能・未実施が残らないときに、この範囲の回帰完了とする。残る場合は実施済み範囲と残作業を報告する。WebView2側の結果と合算するときはTC-ID単位で必要checkpointを突き合わせ、どちらかの未実施を含めたままCS全体E2E完了とは報告しない。

report.htmlにはケース別結果、両環境の画像、ファイル比較、差異の根拠、未実施・残作業、占有終了と復元状態を記載する。

## よくある誤り

- WebView2実行から自動でnativeへ切り替える。占有枠を別途確保して専用ケースを実行する。
- 既存WPFスキルの設定ファイル・同名プロセスkill例をWinFormsへそのまま移す。
- Desktop全体から同名の保存ボタンを拾い、利用者の別アプリを操作する。
- UIAのInvokeならPC占有なしと説明する。nativeケースは一貫して占有枠とする。
- UIAが返らない操作を再送して二重保存・二重更新する。
- 実印刷・外部送信・利用者データの上書きを、一般的な回帰依頼の範囲とみなす。
