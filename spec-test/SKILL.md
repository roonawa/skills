## 目的

カスタムソリューション部の受託開発において、詳細設計書（spec-detail出力）または基本設計書（spec-basic出力）およびテスト戦略（spec-strategy出力）をインプットとして、テストケース・テスト観点・テストデータを統一フォーマットで生成するスキル。

以下の課題を解決する：
- テスト観点の網羅性が確保できない → 正常系／異常系／境界値の3観点を各DD-IDに対して必ず確認する構造で防止
- 業務シナリオと単体テストが混在して管理困難 → テストケース（項目3）と業務シナリオテスト（項目4）を別章で分離
- 設計書とテスト仕様書のトレーサビリティが取れない → DD/BD/FR-ID → TC-IDのマッピング表を内蔵
- TC-IDの採番が担当者によってゆれる → TC-001から自動採番、振り直し禁止で統一
- 個人情報・機微データの扱いが曖昧になる → 項目2で必須確認として組み込み
- テスト手順に高度な判断が必要な箇所があり、テスト設計者の経験に依存してしまう 
- テスト手順が明確でないため、テスト工数にばらつきが出る

省略運用も可。上流ファイルとして直前フェーズ（詳細設計書）だけでなく、基本設計書や要件定義書など、より上流のファイルも指定可。既存設計書（PDF/Word等）からテスト仕様書のみ起こす「テストのみパターン」も許容する。

## スコープ

### やること
- 上流設計書の読み込み（DD/BD/FR-IDの自動展開、案件メタ情報の引継ぎ）
- 5項目のテスト仕様書作成のための壁打ち（草案フェーズ）
- 草案をテスト仕様書テンプレートに整形（整形フェーズ）
- 整形後のブラッシュアップサイクル（項目単位／TC-ID単位での部分修正・深堀り）
- 手順・期待結果は画面表示／ログ内容／ダイアログ文言／ファイル内容など観測可能なものだけで書く形式
- 既存テスト仕様書からの再開モード
- TC-ID自動付与（TC-001, TC-002...）と上流ID（DD/BD/FR）連結
- カテゴリ別TC分類（画面／I/F／内部ロジック）
- バージョン自動管理（v0.1 → v0.2 → ... → v1.0）
- 「⚠ 要確認」の明示
- レビュー依頼を促すメッセージ出力

### やらないこと
- テストの実行（テストケース仕様書の作成のみ）
- テストツール・自動化基盤の構築
- 工数見積もり
- 性能テストの詳細シナリオ生成（観点として記載するのみ）
- 受入テストの主導（顧客側受入基準として提示する場合は5章合否基準で言及）

## 全体フロー

```
[起動]
  ↓
[起動モード選択]
  ├─ A. 新規作成（上流ファイルを指定）
  └─ B. 既存テスト仕様書から再開（→ ブラッシュアップサイクルから開始）
  ↓
[上流ファイル読み込み]
  └─ 詳細設計書（主）・基本設計書（副）からID・内容を引き継ぎ、トレーサビリティ情報として保持
  ↓
① 草案フェーズ（壁打ち）
  ├─ テスト方針・前提
  ├─ テスト環境・データ
  ├─ テストケース（TC-IDで一覧）
  ├─ 結合・シナリオテスト
  └─ 合否基準・残課題
  ↓ ループ：「他に深堀りしたい項目は？観点漏れがないか確認したい」
  ↓
【チェックポイント1】整形に進む前の確認
  ↓
② 整形フェーズ → v0.1 出力
  ↓
③ ブラッシュアップサイクル（反復可能）
  ├─ a. 項目単位で深堀り
  ├─ b. TC-ID単位でピンポイント修正
  ├─ c. 新規追加（TC・シナリオ・観点）
  └─ d. これでOK → 終了
  ↓ 「これでOK」が出た時点
  ↓
【チェックポイント2】v1.0確定前のレビュー依頼（v1.0確定時のみ発動）
  ↓
テスト仕様書 v1.0 として確定
```

## 起動時の動作

スキルが起動したら、最初に起動モードを確認する。

> 「テスト仕様書スキル（spec-test）を起動した。以下のどちらで進める？
> A. 新規作成（設計書を上流ファイルとして指定し、ゼロから壁打ちを始める）
> B. 既存ファイルから再開（途中のテスト仕様書を読み込んで続きから）」

- **Aを選んだ場合**：上流ファイルの指定から開始
- **Bを選んだ場合**：既存ファイルのパスを聞き、読み込んでブラッシュアップサイクルから開始

## 上流ファイルの読み込み（新規作成時）

### 上流ファイルの指定

> 「上流ファイルのパスを教えて。テスト戦略（spec-strategy出力）と詳細設計書（spec-detail出力）が主上流だが、なければ基本設計書や要件定義書でも可。既存設計書（PDF/Word等）しかない場合も対応する。」

### 読み込んで展開する情報

- 案件タイプ（新規開発／機能追加／リニューアル）
- 顧客名、案件名、自社担当
- DD-ID 一覧（処理概要、上流BD-ID）
- BD-ID 一覧（機能の振る舞い）
- FR-ID 一覧（機能要件）
- DBテーブル定義（テストデータ準備に必要）
- エラー処理仕様（異常系テストケース生成に必要）
- 画面・I/F仕様（画面操作テスト・I/Fテストに必要）

### 「テストのみパターン」の扱い

既存設計書（PDF/Word等）からテスト仕様書のみ起こす場合：
- 設計書の内容を要約してメタ情報として記録する
- ID接頭辞は読み込んだ設計書の体系に合わせる（DD/BD/FR どれでも可）
- ID体系が存在しない場合は「設計書参照」として上流IDを記録し、TC-IDのみ採番する

## 草案フェーズの壁打ち（5項目）

質問は**1問ずつ**投げる。複数の質問を一度に投げない。回答内容に応じて追加深堀りを行う。

### 項目1：テスト方針・前提

1. 「上流設計書を読み込んだ。テスト範囲はどこまで？（単体／結合／総合／受入）」
2. 「テスト方針の前提は？（テストレベル、合格基準の方向性、テスト工程のタイミング）」
3. 「上流設計の中で、特に重点的にテストすべき箇所はある？（要確認事項、リスクが高い機能）」
4. 「テストを実施する担当者・体制は？（社内テスト担当、顧客との分担等）」

### 項目2：テスト環境・データ

1. 「テスト環境は？（環境構成、本番環境との差異）」
2. 「テストデータの準備方針は？（既存DBコピー／マスタ手動投入／生成ツール）」
3. 「個人情報・機微データの扱いは？テスト環境に本番データを持ち込む予定がある場合は必ず確認したい。」
4. 「外部システム連携のテスト方法は？（モック／スタブ／本物）」

※ 個人情報・機微データの確認（質問3）は必須。回答を「⚠ 要確認」マーク付きで記録する。

### 項目3：テストケース（TC-IDで一覧）

DD-IDごとに以下の順番で必ず生成する。不要な項目がある場合は不要と明記し、スキップする。

1. 入力条件抽出
2. 業務ルール抽出
3. 正常系
4. 異常系
5. 境界値
6. 権限
7. 排他
8. エラー処理
9. トレーサビリティ確認

→ 整形フェーズでTC-001から自動採番。各TCに上流ID（DD/BD/FR）を連結。

### 項目4：結合・シナリオテスト

1. 「業務シナリオベースのテストは？（複数機能をまたぐ業務フロー）」
2. 「シナリオの代表ケースは？（顧客の典型的な業務、繁忙期想定、エラー発生時のリカバリ等）」
3. 「異なるユーザー権限・ロールの組み合わせテストは必要？」
4. 「性能・負荷の観点はある？（詳細シナリオは作らないが、観点として記載する）」

### 項目5：合否基準・残課題

1. 「リリース判定基準は？（全テストケース合格、重大バグゼロ、性能基準クリア等）」
2. 「未テスト・要再確認事項は？」→ 「⚠ 要確認」マーク付きで記録
3. 「顧客側の受入テスト基準として提示する場合の項目は？」（任意）
4. 「テスト結果の記録・報告フォーマットは？」

### 5項目完了後の確認

5項目すべての壁打ちが完了したら以下を確認する：

> 「ひと通りの壁打ちが完了。他に深堀りしたい項目はある？特に観点漏れ（正常系／異常系／境界値）や、業務シナリオの抜けがないか確認したい。なければ整形フェーズに進む。」

- **「あり」の場合**：該当項目に戻って追加質問を行う
- **「なし」の場合**：チェックポイント1へ

## チェックポイント1：草案完了時
報告前に必ず自己レビューを挟む
* 例：
- DD数: 12
- TC作成済DD: 12
- 未展開DD: なし
- 正常系: 12/12
- 異常系: 12/12
- 境界値: 11/12
- 警告: DD-008に境界値なし
整形フェーズに進む前に以下を伝える：

> 「テスト仕様書の草案ができた。整形に進む前に、観点漏れ（正常系／異常系／境界値）や、業務シナリオの抜けがないか確認したい項目はある？人にレビューを依頼する場合はここで一旦止めて。」

確認が取れたら整形フェーズに進む。

- TC-001から連番で自動採番する


## ブラッシュアップサイクル

整形フェーズ完了後、または既存ファイル再開モード起動時に開始する。「これでOK」と利用者が伝えるまで何度でも繰り返せる。

### サイクル起動時の問いかけ

> 「現状のテスト仕様書（v0.X）を確認した。どこを修正・深堀りしたい？以下から選んで：
> a. 項目単位で深堀り（テスト方針／環境・データ／テストケース／結合・シナリオ／合否基準）
> b. 特定のTCをピンポイント修正（TC-IDを指定）
> c. 新規追加（TC・シナリオ・観点を追加）
> d. これでOK（v1.0として確定）」

### 各モードの動作

| モード | 動作 |
|---|---|
| **a. 項目単位** | 5項目のいずれかを指定させる → 該当項目について追加質問・修正壁打ちを行う → 該当セクションのみ書き換える |
| **b. TC-ID単位** | 修正したいTC-ID（例：TC-003）を指定させる → 該当TCの詳細について壁打ちを行う → 該当行のみ更新する |
| **c. 追加** | 追加したい要素（新TC／新シナリオ／新観点等）を指定させる → 壁打ちを行う → 該当セクションに追記する（TC-IDは自動採番） |
| **d. OK** | ブラッシュアップサイクルを終了する → チェックポイント2へ |

### 部分更新の挙動

- 既存内容を保持しつつ、指定箇所のみ書き換える（全文書き直さない）
- 修正のたびにバージョン番号を自動インクリメントする（v0.1 → v0.2 → v0.3 → ...）
- バージョン管理の基本方針は上書き（最新版のみ保持。Git管理されている前提）
- 利用者が指示した場合のみ、旧版を `<案件フォルダ>/履歴/` に退避する

## チェックポイント2：v1.0確定時（必須）

利用者が「d. これでOK」を選択したら、以下を実行する：

1. バージョンを **v1.0** に確定する
2. ファイル名のバージョン部分を `v1.0` に更新する
3. 以下のメッセージを表示する：

> 「テスト仕様書を v1.0 として確定する。**テスト実施前に、社内レビュー（部長／補佐）を必ず受けてください**。受入テスト基準として顧客側に提示する場合は、その合意も別途必要です。」

**重要**：チェックポイント2は v1.0 確定時のみ発動する。ブラッシュアップサイクルの途中（v0.2, v0.3 等）では発動しない。中間版を都度レビュー依頼すると運用が回らないため。

## テスト結果報告書（HTML）の生成（任意）

テスト仕様書がv1.0として確定した後、必要に応じてテスト結果報告書HTMLを生成できる。ブラウザで開いてTCごとにOK/NG/未実施/保留を選択し、エビデンス画像を添付し、結果を新しいHTMLとして保存できる自己完結型ツール。全案件共通のスクリプトを使用する。

**生成コマンド（1件）:**

```
node "C:\Users\roonawa\.claude\skills\spec-test\scripts\generate-report.js" <テスト仕様書のmdパス> --out <出力フォルダ>
```

**生成コマンド（フォルダ一括）:**

```
node "C:\Users\roonawa\.claude\skills\spec-test\scripts\generate-report.js" --all <テスト仕様書フォルダ> --out <出力フォルダ>
```

`--out` を省略すると、入力mdと同じフォルダに出力される。生成されたHTMLはネットワーク接続不要でブラウザだけで完結し、判定・コメント・エビデンス画像はすべてHTML内にBase64で保存される。「結果をHTMLとして保存」ボタンで書き出したファイルは、再度開いて編集を継続できる。

## 既存ファイル再開モード

### 起動フロー

1. 起動モードでBを選択した場合
2. 「既存のテスト仕様書のファイルパスを教えて」と聞く
3. 指定されたファイルを読み込み、以下をメモリに展開する：
   - 案件メタ情報（案件タイプ、顧客名、案件名、自社担当）
   - 上流設計書のパス（再読み込みして最新のID情報を取得する）
   - TC-ID採番状況（次に振るTC-IDを把握する）
   - 各TCの内容（種別、手順、期待結果、上流ID）
   - 業務シナリオの定義
   - 現在のバージョン番号
4. 読み込んだ内容を要約して提示し、ブラッシュアップサイクルから開始する
5. テンプレート構造から逸脱した記述がある場合は警告を出す

### 想定ユースケース
- 社内レビュー後のフィードバックをテスト仕様書に反映する
- 草案を作って一旦止めていた案件を後日再開する
- v1.0確定後に仕様変更が発生し、テストケースを追加・修正する場合（その場合は v1.1, v1.2, ... で管理）

## 出力ファイルの規則

### ファイル名規則

```
テスト仕様書_<案件名>_v<バージョン>_<YYYY-MM-DD>.md
```

| 状態 | バージョン例 | 備考 |
|---|---|---|
| 整形フェーズ初回出力 | v0.1 | 草案を整形した直後 |
| ブラッシュアップ中 | v0.2, v0.3, ... | 修正のたびに自動インクリメント |
| FIX | v1.0 | 利用者が「OK」を出した時点で確定 |
| FIX後の追加修正 | v1.1, v1.2, ... | 仕様変更・追加要望があった場合 |

### 保存場所
利用者がスキル起動時（または整形フェーズ完了時）に保存先を指定する。案件フォルダ配下に保存するのが基本。

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **正常系／異常系／境界値の3観点を必ず確認する**。各DD-IDに対して漏らさない（テスト観点漏れ防止の核）
- **TC-IDは振り直さない**。一度付与したIDは変更しない（上流設計書とのトレーサビリティを維持するため）
- **TC種別を必ず明示する**（画面／I/F／内部ロジックのいずれか）
- **個人情報・機微データの確認は必須**。項目2の質問3で必ず確認し、曖昧なまま進めない
- **性能・負荷テストの詳細シナリオは作らない**。項目4で観点として記録するのみ。詳細は別途専門テスト計画として切り出す前提を明示する
