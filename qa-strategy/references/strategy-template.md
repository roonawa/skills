## 3. 用語定義

### テストレベル

- **単体テスト** — テスト対象モジュールが定められた入力値から期待する出力値を得られるかを検証する
  （例：割引計算関数の入出力テスト）
- **結合テスト** — 複数モジュールが連動する機能に着目したテスト（例：検索機能とDBクエリの連携テスト）
- **E2Eテスト（業務フローテスト）** — 外部ストレージや連携サブシステムを含む、業務フロー全体を通すテスト
  （例：ユーザー登録→ログイン→商品購入→決済の一連の流れ）

### テストタイプ

- **機能テスト** — ソフトウェアが提供すべき機能の有無・適切性を検証する
- **非機能テスト**
  - 性能テスト — 処理時間・スループットを評価する
  - セキュリティテスト — 脆弱性が無いことを確認する
  - ユーザビリティテスト — 使い勝手を評価する

## 7. リスク分析

プロジェクト固有のリスク（難易度が高い・複雑性が高いモジュール）に着目する。

Impact（影響度 1-5）× Likelihood（発生確率 1-5）でスコアを算出し、下表のバンドにマッピングする。

| リスクレベル | スコア | テスト方針 | 自動化 | 監視 |
|---|---|---|---|---|
| CRITICAL | 15-25 | フル自動化＋手動探索的テスト＋負荷試験 | 必須・コミット毎 | リアルタイムアラート、synthetic monitoring |
| HIGH | 10-14 | フル自動化＋定期的な手動レビュー | 必須・PR毎 | ダッシュボード＋日次確認 |
| MEDIUM | 5-9 | 正常系＋主要異常系の自動化 | 推奨 | 週次レビュー |
| LOW | 1-4 | 手動テストまたはスキップ | 任意 | 不要 |

**機能マッピング例：**

| 機能領域 | Impact | Likelihood | スコア | 対応方針 | 関連FR-ID |
|---|---|---|---|---|---|
| 決済処理 | 5（致命的） | 3（起こりうる） | 15・CRIT | 自動E2E＋単体＋契約テスト＋監視 | ⚠ 要確認 |
| ユーザー認証 | 5（致命的） | 2（起こりにくい） | 10・HIGH | 自動E2E＋セキュリティスキャン＋単体 | ⚠ 要確認 |
| 商品検索 | 3（中） | 3（起こりうる） | 9・MED | 単体＋結合＋正常系E2E | ⚠ 要確認 |
| ダッシュボード表示 | 2（軽微） | 3（起こりうる） | 6・MED | 単体＋ビジュアルリグレッション | ⚠ 要確認 |
| メール配信設定 | 1（無視できる） | 2（起こりにくい） | 2・LOW | 手動確認 | ⚠ 要確認 |

「関連FR-ID」は `spec-req`/`spec-basic`/`spec-detail` の出力から**引用**する。このスキルはFR-IDを新規に
採番しない。

## 8. テストレベル方針とピラミッド分析

| レベル | 検証対象 | 担当 | フレームワーク | 目標割合 | 実行頻度 |
|---|---|---|---|---|---|
| 単体 | 関数・ビジネスロジック・境界値 | 開発者 | ⚠ 要確認 | 70-80% | コミット毎 |
| 結合 | サービス間連携・DB操作・API契約 | 開発者＋QA | ⚠ 要確認 | 15-20% | PR毎 |
| E2E | 重要なユーザージャーニー全体 | QA/SDET | ⚠ 要確認 | 5-10% | デプロイ前＋夜間 |
| API | 契約準拠・スキーマ・エラーハンドリング | 開発者 | ⚠ 要確認 | エンドポイント毎 | PR毎 |
| 性能 | 応答時間・スループット | DevOps/QA | ⚠ 要確認 | 重要パスのみ | 週次＋リリース前 |
| セキュリティ | OWASP Top 10・依存脆弱性 | Security/DevOps | ⚠ 要確認 | リリース毎 | リリース前＋定期 |

### 現状診断

現状のテスト本数・レベル別割合・CI所要時間・フレーキー率を計測し、以下4形状のどれに近いか診断する。

- **健全なピラミッド** — 単体多・結合中・E2E少
- **アイスクリームコーン（逆三角形）** — E2E過多。CIが遅く保守コストが高い
- **ダイヤモンド** — 結合テスト過多
- **砂時計** — 単体とE2Eはあるが結合が手薄

逆三角形／ダイヤモンドの場合のアクションプラン：

1. E2Eの新規追加を凍結する（新規のクリティカルパス以外）
2. 既存E2Eのうち単体レベルで検証可能なロジックを見つけ、下位レベルへ分解する
3. PRチェックリストに「ビジネスロジックを触るPRは単体テストを含む」を追加する
4. 単体:E2E比率が閾値を下回るPRをCIで弾く

砂時計の場合：結合テスト基盤（DBフィクスチャ、サービススタブ、契約テスト）に投資し、サービス境界ごとに
正常系・異常系の結合テストを追加する。

フレーキーなE2Eと本物のバグを暴いているE2Eを混同しない。レース条件を隠すテストを機械的に隔離しない。

## 9. 環境戦略

| 環境 | 目的 | テスト種別 | データ | デプロイトリガー |
|---|---|---|---|---|
| Local | 開発者フィードバック | 単体・結合 | モック/シード | 保存時 |
| CI | 自動検証 | 単体・結合・Lint・SAST | 使い捨て | push/PR時 |
| Staging | 本番前検証 | E2E・ビジュアル・性能・セキュリティ | 本番相当（匿名化） | mainマージ時 |
| Production | 監視・スモーク | スモークテスト・synthetic monitoring | 本番データ | デプロイ時 |

テストデータの管理方法、環境の使い捨て/常設の別、アクセス権、環境固有の設定管理方法を明記する。

|---|---|---|---|
| 技術スタックとの親和性（25%） | | | |
| チームの習熟度（20%） | | | |
| コミュニティ・ドキュメント（15%） | | | |
| CI連携のしやすさ（15%） | | | |
| 保守コスト（10%） | | | |

各項目1-5で採点し重みを掛けて合計する。ライセンス費用だけでなく総保有コストも見る：導入時間（CI設定・最初の

## 11. エントリー/エグジット基準

**単体** — Entry：コードがコンパイルできる、関数の入出力契約がドキュメント化されている。
Exit：全分岐カバー、境界値テスト済み、スキップされたテストが無い、カバレッジ目標達成。

**結合** — Entry：単体テストが通過、依存サービスが利用可能またはスタブ化されている、テストデータ投入済み。
Exit：全サービス境界がテスト済み、異常系が検証済み、フレーキーなテストが無い。

**E2E** — Entry：結合テストが通過、Staging環境がデプロイ済み、テストアカウントが用意されている。
Exit：全重要ユーザージャーニーが通過、P0/P1不具合が0件、性能がSLA内。

**リリース** — Entry：全レベルのテストが通過、CRITICAL/HIGH不具合が0件、リリースノート起票済み。
Exit：本番でのスモークテスト通過、合意した監視期間（デフォルト30分——デプロイ頻度とアラート遅延に応じて調整）
異常なし、ロールバック手順が検証済み。

## 12. 品質ゲート

**PRゲート**（毎PR）：単体テスト通過／結合テスト通過／カバレッジが低下していない／新規Lintエラー無し／
SASTスキャン通過（新規のhigh/critical無し）／レビュアー承認1名以上。

**マージゲート**（mainマージ時）：PRゲート全通過／プレビュー環境に対するE2Eスモーク通過／マージコンフリクト無し。

**デプロイゲート**（本番投入前）：Staging上でフルE2E通過／性能ベンチマーク範囲内／セキュリティスキャン通過／
フィーチャーフラグ設定済み／ロールバック手順検証済み。

**夜間ゲート**（定期実行）：エッジケース含むフルE2E／ビジュアルリグレッション／性能・負荷テスト／
アクセシビリティスキャン／依存脆弱性スキャン。結果は翌朝QAリーダーがレビューする。

各ゲートは具体的な合否閾値を持ち、CIで強制する。クリックで飛ばせるゲートはゲートではなくドキュメントである。

## 13. 品質メトリクス・KPI

| メトリクス | 定義 | 目標 | 計測頻度 |
|---|---|---|---|
| コードカバレッジ | 単体＋結合でカバーされる行/分岐 | 重要サービス＞80%、全体＞60% | PR毎 |
| テストピラミッド比率 | 単体:結合:E2Eの割合 | 70:20:10（±10%許容） | 月次 |
| フレーキー率 | 非決定的に失敗する実行の割合 | ＜2% | 週次 |
| 不具合エスケープ率 | 本番で見つかった不具合の割合 | ＜5% | リリース毎 |
| MTTR | 検知から修正デプロイまで | P0＜4h、P1＜24h | インシデント毎 |
| CIパイプライン所要時間 | Push〜結果確定まで | PR時＜15分、フル＜30分 | 週次 |
| 自動化率 | 自動化されているテストケースの割合 | 回帰スイートの＞80% | 四半期 |

**運用ルール：** 絶対値ではなく推移を追う（30%→60%は好調と評価する）。現状から現実的な目標を設定する
（20%→90%を1四半期で達成は計画ではなく願望）。四半期ごとに経営層とレビューし、改善を称賛する。急な悪化は
インフラの問題として調査し、チームを罰する目的で使わない。

## 16. タイムライン・マイルストーン

一度に全部やろうとすると何も仕上がらない。フェーズに分ける。

**フェーズ1 — 基盤（Week 1-4）：** 全プロダクト領域のリスク評価／単体テストゲート付きCI／
ベースラインメトリクス計測／リスク上位5領域の単体テスト／E2Eフレームワーク選定。
Exit：CIが毎PRで単体テストを実行し、ベースラインメトリクスが文書化されている。

**フェーズ2 — カバレッジ拡大（Week 5-10）：** 全サービス境界の結合テスト／重要ジャーニー上位10本のE2E／
主要画面のビジュアルリグレッション／テストデータ管理／夜間実行。
Exit：全クリティカルパスにE2Eカバレッジがあり、全APIに結合テストがある。

**フェーズ3 — 品質ゲート（Week 11-14）：** PRのカバレッジゲート／CIでの性能ベンチマーク／
セキュリティスキャン／全KPIの監視ダッシュボード。
Exit：PR/マージ/デプロイ/夜間の4ゲートすべてが稼働・強制されている。

**フェーズ4 — 最適化（Week 15-20）：** フレーキーテストの修正または隔離／CIスケーリング
（シャーディング・キャッシュ）／本番synthetic monitoring／初回の四半期戦略レビュー。
Exit：CIが15分以内、フレーキー率2%未満、初回改訂が公開されている。

**継続：** 四半期ごとの戦略レビュー、月次メトリクスレビュー、継続的な保守（リファクタ・デフレーク・廃止）。
