# 分類・原因調査・利用者への影響

## 1. 3種類の数を分ける

- **分類数**：HTTP・メタ情報、内部リンク等、確認目的の数。
- **ケース数**：URL×画面幅×検査方法等の実行単位。
- **原因数**：同一の実装不備・設定不備などの根本原因の数。

同じ原因が複数ケースへ影響し、1ケースに複数原因が併発することがある。原因別件数の合計が全不合格数と一致するとは限らない。

## 2. UIの分類と詳細

一覧は分類単位にし、分類名・何を確認するか・全対象件数・状態内訳を表示する。展開時にURL・端末条件・ケースID・個別結果、さらに判定理由・証拠へ進める。

| 分類 | 確認内容 |
|---|---|
| HTTP・メタ情報 | HTTP / Content-Type / title / canonical / indexability。description・lang等は設定された場合のみ |
| 内部リンク | 選択したページからの内部リンク応答 |
| 存在しないページ | 404等の応答方針 |
| 設定ファイル | 設定ファイルの応答と指定文字列の露出 |
| 非公開ファイル等 | バックアップ・環境設定・Git・ログ等の応答方針 |
| ユーザー情報API / 投稿者URL / XML-RPC | それぞれの公開・転送方針。別の目的を混ぜない |
| レイアウト / アクセシビリティ / 画像比較 | 横はみ出し / axe / 承認済み基準との比較 |
| JavaScriptエラー | ページ表示・表示準備・画像スクロール中の未捕捉例外。現在のハーネスでは独立判定 |
| 操作 / 管理設定 / 手動確認 | 機能や期待値の異なるものは独立して残す |

表示準備（画像・フォント・JS例外）が複数検査の共通前提ならその関係を表示する。独立した結果行がない場合、架空の「表示準備合格」行を作らない。

現在のハーネスはJS例外を独立させ、JS例外だけではlayout・axe・snapshotを止めない。旧履歴や別ハーネスでは準備失敗の場合があるため、実際の停止箇所を読む。独立化後のlayout不合格を、過去のJS例外が原因だと決めつけない。表示検査が合格でもJS検査の不合格は残す。

表示をまとめてもテスト・証拠を削らない。URLごとの期待値差を保持し、未知のケースを無理に既知分類へ統合しない。恒久的な分類は明示メタデータが望ましく、既存IDやタイトルによる推定は後方互換の補助手段とする。

検索・フィルターは詳細にも適用するが、分類全体の状態と一致件数を併記する。例：合格URL1件だけを検索しても、分類全体に不合格があれば隠さない。混在する状態は内訳を表示し、未実施を含む分類を単純に合格表示しない。

UI変更時は、折り畳み、展開、URL検索、要対応フィルター、混在状態、履歴切替、自動更新、証拠への導線、キーボード、スマホ幅を必要範囲で確認する。基準画像の承認等の既存操作も壊さない。過去結果JSONや集計の単位は変えず、表示上の分類と区別する。

## 3. 原因特定の手順

1. 対象のrunId・日時・設定ハッシュ・完了状態を特定し、fail行と証拠を読む。最新の完了実行と、より新しい中断実行を区別する。
2. 失敗メッセージ、最初の例外、スタック、対象URL、停止した処理段階でまとめる。メッセージ一致だけで同一原因と断定しない。
3. **準備→操作→本assert→後始末**のどこまで到達したか確認する。準備で止まった画像比較を「画像差分」、axe未到達を「WCAG違反」としない。
4. traceのpageError、network、readiness、axeのnodes・failureSummary、スクリーンショットを必要な分だけ読む。フルtraceや認証状態を不用意に共有しない。
5. 対象を絞って許可範囲内で再現する。公開HTML、スクリプトの順序、DOMの有無、取得ステータスを照合する。正常ページ・異常ページ、PC・スマホなど最小限の比較を行う。
6. 証拠がそろった範囲で、サイトの不備／期待値誤り／テスト実装の不備／環境や外部依存／未確定を分類する。合格にする目的で期待値を観測値へ合わせない。
7. 確認済み原因、発生条件、影響するケースID、修正候補、再検証条件を記録する。公開HTMLの行番号をPHPソースの位置と混同しない。

サーバー内部や管理設定が未確認なら、そこまで断定しない。原因調査依頼は本番修正・注文・決済の許可にはならない。

## 4. 再利用できる診断パターン

| 観測 | 確認すべき根拠 | 誤った結論を避ける |
|---|---|---|
| `Cannot read properties of null (reading 'style')` | スタックの関数、対象selector、実際のDOM、実行タイミング。特定テンプレート専用要素が共通スクリプトから参照されていないか | DOM欠落とタイミング問題は別。1例外で全JSが停止したとは言わない |
| `jQuery is not defined` | 依存処理とjquery-coreのHTML出力順、async/defer、network取得失敗、後からjQueryが定義されるか、失敗した初期化が再実行されるか | 通信が200でも実行順不良は起こる。原因を特定プラグインと決めつけない |
| 空カートでEC初期化失敗 | 停止したコード内の操作ハンドラー、関数定義、フォームイベント | 実注文未実施なら購入不能と断定しない。テスト環境で数量・遷移・住所・二重送信防止・完了まで確認 |
| `color-contrast` | 実際の前景色・背景色・文字サイズ・太さ・検出要素・ルールの閾値 | 小さい通常文字の基準を全要素へ一律適用しない。透明度・背景画像・重なり等も確認 |
| `link-name` | a要素の文字、aria-label、aria-labelledby、title、子画像のalt等、該当DOM | 通常クリック不能とは別。スライダー複製やSNSの外部読込み状態も確認 |
| 存在しないURLがトップへ302 | 転送前ステータス、Location、最終応答、可能なら実際の転送設定 | soft 404のリスクと検索エンジンの判定済みを混同しない |
| 大量リンクでtimeout | 完了したURL・失敗URL、個別通信とテスト全体の上限、重複巡回 | ページ故障と決めつけない。除外によって検査が完了したことにしない |

修正案は実際の原因に合わせる。例：対象DOMの存在確認、対象ページへのスクリプト出力限定、依存関係を宣言した読込み順、配色変更、目的の分かるリンク名、404応答方針。観測から分からない管理画面の設定名やPHPファイル名を作らない。

## 5. 利用者への影響を説明する

技術エラー → 中断・誤動作する処理 → 利用者の操作 → 業務上の影響、の順に根拠をつなぐ。次の4段階を区別する。

- **再現済み**：実際の操作で起きた現象。
- **技術的に確認済み**：初期化されない、イベント登録前に例外など、コード・ログで裏取りした事実。
- **可能性**：未実施の操作への推定影響。具体的な再確認方法も示す。
- **未確認**：権限・環境・コード不足などで分からない範囲。

説明例：

> カート表示時に依存ライブラリ未定義の例外が発生し、カート関連の初期化が完了しないことは確認しました。数量変更や次画面への遷移に影響する可能性があります。実注文での失敗は未確認なので、テスト環境で購入導線を確認します。

「重大」「高」等はケース数で決めず、購入・公開・情報漏洩・利用阻害など実害と範囲で決める。支援技術利用者への影響を単なる見た目の問題として扱わない。

## 6. 共有する調査結果

案件フォルダーに単体HTMLを作り、一覧から証拠へたどれるようにする。必要な情報は以下。既存の結果ファイルは書き換えず、追加の調査結果として関連づける。

```text
実行ID・日時・環境・設定 / 分類数・不合格ケース数・原因数
原因ID / 該当ケースID / 発生ページ・条件 / 最初の失敗・停止段階
期待結果 / 実際の結果 / 再現手順 / 根拠・証拠
確認済みの利用者影響 / 推定影響 / 未確認範囲
優先度と理由 / 修正方針 / 次の検査・再検証条件
```

コードやログを埋め込むときはHTMLエスケープする。報告書にCookie・認証ヘッダー・秘密値を載せない。外部アセットやリンクだけに依存せず、共有先で必要な証拠が開ける形にする。

## 判断確認用シナリオ

Skillの更新時に、次の入力で判断が崩れないか確認する。

1. カートのnoindex、wp-config.phpの200空本文：一律失敗にせず期待方針と内容を分ける。ただし観測値だけで期待値を変更しない。
2. 3ページ×2幅×3検査が同一の準備例外で停止：18件と1原因を分け、各本assertを未到達と説明する。
3. 合格1・不合格1・未実施1の分類で合格URLだけ検索：全体内訳と検索一致1件を区別し、分類を合格にしない。
4. 空カートで依存ライブラリ例外、実注文は未実施：初期化失敗を事実、購入失敗を未確認とする。
5. 最新runが中断、以前のauditが合格：過去の部分成功を最新の全体合格に置き換えない。
6. 未知テーマ・別EC構成：診断パターンを仮説として使い、固有selectorやプラグイン原因を無条件に流用しない。
