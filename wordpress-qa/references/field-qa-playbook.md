# 実サイトQAの設計・運用

WordPressサイトの「網羅的にテストして」を、実行可能な台帳と証拠へ落とすための手順。他サイトへの展開時はケースの型を再利用し、URL・期待値・代表ページ・権限は置き換える。特定テーマやECプラグインの挙動を共通仕様としない。

## 1. 対象と実行範囲

最初にサイト名、正規origin、環境、機能、変更範囲、公開対象、許可された操作を整理する。会話ですでに確定した内容は再質問しない。未確定でも公開ページの読取りなど独立して進められる作業は進める。

- 本番読取り専用なら表示、HTTP、メタ情報、証拠採取を実施。注文・決済・メール送信・会員登録・設定保存は実施済み扱いにしない。
- 認証情報が提供されても、対象外のFTP・DB・ドメイン管理へ利用範囲を広げない。ログイン可否と操作許可は別。
- 未認証の公開検査に管理者認証を付けない。秘密は設定JSONやコマンドログに直書きせず、既存ハーネスの認証経路を使う。
- テスト環境でも外部メール・決済が本番につながっていないか確認する。書込み検査は一意なテストデータ、回収方法、配送・決済の検証先が揃ってから行う。

案件情報の最低限の記録例（設定JSONのスキーマではない）:

```text
サイト / 正規origin / 環境 / 許可された操作
URL一覧の出典 / テンプレートと重要導線
期待値の出典 / 未確定の仕様
実行日時 / revisionまたは未指定 / 設定ハッシュ / 実行ID
対象外・未実施 / 再現用環境 / 証拠保存先
```

## 2. URL一覧とカバレッジ

1. www有無・HTTPS・末尾スラッシュ等の転送を確認し、正規originと対象URL一覧を分ける。別originへの認証転送は行わない。
2. robots.txt、サイトが公開するサイトマップ、CMSや移行表の既知一覧を使う。`wp-sitemap.xml`がHTTP 200でも、空のurlsetなら一覧取得成功ではない。必要に応じて`/sitemap.xml`やサイトマップindexを確認する。
3. indexの子サイトマップを取得し、重複を整理する。取得URL数、実検査ページ数、除外理由、孤立・未発見の可能性を記録する。サイトマップ取得はテスト合格ではない。
4. 公開記事、固定ページ、商品、一覧、検索、カート・会員などの用途別に整理する。サイトマップ非掲載の重要導線も台帳へ加える。
5. GETにもログアウト・削除・カート操作等の副作用がある。リンク一括巡回の対象は事前に制限する。無制限クロールや高並列アクセスは避ける。

大量の一覧リンクで時間切れになった場合、重複URLの共有キャッシュ、バッチ分割、適切な時間上限を検討する。子ページのHTTP確認済みと、その一覧の全リンク確認済みは別。検査を外す場合も元のblockedと残った範囲を残す。

## 3. 期待値を決める

期待値の根拠を、仕様・公開方針・移行表・担当者の合意などから記録する。現物しかないときは仮説として登録し、観測値に合わせて自動的に合格化しない。

| 項目 | 決め方と落とし穴 |
|---|---|
| indexable | 公開記事とカート・完了画面等を分ける。サイトマップに載っていてもindexableとは限らない。noindexページの掲載は別途整合性の確認対象 |
| canonical | 正規ドメイン・URL方針と照合する。現在のcanonicalの丸写しだけでは検証にならない |
| title / description / lang | 空でないことと、期待文言との一致を分ける。期待値未設定の項目を検査済みと説明しない |
| 非公開ファイル | HTTPステータス、転送先、本文の露出を別に見る。wp-config.phpの200空本文は漏洩の証拠ではない |
| 存在しないURL | 存在しない代表URLで404/410等の方針を確認。トップへの302と、検索エンジンによるsoft 404判定は同義ではない |
| ユーザーAPI / author | 公開仕様と露出情報を確認する。author=1の転送だけで、他の経路も含め列挙不能としない |
| XML-RPC | GET 405等は観測事実。POSTが無効、防御が完全、といった結論には使わない |
| リダイレクト | 許容ステータスだけでなくLocationを照合。403/404等との代替許容時は、実装がLocationを無条件要求しないか確認する |

誤った期待値を直す際は、変更理由・根拠・変更前後を残して再実行する。古い結果や設定ハッシュは書き換えない。

## 4. ケースを作る

各ケースは「ID／分類／リスク／対象URL・条件／期待結果と根拠／操作・取得方法／assert／証拠／後始末／CIまたはQA／未確認範囲」を持つ。

| 検査層 | 適用範囲 | 実施内容 |
|---|---|---|
| audit | 公開URLの明示一覧 | HTTP・HTML・title・canonical・indexability・選択した内部リンク |
| policy | 方針のある代表エンドポイント | 非公開ファイル、転送先、404、API等の応答と必要な本文チェック |
| visual | テンプレート代表＋例外、PC・スマホ | 表示準備、画像・フォント、JS例外、横はみ出し、axe、基準画像比較 |
| journey | 重要導線 | 検索・ナビ・フォーム・購入等。実行範囲内で操作し、結果をassertする |
| admin | 合意済みの設定期待値 | 認証済みの読取り。認証手段を既存UIや案件設定から確認する |
| manual | 自動判定できない・許可されない領域 | 意図した見た目、文章、実決済・メール、支援技術での利用など |

代表例はトップ・商品詳細・一覧・長文・フォーム・カートなどから選ぶ。固定の「4ページ×2幅」を全サイトへ流用しない。検査対象の選定理由を残す。

既存ハーネスがあればその設定・実装を読み再利用する。隣接するharnessがない配布版では実際の設置場所を確認する。存在しないCLIやスキーマを推測しない。コードがない場合は契約を台帳へ整理してから、必要な検査だけ実装する。

## 5. 実行・UI・完了確認

- validate後に必要なsuiteを実行する。設定項目数、選択ケース数、実行件数を分けて報告する。
- Git Bashの`/path`引数変換に注意。PowerShellまたは完全URL・適切なWindowsパスを使う。パス変換を止めると設定ファイル側のUnix風パスも無効になることがある。
- 起動済みUIと登録サイトを確認してから、サイト設定を渡して起動する。設定なしのデモを実サイトの結果と取り違えない。
- UIはローカル待受けとし、実際の画面でサイト選択・履歴・分類・証拠が読めることを確認する。案件設定と結果は一時領域だけに依存しない保存先が望ましい。
- バックグラウンド起動・完了通知は成功の証拠ではない。ラッパーの終了0、ログ末尾、results.jsonの完了状態・内訳・runIdを区別する。中断した実行を「まだ実行中」「完了」と推測しない。
- 初回画像は候補であり合格の基準ではない。レビュー・承認後に比較を再実行する。既存結果は遡って変更しない。

完了報告には、実施範囲、実際のpass/fail/blocked/not_run/review、未登録の必要検査、未解決の重要リスクを含める。全URLのHTTP合格を、購入・メール・権限も含む網羅合格にしない。
