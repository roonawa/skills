# ハーネスの実行手順

## ブラウザーの管理画面

セットアップ済みなら、ハーネスフォルダーで次を実行する。

```powershell
npm run ui
```

http://127.0.0.1:4310 に管理画面を開く。設定を省略した場合は、このPC内のデモサイトも起動する。検査実行、進捗、状態別の集計、履歴、項目詳細、画像・ログ・HTMLレポートを確認できる。デモも実際のハーネスを実行するため、最初の画像検査は「確認待ち」になる。

実サイトは画面左上の「サイトを登録」から登録できる。サイト名・URL・環境、公開ページ、管理設定の期待値を入力し、必要な認証情報を設定して保存する。既存の設定ファイルは起動時にも指定できる。複数サイトは`--config`を繰り返す。各サイトのoutputDirは別々に設定する。

```powershell
npm run ui -- --config C:\projects\site-a\qa\site.json --config C:\projects\site-b\qa\site.json
```

ポート変更は`--port 4311`。サーバーは127.0.0.1だけで待ち受け、登録済みの設定だけを実行する。共有ホスティング・社外公開用のアプリではない。停止は起動したターミナルでCtrl+C（処理中の場合はその終了を待つ）。

画面の使い方:

1. 左上でサイト、上部で検査範囲を選び「検査を実行」。同時実行は1件。
2. 進捗は自動更新。項目を選択すると判定理由と証拠を確認できる。「要対応」で不合格・実行不能・確認待ちを絞り込める。
3. 画像を基準として採用する場合、候補画像を確認し、確認チェックを付けてから承認する。実行中・設定が変わった古い履歴は承認できない。
4. 承認後に再実行。過去の結果は書き換わらない。左側から過去の履歴を選んで確認できる。

UIはCLIと同じresults.jsonを読み、同じCLIで実行・承認する。手動確認のreviewや未実施をUIだけで合格へ変更しない。サーバー再起動前の未完了実行は、完了を確認できない履歴として表示する。UI登録サイトは「設定を編集」で変更できる。起動時に指定した外部設定は読み取り専用で、「新規サイトとして複製」が可能。複製では案件モジュール・メール連携・認証参照を引き継がない。案件モジュールの作成・登録は引き続き外部設定ファイルで行う。

UI自身の検証は`npm run test:ui`。一時フォルダーで実ブラウザーを操作し、実行・進捗・承認・再実行・不具合表示・モバイル表示を確認する。

## UIからのサイト登録と認証設定

1. 「サイトを登録」でサイト名、origin形式のURL（例：https://example.jp）、環境を入力する。
2. 公開ページのパス・正規URL・検索公開可否、管理設定の取得方法・期待値を入力する。各行は追加・削除できる。URL応答方針、表示検査、手動確認は「その他の検査」のJSON配列で編集する。
3. REST認証はWordPressユーザー名とアプリケーションパスワードを入力する。管理画面の認証は「WordPressにログイン」で専用ブラウザーを開き、実際のログイン画面で認証する。二段階認証もそのブラウザーで入力し、QA画面の「ログインを確認」→「保存」で登録する。セッションファイルの作成は不要。
4. 保存すると対象サイトが選択される。検査範囲を選んで実行する。保存だけではサイトへアクセスしない。

認証情報はWindows DPAPIで暗号化し、ハーネスの `.ui/projects` に設定とともに保存する。設定には秘密の値を埋め込まず、実行時だけ子プロセスの環境変数へ渡す。ブラウザーセッションも復号したファイルをディスクに書かず渡す。暗号化データは同じWindowsユーザーで復号するため、別PC・別ユーザーへの移行は認証の再登録が必要。通常の検査期待値は暗号化対象ではないので、秘密そのものを期待値へ入力しない。

編集画面では認証の登録状況だけを表示する。空欄なら維持、再入力なら更新、「削除」にチェックして保存すると削除する。URL変更前には保存済み認証を削除する。同じURLの末尾スラッシュは同一サイトとして扱う。実行中の設定変更と、古い編集画面からの上書きは拒否する。設定変更後も過去の実行結果は保持する。

UI登録・編集・認証保存・検査・再起動復元の検証は `npm run test:settings`（Windows）。既存の `npm run test:ui` と併せて使用する。

## UIからWordPressにログインする

「サイトを登録」または「設定を編集」の認証情報欄で操作する。

1. サイトURLを確認し、「WordPressにログイン」を押す。通常のブラウザーとは分離した専用Chromiumウィンドウが開く。
2. 実際のWordPress画面でユーザー名・パスワードを入力する。必要なら二段階認証やSSOもその画面で完了する。
3. QA画面へ戻り「ログインを確認」を押す。取得したセッションでプロフィール画面にアクセスできることを別コンテキストで検証し、成功したら専用ウィンドウを閉じる。
4. 「保存」を押すと、対象サイトのセッションだけが暗号化して登録される。REST認証とは別なので、RESTを使う検査にはそちらの設定も必要。

ログイン画面が変更されているサイトは「ログインページのパス」を変更する。サブディレクトリ設置ならログインページと管理画面の両方に接頭辞を付ける（例：`/blog/wp-login.php` と `/blog/wp-admin/`）。実サイトはHTTPS、HTTPはローカルループバックのテストだけに対応する。

ログインから保存までの有効時間は10分。同時に1件のみで、完了・キャンセルまでは検査実行を止める。未完了・認証失敗・キャンセル・時間切れでは既存の認証を変更しない。UIを再読込しても対象サイトの設定を開けば進行中のログインに復帰できるが、編集途中の未保存項目は復元しない。

ログインパスワードをハーネスへ入力・保存する必要はない。認証確認は標準WordPressのCookie、プロフィールフォーム、管理バーを使う。プラグインでプロフィール画面を無効化している場合などは確認できないことがある。実行用に取り込むCookie・localStorageは対象サイトへ限定し、SSO先の情報は保存しない。ログインのtrace・画面画像は記録しない。認証が期限切れになったら同じ手順で再ログインする。

検証コマンドは `npm run test:login`。ローカル模擬WordPressで認証失敗・追加認証・セッション保存・管理設定検査・キャンセル・UI再読込を確認する。

```powershell
Set-Location C:\Users\roonawa\.claude\skills\wordpress-qa\harness
npm ci

```

## ローカルで一通り試す

別ターミナルで `npm run demo` を実行すると http://127.0.0.1:4300 に検証用サイトが起動する。WordPress本体ではなく、フォーム・メールAPI・HTML応答の契約を検証するfixtureである。

```powershell
node bin/qa.mjs validate --config examples/site.demo.json
node bin/qa.mjs run --config examples/site.demo.json --suite all
```

初回は画像基準がないためreviewになり終了2。表示されたreport.htmlを開き、画像とreadiness証拠を確認する。意図した表示と確認できた画像だけ承認する。

```powershell
node bin/qa.mjs approve-baseline --config examples/site.demo.json --run <実行フォルダー> --id snapshot.home-mobile
node bin/qa.mjs run --config examples/site.demo.json --suite all
```

承認は以前の結果を書き換えない。設定変更後の古い候補は承認できない。ブラウザー版・OS・表示設定が変わると再レビューになる。基準画像は設定と同様に案件ごとに管理し、正常だと確認した履歴を残す。

ハーネス自身の結合検証は `npm run test:integration`。独立ポートにfixtureを起動し、初回review→明示承認→正常2回→auditのみの未実施記録→意図的不具合検出を自動検証する。fixtureに限り画像承認もテストコードが実行する。実サイトの画像自動承認には転用しない。

## 実サイトへ導入

確認済みのサイトマップURLから一覧を収集する場合は、最初のサイト設定を用意して次を実行する。サイトマップの子一覧も辿るが、同一origin、100サイトマップ・10000ページまで。既存出力は上書きしない。

```powershell
node bin/qa.mjs discover --config <absolute-site.json> --sitemap /wp-sitemap.xml --output inventory.json
```

この例のパスを固定値として扱わず、SEOプラグイン等の実設定に合わせる。inventory.jsonは観測したURL一覧であり、期待値や合格結果ではない。CMS公開一覧や移行対象表と照合し、孤立ページも追加する。

1. 案件フォルダーへ `site.demo.json` をコピーし、名前・URL・環境・ページ期待値・policy・代表ページを実仕様へ変更する。
2. `journeys[].module`には案件の操作モジュールを置く。デモのセレクタや`/send`、`/collect`、cleanup URLはデモ専用なので、そのまま本番へ向けない。
3. 利用できる検証用メールサーバーとAPIを設定する。Mailpit API非互換の場合は案件モジュール側で検証し、到達できなければblockedを返す。
4. デザインの意図・実メール到達・reCAPTCHA実設定・バックアップ等、必要な未自動化項目をmanualへ追加する。
5. validate→audit→journey→visualの順に単独確認し、最後にallで同一実行の結果を集約する。実行結果そのものは別実行とマージしない。報告書に限り、同じ設定の過去結果で未実施項目を補える（後述）。

HTTP認証等のヘッダーは、環境変数へJSONで渡して`headersEnv`に変数名を設定する。認証方法によってstorageStateやログイン処理が必要な場合はPlaywright構成を案件に合わせて拡張する。管理設定の検査はUIで取得したログインセッションにも対応する。公開ページ・操作テストへのログインセッション適用は案件に合わせて設定する。

## スコープと証拠

`--suite audit|journey|visual|all`で実行範囲を選ぶ。他suiteは台帳から消えずnot_runになるため、単独実行は終了2になり得る。これは異常ではなく「全体判定は未完了」の意味。

各実行は出力フォルダーに `context.json`、`results.json`、`report.html`、必要な証拠を保存する。公開側の検査は失敗時の画像・trace、管理設定・拡張検査は秘匿した構造化証拠を使う。拡張検査は途中経過をJSONLへ逐次保存し、ワーカー異常終了後もUIで読み出す。認証ヘッダー値はcontextに保存しないが、trace・画像・HTML断片・案件がattachしたデータには機密情報が入り得る。検証データを使い、共有前に確認し、案件の保管期限・アクセス制限を適用する。

標準ブラウザーはChromium、workers=1、再試行=0。互換性検査ではFirefox/WebKitも指定できる。長い一覧の全リンク検査はtimeoutMs×4のテスト時間を超える場合がある。案件に合わせてページ分割やランナー時間枠を調整する。追加の性能計測・運用アダプター・外部連携は[追加検査](extended-checks.md)、実WordPressを起動する検証環境は[実WordPress検証](real-wordpress.md)を参照。総合脆弱性診断や任意のホスティング環境のDB復元は自動設定されない。

## 実行前確認と中断

「実行前の確認」で認証登録や実行環境などを点検し、「検査を停止」で協調停止できる。投稿の後始末を待つため即時終了ではない。未回収のテスト投稿は実行履歴の回収ボタンから処理する。結果が合格でも未回収や中断があれば全体の条件充足にはしない。

UIの再起動後もCLI・PlaywrightのPIDと実行所有情報を確認し、生存する検査と新規実行・回収が競合しないようにする。WindowsのPID再利用やプロセス起動情報の書込み途中の異常終了では、安全側で実行を止めることがある。その場合は関連プロセスが終了していることを確認してから、出力先の`.qa-active-run.json`、`.qa-run-claim`、該当実行の`run-owner.json`を調査する。プロセス生存中にロックを消して再実行しない。

テストの拡張・修正時は、正常データだけでなく、検出したい不具合を入れたfixtureで失敗することを確認する。新しいテストを毎回生成するのではなく、検証済みの検査を保守する。

ハーネス自体の回帰確認は `npm test`、既存検査の受入れは `npm run test:integration`、拡張検査は `npm run test:extended`、設定・証跡UIは `npm run test:extended-ui`、停止・所有者照合・回収は `npm run test:hardening` で実行する。`npm run test:real-wordpress` は隔離した実WordPressを起動する追加検証。fixtureの成功と実WordPressの成功を分けて記録する。

## 管理設定

`admin` suiteで認証済みREST・管理画面の設定を読み取り、期待値と照合できます。UIの「管理設定」で実行し、項目を選ぶと期待値・取得値・証拠を確認できます。[設定方法と認証](admin-settings.md)を参照してください。

## UIから不具合報告書を生成

### デザイナー向けの共有用HTML

サイトと完了済みの実行履歴を選び、「デザイナー向けレポートを作成・ダウンロード」を開きます。必要なら過去結果での補完と担当者の補足を指定して「デザイナー向けHTMLを生成」を押します。「生成したレポートを開く」で内容を確認し、「HTMLをダウンロード」で単体ファイルを保存できます。再読込後も作成済みファイルを取得でき、再生成は同じ実行の派生レポートのみ更新します。

保存済み証拠から表示・アクセシビリティの指摘をまとめ、利用者影響、管理画面を優先した修正候補、再現手順、枠付き画像、実装・運用担当への引継ぎ、未確認事項を掲載します。画像はHTMLへ埋め込みます。撮影済み証拠がない場合は未取得として記載し、生成ボタンから実サイトの操作や撮影は行いません。機械的な候補整理なので、デザインの意図や原因の確定は担当者が確認してください。

動作確認：`node test/designer-report-browser.mjs`（ローカルfixtureのみ）。

### 全項目の不具合報告書

1. サイトと完了済みの実行履歴を選び、検査項目の上にある「不具合報告書を作成」を開く。
2. 部分再テストなら「未実施の項目を同じ設定の過去結果で補う」を選ぶ。同一baseURL・環境・設定ハッシュで、選択した実行より前の完了履歴だけが対象。ケースIDごとに直近の実施結果を使い、選択した実行で合格・不合格・要確認・実行不能になった項目は上書きしない。
3. 原因調査の確定事項や担当者の判断があれば補足欄に記載。確認日・担当者・根拠を添え、認証情報は入れない。
4. 「報告書を生成」→「生成した報告書を開く」。選択実行のフォルダーに `issue-report.html` を保存する。再生成はこの派生ファイルを更新し、元の `results.json` と証拠は変更しない。ブラウザーの保存操作で単体HTMLとして渡せる。

報告書は不合格をルール・部品・例外メッセージでまとめ、利用者への影響、管理画面を優先した修正候補、コード確認が必要な場合の方針、再検証条件、展開できるケース別証拠を出力する。外部AI送信・本番アクセス・設定変更は行わない。HTML内に必要な証拠の抜粋を埋め込むため単体で読めるが、共有前にHTML断片などの機密情報を確認する。

自動整理の項目数は確定した根本原因数ではない。修正案は検査種別に基づく候補で、実際の設定・コードを調査した結果ではない。追加調査は担当者補足に区別して表示する。履歴補完の出典、要確認・未実施・実行不能、読めなかった証拠を明示し、過去結果を再検査済みとして扱わない。旧ハーネスの準備エラーでは本判定に到達していないことがあるため、元の理由も確認する。

報告書の回帰検査：`node --test test/issue-report.test.mjs` と `npm run test:report-ui`。

表示検査のaxe不合格では、対象要素を表示位置へスクロールし、赤枠と指摘番号を一時的に重ねたPNGを自動保存する。撮影後は枠を撤去し、本番データを変更しない。報告書ではケースの「問題箇所のスクリーンショット」から確認でき、単体HTMLにも画像を埋め込む。対象URL・画面幅・撮影日時・セレクターを併記する。iframe／Shadow DOM等の未対応・非表示・対象不明の場合は未取得理由を記録する。既存の履歴に枠付き画像がなければ、保存済みの失敗画面を「参考画面（枠付けなし）」として掲載し、推測で枠を付けない。新しい枠付き画像は表示検査の再実行で取得する。JavaScriptの内部例外や存在しない要素など、画面位置を示せない指摘では参考画面とエラー証拠を区別する。

枠付け処理の回帰検査：`node test/marked-screenshots.mjs`。

報告書では各指摘のケースごとに「再現手順」を展開できる。実行時のcontext.jsonから対象URL・画面幅を取得し、保存済み証拠に基づく期待結果・実際の結果・確認範囲を記載する。JavaScriptは表示準備と画像スクロール、axeは対象要素と測定、公開応答はNetworkでの確認手順を出力する。操作が分からない検査は推測せず追加確認とする。自動検査で実施した操作と、人が追試するための手順を区別し、内部例外だけから白画面・購入不能などを断定しない。追加調査で確定した発生タイミング・利用者操作は担当者補足へ記録する。

## 登録時のケース生成

### 条件の自動取得（2026-10-28）

新規登録では認証済み管理画面と公開ページから条件を取得し、`automation-discovery.mjs` → `automation-plan.mjs` で検査に変換する。表示・コメント・パーマリンク・有効プラグインは現在値の回帰基準として扱い、業務上の正しさを自動承認しない。入力済み期待値と以前の基準値を維持する。

CF7のページ・ID・入力項目は一意に取得できれば入力不要。登録画面の当該欄は空欄を自動取得として扱い、複数候補の場合だけ対象を指定する。送信許可・テストメール・銀行振込の期待合計などは自動推定しない。公開検査には管理者Cookieを渡さず、フォーム入力検証・通信失敗検査ではすべての書込み通信を遮断する。JS例外は独立した検査へ記録し、入力検証等を中止しない。

既存の登録サイトは「設定を編集」→「保存済みの条件でサイトを再取得」で共通化する。未保存の入力・進行中ログイン・実行中テストがある場合は上書きしない。再取得は読み取りだけであり、投稿・注文・問い合わせの許可を追加しない。通常保存でも登録した追加検査条件を実行可能な設定へコンパイルする。

`discovered-public` は、検出した検索GET導線・検証済みメニュー状態の開閉、宣言済みフォームの必須／メール形式、CF7通信失敗時の表示・入力保持・再操作、robots構文とサイトマップの参照先を検査する。対象・制約が取得できない場合は理由を残す。検索結果の業務上の妥当性、独自境界値、実機、成功時の重複登録まで検査したとは表現しない。

検証環境で投稿操作が許可されれば `wp-cache` も生成する。管理者のブラウザー認証からREST nonceを実行時に取得でき、追加のRESTパスワードを要求しない。自分で作成した投稿だけを公開・更新・非公開化・回収し、匿名のキャッシュ漏洩と3回の更新反映を確認する。一覧・別ロールは固有の条件を追加する。

受信箱API・別ロール認証・隔離復元アダプター・性能上限等は「自動取得と追加条件」で指定する。メール到達は送信と同じ識別子を同一 `browser-flow` の `waitForMail` で照合する。単独のメール検査やCF7のmail_sentだけを受信箱到達の根拠にしない。追加条件はサーバーで既存検査スキーマを検証し、任意モジュールの実行は許可しない。

登録画面では追加ロール1件のREST認証／セッションファイルも登録できる。パスワード・ファイル内容は下書きやプロフィールへ入れず、既存の認証保存へ渡す。複数ロールは設定画面で追加する。

`wp-authz` 等のWordPress検査でも管理者REST認証が未指定なら保存済み管理者ブラウザー認証を利用する。明示したREST認証が壊れている場合は別認証へ黙って切り替えない。別ロール自身の認証はそのロールでの正の認証確認に使用し、管理者認証で代用しない。

計測イベントは `browser-flow` の `assertRequest` で、実際に完了したリクエストの正確なURL・HTTP method・query/bodyの指定値・countを照合できる。ゼロ件はtimeoutMs全体、正の回数は到着後settleMsまで観測する。失敗・未完了通信は合格にしない。外部送信先はネットワーク許可へ明示し、POSTはsandboxと操作許可を要する。証拠は件数のみで生の送信本文を残さない。計測サービス内部での集計完了・無期限の重複防止を保証する検査ではない。

回帰検証は `test/automation-*.test.mjs`、`test/registration-automation.test.mjs`、`test/rediscovery-api.test.mjs`、`test/discovered.test.mjs`、`test/wp-cache-browser-auth.test.mjs` を使用する。

「サイトを登録」でサイトURL・環境・管理者ログイン・閲覧保護と期待値をまとめて設定します。公開済み記事と固定ページを管理画面の認証で取得し、URL検査、代表5ページまでの表示検査、管理設定、CMS一覧照合を生成します。登録時には送信せず、保存後の「検査を実行」で実行し、終了時に不具合報告書を自動生成します。

検証環境ではテスト投稿の作成・更新・予約公開・回収を含められます。CF7送信はフォームID・ページ・項目名・テストメールを登録します。銀行振込注文はWelcartの商品・送料込みの期待合計・決済表示名を登録し、対応する確認・取消手順がある場合に実行します。本番ではテスト投稿と実送信を禁止します。管理者ログインと閲覧保護は別に保存し、公開検査に管理者Cookieを流用しません。

初回の画像基準、内容の正しさ、受信箱到達、別ロール、隔離復元などは自動で正解を決めません。未確認の範囲は報告書に残します。認証の期限切れは再ログインが必要です。「詳細な検査設定」は従来の項目編集です。[範囲と補完手順](coverage-generation.md)も参照してください。

登録から実行・報告書までのローカル検証：`node test/registration-browser.mjs`。実サイトには送信しません。


## 共通自動検査（2026-10-27）
新規登録は `generateCases` で8種類の `standard-public` 検査を生成する。既存管理サイトは設定画面の「保存時に共通自動検査を追加・更新」で追加可能。`--suite standard` / UI「共通自動検査（送信なし）」はこの検査だけを選択する。代表ページ最大5件。HTML構造・宣言済み制約・Tab到達・参考測定等の限定的な自動判定であり、業務全体の合格と表現しない。範囲は `harness/deploy/automation-guide.html` を参照。未設定の包括観点を一律human-reviewへ変換せず、設定不足と人の判断を分ける。

### 万年堂由来の操作検査の共通化（2026-10-27）

登録・設定画面の「共通の操作テスト」で検索、メニュー、CF7入力検証・通信遮断、カート境界値、Firefox、公開情報調査等を設定できる。`profile.interactions` を入力に `generateInteractionChecks` が `site-interaction` を生成する。通常の「すべての検査」、または範囲 `interaction` で実行する。独自サイト専用のモジュールを新規生成しない。使用方法・全対応表は `harness/deploy/common-operation-guide.html`。

万年堂専用21操作は共通操作15＋builtin6へ移植。CMSカスタム投稿型・補助URL・部品転送は `interactions.inventory`、管理画面の追加期待値は `interactions.admin`。本番では送信・注文・投稿作成を許可しない。実行条件未設定、閲覧認証切れ、未回収注文、ブラウザー未導入を合格に置き換えない。旧操作の注文保留記録は取消の確証なしに削除しない。性能参考測定・公開情報調査は合否を保証する仕様検査と区別する。
