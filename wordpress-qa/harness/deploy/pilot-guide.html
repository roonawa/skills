WordPress QA 社内共有版・試用計画

2026年10月27日／Linux・Docker／同じサイトと権限を共有する少人数向け

共有版の基盤を実装済み。社内サーバーへの配置・ネットワーク公開は未実施です。ローカル環境で181件のテストと共有UIの登録を確認済み。Docker Composeの構成検証は成功しましたが、Docker Engineが起動していないため、Linuxコンテナのビルド・起動・HTTPS接続は未確認です。

1. 試用する構成

メンバーのブラウザー
    ↓ HTTPS（社内ネットワーク／VPNからのみ）
Caddy：証明書・TLS終端
    ↓ Dockerネットワーク内 HTTP（アプリのポートは外部公開しない）
QAアプリ：個別ユーザー認証・サイト管理・実行制御・報告書
    ├ Playwright：同時実行は全体で1件、追加実行は待機を案内
    ├ 永続ボリューム：設定／実行結果／画像／監査ログ
    └ Secretファイル：暗号化キー／利用者のパスワードハッシュ

各PCへのテスト実行環境の導入は不要です。ただし初回のWordPressセッション作成は、当面、担当者のPCで行って共有UIへ取り込みます。UIの新規登録は詳細設定画面を使用し、基本テストケースを生成します。ログイン付き自動調査ウィザードは遠隔版に未対応です。

2. 現在の実装と今回の改修

観点調査した現状今回の対応
入口127.0.0.1限定、利用者認証なし既存ローカルモードは維持。共有専用起動を追加し、全画面・API・証拠取得に利用者ごとのHTTP Basic認証。公開originとHostの厳密照合、利用者別CSRFトークン。
認証情報Windows CurrentUserのDPAPI専用共有モードにAES-256-GCMの暗号化保存を追加。32バイトキーは別ファイル。改ざん・異なるキーでは復号失敗。
遠隔ログイン実行PCに可視ブラウザーを開く共有モードでは当該操作をAPIとUIで停止。REST認証と対象サイト専用セッションJSONの取込みを案内。
保存ローカルパスと実行履歴/data配下にUI登録サイト・履歴・暗号化認証を永続化。再起動後の登録復元を検証。
操作の衝突既存の1実行制限、設定バージョン照合、回収待ち制御同じ仕組みを利用。待ち行列は未実装。試用版はアプリ1台のみで運用。
操作記録テストごとの結果・ログ認証済みPOSTの利用者・日時・APIパス・HTTP結果をaudit.jsonlに記録。入力内容・パスワードは監査ログに保存しない。テスト合否は実行履歴で確認。
配布各PCのNode・Playwright環境Dockerfile、Compose、Caddy設定、キーと初期アカウントの生成コマンドを追加。アプリは非root実行、日本語フォントを含む。

3. サーバー管理者が決めること

  • 配置するLinuxホストと社内DNS名、メンバーから接続できるIP・ポート。
  • 最初の利用者名。全員に全サイトの閲覧・設定・実行権限があります。閲覧専用・サイト別権限はまだありません。
  • 社内証明書を使うか、試用用Caddy CAを管理端末へ配布するか。
  • バックアップ先、結果・画像の保存期間、容量上限の運用。画像や結果にはテストで入力した情報が含まれ得ます。
  • 対象サイトへの通信許可。信頼できるメンバーだけを登録し、サーバーのクラウドメタデータや管理ネットワークへの不要な外向き通信は制限してください。登録URLの組織別許可リストは未実装です。

4. Linuxへの導入手順

ハーネスのディレクトリを作業ディレクトリにします。初期設定コマンドにはNode.js 22以上が必要です。既存の顧客設定・認証・履歴をDockerイメージへコピーしないでください。

npm ci
# 新規のディレクトリにのみ生成。既存キーを上書きしない。
node bin/init-pilot.mjs deploy/secrets alice bob
cp deploy/.env.example deploy/.env
# deploy/.envのDNS名・HTTPS origin・接続ポートを設定
# WPQA_BIND_IPは初期値127.0.0.1。社内公開前の確認まで維持。

# 標準のrootful Docker、コンテナ内node UID=1000の場合
sudo chown 1000:1000 deploy/secrets/key deploy/secrets/users.json
sudo chmod 400 deploy/secrets/key deploy/secrets/users.json

docker compose --env-file deploy/.env -f deploy/compose.yaml config --quiet
docker compose --env-file deploy/.env -f deploy/compose.yaml build
docker compose --env-file deploy/.env -f deploy/compose.yaml up -d

initial-passwords.jsonは管理者が利用者本人へ個別配布するためのファイルです。コンテナにはマウントしません。配布後は社内の秘密情報管理方針に従って保管または回収してください。rootless DockerではUIDの対応が異なるため、コンテナ内nodeがキーを読める権限を確認してください。

初期構成はCaddyの内部CAを使います。社内管理者がCA証明書を配布・信頼設定するか、承認済みの社内証明書へ差し替えます。ブラウザーの証明書警告を回避して使う運用にはしません。

# 公開するのはCAの証明書のみ。秘密鍵を配布しない。
docker compose --env-file deploy/.env -f deploy/compose.yaml cp proxy:/data/caddy/pki/authorities/local/root.crt ./qa-pilot-root.crt

DNS・証明書・ログインを確認後、WPQA_BIND_IPを指定の社内インターフェースIPへ変更し、接続元を社内/VPNに限定するファイアウォール規則とともに反映します。アプリの4310ポートをホストへ直接公開しないでください。複数レプリカでは運用しません。

根拠：Caddyのコンテナと証明書の信頼、Docker ComposeのSecretファイル。

5. メンバーの試用手順

  1. 共有URLを開き、自分の利用者名と配布されたパスワードでログイン。
  2. 「サイトを登録」でサイト名・URL・環境を入力し、基本テストケースを生成。対象URLと期待値を確認。
  3. 管理画面の検査が必要なら、担当者が用意したREST認証またはPlaywrightのstorageState JSONを設定画面から取り込む。Cookieのホストとoriginは対象サイトに限定。通常のChromeのログイン状態は自動共有されません。
  4. 認証・期待値が揃った検査から実行。他のメンバーの実行中は完了を待つ。
  5. 結果と未確認事項を確認し、「デザイナー向けHTMLを生成」から共有用レポートを取得。

初版はHTTPS越しのBasic認証です。SSO・MFA・明示的ログアウト・ユーザー管理画面は未実装です。共有PCではブラウザーが認証を保持する点に注意し、個別プロファイルを使用してください。利用者削除やパスワード更新は管理者がハッシュファイルを更新し、アプリを再起動して反映します。暗号化キーを再生成して利用者を更新してはいけません。

6. 万年堂など既存データの移行

初版は新しいサイトを共有UIへ登録する方式です。現在のWindows側の外部設定ファイルや履歴は自動移行しません。Windowsの絶対パス、個別操作スクリプト、DPAPIで暗号化した認証をそのままLinuxへコピーしても動きません。

  1. 既存レポートは単体HTMLとして保存して共有可能。
  2. サイトを共有版へ再登録し、必要なURL・期待値を移す。認証は共有版で再登録。
  3. 個別スクリプトを標準検査へ置き換えるか、Linuxでの依存関係・パスを調査して移行する。
  4. 移行後の結果は新しい実行として記録。Windowsの描画とLinuxの描画は異なり得るため、画像基準は再承認する。

7. 試用開始前の受入確認

  • LinuxでDockerイメージをビルドし、非rootでChromium・Firefoxを起動できる。
  • 未ログインではHTML・API・結果ファイルを取得できない。誤ったHost・Origin・CSRFトークンが拒否される。
  • 2名で同じサイトが見え、重複実行が止まり、設定の同時更新が競合として通知される。
  • サーバー再起動後もサイト・結果・認証が復元される。暗号化キーとデータを分けて保全する。
  • 小さな検証サイトで「登録→検査→結果→HTMLダウンロード」を行う。注文・送信は対象と通知先を設定した後に検証環境で確認する。
  • 本番でテスト投稿・注文・問い合わせ送信の許可を設定できない。
  • 終了時は検査完了とテストデータ回収を待つ。強制終了した検査を自動再送しない。
