# 認証なしセキュリティ基礎診断 設計書

- 作成日：2026-11-02
- 対象：SITE EXAM（wordpress-qa harness）
- 状態：実装済み

## 1. 目的と背景

SITE EXAMは「依頼されたWordPressサイトに不具合やセキュリティ上の問題・脆弱性につながる兆候があるかを診断し、課題を分かりやすく説明して修正対応へつなげる」社内ツールである。現状、脆弱性に関わる検査は管理画面認証が必要な `software-security`（バージョンと既知脆弱性情報の照合）しかなく、URLしか手元にない受付直後の段階では、セキュリティの兆候をほとんど示せない。

診断サービスはまだ開始前で、実際の依頼の流れは想定で決める。想定する利用場面は次のとおり。

- 診断担当者がサイトURLだけを登録した直後に、外から見える危険の兆候を一覧で把握する。
- その結果をそのまま顧客向けの説明と、修正担当への依頼材料に使う。

## 2. ゴール・非ゴール・アンチゴール

### ゴール
- 管理画面認証なしで、公開URLへの読み取りアクセスだけで実行できる基礎診断を追加する。
- 既存の「共通自動検査（送信なし）」と同様に、サイト登録時に `auto-*` 検査として自動生成する。
- 検出した課題ごとに、顧客向けの平易な説明・直し方（担当区分つき）・確認方法を最初から付ける。
- 「兆候あり」と「注意」を区別して表示する（3章）。

### 非ゴール（今回やらない）
- 公開情報から推定したバージョンと脆弱性DBとの照合（改善案4として別途）。
- 2つ目の脆弱性情報源の追加、報告書の統合、修正後の再診断差分。
- 認証付きの検査、侵入テスト、ポートスキャン、サーバーOS・WAFの診断。

### アンチゴール（技術的に動いても失敗とみなすもの）
- 攻撃用の入力、総当たり、POSTによる探り（例：xmlrpcの `system.listMethods`）、大量リクエストを送ること。
- 取得した機密ファイルの中身（`wp-config` のバックアップ、`.git`、`debug.log` 等）を証拠として保存・表示・AIへ送信すること。
- 確認できなかった項目を「問題なし」と表示すること。
- WordPressがよく返す「存在しないURLでも200でHTMLを返す」応答（soft 404）を、露出として誤検出すること。
- 本番環境で、担当者の明示的な許可なしに機密パスへアクセスすること。

## 3. 結果の段階（利用者と合意済み）

| 段階 | 意味 | 台帳上の扱い |
|---|---|---|
| 兆候あり | 明らかな露出・設定不備。放置すると被害に直結しうる | `required:true` の検査が不合格。必須条件は「未達」 |
| 注意 | 多くのサイトで該当し、それだけで危険とは言えないが改善が望ましい | `required:false` の検査にまとめ、UI・レポートで「注意」と表示。必須条件の判定に影響しない |
| 問題なし | 該当なし | 合格 |
| 実行不能 | 通信失敗・接続制限等で確認できない | 既存どおり。「問題なし」にしない |
| 設定が必要 | 許可がなく実行しない（4章） | 既存の `preparationRequired` と同じ扱い |

「注意」は利用者の判断で、CSP等のヘッダー不足やバージョン表示のように一般的に多い項目に使う。

表示要件：
- `security-baseline` 検査の `required:false` で不合格になった行は、UI・results.html・不具合報告書・顧客向け診断HTMLで「不合格」ではなく「注意」と表示する。
- 既存の他の参考検査（AI補完の `required:false` の検査など）の表示は変えない。「注意」は `security-baseline` に限る。

データ形式（設計者の判断）：
- 新しいステータスは作らない。内部の `status` は `'fail'` のままにし、行に `level:'caution'` を付ける。
- `summary` の既存のキーは意味を変えない。`fail` には注意の件数も含める。新しく `summary.caution` を追加する。
- 画面とレポートの「不合格」の件数は `fail − caution` で計算する。
- こうすることで、`results.json` を読む既存の処理（`latest-results.mjs`、報告書の集約、Linux更新スキル等）や過去の結果は、そのまま読める。

必須条件（`releaseGate`）への影響（設計者の判断）：
- 本番で許可がなく `exposure` が「設定が必要」になった場合、必須条件は「未達」のままにする。確認していない項目を合格扱いにしない、という既存の原則に従うため。
- 確認しないと決めた場合は、担当者が既存の手動判定で理由付きの「対象外」にする。

## 4. 本番環境での機密パス確認の許可（利用者と合意済み）

`.git/HEAD` や `wp-config.php.bak` へのアクセスは読み取りだけだが、顧客側のWAF・監視が攻撃の下見と判断して警告やIP遮断をする可能性がある。

- 本番環境では、担当者が明示的に許可したときだけ機密パスの確認（5.1の `exposure` 分類）を実行する。利用者の決定。
- 設定ファイルには、トップレベルの真偽値 `allowSensitivePaths`（省略時は `false`）として保存する。`writes` と `allowTestWrites` の関係にならう（設計者の判断）。`lib/config.mjs` の許可キー一覧に追加し、`validateRuntime(check,config)` で参照する。
- 新しい登録項目 `profile.sensitivePaths`（表示名：「機密ファイル露出の確認（存在確認のみ。顧客の監視に検知される場合があります）」）を追加する。
  - 既存の `writes`／`submit`／`bankOrder` は本番で強制的に無効化されるが、この項目は本番でも選択可能にする。
  - 初期値：本番は未選択。**検証・ローカルは選択済み（設計者の判断）**。検証環境も顧客WAFの配下にある場合があるため、外すことはできる。
- 許可がない場合、`exposure` 検査は実行せず「設定が必要」とし、理由に「本番環境の機密パス確認は許可が必要です」と表示する。「問題なし」にしない。
- AI補完・自動準備（`ui/automatic-preparation.mjs` 等）はこの許可を有効化しない。
- 機密パス以外の分類（通常ページ・ヘッダー・TLS等の取得）は、通常の閲覧と同等なので許可なしで実行する。

## 5. 検査内容

新しい検査種別 `security-baseline` を `lib/checks/` に追加し、`options.area` で分類を分ける。分類ごとに直す担当が異なるため、1件にまとめない。

| 検査ID（自動生成） | area | suite | required | 内容 |
|---|---|---|---|---|
| auto-security-exposure | exposure | authz | true | 機密ファイル・一覧表示の露出 |
| auto-security-transport | transport | authz | true | HTTPS転送・証明書 |
| auto-security-active-mixed | mixed | authz | true | 能動的な混在コンテンツ |
| auto-security-headers | headers | authz | false（注意） | セキュリティヘッダー・Cookie属性 |
| auto-security-disclosure | disclosure | authz | false（注意） | バージョン・ユーザー名・xmlrpc等の情報露出 |

検査IDと分類名は設計者の判断。実装者が変えてよい。

### 5.1 exposure（兆候あり・許可が必要）

各パスにGETし、**内容の特徴が一致した場合だけ**露出と判定する。HTTP 200だけでは判定しない（soft 404対策）。

| 対象 | 判定条件（すべて満たすとき露出） |
|---|---|
| `/.git/HEAD` | 本文先頭が `ref: refs/` または40桁の16進数 |
| `/.git/config` | `[core]` を含む |
| `/wp-content/debug.log` | PHPのログ行形式（例：`PHP Warning:`、`PHP Fatal error:`、`PHP Notice:` を含む行が1行以上） |
| `wp-config.php` のバックアップ（`.bak`、`.old`、`.orig`、`.save`、`~`、`.txt` 程度） | `DB_NAME` または `DB_PASSWORD` を含み、`text/html` のWordPressページではない |
| `/wp-content/uploads/` | `<title>Index of` を含むディレクトリ一覧 |
| `/.env` | `KEY=VALUE` 形式の行が複数あり、HTMLではない |

- 本文は先頭64KiBまでしか読まない。判定後すぐ破棄する。
- 証拠に残すのは「パス、HTTPステータス、Content-Type、サイズ、一致したルール名」だけ。**本文の抜粋は保存しない。**

### 5.2 transport（兆候あり）

- HTTPS転送：`http://<host>/` にGETし、`https://` の同じホストへ転送されるかを確認する。転送先へは接続しない（`Location` ヘッダーを読むだけ）。
- Linux共有版の外部接続制限の変更（利用者と合意済み：限定して許可）：
  - 現状の `lib/egress-policy.mjs` は、`http://` のoriginに社内固定IPの指定を必須にしている。そのため公開サイトの `http://` には接続できない。
  - 次の条件をすべて満たすときだけ、egress proxyは `http://` への接続を通す。
    1. 同じホスト名・既定ポートの `https://` originが許可設定に登録されている。
    2. メソッドはGETで、パスは `/` だけ（クエリなし）。
    3. 名前解決した接続先IPが、既存の判定で `public` に分類される。社内IPや特殊IPは、今と同じく拒否する。
    4. リクエスト本文がない。
  - 管理者が許可設定に `http://` originを書く必要はない（設定画面の変更は不要）。社内固定IPを使う既存の `http://` の許可ルールは、今の動きのまま残す。
  - この緩和は proxy の平文HTTP処理（`bin/egress-proxy.mjs` の `createServer` 側）に限定する。CONNECTの処理は変えない。
  - 上の条件に合わずに拒否された場合は、HTTPS転送確認を「実行不能」とし、理由を表示する。
  - テスト：条件1〜4のそれぞれが欠けたときに拒否されること、POST・別パス・社内IPへの接続が通らないことを確認する。
- 証明書：対象ホストにTLS接続し、残り日数、ホスト名の一致、信頼チェーンを確認する。
  - 期限切れ・ホスト名不一致・信頼できない証明書は「兆候あり」。
  - **残り14日未満も「兆候あり」とする（設計者の判断）。**
  - Linux共有版ではegress proxyのCONNECTトンネル経由で接続する。
- 対象サイトが `http://` のみで運用されている場合（local環境を除く）は「兆候あり」。

### 5.3 mixed（兆候あり）

- HTTPSページで、`http:` の `script`／`iframe`／`form action`／`link rel=stylesheet` は能動的な混在コンテンツとして「兆候あり」。
- `img`／`video`／`audio` 等の受動的な混在コンテンツは `headers` 分類の「注意」に入れる。
- 既存の `standard-public` の `integrations` が `insecure script URL` を出しているため、同じ問題を二重に数えないよう実装者が整理する。

### 5.4 headers（注意）

トップページと代表ページ（既存の `paths` と同じ最大5件）の応答ヘッダーを確認する。
- HTTPS時の `Strict-Transport-Security` の有無
- `Content-Security-Policy` の有無
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options` またはCSPの `frame-ancestors`
- `Referrer-Policy`
- `Set-Cookie` の `Secure`（HTTPS時）、`HttpOnly`、`SameSite` の欠落
- 受動的な混在コンテンツ（5.3）

### 5.5 disclosure（注意）

| 対象 | 方法 |
|---|---|
| WordPressバージョン表示 | トップページの `meta name=generator`、`/readme.html` の版番号、`/feed/` の generator、コアのCSS・JSの `ver=` |
| サーバー・PHPの版表示 | `Server`、`X-Powered-By` ヘッダーに版番号が含まれるか |
| RESTによるユーザー名の列挙 | `GET /wp-json/wp/v2/users` がユーザーの `slug` を含むJSON配列を返すか |
| 投稿者アーカイブによる列挙 | `GET /?author=1` が `/author/<slug>/` へ転送されるか（転送先URLだけを見て、転送先は取得しない） |
| XML-RPCの有効 | `GET /xmlrpc.php` が `XML-RPC server accepts POST requests only` を返すか。POSTは送らない |

- ユーザー名そのものは証拠に残さず、件数だけを残す（設計者の判断）。

### 5.6 通信の制約（すべての分類に共通）

- メソッドはGETとHEADだけ。リクエストヘッダーは通常のブラウザー相当で、攻撃用の文字列は入れない。
- 対象は登録した `baseURL` と同じホストだけ（HTTPS転送確認の `http://` のみ例外）。既存の `sameOrigin`・egress policy・`scopedHeaders` を通す。
- リクエストの上限は、検査（分類）ごとに設ける（設計者の判断）。上限は exposure 16件、transport 4件、mixed・headers・disclosure は各10件で、合計は最大50件。どの分類を選んで実行しても同じ上限を使う。
  - 件数には、転送の各段と、soft 404を見分けるための存在しないURLへの1件を含める。TLS接続は件数に含めない。
  - 検査をまたいだカウンターや応答の共有はしない。同じページを別の分類で取り直すことは許容する。
  - 上限に達したら、残りの項目は「未確認」として証拠に記録する。その検査に兆候がなければ、結果は「実行不能」にする（問題なしにしない）。
- 各検査の中では逐次実行し、リクエストの間に **200ms以上** の間隔を空ける。
- 各リクエストのタイムアウトは既存の検査に合わせる。中断（`signal`）に従う。
- サイト閲覧パスワード（Basic認証等）が登録されていれば、既存の仕組みでそれを使う。管理画面の認証は使わない。

## 6. 説明と修正への引き継ぎ

検出ルールごとに、`lib/failure-explanations.mjs`（または同等の場所）へ次の定型文を用意する。担当者が一から書かなくても顧客へ説明できるようにするため。

- 顧客向けの説明：何が見えているか、放置すると何が起きうるかを平易な日本語で書く。断定を避け「〜のおそれ」とする。
- 直し方と担当区分：「WordPress管理画面・プラグイン」「サーバー・ホスティング設定」「テーマ・開発」のいずれか。例：ヘッダーはサーバー設定またはセキュリティ系プラグイン、`.git` 露出はサーバーからの削除・アクセス拒否。
- 確認方法：修正後に同じ検査を再実行することと、手動で確かめる場合のURL。

不具合報告書・顧客向け診断HTMLは、既存の集約処理でこの説明を拾えるようにする。採点（site-exam-risk-2）の点数は自動で付けない。人が評価する既存の流れのまま。

## 7. 既存機能への組み込み

- `lib/checks/index.mjs` のハンドラー一覧に追加する。許可がない場合の「設定が必要」は `validateRuntime` で `BLOCKED: ` を返す既存の方式で表す。
- `ui/public/case-generator.js` の自動生成（`auto-*`）に5件を追加する。管理画面認証の有無に関係なく生成する。
- 既存の登録済みサイトにも追加する。追加のタイミングは、UIで管理しているサイトの実行前の共通補完とする（設計者の判断）。存在しない `auto-security-*` だけを足す。設定のハッシュが変わることは許容する。外部JSONで読み込んだ旧形式のサイトには自動で追加しない。
- 検査範囲の選択肢では「共通自動検査（送信なし）」に含める（`lib/config.mjs` の `standard` 範囲）。
- 登録画面（`ui/public/registration.js`）・設定画面・準備ウィザードに `sensitivePaths` を追加する。既存サイトの設定を開いたときは未選択として扱う。
- UIの表示コード（`options-form.js`、`coverage-editor.js`、`automation-inputs.js` 等）が検査種別を列挙している箇所に `security-baseline` を追加する。
- 仕様書 `deploy/internal-announcement/SITE-EXAM-specification.md` の2.1、3、4.3、付録A、および操作マニュアルを更新する。

## 8. テスト

- 単体テスト（`node --test`）：
  - 各ルールの判定。特にsoft 404（存在しないパスで200のHTMLを返すサイト）で露出と誤判定しないこと。
  - 本文・ユーザー名が証拠に残らないこと。
  - リクエスト件数の上限と間隔。
- 許可のテスト：本番で `sensitivePaths` が未選択なら `exposure` が「設定が必要」になり、機密パスへのリクエストが1件も出ないこと。
- 通信制限のテスト：egress policyで `http://` が拒否されたとき、HTTPS転送確認が「実行不能」になること。
- 表示のテスト：`required:false` の不合格が「注意」と表示され、集計で不合格と別に数えられること。
- `examples/demo-server.mjs` 相当のローカルサーバーに、露出ありと露出なしの両方のパターンを用意する。

## 9. 実装者に任せる事項

- ファイル分割、関数名、検出ルールの内部表現。
- 定型文の具体的な文面（6章の方針に従う）。
- バックアップファイル名の候補の細部（リクエスト件数の上限を守る範囲で）。
- TLS確認の具体的な実装方法（Windowsローカル版とLinux共有版の両方で動くこと）。
