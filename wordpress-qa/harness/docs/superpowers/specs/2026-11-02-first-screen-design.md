# 結果画面の「次にやること」整理 設計書

- 作成日：2026-11-02
- 対象：SITE EXAM（wordpress-qa harness）の結果画面（`ui/public/app.js`）
- 状態：レビュー済み・利用者の承認待ち

## 1. 目的と背景

利用者の声：「設定が必要な項目が多く、またそれらの設定が難しい」。

調査（テスト用 WordPress サイトを実際の登録画面の流れで登録した直後）：
- 検査112件のうち「設定が必要」22件、人による確認9件。22件中19件に「重要」の点滅が付き、強調の意味がなくなっている。
- 22件の内訳（`ui/evidence-preparation.mjs` の `unresolvedPreparation` が既に付けている category を基に整理）：
  - ツールが自動取得できなかっただけ（category `discovery`）：6件。担当者の入力は不要とツール自身が判定済み。
  - 許可のチェックだけで済む（`permission`）：3件（テスト投稿・キャッシュ・予約公開）。
  - 業務上の値の入力（`input`）：6件（フォーム送信のテスト宛先、計測イベント、注文3件、表示速度上限）。
  - 外部連携（`integration`）：5件（通知メール受信・更新・復元）。
  - 別アカウント（`credentials`）：2件（ロール・会員）。
- 通販でも会員サイトでもないのに、注文・会員の検査が「設定が必要」に並ぶ。
- 説明文に開発者向けの言葉（browser-flow、waitForMail、adminに登録、信頼済みアダプター）がそのまま出る。

目的：知識の浅い診断担当者が、実行直後の結果画面だけで「何が分かったか」と「自分が次にやること」を迷わず把握し、その場で済ませられるようにする。

## 2. ゴール・非ゴール・アンチゴール

### ゴール
- 結果画面を、上から「件数カード → 次にやること → 分かったこと → まだ確認していないもの」の順に並べる（利用者がB案を選択）。
- 「設定が必要」を、担当者が自分でできるもの（次にやること）と、そうでないもの（3区分）に振り分ける。
- 「次にやること」は結果画面の上でその場で入力・保存でき、増えた検査だけをすぐ実行できる（利用者の決定）。
- このサイトに関係しない検査を、登録時の取得情報から自動で見分ける。

### 非ゴール
- 検査そのものの追加・判定ロジックの変更。
- 外部連携（メール受信・更新・復元）の設定画面を作ること。
- 設定画面（既存）の作り直し。既存の設定画面はそのまま残す。

### アンチゴール
- 確認していない項目を「対象外」「問題なし」に見せること。「このサイトに関係しない」は判断の根拠を表示し、手で戻せること。
- 担当者の許可なく、テスト投稿・フォーム送信・機密パス確認などの操作が有効になること。チェックは明示的に担当者が入れる。
- 本番環境でテスト投稿・フォーム送信の入力を出すこと。
- 既存の必須条件（`releaseGate`）・結果データ（`results.json`）の意味を変えること。ただし5.4の「理由付き対象外」は利用者の決定による例外で、既存の「理由付きの対象外は必須条件を満たす」規則の範囲で行う。

## 3. 振り分けの規則

「設定が必要」（`preparationRequired`）の行を、次の4つに振り分ける。判定は既存の `unresolvedPreparation` の category と登録時の取得情報（`profile`・`automation.activePlugins`）・環境を使う。

| 振り分け先 | 対象 | 表示 |
|---|---|---|
| 次にやること | 担当者が結果画面で入力・チェックするだけで実行可能になるもの（4章の一覧） | 「次にやること」欄。重要の印はここだけ |
| ツールが取得できなかったもの | category `discovery` | 折りたたみ「まだ確認していないもの」内 |
| 技術担当の準備が要るもの | category `integration`・`credentials`・`implementation`・`mixed`、計測イベント（analytics）、注文（ECがある場合） | 同上 |
| このサイトに関係しないもの | 5章の自動判定に当たるもの、および本番環境でのテスト投稿・フォーム送信 | 同上。判断の根拠と「関係ありに戻す」操作を表示 |

「重要」の点滅（`preparationImportance`）は「次にやること」に入った項目にだけ付ける（設計者の判断）。

## 4. 「次にやること」の項目

| 項目 | 入力 | 動くようになる検査 | 表示条件 |
|---|---|---|---|
| テスト投稿の作成・公開・削除を許可 | チェック（`profile.writes`） | 投稿・キャッシュ・予約公開 | 検証・ローカル環境のみ |
| フォームの実際の送信を許可＋テスト用メールアドレス | チェック（`profile.submit`）＋メール（`profile.testEmail`） | フォーム送信 | 検証・ローカル環境、かつ問い合わせフォームを検出済み |
| トップページの表示上限（秒） | 数値（`profile.performanceMs`、画面は秒） | 表示速度の合否判定 | 常に。今回の実測値を参考として表示し、「顧客と合意した値を入れる」と書く |
| 機密ファイル露出の確認を許可 | チェック（`sensitivePaths`） | 機密ファイル露出 | 許可がなく `auto-security-exposure` が設定が必要のとき（主に本番） |

- 各項目の下に、その操作でサイトに何が起きるか（例：「QA」で始まるテスト投稿を作り確認後に削除する、通知先にもメールが届く、顧客の監視に検知される場合がある）と、動くようになる検査の件数を書く。
- 本番環境では、テスト投稿・フォーム送信の項目を出さない（既存の登録規則で本番は不可）。
- すべて済むと「やることはありません」と表示する。

### 保存と実行
- 「保存して、増えた検査だけ実行」と「保存だけする」の2つのボタン（設計者の判断）。
- 入力した項目だけを保存する。空欄・未チェックの項目は「次にやること」に残る。
- 保存は既存の設定保存（`POST /api/projects/:id/settings`、`profile` と `sensitivePaths` を含む）と同じ検証・権限・バージョン競合の扱いで行う。既存の登録規則（`validateProfile`、本番での許可の扱い、`allowSensitivePaths` の決め方）を変えない。
- 「増えた検査だけ実行」は、保存後に新たに実行可能になった検査（保存前は設定が必要で、保存後はそうでない行）だけを実行する。

## 5. 「このサイトに関係しない」の自動判定

- 注文（`coverage-order`・`order-record`・`order-cleanup`・`order-notification`）：有効プラグインに通販プラグイン（例：Welcart の `usc-e-shop`、WooCommerce の `woocommerce`）がない。
- 会員（`coverage-membership`）：有効プラグインに会員プラグインがない。対象のスラッグ一覧は実装者が既存コードと一般的なプラグインから決め、一覧として1か所にまとめる。
- 多言語（`coverage-multilingual` がある場合）：多言語プラグインがなく、hreflang も検出されていない。
- 本番環境でのテスト投稿・フォーム送信関連（投稿・キャッシュ・予約公開・フォーム送信）。
- 有効プラグインを取得できなかった場合（管理画面の認証なし等）は自動判定しない（「技術担当の準備」または元の扱い）。
- 表示には根拠を書く（例：「有効なプラグインに通販機能が見つからないため」）。
- 「関係ありに戻す」を押すと、その項目は元の振り分け（技術担当の準備など）に戻る。この選択はサイトごとに保存する。

### 5.1 判定の前提（設計者の判断）
- 有効プラグインの取得が成功したかどうかを区別するため、登録時・再取得時に `profile.automation.pluginInventory = {observed:true|false, slugs:[...]}` を保存する。`observed:true` は管理画面のプラグイン一覧を取得できた場合だけ。既存サイトでこの値がない場合、また `observed:false` の場合は自動判定しない。
- 多言語の自動判定は今回の範囲から外す（hreflang の検出結果が保存されていないため）。多言語は元の振り分けのまま。
- 「関係ありに戻す」の選択は `profile.automation.relevantOverrides`（検査IDの配列）に保存し、既存の設定保存と同じ経路・バージョン競合の扱いで保存する。本番環境でのテスト投稿・フォーム送信は戻せない（ボタンを出さない）。戻した項目は、5章の自動判定がなかったときの振り分けに戻る。

## 5.2 データの経路（設計者の判断）
- 振り分けはサーバー側で行い、新しい読み取りAPI（例：`GET /api/projects/:id/todo`）で結果画面に渡す。結果画面は描画だけを行う。
- 「次にやること」と「まだ確認していないもの」は、選んでいる実行に関係なく**サイトの現在の設定**で計算する。「分かったこと」と件数カードの不合格・注意・合格は、選んでいる実行の結果を使う。
- 問い合わせフォームが検出されていないときのフォーム送信は「技術担当の準備」に入れる。

## 5.3 件数と「増えた検査」（設計者の判断）
- 「次にやること」の各項目が動かす検査は、固定の対応表で決める：テスト投稿の許可 → 投稿・キャッシュ・予約公開（`coverage-publishing`・`coverage-cache`・`coverage-scheduled` と、それに紐づく生成済みの検査）／フォーム送信の許可＋宛先 → `coverage-contact-success` のみ（通知メール等の外部連携は含めない）／表示上限 → `coverage-performance`／機密ファイル確認 → `auto-security-exposure`。
- 「あと n つ設定すると、さらに m 件」の m は、この対応表の検査のうち現在「設定が必要」の件数。
- 「増えた検査だけ実行」は、保存の前後で「設定が必要」から外れた行のうち、対応表に含まれる行だけを実行する。保存後に category が `implementation`・`mixed` になった行は実行しない。
- 件数カードの「やること」は「次にやること」の項目数。結果データ（`results.json`）の `preparationRequired` や集計は変えない。

## 5.4 自動判定した検査を「理由付き対象外」にする（利用者の決定）
- 5章の自動判定に当たった検査は、結果データ上も `status:'not_applicable'` とし、`reason` に判定の根拠（例：「有効なプラグインに通販機能が見つからないため対象外（登録時の取得：2026-11-02）」「本番環境ではテスト投稿・フォーム送信を実行しないため対象外」）を入れる。既存の `releaseGate`（必須でも理由付きの対象外は満たす）により、必須条件の判定から外れる。
- 自動判定の対象外は、手で付けた対象外と区別できる印（例：`autoNotApplicable:true`）を行に付け、画面とレポートで「自動判定」と表示する。
- 「関係ありに戻す」を選ぶと、次回以降の実行から自動対象外をやめ、元の扱い（設定が必要など）に戻る。
- 自動判定は `pluginInventory.observed:true` のときだけ行う（5.1）。取得できていないときは対象外にしない。
- 既存の手動の対象外（`manual` の `not_applicable`）の仕組みは変えない。

## 6. 文言

- 「設定が必要」の理由文のうち、画面に出る部分から開発者向けの言葉を除き、平易な日本語にする（例：「browser-flow の送信→waitForMail」→「送信したメールが届いたかを確かめる仕組み（技術担当が準備）」）。
- 内部の `reason`（results.json・CLI 用）は変えなくてよい。画面表示用の文言を別に持つ（設計者の判断）。

## 7. 画面の構成（B案）

1. 件数カード：不合格・注意・合格・やること。実行不能・未確認の件数はカードの下に小さく表示。
2. 次にやること（4章）。件数の見出し「あと n つ設定すると、さらに m 件を検査できます」。
3. 分かったこと：不合格 → 注意。既存の「不合格の理由・対応方法」のまとめ表示を使う。合格は折りたたみ（設計者の判断）。
4. まだ確認していないもの（あなたの作業ではありません）：折りたたみ。3区分の見出し付き。
- 既存の分類別の一覧（グループ表示・詳細パネル・絞り込み）は、この下に残す。
- 過去の実行を選んだときも同じ構成で表示する。進行中の実行ではやることの入力を無効にする。

## 8. テスト

- 振り分け：テスト用サイト（通販・会員プラグインなし、検証環境）で、次にやることが4章の項目だけになり、注文・会員が「関係しない」に入ること。本番環境ではテスト投稿・フォーム送信が出ないこと。有効プラグインが取得できないと自動判定しないこと。
- 保存：その場の保存で既存の規則が守られること（本番で許可が勝手に有効にならない、バージョン競合で保存されない）。
- 実行：保存後に「増えた検査だけ」が選ばれて実行されること。
- 表示：重要の点滅が次にやることにしか付かないこと。画面の文言に開発者向けの言葉が出ないこと（既定の禁止語リストで確認）。
- ブラウザーテスト：結果画面でチェックと入力をして保存し、増えた検査が実行されるまで。

## 9. 実装者に任せる事項

- 画面の細部（既存の見た目に合わせる）。
- 振り分け関数の置き場所と名前。
- 通販・会員・多言語プラグインのスラッグ一覧の具体的な中身。
- 「増えた検査だけ実行」の実行方法（既存の `--id` を使うか、複数指定を足すか）。
