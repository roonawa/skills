# 修正への引き継ぎ（C-HUB貼り付け文面・再診断比較） 設計書

- 作成日：2026-11-02
- 対象：SITE EXAM（wordpress-qa harness）
- 状態：実装済み

## 1. 目的と背景

SITE EXAMは「課題を分かりやすく説明して、その後の修正対応へつなげる」社内ツールである。現状は不具合報告書・顧客向け診断HTML等で課題を説明できるが、修正担当へ渡す作業と、修正後に直ったかを確かめる作業はツールの外で手作業になっている。ハーネス評価（2026-11-02）では「修正への引き継ぎ」が10点中3点で最も低い。

利用者との合意事項：
- 修正するのは**自社の開発担当**。顧客や顧客側の制作会社へ渡す用途ではない。
- 開発担当への依頼は社内のタスク管理 **C-HUB** で行う。
- C-HUBのタスクは**サイト1件の診断につき1タスク**。課題はその中に一覧で入れる。
- SITE EXAMからC-HUBへ直接登録はしない。**SITE EXAMが件名と本文を作り、担当者がC-HUBへ貼り付ける**。

## 2. ゴール・非ゴール・アンチゴール

### ゴール
- 診断結果から、C-HUBにそのまま貼り付けられるタスクの件名と本文を作る（担当区分ごとに課題を分け、直し方・確認方法つき）。
- 引き継いだ内容を記録し、修正後の再診断の結果と比べて、課題ごとに「解消／未解消／再確認できず／新たに発生」を示す。
- 比較結果も、同じC-HUBタスクへ貼り付けられる文面にする。

### 非ゴール
- C-HUBのAPIを使った登録・更新・完了操作（利用者の判断：貼り付けで十分）。
- 課題ごとに別タスクを作ること。
- 顧客向けの文書（既存の顧客向け診断HTMLが担う）。
- 修正の自動適用。

### アンチゴール（動いても失敗とみなすもの）
- 再診断で確認できていない課題（実行不能・設定が必要・未実施・検査範囲外）を「解消」と表示すること。
- 文面に、認証情報・Cookie・証拠ファイルの本文・ユーザー名など、既存のレポートが載せていない情報を含めること。
- 文面の内容が、同じ実行の結果画面・不具合報告書と食い違うこと（別の判定ロジックで課題を作らない）。
- 合格の項目や対象外の項目まで課題として並べ、本文が読めない長さになること。

## 3. 用語

- **課題**：結果の行（`row`）のうち、表示上「不合格」または「注意」（`displayStatus` が `fail` または `caution`）のものから、`lib/failure-explanations.mjs` が作る説明項目（`row.failures[]`）1件。既存の結果画面の「不合格の理由・対応方法」と同じ単位。
- **区分**：`displayStatus(row)` が `fail` なら「不合格」、`caution` なら「注意」と表示する。基礎診断の「兆候あり」は、内部では必須の検査の `fail` なので「不合格」に含まれる。新しい区分の判定は作らない（**設計者の判断**）。
- **課題キー**：`row.id` と、正規化した `failure.key` の組。前回と今回の課題を同一とみなす単位。
  - 正規化（**設計者の判断**）：`failure.key` に含まれる3桁以上の数字の並び、16進のID・UUID、日時、URLのクエリ文字列を固定の記号に置き換える。エラー文に入るポート番号・時刻・IDの違いで、同じ不具合が「解消」と「新たに発生」に分かれないようにするため。
  - 行の単位でしか判断できないキー（`unclassified:`・`timeout:` で始まるもの）は、その行が今回 `pass` のときだけ「解消」とする。行がまだ `fail` なら、キーの文字列が変わっていても「未解消」とする。
- **状態の対応**（比較と未確認件数の数え方）：
  - 確認できた：`status` が `pass` または `fail`、かつ `preparationRequired` でない。
  - 確認できていない：`preparationRequired`（設定が必要）、`blocked`（実行不能）、`not_run`（未実施）、`not_applicable`（対象外）、`review`（直接確認）、行がない、のいずれか。
- **引き継ぎ記録**：文面を作ったときに保存する、引き継いだ課題の一覧（4章）。

## 4. 引き継ぎ記録

- 担当者が「C-HUB用の文面を作成」を実行したときに、サーバー側でサイトごとに保存する。
- 保存場所はサイトのデータフォルダ配下（例：`<project>/handoffs/<handoffId>.json`）。Linux版の `/data` に含まれるため、既存のバックアップ対象になる。直近20件を残す（**設計者の判断**）。
- 中身：
  - `handoffId`、作成日時、作成者（共有版で `ui/server.mjs` が扱う利用者名〈`actor`〉があれば。なければ空）
  - 元の実行ID、元の実行日時、そのときのサイト名
  - 引き継いだ課題の配列（課題キー、行ID、行のタイトル、区分〈不合格／注意〉、担当区分、対象URL、説明文一式）
  - 担当者が外した課題キーの配列（「除外した課題」）
- 「最新」は作成日時で決める。
- 保存の回数（**設計者の判断**）：文面のプレビューを開くたびに、そのプレビュー用の `handoffId` を1つ決める。同じプレビュー中に「件名をコピー」「本文をコピー」を何度押しても、同じ記録を上書きするだけにする。課題の選択を変えた場合も同じ記録を上書きする。
- サイトを削除すると記録も一緒に消える（既存のサイト削除と同じ扱い）。サイト名を変えても記録は残り、比較できる。
- 説明文は作成時点の内容を複製して保存する。後で説明文の定型が変わっても、記録の内容は変わらない。
- 最新の引き継ぎ記録を、次の再診断比較の基準にする。

## 5. C-HUB用の文面

### 5.1 対象の選び方
- 選んだ実行の課題を一覧にし、既定ですべて選択済みにする。担当者は、引き継がない課題のチェックを外せる。
- 確認できていない行（3章の対応表）は課題ではない。文面には件数だけ「SITE EXAMで未確認の項目：n件」と1行で書く。ただし `not_run`（その実行で選ばなかった検査）は数えない（**設計者の判断**）。
- 対象URLの取り方（**設計者の判断**）：不具合報告書（`lib/issue-report.mjs`）が証拠からURLを取り出している処理を共通の関数として切り出し、不具合報告書と引き継ぎ文面の両方で使う。別の取り出し方を作らないことで、両者のURLを一致させる。取り出せない場合は、行のタイトルだけを載せる。
- 進行中の実行では作成できない。完了した実行だけを対象にする。

### 5.2 件名
`{サイト名}：SITE EXAM 診断結果の修正（{実行日 YYYY-MM-DD}）`
- サイト名は登録済みのサイト名。既存のC-HUB集計スキルが件名先頭の「◯◯：」を案件名として読むため、この形にそろえる。
- サイト名に含まれる改行は空白に置き換え、全角・半角のコロンは全角の「・」に置き換える。案件名の区切りを誤って読まれないようにするため（**設計者の判断**）。
- 実行日は日本時間で表示する。

### 5.3 本文
- C-HUBの本文欄がMarkdownを表示するか分からないため、Markdown記法に頼らないプレーンテキストにする（【見出し】と「・」の箇条書き）（**設計者の判断**）。
- 構成：
  1. 概要：サイトURL（`config.baseURL`）、環境（`config.environment`）、実行日時、実行ID、課題の件数（不合格／注意）、未確認の件数。共有版で公開URL（環境変数 `WPQA_PUBLIC_ORIGIN`）が設定されていれば、結果画面へのリンク。
  2. 担当区分ごとの課題一覧。区分の順序は「管理画面・プラグイン」「サーバー・ホスティング」「テーマ・開発」「担当区分の確認が必要」。
  3. 各課題：`［兆候あり|不合格|注意］タイトル`、対象URL（最大5件、超える分は「ほかn件」）、状況（`actual`）、直し方（`admin`／`code`）、確認方法（`verify`）。
  4. 末尾：「修正後はSITE EXAMで同じ範囲を再診断し、比較結果をこのタスクに追記してください。」
- 並び順：担当区分の中で「不合格」→「注意」。
- 担当区分：
  - 基礎診断の課題は `RULES[rule].owner`（admin／server／theme）を使う。
  - それ以外の課題は担当区分の情報を持たないため「担当区分の確認が必要」に入れ、`admin` と `code` の両方を載せる（**設計者の判断**）。
- 文字数：本文全体の上限を設ける（初期値20,000文字）。C-HUBの本文の上限は不明のため、実装後に実機で確認して調整する。超える場合は次の順で縮める（**設計者の判断**）。
  1. 「注意」の課題の直し方・確認方法を、それぞれ最初の1文だけにする。
  2. 「不合格」の課題も同様に最初の1文だけにする（`admin` と `code` の両方を載せる課題も、それぞれ1文ずつ）。
  3. それでも超える場合は、一覧の後ろの「注意」から順に、タイトルだけの1行に切り替える。
  4. 縮めた場合は、本文の末尾に「全文はSITE EXAMの不具合報告書を参照」と書く。
- プレビューに表示する文面と、コピーされる文面は完全に同じにする。
- 機密情報の伏せ字処理（7章）で文字が置き換わる場合も、置き換え後の文面をプレビューに表示する。

### 5.4 画面
- 結果画面の「不具合報告書を作成」の近くに「開発担当への引き継ぎ（C-HUB）」の欄を置く。
- 欄の中身：課題のチェック一覧、件名と本文のプレビュー（編集不可）、「件名をコピー」「本文をコピー」ボタン。
- コピーはクリップボードAPIを使い、使えない場合はテキストを全選択した状態にして手動コピーを案内する。
- 「コピー」を押した時点で引き継ぎ記録を保存する（プレビューだけでは保存しない）（**設計者の判断**：文面を実際に使った時点を基準にするため）。

## 6. 再診断比較

### 6.1 比較の起点
- サイトに引き継ぎ記録があり、記録の元の実行より新しい完了済みの実行を選んでいるとき、結果画面に「前回の引き継ぎと比較」を表示する。
- 比較の基準は最新の引き継ぎ記録。比較対象は選んでいる実行。

### 6.2 分類（課題キーごと）
| 分類 | 条件 |
|---|---|
| 解消 | 引き継いだ課題の行が今回実行され、`status` が `pass` |
| 未解消 | 引き継いだ課題キーが今回の課題にもある（行単位のキーは3章のとおり、行が `fail` なら未解消） |
| 再確認できず | 引き継いだ課題の行が今回、実行不能・設定が必要・未実施・対象外・直接確認・行そのものがない、集約で別の実行から写した行、のいずれか。または行は `fail` だが、その課題キーが今回の課題にない（文面に「同じ検査に別の課題が残っているため確認できません」と添える） |
| 新たに発生 | 今回の課題のうち、引き継ぎ記録にない課題キー |

- 「解消」は、その行が今回実際に実行されて `pass` になった場合だけ。アンチゴールのとおり、確認できていないものを解消と呼ばない。
- 2026-11-02 利用者の判断で変更：当初は「行は `fail` だが課題キーが今回ない」ものも解消としていた。検査が途中で止まる（時間切れ・非200のページ・上限による未確認）と、調べていない課題のキーも消えるため、行が `pass` のときだけ解消とし、それ以外は「再確認できず」とした。
- 集約結果（`aggregation.notAFreshRun` または `sources` を持つ実行）は再診断として比較できない。
- 引き継ぎ時に担当者がチェックを外した課題が今回も残っていれば、「新たに発生」ではなく「前回引き継ぎ対象外」として別に数える（**設計者の判断**）。
- 同じ課題キーで対象URLの一部だけが直った場合は「未解消」とし、今回残っているURLだけを載せる。あわせて「前回からn件のURLが解消」と書き添える（**設計者の判断**）。
- 検査範囲の違い（**設計者の判断**）：前回と今回で検査範囲が違っても比較はできる。ただし「再確認できず」のうち「今回その検査を選ばなかった（`not_run`・行がない）」ものが1件以上あれば、比較結果の先頭に「前回と同じ検査範囲で再診断していないため、n件は確認できていません」と警告を出す。

### 6.3 比較結果の文面
- 見出し：`【SITE EXAM 再診断結果（{実行日}）】`。
- 件数の要約、分類ごとの一覧。
  - 「解消」「未解消」「再確認できず」はタイトルと対象URLだけ。
  - 「新たに発生」は5.3と同じ詳細。
- 末尾に「タスクを完了にするかは担当者が判断してください。再確認できずの項目は、条件を整えて再診断が必要です。」。
- 画面には「比較結果をコピー」ボタンを置く。

### 6.4 引き継ぎ記録の更新
- 比較画面では、「新たに発生」の課題をチェック付きで一覧にする（既定ですべて選択済み）。チェックの状態は比較結果の文面に反映する（外した課題は文面に載せない）。
- 「比較結果をコピー」を押すと、新しい引き継ぎ記録を保存する（4章と同じく、同じ比較画面で何度押しても1件を上書きする）。
- 新しい記録の中身（**設計者の判断**）：
  - 引き継いだ課題：「未解消」「再確認できず」と、「新たに発生」のうちチェックした課題。
  - 除外した課題：前回の除外した課題のうち今回も残っているもの、「前回引き継ぎ対象外」、「新たに発生」のうちチェックを外した課題。
- 「解消」した課題は新しい記録に含めない。次の比較の基準はこの新しい記録になる。

## 7. 安全と権限

- 文面と比較は、既存の結果画面と同じ閲覧権限で作れる。外部への送信はしない。
- 文面に入れる情報は、既存の `failures[]` と行のメタ情報（タイトル・URL）だけ。証拠ファイルの本文や認証情報は入れない。
- 既存の `redactor`（`lib/evidence.mjs`）を、文面を作る最後の段階でもう一度通す（**設計者の判断**）。
- 引き継ぎ記録の保存APIは、既存の書き込み系API（CSRFトークン・送信元の検証）と同じ保護を使う。

## 8. テスト

- 文面：担当区分の振り分け、並び順、件数、URLの省略表示、上限超過時の短縮、プレーンテキストであること、秘密情報が入らないこと（認証ヘッダー・Cookieの値を含む結果からの生成で確認）。
- 比較：4分類と「前回引き継ぎ対象外」の境界。特に、行が実行不能・設定が必要・未実施・行なしのときに「解消」にならないこと。行が `fail` で課題キーが一部だけ消えた場合。
- 引き継ぎ記録：コピー時だけ保存されること、直近20件の保持、別サイトの記録を参照しないこと。
- 画面：課題の選択とプレビューの連動、コピーボタン、比較ボタンの表示条件。

## 9. 実装者に任せる事項

- 引き継ぎ記録のファイル形式の細部、APIのパス名。
- 文面の細かな文言（5.3・6.3の方針に従う）。
- 画面の配置の細部（既存のパネルの見た目に合わせる）。
