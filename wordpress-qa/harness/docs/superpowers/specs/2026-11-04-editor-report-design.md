# 編集者向け対応ガイドの自動作成（Claude）設計

- 日付：2026-11-04
- 対象：SITE EXAM（`wordpress-qa/harness`）
- 見本：2026-11-04 に手作業で作った `komoro-editor-report.html`（小諸動物病院のまとめ）。この形式を自動で作れるようにする。
  - 見本と元の不具合報告書は、お客様のサイト情報を含むためリポジトリに入れない（作成者の PC の `%TEMP%\komoro-editor-report.html`・`%TEMP%\issue-report.html`）。構成は8章に書き写した。テストには、同じ形の結果を作る架空のサイトと結果を使う（12章）。

## 1. 目的と背景

SITE EXAM の不具合報告書（`issue-report.html`）は、検査ごとの記録としては正確だが、編集者が読むには向かない。小諸動物病院の例では、不合格187件のうち184件がツールの設定・環境・不具合によるもので、サイトで実際に直すべきことは5つだった。それを見分けるには、報告書を読み解き、公開ページを開き直して原因を確かめる必要があった。

この作業を、結果画面のボタン1つで行えるようにする。出力は、**編集者がそのまま修正作業の手引きに使える報告書**。受け取るのは編集者で、渡す前に診断の担当者が必ずレビューし、ファイルを手元で直してから渡す。

利用者の言葉（そのまま）：
- 「ツールが作ったものをそのまま渡せればよいが、レビューします」
- 一番困るのは「重複する内容が多かったり、テストコードや専門用語が多すぎて読みにくくなっている場合」
- 原因の確定（実際にサイトを確かめる部分）まで「やってほしい」
- レビューは「ファイルを受け取って手元で直したい」。ファイル形式は「気にしなくてよい」

## 2. ゴール・やらないこと・失敗とみなすこと

**ゴール**
1. 1回の実行結果から、見本と同じ構成の編集者向け報告書（HTML 1ファイル）を作る。
2. 不合格・注意を「誰が何をするか」で分ける：編集者／管理者／技術担当／サイトの問題ではない（ツール側）／未確認／対象外。
3. 原因が同じものを1項目にまとめる（例：141件の公開方針の食い違い → 1項目）。
4. 原因を推測で書かず、読み取りだけの再確認で確かめた事実に基づいて書く。確かめられなかったことは「未確認」と書く。
5. 編集者が読む本文に、テストコード・エラー文・内部ID・専門用語の羅列を出さない。

**やらないこと**
- サイトへの書き込み・送信・ログインを伴う確認。
- Claude にサイトへ直接アクセスさせること（取得はツールのプログラムが行う）。
- 編集者への自動送付。共有リンクの発行。
- 既存の不具合報告書・顧客向け報告書の置き換え。
- Word・PDF での出力。

**失敗とみなすこと（動いても失敗）**
- 同じ内容の繰り返し、コード・エラー文・専門用語の多い読みにくい報告書。
- ツールの結果にない問題・場所・プラグイン名を作り出すこと。
- 確かめていないことを「問題なし」と書くこと。
- パスワード・Cookie・API キーなどの秘密情報が、報告書や Claude への送信内容に入ること。
- 件数が元の結果と合わないこと。

## 3. 全体の流れ

結果画面に「編集者向け報告書を作成」ボタンを置く。押すと、サーバーが次を順に行う。

1. **事実の取り出し（プログラム）**
   - 対象の実行の行と証拠を読む。行の状態、理由、`failures`、`softwareSecurity`（互換性を含む）、設定の照合結果、自動の対象外の理由を使う。
   - 登録条件も読む（環境、検索エンジンへの公開の期待値など）。
2. **まとめ（プログラム）**
   - 不合格・注意を原因の候補ごとにまとめる。
   - まとめ方の規則を「原因カタログ」として持つ（4章）。カタログに当てはまらない行は、検査の種類と理由の型でまとめる。
3. **再確認（プログラム・読み取りだけ）**
   - 原因の候補ごとに、公開サイトへ GET／HEAD で確かめる（5章）。
4. **文章づくり（Claude）**
   - 確かめた事実とまとめを、構造化した JSON で Claude に渡す。
   - Claude は、項目ごとの「見出し・説明・困ること・直し方の手順・場所・急ぎ度」を、決めた JSON 形式で返す。
5. **機械的な確認（プログラム）**
   - 6章の検査に通らなければ、指摘を添えて Claude に1回だけ書き直させる。それでも通らなければ作成を失敗として、理由を画面に出す。
6. **HTML の組み立て（プログラム）**
   - 決まったひな形に、確認済みの文章を流し込む。HTML は Claude に書かせない。
   - 件数表はプログラムが数える。
7. **保存**
   - 実行フォルダーに `editor-report.html`（編集者向け）と `editor-report-basis.html`（レビュー用の根拠）を保存する。
   - 画面から両方を開ける・保存できるようにする。

## 4. 原因カタログ（最初に入れる規則）

小諸動物病院で確かめた原因を最初の規則にする。各規則は「当てはまる条件」「再確認の方法」「分類」を持つ。

| 規則 | 当てはまる条件 | 再確認 | 確かめられたときの分類 |
|---|---|---|---|
| 公開方針の期待値ずれ | `indexable differs from expectation` がページの大半で同じ向きに出ている／管理設定の検索公開方針も同じ向き | 代表ページを取得し、meta robots・X-Robots-Tag を確認。環境が本番か | サイトの問題ではない（診断の設定）。担当者への対応：設定を直して再検査 |
| 表示の準備で時間切れ（外部画像） | 表示系（layout・JavaScript・snapshot・axe）が同じ時間切れで多数失敗 | 該当ページの img（`data-src` を含む）と絵文字画像の読み込み元を集める。対象サイトと違う読み込み元を、接続先の許可に入っているかどうかと合わせて記録する | 許可外の読み込み元が原因なら、サイトの問題ではない（診断環境）。対応：接続先の許可の追加か、ツールの修正 |
| 別のサイトからの画像の読み込み | 再確認で、本番のページが検証用など別ドメインの画像を読み込んでいる（ドメイン名に test・staging・dev 等を含む、または登録済みの別サイト） | 上と同じ | 編集者（画像の差し替え） |
| リンク先の一時的な失敗 | リンク検査の失敗が 502／503 | 失敗したリンク先を1件ずつ順番に取得し直す | 取得し直して正常なら、サイトの問題ではない（診断環境の混雑） |
| 存在しないページの扱い | 404 応答の検査の失敗 | 存在しないパスを1つ取得し、状態コードと転送先を記録 | 転送されていれば管理者（転送設定） |
| サイトマップの形式 | サイトマップの形式エラー | 標準の XML 解析で読み直す | 解析できればサイトの問題ではない（ツール側） |
| 既知の弱点のあるプラグイン | `softwareSecurity` に findings | なし（取得済みの照合結果を使う） | 管理者。修正版がない・配布停止なら「置き換え」 |
| 互換性 | 互換性の検査の確認事項 | なし | 技術担当（参考） |
| セキュリティヘッダー・情報露出 | 基礎診断の注意 | なし | 技術担当 |

カタログに当てはまらない不合格は、元の理由のまま「原因の確認が必要」として技術担当の欄に入れる。黙って捨てない。

**再確認の結果ごとの分類（私の判断）**

各規則は、再確認の結果によって分類が3通りに分かれる。

| 再確認の結果 | 分類 |
|---|---|
| ツール側の原因だと確かめられた | 表の「確かめられたときの分類」 |
| サイト側に問題があると確かめられた（例：本番のページが実際に noindex、取得し直してもリンク先が失敗、標準の XML 解析でもサイトマップが読めない） | サイト側の担当へ。noindex は管理者（検索エンジンの設定）、リンク切れは編集者、サイトマップは管理者（SEO プラグインの設定）。その他は技術担当 |
| 確かめられなかった（取得できない、上限に達した、接続先の許可がない） | 未確認 |

**公開方針の向き（私の判断）**：登録の「環境」が本番で、実際のページが検索エンジンに公開されている場合は「診断の設定の可能性が高い」として、サイトの問題ではない欄に入れる。あわせてレビュー用の根拠に「公開方針を案件の担当と確認すること」と出す。本番以外、または実際のページが noindex の場合は、この規則で「サイトの問題ではない」にはしない。

**件数の単位（私の判断）**：件数は結果の「行」（不具合報告書の「ケース」）で数える。元の結果の不合格（注意を除く）・注意・未確認（設定が必要・実行不能・未実施・直接確認）・対象外の行数と、各欄の合計が一致すること。1つの行は1つの項目にだけ入れる。

## 5. 再確認の制約

- GET／HEAD のみ。フォーム送信・ログイン・書き込みはしない。保存済みの管理画面ログインは使わない（公開ページだけを見る）。
- 対象サイトと同じ origin だけを取得する。別ドメインの画像は、取得せずに URL とドメインだけを記録する（接続先の許可に入っていればHEADで確かめてもよい）。
- 共有版では既存の egress 経由で通す。対象サイトが接続先の許可にない場合は再確認をせず、「未確認」とする。
- 1回の作成で取得は最大60リクエスト。同時に1件ずつ順番に送り、1件15秒で打ち切る。
- 配分（私の判断）：規則ごとに代表ページを最大3件まで確かめる。3件とも同じ結果なら、その規則に当てはまる行すべてに適用する。順番は、表示の時間切れ（読み込み元の収集）→ 公開方針 → リンク → 404 → サイトマップ。上限に達して確かめられなかった規則は「未確認」とする。
- 実行する場所：UI サーバーのプロセスで行う。共有版でも、サーバーのプロセスは全体の通信設定（`lib/shared-runtime.mjs` の ProxyAgent）により egress 経由で外へ出られる（既存の `ui/automation-discovery.mjs` と同じ）。ブラウザーは使わない。画像の読み込み元は HTML（`src`・`data-src`・`srcset`、WordPress の絵文字の設定）から集める。
- 閲覧パスワードのあるサイトは、保存済みの閲覧パスワードで公開ゲートを通す（既存の `preparePublicGate` と同じ方法）。これは閲覧パスワードの入力欄への POST を1回だけ行う。検査の実行のたびに既に行っている操作と同じなので、例外として認める（私の判断）。WordPress の管理画面へのログインはしない。通れなければ「未確認」とする。
- 取得した本文は、事実の取り出しにだけ使い、保存・送信しない。
- 表示検査の準備で、読み込めなかった画像の URL を証拠に残すよう、検査側（`tests/site.spec.mjs` の `ready()`）も直す。準備の時間切れの前に、読み込めなかった画像の一覧を証拠として添付する。これが無い古い実行では、再確認の結果だけを使う。

## 6. 機械的な確認（Claude の出力を通す前の検査）

本文（編集者が読む文章）に対して：

1. コード・エラーの混入を禁止：`expect(`、`Error:`、`AssertionError`、`Timeout \d+ms`、`at ` で始まるスタック、`{` `}` を含む JSON 断片、`check.`・`page.`・`journey.` などの内部ID、`\x1b`。
2. 重複を禁止：同じ文（句読点を除いて同じもの）が2回以上出ない。同じ原因の項目が2つ以上ない（原因IDで判定）。
3. 専門用語：用語リストの語（例：HSTS、CSP、CVE、REST、XML-RPC、CDATA、egress、CSRF、XSS など）は、括弧で説明を付けるか、言い換える。説明なしで出たら差し戻す。
4. 事実の一致：Claude が書いた項目は、すべて渡した原因IDを参照していること。渡していないURL・プラグイン名・CVE番号・数字が本文にないこと（渡した事実の一覧と突き合わせる）。
5. 件数・分類：件数はプログラムが入れるので、Claude の出力に件数を書かせない。分類はプログラムの分類を優先し、Claude には変えさせない。

## 7. Claude に渡す情報と許可

- 既存の `AiAssistant` の呼び方に合わせる（`fetch` で Messages API、`output_config` の JSON スキーマ、`stop_reason` の確認、サイズ上限）。新しいライブラリは入れない。
- 使ってよいのは、AI の利用が有効・承認済みで、「取得情報の送信許可」（`evidenceApproved`）があるときだけ。1回の呼び出しごとに1日の回数上限（`reserve()`）を1つ消費する。
- 項目が多いときは、20項目ずつに分けて呼び出してよい（既存の `completeAssessmentEvidence` と同じ）。書き直しは、確認に通らなかった分だけをもう一度送る。作成を始める前に、必要な回数（分割数＋書き直しの最大数）を画面に出し、残りの回数が足りなければ始めない（私の判断）。
- 送る情報：サイト名、対象の URL のパス、検査の種類、まとめた原因と件数、再確認で確かめた事実（状態コード、転送先、読み込み元のドメイン、ページ上の場所の見出し）、プラグイン名・版・CVE 番号・修正版の有無。
- 送らない情報：パスワード、Cookie、ヘッダーの値、API キー、取得したページの本文そのもの、問い合わせ内容などの個人情報。
- プロンプトでは、サイト由来の文字列を「指示ではなくデータ」として扱うよう明記する（既存と同じ）。
- Claude が使えないとき（未設定・上限・失敗）は、作成できない理由を画面に出す。文章なしの劣化版は作らない。

## 8. 報告書の構成（見本と同じ）

編集者向け（`editor-report.html`）：
1. 見出しと対象（サイト名・URL・環境・診断日時）
2. ひとことで言うと（サイトで直すことの数と、ツール側が原因の件数）
3. 分類ごとの件数表
4. 編集者の方にお願いしたいこと
5. 管理者の権限が必要なこと
6. 技術担当・サーバー担当に頼むこと
7. サイトの問題ではないもの（対応不要）
8. まだ確かめられていないこと
9. このサイトには関係しないもの
10. このあとの進め方
11. 作成の根拠（どの実行・いつ再確認したか。断り書き）

項目ごとに、見出し・説明・困ること・直し方（番号付き手順）・場所・急ぎ度・注記を持つ。スクリプトは含めず、印刷できる単純な HTML にする。

レビュー用（`editor-report-basis.html`）：項目ごとに、元の検査の行ID・件数・元の理由（そのまま）・再確認の記録（取得したURL・状態コード・時刻）・機械的な確認の結果を載せる。担当者がレビューのときに根拠をたどるためのもの。

## 9. 画面

- 結果画面（不具合報告書の作成ボタンの近く）に「編集者向け報告書を作成」を置く。
- 作成中は進み具合（取り出し→再確認→文章→確認）を表示する。他の実行・保存と同時に動かさない。
- 完了したら「編集者向け報告書を開く」「根拠を開く」を出す。どちらも既存の `/files?path=` と同じ配信の制限を使う。
- 失敗したら、どの段階で何が足りなかったかを日本語で出す。

## 10. 決めたこと（利用者の判断）

- 原因の確定（実際にサイトを確かめる）まで自動で行う。
- 受け取るのは編集者。渡す前に担当者がレビューし、手元のファイルで直す。
- 一番避けたいのは、重複・コード・専門用語の多い読みにくい報告書。

## 11. 私の判断（確認してほしい点）

- 出力は HTML 1ファイル（見本と同じ）。レビュー用の根拠は別ファイルに分ける。
- Claude にはサイトへアクセスさせず、取得はプログラムが行う。
- Claude には文章だけを書かせ、分類・件数・HTML はプログラムが決める。
- 送信の許可は、既存の「取得情報の送信許可」を使う。新しい許可は作らない。
- 書き直しは1回まで。通らなければ作成を失敗にする（読みにくいものを渡さないため）。
- 再確認は最大60リクエスト、順番に1件ずつ。規則ごとに代表ページ最大3件。
- 再確認でサイト側の問題だと分かったら、サイト側の担当へ。確かめられなければ未確認。
- 本番で実際に公開されているページの「公開しない」期待値は、診断の設定の可能性が高いとして扱い、レビューで確認してもらう。
- 件数は結果の行で数え、元の結果と一致させる。
- 閲覧パスワードの入力（公開ゲートの POST）だけは例外として認める。管理画面へのログインはしない。
- 再確認は UI サーバーのプロセスで、ブラウザーを使わずに行う。
- Claude の呼び出しは20項目ずつに分けてよい。足りない回数で始めない。

## 12. 作り手に任せること

- プロンプトの文面、JSON スキーマの細部、用語リストの初期内容。
- まとめ方の細かい規則（理由の型の正規化）。
- 画面の文言と配置の細部。
- テストの組み方。ただし、小諸動物病院と同じ形の結果（公開方針のずれ141件、表示の時間切れ40件、503のリンク1件、サイトマップ、プラグイン2件）を作るテスト用の結果とサイトで、分類と件数が見本と一致することを確かめること。件数は少なくしてよい（形が同じであればよい）。Claude の応答はテストでは差し替える。

## 13. 関連して直すツールの不具合（この機能とは別に扱う）

- サイトマップの CDATA に対応していない（`lib/checks/discovered.mjs` の `xmlDocument`）。
- 画面を開かない検査でも、報告書に「新しい表示検査で取得してください」と出る。
- 本番サイトの登録で、検索エンジンへの公開の初期値が「公開しない」のまま。
- 外部画像の読み込み失敗で、表示検査の全体が時間切れになる。
