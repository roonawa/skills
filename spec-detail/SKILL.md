## 目的

カスタムソリューション部の受託開発において、基本設計書（spec-basic出力）から詳細設計書（Md）を一気通貫で作成するスキル。

以下の役割を担う：
- **社内技術判断**の文書を作る（顧客レビューは原則不要）
- 半期計画9章「仕様書(Md)」に対応
- **Claude Code実装の直接インプットとなる粒度**で仕様を確定する
- FR-ID → BD-ID → AC-ID → DD-ID → TC-IDのトレーサビリティを確保し、後工程（spec-test）との連携を支える

以下の課題を解決する：
- 基本設計書の内容を機械的に詳細設計に展開できる → 壁打ちフローで1対多のDD-ID展開を支援
- BD-IDとDD-IDの対応関係が曖昧になる → 整形フェーズでBD-ID → DD-IDマッピング表を必ず生成
- 実装粒度に達しないまま実装着手してしまう → チェックポイントで「Claude Code実装の直接インプット」であることを確認
- 既存コード資産との整合性確認漏れ → 草案フェーズで既存コード再利用箇所を必ず確認

## スコープ

### やること
- 上流基本設計書の読み込み（BD-IDの自動展開、案件メタ情報の引継ぎ）
- 5項目の詳細設計書作成のための壁打ち（草案フェーズ）
- 草案を詳細設計書テンプレートに整形（整形フェーズ）
- 整形後のブラッシュアップサイクル（項目単位／DD-ID単位での部分修正・深堀り）
- 既存詳細設計書からの再開モード
- DD-ID自動付与（DD-001, DD-002...）と上流BD-ID連結
- バージョン自動管理（v0.1 → v0.2 → ... → v1.0）
- 「⚠ 要確認」の明示
- レビュー依頼を促すメッセージ出力

### やらないこと
- 実装そのもの（→ Claude Codeで実装フェーズへ）
- テストケース生成（→ `spec-test`）
- 工数見積もり
- パフォーマンスチューニングの具体策（観点として記載するのみ）

## 全体フロー

```
[起動]
  ↓
[起動モード選択]
  ├─ A. 新規作成（基本設計書を上流ファイルとして指定し、ゼロから壁打ち）
  └─ B. 既存詳細設計書から再開（途中の詳細設計書を読み込んでブラッシュアップサイクルから）
  ↓
[上流ファイル読み込み]
  └─ 基本設計書からBD-ID・案件メタ情報・技術スタック等を引き継ぎ、メモリに展開
  ↓
草案フェーズ（壁打ち）
  ├─ 5項目を1問ずつ
  └─ ループ：「他に深堀りしたい項目は？」
  ↓
【チェックポイント1】整形に進む前の確認
  ↓
整形フェーズ → v0.1 出力
  ↓
ブラッシュアップサイクル（反復可能）
  ├─ a. 項目単位で深堀り
  ├─ b. DD-ID単位でピンポイント修正
  ├─ c. 追加（新規DD-ID・テーブル・エラーパターン等）
  └─ d. これでOK → 終了
  ↓
【チェックポイント2】v1.0確定時のみ発動（社内技術レビュー依頼）
  ↓
詳細設計書 v1.0 として確定
```

---

## 起動時の動作

スキルが起動したら、最初に起動モードを確認する。

> 「詳細設計スキル（spec-detail）を起動した。以下のどちらで進める？
> A. 新規作成（基本設計書を読み込んでゼロから壁打ちを始める）
> B. 既存ファイルから再開（途中の詳細設計書を読み込んで続きから）」

- **Aを選んだ場合**：上流ファイル読み込みから開始
- **Bを選んだ場合**：既存ファイル再開モードへ（後述）

---

## 上流ファイル読み込み

### 基本設計書の指定

> 「基本設計書のファイルパスを教えて（例：`基本設計書_<案件名>_v1.0_<YYYY-MM-DD>.md`）」

**省略運用も可**：基本設計書がない場合、要件定義書または既存仕様書を上流ファイルとして指定可。その旨を「設計概要・前提」に記載する。直前のフェーズだけでなく、より上流のファイルも指定可。

### 読み込んで展開する情報

指定された上流ファイルから以下をメモリに展開する：

- 案件タイプ（新規開発／機能追加／リニューアル）
- 案件サマリ（顧客名、案件名、自社担当）
- BD-ID 一覧（機能名、振る舞い概要、上流FR-ID）
- システム構成（技術スタック、稼働環境）
- 画面・データ・I/F設計の概要
- 非機能要件・制約

展開後、確認として以下を伝える：

> 「基本設計書を読み込んだ。BD-ID が [XX件] 確認できた。案件タイプは[タイプ]、顧客は[顧客名]。では詳細設計の壁打ちを始める。」

---

## 草案フェーズの壁打ち（5項目）

質問は**1問ずつ**投げる。複数の質問を一度に投げない。回答内容に応じて追加深堀りを行う。

### 項目1：設計概要・前提

1. 「上流基本設計書を読み込んだ。BD-XXX が[XX件]あるが、詳細設計の方針は？（実装言語、フレームワーク、既存コード資産との関係）」
2. 「上流基本設計の中で、詳細化が必要な要確認事項はある？」
3. 「コーディング規約・命名規則の前提はある？（既存プロジェクトの規約がある場合はその内容も教えて）」

### 項目2：クラス・モジュール設計

1. 「クラス・モジュール構成は？（責務分担、レイヤー構造）」
2. 「ファイル構成は？（ディレクトリ構造、ファイル分割の方針）」
3. 「既存コードを再利用する箇所はある？（再利用箇所と再利用方針を教えて）」
4. 「クラス図はテキスト表現（mermaid等）で含める？」

### 項目3：機能詳細（DD-IDで一覧）

各BD-IDについて以下を順に確認する（BD-IDが複数ある場合は1つずつ処理する）：

1. 「BD-XXX（[機能名]）を詳細設計に展開する。1対1か、複数のDD-XXXに展開するか？」
2. 「処理フローは？（入力 → 処理 → 出力の流れ、分岐条件）」
3. 「使用するクラス・メソッドは？インタフェースは？」
4. 「アルゴリズム・計算式の詳細は？」
5. 「画面に紐づく機能の場合、イベント処理（クリック、入力、初期表示等）は？」
6. 入力項目と制約は？
7. 業務ルールは？
8. 正常終了条件は？
9. 異常終了条件は？
10. 更新対象データは？

→ 整形フェーズでDD-001から自動採番。各DDに上流BD-IDを連結。BD-IDが複数のDD-IDに展開される場合（1対多）も許容。

### 項目4：DB・SQL設計

1. 「DBテーブル定義は？（カラム、データ型、制約、インデックス）」
2. 「主要SQLは？（CRUD、複雑なJOIN、集計クエリ等）」
3. 「トランザクション境界は？」
4. 「マイグレーション・データ移行の必要性は？（Delphi→C#リニューアル等の既存システム改修案件で重要）」

**小規模案件での省略可**：DBを使用しない場合、またはシンプルなCRUDのみの場合は「テーブル定義のみ記載、SQLは省略」で可。「該当なし」も許容。

### 項目5：エラー処理・例外設計・制約

1. 「想定されるエラーパターンは？（業務エラー、システムエラー、外部連携エラー）」
2. 「エラー時のユーザー通知方針は？」
3. 「ログ出力の方針は？（出力レベル、出力箇所、ローテーション）」
4. 「監視・アラートの観点は？」
5. 「実装上の制約・要確認事項は？」→ 「⚠ 要確認」マーク付きで記録

### 5項目完了後の確認

5項目すべての壁打ちが完了したら以下を確認する：

> 「ひと通りの壁打ちが完了。他に深堀りしたい項目はある？なければ整形フェーズに進む。」

- **「あり」の場合**：該当項目に戻って追加質問を行う
- **「なし」の場合**：チェックポイント1へ

---

## チェックポイント1：草案完了時

整形フェーズに進む前に以下を伝える：

> 「詳細設計の草案ができた。整形に進む前に、漏れがないか確認したい項目はある？人にレビューを依頼する場合はここで一旦止めて。」

確認が取れたら整形フェーズに進む。

**DD-IDの採番ルール：**
- DD-001から連番で自動採番する
- 1つのBD-IDが複数のDD-IDに展開される場合（1対多）は連続した番号を付与する
- ブラッシュアップサイクルで追加した場合は続き番号を付与する（既存IDは変えない）
- 採番済みのDD-IDを振り直さない

## ブラッシュアップサイクル

整形フェーズ完了後、または既存ファイル再開モード起動時に開始する。「これでOK」と利用者が伝えるまで何度でも繰り返せる。

### サイクル起動時の問いかけ

> 「現状の詳細設計書（v0.X）を確認した。どこを修正・深堀りしたい？以下から選んで：
> a. 項目単位で深堀り（設計概要／クラス・モジュール／機能詳細／DB・SQL／エラー処理）
> b. DD-ID単位でピンポイント修正（DD-IDを指定）
> c. 追加（新規DD-ID・テーブル定義・エラーパターン等を追加）
> d. これでOK（v1.0として確定）」

### 各モードの動作

| モード | 動作 |
|---|---|
| **a. 項目単位** | 5項目のいずれかを指定させる → 該当項目について追加質問・修正壁打ちを行う → 該当セクションのみ書き換える |
| **b. DD-ID単位** | 修正したいDD-ID（例：DD-003）を指定させる → 該当機能の詳細について壁打ちを行う → 該当行・該当節のみ更新する |
| **c. 追加** | 追加したい要素（新規DD-ID／新規テーブル／新規エラーパターン等）を指定させる → 壁打ちを行う → 該当セクションに追記する（DD-IDは続き番号で自動採番） |
| **d. OK** | ブラッシュアップサイクルを終了する → チェックポイント2へ |

### 部分更新の挙動

- 既存内容を保持しつつ、指定箇所のみ書き換える（全文書き直さない）
- 修正のたびにバージョン番号を自動インクリメントする（v0.1 → v0.2 → v0.3 → ...）
- バージョン管理の基本方針は上書き（最新版のみ保持。Git管理されている前提）
- 利用者が指示した場合のみ、旧版を `<案件フォルダ>/履歴/` に退避する

---

## チェックポイント2：v1.0確定時（必須）

利用者が「d. これでOK」を選択したら、以下を実行する：

1. バージョンを **v1.0** に確定する
2. ファイル名のバージョン部分を `v1.0` に更新する
3. 以下のメッセージを表示する：

> 「詳細設計書を v1.0 として確定する。**実装に着手する前に、社内技術レビュー（部長／補佐／次長）を受けてください**。詳細設計はClaude Code実装の直接インプットになります。Claude Codeへの指示はこの設計書を根拠として進めてください。」

**重要**：チェックポイント2は v1.0 確定時のみ発動する。ブラッシュアップサイクルの途中（v0.2, v0.3 等）では発動しない。詳細設計は顧客レビュー不要。社内技術判断としての品質を担保するレビューを促す。

---

## 既存ファイル再開モード

### 起動フロー

1. 起動モードでBを選択した場合
2. 「既存の詳細設計書のファイルパスを教えて」と聞く
3. 指定されたファイルを読み込み、以下をメモリに展開する：
   - 案件メタ情報（案件タイプ・顧客名・担当者）
   - 上流基本設計書のパス（記載がある場合は再読み込みする）
   - DD-ID採番状況（次に振るDD-IDを把握する）
   - 各DDの内容（機能名・処理概要・上流BD-ID）
   - DB設計の現状（テーブル定義・主要SQL等）
   - 現在のバージョン番号
4. 読み込んだ内容を要約して提示し、ブラッシュアップサイクルから開始する
5. テンプレート構造から逸脱した記述がある場合は警告を出す

### 想定ユースケース

- 途中まで作った詳細設計書を翌日以降に続ける
- 基本設計書が更新されたため、詳細設計書に差分反映する
- v1.0確定後に実装で仕様変更が発生し、v1.1 として更新する

---

## 出力ファイルの規則

### ファイル名規則

```
詳細設計書_<案件名>_v<バージョン>_<YYYY-MM-DD>.md
```

| 状態 | バージョン例 | 備考 |
|---|---|---|
| 整形フェーズ初回出力 | v0.1 | 草案を整形した直後 |
| ブラッシュアップ中 | v0.2, v0.3, ... | 修正のたびに自動インクリメント |
| FIX | v1.0 | 利用者が「OK」を出した時点で確定 |
| FIX後の追加修正 | v1.1, v1.2, ... | 実装中の仕様変更があった場合 |

### 保存場所

利用者がスキル起動時（または整形フェーズ完了時）に保存先を指定する。案件フォルダ配下に保存するのが基本。

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **上流ファイルは必須**：基本設計書のパスを必ず指定させる。省略運用の場合は要件定義書または既存仕様書で代替可（その旨を設計概要・前提に明記）
- **DD-IDは振り直さない**。一度付与したIDは変更しない（後続スキルとのトレーサビリティを維持するため）
- **BD-ID → DD-IDの1対多展開を許容**。1つのBD-IDが複数のDD-IDに展開される場合は連続番号で管理し、BD-ID→DD-IDマッピング表（1.1節）に必ず記載する
- **エラーパターンは3区分で必ず聞く**：業務エラー／システムエラー／外部連携エラーの3区分を網羅する
- **DB・SQL設計は小規模案件で簡略化可**：テーブル定義のみで省略可、「該当なし」も許容する
- **既存コード再利用箇所とコーディング規約を草案フェーズで必ず確認する**（Delphi→C#リニューアル等の既存システム改修案件での整合性確認漏れを防ぐ）
- **数値を推測で記載しない**。未確定の金額・工数・期日等は「⚠ 要確認」として明示する。想定値を記録しない
