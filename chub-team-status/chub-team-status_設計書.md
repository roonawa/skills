## 1. 目的

C-HUB の **CS部の3ボード**（CS部・CS部_保守関連・CS部_企画/内部）のタスクを **管理者目線で横断して俯瞰する** Claude Code スキル。
（2026-09-29 の実データ確認後、対象を CS部用に絞った。当初は全プロジェクトを対象にしていた）
「今、誰が何をしているか」「どこが遅れ・止まっているか」を、週1棚卸しの前などに短時間で把握できるようにする。

運用ガイドの共通ルールにある「棚卸しは機械的に拾う」「担当者の表記を揃えて横断で件数を見る」を、画面を1枚ずつ見て回らずに実現する。

### 使い方の想定

引数で役割を切り替える（`/chub-team-status` ＝相談、`/chub-team-status report`（または `レポート`）＝レポート）。

- **相談**（引数なし）：「今週の期限切れは？」「◯◯さんの抱えている件数は？」「手が空いている人は？」と Claude に聞くと、集計結果から会話で答える
- **レポート**（`report` / `レポート`）：担当者別のガント・要対応一覧などを1枚の HTML ファイルに出力し、会話にも要点（基準日・要対応の件数・目立つ点3つまで・ファイルの場所）を出す
- 「棚卸し」の役割（担当者別に確認事項を並べる）は見送り。ブラッシュアップ候補 6章を参照

## 2. スコープ

| 対象 | 対象外 |
| --- | --- |
| C-HUB タスク管理の **読み取り** | タスクの作成・更新・削除、チャットへの投稿（書き込みは一切しない） |
| CS部の3ボード（CS部・CS部_保守関連・CS部_企画/内部） | 上記以外のプロジェクト（案件プロジェクト・他部署・信大系・テンプレート）。本人が参加していない非公開プロジェクト（API の仕様上取れない） |
| ローカルでの集計・HTML 出力 | claude.ai 等への公開、共有フォルダへの自動保存 |

### 位置づけ（部門方針との整合）

- **C-HUB が正本**。スキルは C-HUB から読んで並べて見せるだけで、タスクを保持・管理しない（Cocoon 審査で整理した「表示はよい、保持は問題」の考え方に合わせる）
- 10/1 からの「ルール→教育→仕組み」の順を崩さないため、当面は **管理者の棚卸し支援（個人利用）** として使う。部門の仕組みとして展開するかは仕組みフェーズで改めて判断する

## 3. 構成

```
chub-team-status/            … スキル本体（Claude Code の skills 配下に置く）
├─ SKILL.md                  … いつ使うか・手順・判定の定義・注意点
├─ scripts/
│   ├─ run.py                … 入口。取得→集計→（HTML）をまとめて実行
│   ├─ chub_config.py        … 設定ファイル（接続先・キー）を読む
│   ├─ chub_client.py        … C-HUB API の GET だけを行う
│   ├─ fetch.py              … C-HUB API から取得して生データ JSON を保存
│   ├─ aggregate.py          … 生データから集計 JSON を作る（通信しない）
│   └─ render_html.py        … 集計 JSON から単一 HTML を作る（通信しない）
└─ tests/                    … 固定データで設定・通信・判定・集計・描画を検証
```

- 取得・集計・描画を分ける。集計と描画はネットなしで動くので、固定データでテストでき、数字の正しさをテストで担保できる
- Claude は会話で答えるとき **集計 JSON を読む**。生データを Claude が数えることはしない（件数が多いと数え間違えるため）。「◯◯さんの要対応は？」のような質問は、集計 JSON の担当者別一覧から答える（SKILL.md にもこの旨を書く）。「◯◯さんの要対応は？」のような質問は、集計 JSON の担当者別一覧から答える（SKILL.md にもこの旨を書く）
- Python 標準ライブラリのみで作る（HTTP は `urllib`）。追加のインストールは不要

### 処理の流れ

1. `fetch.py`：プロジェクト一覧 → 名前が CS部の3ボードと一致するプロジェクトだけ、詳細（区分・状態・カスタム項目）→ 各プロジェクトのタスク全件（`show_completed=true`）を取得
2. `aggregate.py`：基準日（既定は実行日、日本時間）で判定・集計
3. 会話で答える／`render_html.py` で HTML を出す

## 4. 設定とキーの扱い

### 置き場所

設定は **1ファイル**で、スキルとは別の場所に置く。

```
%LOCALAPPDATA%\chub-team-status\config.json
```

```json
{
  "base_url": "https://chub.ailesys.co.jp",
  "api_key": "発行されたキー"
}
```

- `base_url` は **ホストまで**（`/api` は付けない。API のパスが `/api/...` から始まるため）
- 接続先とキーを1組で持つ。キーは発行した接続先でしか通らないため、接続先だけ書き換えて別サーバーにキーを送る事故を防ぐ
- 環境変数 `CHUB_CONFIG_FILE` があれば、そのパスを優先して読む
- 別の PC ではユーザー名が違っても `%LOCALAPPDATA%` で自動的に読み替わる。スキル側の変更は不要

### スキル配下・`.claude` 配下に置かない理由

- スキルは別の人・別の PC に渡すことがある。キーが一緒に配られる事故を防ぐ
- `.claude` 配下は Claude が日常的に読み書きする場所で、PC 間で複製することもある

### キーの取り扱いルール

- 権限は **`task-manager:read` のみ**（書き込み権限は付けない）
- **1人1PC につき1本**。PC を手放すときはそのキーだけ失効する
- ファイルのアクセス権は本人のみに絞る
  ```
  icacls "%LOCALAPPDATA%\chub-team-status\config.json" /inheritance:r /grant:r "%USERNAME%:(M)"
  ```
- **キーの書き込みは Claude Code を閉じた状態で行う**。Claude Code は、会話中に Claude が触ったファイルが変更されると、その中身を会話に取り込むことがある。キーが会話に入った場合は、すぐに C-HUB の「AI とつなぐ」で失効・再発行する（ログ削除だけでは送信済みの事実は消えない）
- スクリプトはキーの値をログ・出力・エラー文に一切出さない

## 5. 取得（fetch.py）

| 順 | API | 回数 |
| --- | --- | --- |
| 1 | `GET /api/plugin/task-manager/projects` | 1 |
| 2 | `GET /api/plugin/task-manager/projects/{id}` | 対象ボード数（3） |
| 3 | `GET /api/plugin/task-manager/projects/{id}/tasks?show_completed=true` | 対象ボード数（3） |

- 2・3 は、名前が「CS部」「CS部_保守関連」「CS部_企画/内部」と完全一致するプロジェクトだけ呼ぶ（ボード名はスクリプトに書いておく）
- 3つのうち見つからないボードがあれば警告を出して続ける（名前の変更に気づくため）
- 保管済み（`archived=1`）のプロジェクトは 2・3 を呼ばない
- 回数上限（既定 120 回/分）を超えないよう、呼び出しの間に 0.5 秒空ける。429 が返ったら 60 秒待って 1 回だけ再試行する
- 成否は HTTP ステータスで判断する（401/403/429 は `ok` 項目が無いため）
- 実行時に接続先 URL・取得したプロジェクト数・タスク数を表示する（キーは表示しない）

### 出力の保存と後始末

- 既定の保存先：`%LOCALAPPDATA%\chub-team-status\runs\YYYYMMDD-HHMMSS\`（生データ・集計・HTML）
- **直近 5 回分だけ残し、古いものは自動で消す**（C-HUB の写しを溜め込まないため）
- 棚卸しで配る場合は、HTML だけを利用者が必要な場所へコピーする。スクリプトは共有フォルダへ自動保存しない

## 6. 判定と集計（aggregate.py）

### 対象

- 保管済みプロジェクトは除く
- 対象は CS部の3ボードだけ（取得の段階で絞る。テンプレート「テンプレート：CS案件」も取得しない）
- CS部ボードで、区分が **失注・保留** のカード、またはセクションが **失注・保留中** のカードは判定から除き、件数だけ別枠で出す
- **CS部_保守関連** はずっと稼働中の契約を表すカードなので、「期限切れ」「動きなし」「期限なし（入力漏れ）」の判定と、負荷の偏り・ガント・完了実績から除く（担当なしの判定だけは行う）

### 判定の定義

| 判定 | 定義 |
| --- | --- |
| 未完了 | 状態種別（`status_category`）が `open` または `active` |
| 期限切れ | 未完了かつ 期限 < 基準日。超過日数も出す |
| 詰まり | 状態名が「詰まり」（状態種別には無いため名前で判定） |
| 動きなし | 未完了かつ 最終更新から **14 日以上** |
| ゲート違反 | 未完了の CS部カードで、段階が「見積中」以降なのに、確認状況が「客先すり合わせ済み」でない |
| 入力漏れ | 未完了で、担当なし または 期限なし |
| 期限間近 | 未完了で、期限が基準日から 14 日以内 |

- 「カード据え置き」（案件プロジェクトは動いているのに CS部カードが据え置き）は、案件プロジェクトを取得しなくなったため判定しない（11章の候補へ）

### CS部ボードの段階（セクション）

C-HUB の実際のセクション名で扱う（2026-09-29 時点）。

| 段階の並び | ゲート判定の対象（見積中以降） |
| --- | --- |
| 引き合い/予定 | 対象外 |
| 見積中 | 対象 |
| 見積提出済み（※受注したら、製造セクションへ移動） | 対象 |
| 製造 | 対象 |
| テスト | 対象 |
| 納品待ち | 対象 |
| 請求書発行待ち | 対象 |
| 完了 | 対象 |

- 保留中・失注のセクションは段階の並びに入れず、除外の別枠で件数を出す
- 上記以外のセクション名が出てきたら「（段階なし・その他）」に数える

- 日数のしきい値（14 日）は引数で変えられる
- 担当者は `assignee`（ユーザー名）で集計し、表示は `assignee_display_name` を使う

### 集計

| 集計 | 中身 |
| --- | --- |
| 要対応 | 期限切れ・詰まり・動きなし・ゲート違反・入力漏れ の件数と一覧。判定別の一覧に加え、**担当者別の一覧**（`assignee` をキー、`assignee_display_name` を表示名。担当なしは「（担当なし）」として末尾）も集計 JSON に持つ。1件が複数の判定に該当する場合は、担当者別では1件として数え、該当する判定を併記する |
| 負荷の偏り | 担当者別の未完了件数（未着手・進行中・詰まりの内訳）、期限切れ件数、期限間近件数 |
| ガント用データ | タスクごとの棒の始点・終点・色分け（下記） |
| 商談状況 | CS部ボードの段階別件数（失注・保留は別枠）、ゲート違反一覧 |
| 完了実績 | 直近 8 週の週別完了件数（全体・担当者別）。完了日時で判定 |

## 7. ダッシュボード（render_html.py）

1枚の HTML ファイル。外部の CDN やフォントを読まない（社外への通信を発生させない。オフラインでも開ける）。上から「全体 → 人 → タスク」の順に並べる。

1. **要対応（棚卸し候補）**：判定ごとの件数と一覧。タスク名・プロジェクト・セクション・担当・期限・最終更新
   - 一覧は **「判定別 / 担当者別」の表示切替**（既定は判定別。切替は HTML 内の script で行い、外部通信はしない）
   - 担当者別では、担当者ごとの折りたたみブロックにする。見出しは「氏名（要対応◯件）」、中は期限切れ・詰まり・動きなし・ゲート違反・入力漏れの順に並べる。担当なしは末尾に「（担当なし）」
   - 描画側では数えず、集計 JSON の担当者別一覧をそのまま並べる
2. **負荷の偏り**：担当者別の件数を横棒で並べる
3. **ガント**：担当者ごとの行の下にタスクを並べる
4. **CS部ボードの商談状況**：段階別件数とゲート違反
5. **完了実績の推移**：週別の完了件数

### ガントの描き方

C-HUB では開始日がほとんど入力されていないため、次のように描く。

| 項目 | 描き方 |
| --- | --- |
| 左端 | 開始日があればそれ、無ければ **起票日** |
| 右端 | 完了済みは完了日、未完了は期限 |
| 期限なし | 今日まで点線で描き、色を変える |
| 色 | 期限切れ＝赤（今日まで伸ばす）、詰まり＝橙、完了＝薄色 |
| 表示範囲 | 既定で今日の 4 週前〜8 週後。今日の位置に縦線 |
| 表示するタスク | 未完了の全タスク＋表示範囲内に完了したタスク |

起票日で代用すると、起票から着手まで間が空くタスクは棒が長く見える。見づらい場合は、タスクの操作履歴（単一取得の `activities`）から「最初に進行中にした日」を左端にする方式に切り替える（1件ずつ取得するため時間がかかる）。

## 8. エラー時の動き

| 状況 | 動き |
| --- | --- |
| 設定ファイルが無い・JSON が壊れている・キーが空 | 理由と置き場所を表示して止まる（キーの値は出さない） |
| `base_url` が `https://` でない | 止まる（C-HUB は HTTPS のみ） |
| 401 | 「キーが違う・期限切れ・失効済み、または接続先の違い」と表示して止まる |
| 403 | プロジェクト一覧で出たら「キーの権限不足（task-manager:read）」と表示して止まる。個別のプロジェクトで出たら、そのプロジェクトだけ飛ばして続ける（下の「一部のプロジェクトで取得失敗」と同じ） |
| 30x（リダイレクト） | 追いかけずに止まる（キーをリダイレクト先に送らないため） |
| 想定外のエラー | 例外の種類だけを表示して止まる（詳細やトレースバックは出さない。キーが紛れ込む経路を断つため） |
| 429 | 60 秒待って 1 回再試行。再度 429 なら止まる |
| 一部のプロジェクトで取得失敗 | そのプロジェクトを飛ばして続け、最後に飛ばした一覧を表示する。集計結果にも「欠けあり」と明記する |

## 9. テスト

- `aggregate.py` の判定を固定データで検証する（期限切れの境界＝期限当日は切れていない、詰まりの名前判定、据え置きの同名対応、失注・保留の除外、保守ボードの除外、完了済みを未完了に数えない、担当者別一覧の件数が判定別の重複除外件数と一致する、担当なしが末尾にまとまる 等）
- `fetch.py` は実環境で1回動かし、取得件数を C-HUB の画面と突き合わせる
- `render_html.py` は生成した HTML をブラウザで開いて目視確認する

## 10. 実データで確認が必要な前提

新しいキーを入れた後、最初に確認する。

| 前提 | 外れたときの対応 |
| --- | --- |
| ボード名が「CS部」「CS部_保守関連」「CS部_企画」で取れる | ボードの見分け方を名前以外（ID の設定など）にする |
| 一覧 API で `custom_field_values`（区分・確認状況）が返る | 単一取得で補うか、ゲート違反・失注除外を外す |
| 状態名「詰まり」が全ボードで同じ表記 | 表記ゆれを設定で吸収する |
| テンプレートを名前で見分けられる | 見分け方を別途決める |
| `updated_at` の時刻が日本時間か UTC か | 日付計算の補正を入れる |
| 担当者の表記が3ボードで揃っている | 揃っていない担当者を一覧で出す |

### 確認結果（2026-09-29、全78プロジェクト・3156タスクを取得して確認）

| 前提 | 結果 | 対応 |
| --- | --- | --- |
| ボード名 | **外れ**。実際は「CS部_企画/内部」 | スクリプトのボード名を実名に直す |
| `custom_field_values` | 一覧 API で返る。ただし値が入っているのは CS部カード 66 枚中 28 枚 | 対応不要（値なしは確認状況「未設定」として扱う） |
| 「詰まり」の表記 | 持っている5プロジェクトはすべて「詰まり」。CS部_保守関連には「詰まり」の状態が無い（未着手・進行中・終了） | 対応不要 |
| テンプレート | 「テンプレート：CS案件」を名前で見分けられた | CS部用に絞ったため、取得しない |
| `updated_at` | **日本時間**（`YYYY-MM-DD HH:MM:SS`。取得時刻 10:55 に対し最新更新が 10:48）。CS部外の1件だけ UTC の ISO 形式（末尾 `Z`） | 対応不要（CS部の3ボードに UTC 形式は無い） |
| 担当者の表記 | 3ボードで揃っている（ユーザー名と表示名が1対1） | 対応不要 |
| （追加）CS部のセクション名 | **外れ**。想定の「引き合い」ではなく「引き合い/予定」。ほかに「見積提出済み（※…）」「請求書発行待ち」「保留中」「失注」がある | 6章「CS部ボードの段階」のとおりに直す |

- 確認の過程で、案件プロジェクトや信大系ボードには独自の状態（保留・着手不可・差し戻し等）があるとわかった。全体を対象にするには状態の扱いを別途決める必要があるため、当面は CS部用とした
- C-HUB 画面との件数の突き合わせと、ガントの見やすさの確認は、CS部用に直した後で行う

## 11. やらないこと（今後の候補）

- タスクの書き込み・チャット投稿（必要になったら別スキル／別キーで検討）
- 自動実行（定期実行）。まずは手動で使って判定の妥当性を確かめる
- 操作履歴を使った着手日の推定（ガントが見づらい場合に検討）
- MCP 接続（`/api/mcp`）。書き込み系の道具が確認なしで実行されるため、読み取り専用の用途では使わない
- CS部以外のプロジェクトへの拡大（ボードごとの状態名・セクション名の扱いを決めてから）
- カード据え置きの判定（同名の案件プロジェクトを取得する必要がある）
