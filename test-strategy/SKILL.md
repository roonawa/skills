## 目的

「方針が明文化されていること」そのものがテスト戦略の価値であり、テスト設計やテスト実行の前に、関係者間で合意形成することが重要。
そのため、要件定義書や設計書、改修案件であれば既存ドキュメントやソースコードを参照しながら、テスト戦略の作成を補佐するスキル。
要件定義書や詳細設計書の読解を通じて、ユーザーへの提案や質問を行い、テスト戦略の骨子を作成する。
あくまで判断をするのはユーザーであり、スキルは提案や質問を通じてユーザーの意思決定を補佐する。

### 解消するべき課題
- リリース判断の根拠がない。
- テスト設計やテスト実行の前に、関係者間で合意形成されていない。
- 単体テストでどこまでカバーすべきかわからない
- E2Eテストでどこまでカバーすべきかわからない
- テストの優先順位が決められない。
- テストの優先順位に基づいた工数配分ができない。

## 前提
テストプロセスにAIを活用している。手動テストの前に、AIによるテスト実施を行うことで手動テスト実施前にリスクを未然に回避している。
静的解析を重めにすることで、テスト実行の前に手戻りリスクを未然に最小化することを重視している。

## スコープ

### テスト戦略に書くこと
- 品質目標 — このプロダクトで守るべき品質は何か
例：「決済処理の信頼性」「個人情報のセキュリティ」「初回ユーザーの操作完了率」

- リスク分析と優先順位 — どこにリスクが高く、どこに集中するか
例：「外部API連携は障害リスクが高いため、重点テスト領域とする」

- テストレベルの方針 — どのレベルで何を担保するか
例：「ビジネスロジックは単体テストで網羅。UIフローはE2Eで主要パスのみ」

- テスト観点の方針 — 重視する観点と軽量化する観点
例：「異常系・境界値を重視。正常系の単純確認は自動化で対応」

- 終了条件 — テストの「完了」をどう定義するか
例：「重大バグ0件、主要シナリオ全通過、ステークホルダーの合意」

### 具体的な項目
- テスト目的・品質目標
- リスク分析
- テストレベルの方針（単体／結合／E2E）
- テスト観点の方針（正常系／異常系／境界値／セキュリティ／パフォーマンス等）
- テスト終了条件（完了定義）
- テスト対象外の定義
- テスト実行の工数（機能ごとの工数配分）

## 起動時の動作

スキルが起動したら、最初に起動モードを確認する。

> 「要件定義スキル（spec-req）を起動した。以下のどれで進める？
> A. 新規作成（完全新規案件、ゼロから壁打ちを始める）
> B. 既存ファイルから再開（過去の出力Mdを読み込んで続きから）」

- **Aを選んだ場合**：案件タイプ判定から開始
- **Bを選んだ場合**：既存ファイルのパスを聞き、読み込んでブラッシュアップサイクルから開始

---

## 作成方法

詳細設計書、要件定義書を参照しながら、テスト戦略の骨子を起こす。
ドキュメントにない情報については、ユーザーに質問あるいは提案する。
質問は**1問ずつ**投げる。複数の質問を一度に投げない。回答内容に応じて追加深堀りを行う。

## チェックポイント2：v1.0確定時（必須）

利用者が「d. これでOK」を選択したら、以下を実行する：

1. バージョンを **v1.0** に確定する
2. ファイル名のバージョン部分を `v1.0` に更新する
3. 以下のメッセージを表示する：

> 「テスト戦略を v1.0 として確定する。**次工程への移行前に、社内でのレビュー（部長／補佐、または該当担当者）を必ず受けてください**。」

**重要**：チェックポイント2は v1.0 確定時のみ発動する。ブラッシュアップサイクルの途中（v0.2, v0.3 等）では発動しない。中間版を都度レビュー依頼すると運用が回らないため。

## 既存ファイル再開モード

### 起動フロー

1. 起動モードでBを選択した場合
2. 「既存のテスト戦略のファイルパスを教えて」と聞く
3. 指定されたファイルを読み込み、以下をメモリに展開する：
   - 案件タイプ
   - FR-ID採番状況（次に振るFR-IDを把握する）
   - 現在のバージョン番号
4. 読み込んだ内容を要約して提示し、ブラッシュアップサイクルから開始する
5. テンプレート構造から逸脱した記述がある場合は警告を出す

### 想定ユースケース
- 顧客との打ち合わせ後、得た情報を既存テスト戦略に反映する
- 草案を作って一旦止めていた案件を後日再開する
- v1.0確定後に追加要望が出てきた場合の更新（その場合は v1.1, v1.2, ... で管理）

## 出力ファイルの規則

### ファイル名規則

```
テスト戦略_<案件名>_v<バージョン>_<YYYY-MM-DD>.md
```

| 状態 | バージョン例 | 備考 |
|---|---|---|
| 整形フェーズ初回出力 | v0.1 | 草案を整形した直後 |
| ブラッシュアップ中 | v0.2, v0.3, ... | 修正のたびに自動インクリメント |
| FIX | v1.0 | 利用者が「OK」を出した時点で確定 |
| FIX後の追加修正 | v1.1, v1.2, ... | 顧客合意後の修正があった場合 |

### 保存場所
利用者がスキル起動時（または整形フェーズ完了時）に保存先を指定する。案件フォルダ配下に保存するのが基本。

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **「やらないこと」は必ず聞く**。スコープ肥大化を防ぐための重要項目
- **数値を推測で記載しない**。未確定の金額・工数・期日等は「⚠ 要確認」として明示する。想定値を記録しない
- **個人名の扱い**：ドキュメント上で個人名を匿名化する必要がある場合は「担当者A」「担当者B」等の役割表記を使う
- **FR-IDは振り直さない**。一度付与したIDは変更しない（後続スキルとのトレーサビリティを維持するため）
- **チェックポイント2はv1.0確定時のみ**発動する。中間版では発動しない
- **モードCで参照ドキュメントが読み取れない場合**は「⚠ 内容未抽出」と明示し、利用者から口頭で概要を聞く
- **モードCの参照ドキュメントは3〜5本程度を目安**とする。それ以上の場合は利用者が事前に主要ドキュメントを選定して指定する
