# CSアプリのWebView2回帰テスト

## 目的と境界

実際のCSアプリ内のWebView2をPlaywrightのCDP接続で操作し、PT/STで同じケースを実行して、画面表示・操作結果・占有なしで取得できる出力ファイルを比較する。ブラウザだけで動かした結果をCSアプリのE2E成功として扱わない。

このスキルはWebView2内の操作に限定する。APIへの直接リクエスト、API応答・GraphQL payloadの比較、認可・所有者検証、DB照合、負荷試験は行わない。画面操作に伴う通常のAPI通信はアプリに任せる。

ただし、画面が呼び出すAPIの網羅は本スキルの成果物に含める。画面からたどれるAPIの呼び出し箇所をすべて一覧にし（後述の「APIの呼び出し網羅」）、各呼び出し箇所を、それを呼ぶ画面操作のケースに対応付け、実行中に送られたAPIの操作名・状態コード・GraphQLエラーの件数を記録して、報告書に「API一覧」と「テスト×API対応表」を載せる。依頼に明示がなくても行う（利用者の関心は「画面内のAPIがすべて適切に呼ばれること」であることが多く、ケースの網羅だけでは答えにならない）。

本スキルの目的は、人が実機のCSアプリを操作して画面を確認する作業の代替（スモークテスト）である。境界値や全分岐を網羅するQAは目的にしない。記録対象は正常系を基本とし、ロールや表示モードで挙動が変わる場合はその組合せぶんだけ正常系を用意する。必須入力フォームを持つ操作に限り、必須項目あり（成功）と必須項目なし（バリデーションエラー）の2パターンを追加する。それ以外の異常系・境界値は `dev-test` / `spec-test` で扱う。

「網羅的」とは、カバレッジ率ではなく、後述の画面マニフェストの全項目が「実行済み」か「理由付きで除外」に確定している状態を指す。

FlaUI、UI Automation、Win32の操作、OSへのキー送信、座標クリック、ウィンドウの前面化・移動・リサイズは行わない。非占有で実行できそうなUIA操作もこのスキルには含めない。

### ネイティブのログイン画面があるとき（認証準備）

CSアプリが起動時にWebView2の外のログイン画面（証明書方式のLoginView等、WinForms）を出す構成では、ログインは本スキルの外の認証準備とする。

1. 各実行の前に、`cs-native-regression-test` の「ログイン前処理」で、CDPポート付きでCSアプリを起動し、ネイティブのログインを通す。前処理はPC占有の短い時間枠として、実行前に利用者へ示す。
2. 前処理から、起動したPID・CDPポート・ログインしたアカウントの区分を受け取る（本スキルの実行の `evidence/<run-id>/login-handoff.json`）。本スキルはそのインスタンスに `connectOverCDP()` で接続し、対象画面のURLと見出しを確かめてから始める。
3. 本スキルのspec・fixtureにFlaUIの呼び出しを書かない。前処理は別プロセス・別ステップで行い、終わってから接続する。
4. 前処理が失敗した、または接続した先がログイン画面のままなら、その実行の全ケースを「未実施（認証準備失敗）」とする。
5. 実行中にネイティブのログイン画面へ戻された（セッション切れ・証明書のエラー）ら、そのケースを停止し、前処理からやり直す。戻されたこと自体を、そのケースの結果として記録する。

**パスワードの自動入力が許されないとき（手動ログイン）**：エージェントの安全規則（ローカル開発ホストや名前でテスト環境と分かるホスト以外ではパスワードを入力しない）により、前処理の自動入力ができないことがある（例：`allcweb1.local…` のように名前で試験環境と判定できないホスト）。このときは次の手順に切り替え、規則を回避しない。

1. CDPポートと専用のTEMPを付けてテスト用インスタンスを起動する（利用者の作業用インスタンスとは別。起動はPC占有の前処理）。
2. 利用者に「どのウィンドウ（PID）に、どのアカウント区分で」ログインするかを示し、ログインしてもらう。資格情報の値を会話に出させない。
3. CDPの `/json/list` に対象ホストの `/CS/` のページが現れるまで、期限付きで待つ（同時にPIDの生存も確認し、消えたら待つのをやめて知らせる）。
4. `login-handoff.json`（または起動記録）に `login: manual` と、アカウント区分・時刻を残す。報告書の実行条件にも書く。
5. 利用者が作業用インスタンスの方にログインしてしまうことがある。どちらもタイトルが同じなので、PIDで示し、ログイン後にCDPで確認する。

## PC占有との分離

テストは原則 `webview` と `native-required` の2区分にする。同じspecで混在させない。

| 区分 | 例 | このスキルの扱い |
|---|---|---|
| webview | DOMでの検索、入力、一覧選択、Webダイアログ | Playwrightで実行 |
| webview | 事前設定した専用フォルダへ無人出力できる帳票 | 条件を実証できた場合だけ実行・比較 |
| native-required | Windowsのファイルを開く・保存・フォルダ選択・印刷ダイアログ、外部Excel/PDFアプリ、IME操作 | 未実施として別スキルへ引継ぎ |
| webview | `<input type="file">` へのファイル指定（`setInputFiles` でOSのダイアログを出さずに渡せる場合） | 小さく実証できた場合だけ実行。OSのダイアログが出る実装なら native-required |
| 認証待ち | 人の操作を要するMFA・SSO | 認証準備待ちとして記録し、認証後に再開 |

DOM操作は通常、利用者のマウス・キーボードを使わない。ただし実アプリの起動、認証、プラグイン、ダウンロードは前面化や外部アプリ起動を伴うことがある。「PCを一切占有しない」と保証しない。

最初に小さなケースでフォーカス・ネイティブダイアログ・外部起動の有無を確認する。初回の起動確認が人の作業を妨げるなら、その時間を調整するか専用PC/VMを使う。テスト用CSアプリは利用者の作業用インスタンスと分ける。

ネイティブUIが必要と判明した操作は、以降のwebview実行から除外する。実行中に予期せず出た場合はそのケースを停止し、同じインスタンスで後続を続けない。閉じるために勝手にクリックせず、所有するテストプロセスの終了で回復できるか確認する。

更新・帳票処理が進行中、未保存の変更がある、処理状態が不明な場合は強制終了しない。ケースを保留し、利用者に状態と必要な対応を伝える。MFA待ちは期限付きにし、期限切れは未実施とする。再開時は認証とデータ状態を確認し、更新途中のケースを無条件に最初から再実行しない。

引継ぎ先は `cs-native-regression-test`。FlaUIによるWindows側の回帰テストはPC占有枠を確保して別実行にする。引継ぎ先を自動実行しない。利用者が別途PC占有テストを依頼したときに使う。ただし、次の「ネイティブのログイン画面があるとき」の前処理は、引継ぎではなく本スキルの実行の認証準備なので、実行前に占有を示したうえで毎回行う。

## 入力と調査

利用者の依頼と既存資料から次を特定し、不足する実行必須情報だけ質問する。

- 対象画面・ケース・対象ロール、比較元/比較先、意図した変更。
- PT/STのURL、接続条件、実行するexe・DLL・Web版の組合せ。
- テストアカウントの取得方法、認証準備方法。秘密値は環境変数等から受け取り、文書やソースに埋め込まない。
- 同じ検索条件・年度・学籍番号等で比較できるデータ。更新ケースは専用データと復元方法。
- 証跡保存先、帳票出力先、ネイティブ操作を必要とする既知のケース。

リポジトリのAGENTS.mdを確認し、現在のコード・設定を読んで接続方法を決める。Allcampus固有の調査箇所とCDP接続の要点は [references/allcampus-webview2.md](references/allcampus-webview2.md) を読む。

既存の `capi-regression-test` の同一ケース比較・差異分類と、`capturing-playwright-evidence` の証跡完全性の考え方を参考にする。ただしAPI比較、campus専用の認証方法、強制CSS変更、ヘッダー非表示、固定待機時間は取り込まない。これらのスキルを無条件の実行依存にしない。

PTを常に新版、STを常に旧版と決めつけない。比較元と比較先は今回のビルド・デプロイ状態で決定し、exe、プラグインDLL、Web版の識別情報を保存する。差がクライアント由来かWeb由来かを判断できるようにする。

### 比較元と比較先が同じ環境の段階違いのとき（段階比較）

依頼が「同じ環境（例：社内PT）で、設定・機能の段階を入れる前（ベースライン）と後を比べる」場合は、本書の「ST／PT」「両環境」を次のように読み替える。それ以外の規則はそのまま適用する。

| 本書の記述 | 段階比較での読み替え |
|---|---|
| ST・PT（両環境） | ベースライン（例 `R-0`）と比較先の段階（例 `R-2`）。ラベルは依頼の段階名をそのまま使う |
| 証跡の `ST/`・`PT/` | `<段階ラベル>/`（例 `R-0/`・`R-2/`）。1つの `evidence/<run-id>/` に1段階を入れ、ベースラインの run-id を manifest の `baselineRunId` に書く |
| 両環境のデータが同一であること | ベースラインと比較先の実行前のデータの状態が同じであること。同じ代表キー・件数を比較先の実行前に画面で確かめ、ずれていれば「比較不能（データ変化）」 |
| 両環境で成功 | ベースラインと比較先の両方で、同じテストコードを変えずに実行して成功 |
| `comparison.json`・`report.html` | 比較先の run に置く（ベースラインの run には置かない） |

- 段階の切り替え（サーバーの設定の変更・戻し）は本スキルで行わない。依頼側の担当者が行い、その設定を受け取る。
- manifestに、段階ごとのサーバー側の設定（各機能のモード・フラグ）と、切り替えた日時を記録する。設定を確かめられない段階は比較しない。
- ベースラインは、比較先と同じテストコード・同じ母数（マニフェスト）で取る。画面やコンポーネントを母数に足したら、比較の前にベースラインを取り直す。
- 段階の切り替えはサーバーの設定なので、TC単位で両方を交互に流すことはできない。ベースラインを全件取ってから切り替える。間があく場合は、更新系ケースで作ったデータを残さないこと（後始末の確認）を徹底する。
- 段階比較の「意図した差分」は、その段階の設計で決まっている変化（例：エラー文言の固定化）だけにする。根拠の文書と該当箇所を記録する。

## 画面マニフェスト（網羅の分母）

担当者の裁量で対象を決めないため、画面ごとに `coverage/cs-screens/<ScreenId>.json` を作成してコミットする。証跡と違い、これはgit管理対象にする。

1. `frontend/gakumu/src/router/index.ts` 等から、CSアプリ内で到達できる画面を機械的に列挙する。desktopOnlyで誘導される画面も対象に含める。
2. 画面ごとに、操作（検索・一覧選択・登録・Webダイアログ等）と、ロール・表示モード（タブ、ラジオボタン等の切替）を、テンプレートの `v-if`・`computed`・ガード条件から抽出する。
3. 各項目を次のいずれかに確定する。

| 区分 | 内容 |
|---|---|
| webview | Playwrightで実行する。`depth` と `risk` を付ける |
| native-required | 保存・印刷ダイアログ、外部アプリ、IME等。根拠を付けて `native-handoff.md` へ回す |
| auth-wait | MFA・SSO待ち。期限と再開条件を付ける |
| excluded | デッドコード（onMounted・テンプレートから参照なし。grep結果を根拠にする）、タイミング依存、外部要因依存。`reason` と `evidence` を必須にする |

```json
{
  "screen": "Portal",
  "operations": [
    { "name": "次の授業ブロック表示", "kind": "webview", "depth": "フル", "risk": "高", "scenarios": ["TC-001", "TC-002"] }
  ],
  "reports": [],
  "nativeRequired": [],
  "excluded": [{ "target": "...", "reason": "dead-code", "evidence": "grep結果" }],
  "apis": { "source": "apiInventory.cjs の出力ファイル", "list": [] },
  "noTargetsReason": null
}
```

`reports` は帳票出力操作、`noTargetsReason` は `operations` と `reports` が両方空のときに理由を必須とする。`apis` は後述の「APIの呼び出し網羅」の母数で、APIを呼ばない画面でも `list: []` と根拠（import をたどった結果）を残す。いずれも該当なしの場合は空配列・`null` を明記し、キーを省略しない。

`coverage/` がリポジトリの `.gitignore` 対象になっている場合がある（Allcampusは対象）。その場合はコミットできないので、置き場所を利用者に確かめる（強制追加やignoreの変更をしない）。

### コンポーネントも母数にするとき

依頼が「全コンポーネントがAPIを呼べること」を求める場合は、画面とは別に `coverage/cs-components.json` を作り、コンポーネントを1件ずつ確定させる。

1. 母数は `frontend/gakumu/src/components` の .vue から機械的に作る。APIを呼ぶかどうかは、実際の呼び出し（`services.api.X`・`services.batch`・`pagingRequestIterator`・`pollableRequestIterator`・`SkdWithBearer`・`GraphQLClient`）と、store・composable経由の呼び出し（呼んでいる関数まで辿る）で判定する。`useApiService` の import や client の生成だけでは「呼ぶ」に数えない。
2. 各コンポーネントを、`catalog`（一覧画面で確かめる。並べる一覧画面のルート名を書く）か `excluded`（APIを呼ばない、どこからも使われていない等。`reason` と `evidence` 必須）に確定する。
3. 一覧画面（コンポーネントを並べた検証用の画面）は、画面マニフェストにも1画面として入れ、`operations` に並べたコンポーネントを1件ずつ書く。各コンポーネントは、初期表示 → 候補の読み込み → 選択し、選んだ値が画面の確認欄に出るところまでを1つのcheckpointにする。
4. 一覧画面がまだ無い、またはそのビルドに含まれない環境では、該当するコンポーネントを「未実施（一覧画面なし）」とし、実施の手段（一覧画面の作成・デプロイ）を添える。一覧画面を本スキルで作らない（アプリの変更になる）。

```json
{ "component": "AlSearchGakuseki", "kind": "catalog", "catalogRoute": "ComponentCatalog2", "callsVia": "services.api.getFilteredTblGakuseki" }
```

### APIの呼び出し網羅（画面ごとのAPI母数）

画面マニフェストに `apis` を必ず作る。ケースの網羅とは別の母数で、「画面内で呼ぶAPIがすべて、画面操作で適切に呼ばれたか」を確かめるためのもの。

1. **母数を機械的に作る**：画面の .vue から import を再帰的にたどり、実際の呼び出し（`services.api.X`・`services.batch`・`pagingRequestIterator`・`pollableRequestIterator`・`SkdWithBearer`・`GraphQLClient`）を、ファイルと行の単位で列挙する。コメント行・`import type`・クライアント生成だけは数えない。共通ライブラリ（share）経由の送信（例：クライアントログのREST）も、画面操作で送られるものは母数に入れる。Allcampusでは `frontend/gakumu/e2e-cs/apiInventory.cjs` を使う。
2. **呼び出し箇所ごとに到達可否を決める**：同じAPIでも呼び出し箇所が複数あれば別々に扱う。この画面から到達しない呼び出し箇所（親が必要なpropsを渡さない、フラグが立たない等）は `reachable: false` とし、根拠（行番号・grep）を書く。到達しないことを画面操作で示せるなら、そのケースで「0回」を確かめる。
3. **期待を決める**：到達する呼び出し箇所ごとに、契機（画面表示時・ボタン・ダイアログを開いたとき・入力時の照会等）と、`expectAt`＝それを呼ぶケース・checkpoint・最小回数（到達不能の確認は最大0回）を書く。同じ操作名の呼び出し箇所は回数の合計で区別する。対応するケースが無い呼び出し箇所があれば、ケースを足す（サブダイアログ、コード入力時の照会、選択肢の読み込み等は抜けやすい）。
4. **記録する**：`page.on('request'/'response')` で、時刻・メソッド・パス・GraphQLの `operationName`・HTTP状態コード・GraphQLの `errors` の件数だけを保存し、直前のcheckpointからの呼び出しを次のcheckpointに紐づける。variables・本文・応答の中身・ヘッダーの値（トークン）は保存しない。
5. **判定**：呼び出し箇所ごとに「確認（期待の回数以上・状態200・エラー0）」「要確認（回数不足・200以外・GraphQLエラーあり）」「記録なし（記録を取っていない実行。画面上の結果で確認した旨を書く）」「除外（到達しない）」。**HTTP 200でも `errors` が1件以上なら、画面が正常に見えても要確認**とする（画面がエラーを握りつぶして「データは有りません」と出す例がある）。母数に無い操作名（ポータル等が呼ぶもの）は「画面外」として分け、判定に混ぜない。
6. **報告**：report.html に「画面が呼び出すAPIの一覧」（ID・API・種類・用途・呼び出し箇所と契機・期待→実測・呼び出したケース・判定）と「テストとAPIの対応表」（ケース×APIの回数、エラーを含むマスを強調）を載せ、各ケースの詳細にもcheckpointごとの呼び出しを載せる。

```json
{ "id": "API-07", "name": "getFilteredTblKyoukanNew", "kind": "GraphQL query",
  "callSites": [
    { "at": "src/components/AlTeacherCodeSearchParts.vue:128", "trigger": "教員コード入力時の照会", "reachable": true,
      "expectAt": [{ "tc": "TC-016", "cp": "02-range-set", "min": 1 }] },
    { "at": "src/components/AlLectureCodeSearch.vue:233", "trigger": "コード入力時の照会", "reachable": false,
      "reason": "親が basyo・nendo を渡さず先頭で戻る", "expectAt": [{ "tc": "TC-015", "cp": "02-range-set", "max": 0 }] }
  ] }
```

更新系で記録を取らずに実行した場合、記録のためだけに更新を再実行しない（再実行は改めて承認を得る）。その呼び出し箇所は「記録なし（画面で確認）」と書く。

### 記録深度

全操作に同じ厳密さを投じない。ロール制御のみ・本人限定・全件参照の操作は「軽量」とし、個人情報、担当範囲による行レベル制御、帳票、更新を伴う操作は「フル」とする。判定に迷う場合はフルにする。軽量は明確にリスクが低い場合だけの省略であり、既定値にしない。

| 深度 | 適用 |
|---|---|
| 軽量 | 初期表示と代表的な1操作のcheckpoint。値の構造化保存は表示値の主要列でよい |
| フル | ケース設計の全観点。一覧は全列を構造化保存してアサートする。帳票は内容まで比較する |

リスクが高い操作は、DOMから取れる表示値の全量保存を省略しない。

## ケース設計

両環境で同じTC-IDとcheckpoint名を使い、操作手順と期待結果を定義する。既存テストがあれば再利用できる部分を確認する。実装から推定した期待結果と、仕様・利用者確認で確定した期待結果は区別する。

ケース一覧には最低限、TC-ID、画面、ロール、前提データ、操作、期待結果、checkpoint、区分、更新有無、復元方法を記録する。

画面に応じて、初期表示、代表的な検索、一覧の値・件数・順序、詳細表示、ページ切替、入力バリデーション、Webダイアログ等を選ぶ。APIへの直接要求のケースは作らない。一方で、APIの母数（`apis`）の到達する呼び出し箇所に対応するケースが無ければ、それを呼ぶ画面操作のケースを足す（ダイアログの中のサブダイアログ、コード入力時の照会、選択肢の読み込みは抜けやすい）。

- 到達可能なロール・表示モードの組合せごとに、最低1つの正常系TCを対応付ける。対応するTCがない組合せは、マニフェストに理由を書く。
- 必須入力フォームを持つ操作に限り、「必須項目あり成功」と「必須項目なしのバリデーションエラー」の2パターンを作る。
- 検索・一覧・帳票出力では、0件を代表ケースにしない。内容を比較するのが目的であり、0件では検証にならない。事前に画面で実データを確認し、複数行・複数ページが出る条件を選ぶ。0件表示そのものを確認するTCは別に1つ作る。
- 一覧は、自由記述のように空になりがちな列にも値が入っている行を選ぶ。値が1件もなければ、その列は「未検証」と記録する。値の有無を確認せずに「一致」と判定しない。
- 同一分岐・同一データ範囲を重複して記録するTCを増やさない。複数ロールで同じ検証構造を繰り返す場合は、パラメータ化して1つのテスト関数にまとめる。
- テスト実装時に、各TCについて「このテストを失敗させる変更は何か」を1つ言えるようにする。言えない場合は、表示有無だけのアサーションなので、観点を設計し直す。
- データに依存する候補（未登録の題目、別区分で登録済みの題目、特定の教員等）は、区分名などの思い込みで決めず、specの中で実行時に画面の検索結果から選ぶ。選んだ値（コード・名称）と、選んだ根拠の件数をcheckpointの値に保存する。候補が無ければ、そのTCは失敗として扱い、データの事情を報告する（条件を緩めて通さない）。
- 期待結果は、別の検索結果から導ける形にすると強くなる（例：範囲で絞った結果＝範囲なしの結果のうち該当する行の集合）。「1件以上出る」だけにしない。
- 検索条件は、中止・ダイアログを閉じる等では戻らないことが多い。ケースや手順ごとに、使う条件を毎回明示的に設定する（前の手順の状態に頼らない）。

ケースの前提データを、対象画面とは別の画面の操作で作る必要がある場合（例：時間割を作ってから題目の教員を変える）、その準備は既定では範囲外とする。更新系と同じ承認（環境・画面・操作・後始末）を得たときだけ行い、得られなければ「未実施（前提データなし）」として手段を提案する。

テストアカウントは既存の運用で用意されたものを優先する。必要な組合せ（担当範囲、データ件数）が既存アカウントや実データで用意できないと確認できた場合は、保留や対象外で止めず、利用者の承認範囲内で専用データを用意してケースを完成させる。その場合、マニフェストの該当項目に `testDataSource: "self-created"` と作成内容を書き、既存データでの検証と区別する。更新を伴う準備は、承認範囲と復元方法を先に確認する。

### 更新系ケース（登録・修正・削除）

登録・修正・削除も実行対象にする。ただし、既存の実データを壊さないため、次の条件で実行する。

1. 実行前に、次を確認し、manifestとcases.jsonに記録する。
   - ST・PTの両環境のデータが完全に同一であること。この条件を満たす場合に限り、両環境にテスト用データを書いてよい。同一性は、対象画面で参照するデータ（対象テーブル相当の件数、代表キー、ロール・担当の紐づき、採番状態）を画面または利用者提供の資料で突き合わせて確認し、確認方法と結果を記録する。確認できない、または差がある場合は、更新ケースを実行せず「未実施（データ非同一）」とする。
   - 対象画面・操作
   - 使ってよいテスト用データの範囲
   - **書き込みの範囲**：その操作が呼ぶ更新API（mutation）のサーバー実装を読み、対象の行以外に何を書くか（画面に表示中の既存行を再保存・更新するか、関連テーブルに書くか、通知を送るか）を確かめて記録する。表示中の既存行まで更新する実装なら、表示する行を最小にする検索条件を選ぶか、承認範囲を利用者に確かめ直す。

   単一環境の実行（PTだけの試行など）では、両環境のデータの同一性は「対象外（単一環境）」と記録し、代わりに実行前の件数・代表キーを画面で記録する。その環境に書いてよいかは、利用者の承認（環境・画面・操作・データの範囲・後始末の方法）だけで決まる。同一性の条件が無いことを、承認なしに書いてよい理由にしない。
   - **画面から消せない書き込み**（操作ログ・履歴・採番の消費など、後始末の画面操作では元に戻らないもの）があれば、承認を求める文面に「何が・何件・どこに残るか」を書き、承認を得てから実行する。実行後は残った内容を report.html と comparison.json の注意欄に記録する。

   実行できず「未実施」とした更新ケースには、必ず実施する手段の提案を付ける（後述の「未実施の扱い」）。
2. 更新の対象は、テスト用に作成したデータだけにする。名前・コード等に、実行ごとに一意で識別できる接頭辞（例: `E2E-<run-id>-`）を付ける。既存データの修正・削除は、専用に用意され、承認された範囲のものに限る。接頭辞で絞れない削除対象は実行しない。
   ただし、コードに接頭辞を付けられない場合（既存のマスタを紐づけるだけの登録、例：既存の授業題目をWEB履修登録の対象に加える。固定形式で採番するコード、例：科目コード＋2桁）は、「実行前の再検索で未登録・未使用だった、承認範囲内の1件のコード」を識別子とする。名称など自由入力の項目があれば、そこには接頭辞を付ける。そのコードを押す前に状態ファイル（例 `update-state.json`）に記録し、後始末はそのコードの1件だけを対象にする。重複チェックが壊れていて二重に登録された等、自分の行を区別できない状態になったら自動で消さず、利用者に知らせる。
3. 登録・修正・削除は、1つのライフサイクルとして並べる（登録→再検索して確認→修正→再表示して確認→削除→再検索で消えたことを確認）。前のTCの成功を後のTCの前提にするため、依存関係をcases.jsonに明記し、前段が失敗した場合は後段を「未実施（前段失敗）」とする。
4. 成功メッセージだけで成功としない。保存後に、画面で再検索・再表示して、値（全項目）が反映されたことを確認する。削除は、一覧から消えたこと、再検索でも出ないことを確認する。
5. バリデーションエラー等で保存されないはずの操作は、保存されていないことも再検索で確認する。
6. 各更新TCに、後始末（クリーンアップ）手順を定義する。テストが途中で失敗しても、自分が作った接頭辞付きデータだけを、画面操作で削除する。Playwrightの `afterAll` ではテスト単位のfixture（page）が使えないため、後始末はライフサイクル（`test.describe.serial`）の外に置いた最後のテスト（例 `CLEANUP`）にし、前段が失敗しても必ず走るようにする。後始末のテストは、残っていなければ「残存なし」を再検索で確かめて記録する。クリーンアップに失敗した場合は、残存データの識別子と場所を `native-handoff.md` ではなく `comparison.json` の注意欄とreport.htmlに記録し、利用者に伝える。
7. 自動再試行は0とする。結果が不明（成功メッセージが出たか分からない）のときは、再実行する前に、画面で再検索して、データが作られたか・消えたかを確認する。
8. ST・PTで、同じTC-IDと同じ操作・同じ入力値（接頭辞・コード・名称を含む）を実行し、保存結果を比較する。両環境のデータが同一であることが前提なので、環境ごとに値を変えない。ただし、STとPTは別のデータベースであり、同じレコードを共有しない。片方の環境で更新が完了してから、もう一方を実行し、各環境の実行前の状態が同じであることを確認する。実行前にすでに差が出ている場合は、「比較不能」とする。
9. 生成日時・採番ID・更新日時は、既知の揺らぎとして、限定した規則で正規化する。値の除外やマスクを広げない。
10. 外部送信（メール・通知）、実印刷、一括処理、取り消せない外部連携を伴う更新は、テスト準備の名目でも追加しない。対象画面の更新操作がそれらを伴う場合は、そのTCを `excluded` または「未実施」として理由を記録する。
11. 更新系は、記録深度を必ず「フル」にする。

### 未実施の扱い（実施する手段を必ず提案する）

更新ケースに限らず、「未実施」「比較不能」と判定したケースは、理由だけで終わらせない。report.html とケース一覧の該当行に、実施できるようにする手段を提案として添える。提案は、実行者・必要な承認・見込みの手間が分かる形にする。

| 未実施の理由 | 提案の例 |
|---|---|
| データ非同一 | 両環境のデータを揃える依頼（データ同期・復元元の指定）。差が一部の項目だけなら、その項目に依存しない代替ケースの追加 |
| 承認待ち | 承認が必要な範囲を最小化した依頼文（環境、画面、操作、テストデータの接頭辞、後始末の方法） |
| 前段失敗 | 前段の失敗原因の切り分けと、前段だけの再実行 |
| 認証待ち（MFA・SSO） | 認証準備の時間枠の確保、テスト用アカウントでMFAを免除する設定の依頼 |
| native-required | `cs-native-regression-test` での実施、専用PC/VMの手配、無人出力フォルダの事前設定 |
| 接続失敗・環境エラー | ポート・プロファイルの切り分け手順、環境担当への確認事項 |
| 取り消せない外部連携を伴う更新 | 送信先をテスト用に切り替える設定、または送信直前までのケースへの分割（利用者の承認が必要） |

提案は実行しない。提案を採るかどうかは利用者が決める。

削除・修正の前後の状態は、DOMから構造化して保存する。内部APIの応答や、DB直接照合を、保存結果の確認に使わない。

## テストハーネス

0. 本格実装の前に、フル深度の代表画面1つで、次を小さく実証してreferenceに記録する。未実証のまま全画面へ展開しない。
   - 環境変数によるCDP有効化が効くか（MainFormが `AdditionalBrowserArguments` を自前で指定していれば上書きされ得る）
   - 無人で認証を通せるか、起動のたびに閲覧データが消える条件での認証準備方法
   - screenshot・download・traceがCDP接続で取れるか
   - 起動時のフォーカス奪取・ネイティブダイアログ・外部起動の有無
   - 実機のexe・DLL・Web版の版が、リポジトリの現行ソースと一致するか。共有コンポーネントが先行して移行済み、または未デプロイの場合があるため、ソースだけを根拠に期待結果を決めない
1. 既存gakumuの設定を上書きせず、CS専用のconfig/fixture/specを分ける。通常のブラウザ用 `page` fixtureを実WebView2に接続したものへ置き換える。Allcampusでは実証済みのハーネス（`frontend/gakumu/e2e-cs/`：起動・CDP接続・操作ヘルパー・API記録・レポート生成）があれば、それを使い、画面ごとに `e2e-cs/<Screen>/` を足す。新しく作り直さない（構成と使い方は reference）。起動・接続・記録・レポートは実証済みなので、手順0の実証は繰り返さない。画面固有の部品（その画面のダイアログ・入力部品・一覧）は、specを書く前に読み取りだけの探索スクリプトで構造と挙動を確かめる（referenceの部品表に無いものは、確かめた結果をreferenceに足す）。
2. テスト起動プロセスに限定して `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=<空きポート>` を渡す。恒久的なOS環境変数にしない。CDPはローカルでのみ利用し、外部公開しない。
3. 環境別・実行別にプロセス、CDPポート、プロファイル、出力先を分離する。アプリの一時プロファイル管理を確認し、対応していない上書き設定を推測で使わない。userDataFolderをTEMPの下に固定で作るアプリでは、子プロセスにだけ専用の `TMP`/`TEMP` を渡して利用者の作業用インスタンスと分ける（同じuserDataFolderを共有すると、既存のブラウザプロセスに相乗りして環境変数が効かない）。
4. 起動したPIDを記録し、CDP準備を期限付きで待つ。起動失敗・ポート衝突・未接続はテスト環境エラーとして扱う。
   - 各実行の前に、PIDの生存とCDPの `/json/list` に対象ホストの `/CS/` があることを確かめる。テスト用インスタンスは記録を残さず終了することがあり、日をまたぐと使えない。消えていたら、前の結果を流用せず、起動とログインからやり直す（新しいrun-idにする）。
   - 実行中にインスタンスが消えた（`Target page, context or browser has been closed`）ら、以降のケースを止め、消えた時刻を記録する。
5. `chromium.connectOverCDP()`で接続し、既存contextのページから対象ホスト・パスで選ぶ。最初のpageを無条件に採用しない。ログイン中はそのcontext内の認証ページを扱い、認証後に対象画面を選び直す。
6. 正しいPT/STのURLと画面見出し、実アプリのhost objectの存在を確認する。通常ブラウザへの差し替え、host objectのモック、API応答のモックで成功させない。
7. ログインは実CSアプリ内で行う。通常ブラウザのstorageStateをコピーするだけで認証済みとみなさない。起動時にデータを消すアプリでは実インスタンスごとに認証を準備する。
8. `workers: 1`で環境ごとに逐次実行する。更新ケースの自動再試行は0とする（手順は「更新系ケース」参照）。
   - `use.actionTimeout` を必ず設定する（例 60秒）。未設定だと、隠れた要素への操作がテスト全体の時間切れまで無言で待つ。検索などの長い待ちは、操作ではなく専用の待ち（読み込み表示の消失）で別に長く取る。
   - 各ケースの開始時に、前のケースが失敗して残したダイアログ・確認ダイアログを閉じてから画面を開き直す。確認ダイアログは「いいえ」があれば必ず「いいえ」（登録の確認で「はい」を押さない）、ボタンが1つの警告・エラーだけ閉じる。閉じ方が分からないものが残っていたら止める。
   - 画面は毎ケース、ポータルからメニュー操作で開き直す（同じルートへの遷移では画面が作り直されない）。遷移の直後は読み込み表示がメニューを覆うことがあるので、消えてから操作する。
   - spec・ヘルパーを直したら、結果をまとめる前に全ケースを同じコードで流し直す。更新系だけは書き込みを増やさないよう、直した箇所を使わないケースは再実行せず、その旨を報告書に書く。
9. 終了時は接続、環境変数、出力設定等を後始末する。終了対象は今回起動したPIDだけに限定し、同名プロセス一括killやユーザーのアプリ終了はしない。

Playwright/CDPの対応機能は採用バージョンで小さく確認する。スクリーンショット、trace、downloadが利用できると決めつけない。必要な証跡が取れなければ制約を記録し、未実施項目を成功扱いしない。

## 実行と証跡

意味のあるDOM条件で待つ。検索結果の値・表示件数、loading消失、ダイアログ表示等をアサートし、固定sleepや `networkidle` だけで完了としない。OSキーボード送信を避け、DOM locatorの `fill`、`click`、`selectOption` 等を使う。

加えて、共通の操作ヘルパーは、クリック・入力・選択・タブ切替等あらゆる操作の直後に0.5秒（`page.waitForTimeout(500)`）の固定待機を入れてから次へ進む。ダイアログの開閉などでopacityが切り替わる途中の描画を拾い、崩れた撮影や不安定な待機で失敗するのを防ぐ目的である。この固定待機は安定化の補助であり、完了判定の代わりにはしない。DOM条件のアサートは必ず併用する。個別のspecで操作ごとに待機を書かず、ヘルパーに集約し、待機時間は設定値として1か所で変更できるようにする。

撮影前に環境ホスト、画面パス、見出し、checkpointの期待要素を確認する。IdP・ログイン・desktopOnly・エラー画面への遷移は成功にしない。body表示だけの確認は不十分。

checkpointは「撮影と値の保存 → 判定」の順に書く。判定を先に書くと、失敗したときの画面が残らない。失敗した実行の証跡は、直して再実行する前に別フォルダ（例 `_failed-<時刻>`）へ退避して残す。

スクリーンショットは成功時も指定checkpointで明示取得する。WebView2の実サイズを記録し、比較する両環境の解像度・DPI・サイズ・ズーム・ロケールを揃える。サイズを揃えるために利用者のウィンドウを勝手に動かさない。

ダイアログ・固定オーバーレイは現在のviewportで撮影する。証跡のためにCSS、opacity、レイアウト、viewportを強制変更しない。表示が落ち着く条件で待ち、取得画像を開いて意図した状態が写っていることを確認する。

DOMから表示値を構造化して保存してよい。非表示ストアや内部API応答をDOM回帰の代替の比較対象にしない。traceを採る場合は診断用であり、通信内容をAPI比較へ流用しない。機微情報が含まれるため共有前に内容を確認する。

### サーバー側のログを合格条件に含む依頼のとき

依頼の合格条件に「サーバーの監査ログ・アクセスログに拒否・エラーが無いこと」が入っている場合、本スキルはログを読まない（API・DBの調査に広げない）。代わりに、ログ側で突き合わせるための鍵を残し、集計結果を受け取って判定に入れる。

1. checkpointごとに、TC-ID・checkpoint名・段階ラベル・アカウント区分・開始と終了の時刻（Asia/Tokyo、ミリ秒）を `cases.json` に記録する。実行の始めに、PCとサーバーの時刻差（応答の `Date` ヘッダーとPCの時刻の差）を測って manifest に書き、集計する側が時刻の範囲を補正できるようにする。
2. 操作中に送った API の記録は「APIの呼び出し網羅」と同じものを使う（常に取る）。ログ側との突き合わせには、その時刻と `operationName` を渡す。
3. ログの集計（例：時刻の範囲ごとの拒否・エラーの件数）は依頼側の担当者が行い、結果のファイルを受け取る。集計の方法は本スキルで決めない。
4. 判定：集計結果でそのcheckpointの時刻の範囲に拒否・エラーがあれば「要確認」。集計結果がまだ無いcheckpointは「一致」にせず「未実施（ログ集計待ち）」にする。

帳票は通常の画面操作から、ネイティブUI・外部アプリなしで専用フォルダへ出力できる場合だけ対象とする。ダウンロードイベントを操作前に登録するか、専用出力先の新規ファイルと書込み完了を待つ。前回のファイルを今回の成果物と誤認しない。直接ダウンロードAPIを叩いて代替しない。

CSVは列・値・件数を比較し、順序が仕様なら順序も比較する。PDFは文字内容と必要なレイアウトを比較する。生成日時等の既知の揺らぎだけを明示した規則で正規化し、原本を保持する。ファイル存在だけでは帳票成功としない。

セッションにつき1つの保存先へ集約する。

```text
evidence/<run-id>/
  manifest.json
  cases.json
  launch-<ENV>.json          # 起動したPID・CDPポート・exeの版・TEMP・ログイン方法
  ST/<screen>/<TC-ID>/<checkpoint>.png
  PT/<screen>/<TC-ID>/<checkpoint>.png
  PT/<screen>/<TC-ID>/result.json   # 状態・checkpointの時刻・apiCalls
  PT/update-state.json       # 更新系で作ったデータの識別子と後始末の結果
  judgements.json            # 判定の上書きと原因・提案（人が書く）
  comparison.json
  native-handoff.md
  report.html
```

各ケース配下に表示値・出力原本・実行結果・診断証跡を必要に応じて保存する。ST/PTのラベルと比較元/先の対応はmanifestに記録する。manifestにはURL、バージョン（exe・DLLの版と、画面に表示されるWeb版の識別子）、実行日時（Asia/Tokyo）、表示条件、データ前提、正規化規則、証跡パスを含める。秘密値は含めない。トークン付きのURLは伏せ字にして記録する。

実行日時・所要時間は、`result.json` のcheckpointの記録（UTC）をAsia/Tokyoに直して書く。記憶や推測で書かない。Web版は同じ日でも再デプロイで変わるので、画面の表示を実行のたびに読む。

証跡・認証ファイル・生成帳票はgit管理対象外にする。既存のignore規則を確認し、不足時だけ実際の保存先を除外する。個人情報やトークンを含む画像・trace・HTMLを無確認で公開しない。

## 比較と完了判定

TC-ID × checkpoint単位で両環境の証跡・期待結果を突き合わせる。画面全体のファイル数合計で完全性を判断しない。対応確認はcasesと実行結果・ファイル一覧を走査して機械的に集計する。

| 判定 | 基準 |
|---|---|
| 一致 | 比較可能な前提で、期待結果と両環境の値・操作結果が一致（サーバー側のログを合格条件に含む依頼では、集計結果にも拒否・エラーが無い） |
| 意図した差分 | 承認済み仕様・変更記録で説明できる差分。根拠を記録 |
| 要確認 | 未説明の値・表示・動作差、期待結果違反 |
| 比較不能 | データ・ビルド・表示条件が揃わず、比較が成立しない |
| 未実施 | native-required、認証待ち、接続失敗、証跡欠落等 |

単一環境の実行（PTだけの試行、段階比較のベースライン取得など）は比較が成立しないので、判定は「期待どおり（期待結果を満たし、APIの呼び出しもエラーなし）／要確認／未実施」にする。「一致」は使わない。

どちらの場合も、画面の期待結果を満たしていても、そのケースが送ったAPIにGraphQLエラーまたは200以外の応答があれば「要確認」にする。

要確認の原因は、テスト側（ハーネス・期待値の誤り）とアプリ側に切り分けてから書く。アプリ側の候補は、該当するソースの行と、そう判断した根拠（記録・画像・コード）を添える。エラーの中身を記録しない取り決めのため、原因の説明がコードからの推定であればそう書く。

件数差を直ちに不具合または意図した差分としない。前提データを画面・提供資料で確認し、揃えられなければ比較不能にする。API/DBへの調査へ勝手に拡張しない。STの結果を自動で正解とせず、両環境に共通する不具合も期待結果で検知する。

失敗はアプリ不具合候補、テスト実装の問題、環境/認証問題に分けて記録する。元の失敗証跡を保存し、期待値を緩めたりbaselineを更新して緑にしない。テスト側の修正が必要なら根拠・変更・再実行結果を残す。アプリコードを本スキルで修正しない。

同じテストコードを変更せずにST・PTの両方へ実行し、両環境で成功したことを完了条件にする。片方だけを通すための `test.skip()` / `test.fixme()`、早期return、アサーションの緩和は禁止する。PT側だけ失敗する場合は、先にアプリ側の差分を疑い、期待値の記録ミスと判明した場合に限りテストを直す。環境・ビルドの対応（`E2E_TARGET` 等）は環境変数で外部化し、URLやホストをspecに直書きしない。

マニフェストの全項目が、次のいずれかに確定していることを機械的に集計して確認する。「実行済みで一致・意図した差分（単一環境は期待どおり）」「native-required（引継ぎ済み）」「auth-wait（期限・再開条件付き）」「excluded（理由と根拠付き）」。カバレッジ率の数値目標では判定しない。

`apis` の到達する呼び出し箇所が、すべて「確認」「記録なし（画面で確認、理由付き）」「要確認（原因付き）」のいずれかに確定していることも、同じく機械的に集計して確認する。期待を書いていない（`expectAt` が無い）到達する呼び出し箇所が1つでも残っていれば未完了。

単一環境の実行（PTだけの試行など）は、上の「両環境で成功」を「その環境で、同じテストコードの全ケースが期待どおり、または原因付きの要確認・手段付きの未実施に確定し、`apis` の網羅も確定している」に読み替える。新旧の比較は完了していないので、報告では「単一環境での確認の完了」と書き、「回帰テストの完了」と書かない。

完了はwebview区分の対象ケースについて両環境の実行・比較・証跡確認が揃い、要確認や比較不能が解消された状態。native-requiredが残る場合は「WebView2回帰の完了」と「CS全体E2Eの未完了」を分けて報告する。

report.htmlにはケース別結果、両環境の画像、値の差分、意図した差分の根拠、未実施理由、「画面が呼び出すAPIの一覧」と「テストとAPIの対応表」を含め、ローカルに保存する。外部サービスへの投稿はこのスキルの必須工程にしない。報告前に、生成したreport.htmlを開いて（ヘッドレスのブラウザで撮影してもよい）、表が崩れていないこと・画像が空でないことを確かめる。

native-handoff.mdにはTC-ID、画面、両環境の版、直前までの操作、発生するWindows UI、必要な操作、期待結果、出力先、データ復元方法、証跡パスを記載する。引継ぎ対象が0件ならその旨を記録する。

## よくある誤り

- ブラウザでCS判定を偽装して、実アプリE2Eとして報告する。
- 非占有のUIAならよいとしてFlaUIを混ぜる。Windows操作はすべて別実行へ分ける。
- 出力ボタンを押した時点で帳票成功とする。ファイルの完成と内容確認まで必要。
- MFA待ちやネイティブ未実施をskipして、全件成功として集計する。
- データ差をスクリーンショットの広いmaskや値の除外で消す。正規化対象と根拠を限定する。
- 既存campusスキルのAPI比較や認証経路をgakumuへそのまま持ち込む。
- 検索・一覧・帳票のケースで、0件の状態をそのまま証跡にする。
- 一覧の一部の列だけをアサートして、一致と判定する。詳細画面の一致は、一覧の一致を保証しない。
- マニフェストを作らず、「記録した」という自己申告で終わらせる。
- 軽量深度を、担当範囲・個人情報・更新を伴う操作にまで広げる。
- 更新ケースで、成功メッセージだけを見て保存成功とする。
- 接頭辞で識別できない既存データを、修正・削除の対象にする。
- 更新テストが失敗しても、後始末をせずに終わる。または、結果不明のまま再実行して二重登録する。
- 両環境のデータが同一であることを確認せずに、登録・修正・削除を実行する。
- 未実施・比較不能の理由だけを書いて、実施する手段の提案を添えない。
- 実データやアカウントが揃わないことを理由に、ケースを保留のまま残す。
- CDPやdownload・traceの可否を実証せずに、全画面のテストを書き始める。
- 操作後の0.5秒固定待機を省略して、遷移途中のダイアログを撮影する。逆に、固定待機だけで完了とみなし、DOM条件のアサートを省く。
- ネイティブのログイン画面を理由に、人がログインする auth-wait にする、またはspecの中でFlaUIを呼ぶ。ログインは前処理で通してから接続する。パスワードの自動入力が安全規則で許されないときは、起動したテスト用インスタンスへの手動ログイン（認証準備）に切り替え、規則を回避しない。
- ケースの網羅だけで報告し、画面が呼ぶAPIの一覧とテスト×API対応表を出さない。
- 画面が正常に見えたので一致・期待どおりとし、APIのGraphQLエラー（HTTP 200）を見落とす。
- ダイアログの中のサブダイアログ・コード入力時の照会・選択肢の読み込みなど、ボタン1つ奥のAPIにケースを対応付けない。
- テストデータの候補を区分名などの思い込みで決める（例：その年度に前期の登録がある前提）。実行時に画面から選ぶ。
- `actionTimeout` を付けずに、隠れた要素への操作でテストが時間切れまで止まる。
- 前のケースが残したダイアログのせいで後続が全滅する。ケースの開始時に片付ける。
- 判定を撮影より先に書き、失敗時の画面を残さない。
- 報告の実行時刻を記憶で書く。`result.json` の記録から転記する。
- 更新の前に、その操作が対象行以外に何を書き込むかを確かめない。
- 記録を取るためだけに、承認を取り直さず更新系を再実行する。
- 段階比較で、ST・PTが無いことを理由に完了条件を満たせないと判断する。ベースラインと比較先に読み替える。
- 母数に画面やコンポーネントを足した後、取り直していない古いベースラインと比べる。
- サーバー側のログの集計結果が届く前に、画面が一致したというだけで「一致」にする。
- 操作名の記録のついでに、variables や応答の本文を保存する。
