# 1. 協議で決まっていること（2026-09-10）

| 区分 | 内容 |
|---|---|
| 体制 | 信大インシデントのテストは品質保証チームへ全面委譲。開発陣とのやり取りも直接行う |
| 正常系 | Playwright で自動化。各画面でできる操作・分岐（タブ、ラジオによる表示切替等）を一通り実施 |
| 異常系 | 「必須項目あり／なし」の2パターンのみ。組み合わせは実施しない |
| 組み合わせ・細かいエラー | 単体テストでカバーする |
| モック | 使わない（数画面で試作したが不要と判断） |
| モンキーテスト | 当面やらない |
| 判定の考え方 | 是正前後で同じ画面・同じデータが出ること。位置づけは回帰テスト |
| リリース | 一括リリース。コンポーネントが共通のため段階リリース不可 |
| 担当割り | フォルダ／スキーマ単位（シラバス、検診 等）。共通コンポーネントは全体完成後 |
| エビデンス | 単体テストぶんの画面キャプチャは取らない方向 |

## 1.1 協議で挙がった技術的リスク

> 作り変えによってコンポーネント名・関数名が変わると、現行環境で作った Playwright シナリオも単体テストクラスも新環境で動かない。

| # | 内容 |
|---|---|
| 1 | 現行環境で3画面ほどテストコードを作成中。夜間に新旧同じものを流して結果を比較する想定 |
| 2 | 要素の指定（関数名・コンポーネント名）が変わると同じシナリオが流せず、比較そのものが成立しない |
| 3 | 1週間ほど前にポータルのコードが大きく変更された実例がある |
| 4 | 対策案として、要素の指定を日本語ラベルベースで作る方法がある。ただしテストの信頼性は落ちる |

## 3.4 操作の深さ

単位を「画面の操作」ではなく「画面が呼ぶAPI操作」に置く案。

> その画面が呼ぶAPI操作を、すべて1回ずつ発火させる最短の操作列を通す。

ケースを分ける基準は「発火するAPI操作が変わるかどうか」のみ。

| 状況 | 分けるか |
|---|---|
| 新規追加と既存更新が別操作 | 分ける |
| 削除・取込（CSV）が別操作 | 分ける |
| 検索条件の有無で呼ぶ操作が変わる | 分ける |
| 入力値が違うだけ | 分けない |

## 3.5 「画面に出てはいけないもの」の3段階

| 段 | 定義 | 判定方法 |

| レベル1 | 未使用と確定したフィールド（全体の79.7%）が含まれていたらNG | 画面ごとの一覧があれば目視 |

# 4. 配布スキル `regression-test` の内容

## 4.1 仕様

| 項目 | 内容 |
|---|---|
| 道具 | Playwright（MCP 経由） |
| シナリオ | `frontend/campus/src/router/routes.ts` を解析し、`path` / `name` / `meta.roles` から自動生成。生成後に人がレビュー・編集する前提 |

## 5.1 フロント側で新旧比較が成立する理由

開発方針として次が共有されている。

| # | 内容 |
|---|---|
| 1 | サーバ側のキャンパス情報システム利用APIをすべて複製し、別フォルダへ配置する |
| 2 | 共通関数は使わず、それぞれのフォルダに作成する |
| 3 | フォルダ間での共有はしない。**ただしコンポーネントは共有する** |

層ごとの成立可否。

| 層 | 是正後の扱い | 同一テストの実施 |
|---|---|---|
| コンポーネント（Vue） | 共有される | 成立する。テスト対象そのものが変わらない |

| サーバ側 controller | 新設 | 成立しない。是正前に対応物がない |
| サーバ側 service / DAO | 複製される | 成立しない |

## 5.3 現在のテストで検出できない事象

サーバの応答を丸ごと偽物に置き換え、その内容をテスト側が手書きしている。

```
getOwnAffiliation: vi.fn().mockResolvedValue({ nenji: "2", shozoku1Kubun: "1" })
```

この値に型の指定がないため、実際の専用サービスが返す内容と食い違っても検査されない。

| # | 経過 |
|---|---|
| 1 | 是正で専用Payloadを絞る際に `shozoku1Kubun` が落ちる |
| 2 | 専用サービスの型宣言も `nenji` のみに変わる |
| 3 | テストの偽データは両方を返し続ける |
| 4 | 画面部品は `shozoku1Kubun` を読んで初期チェックする処理を持つ |
| 5 | **テストは合格する。実環境では初期チェックが効かない** |

型チェック用スクリプトが未定義で、Vitest は型を落として実行するため、`npm run test` では型エラーが検出されない。

## 5.4 値が画面へ届くまでの経路と確認状況

```
サーバのPayloadクラス（Java）
    ↓
GraphQLスキーマ（.graphqls）
    ↓
フロントの型宣言（手書き）
    ↓
テストの偽データ（手書き）
```

| つなぎ目 | 確認手段 | 状況 |
|---|---|---|
| Payloadクラス ↔ スキーマ | Javaの型 | 自動的に効く |
| スキーマ ↔ フロントの型宣言 | **`capi-check`** | **機械チェックが存在する**（6.2）。ただし CRLF 不具合・CI 未組み込み |
| フロントの型宣言 ↔ テストの偽データ | ─ | **手段が無い。`capi-check` はテストコードを見ない** |

> v0.3（`20260910_単体テスト活用方針_検討結果.md`）§6.4 は「スキーマ照合ツールの作成が必要」としていたが、**`capi-check` として既に実装されている**。本書で更新する。

## 5.5 ダミーデータで等価性が言える範囲

> 同一のテストコードと同一のダミーデータを、是正前と是正後の双方へ実施し、双方とも同じ結果になること。

| # | 成立条件 |
|---|---|
| 1 | 確認内容が是正前後で同一であること |
| 2 | ダミーデータが実物の型と一致していること |
| 3 | どの入力を通したかが記録に残ること |

限界は、実運用データがダミーの範囲外の形（想定外のnull、桁あふれ、未登録の区分値）を持つ場合、その範囲が未確認のまま残ること。

| 手段 | 言える内容 |
|---|---|
| 単体テスト（ダミーデータ） | 規則の等価性。同じ条件なら是正前後で同じ振る舞いをする |
| Playwright・`regression-test`（実環境） | 事実の等価性。実際に開いた画面が同じになる |
