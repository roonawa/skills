# SKILL.md 対話作成支援

## 目的と適用範囲

利用者との対話で必要な情報を整理し、別のエージェントが実行できる新規スキルを作る。
対象はSKILL.mdが存在しない場合、または空・雛形だけの場合。既存の内容があるSKILL.mdの改善・レビューは対象外として案内する。

目的・適用条件の整理、本文と必要な付属ファイルの作成、形式確認、机上確認、保存を行う。
サブエージェントによる圧力シナリオテスト、デプロイ、git commitは標準フローに含めない。追加で依頼された場合は別の作業として扱う。

## 対話の進め方

- 最初に依頼文と提供資料から既知の情報を整理する。回答済みの事項を再質問しない。
- 質問は原則1問ずつ。密接に関連する短い項目はまとめてもよい。利用者が一括回答を望む場合は合わせる。
- 「提案して」と言われた場合や判断材料が不足する場合は、選択肢と推奨理由を示す。
- 対象外の範囲は必ず整理する。ただし、既に分かっていれば改めて質問しない。
- 重要な未確定事項と、後から変えられる仮定を区別する。成果物・権限・外部操作に影響する不明点は確認し、軽微な構成判断は仮定を明示して進める。
- 必要な情報が揃えば草案へ進む。全質問の消化や、段階ごとの定型的な承認を目的にしない。

## 1. 目的と使用場面を整理する

不足している項目だけを聞く。

- このスキルがないと、誰がどの場面で何に困るか。
- 繰り返し使う見込み、他者への共有、手順の再現性など、スキル化する価値はあるか。
- どんな依頼・症状・キーワードで使うか。似ているが対象外の依頼は何か。
- やることとやらないこと。既存スキルに任せる範囲はあるか。

一回限りで再利用の見込みも乏しい場合は、通常の依頼文や手順書で済ませる案を示す。ただし、利用者が理由を理解したうえでスキル化を希望するなら進める。

## 2. 入力・成果物・完了条件を確定する

以下を設計メモとして整理する。すべてを個別の質問にする必要はない。

| 項目 | 確定する内容 |
|---|---|
| 入力 | 必要なファイル、情報、形式、任意項目と既定値 |
| 情報不足 | 追加質問が必要な条件、仮定で進められる条件 |
| 成果物 | 内容、形式、保存場所または提示方法 |
| 完了条件 | 何を確認できれば完了か。未完了・未検証の扱い |
| 環境・依存 | 対象製品、ツール、必要な権限、参照資料・スキル |
| 手順・分岐 | 主要な処理、判断材料、分岐先 |
| 失敗時 | 入力不正、ツール不在、実行失敗時の対応と停止条件 |
| 外部への変更 | 書き込み・送信・公開などの範囲と、必要な承認 |

参照するスキル・ツールは対象環境で利用可能か確認する。必須依存が利用できず代替もない場合は、その箇所を未解決として示し、実行可能と扱わない。
作成の許可を、生成したスキルが将来行う送信・公開などの許可として扱わない。

## 3. 構成と具体例を選ぶ

エージェントが内容からタイプを判断する。分類名を利用者に選ばせる必要はない。混合型でもよい。

| タイプ | 本文の中心 |
|---|---|
| 技術：具体的な方法 | 入力から成果物に至る手順、分岐、検証 |
| 判断：判断の型 | 適用条件、判断基準、適用例と限界 |
| 情報：参照情報 | 情報の探し方、参照先、使い方、制約 |

代表的な入力と期待する出力を1組用意する。重要な分岐や対象外との区別が伝わらない場合だけ例を追加する。
コードを扱わないスキルには、無理にコード例を入れない。
よくある失敗と回避方法を集める。フローチャートは判断の分岐を理解しやすくする場合だけ使う。

### 付属ファイルの判断

固定の行数だけで分割しない。

- 常に必要な適用条件・主要手順・制約はSKILL.mdに置く。
- 特定の場面だけで読む詳しい資料は `references/` に置く。
- 繰り返し実行する処理や、機械的な検証に有用なコードは `scripts/` に置く。
- 成果物に使うテンプレート等は `assets/` に置く。
- 本文から相対リンクを張り、いつ読む・使うかを明示する。必要性のないフォルダは作らない。

## 4. SKILL.mdを作成する

### 公式仕様上の必須条件

[Agent Skills仕様](https://agentskills.io/specification)を基準にする。仕様の変更が疑われる場合は一次情報で確認する。対象製品固有の制約は共通仕様と区別する。

- YAML frontmatterに文字列の `name` と `description` を置く。
- `name` は1〜64文字。小文字の英字 `a-z`、数字 `0-9`、ハイフンだけを使用する。
- `name` の先頭・末尾のハイフン、連続ハイフンは禁止。親ディレクトリ名と一致させる。
- `description` は空でない1〜1024文字の文字列。1024文字はfrontmatter全体の上限ではない。
- YAMLとして有効にする。コロン等で値の解釈が変わる場合は引用符やブロックスカラーを使う。

### このスキルでの推奨方針

以下は公式仕様の必須条件ではない。

- 名前は短く、用途を推測できるものにする。動名詞形への統一は必須にしない。
- descriptionは「何ができるか」と「いつ使うか」を簡潔に書く。混同しやすい対象外も必要に応じて添える。
- `Use when ...` 形式は選択肢の一つ。詳細な作業順序や本文の代わりになる説明は入れない。
- descriptionは300文字以内を目安にし、短くても意味が通れば引き延ばさない。
- 本文は500行未満を目安に、判断に役立つ内容に絞る。上限を埋める必要はない。

### 構成例

必要な節だけを採用し、タイプに合わせて変更する。空の節や未記入の雛形を残さない。

```markdown
---
name: example-skill
description: "何を支援するか。どの依頼・状況で使うか。"
---

# スキル名

## 目的・適用範囲
使用場面と、混同しやすい対象外。

## 入力と前提
必要な入力、環境、情報不足時の対応。

## 手順・判断基準
入力から成果物までの処理と分岐。
Reference型なら参照先と利用手順を中心にする。

## 成果物・完了条件
出力形式と、完了の判断に使う確認方法。

## 具体例
代表的な入力と期待する出力。

## 失敗時の対応
よくある失敗、回避策、続行できない条件。
```

## 5. 形式と実行可能性を確認する

### 形式・整合性チェック

- [ ] YAMLの構文、nameの文字種・長さ・ハイフン制約、ディレクトリ名との一致を確認した。
- [ ] descriptionの長さ、能力と使用場面の説明、対象外との区別を確認した。
- [ ] 必要な入力・成果物・完了条件・失敗時の対応が記載されている。
- [ ] 手順の矛盾、未記入の雛形、不要な繰り返しがない。
- [ ] 参照ファイルが存在し、利用条件が分かる。必須ツール・依存関係の有無を確認した。
- [ ] 独自の推奨を公式仕様の必須条件として説明していない。

利用可能な検証ツールがあれば実行する。形式検証の合格だけで、発動や処理の正しさを証明したことにしない。

### シナリオによる机上確認

作成した本文だけを根拠に、以下を追跡する。作者が知っている未記載の前提で穴を埋めない。

| シナリオ | 確認すること |
|---|---|
| 代表的な対象内の依頼 | 適用対象と判断でき、入力から期待する成果物まで手順を追える |
| 似ている対象外の依頼 | 対象外と判断でき、不要な処理を始めない |
| 必須入力の不足 | 何を質問するか、どこまで進められるか決まっている |
| 主要な失敗・境界条件 | 停止・代替・再試行の判断と、利用者への報告が決まっている |

各結果を「シナリオ／期待する判断／本文の根拠／不足点」の形で短く整理する。
不足点があれば修正し、影響するシナリオを再確認する。共通の適用条件を変えた場合は全シナリオを再確認する。
新規・変更スクリプトがある場合は、許可された範囲で実行確認する。実行できないものは未検証として明示する。

机上確認は実際のエージェントでの動作テストではない。自動選択の成功や実環境での動作を保証したと表現しない。

### 確認例：議事録からTODOを抽出するスキル

- 対象内：「この議事録から担当者と期限つきのTODO一覧を作って」→ 元文を根拠に一覧化する。
- 対象外：「会議の招待メールを送って」→ 送信は対象外と判断する。
- 入力不足：議事録がない → 提供を求め、TODOを推測して作らない。
- 境界条件：期限の記載がない → 「未記載」と表示し、任意の日付を補わない。

これは確認方法の例であり、すべてのスキルにTODO抽出の規則を加えるものではない。

## 6. 提示・修正・保存

1. 草案と確認結果を提示する。形式確認・机上確認・実行確認・未検証事項を区別する。
2. 修正希望があれば反映し、影響箇所を再確認する。特定の「OK」という語句を要求しない。
3. 保存は依頼の範囲に従う。草案のみの依頼なら書き込まない。作成・保存まで依頼され、保存先も決まっていれば重ねて承認を求めない。
4. 保存先の指定がなければ、Claude Code用として `~/.claude/skills/<name>/SKILL.md` を提示し、不明な配置方針だけ確認する。別の環境が指定された場合はその配置規則に従う。
5. 書き込み直前に保存先を確認する。内容のある同名ファイルが見つかったら、新規作成の範囲では上書きしない。別名で作るか、既存編集として扱うかを確認する。
6. 保存後に再読込し、内容・ファイル名・参照先を確認する。失敗時は保存済みと報告せず、草案と失敗理由を提示する。

最後に保存先、主な設計判断、実施した確認、残る未検証事項を簡潔に報告する。
