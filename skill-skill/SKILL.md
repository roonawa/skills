# SKILL.md 対話作成支援

## 目的

対話形式で効果的な質問を重ねながら、ゼロから高品質なSKILL.mdを作成するためのスキル。
質問時に、「提案して」と言われたら、例となる回答の選択肢を提示する。

一発でSKILL.mdを書き上げると、目的やトリガー条件が曖昧なまま完成してしまい、
「発動すべき時に発動しない」「発動条件が広すぎて誤発動する」「本文が処理内容の作文になり手順としてなぞれない」
といった品質問題が起きやすい。段階的な壁打ちでこれを防ぐ。

frontmatterおよび命名規約は [agentskills.io/specification](https://agentskills.io/specification) に準拠する。

## スコープ

### やること
- 新規SKILL.mdの対話形式での作成（壁打ち→整形→セルフチェック→ブラッシュアップ→保存）
- 目的・課題のヒアリング（作る価値があるかの見極め含む）
- description用のトリガー条件の明確化（"Use when..."形式）
- スキルタイプ判定（Technique／Pattern／Reference）
- スコープ（やること／やらないこと）の壁打ち
- 構成・本文（具体例、フローチャートの要否、参照する既存スキル）の壁打ち
- 公式仕様準拠のfrontmatter生成
- セルフチェックリストによる品質確認
- ブラッシュアップサイクル（利用者の修正要望に応じた反復）
- 保存先の確認と書き込み

### やらないこと
- 既存SKILL.mdの読み込み・改善・レビュー（別スキル候補）
- サブエージェントを使った圧力シナリオテスト（superpowers:writing-skills方式のTDD的検証は対象外。品質確認はセルフチェックリストに留める）
- スキルのデプロイ・git commit（利用者から明示的な指示があれば行うが、自動では行わない）

---

## 全体フロー

```
[起動]
  ↓
① 目的・課題のヒアリング
  ↓
② トリガー条件・使用場面の明確化（description用）
  ↓
③ スキルタイプ判定（Technique／Pattern／Reference）
  ↓
④ スコープ壁打ち（やること／やらないこと）
  ↓
⑤ 構成・本文の壁打ち
  ↓ ループ：「他に深堀りしたい項目は？」
  ↓
【チェックポイント】整形に進む前の確認
  ↓
⑥ 整形フェーズ（SKILL.md生成）
  ↓
⑦ セルフチェックリスト実行
  ↓ 指摘があれば該当項目に戻って修正 → 再チェック
  ↓
⑧ ブラッシュアップサイクル（利用者の追加修正要望に応じ反復）
  ↓ 「これでOK」
  ↓
⑨ 保存先確認 → 書き込み
```

## ① 目的・課題のヒアリング

質問は**1問ずつ**投げる。

1. 「このスキルが無いと、具体的にどんな困りごとが起きる？」
2. 「それは今回限りの話？それとも今後も繰り返し起きること？」

回答が「今回限りの一回性の解決策」に近い場合は、以下を伝えて作成を思いとどまらせる。

> 「一回限りの対応であればスキル化のコストに見合わない可能性がある。今後も繰り返し使う見込みがあるか、もう一度確認したい。」

繰り返し使う価値があると確認できたら②へ進む。

## ② トリガー条件・使用場面の明確化

1. 「どんな状況・症状のときにこのスキルを開くべき？エラーメッセージ、具体的なキーワード、状況をできるだけ具体的に」
2. 「逆に、似ているけど対象外にしたいケースは？」

※ここで集めた内容はdescriptionの元になるが、**手順の要約にはしない**。整形フェーズで生成するdescriptionは
トリガー条件（症状・状況）のみを記述し、処理内容（どう解決するか）は書かない。
処理内容をdescriptionに書くと、エージェントが本文を読まずにdescriptionだけで済ませてしまい、本文の分岐や手順を無視する原因になる。

## ③ スキルタイプ判定

3つのどれに近いか確認する。判断が難しい場合は具体例を示して選ばせる。

| タイプ | 説明 | 例 |
|---|---|---|
| Technique | 手順を伴う具体的な方法 | 条件待ちのテスト手法、根本原因の追跡 |
| Pattern | 問題への考え方・思考モデル | データ構造のフラット化、テスト不変条件 |
| Reference | API・ツール・仕様のリファレンス | Office文書操作、外部APIの使い方 |

## ④ スコープ壁打ち

1. 「やることを箇条書きで挙げて」
2. 「やらないことは？他のスキルに任せたい範囲、意図的に対象外にしたい範囲を明確にしたい」

※「やらないこと」は必ず聞く。スコープ肥大化を防ぐための重要項目。

## ⑤ 構成・本文の壁打ち

1. 「具体例を1つ挙げるとしたら何が一番わかりやすい？（複数言語・複数パターンは作らず1つに絞る）」
2. 「利用者が判断を誤りやすい非自明な分岐はある？（あればフローチャート化を検討する。単なる手順の羅列なら不要）」
3. 「参照したい既存スキルはある？（あれば `REQUIRED SUB-SKILL: <skill-name>` 形式で明記する。`@`によるファイル直リンクはしない）」
4. 「よくある失敗・アンチパターンはある？（Common Mistakesセクションに載せる）」
5. 「別ファイルに切り出すべき重い参考資料や再利用可能なツール・スクリプトはある？（100行超の参照資料や実行可能ツールのみ切り出す。原則は本文に収める）」

### 深堀り完了後の確認

> 「ひと通り壁打ちが完了した。他に深堀りしたい項目はある？なければ整形フェーズに進む。」

- 「あり」の場合：該当項目に戻って追加質問を行う
- 「なし」の場合：整形フェーズへ

---

## ⑥ 整形フェーズ

壁打ちの内容を以下の構造に整形する。

```markdown
---
name: <skill-name-with-hyphens>
description: Use when <具体的なトリガー条件・症状>
---

# <Skill Name>

## Overview
<核となる考え方を1〜2文で>

## When to Use
<症状・使用場面の箇条書き。使わないべきケースがあれば併記>

## Core Pattern
<Technique/Patternの場合のみ。Before/Afterの比較や中核パターン>

## Quick Reference
<早見表・箇条書き>

## Implementation
<本文50行未満ならインラインのコード例。超える場合は別ファイルへのリンク>

## Common Mistakes
<失敗パターンと対処>
```

**命名規則：**
- `name`は英数字とハイフンのみ（括弧・特殊文字不可）
- 動詞先行のgerund形が望ましい（例：`creating-skills` > `skill-creation`）
- 「何をする」より「核となる着眼点」を表す名前を優先する（例：`root-cause-tracing` > `debugging-techniques`）

**description生成ルール：**
- "Use when..."から始める
- 第三者視点で記述する（"I can help..."は不可）
- 症状・状況・トリガー条件のみを書き、処理手順やワークフローを要約しない
- 300字以内を目安にする
- frontmatter全体で1024字以内に収める

整形後、いったん全文を提示し、⑦のセルフチェックに進む。

---

## ⑦ セルフチェックリスト

整形したSKILL.mdを以下の観点で確認する。指摘事項があれば該当箇所を修正し、再度全項目を確認する。

- [ ] `name`が英数字とハイフンのみで構成されている
- [ ] `description`が"Use when"で始まり、第三者視点で書かれている
- [ ] `description`がワークフロー・処理手順を要約していない（トリガー条件のみ）
- [ ] `description`が300字前後に収まっている
- [ ] frontmatter全体が1024字以内
- [ ] 具体例が1つに絞られている（多言語化・複数パターンの乱立がない）
- [ ] フローチャートは非自明な分岐にのみ使われている（単純な手順の羅列に使っていない）
- [ ] フローチャートのラベルに`step1`等の無意味な連番がなく、意味のある名前になっている
- [ ] ナラティブ調（「〜のセッションで見つけた」等、特定の1回の出来事の物語）になっていない
- [ ] 他スキル参照は`REQUIRED SUB-SKILL: <name>`形式で、`@`直リンクを使っていない
- [ ] Common Mistakesセクションに具体的な失敗パターンがある
- [ ] 100行を超える参照資料・再利用可能なツールは別ファイルに切り出されている

すべて満たしたら、修正結果を要約して利用者に提示する。

---

## ⑧ ブラッシュアップサイクル

セルフチェック完了後、利用者が「これでOK」と伝えるまで反復できる。

> 「セルフチェックを終えたドラフトができた。どこを修正したい？
> a. セクション単位で深堀り・修正
> b. name／descriptionの見直し
> c. 具体例の差し替え
> d. これでOK」

| モード | 動作 |
|---|---|
| a. セクション単位 | 対象セクションを指定させ、追加壁打ち→該当箇所のみ書き換え→⑦を再実行 |
| b. name／description | ②③の内容に戻って再確認→該当箇所のみ書き換え→⑦を再実行 |
| c. 具体例差し替え | 新しい具体例を壁打ちし、Implementation／Core Patternを差し替え→⑦を再実行 |
| d. OK | ⑨へ進む |

---

## ⑨ 保存先確認・保存

以下を確認してから書き込む。

1. 保存先パス（`~/.claude/skills/<skill-name>/SKILL.md`が既定）を提示し、利用者に確認する
2. ディレクトリ名が`name`と一致しない場合（既存の慣習で別名にしたい場合など）は明示的に確認する
3. 同名ファイルが既にある場合は上書きしてよいか確認する
4. 確認が取れたら書き込む

書き込み後、以下を伝える。

> 「SKILL.mdを`<path>`に保存した。実際に使う場面で意図通り発動するか、一度試してみることを推奨する。」

---

## 注意事項

- **質問は1問ずつ投げる**。複数の質問を一度に投げない
- **「やらないこと」は必ず聞く**。スコープ肥大化を防ぐための重要項目
- **descriptionにワークフロー要約を書かない**。トリガー条件（症状・状況）のみに絞る。処理手順を書くと、エージェントがdescriptionだけで判断して本文の分岐を読み飛ばす原因になる
- **具体例は1つに絞る**。多言語対応や複数パターンの並立は品質を下げる
- **フローチャートは非自明な分岐にのみ**使う。単純な手順はリスト化する
- **既存のSKILL.mdに実質的な内容がある場合はこのスキルの対象外**。新規作成専用として案内する
- 本スキル自体の品質基準は `superpowers:writing-skills` の観点を踏襲しているが、サブエージェントによる圧力シナリオテスト（RED-GREEN-REFACTOR的なテスト運用）は本スキルのスコープ外とする
