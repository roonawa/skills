## 目的

顧客・タスク管理システム（C-HUB等）からコピーした「不具合報告＋修正内容」の文章を渡されたときに、次の一連の作業を毎回同じ手順・同じ品質・同じ体裁で実行するスキル。

- 「修正した」という報告を鵜呑みにせず、実際のコミット・実装を自分で読んで裏取りする
- 可能な限り、その修正を検知できる回帰テストを実際に**実行**する（無ければ新規作成する）
- そのテストが本当に不具合を検知できるかを、修正前の状態に一時的に戻して**実際に失敗させる**ことで証明する
- 結果を、毎回同じ視覚言語（デザイントークン）のHTMLレポートにまとめ、Artifactとして発行する
- 検証できなかった範囲・未回答の論点は、報告書側の文言をそのまま引き継ぎ、絶対に隠したり誇張したりしない
- 必ず、人間が手動確認を行うための再現手順を記載する

「テストコードを書いて」ではなく「この修正合ってる？テストして」と渡されたときに起動する。1回のやり取りで複数件（不具合A, B, C...）を連続して依頼されることも多いので、そのつど本フローを繰り返す。

## 想定する入力

だいたい次のような文章が渡される（全部揃っていなくてもよい）：

- 不具合の症状（画面名、対象データ、再現条件）
- 「【修正内容】」以下の、修正者自身による原因・対応内容の説明

指示文は「これもお願い」「こちらも同様に」のように短いことが多い——それは「直前と同じ手順で頼む」という意味なので、毎回このスキルの全ステップを省略せずに繰り返す。

## 全体フロー

```
1. 修正コミットの特定（git log --all -i --grep、キーワードは報告文から抽出）
   ↓
2. 実装を直接読んで裏取り（報告文の行番号・変数名・コメントと一致するか）
   ↓
3. 個別の主張を独立検証できるものは検証する（javap／DDL grep／横断grep等）
   ↓
4. テストを探す。無ければ、そのスタック規約に沿って最小限のテストを新規作成する
   ↓
5. 【最重要】修正前へ一時的にrevert→実行して失敗を確認→git checkoutで復元→再実行して成功を確認
   ↓
6. 既存テスト・モジュール全体への影響を確認
   ↓
7. 未検証・未回答・対象外の論点を洗い出す（報告文の文言を引き継ぐ）
   ↓
8. HTMLレポートを作成しArtifactとして発行（テンプレート: templates/report.html）
   ↓
9. チャットに要点とArtifact URLを短く報告
```

各ステップの詳細は以下。

---

## 1. 修正コミットの特定

報告文から検索キーワードを抜き出す：バグID（`BUG-XXX`, `task-XXXXXXXXXX-xxxxx`）、テーブル名・カラム名、クラス名・メソッド名、画面名の一部。

```bash
git log --all -i --grep="キーワード1" --grep="キーワード2" -E --oneline | head -20
```

- ヒットしなければキーワードを変えて何度か試す。それでも見つからなければ「見当たらない」と正直に報告し、他ブランチ（`git branch -a`、`git log origin/<branch>`）やstale pullの可能性を追加確認する。**「見つからない」を隠して話を合わせない。**
- 複数コミットに分かれている場合がある（本体修正＋レビュー指摘反映の追いコミット等）。`git log --all --grep` の結果は全部見る。
- `git show --stat <hash>` で変更ファイル一覧、`git show <hash> -- <path>` で個別ファイルの差分を見る。

## 2. 実装を直接読んで裏取りする

コミットメッセージやユーザーの報告文を信じるのではなく、**現在のHEADの実ファイルをReadで開いて**、報告文にある行番号・変数名・コメント文言と一致するか確認する。

- 報告文が「〇〇行目」と言っていたら、実際にその行を読む（コミット時点からズレていてもよい。現在のHEADで再確認する）
- 複数箇所の修正がある場合は全箇所を読む
- 関連する「前のバグ」（BUG-666→BUG-706→今回、のような系譜）が引用されていたら、その過去コミットも `git show` で見て文脈を掴む
- 一致しなければ、Pull漏れの可能性がある。Pullは勝手に実行せず、また断定せずに「一致しない」という事実だけを報告し、ユーザーに確認を仰ぐ。辻褄合わせの推測で埋めない。

## 3. 個別の主張を独立検証する

報告文中の技術的主張は、可能な限り自分の手で検証する。「書いてあるから正しい」で済ませない。代表的な検証手段：

| 主張の種類 | 検証方法 |
|---|---|
| 例外クラスの継承関係（Java） | `javap -classpath <jar> <FQCN>` |
| カラムにNOT NULL制約が無い | DDLファイルを `grep` して該当 `create table` を確認 |
| 「リポジトリ内に〇〇の使用例が0件」 | `grep -rn` で該当リポジトリ全体を検索 |
| 「A画面とB画面でロジックが同一」 | 両方のソースを実際に横に並べて比較 |
| SQLの計算結果 | 4節参照。実データが無理なら合成データで実行 |
| ライブラリの挙動 | 小さなスクリプト/REPLで実際に実行して確認 |

## 4. テストを探す。無ければ作る

まず既存テストを探す（`find`, `grep -rn "対象クラス名"`）。見つかったら**実際に実行する**（「テストがある」で終わらせない）。

無ければ、そのモジュールのスタック・既存の作法に沿って最小限の回帰テストを新規作成する。作法が分からなければ、同じディレクトリ内の他のテストファイルを読んで真似る。

### Java (Spring / Mockito / JUnit5)
- 対象フィールドが `protected` かつテストを同一パッケージに置けば、リフレクション無しで直接差し替えられる
- `@InjectMocks` + `@Mock` の組み合わせで依存Behaviorをモックし、狙った例外/戻り値を注入する
- そのモジュールに `src/test` が無い場合、pom.xmlの親に `spring-boot-starter-test` があれば依存関係としては使える（動かないのはテストが無いだけ）
- ローカルの `.m2` に無い自社ライブラリ（`dbflute-common`, `common`, `auth-core` 等）が原因でビルドが通らない場合、`shared-libs` 配下の各モジュールを先に `mvnw install` する
- Maven実行時は `JAVA_HOME` をJDK21の実パスに、`PATH` に `mvnw` かローカルMavenのbinを通す（PowerShellツールで実行。Bashツールにはmvnが無いことが多い）

### Vue 3 (`<script setup>`) / vitest
- `defineExpose()` を呼んでいないコンポーネントは、`wrapper.vm.<関数名>` で内部関数に直接アクセスできる（呼んでいる場合は公開された名前だけになる）
- `shallowMount` は子コンポーネントを自動でスタブするので、子コンポーネント個別のスタブ登録は基本不要
- 大きいページコンポーネント（数千行）をマウントすると重い。`it(..., 30000)` のように**個別タイムアウトを30秒程度**に伸ばす（既定5秒だと頻繁にタイムアウトする）
- 依存モジュール（`share`, `share/src`, `share/Date`, `share/polyfill`, `@/stores`, `vue-router`, `vue-i18n` 等）は import 文をひとつずつ確認し、実際に使われている**値**（型ではない）を全部モックする。エラーメッセージ「No "xxx" export is defined」が出たら順次追加すればよい
- 子コンポーネントがPiniaストアを直接 import している場合（`shallowMount` でも設定によって子のsetupが走ることがある）、`beforeEach` で `setActivePinia(createPinia())` しておくと安全
- モック対象の `build*Input` / `build*Payload` 系ヘルパーは、既定で `() => ({})` にすると引数の値が消えて検証できなくなる。**フィールドをそのまま透過するモック**（`(item) => ({ ...item })`）に置き換える

### C# (.NET / xUnit)
- `dotnet test` が可能。NuGetキャッシュ（`~/.nuget/packages`）に必要パッケージが無ければ取得できるか確認する
- 対象メソッドが `private static` でもソースを変更せず `MethodInfo`（リフレクション）で直接呼べる。テスト対象プロジェクトを `ProjectReference` で参照する専用テストプロジェクトを作る
- 既存にテストプロジェクトが無いモジュールが多い（デスクトップ帳票プラグイン等）。無ければ `dotnet new xunit` 相当の最小csprojを新規ディレクトリに作る

### 生SQL（DBFluteの外部SQLファイル等）
本番同等DBにネットワーク到達できないことが多い。その場合：
1. Dockerが動いているか確認（`docker ps`）。動いていなければ `Docker Desktop.exe` を起動して起動待ちする
2. **既存のコンテナに触らない**。名前を変えた使い捨てコンテナを別ポートで立てる（`docker run -d --name <一時名> -e POSTGRES_PASSWORD=... -p <別ポート>:5432 postgres:<version>`）
3. 実際のDDL（`database/DDL/*.sql`）から、そのSQLが参照するテーブル・カラムだけを抜いた最小スキーマを作る（型は実DDLに合わせる。想像で作らない）
4. 不具合の力学を再現できる合成データを設計する（例：0点選択肢を含む設問／含まない設問／全部0点の設問、のように「効くはずのケース」「効かないはずのケース」「境界ケース」を並べる）
5. 修正前のSQL文（`git show <parent>:<path>`で取得）と修正後のSQL文を、同じ合成データに対して両方実際に実行し、数値を比較する
6. Windows + Git Bash から `docker cp` を使うと稀にパス変換で失敗する。`cat file.sql | docker exec -i <container> psql -U ... -d ...` のように**標準入力経由で流し込む**方が安定する
7. 検証が終わったら使い捨てコンテナは必ず `docker rm -f` で削除する（既存の他コンテナは無事であることを `docker ps` で確認する）

いずれのスタックでも、テスト対象の関数・SQLが**実際に機能から呼ばれているか**（デッドコードでないか）を `grep` で確認しておく。

## 5.【最重要】revert → 失敗確認 → 復元 → 成功再確認

これがこのスキルの核。「テストが通った」だけでは、そのテストが本当にこの不具合を検知できる設計になっているかは分からない。**修正前の状態に戻すと本当に失敗するか**を実際にやって見せる。

1. `git status --short -- <対象ファイル>` で作業ツリーがクリーンなことを確認する（他の変更が紛れていないか）
2. Editツールで、報告文に書かれた「修正前」の状態を再現する最小の変更を加える（配列からキーを1個抜く、ループ範囲を1個に狭める、try-catchを外す、等）
3. テストを再実行し、**報告された症状と一致するメッセージで失敗すること**を確認する（`expected null to be ''` のように、期待値と実際値が意味的に症状と一致しているかまで見る）
4. `git checkout -- <対象ファイル>` で直ちに元に戻す
5. `git status --short -- <対象ファイル>` で差分が無いことを再確認する
6. テストを再実行し、成功することを確認する

この手順を経ていないテストは「回帰テストのように見えるだけのテスト」であり、レポートに「PASS」と書いてはいけない。逆に、この手順を踏んだテストは、たとえ新規作成した簡易なものであっても、修正者自身が書いたテストより説得力のある証拠になる。

## 6. 既存テスト・モジュール全体への影響を確認

- 同じテストファイル内の既存テスト、同じモジュールの他テストファイルも一緒に実行し、回帰が無いか確認する
- 可能ならモジュール全体の `compile` / `build` を通す
- DBやネットワークに依存する既存テスト（`ApplicationTests.contextLoads` 等）がこの環境で失敗するのは環境起因であり、対象の修正とは無関係——と決めつける前に、失敗理由（スタックトレース）を見て無関係であることを確認する

## 7. 未検証・未回答・対象外の論点を洗い出す

報告文には次のようなものが含まれていることが多い。これらは**検証できなかったなら検証できなかったと明記する**。都合よく省略しない：

- 「PT等の実機環境では未確認」
- 「〇〇のケースは該当データが無く未検証」
- 「施主判断が未回答」（回答次第でコミットをrevertする可能性がある、等）
- 「別課題として起票予定」の対象外事項

自分が追加で見つけた限界（例：DBに到達できないので合成データで代替した、テストは代表1クラスのみで全件は検証していない等）も同様に書く。

## 8. テスト担当者が手動確認を行うための再現手順を記載する（実機確認ができない場合は不要）

再現手順は、テスト担当者が手動で確認するための手順を明示する。自動テストだけでは確認できない場合や、実機での挙動を確認する必要があるため重要。
ここでは、テスト担当者が実機（PT環境）で手動で確認するための具体的な手順を記載する。
DB操作が必要であれば、SQL文や操作手順を明示する。画面操作が必要であれば、画面遷移や入力内容を具体的に記載する。

## 9. HTMLレポートを作成してArtifactとして発行する

`templates/report.html` を土台にする。Writeツールでファイルをコピーしてから中身を埋める（プレースホルダ `{{...}}` を全部実データに置き換える。埋め忘れを残さない）。

- **数値・ログは実際に実行した出力をそのまま貼る**。要約して作文しない。`pre.log` には実行結果をコピーする
- 施主判断待ち・重大な留保がある場合だけ `.decision-banner` を有効化する（無ければ削除する）
- 不具合の力学を図で見せた方が伝わる場合（連続コマの時間割グリッド、バグの系譜チェーン等）は、テンプレートに無い装飾要素を追加してよい。ただし装飾のための装飾は入れない（構造は内容を反映させる）
- 発行前に、Artifactツールを呼ぶ前提として `artifact-design` スキルの規約（ライト/ダークテーマ両対応、`body`に明示的な背景色、等）を守る。このテンプレート自体は両テーマ対応済みなので、色を追加する場合は既存の `--変数名` を再利用し、新しい生色を直接書かない
- favicon: これまでのシリーズでは実行系の確認レポートに🧪を使っている。トピックが大きく変わる場合のみ別の絵文字にする。同じレポートを再発行するとき（同じconversationでの更新）は同じfaviconを保つ
- title: 「〇〇修正テスト結果」のような、対象不具合が特定できる短い複合名にする（一覧に並んだときに区別できるように）

## 10. チャットへの報告

Artifactの発行後、チャットには短く要点だけ書く：

- 対象コミットのハッシュ・日付・作者
- 実施したこと（何を読んだか、何を実行したか、revert検証で何を確認したか）を箇条書き3〜6行程度
- 重大な留保（施主判断待ち等）があれば冒頭で目立たせる
- 新規作成したテストファイルは**未コミットのまま残す**ことと、そのパスを明記する（コミットするかはユーザー判断に委ねる。指示されない限りgit add/commitしない）
- Artifact URL(エビデンスとして出力したHTMLレポートファイル)を出力する

レポート本文で言えることをチャットで長々と繰り返さない。チャットは要約、詳細はArtifact側に書く。

## 注意事項

- **絶対にテスト結果を偽造しない**。実行できなかったものは「未実施」と書く。実行環境が無い（本番DB非到達等）ときは、代替手段（合成データ、ローカルDocker等）を試すが、それでも無理なら諦めて正直に書く
- **ユーザーの指示がない限りコミットしない**。新規テストファイルは untracked のまま提示する
- **一時的なrevert編集は必ず直後に `git checkout --` で戻す**。放置しない。戻した後に必ず「差分なし」をgit statusで確認する
- **リスクのある操作（Docker起動、既存コンテナの扱い等）は既存インフラを壊さないよう名前・ポートを分離する**。既存コンテナは削除・再起動しない
- 一度のやり取りで複数件を連続依頼されたときも、毎回0〜9の全ステップを省略しない（「これもお願い」＝「同じ手順で」の意味）
- 報告文の内容が古い/コード側と一致しない場合、pull漏れを最初に疑う。それでも解決しなければ正直に不一致を報告し、勝手に話を合わせない
- デザインはこのスキル専用の一貫した視覚シリーズとして扱う。レポートごとに配色・フォント・レイアウト方針を変えない（テンプレートの `--変数` は保つ。個別の飾りは追加可）
