・auto-inventory
メモリ（~/.claude/projects/<project>/memory/）の棚卸

・cause-repro
UAT不具合管理表のような自然言語で書かれた不具合の症状から実機での再現手順を明示する

・dev-test
ドキュメントがない根性案件で、ソースコードを基にテストケースを作らせる。自動化はやらない

・skill-skill
skill.mdを生成するskill

・spec-basic
仕様書、要件定義書を基に基本設計書を作らせる

・spec-detail
仕様書、要件定義書、基本設計書を基に詳細設計書を作らせる

・spec-rec
要件定義の壁打ちを基に要件定義書を作らせる

・spec-test
詳細設計書を基にテスト仕様書を作らせる

・text-execute
不具合報告と修正内容の両方を基に、修正の是非を自動化テストで検証する。

・test-strategy
要件定義書、詳細設計書を基にテスト戦略を作成する

・test-verify
不具合報告＋「修正内容」の文章を渡すと、実装コミットを特定してコードを裏取りし、回帰テストを実行（無ければ新規作成）、修正前に一時的に戻して実際に失敗することまで確認したうえで、結果をHTMLレポート（Artifact）にまとめる。

・uat-verify
不具合報告(UAT)と修正内容の両方を基に、修正の是非を自動化テストで検証する。また、おまけで実機での再現手順も追記する。

・wordpress-qa
Wordpress案件限定で、以下の流れを一気通貫に策定させる
品質リスク分析→QA観点整理→テスト戦略策定→自動化判断→CI生成方針策定→手動テスト定義→リリース判定基準

・xUnit
C#限定で、xUnit用の単体テストコードを生成させる。実装の再現ではなく仕様の検証に注力しているため、仕様変更に強い。
